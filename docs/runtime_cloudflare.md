# Runtime: Cloudflare Workers + Durable Objects

Fog has one production runtime: a public request Worker and a private state
Worker containing three SQLite-backed Durable Object classes.

## Worker topology

| Worker | Entry | Responsibility | Secrets |
| --- | --- | --- | --- |
| Request | `app/server.cloudflare.ts` | HTTP, session validation, canonical user routing, RPC error translation | `SESSION_SECRET`, directory-routing keyring |
| State | `app/server.state.ts` | User Data, Identity Directory, Account Home DOs and Alarms | Only secrets needed by external job adapters |

The request Worker binds `USER_DATA`, `IDENTITY_DIRECTORY`, and `ACCOUNT_HOME`
to the `fog-state` script. A client never provides a Durable Object ID or
partition key. The request Worker derives routing from the authenticated
canonical `userId`; credential-directory locators use HMAC and never contain
raw email/provider subjects.

The state config uses declarative `exports` with `storage = "sqlite"`. Do not
replace it with Wrangler's legacy `migrations` array.

## Local development

```bash
pnpm install
cp apps/web/.dev.vars.example apps/web/.dev.vars
openssl rand -base64 48
openssl rand -base64 48
pnpm dev
```

Use the first generated value for `SESSION_SECRET` and the second for
`DIRECTORY_ROUTING_SECRET_ACTIVE`.

`pnpm dev` runs:

```bash
wrangler dev \
  -c apps/web/wrangler.request.toml \
  -c apps/web/wrangler.state.toml \
  --persist-to apps/web/.wrangler/state
```

The first config is the primary Worker at `http://localhost:8787`; the state
Worker is secondary and reachable only through bindings. Wrangler executes the
request config's custom Vite build before startup. Both Workers share one
persist directory and Wrangler tears down the full session on SIGINT or startup
failure.

Both configs live next to `.dev.vars`, but the state config declares an empty
required-secret set. Wrangler therefore excludes the request-only keys from the
state Worker. Keep request secrets out of `[vars]`.

## Configuration files

| File | Purpose |
| --- | --- |
| `wrangler.request.toml` | Local primary request Worker and Vite custom build |
| `wrangler.state.toml` | Local state Worker, bindings, and DO class lifecycle |
| `wrangler.{request,state}.{stage}.toml.tpl` | Committed remote templates |
| `wrangler.{request,state}.{stage}.toml` | Ignored files generated by `cf:render` |

Generate cross-Worker binding types after changing either config:

```bash
pnpm cf:types
```

## Stage configuration and DNS

Pulumi manages the zone/custom-domain metadata only. It does not create
databases, Queues, or Durable Object namespaces.

```bash
pnpm --filter @repo/infra-cloudflare exec pulumi -C resources -s staging up
pnpm cf:render:staging
pnpm deploy:staging:dry
```

After both Workers have been deployed, apply the routes stack. Its config takes
the zone ID, hostname, and request Worker name directly; it does not read a
resources-stack reference.

```bash
pnpm --filter @repo/infra-cloudflare exec pulumi -C routes -s staging up
```

Repeat with `production` for production.

## Secrets

Set request secrets only on the request config:

```bash
openssl rand -base64 48
pnpm --filter @repo/web exec wrangler secret put SESSION_SECRET \
  --config wrangler.request.staging.toml

openssl rand -base64 48
pnpm --filter @repo/web exec wrangler secret put \
  DIRECTORY_ROUTING_SECRET_ACTIVE \
  --config wrangler.request.staging.toml
```

Repeat against `wrangler.request.production.toml` for production. Never set
these secrets on `wrangler.state.*.toml`.

`SESSION_SECRET` rotation invalidates every existing session immediately. Set
the replacement on the request Worker and verify an old cookie is rejected.

Directory routing uses an active/previous keyring:

1. Keep the current active key as `DIRECTORY_ROUTING_SECRET_PREVIOUS` and its
   generation as `DIRECTORY_ROUTING_GENERATION_PREVIOUS`. During the rotation
   window, add the previous secret name to the request config's
   `[secrets].required` and the previous generation to `[vars]`.
2. Generate and set the new active secret and generation.
3. Deploy the request Worker.
4. Run the operator-only checkpoint scan across every fixed directory bucket.
   Persist and resume the checkpoint; record scanned, moved, and conflict counts.
5. Confirm both directory mappings and Account Home reverse locators have zero
   references to the previous generation.
6. Remove the previous key/generation and deploy again.

Do not log canonical credentials, email addresses, SSO subjects, raw locators,
or secret-derived routing material.

## Deployment order and compatibility

Always deploy state first, request second:

```bash
pnpm cf:render:staging
pnpm deploy:staging:dry
pnpm deploy:staging
```

The aggregate command preserves that order. During rollout, state RPC handlers
must accept the request Worker's currently deployed contract as well as the new
contract. Remove an old RPC version only after the request deployment using it
has been retired. If the state deployment fails, do not deploy request. If
request fails, keep the backward-compatible state deployment and retry request.

## Schema migrations

Each DO class owns a `schema_migrations` table and performs forward-only,
idempotent lazy migrations during activation:

- `UserDataDurableObject`: profile/settings, AI connections, content, FTS,
  idempotency, export/deletion state, and persistent jobs.
- `IdentityDirectoryDurableObject`: credential mappings, reservations,
  reset/SSO primitives, and reconciler state.
- `AccountHomeDurableObject`: account summary, credential locators, saga state,
  and the authoritative non-PII tombstone/epoch.

Never assume every object has migrated immediately after deploy. Keep readers
compatible for the rollout window. A failed migration must roll back and retry
on the object's next activation.

## Alarm and reconciler incidents

User Data external-I/O/retention jobs are at-least-once. A job records its
attempt, next-run time, provider idempotency key, lease, owner token, and poison
reason. The mutation and earliest next-run lookup commit before `setAlarm`.

For an incident:

1. Tail the state Worker without logging PII.
2. Inspect job status, attempt, lease expiry, next-run time, and poison reason.
3. Let an expired lease be reclaimed; never force-complete a job under a
   different owner token.
4. Verify the downstream provider using the stored idempotency key before
   redriving.
5. Requeue poison work only after correcting the cause.
6. If alarm scheduling failed, invoke a normal operator input so the DO
   recalculates the earliest pending time and re-arms the Alarm.

Identity reservations are recovered by the Directory reconciler. Resume the
stable operation ID from its persisted fault point; do not create a replacement
operation or manually activate only one side of the saga.

## Export and deletion

Export is intentionally sequential per user. Resolve the authenticated
`userId`, stream bounded pages from that user's User Data DO, preserve a
checkpoint between pages, and finish one user before moving to another. Do not
construct cross-user SQL queries or bulk-load every object into memory. The
user-facing export use case/UI remains Issue #15.

Deletion starts by writing `deleting` and incrementing the authoritative epoch
in Account Home. Then tombstone all credential locators, confirm User Data
`deleteAll()`, purge directory mappings, and retain only the non-PII Account
Home tombstone/epoch/completion time. Every retry uses the same operation ID and
epoch. Never reactivate restored directory/user data whose epoch is older than
Account Home.

Password change remains Issue #11. Password reset and SSO link/unlink UI remain
Issue #12; only their storage/primitive contracts exist here.

## PITR policy and staging smoke

Cloudflare PITR is remote-only and object-scoped. Run this smoke only against
authenticated disposable staging objects:

| Class | Restore allowed | Required check |
| --- | --- | --- |
| User Data | Yes | Compare current Account Home tombstone/epoch before and after restore, then reconcile |
| Identity Directory | Yes | Compare current Account Home tombstone/epoch before and after restore, then reconcile |
| Account Home | No | Operator/admin tooling must reject the class before any restore call |

For User Data or Identity Directory:

1. Create a disposable staging account and record its current Account Home
   tombstone/epoch.
2. Through the operator-only wrapper, record
   `ctx.storage.getCurrentBookmark()`.
3. Write a recognizable disposable change and obtain a newer bookmark.
4. Request `onNextSessionRestoreBookmark(oldBookmark)`, abort/restart the
   object, and confirm only that object returned to the expected state.
5. Re-read current Account Home. If its tombstone/epoch changed or marks the
   account deleted, do not expose the restored data; run reconciliation.
6. Restore the newer bookmark to undo the smoke and repeat the Account Home
   check.
7. Record stage, class, opaque object identifier, bookmarks, timestamps, and
   outcome without PII.

PITR is not supported by local workerd. Never substitute another storage product's restore commands
for Durable Object PITR.
