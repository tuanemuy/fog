# Testing

Tests are classified along two axes: **layer × purpose**. By separating a fast unit layer from an integration layer that verifies OCC behavior against a real DB, we keep the day-to-day development loop light while continuously covering adapter pitfalls.

## Test layer classification

### Unit (`pnpm test:unit`)

- **Targets**: domain-layer + application-layer logic (the pure parts), plus the pure logic behind `apps/web`'s screens — formatters, schemas, list state, and presentation-layer helpers.
- **Dependencies**: the only fakes kept on hand are the four under `packages/core/src/application/__tests__/fakes/`: `FakeIdGenerator` (a deterministic UUIDv7 stream), `FakeLogger` (a recording Logger), `FakePasswordHasher` (a cheap deterministic digest), and `trippingIdentityGateway` (an `IdentityGateway` whose every entry throws). `Clock` can simply be passed to the usecase as a freestanding `now: Date`, and repository-style fakes are intentionally absent (the judgment being that imitating transaction / OCC with an in-memory fake is no substitute for integration). We don't aim to exhaustively cover application-layer logic with fakes; behavior verification is pushed onto integration tests.
- **Aim**: invariants of the domain layer (value object / entity / the event-type roster), error-code branching, and the behavior of pure application-layer helpers like the constraint checks in `createDeliveryTuning`.
- **Speed**: a few to a dozen-or-so milliseconds. `vitest.config.unit.ts` excludes `**/*.integration.test.ts` and `**/*.dom.test.{ts,tsx}`, so nothing here touches a DB or a DOM.
- **Naming**: `**/__tests__/<target>.test.ts` (e.g. `entity.test.ts`, `eventTypeRoster.test.ts`, `tuning.test.ts`).

### DOM (`pnpm test:unit`)

- **Targets**: the rendering branches of `apps/web`'s components — which of two shapes a branch draws, and where a link leads. Three kinds are drawn: `"use client"` islands, server components that are pure functions of their props, and `async` data-loading leaves, the last by `await`ing the component and rendering the element it returned. Routes, loaders, `renderServerComponent` (Flight), hydration and CSS are **not** drawn: reaching them takes the Flight boundary and yields no branch these three do not already reach.
- **Dependencies**: `jsdom`, `@testing-library/react` and its `@testing-library/dom` peer — and nothing else: no `setupFiles`, no vite plugin. A component carrying a `Link` or reading `useRouter` is drawn through the shared harness `apps/web/app/components/__tests__/renderWithRouter.tsx`, which builds a memory-history router with stub routes for the paths under test and, after the render, feeds every internal `href` on the page back through `router.matchRoutes` so that a `to` with no stub behind it goes red instead of silently building a URL nothing serves.
- **Aim**: "what does this branch draw". Assert **both sides** of a branch — that the dead step is not a link *and* that the live one leads to the expected URL; asserting only the first stays green when every step is drawn dead. An assertion that something is **absent** takes the same string from the present side first (`getByText` finds it there, `queryByText` answers `null` inside the absent row), because a misspelled query answers `null` whether or not the branch works. Queries are accessibility-first (`getByRole` / `getByText`) plus `closest("a")` / `getAttribute("href")`. No snapshots — a diff whose meaning is buried in class names stops claiming that a branch does anything.
- **Norm**: **when you add or change a rendering branch, add the DOM test with it.**
- **Naming**: `apps/web/app/**/__tests__/<target>.dom.test.{ts,tsx}`. The unit project drops that suffix and this project's `include` claims it, rooted at `apps/web/app/`. **A file outside that root runs nowhere** — a correctly named test under `packages/core/` or `apps/web/scripts/` is dropped from the unit project by its suffix and claimed by no project here, so it reports nothing rather than failing. When you start putting DOM tests in another directory, add it to `vitest.config.dom.ts`'s `include` in the same change.
- **Limits**:
  - Nothing enforces the Norm mechanically; it is a review discipline. The branches actually covered are the ones the five files named here cover — `apps/web/app/components/document/__tests__/{documentNotFound,documentBoard,documentFeed}.dom.test.tsx`, `apps/web/app/components/documentEdit/__tests__/newDocumentFeed.dom.test.tsx` and `apps/web/app/components/timeline/__tests__/memoEntry.dom.test.tsx` — and no more.
  - What `renderWithRouter`'s href check verifies is that the href built from `to` / `params` hits a path in the harness's stub tree — nothing more. The stubs reproduce neither the `/` route's `validateSearch` nor any search serialization production configures, and the check reads only the pathname, so an asserted href's search string is still the URL the harness built. Change how production serializes search and these tests stay green. Anchors whose href does not start with `/` are not checked at all.
  - For "the document is not there" the covered path is the **outer** of `DocumentFeed`'s two `isNotFoundError` catches — the one around the document reads — and that one **only**. (The inner one, around the topic-name resolution, is covered too, but it draws a different thing: the topic link falls back to a generic label while the document stays on the page.) The other way to the missing-document screen — the route refusing an undisplayable id (`isDisplayableDocumentId` → no feed → `DocumentNotFound`) — has a unit test for the predicate, but the connection from that predicate to what is drawn is still manual testing.
  - "The topic is not there" is a wider gap, because `TopicNotFound` is shared by two screens and has **four** ways in. Two of them are feed catches: `NewDocumentFeed`'s `isNotFoundError` catch (P-09) and `TopicDetailFeed`'s (P-07). Only the first is covered — there is no `topicDetailFeed.dom.test.tsx`, so P-07's catch is drawn by no test here even though it is the same shape of catch. The other two are the routes refusing an undisplayable id (`isDisplayableTopicId` → no feed → `TopicNotFound`, in both `topics_.$topicId.tsx` and `topics_.$topicId_.documents.new.tsx`); as on the document screen those have a unit test for the predicate, and the connection from it to what is drawn is manual testing.

### Integration (`pnpm test:integration`)

- **Targets**: the D1 adapter implementation, adapter × application integration, OCC (optimistic concurrency control) scenarios, and the Durable Object machinery — schema migrations, the job runner, the Outbox relay, and the queue handlers that consume what the relay publishes.
- **Dependencies**: a real Workers isolate (Miniflare), in two projects — an in-memory D1 binding (`env.DB`) for the D1 suites, SQLite-backed Durable Objects for the DO suites.
- **Aim**: realistically verify batch rollback, `ConflictError("OPTIMISTIC_LOCK_FAILURE")` — its one source is the matched-row count a DO store reads back from its conditional `UPDATE` (`userSettingsRepository.save`) — and the claim / publish / finalize passes a DO's `alarm()` runs over `jobs` and `outbox_events`. The `_occ_guard` CHECK on the D1 side is the same mechanism, but the `PendingBatch` that translated it has no caller left, so no `ConflictError` arises there; what `occGuard.integration.test.ts` pins is the abort of `db.batch()` and the guard table returning to empty.
- **Speed**: roughly 10× unit. Day to day you run `pnpm test:unit`, and run `pnpm test:integration` when you touch an adapter or before a PR.
- **Naming**: `**/__tests__/<target>.integration.test.ts` (e.g. `loginWithPassword.integration.test.ts`, `helpers.integration.test.ts`, `outboxRelay.integration.test.ts`).

### Property-based (fast-check)

- **Targets**: value-object invariants, entity state transitions, and edge cases that fail under random input.
- **Dependencies**: `fast-check` (devDependency).
- **Aim**: automatically verify properties such as "if the post-trim length is 1-140 it is always accepted", "`complete` → `reopen` returns to the original active state", and "change status is idempotent for the same input" over hundreds of samples.
- **When to use**: boundary values (TitleEmpty / TitleTooLong), state transitions (active ⇄ completed), invariants (monotonic increase of `version`). Keep custom arbitraries to the bare minimum, and use combinations of `fc.string()` / `fc.integer()` for anything that can be written that way.
- **Naming**: `**/__tests__/<target>.property.test.ts` (e.g. `valueObject.property.test.ts`, `entity.property.test.ts`).

## Fake policy

Currently the following four are the only fakes kept under `packages/core/src/application/__tests__/fakes/`:

- **`FakeIdGenerator`** — returns deterministic ids by embedding a counter into a UUIDv7 template. The output is shaped to pass the adapter-side rehydration validation (`IdGenerator.validate`), so it won't fail format checks even in round-trip tests through storage. The starting number can be fixed via the constructor, and the prefix is `ffffffff-...` so that generated ids sort after the test's fixed rows (they come after the `01950000-...` series when sorting by `(createdAt, id)`).
- **`FakeLogger`** — merely records each `info` / `warn` / `error` call into an `entries` array. Use `byLevel("error")` to extract them and assert on the observability behavior of a usecase or of the presentation-layer error middleware.
- **`FakePasswordHasher`** — a cheap deterministic digest, so integration suites don't pay a real key derivation per registration / login (the real algorithm is covered by the WebCrypto adapter's own unit tests, and a test that genuinely needs a PBKDF2 round trip injects `createPbkdf2PasswordHasher({ iterations })` at a low count instead). Its output deliberately does **not** embed the plaintext: `registerWithPassword.integration.test.ts` reads the stored value back and asserts "no plaintext reached `credential_mappings.password_verifier`" against it, and a fake that prefixed the password would make that assertion hold by accident. That is the scope of the claim — it is the one suite that reads the fake's own output for the plaintext. `loginWithPassword.integration.test.ts` makes the same assertion about the same column against the **real** hasher's output, and `getCurrentUser.integration.test.ts` asserts the plaintext is absent from the projected view rather than from the stored row.
- **`trippingIdentityGateway`** — an `IdentityGateway` whose every entry throws through a caller-supplied `trip`, with `overrides` supplying the entries a given suite does expect to be called. It is written as a total implementation rather than a partial cast, so a method added to the port turns these suites red instead of leaving one entry silently unguarded. The unit suites that assert "this usecase / this presentation helper reaches no Durable Object" are built on it (`loginWithPassword.test.ts`, `logout.test.ts`, and the three suites under `apps/web/app/presentation/__tests__/`).

The `FakePasswordHasher` case is the criterion for adding a fake at all: the port is a pure CPU-bound transform whose real implementation is separately unit-tested, and the fake preserves the one property the tests read off it. `trippingIdentityGateway` does not meet that criterion and is not an exception to it — it is a tripwire that fails the moment every method of the port is walked, not a stand-in for the gateway's behavior, and no test reads a value off it. Fakes for repositories, the UoW, and the Clock are intentionally not kept.

- Even if you fake repositories / the UoW in-memory, you can't reproduce the essential adapter-derived behaviors like a `transactionSync` rollback or `ConflictError("OPTIMISTIC_LOCK_FAILURE")`. Logic tests for application services are better done at the integration layer (real SQLite), where they cover actual harm.
- `Clock` is just a `() => Date`, so it's enough to construct a constant like `new Date(0)` within a test and pass it to the usecase / domain. There's no need to fake it as a port object.
- A DOM test's `vi.mock` of a module is not a fake in this sense and never joins the roster above: it replaces a module the component under test imports (a request-scoped entry point, a usecase module), not an implementation of a port.

## Real DB test (integration) policy

- `pnpm test:integration:cf` runs every integration suite inside a **Workers isolate** via `vitest-pool-workers`. `vitest.config.integration.ts` is a thin delegation: it lists two projects and nothing else. The pool configuration lives in each of them — `vitest.config.d1.ts` (a Miniflare D1 binding) and `vitest.config.do.ts` (SQLite-backed Durable Objects and a test entry for `main`) — because `@cloudflare/vitest-pool-workers` configures `main` and `durableObjects` per pool, that is, per project.
- `setupFiles` belongs to the **D1 project only**: `packages/core/src/adapters/d1/__tests__/setup.ts` applies the migrations and runs the `beforeEach` TRUNCATE. The DO project has none — a Durable Object is identified by its name, so its suites get per-test isolation by addressing a fresh locator (`nextUserId()` / `nextBucket()` in `packages/core/src/adapters/cloudflare/__tests__/helpers.ts`).
- `createTestContainer()` (`packages/core/src/application/identity/__tests__/helpers.ts`) returns a production-equivalent request container wired to the two Durable Object bindings. It belongs to the **DO project**: the identity usecases have no D1 dependency left. The same module holds the seeding helpers those suites need — `inUserDataStorage` / `inDirectoryStorage` reach a Durable Object's SQLite directly, which is how the states no production caller can create yet (`credentialVersion` disagreement, a change in flight, a lockout, two locator generations) are set up. Adding an RPC that writes them instead would break "a table with no write path is adapter-owned".
- The `afterEach` in that setup file asserts `_occ_guard` is empty after every test of the D1 project, and it is the only automated check that the OCC guard's CHECK leaves no rows behind (the dedicated libSQL-side test was deleted with that runtime in PR #39). Do not add a blanket `DELETE FROM _occ_guard` to the cleanup — it would silently mask exactly the schema regression this assertion exists to catch.
- File names are `*.integration.test.ts`. `vitest.config.unit.ts` excludes this pattern and runs only unit tests.
- The suffix alone is not enough to get a file run: each project selects its tests through an explicit `include` allow-list of directories. `vitest.config.d1.ts` covers `packages/core/src/adapters/d1/`; `vitest.config.do.ts` covers `packages/core/src/adapters/cloudflare/`, `packages/core/src/application/` and `apps/web/app/worker/cloudflare/`. A new `*.integration.test.ts` outside both allow-lists is excluded from the unit suite by its suffix **and** claimed by neither project — it silently runs nowhere. When you add integration tests under a new directory, decide which project it belongs to — a D1 binding or a Durable Object — and add the directory to that project's `include` in the same change. `vitest.config.integration.ts` has no `include` of its own; adding one there changes nothing.
- OCC in a Durable Object is a conditional `UPDATE` guarded on `version` whose matched-row count is read back through `updateMatchedRow`: zero matched rows raise `ConflictError("OPTIMISTIC_LOCK_FAILURE")` right there, and nothing above it retries. A test reaches that branch by handing `save` a `version` that is already stale — reading and writing inside one `run` callback cannot produce it, because the callback is fully synchronous and a Durable Object is single-threaded, so two such callers serialize and both succeed. No test races two OCC-guarded writes today; in one that did, which caller loses is not fixed, so keep the assertions loose enough to accept either.
- Asserting that a projection **did not run** takes a sentinel, not a before/after comparison of the row. `upsertSearchEntry` keeps the rowid and writes back the same title, body and timestamp, so re-running it on unchanged data leaves the row byte-identical — a comparison passes whether or not the projection ran, and `version` and the revision count do not move on a no-op either. Write a value only the projection owns (`search_entries.body`) from the test, run the operation, and assert the value survives: re-running would overwrite it with the entity's own text. `markSearchEntry` / `PROJECTION_MARK` in `packages/core/src/application/memo/__tests__/helpers.ts` are the shipped form.

## Property-based policy

- fast-check is adopted mainly to verify **boundary values + invariants**.
- It's useful for property checks such as each domain value-object factory, entity state transitions (`complete` → `reopen` returns to the active state, the idempotency where repeating `rename` with the same value doesn't increment version, etc.), and the idempotency of set-style usecases.
- Before writing a custom arbitrary, consider whether existing `fc.string()` / `fc.integer()` plus `filter` suffice. Don't make the domain overly dependent on fast-check.

## Timeout / flakiness

- The configs currently use Vitest's default timeouts. Unit tests finish in a few hundred milliseconds; if an integration test needs a longer ceiling, set `testTimeout` in the project config that owns it — `vitest.config.d1.ts` or `vitest.config.do.ts` — rather than slowing the unit suite. A `test` option on `vitest.config.integration.ts` does not reach either project: in projects mode the root config only lists them. The same holds for `vitest.config.ts`, which lists `vitest.config.unit.ts` and `vitest.config.dom.ts` and carries no `test` options of its own.
- The D1 adapter has **no** built-in transient retry, so there is no retry backoff to tune. `SQLITE_BUSY` / `SQLITE_LOCKED` are connection-level conditions the D1 binding handles upstream of the adapter, and whatever still reaches the caller is a signal, not a retry candidate (`packages/core/src/adapters/d1/repositories/helpers.ts`).
- No suite asserts on elapsed time. A Miniflare timing is a local number, not a production one, so a threshold on it turns ordinary CI variance into a red build whose failure reads as broken behavior. When a decision needs the order of magnitude, take the measurement through an existing suite as a one-off, and record the number **with the conditions it was taken under** wherever that decision lives — the suite keeps asserting behavior only. The limit that comes with it: such a number is a snapshot and nothing re-takes it when the code moves.
- Two integration tests run work concurrently: `loginWithPassword.integration.test.ts` overlaps two failing logins on one credential and holds both at a fake hasher's barrier until each has read the abuse counters, which makes the interleaving deterministic rather than raced, and `registerWithPassword.integration.test.ts` fires two registrations of one address but asserts only that exactly one wins, because which one is not fixed. Everywhere else the Durable Object suites race nothing: contention over a row is expressed by seeding its lease and `owner_token` state and then running one pass, not by firing two callers. Nothing races two OCC-guarded writes yet — that is the one shape with two possible outcomes (see "Real DB test (integration) policy" above), so a new test of that kind should assert loosely enough to accept both before reaching for per-test `test.extend` / `vi.useFakeTimers`.

## Coverage

Coverage numbers are not enforced. Rules of thumb:

- **Domain**: aim for ~100%. Logic is local and easy to fully cover, and a missing test translates directly into a broken invariant.
- **Application + Adapter (integration)**: per "representative path". Provide at least one for each route, such as OCC success / OCC failure, same-tx placement of the outbox row, per-row isolation in the Outbox relay (one row that cannot be published backs off without touching the others), and the race of a concurrent delete. For usecase orchestration coverage, prioritize confirming it "ran on a real DB" via integration over exhaustive coverage with fakes.
- **Frontend**: rendering branches are held by the DOM tests (the DOM section above is the authority on which ones, and where the cover stops); the pure logic behind the screens — formatters, schemas, list state, presentation-layer helpers — is held by unit tests (the Unit section above); what is left, such as form validation as the reader meets it and how the optimistic UI looks, stays manual testing.
