# Testing

Tests are classified along two axes: **layer × purpose**. A fast unit layer and a jsdom layer run in Node; an integration layer runs inside a Workers isolate against real SQLite-backed Durable Objects. Keeping the day-to-day loop on the first two keeps it light while the third covers the adapter pitfalls — OCC, transactions, the Alarm, the relay.

## Test layer classification

### Unit (`pnpm test:unit`)

- **Targets**: domain-layer + application-layer logic (the pure parts), plus the pure logic behind `apps/web`'s screens — formatters, schemas, list state, and presentation-layer helpers.
- **Dependencies**: the fakes under `packages/core/src/application/__tests__/` (see "Fake policy"). `Clock` is passed to the usecase as a freestanding `now: Date`; repository-style fakes are intentionally absent (imitating transaction / OCC with an in-memory fake is no substitute for integration). Application-layer logic is not exhaustively covered with fakes; behavior verification is pushed onto integration tests.
- **Aim**: invariants of the domain layer (value objects, entities, `EventId`), the delivery roster (`jobKinds.test.ts` / `rosterGrep.test.ts`: the `jobs.kind` and `event.type` values in the sources are exactly the ones `spec/async/index.md` lists), error-code branching, and the behavior of pure application-layer helpers like the constraint checks in `createDeliveryTuning`, the rotation's pure functions (`judgeCanonicalRow`, `isRetired`, `confirmDeletion`) and the job runner's `failureOutcome`.
- **Speed**: a few to a dozen-or-so milliseconds. `vitest.config.unit.ts` excludes `**/*.integration.test.ts` and `**/*.dom.test.{ts,tsx}`, so nothing here touches a DB or a DOM.
- **Naming**: `**/__tests__/<target>.test.ts` (e.g. `entity.test.ts`, `rosterGrep.test.ts`, `tuning.test.ts`). Repository-wide scans are unit tests too: `lint/banList.test.ts` (the error-class roster), `packages/core/src/adapters/cloudflare/__tests__/rotationCheckpointWriters.test.ts` (the one writer of `rotation_checkpoints`), `packages/core/src/adapters/cloudflare/__tests__/storageWriters.test.ts` (no `INSERT` / `UPDATE` / `DELETE` / `REPLACE` statement outside `packages/core/src/adapters/`; reads, and a statement assembled from pieces, are outside it), `lint/designTokens.test.ts` (`styles/tokens.css` carries exactly the names and values of `spec/design/tokens.md`'s code blocks; nothing under `styles/` has a `var()` fallback or reads an undefined custom property; no raw color, and no raw length, typeface, weight, line-height, radius, shadow or transition outside tokens.md's allowlist, appears in the hand-written CSS or in the utilities Tailwind generates from `apps/web`'s sources; a projected token is read by its utility name, not as `(--token)`; outside `components/ui`, no variant or utility styles an element other than the one carrying it. The mock HTML, a TSX `style` attribute, and a property a primitive inherits from its wrapper because it does not set it itself are outside it) and `apps/web/app/presentation/__tests__/adapterImports.test.ts` (no module under `apps/web/app` but the entry points — `server.cloudflare.ts` and `worker/cloudflare/` — imports a concrete adapter; the scan reads `from "@repo/core/adapters/…"` text, so a dynamic `import()` or a re-export through another package is outside it).

### DOM (`pnpm test:unit --project dom`)

- **Targets**: the rendering branches of `apps/web`'s components — which of two shapes a branch draws, and where a link leads. Three kinds are drawn: `"use client"` islands, server components that are pure functions of their props, and `async` data-loading leaves, the last by `await`ing the component and rendering the element it returned. Routes, loaders, `renderServerComponent` (Flight), hydration and CSS are **not** drawn: reaching them takes the Flight boundary and yields no branch these three do not already reach.
- **Dependencies**: `jsdom`, `@testing-library/react` and its `@testing-library/dom` peer. One `setupFiles` entry, `apps/web/app/components/__tests__/domSetup.ts`, which raises `@testing-library/react`'s `asyncUtilTimeout` from 1 s to 5 s — a ceiling, not a wait, for components that chain two or three server-function round trips through transitions under the full parallel run. `globals: true` is set only so the library registers its `afterEach` cleanup; test bodies import from `vitest` explicitly. A component carrying a `Link` or reading `useRouter` is drawn through the shared harness `apps/web/app/components/__tests__/renderWithRouter.tsx`, which builds a memory-history router with stub routes for the paths under test and, after the render, feeds every internal `href` on the page back through `router.matchRoutes` so that a `to` with no stub behind it goes red instead of silently building a URL nothing serves.
- **Aim**: "what does this branch draw". Assert **both sides** of a branch — that the dead step is not a link *and* that the live one leads to the expected URL; asserting only the first stays green when every step is drawn dead. An assertion that something is **absent** takes the same string from the present side first (`getByText` finds it there, `queryByText` answers `null` inside the absent row), because a misspelled query answers `null` whether or not the branch works. Queries are accessibility-first (`getByRole` / `getByText`) plus `closest("a")` / `getAttribute("href")`. No snapshots — a diff whose meaning is buried in class names stops claiming that a branch does anything.
- **Norm**: **when you add or change a rendering branch, add the DOM test with it.**
- **Naming**: `apps/web/app/**/__tests__/<target>.dom.test.{ts,tsx}`. The unit project drops that suffix and this project's `include` claims it, rooted at `apps/web/app/`. **A file outside that root runs nowhere** — a correctly named test under `packages/core/` or `apps/web/scripts/` is dropped from the unit project by its suffix and claimed by no project here, so it reports nothing rather than failing. When you start putting DOM tests in another directory, add it to `vitest.config.dom.ts`'s `include` in the same change.

A DOM test's `vi.mock` of a module replaces the request-scoped entry point or usecase module the component imports, never a port implementation, and is not a fake in the sense of "Fake policy".

### Integration (`pnpm test:integration`)

- **Targets**: the Durable Object adapters and the usecases that run through them — the two DO classes, their stores, OCC, the schema gate and lazy migration, the job runner and every `jobs.kind` handler, the Outbox relay, the operator entries, the mapping-key and encryption-key rotations, and the request-side gateways' stub selection.
- **Dependencies**: a real Workers isolate (Miniflare) via `@cloudflare/vitest-pool-workers`, one project: `vitest.config.do.ts` (SQLite-backed `USER_DATA` / `IDENTITY_DIRECTORY` bindings, an `EVENTS_QUEUE` producer with its consumer settings, three state-Worker secrets as literal bindings, and `packages/core/src/adapters/cloudflare/__tests__/testWorker.ts` as `main` so `runInDurableObject` hands back the same instances the bindings address). `vitest.config.integration.ts` only lists that project; it has no `test` options of its own.
- **Aim**: realistically verify the writes only the adapter can produce — `ConflictError("OPTIMISTIC_LOCK_FAILURE")` from the matched-row count `updateMatchedRow` reads back, same-transaction placement of the outbox row and the FTS5 projection, the claim / publish / finalize passes of `alarm()`, terminal mode and the cleanup stages, fail-closed on a schema ahead of the code, the transfer's CAS predicates and checkpoints.
- **Speed**: roughly 10× unit. Day to day you run `pnpm test:unit`, and run `pnpm test:integration` when you touch an adapter or before a PR.
- **Naming**: `**/__tests__/<target>.integration.test.ts`. The suffix alone is not enough to get a file run: `vitest.config.do.ts` selects tests through an explicit `include` of `packages/core/src/adapters/cloudflare/`, `packages/core/src/application/` and `apps/web/app/worker/cloudflare/`. A new `*.integration.test.ts` outside those directories is excluded from the unit suite by its suffix **and** claimed by no project — it silently runs nowhere. When you add integration tests under a new directory, add it to that `include` in the same change.

## Fake policy

The fakes live in `packages/core/src/application/__tests__/fakes.ts` (which also re-exports the five gateway tripwires under `fakes/`), and that is the roster:

- **`FakeIdGenerator`** — returns deterministic ids by embedding a counter into a UUIDv7 template. The output is shaped to pass the adapter-side rehydration validation (`IdGenerator.validate`), so it won't fail format checks even in round-trip tests through storage. The starting number can be fixed via the constructor, and the prefix is `ffffffff-...` so that generated ids sort after the test's fixed rows.
- **`FakeTokenGenerator`** — a deterministic stream for the opaque tokens (`callerToken`, reset tokens) a usecase mints, so a unit test can assert what was handed to the gateway.
- **`FakeLogger`** — records each `info` / `warn` / `error` call into an `entries` array. Use `byLevel("error")` to extract them and assert on the observability behavior of a usecase or of the presentation-layer error middleware.
- **`FakePasswordHasher`** — a cheap deterministic digest, so unit suites don't pay a real key derivation (the real algorithm is covered by the WebCrypto adapter's own unit tests, and the integration suites inject `createPbkdf2PasswordHasher({ iterations: 1000 })` through `createTestContainer()` instead). Its output deliberately does **not** embed the plaintext.
- **`trippingIdentityGateway`** and **`tripping{Memo,Knowledge,Search,Trash,Export}Gateway`** — gateways whose every entry throws through a caller-supplied `trip`, with `overrides` supplying the entries a given suite does expect to be called. Each is written as a total implementation rather than a partial cast, so a method added to the port turns these suites red instead of leaving one entry silently unguarded. The unit suites that assert "this usecase / this presentation helper reaches no Durable Object" are built on them: the identity usecase suites through `packages/core/src/application/identity/__tests__/unitContainer.ts` (`recordingGateway` / `trip` / `makeContainer`), the memo suites through `packages/core/src/application/memo/__tests__/memoContainer.ts`, the knowledge / search / export suites directly, and on the web side `apps/web/app/presentation/__tests__/{currentUser,session,errorResponseMiddleware}.test.ts`, `presentation/ai/__tests__/handlers.test.ts` and `presentation/export/__tests__/handler.test.ts`.

The `FakePasswordHasher` case is the criterion for adding a fake at all: the port is a pure CPU-bound transform whose real implementation is separately unit-tested, and the fake preserves the one property the tests read off it. The tripwires do not meet that criterion and are not an exception to it — a tripwire fails the moment every method of the port is walked, is not a stand-in for the gateway's behavior, and no test reads a value off it. Fakes for repositories, the UoW, and the Clock are intentionally not kept.

- Even if you fake repositories / the UoW in-memory, you can't reproduce the essential adapter-derived behaviors like a `transactionSync` rollback or `ConflictError("OPTIMISTIC_LOCK_FAILURE")`. Logic tests for application services are better done at the integration layer (real SQLite), where they cover actual harm.
- `Clock` is just a `() => Date`, so it's enough to construct a constant like `new Date(0)` within a test and pass it to the usecase / domain. There's no need to fake it as a port object.

## Real DB test (integration) policy

- `pnpm test:integration:cf` runs every integration suite inside a **Workers isolate** via `vitest-pool-workers`. The pool configuration lives in `vitest.config.do.ts`, because `@cloudflare/vitest-pool-workers` configures `main` and `durableObjects` per project.
- There is no `setupFiles` and no per-test truncation: a Durable Object is identified by its name, so the suites get isolation by addressing a fresh locator — `nextUserId()` / `uniqueEmail()` in `packages/core/src/adapters/cloudflare/__tests__/helpers.ts`. Identity Directory buckets are shared across a file (the same 16 bucket names for every email), so a bucket-wide assertion compares against the live count rather than a constant, and a test that deploys a commitment or a keyring to a bucket (`overrideDirectoryEnv`) restores it afterwards.
- `createTestContainer()` / `registerTestUser()` / `bucketOfEmail()` (`packages/core/src/adapters/cloudflare/__tests__/testContainer.ts`) return a production-equivalent request container wired to the two Durable Object bindings with a cheap PBKDF2, and address the bucket a canonical email lives in. `helpers.ts` holds the seams the suites reach storage through — `inUserDataStorage` / `inDirectoryStorage` (a Durable Object's SQLite and `DurableObjectState`, via `runInDurableObject`), `overrideDirectoryEnv` / `overrideUserDataPlan` (a bucket's `env`, a User Data object's migration plan), `twoGenerationKeyring` / `commitmentJsonFor` (the rotation suites' second generation). Seeding a state no production caller can create yet — `credentialVersion` disagreement, a change in flight, a lockout, a copy in a second generation, a `poison` row — is done through these seams. Adding an RPC that writes them instead would break "a table with no write path is adapter-owned". Memo suites use `packages/core/src/application/memo/__tests__/memoFixtures.ts` (`post` / `postAt` / `setPostedAt` / `searchHits` / `readMemoRow`).
- OCC in a Durable Object is a conditional `UPDATE` guarded on `version` whose matched-row count is read back through `updateMatchedRow`: zero matched rows raise `ConflictError("OPTIMISTIC_LOCK_FAILURE")` right there, and nothing above it retries. A test reaches that branch by handing `save` a `version` that is already stale — reading and writing inside one `run` callback cannot produce it, because the callback is fully synchronous and a Durable Object is single-threaded, so two such callers serialize and both succeed. No test races two OCC-guarded writes; in one that did, which caller loses is not fixed, so keep the assertions loose enough to accept either.
- Asserting that a projection **did not run** takes a sentinel, not a before/after comparison of the row. `upsertSearchEntry` keeps the rowid and writes back the same title, body and timestamp, so re-running it on unchanged data leaves the row byte-identical — a comparison passes whether or not the projection ran. Write a value only the projection owns (`search_entries.body`) from the test, run the operation, and assert the value survives: re-running would overwrite it with the entity's own text.
- The pool fires a due Alarm at once: a row whose `next_run_at` is in the past may already have run by the time the test reads it. Assert "pending or already done" for such rows, or pull `next_run_at` back and call `runDurableObjectAlarm` yourself.

## Timeout / flakiness

- The configs use Vitest's default timeouts. Unit tests finish in a few hundred milliseconds; if an integration test needs a longer ceiling, set `testTimeout` in `vitest.config.do.ts` rather than slowing the unit suite. A `test` option on `vitest.config.integration.ts` does not reach the project: in projects mode the root config only lists them. The same holds for `vitest.config.ts`, which lists `vitest.config.unit.ts` and `vitest.config.dom.ts` and carries no `test` options of its own.
- No suite asserts on elapsed time. A Miniflare timing is a local number, not a production one, so a threshold on it turns ordinary CI variance into a red build whose failure reads as broken behavior. When a decision needs the order of magnitude, take the measurement through an existing suite as a one-off, and record the number **with the conditions it was taken under** wherever that decision lives — the suite keeps asserting behavior only. Such a number is a snapshot and nothing re-takes it when the code moves.
- The Durable Object suites race nothing: contention over a row is expressed by seeding its lease and `owner_token` state and then running one pass, not by firing two callers. `signupSaga.integration.test.ts` fires two registrations of one address but asserts only that exactly one wins, because which one is not fixed. Interleavings inside one RPC (a row moved between two probes, a credential change landing between s3 and s4) are reproduced by seeding the intermediate state or by a delegating stub wrapper (`lookupGeneration.integration.test.ts`), never by timing.

## Limits — what no suite can pin

- The atomicity of a `transactionSync` under a failure in the middle (a rollback's failure injection). The suites pin what each transaction writes together; the rollback itself is the runtime's.
- `rotate-encryption`'s read / write interleaving (a row deleted and re-reserved between the chunk's read and its `UPDATE`) and the s4 re-read interleaving of the mapping-key transfer. The guard predicates are pinned as statements (`rotateEncryption.integration`, `transfer.test.ts`), not as races.
- A Durable Object reset in the middle of a `remap-chunk`: the absence of the s6 checkpoint is pinned for an entry-level refusal only.
- The export size ceiling (`EXPORT_MAX_SOURCE_BYTES`, 24 MiB) is pinned by integration; a browser cannot produce the input.
- The reservation TTL inequality of `spec/testcases/recovery/sagaRecovery.md` row 26 is an operational value, not a testable behavior.
- `apps/web/app/components/settings/__tests__/aiConnectionsList.dom.test.tsx` went red once under the full parallel run (PH-09A) and passed on every rerun; `domSetup.ts`'s 5 s ceiling is the response. A second occurrence is a bug report, not a retry.

| Integration only (Workers pool: Durable Objects) | `pnpm test:integration` (alias of `pnpm test:integration:cf`) |
| DOM only (the jsdom project inside the unit run) | `pnpm test:unit --project dom` |

## Coverage

Coverage numbers are not enforced. Rules of thumb:

- **Domain**: aim for ~100%. Logic is local and easy to fully cover, and a missing test translates directly into a broken invariant.
- **Application + Adapter (integration)**: per "representative path". Provide at least one for each route, such as OCC success / OCC failure, same-tx placement of the outbox row, per-row isolation in the Outbox relay (one row that cannot be published backs off without touching the others), and a saga's terminal mode. For usecase orchestration coverage, prioritize confirming it "ran on a real DB" via integration over exhaustive coverage with fakes.
- **Frontend**: rendering branches are held by the DOM tests (the DOM section above is the authority on which ones, and where the cover stops); the pure logic behind the screens — formatters, schemas, list state, presentation-layer helpers — is held by unit tests (the Unit section above); what is left, such as form validation as the reader meets it and how the optimistic UI looks, is manual testing (`spec/manual-tests/`).
