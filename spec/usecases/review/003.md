# ユースケース設計レビュー 003（ゼロベース）

- 対象: `spec/usecases/*.md`（identity / memo / knowledge / search / trash / export）
- 照合資料: requirements.md（特に 4.5）、scenario/ 全ファイル、pages/index.md、ADR-001〜006、domains/*.md
- 観点: トレーサビリティ（全操作カバー / AI 非公開領域の非公開維持）、命名、DTO 完全性、アーキテクチャ適合性、エラー網羅性、単一責任、ドメイン設計との整合（メソッド実在・シグネチャ一致 / 競合・レース排除方式の一貫性）

## 結論

**問題なし**

以下を確認したうえで、実装時に確実に手が止まる実質的問題は検出されなかった。

- 全シナリオ（S-AC / S-TL / S-DT / S-SE / S-TR / S-AI / S-ST）と全画面（P-01〜P-14）の操作がいずれかのユースケースに対応し、requirements 4.5 の AI 公開動詞 10 種と AI 公開ユースケースが 1:1 に対応する。域外の責務（セッション・OAuth プロトコル・差分計算・表示制御）の分界も明記どおり
- AI 非公開領域（ハードデリート・ゴミ箱・履歴・ロールバック・IncludingTrashed 読み取り）は、AI に配線される全ユースケースの読み取り経路が `findById` / `listActiveByIds` 系（active / Live のみ）に閉じており、出力 DTO（検索結果の `sourceOfDocumentIds` / `sourceMemoIds` を含む）にもゴミ箱内 ID の露出経路がない
- 参照される全ドメインメソッド・ポート（`TopicTrashService.trashTopicSet` / `restoreTopicSet`、`RestorePolicy.decideDocumentRestore`、`HardDeletePolicy.expandTargets`、`DocumentPatch.create` / `apply`、各リポジトリの userId スコープ付きメソッド等）が domains/*.md に実在し、シグネチャ・戻り値・エラー契約が一致する
- 競合処理は方式が一貫している: 人間 UI の編集競合は `expectedVersion` 入力 + 正常応答 `result: "conflict"`（editMemo / editDocument 同構造）、AI 編集は UoW 内読み直し + OCC、トピック配下へのドキュメント出現レース（createDocument / restoreDocument の restoreAlone・selectDestination）はトピック touch による OCC 直列化で統一。ハードデリート系（hardDeleteTrashItem / emptyTrash / pruner）の no-op 続行・重複除去規約も一貫
- シナリオ異常系（空本文、パッチ不一致・曖昧一致、changeReason 省略、出典メモ / トピック不正時の全体失敗、trashed への AI 操作の NotFound、リセットトークン期限切れ、登録有無の秘匿、OCC 競合）はすべてエラーケース表に対応がある
