# ユースケース設計レビュー 002

ゼロベースレビュー。対象: spec/usecases/{identity, memo, knowledge, search, trash, export}.md。
照合先: requirements.md（特に 4.5）、scenario/ 全ファイル、pages/index.md、adr/001〜006、domains/*.md。

総評: トレーサビリティ（シナリオ・ページ・requirements 4.5 の全操作）、AI 非公開領域の構造的排除（ゴミ箱・履歴・ハードデリート、`sourceOfDocumentIds` / `sourceMemoIds` のファンアウトによる ID 非露出まで含む）、AI 動詞の 1:1 ディスパッチ、ドメインのポート実名・シグネチャとの整合は高水準で成立している。対応が必要な問題は以下の 5 件。

---

## 1. 【重要度: 高】restoreDocument の復元経路に createDocument と同じレース排除がなく、「trashed トピック配下に active ドキュメント」が復元経由で再発し得る

- 対象: `usecases/trash.md` restoreDocument（restoreAlone 分岐、selectDestination の `kind: "existing"` 分岐）
- 内容: `usecases/knowledge.md` createDocument は、並行する `trashTopic` とのレース（listActiveByTopic によるセット削除対象確定とドキュメント作成のすれ違い）を「同一 UoW 内でトピックを OCC トークン付きで読み touch する」設計判断で構造的に排除している。一方 restoreDocument は、所属トピックの現況確認（処理フロー手順 4 の `findByIdIncludingTrashed`）が UoW 外にあり、restoreAlone の UoW 内ではドキュメントしか再取得しない。selectDestination の既存トピック分岐も UoW 内で `TopicRepository.findById` は行うが touch しない。
- 失敗シナリオ: restoreDocument がトピック存命を確認 → 並行する trashTopic が配下 active ドキュメントを確定（復元前のドキュメントはまだ trashed なので含まれない）してトピックをセット削除・コミット → restoreDocument がコミット。結果、trashed トピック配下に active ドキュメントが生まれ、不変条件 1（knowledge.md）に違反し、AI からも `getDocument` で見える孤立ドキュメントになる。createDocument で閉じたレースと同型であり、方式の一貫性が崩れている。
- 対応案: restoreAlone / selectDestination(existing) の UoW 内で復元先トピックを OCC トークン付きで読み、createDocument と同方式で touch（`TopicRepository.save`）して直列化する。restoreWithTopic 分岐はトピック自身を OCC 付きで save するため対応不要。

## 2. 【重要度: 高】maintainSearchIndex の stamp-first 冪等処理と「失敗時は Outbox のリトライに乗る」が矛盾している

- 対象: `usecases/search.md` maintainSearchIndex 処理フロー手順 1 とエラーケース表
- 内容: 手順 1 は `idempotencyStore.markProcessed(eventId)` を先に行い（stamp-first）、`alreadyProcessed: true` なら ack して終了する。一方エラーケース表は `SearchIndexUnavailable` / `EmbeddingFailed` を「retryable。Outbox のリトライに乗る」とする。stamp-first でクレーム後にハンドラーが失敗すると、再配信時には `alreadyProcessed: true` となり処理がスキップされるため、リトライは実質機能せず、インデックス更新が失われる（対象が検索から恒久的に消える / 更新されない）。テンプレート（docs/backend_implementation_example.md）も「副作用とスタンプを一緒にロールバックしたい場合は UoW 内で markProcessed する」パターンを併記しており、外部ストア書き込みである本 consumer は素の stamp-first と両立しない。
- 対応案: 本 consumer は upsert / remove が完全冪等なので、スタンプをハンドラー成功後に行う（stamp-after-success。重複配信は冪等上書きで吸収）か、失敗時にクレームを解放する契約を明記する。いずれにせよ「失敗 → リトライで回復する」経路が実際に成立するよう仕様を修正すること。

## 3. 【重要度: 中】memo の ActorView `{ kind; name: string }` が UserActor から構築できず、knowledge の Actor 射影と不整合

- 対象: `usecases/memo.md` 共通事項 ActorView、`usecases/knowledge.md` の actor 射影
- 内容: memo は `ActorView = { kind: "user" | "aiClient"; name: string }` と定義するが、identity の `UserActor` は `userId` しか持たず、`kind: "user"` のときの `name` の出所が存在しない（ユーザー表示名という属性は User エンティティにもない）。knowledge 側は `{ kind: "user" } | { kind: "aiClient"; clientName: string }` の判別可能ユニオンで、user に名前を要求しない。同じ「誰が」の表示射影が 2 ドメインで形も実現可能性も食い違っており、memo 側は実装時に必ず手が止まる。
- 対応案: memo の ActorView を knowledge と同形（`{ kind: "user" } | { kind: "aiClient"; clientName: string }`）に統一する。「あなた / クライアント名」の表示文言は presentation の責務とする。

## 4. 【重要度: 低】maintainSearchIndex の契機イベント表に `topic.created` / `topic.updated` がなく、入力バリデーションと矛盾する

- 対象: `usecases/search.md` maintainSearchIndex 入力DTO（`eventType` は「下表の契機イベントのいずれか」）と契機イベント表
- 内容: knowledge は `topic.created` / `topic.updated` も Outbox に発行する（domains/knowledge.md イベント表）。表は `topic.trashed` / `topic.restored` / `topic.archived` / `topic.unarchived` を「何もしない」と明記する一方、`topic.created` / `topic.updated` を列挙しておらず、入力バリデーションの規定どおりならこれらはデコード失敗 → リトライ → 隔離（quarantine）に落ちる。identity 系イベントを consumer に配るかどうかも含め、購読対象の境界が未定義。
- 対応案: `topic.created` / `topic.updated` を no-op 行として表に追加する（トピック名は index に持たず query 時に解決するため no-op で正しい）か、consumer が購読するイベント種別の集合を明記して未購読イベントは relay 側で届かないことを規定する。

## 5. 【重要度: 低】search の入力DTOがドメイン型 `Pagination` を直接受けており、DTO 規約・他ユースケースと不整合

- 対象: `usecases/search.md` search 入力DTO `pagination: Pagination`
- 内容: 各ファイルの共通事項は「DTO のフィールドはプリミティブ」（ブランド VO・ドメイン型を露出しない）を規約とし、`usecases/trash.md` listTrash は `page: number` / `limit: number` で受けて内部で `Pagination` を構築している。search だけ入力に `domain/common/pagination.ts` の型をそのまま置いており、presentation からの受け渡し形が二様になる。
- 対応案: listTrash と同様に `page` / `limit`（プリミティブ + 範囲バリデーション）で受け、ユースケース内で `Pagination` を構築する形に揃える。

## 問題なしと確認した観点（要点のみ）

- トレーサビリティ: S-AC-01〜07 / S-TL-01〜07 / S-DT-01〜09 / S-SE-01〜03 / S-TR-01〜05 / S-AI-01〜06 / S-ST-01〜02、P-01〜P-14 の全操作にユースケースが対応。requirements 4.5 の AI 公開動詞 11 個は全て実体ユースケースと 1:1 対応し、`get` / `delete` の種別ディスパッチも presentation 層の責務として完結している
- AI 非公開: ハードデリート・ゴミ箱・履歴・ロールバック・IncludingTrashed 読み取りを含むユースケースはすべて ★ で AI 側に配線されず、検索結果・出典 ID 経由のゴミ箱内 ID 露出もファンアウト再インデックスで防がれている
- ドメイン整合: 呼び出されるポートメソッド（`listActiveByIds` / `listSourceLinksByMemos` / `listByIds` / `TrashQueryPort.*` 等）はすべてドメイン定義に実在し、シグネチャ（userId 第一引数・Versioned 返却）とも一致。編集競合は editMemo / editDocument とも「正常応答 conflict + ConflictView + expectedVersion 再送」の同一方式で一貫（上記 1 のレース排除の非一貫のみ例外）
- エラー網羅: シナリオ異常系（空本文、変更理由必須、パッチ不一致、出典メモ不正で全体失敗、認証情報の非特定応答、登録有無の秘匿等）はいずれも対応するエラーケースを持つ
- 単一責任: updateTopic の合成・restoreDocument の 3 分岐はいずれも上流（ドメイン設計・ADR-001）が定めた単位であり、混在とは判断しない
