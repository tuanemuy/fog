# ユースケース設計レビュー 001

対象: spec/usecases/*.md（identity / memo / knowledge / search / trash / export）
照合: requirements.md（特に 4.5）、scenario/*、pages/index.md、adr/001〜006、domains/*.md

トレーサビリティの確認結果（問題なしの範囲）: requirements 4.5 の AI 動詞 11 種（search / get / list_topics / recent_memos / post_memo / update_memo / create_topic / update_topic / create_document / edit_document / delete）はすべてユースケースに対応があり、AI 非公開領域（ハードデリート・ゴミ箱・履歴・ロールバック・エクスポート・identity 全般）はすべて ★（人間UI専用）または内部ワーカーに限定されている。シナリオ S-AC / S-TL / S-DT / S-SE / S-TR / S-ST / S-AI の各操作もユースケースでカバーされている。処理フローで参照する振る舞い・ポートメソッド名はドメイン設計（domains/*.md）に実在し、シグネチャの齟齬は検出しなかった。

以下、対応が必要な問題点のみを重要度順に挙げる。

## 1. [高] 編集競合（version）の扱いが memo と knowledge で不一致

- 対象: `spec/usecases/memo.md`（editMemo）、`spec/usecases/knowledge.md`（editDocument）
- 問題: 同じシナリオ要件（S-TL-04 / S-DT-05「他者編集の警告 → そのまま保存」）に対して設計が食い違っている。
  - editMemo は入力 `expectedVersion`、不一致時は**正常応答** `result: "conflict"` + `ConflictView`（`currentBody` / `currentVersion` / `latestRevision` = 誰が・いつ）を返す。
  - editDocument は入力 `baseVersion`、不一致時は **`ConflictError("OPTIMISTIC_LOCK_FAILURE")`** を投げるのみ。
  - editDocument の `ConflictError` には再実行に必要な現在の `version` も「誰が編集したか」も含まれず、UI は警告表示・再試行のために `getDocument`（+ 必要なら `listDocumentRevisions`）を追加で呼ぶことになる。この必要手順はどこにも書かれていない。
  - フィールド名も `expectedVersion` / `baseVersion` と同一概念に別名が付いている。
- 修正提案: どちらかの方式に統一する。推奨は memo 方式（競合は業務上の正常フローであり、警告表示に必要な情報を一往復で返せる）。editDocument を `result: "conflict"` + ConflictView（currentVersion・currentTitle/currentBody・latestRevision の actor/changeReason/createdAt）を返す形に改め、フィールド名も `expectedVersion` に揃える。ConflictError は「判定通過後 save までのレース」用に限定する（editMemo と同じ構造）。

## 2. [高] AI 動詞 get / delete の種別ディスパッチが設計上完結していない

- 対象: `spec/usecases/memo.md`（get / delete）、`spec/usecases/knowledge.md`（getDocument / trashDocument / trashTopic）
- 問題: requirements 4.5 の `get` はメモ/ドキュメント、`delete` はメモ/ドキュメント/トピックを単一動詞で扱うが、ユースケースは種別ごとに分かれている。memo 側 delete に「種別ディスパッチはプレゼンテーション（MCPツール）層の責務」と注記があるだけで、**どうやって種別を判別するか**（ツール入力に種別フィールドを持つのか、ID から解決するのか）がどこにも定義されていない。ID は不透明文字列であり、種別指定なしでは presentation はディスパッチできない。`get` に至っては注記自体がない。
- 修正提案: ユースケース設計（または presentation 設計への引き継ぎ事項として明記）で、MCP / REST の入力スキーマに判別子を定める。例: `get` は `{ type: "memo" | "document"; id }`、`delete` は `{ type: "memo" | "document" | "topic"; id }` とし、presentation が type で対応ユースケースへルーティングする旨を memo.md / knowledge.md 双方の該当ユースケースに記載する（search 結果の `type` と同じ語彙を使う）。

## 3. [中] listDocumentRevisions が全リビジョンの全文を返す（memo の履歴設計と不整合・ペイロード過大）

- 対象: `spec/usecases/knowledge.md`（listDocumentRevisions）
- 問題: memo は「履歴一覧はメタのみ（listMemoRevisions）+ 差分用の二点全文取得（diffMemoRevisions）」に分離しているのに対し、knowledge は履歴一覧の `DocumentRevisionView` に `title` / `body`（全文スナップショット）を全件含める。`DocumentBody` は最大 1,000,000 文字であり、リビジョン数 × 全文の一覧応答は現実的でない。同じ「履歴一覧 + 二点差分」（S-TL-05 / S-DT-06、P-05 / P-10）の要件に対して構造が割れている。
- 修正提案: memo と同じ分割にする。listDocumentRevisions はメタ（revisionNumber / actor / changeReason / createdAt）のみを返し、`diffDocumentRevisions`（二点の全文 + メタ）を新設する。ロールバック確認表示に単一リビジョン全文が要るなら diff ユースケースの単点利用または findRevision 相当の読み取りで賄う。

## 4. [中] 出力DTO の日時型が knowledge だけ異なる

- 対象: `spec/usecases/knowledge.md`（全ユースケース）、他ファイルとの整合
- 問題: memo / identity / search / trash の出力DTOは日時を `Date` で定義しているのに対し、knowledge のみ `string`（ISO 8601）で定義している。同一プロジェクト内で DTO の日時表現が割れており、実装時に境界（シリアライズ位置）がぶれる。
- 修正提案: どちらかに統一する（共通事項に「出力DTOの日時は Date とし、シリアライズは presentation の責務」等を明記し、knowledge を合わせるのが変更量最小）。

## 5. [低] maintainSearchIndex の入力DTO が topic 系イベントと矛盾

- 対象: `spec/usecases/search.md`（maintainSearchIndex）
- 問題: 契機イベント表には `topic.trashed` / `topic.restored` / `topic.archived` / `topic.unarchived`（処理は「何もしない」）が列挙されているが、入力DTOの `targetId` は「`MemoId` または `DocumentId`」と定義されており、TopicId が来るケースと矛盾する。consumer が topic 系イベントを購読しない（relay の購読設定で除外する）のか、受けて no-op するのかも判別できない。
- 修正提案: `targetId` の型注記に TopicId を加えて「topic 系イベントは no-op」と揃えるか、そもそも consumer の購読対象から topic 系イベントを外す旨を明記して表から削る。

## 6. [低] 人間UIの検索結果に表示する「所属トピック名」の解決手段が未定義

- 対象: `spec/usecases/search.md`（search）
- 問題: P-11 / S-SE-01 は結果ごとに「所属トピック」を表示するが、`SearchResultItemDto` は `topicId` のみを返す。人間UIがトピック名をどう解決するか（listTopics の結果と突き合わせる等）がどこにも書かれていない。AI 向けには事実データ（ID）のみで正しいが、人間UI経路の表示要件が宙に浮いている。
- 修正提案: 「人間UIのトピック名解決は presentation が listTopics（includeArchived: true）の結果と突き合わせる」旨を search ユースケースに注記するか、人間UI専用の射影としてトピック名を付与する方針を明記する。

## 7. [低] createDocument と trashTopic の並行競合でソフトデリート済みトピック配下に active ドキュメントが残り得る

- 対象: `spec/usecases/knowledge.md`（createDocument / trashTopic）
- 問題: createDocument は `TopicRepository.findById` でトピックの Live を確認するが、トピックの version には触れない（save しない）。そのため trashTopic の `listActiveByTopic`（セット削除対象の確定）と createDocument の insert が並行すると、確認をすり抜けた active ドキュメントが trashed トピック配下に生まれ得る。この状態はゴミ箱・一覧のどの経路でも想定されておらず、注記もない。
- 修正提案: 実装上の防御（同一 UoW での直列化・トピック行の共有ロック相当・DB 制約等）をアダプター/ユースケースいずれの責務とするかを明記する。少なくとも「この競合は許容し、発生時は◯◯で回復する」等の設計判断を createDocument に注記する。
