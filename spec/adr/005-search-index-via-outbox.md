# ADR-005 検索インデックスの更新方式

## ステータス

Superseded（Issue #19、2026-07-28）

このADRは判断履歴として本文を保持する。現行の規則は [Search domain](../domains/search.md)、[search usecase](../usecases/search.md)、[DB設計](../database/index.md)、および [.thread/19/adr.md](../../.thread/19/adr.md) を参照する。検索はUser Data Durable Object内のSQLite FTS5単独とし、本体変更とtransaction-scoped projectionを同期commitする。非同期配送基盤は使わず、Alarmは外部I/Oとretentionの永続jobだけに使う。

## コンテキスト

ハイブリッド検索（キーワード + ベクトル）はメモ・ドキュメントの本文からインデックス（転置インデックス相当の全文検索と埋め込みベクトル）を維持する必要がある。埋め込み生成は外部API呼び出しを伴い、書き込みトランザクション内で同期実行すると投稿の快適さ（要件: 直接操作は人間にとっても快適であること）を損なう。

## 決定

検索インデックスの更新は、ドメインイベント（memo/document の作成・更新・削除・復元）を Outbox 経由で consumer が受け取り、非同期に行う。テンプレートの Outbox / relay / consumer 基盤をそのまま使う。

- 書き込みユースケースはエンティティ永続化とイベント登録のみを行う（同一トランザクション）
- consumer がイベントを受けてインデックス更新（埋め込み生成を含む）を実行する
- 配信は at-least-once・順序保証なしのため、インデックス更新は冪等に設計する（対象IDの最新状態を読み直して upsert / delete する）

## 検討した代替案

- **書き込みトランザクション内で同期更新** — 外部API（埋め込み生成）の遅延・障害が投稿の成否に直結する。不採用
- **定期バッチで全件再インデックス** — 反映遅延が大きく「さっきメモした内容をAIに探させる」体験を損なう。補助（修復用）としては有用だが主方式にはしない

## 影響

- 検索結果には短い反映遅延があり得る（投稿直後は検索にヒットしない場合がある）。recent_memos が直近の文脈把握を補う
- consumer は冪等な upsert / delete で実装する。イベントペイロードは対象IDのみを運び、本文は処理時に最新を読み直す（古いペイロードによる巻き戻りを防ぐ）
- ソフトデリート・ハードデリート・復元もイベントとして流し、インデックスから除去・再登録する
