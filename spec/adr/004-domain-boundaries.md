# ADR-004 ドメイン境界の切り方

## ステータス

承認済み

## コンテキスト

fog の三層モデル（メモ / ドキュメント / トピック）と、横断機能（検索・ゴミ箱・エクスポート・認証/認可）をどのドメイン境界で切るかを決める必要があった。

## 決定

6ドメインに分割する: identity / memo / knowledge / search / trash / export。

- **memo と knowledge を分ける**: メモは「時系列・追記型・非構造」、ドキュメント/トピックは「主題・編集型・構造化」で、ライフサイクルも不変条件も異なる。出典リンクは knowledge 側が `MemoId` をID参照で持つ
- **topic と document は knowledge にまとめる**: 「ドキュメントは必ずトピックに属する」「トピック削除は配下セット削除」という強い整合性要件があり、同一ドメイン内のほうが不変条件を表現しやすい
- **search / trash / export は独立ドメイン**: いずれも memo・knowledge を横断する関心事で、どちらか一方に置くと依存が歪む。エンティティは持たず、値オブジェクト・ドメインサービス・ポートが中心
- **identity に認証・AIクライアント認可・ユーザー設定を集約**: 操作主体（Actor）と権限スコープの定義は全ドメインの前提となるため一箇所に置く

## 検討した代替案

- **メモ・ドキュメント・トピックを1つの「ノート」ドメインにまとめる** — 境界は減るが、性質の異なる2モデル（追記型と編集型）の不変条件が混ざり肥大化する。不採用
- **topic を独立ドメインにする** — トピック削除と配下ドキュメントのセット削除・セット復元の不変条件がドメインをまたいでしまう。不採用
- **trash をドメインにせず各ドメインのユースケースに分散** — 保持期限・復元規則・「AIから見えない世界」という一貫した規則が分散し、規則の置き場が曖昧になる。横断ルールの単一の置き場として独立させた
- **検索を memo / knowledge それぞれの機能にする** — メモ・ドキュメント横断の単一全文検索という要件に反して入口が分かれる。不採用

## 影響

- ドメイン間参照はすべてID参照となり、集約境界が保たれる
- trash / search / export はエンティティを持たない薄いドメインになる（ポートとサービスが中心）
- ソフトデリート状態そのものは memo / knowledge の各エンティティのライフサイクル状態として持ち、trash は規則と横断操作のみを担う
