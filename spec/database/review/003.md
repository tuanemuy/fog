# DB設計レビュー 003

- 対象: spec/database/index.md
- 方式: ゼロベースレビュー（過去レビューは参照していない）
- 照合対象: spec/domains/*.md、spec/usecases/*.md、spec/adr/001〜006、docs/backend_implementation_example.md（adapter / schema / UoW）

## 結論

問題なし。

実装時に確実に手が止まる、またはデータ破壊につながる実質的な問題は検出されなかった。

## 確認した観点（すべて充足）

- 永続化先の網羅: 全エンティティ（User / AiClientConnection / Memo / MemoRevision / Topic / Document / DocumentRevision / SourceLink）と永続化を要する VO に対応テーブルがある。trash / search / export がテーブルを持たないことは ADR-004 と整合。セッション・OAuth トークンのスコープ外宣言は identity.md と一致
- 型・制約のドメイン整合: 各直和型（users の認証方式、memos / documents / topics / ai_client_connections のライフサイクル、リビジョンの Actor）の CHECK はドメインの判別可能ユニオンと 1:1 対応。三値論理も確認済み（nullable カラムの単独 CHECK は NULL 時に通過し、テーブル制約側の IS NULL / IS NOT NULL で網羅されるため穴がない）
- 正規化: リビジョン・出典リンクが親から導出可能な `user_id` を持たない設計は、読み取り経路（親 JOIN / サブクエリ）が全ポート契約でスコープ済みであることを確認。`actor_client_name` の非正規化はドメイン仕様（表示用スナップショット、S-AI-04）どおり
- インデックス: usecases/*.md に現れる全クエリパターン（タイムライン双方向カーソル・アンカー読み、ゴミ箱一覧 / 期限切れ列挙、出典リンク双方向逆引き、トピック配下一覧、SSO / email 解決、接続一覧、リビジョン取得、エクスポート全件読み、indexer 専用読み取り）に対応インデックスまたは PK があることを確認
- FK・UNIQUE・CHECK と ADR の整合: `documents.topic_id` に FK を張らない判断は ADR-001 と一致。source_links の「アプリ層消去が一次・FK カスケードは defense-in-depth」は ADR-003 と一致。`(document_id, memo_id)` PK、`(memo_id, revision_number)` / `(document_id, revision_number)` の一意制約は履歴線形性・重複排除の最終防衛線として妥当
- UoW 実行順序と SQL の整合: メモハードデリート時の `deleteSourceLinksByMemo` を documents 側 JOIN に限定する注記（memos 側 JOIN だと同一 UoW 内で既に削除済みのため 0 行更新になる罠）が明記済み。挿入順（親 insert → リビジョン / リンク insert）は FK 即時検査と整合。D1 PendingBatch のフラッシュ順・`_occ_guard` による OCC abort、libSQL 対話 tx の双方で破綻しないことを確認。`ExpectedVersion` トークン方式（読み取り時の値で WHERE）は moveToTopic → restore のような多段遷移 + 単一 save でも正しく機能する

## 対応不要の軽微な所見（参考。修正必須ではない）

- `outbox` の説明にある「payload は対象 ID のみ（ADR-005）」は memo / knowledge イベントに関する規則であり、identity イベント（`authMethod` / `retentionDays` を含む）はこの限りではない。payload は TEXT / JSON のため実装は止まらない
- `users.email` / `password_reset_tokens.token_hash` はカラム UNIQUE と名前付き UNIQUE インデックスが二重定義に読める。実装ではどちらか一方でよい
- export の `updatedAt`（最新リビジョンの日時）を `memos.updated_at` / `documents.updated_at` から取ると restore 等で進んだ値になる。厳密には各リビジョンテーブルの最大リビジョンの `created_at` から導出する（既存インデックスで可能。スキーマ変更不要）
