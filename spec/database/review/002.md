## 問題点

### 1. [中] `deleteSourceLinksByMemo` の userId スコープ実装が memos JOIN だと必ず no-op になる（孤児リンク残存 = ADR-003 違反）

`source_links` は `user_id` を持たず、index.md は「読み取りの userId スコープは `documents`（**または memos**）との JOIN で担保する」と両論併記している（source_links の節）。しかしメモのハードデリートのオーケストレーション順序は、memo.md・index.md とも

1. `listSourceLinksByMemo` で影響ドキュメント確定
2. `MemoRepository.hardDelete`（メモ本体 + 全リビジョン消去）
3. `DocumentRepository.deleteSourceLinksByMemo(userId, memoId)`

であり、手順 3 の時点で **memos の当該行は同一 UoW 内で既に削除済み**（libSQL の interactive tx でも、D1 の PendingBatch の実行順でも同じ）。したがって手順 3 の DELETE を

```sql
DELETE FROM source_links WHERE memo_id = ?
  AND EXISTS (SELECT 1 FROM memos m WHERE m.id = memo_id AND m.user_id = ?)
```

のように **memos 側 JOIN でスコープすると常に 0 行更新の no-op** になり、出典リンクが消えずに残る。共通方針どおり FK カスケードは一次担保ではない（PRAGMA 接続依存・D1 バッチ順依存）ため、defense-in-depth も効かない環境では孤児リンクが恒久残存し、ADR-003（ハードデリート後はリンクごと消え痕跡を残さない）に反する。0 行更新は「冪等な no-op」として正常扱いされる契約のため、テストでも気づきにくい。

対応: index.md の source_links の節に、**`deleteSourceLinksByMemo` の userId スコープは documents 側 JOIN（`document_id IN (SELECT id FROM documents WHERE user_id = ?)`）で行うこと（memos 側 JOIN は本体消去後に実行されるため不可）** を明記する。読み取り系の「documents または memos」併記も、消去系だけは documents 側に限定する旨を分ける。
