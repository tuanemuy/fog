# ゴミ箱 テスト

## 概要

このドキュメントはゴミ箱（ソフトデリート済み項目の一覧・復元・完全削除・空にする・保持期限による自動削除）に関するマニュアルテストの手順書です。

対応シナリオ: `spec/scenario/trash.md`（S-TR-01〜05）
対応画面: P-12 ゴミ箱（`/trash`）、P-13 設定（`/settings`、保持期限の変更）
関連: ADR-001（所属トピックがハードデリート済みのドキュメントの復元）、ADR-003（ハードデリート時の出典リンク消去）

## 前提条件

### 環境

- アプリケーションが起動しており、ブラウザからアクセスできる
- テスト用アカウントでログイン済み（例: `trash-test@example.com`）
- ゴミ箱の保持期限は既定値（30日）に設定されている
- TC-13（自動削除）・TC-23・TC-24（保持期限まわり）では、次の2つの操作手段がテスト環境に用意されていること。**保持期限切れ項目のハードデリートは、そのユーザーの Durable Object に張られた `purge-trash` ジョブ（Alarm）が実行する**ので、常駐ワーカーの手動起動という手段は存在しない
  - **期限切れの状態を作る手段** — 対象ユーザーの Durable Object へ、削除日時（`trashedAt`）が過去のゴミ箱項目を直接投入する（DO 単位のシード投入）か、時計を巻き戻すのに相当する手段
  - **`purge-trash` ジョブを待たずに走らせる手段**（Alarm の強制発火に相当する手段）

  **どちらも実体は #38（運用ドキュメント）が定める。** 手段が用意できない環境では各ケースの該当手順を対象外とし、実行記録の備考に記録する

### テストデータ

以下の呼称でデータを準備する。作成手順は「事前準備」を参照。

| 呼称 | 内容 | 用途 |
|---|---|---|
| メモM1 | 本文 `ゴミ箱テスト用メモM1`。ドキュメントD1の出典に引用済み | 復元・出典リンク確認 |
| メモM2 | 本文 `ゴミ箱テスト用メモM2`。ドキュメントD1の出典に引用済み | 完全削除・出典リンク消滅の確認（ADR-003） |
| トピックT1 | 名前 `ゴミ箱テストT1`（存命のまま使う） | 単独復元の復元先 |
| ドキュメントD1 | T1配下。タイトル `単独復元用D1`。出典にメモM1・M2を引用 | 単独復元（restoreAlone）・出典リンク確認 |
| トピックT2 | 名前 `ゴミ箱テストT2`（配下ごとセット削除する） | セット復元（restoreWithTopic） |
| ドキュメントD2a / D2b | T2配下。タイトル `セット削除用D2a` / `セット削除用D2b` | セット復元・完全削除 |
| トピックT3 | 名前 `ゴミ箱テストT3`（ハードデリートする） | 復元先選択（selectDestination） |

| ドキュメントD4 | T2配下。タイトル `個別削除用D4`（T2のセット削除より前に個別削除する） | 個別削除分がセットに含まれないことの確認 |

### 事前準備

各テストケースの「削除状態」は以下の手順で作る。テストケース本文では「準備A」等で参照する。

1. **基礎データ作成**: タイムライン（P-04）でメモM1・M2を投稿する。トピック一覧（P-06）でトピックT1・T2・T3を作成する。トピック詳細（P-07）からD1（T1配下）、D2a・D2b・D4（T2配下）、D3（T3配下）を作成する。ドキュメント編集（P-09）でD1の出典にメモM1・M2を引用して保存する
2. **準備A（メモの削除）**: タイムライン（P-04）でメモM1を削除する（ソフトデリート）
3. **準備B（ドキュメントの個別削除）**: ドキュメント（P-08）またはトピック詳細（P-07）からD1を削除する（ソフトデリート。所属トピックT1は削除しない）
4. **準備C（トピックのセット削除）**: 先にD4を個別に削除しておき、その後トピック詳細（P-07）からT2を削除する。T2とD2a・D2bがセット削除としてゴミ箱に入る（D4は個別削除のままゴミ箱内）
5. **準備D（所属トピックのハードデリート済み状態）**: ADR-001 の `selectDestination` 分岐の前提。UIのみで作れる:
   1. D3を個別に削除する（ソフトデリート）
   2. トピック詳細（P-07）からT3を削除する（ゴミ箱へ）
   3. ゴミ箱（P-12）でT3の「完全に削除」を実行する。個別削除されたD3はハードデリートの対象に含まれないため、D3だけが「所属トピックがハードデリート済み」の状態でゴミ箱に残る
6. **再作成（ハードデリート後の準備のやり直し）**: ハードデリート系のテストケース（TC-10〜TC-12）を実施した後は、M2・T2・D2a・D2b など基礎データの一部（TC-12 の「空にする」の後はゴミ箱内にあった全項目）が消滅している。以降のテストケースで準備A〜Dを行う場合は、まず基礎データ作成（手順1）の該当項目を**同名で作り直してから**該当の準備を実施する。作り直したデータは ID が変わるが、呼称と手順は同じでよい。各TCではこれを「準備A（再作成）を実施」のように表記する
7. **実施済みの準備のスキップ**: 各TCの手順にある「準備X を実施する」は、先行TCで実施済みでその状態が維持されている場合（例: TC-01 手順1で準備A〜C実施済みのまま TC-04・TC-05 に進む場合）は再実行せず、「その状態になっていることを確認する」に読み替えてよい。削除操作を二重に行う必要はない

## TC-01: ゴミ箱一覧の表示（S-TR-01）

**種別**: 正常系
**目的**: 3種別（メモ / ドキュメント / トピック）が削除日時付きで一覧され、保持期限までの残り日数が表示されることを確認する

| 2 | グローバルナビゲーションからゴミ箱（P-12）を開く | メモM1、ドキュメントD1、トピックT2、D2a・D2b、D4 が一覧に表示される |

| 5 | 各項目の保持期限表示を確認する | 各項目に保持期限（既定30日）までの残り日数が分かる表示がある（削除直後は残り30日相当） |

## TC-13: 保持期限による自動削除（S-TR-05）

**種別**: 正常系
**目的**: 保持期限を短く変更すると既存のゴミ箱項目にも遡及適用され、期限切れ項目が自動でハードデリートされることを確認する

前提: 環境前提の2つの手段（期限切れの状態を作る手段 / `purge-trash` ジョブを待たずに走らせる手段）が使えるテスト環境で実施する。30日の経過待ちはしない。

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | メモを1件削除し、ゴミ箱（P-12）で残り日数が約30日であることを確認する | 残り30日相当の表示 |
| 2 | 設定（P-13）でゴミ箱の保持期限を `1`（日）に変更して保存する | 保存が成功する |
| 3 | ゴミ箱（P-12）を再読み込みする | 既にゴミ箱にある項目の残り日数表示が新しい期限（残り1日以内）に更新されている（遡及適用） |
| 4 | 当該項目の削除日時（`trashedAt`）が2日前である状態を作る（対象ユーザーの Durable Object へのシード投入、または時計の巻き戻しに相当する手段。実体は #38） | — |
| 5 | 当該ユーザーの `purge-trash` ジョブを待たずに走らせる（Alarm の強制発火に相当する手段。実体は #38） | 実行が正常終了する |
| 6 | ゴミ箱（P-12）を再読み込みする | 期限切れ項目が一覧から消えている（自動ハードデリート）。期限内の項目（あれば）は残っている |
| 7 | 事後処理として設定（P-13）で保持期限を30日に戻す | 保存が成功する |

**確認ポイント**:
- 手順6で期限内の項目が消えていないこと（「期限内であればいつでも復元できる」の保証）
- 手順3の遡及適用は、保持期限の変更と同一トランザクションで既存項目の保持期限が再計算されることによる（表示のたびに計算し直しているのではない）
