# ドメイン一覧

ドメイン境界の判断は [ADR-004](../adr/004-domain-boundaries.md) を参照。

| ドメイン | 責務（一文） | 主な集約 |
|---|---|---|
| [identity](./identity.md) | ユーザーの認証・AIクライアント認可・ユーザー設定を管理する | User, AiClientConnection |
| [memo](./memo.md) | タイムラインに積まれるメモとそのリビジョン履歴を管理する | Memo |
| [knowledge](./knowledge.md) | トピック・ドキュメント・出典リンクと、ドキュメントのリビジョン履歴を管理する | Topic, Document |
| [search](./search.md) | メモ・ドキュメント横断の全文検索の問い合わせを担う | （検索クエリ・結果の値オブジェクトとポートのみ） |
| [trash](./trash.md) | ソフトデリート済み項目の横断閲覧・復元・ハードデリート・保持期限の規則を定める | （横断ビューとドメインサービス。項目自体の削除状態は各ドメインが持つ） |
| [export](./export.md) | ユーザーの全データを可搬形式（Markdown）で書き出す | （エクスポート生成サービスとポート） |

## ドメイン間の依存方向

```
identity ←─ memo ←─ knowledge
   ↑          ↑        ↑
   └── search ┘────────┘
   └── trash（memo, knowledge に依存）
   └── export（memo, knowledge に依存）
```

- identity の `UserId` はドメイン間で ID として参照されるが、**リポジトリ・ポートの引数には現れない**（ユーザー単位 Durable Object の選択で消費済み。下記「テナント分離」）
- knowledge は memo の `MemoId` を出典リンクとして参照する（ID参照のみ。エンティティ直接参照はしない）
- search / trash / export は memo・knowledge のエンティティをIDおよび読み取り専用ビューで扱う
- 循環依存はない

## 共通の横断事項

- **操作主体（Actor）**: リビジョンの「誰が」は、人間ユーザーまたはAIクライアント（トークン識別）を表す `Actor` として identity が定義し、memo / knowledge が利用する
- **テナント分離**: ユーザーのデータは本人にのみ属する（requirements 5.1）。**ユーザーのドメインデータはユーザー単位の SQLite-backed Durable Object に物理分離される**（requirements 5.1）。`userId` は Durable Object の選択で消費されるので、DO 内のリポジトリ・ポートは `userId` を引数に取らない。**構造的保証の在り処は「型（第一引数の `userId`）」ではなく「到達可能性」である** — 他ユーザーの Durable Object stub を得る経路が存在しないので、誤った `userId` を渡す経路そのものが無い。他ユーザーの ID を指定した操作は NotFound として扱う（DO の中に他ユーザーの行が原理的に存在しないので、結果は null / 空になる。存在の有無も漏らさない）。ユースケース層の追加検証（取得後の `entity.userId` 照合）に依存しない構造的保証とする。**例外は無い**
- **権限の非対称性**: ハードデリート・ゴミ箱操作・履歴閲覧はAIトークンのスコープに存在しない。この制約は二層で構造的に表現する（domains/identity.md「TokenScope」）: `actor` を入力に持つ人間 UI 専用（★）ユースケースは `actor` の型を `UserActor` に限定して型エラーで排除し、`actor` を持たない ★ ユースケースは application 層の公開範囲（AI 側 presentation に配線しない配線分離）＋ AI トークンの認可ミドルウェアの許可ユースケース列挙で排除する
- **ポートの同期契約**: 全ドメインポートは同期契約である（`Promise` を返さない）。書き込みは Durable Object 内の単一の同期トランザクションで完結し、その中では `await` を挟めないためである。**例外は `PasswordHasher` と `MailSender` の2つで、これは列挙であって導出規則ではない** — 残る理由は「暗号計算と外部 I/O であり、実装できる API が非同期しか無い」ことである。**トランザクションの外で動くことは `Promise` の根拠にならない**（`ArchiveWriter.write` は Durable Object の外で動くが同期契約である。domains/export.md）。新しいポートを足すときは、この2つに並べてよいかを「非同期 API しか無いか」で判定する。**Outbox の relay（Queue への publish）はこの列挙を開かない** — `queue.send()` はアダプター（DO クラス）の内部実装であり、ドメインもユースケースも触らないからである。**スロットル窓の `PasswordResetThrottlePort` も同期契約なので列挙は2つのまま動かない**（identity.md）。**locator の導出と canonical の封緘・開封もこの列挙を開かない** — どちらも `crypto.subtle` を使うので非同期だが、**ポートではなくアダプター内部の関数として閉じている**（呼ぶのは stub 選択アダプターと Identity Directory の RPC 入口であり、ドメインもユースケースも触らない。`spec/inventory/adapter.md` の `ADP-identity-030` / `ADP-identity-031`）
- **再水和の再検証**: 集約の再水和（`reconstruct`）は、行の各列を**その列に対応する値オブジェクトの `create` に通し直す**。読み出しは行の値をそのまま返さず、書き込みと同じ不変条件を毎回もう一度当てる。壊れた行は読んだ時点で `RehydrationError` になり、アダプターがそれを `SystemError(DataIntegrityError)` に翻訳して止める。**したがって値オブジェクトの不変条件を締める変更（上限を下げる・許容する形を狭める）は、保存済みの行に対する破壊的変更である** — 締める側は (1)**新しい不変条件に違反する行が存在しないことの確認**（確認の根拠と、その根拠がどこまでを言えているのかの限界を、値を定義している成果物に書く）か、(2)**再水和での再検証の緩和**（再水和は「既に永続化された状態の復元」であって入力検証ではない、という整理で当該の検証を `reconstruct` から外す）のどちらかを済ませてから入れる。(1) が成り立たない状況、あるいは (1) の前提が後から破れた状況で正しい手当ては (2) であり、値を戻すことではない（値を戻しても、その間に書かれた行との整合が取れるだけで、次に締めるときに同じ問題が再発する）。**射程は読み取り経路だけではない** — ゴミ箱からのハードデリートと保持期限切れの回収は消去の直前に対象を OCC トークン付きで取り直す（usecases/trash.md）ので、締めた不変条件に違反する行は**ゴミ箱に入れることはできても捨てられない**。容量が逼迫した Durable Object の復旧導線（「ゴミ箱を空にする」「エクスポートして削除する」。[database/index.md](../database/index.md)「物理境界」）は違反する行に対して**両方とも**塞がり、書き込みが通らない状態ではその行を直す手段も無い。**(1) の前提が破れたことの signal は1つである** — 当該の値オブジェクトの不変条件違反に由来する `SystemError(DataIntegrityError)`（アダプターが `RehydrationError` に付けるメッセージは「保存済みの行が不変条件に違反している」旨を述べる）が、**その列を読む経路から**出ること。本文の不変条件についてその経路は、本文を読む読み取り（詳細表示・リビジョンの二点取得）と削除の取り直しである。**限界: 本文を読まない一覧と逆引きの導線は再水和を通らず、読んだ列だけを値オブジェクトに通す**（下の「読み取り射影（サマリ）」）ので、締めた不変条件に違反する行も行として出せる。落ちるのはその行の本文を読む経路に入った時点なので、一覧に出ていることは行が新しい不変条件を満たしていることの根拠にならない。**この signal には型もテストも掛けられない** — 掛けられるのは「再水和が再検証する」という事実の記述と、この見分け方だけである。不変条件を**緩める／広げる**変更にこの帰結はない（保存済みの行は新しい不変条件を必ず満たす）
- **派生データの更新**: 検索インデックスのような派生データは、本体を書くのと同一のトランザクションの中で更新する。**派生データを別ストアへ非同期に反映する経路は持たない** — 検索 projection に indexer は存在せず、即時整合である（search.md「インデックスの維持」）。業務上の変更履歴はリビジョン（`memo_revisions` / `document_revisions`）が持つ（**外部への配送は次項**。正本は [async/index.md](../async/index.md)）
- **外部への配送**: 派生データの更新とは別に、**外部への配送は DO ローカル Outbox が担う**（`outbox_events` → Alarm relay → Queue → consumer → DLQ）。**登録口はドメインポートではなく UoW コンテキストの `enqueueEvent` 1つだけ**であり、業務データの書き込み・FTS5 projection の更新と同じ `transactionSync` の中でイベント行が追加される（rollback すると3つとも巻き戻る）。**どのドメインがどのイベントを発行するかの全数は [async/index.md](../async/index.md) が持つ** — 定義済みのイベント型は identity の1件だけで、memo / knowledge / search / trash / export はイベントを定義しない
- **ドメインイベントの契約**: ドメインが返すのは **identity-less な draft** である（`{ type, payload, occurredAt, aggregateId }`）。**`EventId` はアプリケーション層が付ける** — UoW 実装が `IdGenerator` から採番するので、ドメインは id 生成に触らない。**イベントを発行する**エンティティのファクトリ / 遷移は `{ entity, eventDrafts }` の形で draft を返し、ユースケースがそれを `enqueueEvent` へ渡す。**現状そのような遷移は1つも存在しない**ので、既存の「状態遷移は次状態のエンティティだけを返す」（memo.md / knowledge.md）は動かない — この形は将来イベントを発行する遷移が現れたときの契約であって、既存のファクトリのシグネチャを変える指示ではない。**エンティティ遷移を伴わないイベントは draft ファクトリから出す** — `{ entity, eventDrafts }` は遷移から出るイベント用の形なので、遷移しない発行点（現状は identity の1件だけで、`requestPasswordReset` は `User` も `CredentialMapping` も遷移させない）はそこに乗らない。**その場合もユースケースが draft をリテラルで組み立てることは無く、ドメインが持つ draft ファクトリ1本が `type` の文字列・`aggregateId` の選び方・payload の形を決める**（決めないと「行の形が一様であること」を保証する主体が誰も居なくなる）。**payload に PII と再利用可能な秘密を載せない**（衛生規則の正本は [async/index.md](../async/index.md)）。**配送のための識別子（`EventId` / 宛先 DO の routing key）は payload に入れない** — どちらもアプリケーション層 / アダプターが付ける。契約の詳細は identity.md「ドメインイベント」
- **読み取り射影（サマリ）**: 本文のような重い列を画面が描かない読み取りは、エンティティではなく**射影型**を返す。射影型の作り方は次の5点で固定する。**規約はここにだけ置き**、各ポートの記述（`spec/domains/{knowledge,memo}.md`）とポートの JSDoc はここを参照する
  1. **射影型はエンティティのフィールドの部分集合として定義する**（実装では `Pick<Entity, ...>`）。新しいフィールド名も新しい語彙も作らない。`status` を `deleted: boolean` に読み替えるのはアプリケーション層の View の仕事であって、ポートの仕事ではない
  2. **置き場所はそのポートを定義するファイル**（`domain/{domain}/ports/*.ts`）。エンティティのファイルには置かない。射影は「このポートがどう読むか」であってドメインの語彙ではない（`MemoRepository` の `TimelinePage` / `TimelineAnchor` と同じ扱い）
  3. **命名は型名とメソッド名の両方を決める。** 型名は `<Entity>Summary`（エンティティ側にライフサイクルの直和があるなら接頭辞をそのまま引き継ぐ。`ActiveDocument` → `ActiveDocumentSummary`）。メソッド名は既存の entity 読みの名前のうち、エンティティを指す名詞を `<名詞>Summaries` に置き換える（名詞が省略されていて置き換える先が無い名前では、動詞 `list` の直後に `Summaries` を挿入する）。**限界: この規則が及ぶのはポート側だけである** — アプリケーション層の View 名（`RevisionSummaryRowView` / `TopicDocumentRowView` など）は用途由来のままで、ポート側の `<Entity>` とは揃わないし揃えない（一致するのは `Summary` の語幹までである）。**この規則が決めるのは新しい名前の導き方だけで、左側の entity 読みが残るか消えるかは決めない**（それは下記「残すか置き換えるか」が1本ずつ決める）。導き方の例:
     - `listActiveByTopic` → `listActiveSummariesByTopic`（左は entity 全体を要る呼び出し元があるので残る。すなわちこれは併存する射影の名前の導き方であって、改名ではない）
     - `listByIdsIncludingTrashed` → `listSummariesByIdsIncludingTrashed`
     - `listRevisions` → `listRevisionSummaries`
  4. **射影は `Versioned<...>` を持たない。** OCC トークンを発行しないので、射影で読んだ行を `save` に渡すことは型エラーになる。「読まずに書く」を型で塞ぐ既存規約の裏返しで、「本文を読まずに書く」も同じ仕組みで塞がる
  5. **列は「その射影を使う読み取り全体が描くもの」で決め、呼び出し元ごとには切らない。** 落とすのは重い列と OCC トークンであって、呼び出し元ごとの最小化ではない（最小化すると射影が呼び出し元の数だけ増え、ポートの読み口が増殖する）。**ただし、エンティティ側にライフサイクルの直和があるとき、その直和を判別する列は、どの呼び出し元も描かなくても残す** — 構造的部分型のもとでは、判別子が無いと広い側の射影が直和の一方に限定した読み口へそのまま代入できてしまうからで、列としてではなく型の境界として要る（`ActiveDocumentSummary` の `status` がこれにあたり、同じ形のライフサイクルを持つ他のエンティティの射影も同様に扱う）。**引数から決まる列を落とすかどうかも、同じ単位で決める** — 判定の単位は読み1本ではなく射影1つである。**その射影を返すすべての読みにおいて、引数が当該列の値を全行ぶん決めるときだけ落とす。** 集合を引数に取る読みが1つでもあれば引数は行ごとの値を決めないので、その列は結合・グルーピングのために残す。`ActiveDocumentSummary` の `topicId` と `DocumentSummary` の `id` が残っているのはこれで、前者は複数トピックを一度に読む呼び出し元がグルーピングに使い、後者は ID 群を引数に取る読みで欠落 ID がありうるため呼び出し元が行を突き合わせるのに使う。`MemoRevisionSummary` の `memoId` を落とすのは、この射影を返す読みが単一の `MemoId` を引数に取るもの1本だけだからである

  **既存メソッドを残すか置き換えるかは、メソッド1本ずつに決める**: **entity 全体を要る呼び出し元が存在する（将来ぶんを含む）メソッドだけ、現状の契約のまま残す。存在しないメソッドは返り値を射影に置き換える。** 単数形 / 複数形の対では判定しない（一方だけが entity 全体を要ることがある）
