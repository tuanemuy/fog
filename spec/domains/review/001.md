# ドメイン設計レビュー 001

対象: spec/domains/*（identity / memo / knowledge / search / trash / export）
観点: 実装可能性・アーキテクチャ適合性・ビジネスロジック網羅・ドメイン間整合

対応が必要な問題のみを重要度順に挙げる。

## 問題 1（重大）: メモのハードデリート時の出典リンク消去の責務が 3 ファイルで矛盾

- 対象: spec/domains/memo.md、spec/domains/knowledge.md、spec/domains/trash.md
- 問題:
  - memo.md（「ドメイン境界に関する前提」および ドメインイベント表の `memo.hardDeleted` 行）は「**`memo.hardDeleted` イベントを受けた knowledge 側（consumer）の責務**であり、memo は関知しない」と非同期方式を規定している
  - knowledge.md（`DocumentRepository.deleteSourceLinksByMemo` の doc コメント、ユースケース概要末尾）は「memo ハードデリートのユースケース（trash ドメイン）が**同一 UoW で呼ぶ**」と同期方式を規定している
  - trash.md（「書き込みポートについて」）はさらに「`MemoRepository.hardDelete(id, expectedVersion)`。**リビジョン・出典リンクの同時消去を含む契約**」と書いており、memo.md の `MemoRepository.hardDelete` の契約（メモ本体と全リビジョンのみ削除。出典リンクは knowledge のテーブルであり memo のリポジトリからは触れない）とも矛盾する
  - Outbox は at-least-once・順序保証なし・遅延ありのため、非同期方式だと ADR-003（ハードデリート後は出典リンクを残さない）の充足タイミングが不定になる。方式の選択自体が実装結果を左右する
- 修正提案: **同期方式（同一 UoW）に一本化**する。trash のハードデリート系ユースケースが `MemoRepository.hardDelete` と `DocumentRepository.deleteSourceLinksByMemo` を同一 UoW で呼ぶ、と memo.md の該当 2 箇所（前提・イベント表の購読者欄）を修正する。`memo.hardDeleted` の購読者は search（インデックス除去）のみとする。trash.md の「`MemoRepository.hardDelete` は出典リンク消去を含む」という記述を「出典リンク消去は同一 UoW での `DocumentRepository.deleteSourceLinksByMemo` 呼び出しによる」に修正する

## 問題 2（重大）: ゴミ箱保持日数の値オブジェクトが identity と trash で二重定義され、所有権の記述が矛盾

- 対象: spec/domains/identity.md、spec/domains/trash.md
- 問題:
  - identity.md は `TrashRetentionDays`（既定 `TrashRetentionDays.default()` = 30、エラー `IdentityErrorCode.InvalidTrashRetentionDays`）を **identity の値オブジェクト**として定義
  - trash.md は `RetentionDays`（`RetentionDays.DEFAULT` = 30、エラー `TrashErrorCode.InvalidRetentionDays`）を定義し、「**VO は trash に置き identity が参照する**」と規定
  - 同一概念に対し、名前・定義ドメイン・エラーコード・既定値アクセサがすべて食い違う。さらに trash の記述どおり identity が trash の VO を参照すると、trash → identity（`UserId`）の既存依存と合わせて **identity ⇄ trash の循環依存**が生じ、domains/index.md の依存図（循環なし）に反する
- 修正提案: identity 側の `TrashRetentionDays` に一本化し、trash.md の `RetentionDays` 定義を削除して「identity の `TrashRetentionDays` を参照する」に書き換える（依存方向 trash → identity は既存で問題ない）。`RetentionPolicy` / `TrashQueryPort` の引数型も `TrashRetentionDays` に揃える

## 問題 3（重大）: search インデックスの出典関連フィールドが陳腐化する更新パスの欠落と、存在しないイベントへの言及

- 対象: spec/domains/search.md（インデックス更新フロー）、spec/domains/memo.md / knowledge.md（イベント定義）
- 問題:
  - search.md の契機イベント表に「**出典リンクの生成（ドキュメント作成時）**」という行があるが、memo / knowledge にそのようなイベントは存在しない（存在するのは `document.created`、ペイロードは `{ documentId }` のみ）。`document.created` だけでは「出典メモ各件の upsertMemo（`sourceOfDocumentIds` の反映）」に必要なメモ ID がイベントから得られず、consumer が出典リンクを逆引きして**複数対象へファンアウト**する必要がある。これは同フロー末尾の「イベント種別ごとの分岐を持たず、対象 ID の可視状態を見て upsert / remove する単一の冪等処理に正規化してよい」という記述と矛盾する
  - `memo.hardDeleted` 時: 当該メモを出典とするドキュメントの `DocumentIndexEntry.sourceMemoIds` を更新する契機がない。ハードデリート済みメモの ID が検索結果（`sourceMemoIds`）に残り続け、ADR-003（痕跡を残さない）に反する
  - `document.hardDeleted` 時: 同様に出典メモ側の `MemoIndexEntry.sourceOfDocumentIds` が陳腐化する。しかもリンク行はドキュメントと同時に消えるため、consumer がイベント受信時点で影響メモを逆引きすることすら**できない**
- 修正提案:
  - 契機イベント表の「出典リンクの生成」行を `document.created` に統合し、「consumer は `listSourceLinksByDocument` で出典メモを逆引きし、各メモも upsert する」とファンアウトを明記する。「単一の冪等処理に正規化してよい」の記述は削除するか「出典の相互反映を除き」と限定する
  - ハードデリート時は、trash のユースケースが削除実行前に影響先を確定し、影響ドキュメント（メモのハードデリート時）・影響メモ（ドキュメントのハードデリート時）の再インデックス用イベント（`document.edited` / `memo.edited` の再利用、または専用イベント）を同一 UoW で発行する、と memo.md / knowledge.md / trash.md に規定する

## 問題 4（中）: trash.md が参照する `Topic.restoreWithDocuments` が knowledge に存在しない

- 対象: spec/domains/trash.md（「書き込みポートについて」）、spec/domains/knowledge.md
- 問題: trash.md は復元経路として「knowledge の `Document.restore(...)` / **`Topic.restoreWithDocuments(...)`**」と書くが、knowledge.md に定義されているのは `Topic.restore` と `TopicTrashService.restoreTopicSet` であり、`Topic.restoreWithDocuments` というメソッドは存在しない
- 修正提案: trash.md の記述を `TopicTrashService.restoreTopicSet(...)` に修正する

## 問題 5（中）: knowledge のリポジトリ一覧系メソッドが OCC トークンを返さず、規定された同一 UoW の書き込みフローが実装できない

- 対象: spec/domains/knowledge.md（TopicRepository / DocumentRepository）、spec/domains/trash.md（pruner フロー）
- 問題:
  - コード規約（backend_implementation_example.md）では `save` / `delete` は `ExpectedVersion` トークン必須で、トークンの発行点は `findById` のみ。しかし knowledge の `listActiveByTopic` / `listTrashedByTopic` / `listTrashedByUser` / `listTrashedBefore` はいずれも**素のエンティティ配列**を返す
  - 一方、セット削除（`trashTopicSet` 後の全ドキュメント save）、セット復元、トピックのハードデリート（配下ドキュメントの delete）、pruner は、これらの一覧結果に対して save / delete する設計になっており、トークンが手に入らない。memo 側の同種メソッド（`listTrashed` / `listTrashedBefore`）は `Versioned<TrashedMemo>[]` を返しており、ドメイン間で規約適用が不整合
- 修正提案: knowledge の一覧系のうち書き込みに接続するもの（上記 4 メソッド）の戻り値を `Versioned<...>` に変更し、memo と揃える（純表示用の一覧はそのままでよい）

## 問題 6（中）: 保持期限切れ抽出の経路が二重定義され、`listTrashedBefore(cutoff)` はユーザー別 retentionDays を表現できない

- 対象: spec/domains/memo.md（`MemoRepository.listTrashedBefore`）、spec/domains/knowledge.md（`TopicRepository.listTrashedBefore` / `DocumentRepository.listTrashedBefore`）、spec/domains/trash.md（`TrashQueryPort.listExpiredItems`）
- 問題: 保持期限はユーザー設定（既定 30 日、変更可・遡及適用）だが、memo / knowledge の `listTrashedBefore` は**単一の cutoff 日時**を受けるため、ユーザーごとに異なる retentionDays を適用できない。trash.md の pruner は正しく `TrashQueryPort.listExpiredItems`（ユーザー設定と結合して抽出）を使う設計であり、`listTrashedBefore` は「自動ハードデリート用」と注記されているにもかかわらず実際には使われない・使うと誤る二重定義になっている
- 修正提案: memo / knowledge の `listTrashedBefore` を削除し、期限切れ抽出は `TrashQueryPort.listExpiredItems` に一本化する（ハードデリート実行時の対象取得・OCC トークンは `findByIdIncludingTrashed` / `findById` で個別再取得する旨を pruner フローに明記する）

## 問題 7（低〜中）: AI からのゴミ箱非可視の実現方法が memo と knowledge で非対称

- 対象: spec/domains/knowledge.md（DocumentRepository / TopicRepository）、spec/domains/memo.md
- 問題: memo は「`findById` が active のみ返す」ことで S-AI-04（ゴミ箱内は存在しない扱い）を構造的に実現するのに対し、knowledge の `findById` は「trashed も返す」契約で、AI 向け `get` / `edit_document` / `delete` での非可視化は各ユースケースの状態チェックに委ねられる（チェック内容は明文化されていない）。同一の規則（S-AI-02 / S-AI-04）の実現手段がドメイン間で食い違い、knowledge 側でチェック漏れが起きやすい
- 修正提案: knowledge にも `findActiveById(id): Promise<Versioned<ActiveDocument> | null>`（Topic は `LiveTopic`）を追加し、AI 系ユースケースはそれのみを使う規約にする（人間 UI のゴミ箱系だけが全状態版を使う。memo の `findById` / `findByIdIncludingTrashed` の対に揃える）

## 問題 8（低）: `HardDeletePolicy.expandTargets` のシグネチャでは規定された処理が実装できない

- 対象: spec/domains/trash.md（HardDeletePolicy）
- 問題: `expandTargets(item: TrashItem): readonly TrashItem[]` は、トピックの場合に「`documentIds` に対応する `TrashedDocumentItem[]` を含めて返す」とされるが、`TrashedTopicItem` が持つのは ID のみで、純関数の引数に子項目が渡されない以上、`TrashedDocumentItem` を構築できない。本文の補足自体がオーバーロードの必要性を認めており、主シグネチャが実装不能のまま残っている
- 修正提案: シグネチャを `expandTargets(item: TrashItem, children: readonly TrashedDocumentItem[]): readonly TrashItem[]`（memo / document では `children` は空）に確定し、`children` の取得は `TrashQueryPort` を使うユースケースの責務と明記する

## 問題 9（低）: リビジョン番号の型がドメイン間で不揃い

- 対象: spec/domains/knowledge.md（DocumentRevision.revisionNumber / Document.latestRevision / `findRevision`）、spec/domains/memo.md（RevisionNumber）
- 問題: memo は `RevisionNumber`（ブランド VO、1 以上の整数をバリデーション）を定義するが、knowledge は同じ概念（1 始まり連番・線形履歴という同一の不変条件）を素の `number` で扱う。線形性の不変条件 3 が値レベルで保証されず、共有概念の型定義が並行執筆で分岐した状態になっている
- 修正提案: knowledge にも同等のブランド VO（`DocumentRevisionNumber`、または common へ昇格した `RevisionNumber`）を導入し、`latestRevision` / `findRevision` の型を揃える

## 問題なしを確認した観点

- export の `ExportSourceReader.readAll` の範囲（ゴミ箱除外・最新リビジョンのみ・完了済みトピック含む・ハードデリート済み出典 ID 除外）は ADR-002 / ADR-003 と一致
- `Actor` / `UserId` / `MemoId` / `DocumentId` / `TopicId` の定義元と参照方向は（問題 2 を除き）一貫。集約間はすべて ID 参照
- ドメインイベント名・ペイロード（ID のみ）は発行側と search consumer の期待で一致（問題 3 の出典関連の欠落を除く）
- シナリオ S-TL / S-DT / S-SE / S-TR / S-AI / S-AC / S-ST の正常系・異常系は、上記の問題箇所を除きドメインの振る舞い・ポート・ユースケース概要でカバーされている
- ドメイン層に DB / HTTP 依存はなく、`new Date()` / ID 生成の排除、判別可能ユニオンによる排他状態の型表現（User / AiClientConnection / Memo / Topic / Document / TrashItem / SearchResultItem）はコード規約に適合
