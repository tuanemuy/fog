# ドメイン設計レビュー 006

ゼロベースレビュー（過去レビューファイル不参照）。対象: spec/domains/*.md（identity / memo / knowledge / search / trash / export）。

シナリオ全パス・ADR・実装規約（docs/backend_implementation_example.md）との突き合わせの結果、集約境界・直和型設計・イベントの発行/購読対応・trash のオーケストレーション・検索インデックスのファンアウト規則は一貫しており、大きな欠陥はない。実装時に手が止まる問題は以下の 3 件のみ。

## 1.（中）パスワードリセットの SSO ユーザー分岐が未定義 — identity.md

- `requestPasswordReset` は `UserRepository.findByEmail` でユーザーを特定してトークンを発行するが、見つかったユーザーが `SsoUser` の場合の挙動が定義されていない
- `executePasswordReset` はエンティティ上 `User.changePassword` を共用するが、`changePassword` は `PasswordUser` のみを受ける（型で保証）。SSO ユーザーに対してトークンが発行されると、リセット実行時に型の行き止まりに達し、返すべきエラーも定義がない
- 対応案: `requestPasswordReset` は対象が `SsoUser` の場合トークンを発行せずメールも送らない（応答は「登録されていれば送信された」のまま。登録有無・認証方式を明かさない）と明記する。`executePasswordReset` 側にも防衛的分岐（対象が `SsoUser` なら `ValidationError("RESET_TOKEN_INVALID")` 相当）を記す

## 2.（中）`TrashQueryPort.findTrashItem` が `expiresAt` を算出できない — trash.md

- `TrashItem` は required の `expiresAt` を持ち、「アダプターが `RetentionPolicy.expiresAt` を用いて付与する」とあるが、算出には `retentionDays` が必要
- `listTrashItems` は `retentionDays` を引数で受け取り、`listExpiredItems` は identity のユーザー設定テーブルと結合する旨が明記されている一方、`findTrashItem(userId, ref)` には引数も結合の記述もなく、契約が矛盾している
- 対応案: `findTrashItem` にも `retentionDays: TrashRetentionDays` を引数追加する（`listTrashItems` と同規約に揃えるのが最小変更）

## 3.（低）SSO 主体一意制約のレース時のエラーマッピングが未定義 — identity.md

- メール一意性には「事前チェック + DB 制約の二重防御。`insert` の email 一意制約違反 → `ConflictError("EMAIL_ALREADY_REGISTERED")`」が明記されているが、同じく「全ユーザー間で一意」とされる `(provider, providerSubject)` については事前検証（`findBySsoIdentity`）のみで、`insert` 時の一意制約違反のマッピングが定義されていない
- 同時初回 SSO サインインのレースで制約違反が起きた場合、規定がないとアダプターの `mapDbError` により `SystemError(DatabaseError)` に落ち、不変条件違反の競合が 5xx 扱いになる
- 対応案: email と同様に `insert` の (provider, providerSubject) 一意制約違反 → `ConflictError`（コード例: `SSO_IDENTITY_ALREADY_REGISTERED`）を UserRepository のエラーケースに追記する
