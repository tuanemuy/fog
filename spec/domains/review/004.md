# ドメイン設計レビュー 004

ゼロベースレビュー（過去レビューは参照していない）。対象: spec/domains/ 全ファイル。照合対象: requirements.md / idea.md / scenario/ 全ファイル / pages/index.md / ADR-001〜006 / docs/backend_implementation_example.md。

確認して問題なしと判断した主な点（記録のみ）:

- ドメインイベントの発行側（memo / knowledge）と購読側（search consumer 表）は `memo.*` 6種・`document.*` 6種・`topic.*` の扱いまで一致している
- trash のオーケストレーションが参照する他ドメインのメソッド（`DocumentRepository.deleteSourceLinksByMemo` / `listSourceLinksByMemo` / `listSourceLinksByDocument`、`TopicTrashService.restoreTopicSet`、各 `findByIdIncludingTrashed` 等）はすべて定義済み
- 依存方向は index.md の宣言どおりで循環なし。ドメイン間参照はすべて ID / 読み取りビュー参照
- 排他的状態（User の認証方式、AiClientConnection、Memo / Topic / Document のライフサイクル、TrashItem、SearchResultItem）は直和型で表現され、不正遷移は引数型で排除されている
- ADR-001 / 002 / 003 / 005 / 006 の決定はそれぞれ trash / export / knowledge・memo / search / memo の設計に正しく反映されている

以下、対応が必要な問題点のみを重要度順に挙げる。

## 1. タイムラインの読み取りポートが「新しい側」への読み込みを表現できない（中〜高）

- 対象: `spec/domains/memo.md` — `MemoRepository.findTimelinePage` / `findCursorNearDate` / `TimelineCursor`
- 問題: `findTimelinePage` は「カーソル位置から postedAt 降順（過去方向）へ」の単方向ページングのみを定義している。一方、上流は次を要求する:
  - S-TL-03 / P-04: 日付ジャンプ後もタイムラインとして閲覧が継続する（ジャンプ位置より新しいメモへ戻れる必要がある）
  - P-04「指定メモ位置の表示」: 他画面（P-05 / P-07 / P-08 / P-11）から該当メモ位置へ遷移し、スクロール＋ハイライト表示する。該当位置を「ページの途中」に置くには、位置の前後（新しい側・古い側）両方の読み込みが要る
  - `findCursorNearDate` で得たカーソルから始めると古い側しか読めず、上方向（新しい側）の無限スクロール・文脈表示を実装する手段がポートに存在しない
- 対応案: `findTimelinePage` のクエリに `direction: "older" | "newer"`（または `before` / `after` カーソル）を追加する。あわせて「指定メモ位置」遷移用に、memoId からカーソルを得る手段（人間 UI 経路で `findByIdIncludingTrashed` → postedAt → `findCursorNearDate` で足りるかを含め）を明記する。

## 2. 検索インデックスの出典 ID 群に「ソフトデリート済みの相手」を含めるかが未定義（中）

- 対象: `spec/domains/search.md` — `MemoIndexEntry.sourceOfDocumentIds` / `DocumentIndexEntry.sourceMemoIds`、インデックス更新フロー
- 問題: consumer がエントリを構築する際、出典リンクの相手側（参照先ドキュメント / 出典メモ）がゴミ箱内の場合に ID を含めるかどうかの規則がどこにも書かれていない。実装者はここで必ず判断を迫られる。さらに:
  - 素直に「リンク全件を含める」と実装すると、AI が search 結果の `sourceOfDocumentIds` 経由でゴミ箱内ドキュメントの ID（＝存在の事実）を観測できる。`get` は NotFound になるため実害は小さいが、「ゴミ箱の中身は AI から見えない世界」（requirements 4.5 / trash.md）と整合しない
  - 「含めない」と決めた場合、`document.trashed` / `document.restored` 時に出典メモ側のエントリを更新する契機（ファンアウト）が現在のイベント表に存在せず、規則を守れない（ハードデリート時の `*.sourceLinksChanged` は定義済みだが、ソフトデリート時の相手側再インデックスは未定義）
- 対応案: どちらかに決めて search.md に明記する。
  - (a) 相手の削除状態を問わずリンク全件を含める（実装が単純。ID 露出は許容と明記する）
  - (b) ゴミ箱内の相手を除外する。その場合は `document.trashed` / `document.restored` の consumer 処理に「出典メモのファンアウト upsert」（`memo.trashed` / `restored` 側も同様）を追加する

## 3. pruner の setMembers 取得手段が TrashQueryPort に存在しない（低）

- 対象: `spec/domains/trash.md` — 自動削除フロー手順 3「期限切れトピックは `TrashQueryPort` で取得したセット配下の `TrashedDocumentItem` 群を `setMembers` に渡し」
- 問題: `TrashQueryPort` には「トピックのセット配下項目を取得する」メソッドがない（`listTrashItems` はユーザー単位ページング、`findTrashItem` は単一取得、`listExpiredItems` は期限切れ横断）。フローの記述どおりには実装できず、手が止まる。`TrashedTopicItem.documentIds` を `findTrashItem` で 1 件ずつ引く迂回は可能だが、仕様上どの経路を意図しているのか不明確
- 対応案: いずれかを trash.md に明記する。
  - (a) `HardDeletePolicy.expandTargets` の topic 分岐は実質 `item.documentIds` だけで決まるため、`setMembers` を廃して `documentIds` を直接使う（シグネチャ簡素化。emptyTrash の重複除去規則は維持）
  - (b) `setMembers` を残すなら、`findTrashItem` の反復取得で解決する旨（または一括取得メソッドの追加）を書く
