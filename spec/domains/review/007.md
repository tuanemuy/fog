# ドメイン設計レビュー 007（ゼロベース）

対象: spec/domains/*.md（identity / memo / knowledge / search / trash / export）
照合: requirements.md, idea.md, scenario/ 全件, pages/index.md, ADR-001〜006, docs/backend_implementation_example.md

検査済みで問題なしと判断した主な点:

- 参照先メソッドの実在（memo→knowledge の出典リンク系、trash→memo/knowledge の書き込み系、search→knowledge の逆引き系）はすべて定義と一致
- イベントの発行側・購読側の対応（`*.sourceLinksChanged` の trash 同一UoW発行、search consumer のファンアウト表を含む）は memo / knowledge / search / trash の4ファイル間で整合
- 排他的状態の直和型（User / AiClientConnection / Memo / Topic の wasArchived / Document の trashedWith）はあり得ない状態を型で排除できている
- シナリオ全パス（ADR-001 の3分岐、S-TR-02 の skippedDocuments 追加復元、emptyTrash の二重展開の重複除去、pruner の no-op 規約、S-AI-02〜05 の AI 非可視規則）はカバーされている

対応が必要な問題は以下の1件。

## 1. 【高】他ユーザーのリソースに対する所有権検証がユースケースの検証項目に明文化されていない

- 該当: knowledge.md「ユースケース（概要）」の `createDocument`（および memo/knowledge の `get` / `update_memo` / `edit_document` / `delete` 等、ID を外部入力から受け取る全ユースケース）、memo.md / knowledge.md の各リポジトリ `findById` 系
- 内容: `MemoRepository.findById` / `DocumentRepository.findById` / `TopicRepository.findById` はいずれも `userId` を受けずグローバル ID のみで引く契約になっている。一方、`createDocument` の検証記述は「出典メモ ID 群の実在・非ゴミ箱、作成先トピックの実在・非ゴミ箱を検証」とだけ列挙しており、**取得したエンティティの `userId` が操作主体（Actor）のユーザーと一致すること**の検証が含まれていない。knowledge.md 不変条件 10 に「スコープはリポジトリのクエリと application 層で強制」と一般論はあるが、`findById` はクエリでスコープしないため、実際の強制点は各ユースケースの所有権チェックのみになる。列挙された検証項目をそのまま実装すると、AI クライアント（または人間 API）が他ユーザーの `memoId` を `create_document` の `sourceMemoIds` に渡して出典リンクを張れる・他ユーザーの ID で `get` / 編集 / ソフトデリートできるクロステナント欠陥を作り込む（requirements 5.1「ユーザーは自分のメモ・ドキュメント・トピックのみにアクセスできる」違反）
- 対応案（いずれか。両方でもよい）:
  1. ID を外部入力から受けるユースケースの共通規則として「`findById` 系で取得後、`entity.userId` と操作主体の `userId` の一致を検証し、不一致は `NotFoundError`（存在有無を漏らさない）とする」を domains/index.md の横断事項および各ドメインのユースケース概要（少なくとも `createDocument` の検証列挙）に明記する
  2. `findById` / `findByIdIncludingTrashed` 系の契約に `userId` 引数を追加し、リポジトリのクエリ層で常時スコープする（強制点を一箇所に固定でき、チェック漏れが構造的に起きなくなる）
