# ドメイン設計レビュー 003

ゼロベースレビュー（過去レビューは未参照）。対象: spec/domains/ 全6ドメイン。照合先: requirements.md / idea.md / scenario 全件 / pages/index.md / ADR-001〜005 / docs/backend_implementation_example.md。

全体として、直和型によるライフサイクル表現、ID参照による集約境界、trash のオーケストレーション責務、Outbox 経由のインデックス維持は一貫しており、シナリオの主要パス（S-AC / S-TL / S-DT / S-SE / S-TR / S-AI / S-ST）はカバーされている。以下は実装時に手が止まる、または判断がぶれる実質的な問題のみ。

## 指摘事項（重要度順）

### 1. [中] 出典リンクの一括逆引きポートが欠落（memo.md の前提と knowledge のポート定義の不一致）

- memo.md「ドメイン境界に関する前提」は、タイムラインの「→ ドキュメントX」導線を「knowledge 側へ MemoId で照会（**メモ群**を出典とする出典リンクの逆引き）」で実現するとし、getTimeline ユースケースも「knowledge へ出典リンクを逆引き照会する」と規定している。
- しかし knowledge の `DocumentRepository` に定義されているのは単一メモ用の `listSourceLinksByMemo(memoId: MemoId)` のみ。タイムライン1ページ（最大100件）の表示でメモ件数分の N+1 照会になり、ホーム画面の主経路として設計意図（1クエリ成立を明記した `listByIdsIncludingTrashed` 等と同水準）と食い違う。
- 同型の不足が他にもある:
  - `listTopics`（UI / MCP `list_topics`: 「トピックと**配下ドキュメント**の一覧」）に対し、複数トピックの配下ドキュメントを一括取得する手段がない（`listActiveByTopic` は単一トピック用）
  - `getTopic` の関連メモ（配下ドキュメントの出典リンク集約）に対し、`listSourceLinksByDocument` が単一ドキュメント用のみ
- 対応: `listSourceLinksByMemos(memoIds: readonly MemoId[])` / `listSourceLinksByDocuments(documentIds: readonly DocumentId[])` / `listActiveByUser(userId)`（または topicIds 複数指定）等の一括読み取りメソッドを `DocumentRepository` に追加し、memo.md の照会前提と揃える。

### 2. [中] update_memo の編集形式が requirements 4.3 と未整合（設計判断の明文化漏れ）

- requirements 4.3「AIへの編集インターフェース」は**メモ・ドキュメント共通**の節にあり、「原則パッチ形式とする。全文指定は新規作成・明示的な全面書き直しに限定」と規定している。
- 一方、設計上パッチ機構（`DocumentPatch`）は knowledge のみに存在し、memo の `Memo.edit` / AI 用 `update_memo` は全文置換のみ。S-AI-04 の記述（「メモは update_memo、ドキュメントは edit_document（パッチ形式…）」）はメモ＝全文を示唆しており、設計はシナリオ側に寄せた形だが、要件文言との齟齬がどこにも明記されていない。
- 実装者が「update_memo にもパッチが必要か」で手が止まる。対応: 「メモはアトム（上限10,000文字）でありパッチ編集の対象外、4.3 のパッチ原則はドキュメントに適用」という判断を memo.md（または ADR / requirements の修正）として明文化する。

### 3. [低] emptyTrash でのトピックとセット配下ドキュメントの二重処理が未規定

- ゴミ箱一覧にはセット削除されたトピックとその配下ドキュメントが**両方**項目として現れる（S-TR-01）。`emptyTrash` が全項目へ `HardDeletePolicy.expandTargets` を適用すると、セット配下ドキュメントはトピック側の展開結果と自身の項目とで二重にハードデリート対象になる。
- pruner（S-TR-05）側には「行不在の検出で片方が no-op」と冪等性の記述があるが、emptyTrash（trash.md ユースケース概要）には重複除去または no-op 許容の規定がない。`HardDeletePlan` をマージする場合の重複除去規則も未定義。
- 対応: emptyTrash の仕様に「展開後の対象 ID 集合を重複除去する」または「既に消去済みの対象（`findByIdIncludingTrashed` が null）は no-op として続行する」のいずれかを明記する。

### 4. [低] 設定画面用のアカウント情報読み取りユースケースが identity にない

- P-13 の表示には「現在のゴミ箱保持日数」「パスワード変更項目の表示可否（authMethod 判定。S-AC-07 エッジケース: SSO のみのユーザーには非表示）」が必要だが、identity のユースケース一覧に該当する読み取り（getCurrentUser / getAccountSettings 相当）がない。`listAiClientConnections` / `changeTrashRetentionDays` はあるため、表示側だけが宙に浮く。
- 対応: 現在ユーザーの設定表示用読み取りユースケース（email・authMethod・trashRetentionDays を返す DTO）を identity のユースケース一覧に追加する。

## 確認済み（問題なしと判断した主な観点）

- 排他的状態の直和型: User（password/sso）、AiClientConnection（active/revoked + revokedAt）、Memo（active/trashed）、Topic（active/archived/trashed + wasArchived）、Document（active/trashed + trashedWith）、TokenScope（human/ai の権限非対称）はいずれも不正状態を型で排除できている
- 集約境界: ドメイン間参照はすべて ID / VO 参照。RevisionNumber の重複定義は「依存を作らない」と明記済み。循環依存なし（trash → identity の TrashRetentionDays 参照も既存方向と同一）
- ADR 整合: ADR-001（復元先選択の3分岐 = RestorePolicy）、ADR-002（エクスポート範囲）、ADR-003（同期方式のリンク消去 + sourceLinksChanged 再インデックス）、ADR-005（ID のみペイロード・冪等 consumer）まで一貫
- イベントの発行側・購読側: memo / knowledge の全イベントが search.md のインデックス更新フロー表と一致。`document.created` の出典メモへのファンアウト、`topic.archived` を除去契機にしない注意も記載あり
- セット削除・セット復元の不変条件: `TopicTrashService` + `trashedWith` + skippedDocuments の追加復元（S-TR-02 の全エッジ）まで到達可能なパスを網羅
- 権限の非対称性: ユースケース公開範囲 + TokenScope + `findById` が active のみ返す三重の構造的保証で「AI からゴミ箱は存在しない」を実現しており、ガイダンス非依存の要件を満たす
