# ドメイン設計レビュー 005

ゼロベースレビュー（過去レビューは未参照）。対象: spec/domains/ 全6ドメイン。照合先: requirements.md / idea.md / scenario 全ファイル / pages/index.md / ADR-001〜006 / docs/backend_implementation_example.md。

検証したが問題なしと判断した主な点（記録のみ）:

- イベントの発行側・購読側は memo / knowledge / search の3ファイル間で完全に一致（`memo.sourceLinksChanged` / `document.sourceLinksChanged` の発行契機・同一UoW規則・ファンアウト含む）
- 参照先メソッドはすべて実在する（`TopicTrashService.restoreTopicSet` / `DocumentRepository.deleteSourceLinksByMemo` / `TrashQueryPort.listExpiredItems` 等、他ドメインから言及されるポート・サービスの定義を突合済み）
- 集約境界はすべてID参照、依存方向（trash→identity の `TrashRetentionDays` 参照含む）に循環なし
- 排他的状態（User の認証方式 / AiClientConnection / Memo / Topic / Document / SearchResultItem / TrashItem）はすべて直和型で表現され、`wasArchived` / `trashedWith` の復元規則も整合
- シナリオの主要パス（S-AC / S-TL / S-DT / S-SE / S-TR / S-ST / S-AI）とADRの決定事項（ADR-001 の3分岐、ADR-003 の同期消去、ADR-005 の冪等 consumer、ADR-006）はほぼ網羅されている
- pruner / emptyTrash の二重消去・冪等性、保持期限の遡及適用（照会時算出）も設計上成立する

対応が必要な問題点は以下の2件。

## 1.【中】AI の「明示的な全面書き直し」経路が未定義。空本文ドキュメントは AI から編集不能になる

- 観点: ビジネスロジック網羅（シナリオパスの欠落）
- 根拠:
  - requirements.md 4.3「全文指定は新規作成・**明示的な全面書き直し**に限定」、S-AI-04 手順2「ユーザーが明示的に全面書き直しを求めた場合に限り、AIは全文指定の書き直しを行える」
  - knowledge.md の AI 向け経路は `editDocumentByPatch`（MCP `edit_document`）のみで、全文置換モードが存在しない。ADR-006 はメモ側だけを扱い、ドキュメントの全面書き直し経路には触れていない
- 実害:
  - 全面書き直しを「本文全体を oldText にしたパッチ」で代替する運用も考えられるが、設計にその規定はなく、実装時に MCP ツール定義で手が止まる
  - さらに `DocumentBody` は空文字を許容する（「書きかけのドキュメントは正当な状態」）一方、`DocumentPatch` は `oldText` 非空を要求する（`EmptyPatchOldText`）。**人間が本文空のドキュメントを作り AI に執筆を頼むと、`edit_document` ではいかなるパッチも適用できず、AI 側に編集手段が存在しない**（空本文にマッチする oldText を構成できない）
- 対応案（いずれかを knowledge.md に明記する）:
  - `edit_document` に全文置換モード（例: `mode: "patch" | "replaceAll"`、replaceAll は明示的な全面書き直し専用である旨をツール定義に記載）を設け、application 層は `Document.edit`（全文）に直結する
  - または「全面書き直し・空本文への追記は本文全体を oldText とするパッチで行う」等の代替規則を明文化し、空本文ケースの扱い（例: 空本文のみ oldText 空を許す）を定める

## 2.【低〜中】トピック詳細の関連メモ一覧に必要な「documentId 群 → SourceLink」の一括逆引きポートがない

- 観点: 実装可能性（ポート定義漏れ）
- 根拠:
  - `getTopic` は「配下ドキュメント一覧 + 関連メモ = 配下ドキュメントの出典リンク集約」（knowledge.md ユースケース概要、P-07 / S-DT-02）を返すが、`DocumentRepository` にあるのは単一の `listSourceLinksByDocument(documentId)` のみ
  - 本設計は N+1 回避のための一括ポートを明示的に用意する方針を取っている（`listActiveByTopics`、`listSourceLinksByMemos`、`listByIdsIncludingTrashed` はいずれもその理由付きで定義済み）にもかかわらず、この経路だけ配下ドキュメント数分のループ照会になる
- 実害: 実装時に「方針どおり一括ポートを追加するのか、単発メソッドをループするのか」で判断が止まる。設計の自己一貫性からすれば定義漏れと読める
- 対応案: `DocumentRepository` に `listSourceLinksByDocuments(documentIds: readonly DocumentId[]): Promise<readonly SourceLink[]>` を追加し、`getTopic` の使用ポートとして明記する（関連メモの本文・削除済み表示は既存の `MemoRepository.listByIdsIncludingTrashed` で足りる）
