# ドメイン設計レビュー 002

ゼロベースレビュー。成果物（requirements / idea / scenario / pages / adr / domains / backend_implementation_example）とチェックリストのみで評価した。

全体として設計品質は高い。直和型による排他状態の表現、ID参照による集約境界、trash のオーケストレーション責務の一意化（ADR-003 同期方式）、イベント名・ペイロードの発行側と購読側の対応はいずれも一貫している。対応が必要な問題は以下の4件。

## 問題点（重要度順）

### 1. [高] 個別削除ドキュメントのセット復元経路で、復元要求したドキュメント自身が復元されない

- 対象: `spec/domains/knowledge.md`（`TopicTrashService.restoreTopicSet`）、`spec/domains/trash.md`（`RestorePolicy` / restoreDocument）
- 問題: 次の到達可能な状態で S-TR-02 の期待を満たせない。
  1. ドキュメント D を個別にソフトデリート（`trashedWith: null`、`topicId = T`）
  2. その後トピック T をソフトデリート（D は既に trashed のためセット対象外）
  3. ユーザーがゴミ箱で D の復元を選ぶ → `RestorePolicy.decideDocumentRestore` は `topicStatus: "trashed"` により `restoreWithTopic` を返す
  4. 仕様どおり `restoreTopicSet(T, docs)` を実行すると、D は `trashedWith: null` のため **`skippedDocuments` に分類されゴミ箱に残る**

  knowledge.md は「対象ドキュメントだけを引き抜く復元経路は設けない」「`restoreTopicSet` をそのまま使う」と明記しているため、ユーザーが復元を要求した当のドキュメントが復元されない結果になる。S-TR-02「確認のうえセットで復元される」に反する。
- 修正提案: いずれか一方を仕様化する。
  - (a) trash の `restoreDocument` ユースケース（分岐 restoreWithTopic）で、`restoreTopicSet` 実行後に、要求対象ドキュメントが `skippedDocuments` に含まれていれば同一 UoW 内で追加で `Document.restore` する（トピックは直前に復元済みのため不変条件は満たされる）
  - (b) `restoreTopicSet` に「明示的な追加復元対象（要求ドキュメント）」を受けるパラメータを設け、`trashedWith: null` でも要求対象だけは復元する

### 2. [中] SSO 初回登録時に、同一メールの既存パスワードアカウントが存在する場合の挙動が未定義

- 対象: `spec/domains/identity.md`（`User.registerWithSso` / registerOrLoginWithSso ユースケース、不変条件「email は全ユーザー間で一意」）
- 問題: `email` は全ユーザー間で一意（DB 制約 + `EMAIL_ALREADY_REGISTERED`）だが、SSO 初回ログイン（S-AC-02「初回なら自動でアカウントが作成され」）で IdP から返ったメールアドレスが既存のパスワードユーザーと衝突するケースの分岐が定義されていない。このまま実装すると insert が `ConflictError` になり、ユーザーには文脈のない失敗として現れる。実装者はここで方針判断（既存アカウントへのリンク / 明示エラーとログイン導線 / 別アカウント許容）を迫られて手が止まる。
- 修正提案: 方針を1つ決めて identity.md（および必要なら scenario/account.md の異常系）に明記する。現行の「認証方式は生成時に決まり以後変わらない」「共有・リンク機能はスコープ外」という前提に沿うなら、「既にパスワード登録済みのメールです。パスワードでログインしてください」という明示エラーにするのが最小の整合的解。

### 3. [低] 「削除済みの参照先」表示に使う読み取り経路の注記が用途と矛盾している

- 対象: `spec/domains/memo.md`（`findByIdIncludingTrashed`「復元・ハードデリート・ゴミ箱表示用（人間 UI 系ユースケース専用）」）、`spec/domains/knowledge.md`（`DocumentRepository.findByIdIncludingTrashed` /「人間 UI のゴミ箱系・trash ドメイン専用」）
- 問題: タイムラインの「→ ドキュメントX（削除済みのドキュメント）」表示（S-TL-07）と、ドキュメントの「元になったメモ（削除済みのメモ・投稿日時付き）」表示（S-DT-07）は、**trashed 状態の参照先のタイトル・投稿日時**を必要とする。これを取得できる唯一のポートは各 `findByIdIncludingTrashed` だが、その用途注記が「ゴミ箱系・trash 専用」に限定されており、タイムライン／ドキュメント閲覧ユースケースでの使用可否が読み取れない。忠実に従うと表示要件を満たす手段がなくなる。
- 修正提案: 注記を「trashed を扱う必要のある人間 UI 系ユースケース（ゴミ箱・出典リンクの削除済み表示を含む）」に改める。あわせて、出典表示は ID ごとの単発取得（N+1）になるため、必要なら `findByIdsIncludingTrashed`（一括）の追加を検討する旨を書いておくと実装で迷わない。

### 4. [低] pruner・検索インデックス consumer の依存が WorkerContainer の契約に収まらない

- 対象: `spec/domains/trash.md`（自動削除「`WorkerContainer` ベースで実装」）、`spec/domains/search.md`（インデックス更新 consumer）、`docs/backend_implementation_example.md`（`WorkerContainer` は `outboxRepository` + `idempotencyStore` のみで `unitOfWorkProvider` を持たない）
- 問題: pruner のフローは `TrashQueryPort` + UnitOfWork + memo/knowledge の各リポジトリを要求し、検索 consumer は memo/knowledge の読み取りポート + `SearchIndexPort` を要求するが、テンプレートの `WorkerContainer` にはいずれも存在しない。仕様に「WorkerContainer ベース」と書かれているため、実装者はコンテナ設計をどう拡張してよいか判断できず手が止まる。
- 修正提案: trash.md / search.md に、これらのワーカーは `WorkerContainer` を拡張した専用コンテナ（例: `unitOfWorkProvider`・`trashQueryPort`・`searchIndexPort` を追加した pruner / indexer 用コンテナ）で動かす旨を一文明記する（テンプレートの「スコープごとに独立したコンテナ型」の方針とも整合する）。

## 補足（対応必須ではない観察）

- `AiClientConnection.recordUsage` を `TransactionalRepository.save`（OCC）にそのまま乗せると、並行する AI API 呼び出し同士で `lastUsedAt` 更新が `OPTIMISTIC_LOCK_FAILURE` を起こし得る。ベストエフォート更新（失敗しても API 呼び出し自体は成功させる）である旨を実装時に決めておくとよい。
