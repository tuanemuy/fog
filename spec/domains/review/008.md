# ドメイン設計レビュー 008（ゼロベース）

対象: spec/domains/*.md（identity / memo / knowledge / search / trash / export）を requirements・scenario・pages・ADR-001〜006・docs/backend_implementation_example.md と照合。対応が必要な問題のみ記載する。

## 問題点（重要度順）

### 1. [実装可能性・高] TopicRepository / DocumentRepository の「継承分の再宣言」は型エラーになる

knowledge.md のポート定義は `extends TransactionalRepository<Topic, TopicId>`（/ `<Document, DocumentId>`）としたうえで、`findById` を `(userId: UserId, id: TopicId)` の 2 引数に「再宣言」している。基底契約の `findById(id: TId)` に対し、必須引数が多い関数型は代入不能であり、TypeScript ではこの再宣言は `incorrectly extends` のコンパイルエラーになる。実装時に必ず手が止まる。

- memo.md の `MemoRepository` は同じテナント分離を実現するために **extends せず**「OCC 契約に従う」と記述するだけの方式を採っており、正しい。knowledge 側だけ extends を残しているのはドメイン間の不整合でもある
- 対応案: (a) knowledge の両リポジトリも extends をやめ memo と同じ「契約準拠」方式に統一する、または (b) テンプレートに userId スコープ付きの基底契約（例: `UserScopedTransactionalRepository<TEntity, TId>`）を追加し、memo / knowledge がそれを使う旨を明記する。いずれかに揃えること（`save` / `delete` / `insert` は基底シグネチャのままで問題ない）

### 2. [ドメイン間整合・高] createDocument（AI 経路）が使う `listByIdsIncludingTrashed` は memo 側で「AI 向けユースケースでは使用しない」と規定されており矛盾

knowledge.md のユースケース `createDocument` は「UI / MCP `create_document`」の共通経路で、出典メモの実在・非ゴミ箱検証に `MemoRepository.listByIdsIncludingTrashed` を使うと明記している。しかし memo.md は同メソッドの使用範囲を `findByIdIncludingTrashed` と同じ（= AI 向けユースケースでは使用しない）と規定しており、正面から矛盾する。実装者はどちらに従うべきか判断できない。

- 対応案: (a) `MemoRepository` に active 限定の一括読み取り（例: `listActiveByIds(userId, ids)`）を追加し、createDocument の出典検証はそれを使う（存在しない/ゴミ箱内はいずれも「結果に含まれない → エラー」で S-AI-03 異常系を満たし、AI にゴミ箱内の存在事実も漏れない）、または (b) memo.md の使用制限に「createDocument の出典検証のみ例外（結果はエラー種別を区別せず一律失敗にする）」の但し書きを加える。(a) を推奨（規則の例外を作らない）

### 3. [アーキテクチャ適合性・中] knowledge.md のユースケース ★（人間 UI 専用）マークが不完全で、AI 公開面が requirements 4.5 と一致しない

knowledge.md で ★ が付いているのは `rollbackDocument` と `listDocumentRevisions` のみだが、requirements 4.5 の AI 公開インターフェース（search / get / list_topics / recent_memos / post_memo / update_memo / create_topic / update_topic / create_document / edit_document / delete）に含まれない以下も人間 UI 専用のはずであり、未マークのまま実装すると AI 側 presentation に誤配線されるリスクがある。

- `editDocument`（人間 UI 用。変更理由省略時に既定値を補完する経路であり、AI に配線すると「変更理由必須」が骨抜きになる。AI 経路は `editDocumentByAi` が別に存在する）
- `getTopic`（AI には list_topics のみ。関連メモ表示に `listByIdsIncludingTrashed` を使うため、AI に配線するとゴミ箱内メモの存在が漏れる）
- `listDocumentSourceMemos` / `listDocumentsReferencingMemo`（IncludingTrashed 読み取りで「削除済み」表示を組み立てる人間 UI 向けの読み取り）

対応: 上記 4 ユースケースに ★ を付し、AI 公開ユースケースの全量が requirements 4.5 の動詞リストと 1:1 対応することを knowledge.md 上で明示する。

### 4. [ドメイン間整合・中] AiClientConnectionRepository がテナント分離の横断規則に従っていない

domains/index.md は「外部入力の ID を受けるメソッドは userId を第一引数に取る。ユースケース層の追加検証に依存しない構造的保証とする」と定めるが、identity の `AiClientConnectionRepository` には userId スコープ付きの単体取得がない。`revokeAiClientConnection`（S-AC-06）の対象 connectionId は設定画面からの外部入力であり、継承の `findById(id)` で引くと他ユーザーの接続を失効できてしまう（防ぐにはユースケース側で `connection.userId` 照合が必要になり、横断規則の方針と矛盾する）。

- 対応案: `findById(userId: UserId, id: AiClientConnectionId)` のスコープ付き取得を定義する（問題 1 の解決方式に合わせる）。`findActiveById` はトークン由来の信頼済み ID を扱う認可ミドルウェア専用である旨を明記して現行シグネチャのままとし、外部入力経路（revoke）とは経路を分ける

### 5. [ドメイン間整合・低] `DocumentRepository.deleteSourceLinksByMemo(memoId)` が userId を取らない書き込みになっている

呼び出し元（trash のハードデリート系ユースケース・pruner）の memoId は外部入力起点であり、直前の `findByIdIncludingTrashed(userId, memoId)` による所有権確認を実装者が省くと他ユーザーのリンクを消せてしまう。横断規則（構造的保証）に合わせ `deleteSourceLinksByMemo(userId: UserId, memoId: MemoId)` とするか、「同一 UoW 内で userId スコープ付き再取得に成功した場合のみ呼ぶ」契約であることをポート仕様に明記すること。
