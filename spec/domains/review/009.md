# ドメイン設計レビュー 009（ゼロベース）

対象: spec/domains/index.md, identity.md, memo.md, knowledge.md, search.md, trash.md, export.md
照合先: requirements.md, idea.md, scenario/ 全ファイル, pages/index.md, adr/001〜006, docs/backend_implementation_example.md

観点: 実装可能性（フィールド・型・シグネチャの完備 / 直和型 / ポート・VO定義漏れ / 型整合）、アーキテクチャ適合性（インフラ非依存 / ロジック配置 / ID参照 / 循環依存 / テナント分離）、ビジネスロジック網羅（シナリオ全パス / 不変条件）、ドメイン間整合（共有型 / イベント発行・購読 / 参照先メソッドの実在・シグネチャ一致）。

## 指摘事項

### 1. [低] memo.md: `ExpectedVersion<Memo>` の発行点の記述が自ドメインのインターフェース定義と矛盾

memo.md「ポート > MemoRepository」の規約文は

> `ExpectedVersion<Memo>` トークンは `findById` / `findByIdIncludingTrashed` のみが発行し、`save` / `hardDelete` は必須引数として受ける

としているが、同じインターフェース定義内の `listTrashed`（`Versioned<TrashedMemo>[]`）と `listActiveByIds`（`Versioned<ActiveMemo>[]`）もトークンを発行している。knowledge.md はむしろ「一覧系のうち書き込みに接続するものは `Versioned` で返す（**memo 側の `listTrashed` と同規約**）」と、memo の一覧系がトークン発行点であることを前提にしており（trash の emptyTrash / セット復元フローが読み直しなしで書き込むための設計）、この規約文だけが古い。

対応: memo.md の当該文を「トークンは `findById` / `findByIdIncludingTrashed` および `Versioned` を返す一覧系（`listTrashed` / `listActiveByIds`）が発行する」に修正する。実装への影響はインターフェース定義側が正であり、コード変更は不要。

## 問題なしと確認した主な論点（抜粋）

- ドメイン間の参照先メソッドはすべて定義元に実在し、シグネチャ（userId 第一引数のテナント分離を含む）が一致する: memo ハードデリート時の `listSourceLinksByMemo` → `hardDelete` → `deleteSourceLinksByMemo` の同期オーケストレーション（memo.md / knowledge.md / trash.md で三者一致）、getTimeline の `listSourceLinksByMemos`、getTopic の `listSourceLinksByDocuments` + `MemoRepository.listByIdsIncludingTrashed` 等
- イベントは発行側（エンティティ振る舞い / trash ユースケース直接発行）と search consumer の処理表が全種で対応し、`sourceLinksChanged` 系の「同一 UoW で影響先確定 → 発行」の規則も 4 ファイル間で矛盾なし。ゴミ箱内 ID を検索結果に露出させないファンアウト規則も一貫
- 排他的状態は直和型で網羅（User の認証方式、AiClientConnection の失効、Memo / Document / Topic のライフサイクル、`wasArchived` / `trashedWith`）。`ExpectedVersion<T>` のファントム型は共変であり、`Versioned<ActiveMemo>` のトークンを `ExpectedVersion<Memo>` 引数に渡す等の設計はコンパイル可能
- シナリオ全パス（S-AC-01〜07 / S-TL-01〜07 / S-DT-01〜09 / S-SE-01〜03 / S-AI-01〜06 / S-TR-01〜05 / S-ST-01〜02）と ADR-001〜006 の全分岐に対応するユースケース・サービス・ポートが存在する。ADR-001 の 3 分岐（`RestorePolicy.decideDocumentRestore`）、セット復元時の `skippedDocuments` 追加復元、emptyTrash の展開重複除去、pruner のユーザー別保持日数適用まで手当て済み
- インフラ非依存（OAuth / セッション / 埋め込み生成 / zip / パッチ以外の検索統合方式はすべてポートの背後）、ドメイン層の型依存は identity ← memo ← knowledge の一方向で循環なし。application 層での横断利用（memo の getTimeline が knowledge のポートを併用等）は明示された設計判断であり型循環を生まない

## 結論

対応が必要な問題は上記 1 件（軽微・ドキュメント修正のみ）。実装を止めるレベルの欠落・型不整合・ドメイン間矛盾は検出されなかった。
