# メモアプリ 要件定義

## 1. 目的・コンセプト

人が書き留めた言葉の断片を、AIが紡いで価値にする。

- ユーザーは雑にメモを投稿するだけでよく、整理を求められない。追加・閲覧・復元といった直接操作は人間にとっても快適であること
- 整理・検索・ドキュメント化はAIが担う
- アプリ本体は堅牢な土台（データモデル・API・UI）に徹し、賢さはAI側に置く

### スコープ外

- 会話ログの保存はLLMアプリ側の責務とし、本アプリは扱わない。本アプリに残るのは「残す価値が確定したもの」のみ
- AIの振る舞いそのもの（プロンプト、エージェント設計）は本アプリの外側

## 2. ユビキタス言語とドメインモデル

三層モデルを採用する。

| 用語 | 定義 |
|---|---|
| メモ | タイムラインに積まれるタイムスタンプ付きの最小単位。時系列・追記型・非構造テキスト |
| ドキュメント | 主題を持つ編集型の文書。構造化テキスト（Markdown/HTML互換） |
| トピック | ドキュメントを束ねるコンテナ。文脈の単位 |

### モデル上のルール

- メモはタイムラインに直接投稿される。日付ごとの表示はUIのグルーピングとして実現する
- メモはアドレス可能な最小単位（アトム）であり、内部構造を持たない
- ドキュメントは必ずいずれかのトピックに属する

### 出典

- メモはドキュメントの出典（ソース・引用元・参照先）になれる
- 出典は、ドキュメント作成時に紐付けられる出典メモへの参照リンクとして表現される。ドキュメントがいつのメモから生まれたかは、このリンクにより記録される
- 複数の考えを含む長文メモのどの部分を出典とするかは、ドキュメント作成時にAIが判断する

## 3. 主要ユースケース

1. **雑に記録する** — 思いついたことをタイムラインに投稿する。分類・整理は不要
2. **思い出して探す** — 「あの話どこだっけ」とAIに聞くと、メモ・ドキュメントを横断して探し出してくれる
3. **議論をドキュメントに起こす** — 壁打ちで深まった内容を、AIがドキュメントとして起こし、出典メモを紐付けて適切なトピックへ配置する（なければトピックを新設する）

## 4. 機能要件

### 4.1 タイムライン（メモ）

- メモを投稿できる。タイムスタンプは自動付与する
- メモの本文はプレーンテキストとする。Markdown軽装飾（箇条書き・コードブロック等）は表示上許容するが、データモデル上は非構造テキストとして扱う
- タイムラインは日付見出しでグルーピング表示する
- タイムラインは汎用の絞り込み手段（キーワード、日付へのジャンプ）を持つ。トピックを起点とした閲覧はタイムラインの機能とせず、トピック詳細画面の関連メモ一覧（4.2）として提供する
- 出典関係を双方向に表示する
    - メモ側：出典になっているメモに参照先ドキュメントへの導線（例:「→ ドキュメントX」）を表示し、タップで遷移できる。複数ドキュメントの出典になった場合は導線を複数並べる
    - ドキュメント側：「元になったメモ」一覧を本文とは別領域に投稿日時付きで表示し、各メモへ遷移できる
    - 出典リンクはリビジョンではなくメモを指す。元メモが編集された場合は最新版が見え、当時の内容は履歴で辿れる。元メモがソフトデリートされた場合は「削除済みのメモ」として表示を残す

### 4.2 ドキュメントとトピック

- ドキュメントの本文はMarkdown・HTMLとの互換を想定した構造化テキストとする
- トピックの作成、ドキュメントの作成・編集ができる
- ドキュメント作成時に出典メモを紐付けられ、出典リンクが自動生成される
- トピックはオプション属性として短い説明文（description、プレーンテキスト数行）を持つ。トピック一覧やヘッダーに表示され、AIは作成先トピック判断の材料に使える
- トピック詳細画面に、当該トピック配下のドキュメントの出典になっているメモの一覧（関連メモ）を表示する
- トピックは archived フラグを持つ。アーカイブ済みトピックは一覧の主要領域から退くが、検索には引き続きヒットし、期限で消えることもない
    - UI上は「アーカイブ」という用語を出さず「完了にする」というワンアクションとして提示する。完了済みトピックは一覧下部の「完了済み」セクションに畳む。削除操作は別の場所（長押しメニュー等）に置き、削除とアーカイブが並ぶ選択場面を作らない

### 4.3 編集履歴と削除（メモ・ドキュメント共通）

- リビジョン履歴
    - メモ・ドキュメントとも、不変リビジョンの線形履歴を持つ。編集ごとに新リビジョンを積み、履歴は削除しない
    - ドキュメントの各リビジョンには「誰が（人間 / どのAIクライアントか）・いつ・なぜ（変更理由の一行サマリ）」を記録する
    - メモのリビジョンには「誰が・いつ」のみ記録し、変更理由は持たない
    - 保存形式は毎リビジョン全文スナップショットとし、差分は表示時に計算する
    - UI：履歴一覧、任意二点間の差分表示、ワンタップロールバック（過去リビジョンと同内容の新リビジョンを積む方式）を提供する
- AIへの編集インターフェース
    - 原則パッチ形式（該当箇所の置換指定）とする。全文指定は新規作成・明示的な全面書き直しに限定する
- 削除
    - メモ・ドキュメント・トピックの削除はすべて、ソフトデリート → ゴミ箱 → ハードデリートの経路をとる
    - トピックのソフトデリート時は配下ドキュメントもセットでソフトデリートし、復元時はセットで復元する
    - ゴミ箱UI：ソフトデリート済み項目の一覧・復元・個別ハードデリート・全件空にする操作を提供する
    - 保持期限（既定30日、設定可能）経過後、自動でハードデリートする
    - ハードデリートはリビジョン履歴ごとの完全消去を意味する
    - **ハードデリートは人間のUI操作専用とし、AIには許可しない。** 不可逆操作をAPIから構造的に排除し、「AIが何をしても人間が復元できる」ことを本アプリの信頼モデルの核とする

### 4.4 検索

- SQLite FTS5 による全文検索を単一の検索として提供する。検索方式の選択をAIに委ねない
- トピックによるスコープ絞り込みができる
- メモとドキュメントを横断して検索できる
- ゴミ箱内の項目は検索にヒットしない。アーカイブ（完了）済みトピックの内容はヒットする
- 検索結果
    - 検索APIは結果を一切加工しない。要約・再構成はAIクライアントの責務とする
    - 返すのは事実データのみ：ID・種別（メモ/ドキュメント）・原文スニペット・タイムスタンプ・所属トピック・出典リンク先ID
    - 検索は全文を返さない（短いメモは実質全文になる）。切り詰め方式は実装詳細とし、要件では規定しない
    - 原文の完全性が必要な場合、AIはIDを用いて単体取得API（get）で全文を取る。getは検索専用ではなく、パッチ編集の前提として存在する基本操作である

### 4.5 AI接続

- リモートMCPサーバーを主要な接続形態とする
- MCPを持たないクライアント向けに、同一の認可基盤の上にREST APIを併存させる
- APIの設計原則：冪等・失敗しても壊れない・少ない動詞
- MCPサーバーは自己記述的であること。ツール定義とサーバー指示に、操作方法と推奨の振る舞い（ドキュメント化の提案タイミング、作成先トピックの選び方等）を含める
- アプリの保証（履歴・削除の安全性）はガイダンスに依存しない。ガイダンスを無視するAIクライアントに対しても安全性が保たれることはAPI設計の責務とする

#### 公開するインターフェース（動詞レベル。フィールド定義は設計工程で行う）

- 読み取り
    - search — 全文検索。トピックによる絞り込み可
    - get — メモ/ドキュメントの全文取得。パッチ編集の前提
    - list_topics — トピックと配下ドキュメントの一覧。作成先トピック判断の材料
    - recent_memos — タイムラインの直近の取得。直近の文脈把握に用いる
- 書き込み
    - post_memo — メモの投稿
    - update_memo — メモの修正（履歴は自動で積まれる）
    - create_topic / update_topic — トピックの作成・更新。アーカイブフラグの変更を含む（可逆であるためAIに許可する）
    - create_document — ドキュメントの作成。出典メモのID群を渡すと出典リンクが自動生成される
    - edit_document — パッチ形式の編集。変更理由を必須とする
    - delete — ソフトデリートのみ

#### 公開しないインターフェース

- ハードデリートおよびゴミ箱操作（一覧・復元・空にする）。ゴミ箱の中身はAIから見えない世界とし、復元も人間のUI専用とする
- 履歴の閲覧・ロールバック。ロールバックは人間の安心装置であり、まずは非公開とする。必要が生じた場合も、履歴の読み取りのみを追加公開の候補とする

## 5. 非機能要件

### 5.1 ユーザーモデルと提供形態

- 公開サービスとして提供する
- マルチテナント構成だが、データは利用者個人に閉じる。ユーザーは自分のメモ・ドキュメント・トピックのみにアクセスできる。共有・コラボレーション機能は現段階のスコープ外
- ユーザーのドメインデータはユーザー単位の SQLite-backed Durable Object に物理分離される。分離の保証は列条件（`user_id`）ではなく到達可能性（他ユーザーの Durable Object stub を得る経路が存在しないこと）に依る

### 5.2 認証・認可

- 人間の認証：パスワード認証または SSO（Google / Apple 等の OAuth）
- AIクライアントの認可：OAuth 2.1 ベース。ユーザーが自分のAIクライアントに対して自分のデータへのアクセスを許可する（コネクタ追加 → ブラウザでログイン・許可 → 以後AIがユーザーの代理として読み書き）
- 権限の非対称性をトークンスコープで構造的に表現する。AI用トークンにはハードデリート権限が存在しない
- リビジョンの「誰が」は、クライアントごとのトークン識別により記録する

### 5.3 永続化

- データはクラウドに保存し、一般的なSaaS水準の永続化・バックアップ・復元手段を備える。リージョン等の詳細は実装時に選定する
- 1 ユーザーあたりのストレージ上限は 1 Durable Object あたり 10 GB で、本体データと全文検索インデックスの合計で見る。**Outbox のイベント行（`outbox_events`）とリセット依頼のスロットル窓（`reset_request_windows`）も同じ上限に算入する**（前者は保持期間ぶんの終端行を、後者は掃除されるまでの窓行を抱える）
- **検索インデックスは本体の更新と同一トランザクションで確定する（即時整合）。** 投稿・編集した項目は直後の検索から必ずヒットする
- **外部への副作用（メール送信等）とイベントの配送は結果整合である。** 配送は at-least-once・順序保証なしで、同じ通知が複数回届きうる。イベント間の順序に依存しない
- オフラインには対応しない
- ユーザーは自分の全データを可搬形式（Markdown等）でエクスポートできる
