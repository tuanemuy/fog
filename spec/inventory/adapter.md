## 非同期配送（relay / consumer / DLQ）

**3つとも層はアダプターであり、`spec/inventory/usecase.md` には行を足さない**（`.adr/013`）。mail consumer は「DO の送信材料 RPC の2分岐 → `MailSender`」という2ポートの合成を持つのでユースケースに見えるが、**業務判断はすべて RPC の向こう側（DO の中）にあり、consumer 側には1つも無い。判断が無いものはユースケースではない。** Outbox へ移る前のメール送信ジョブも同じ形でアダプター側にしか行を持たなかった。**consumer が1つしかない現状での判断である** — consumer が「どのイベント型をどう処理するか」の分岐を持ち始めたら帰属を再検討する。

| ID | 要素 | 定義場所 | 実装されるべき振る舞いの要点 |
|----|------|---------|------------------------------|
| ADP-outbox-relay-001 | Outbox relay（DO の `alarm()` の中） | spec/async/index.md#配送機構の契約と責務 | **1本の Alarm が `jobs` と `outbox_events` を多重化する**。`setAlarm(min(min(jobs.next_run_at) WHERE status IN ('pending','running'), min(outbox_events.next_run_at) WHERE status IN ('pending','publishing')))` で張り、**lease 中の行は `max(next_run_at, lease_until)` で算入し**（算入しないと空振り起床を繰り返す）、**両方が空のときだけ `deleteAlarm()`**。`alarm()` の順序は **(1) 再武装 + 永続化の確認 → (2) migration ゲート → (3-a) relay パス → (3-b) jobs パス → (4) 両表から再計算して張り直す**で、**relay は `queue.send()` を await するので `await` を1つも挟まないゲートの中には置けない**。**件数上限は各パスが独立に持ち、毎回の起床で両方を必ず1回通す**（共有すると片方の滞留がもう片方を飢えさせる）。**1パスは3相で、Queue への送信だけがトランザクションの外にある** — (1) `transactionSync` で実行可能な行を上限件数まで claim（`publishing` + `lease_until` + `owner_token` を CAS）/ (2) トランザクション外で Queue へ publish / (3) `transactionSync` で `published` へ落とす。**claim で書く `owner_token` は行ごとに採り直す** — 1回の起床につき1個の値を全 claim 行へ共有しない（共有すると1件の漏出が同じバッチ全行の呼び出しガードを通す）。暗号論的乱数から採り、時刻・連番・DO 識別子から導かず、長さは 128 bit 以上（`ADP-outbox-events-001`）。**`owner_token` は再利用可能な秘密なので、publish の失敗ログにも Queue メッセージ全体を出さない**（載せてよいのは `event.id` と `type` まで）。失敗は `attempt` を進め backoff で先送りし、上限超過は `quarantined` + `terminal_reason`。**at-least-once の根拠は相2と相3のあいだにあり**、そこで DO がリセットすると lease 満了後に同じ行が再 claim され再 publish される。**`alarm()` から throw しない規則は relay にも掛かる**（1行の失敗が他の配送を止めない per-row catch）。**fail-closed で止まっている DO は relay もしない**（ゲートで戻るので (3-a) に到達しない）が、**滞留は失われた配送ではない**。prune は同じ末尾処理に載せ、保持期間を過ぎた `published` を上限件数だけ消す（`quarantined` は残す）。**Queue メッセージが運ぶのは `event.id` / `type` / `payload` / 宛先 DO の routing key / `owner_token` の5項目だけであり、行の他の列は載せない — メッセージは行の写しではない**（特に `aggregate_id`（窓キー）は載せない。同一アドレス・同一窓に対して安定した仮名なので、載せると DLQ 上で複数のメッセージを同じ宛先へ相関させる材料になる）。各項目は行の値をそのまま運び、Queue 側で組み立て直さない。**routing key だけは relay が publish 時に押す項目であり、行にもドメイン payload にも無い** |
| ADP-mail-consumer-001 | mail consumer（request Worker の `queue()` ハンドラ） | spec/async/index.md#consumer-の一覧と責務 | **初期で唯一の consumer である**。対象 `event.type` は `identity.passwordResetRequested`。責務は「発行元 bucket へ**送信材料 RPC** を打ち、`send` なら `MailSender` を呼ぶ／`nothing-to-send` なら no-op する。どちらでも ack する」だけで、**宛先の解決・トークンの生存確認・supersede の判定・冪等キーの導出はすべて DO 側にある**。**応答は `send` / `nothing-to-send` の2分岐でこれが全数**であり、`nothing-to-send` は**理由を1つも載せない空**で失敗でもない（理由を載せると宛先の登録有無が DO の外へ漏れる）。**呼び出しガードは3条件** — (a) その `event.id` の行が存在する / (b) `quarantined` でない / (c) 呼び出しが持つ不透明な `owner_token` が行の値と一致する。**`status` は照合しない** — consumer が RPC を打つのは relay が `published` へ落とした後なので、`status='publishing'` を条件にすると正常系の配送が全滅する。**二重送信の抑止は `status` ではなく `providerIdempotencyKey`（DO が `event.id` から導出し `send` の応答に載せる）が担い、役割を混ぜない**。**`send` の応答から得た `providerIdempotencyKey` を `MailSender.sendPasswordResetMail(to, resetToken, providerIdempotencyKey)` の第3引数へそのまま渡す**（`ADP-identity-016`）— consumer 側で組み立て直さず、導出鍵も持たない。渡さないと at-least-once 下で重複メールを止める機構が消える。**処理済み `EventId` を保持しない**（冪等化は provider 側のキーと送信材料 RPC の再確認の2段）。**メール provider の秘密は request Worker に帰属する**（state Worker から移った。`.dev.vars.example` の追記は #51）。**consumer 側の catch 境界を持つ**（失敗は Queue の retry へ落とす）。**エラーログに載せてよいのは `event.id` と `type` までで、Queue メッセージ全体も `owner_token` も出さない**（`ADP-outbox-events-001`） |
| ADP-dlq-handler-001 | DLQ ハンドラ（request Worker の `queue()` ハンドラ） | spec/async/index.md#責務分界と-dlq | **責務分界は「Queue に入る前か後か」の1本だけである** — relay が publish できない失敗は発行元 DO の `quarantined`、consumer の失敗は Queue の retry → DLQ。**発行元 DO へ ack を書き戻さない**（書き戻し自体が at-least-once で失敗しうるため三段目の隔離先が要る）。**operator 導線は2つ** — DO の maintenance 経路（`list-quarantined-events` / `requeue-quarantined-event`）と本ハンドラであり、**end-to-end の配送は1箇所で観測できない**。**fail-closed の DO へ送信材料 RPC を打った consumer はここへ落ちる**（ゲートが `SystemError` を返し retry を焼き切る。デプロイのスキュー期間限定で、復旧は DLQ の再駆動）。**DLQ のメッセージは `owner_token` を運ぶので、外部の監視基盤・ログ集約先へ転送しない**（転送する設計を足すなら `.adr/013` の判断へ戻る）。**ログに載せてよいのは `event.id` と `type` まで**（`ADP-outbox-events-001`）。**運用値の制約2本**（`DLQ 保持期間 < リセットトークン TTL` / `Queue 最大 retry + DLQ 保持期間 ≤ published 行の保持期間`。実値の確定は #38）を満たす前提で組む — 後者を落とすと prune が行を消した後の再駆動が必ず `nothing-to-send` になり、恒久的に空振りする |
