# シナリオ: AI連携

前提: ユーザーはAIクライアント（LLMアプリ）を接続済みである（→ S-AC-05）。AIはユーザーの代理として読み書きする。接続時に、利用できる操作と推奨する振る舞いをAIへ提示する。

## S-AI-01 AIに雑に記録してもらう

1. ユーザーがLLMアプリとの会話中に「これメモしといて」と頼む
2. AIがメモを投稿する。タイムスタンプは自動付与される
3. ユーザーが後で fog のタイムラインを開くと、そのメモが表示されている。リビジョンの「誰が」にはAIクライアント名が記録されている

異常系:

- 接続が失効している場合は認可エラーとなり、AIはユーザーに再接続を促す
- 空の本文はエラーになり、メモは作成されない

## S-AI-02 AIに思い出して探してもらう

1. ユーザーが「あの話どこだっけ」とAIに聞く
2. AIがメモとドキュメントを横断検索する。必要に応じてトピックで絞り込む。直近の文脈が要るときは最近のメモを、トピック構成の把握にはトピック一覧を取得する
3. 検索結果には事実データだけが含まれる（識別子・種別・スニペット・タイムスタンプ・所属トピック・出典リンク先の識別子）。全文が必要なら対象を単体で取得する
4. AIが見つけた内容をユーザーに提示する。要約・再構成はAI側の責務

エッジケース:

- ゴミ箱内の項目は検索にも単体取得にも現れない（AIからはゴミ箱の中身は見えない）
- 完了済みトピックの内容はヒットする

## S-AI-03 AIに議論をドキュメントに起こしてもらう

1. ユーザーがAIと壁打ちして議論が深まり、AIが（またはユーザーの指示で）ドキュメント化を提案する
2. AIが既存トピックを確認し、適切な作成先を判断する。適切なトピックがなければ新設する
3. AIが本文と出典メモを指定してドキュメントを作成する。出典リンクは自動生成される
4. ユーザーが fog でドキュメントを開くと、本文と「元になったメモ」一覧が確認できる

エッジケース:

- 長文メモの一部だけが出典の場合も、リンクはメモ単位で張られる（どの部分かの判断はAI側）
- 存在しないメモを出典に指定した場合はエラーとなり、ドキュメントは作成されない（部分的に壊れた状態を作らない）
- 存在しない・削除済みのトピックを作成先に指定した場合も同様にエラーとなり、ドキュメントは作成されない

## S-AI-04 AIがメモ・ドキュメントを修正する

1. ユーザーが「さっきのメモ、〜に直しといて」と頼む
2. メモは全文置換、ドキュメントは部分編集（変更理由必須）で修正される。履歴は自動で積まれる。ユーザーが明示的に全面書き直しを求めた場合に限り、AIはドキュメントを全文置換できる。この場合も履歴は積まれる
3. ユーザーは履歴画面で「どのAIが・いつ・なぜ」変えたかを確認でき、気に入らなければロールバックできる（→ S-TL-05 / S-DT-06）

異常系:

- 変更対象が見つからない（本文が既に変わっている等）場合はエラーとなり、ドキュメントは変更されない。AIは最新の本文を取得して再試行する
- ドキュメントの編集時に変更理由を省略した場合はエラーとなる
- ソフトデリート済みの項目を修正または削除しようとすると、「存在しない」扱いのエラーになる（ゴミ箱の中身はAIから見えない世界を貫く）

## S-AI-05 AIが削除する → 人間が復元する

1. ユーザーが「あのメモ消しといて」と頼み、AIがソフトデリートする。メモ・ドキュメント・トピックのいずれも対象にできる
2. 項目はゴミ箱に移る。トピックを削除した場合は配下ドキュメントもセットでゴミ箱に移る（人間UIの削除と同じ挙動 → S-DT-09）。AIにはハードデリートとゴミ箱の操作が存在しないため、これ以上は消せない
3. 実は必要だったと気づいたユーザーは、fog のゴミ箱から自分で復元する（→ S-TR-02）

補足:

- ガイダンスを無視するAIクライアントに対しても、ハードデリートを操作として提供しないため安全性は保たれる

## S-AI-06 AIがトピックを整理する

1. AIがトピックの作成、名前や説明文の更新、完了状態の変更を行う
2. アーカイブは可逆であるためAIに許可されている。ユーザーはトピック一覧でいつでも完了を解除できる
