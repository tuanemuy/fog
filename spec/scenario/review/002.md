# シナリオレビュー 002

ゼロベースレビュー（requirements.md / idea.md / ADR-001 / ADR-002 とシナリオ全ファイルの照合）。対応が必要な問題点のみ記載する。

## 1. 出典リンク先がハードデリートされた場合の表示が未定義

- 対象: `spec/scenario/trash.md`（S-TR-03 / S-TR-05）、`spec/scenario/timeline.md`（S-TL-07）、`spec/scenario/document.md`（S-DT-07）
- 問題: requirements.md 4.1 は出典メモが「ソフトデリートされた場合」の表示（「削除済みのメモ」として残す）のみを規定しており、シナリオもソフトデリート時の挙動しか書いていない。しかしゴミ箱シナリオでは出典メモ・参照先ドキュメントのハードデリート（手動 S-TR-03 / 全件 S-TR-04 / 自動 S-TR-05）に到達できる。このとき、ドキュメント側の「元になったメモ」一覧の当該行、およびメモ側の「→ ドキュメントX」導線がどうなるか（表示ごと消えるのか、「完全に削除されたメモ」として恒久表示が残るのか）がどのシナリオにも書かれていない。ソフトデリート時は「復元すれば再び機能する」と定義済みなだけに、復元不能になった後の状態の欠落が目立つ
- 提案: S-DT-07 と S-TL-07 のエッジケースに「参照先がハードデリート済み（自動削除含む）の場合」の挙動を追記する。挙動の決定（表示除去か恒久的な削除済み表示か）は設計判断を伴うため、必要なら ADR として記録する

## 2. ソフトデリート済み項目に対する書き込み系APIの挙動が未定義

- 対象: `spec/scenario/ai.md`（S-AI-04 / S-AI-05）
- 問題: 読み取り系については「ゴミ箱内は search にヒットせず get でも取得できない」（S-AI-02）と定義されているが、書き込み系が未定義。AIが把握しているIDのメモ・ドキュメントが（人間または別セッションのAIにより）ソフトデリートされた後に update_memo / edit_document / delete を呼んだ場合の挙動がどこにも書かれていない。「AIからはゴミ箱の中身は見えない世界」という原則からすればリソース不在エラーになるべきだが、シナリオとして確認できない
- 提案: S-AI-04（または S-AI-05）の異常系に「対象がソフトデリート済みの場合、APIは存在しない扱いのエラーを返し、変更は行われない」を追記する

## 3. 人間編集時の変更理由の任意性が requirements と不整合

- 対象: `spec/scenario/document.md`（S-DT-05）
- 問題: requirements.md 4.3 は「ドキュメントの各リビジョンには『誰が・いつ・なぜ（変更理由の一行サマリ）』を記録する」と規定し、AI経由の edit_document では変更理由必須（S-AI-04 で省略はエラー）としている。一方 S-DT-05 は人間の編集について「変更理由（一行サマリ）を残せる」と任意の表現になっており、省略した場合にリビジョンの「なぜ」がどう記録されるのかが不明。要件の「各リビジョンに記録する」との整合が取れていない
- 提案: 人間編集時の変更理由を必須とするか、任意とするなら省略時の記録内容（空欄を許容する等）を明記し、要件からの逸脱であれば要件側の修正または ADR 化を行う

## 4. SSOのみで登録したユーザーのパスワード関連フローが未定義

- 対象: `spec/scenario/account.md`（S-AC-07）
- 問題: S-AC-07 の「設定画面から現在のパスワードを入力のうえ変更できる」はパスワード登録ユーザーが前提。S-AC-02 のSSO登録ユーザーには現在のパスワードが存在せず、このフローに乗れない。設定画面でどう扱われるか（項目を出さない等）が書かれておらず、利用者視点で行き止まりになる
- 提案: S-AC-07 のエッジケースに「SSOのみで登録したユーザーの場合」の扱い（パスワード変更項目を表示しない、またはパスワード新規設定の導線を示す等）を追記する
