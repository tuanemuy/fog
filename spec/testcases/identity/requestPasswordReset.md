# テストケース: requestPasswordReset

[usecases/identity.md](../../usecases/identity.md) の requestPasswordReset に対するテストケース。

**中心的な検証点は「登録済み / 未登録 / SSO 専用 / スロットル中の4ケースで処理経路が完全に一致すること」である。** どのケースでも同じトランザクションで送信ジョブの行を1行書き、同じ起床を張り、同じ応答を返す。違うのは行の中身だけである — 行を書くか書かないかで分岐させると、その差が測定可能な処理時間差になり、登録済みメールの列挙オラクルになる。

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| パスワードの検証材料を持つクレデンシャルが登録済み | 登録済みメールでリセットを依頼する | 同一トランザクションで送信ジョブの行が1行書かれ、起床が張られる。行の中身は「送る側」で、起床時に `MailSender.sendPasswordResetMail` が同メール宛にリセットメールを送る。正常終了（`void`） | |
| 該当メールのクレデンシャルが未登録 | 未登録メールでリセットを依頼する | **同じトランザクションで送信ジョブの行が1行書かれ、同じ起床が張られ、同じ応答が返る。** 行の中身は宛先を持たない「送らない側」で、起床した時点で何も送らずに完了する | |
| 同一メールのクレデンシャルは存在するが、パスワードの検証材料を持たない（SSO 専用アカウント） | そのメールでリセットを依頼する | **送らない側**である。行の書き込み・起床・応答は上の2ケースと完全に一致する。`kind = 'email'` の mapping 行は SSO 登録でも置かれるので、**判定は「mapping の有無」ではなく「`passwordVerifier` の有無」で行う** | |
| 登録済み / 未登録 / SSO 専用 / スロットル中の4ケース | それぞれの応答と処理経路を比較する | すべて同一の成功応答であり、登録有無・認証方式・スロットル状態のいずれも区別できない。書き込みの有無による処理時間差も生じない | |
| — | メール形式不正な入力でリセットを依頼する | `BusinessRuleError(IdentityErrorCode.InvalidEmail)` | |
| パスワードの検証材料を持つクレデンシャルが登録済み（メールは canonical 化して保存） | 大文字混在の同一メールでリセットを依頼する | 正規化後の一致で送る側の行が書かれ、メールが送られる | |
| `PasswordResetTokenPort.issue` がストア障害で失敗する | リセットを依頼する | `SystemError`（宛先の実在性に起因する失敗は応答に反映しない） | |
| 起床したジョブの `MailSender.sendPasswordResetMail` が送信基盤障害で失敗する | リセットを依頼する | 依頼そのものの応答は成功のまま変わらない（宛先の実在性を応答に反映しない）。送信の失敗はジョブの再試行として扱われる | |
| `CredentialMappingRepository.findByEmail` で DB 例外が発生する | リセットを依頼する | `SystemError` | |
| パスワードの検証材料を持つクレデンシャルが登録済み | 同一の canonical なメールへ短時間に連打する | **`operationKey` が同じなのでジョブ行1本に収束する。** 書き込みと起床の回数は依頼回数ではなく時間の窓の数に比例し、応答は毎回同一である | |
| 同一メールへの依頼がスロットル中（同じ `operationKey` のジョブ行が既にある） | そのメールでリセットを依頼する | 既存のジョブ行に収束するだけで、**書き込み・起床・応答は他の3ケースと同一である**。スロットル中であることを応答から観測できない | |
| 送る側のジョブ行が書かれた | ジョブ行の中身を確認する | 載っているのはトークンの識別子（`tokenId`）だけであり、**生のトークンは載らない**。生のトークンは送信直前に認証情報側で導出される | |
| 未使用のリセットトークンを既に保有するクレデンシャル | 同じクレデンシャル宛に新しいトークンを発行する | **新しい発行がそのクレデンシャル宛の未使用トークンをすべて置き換える。** 古いリンクは以後効かない | |
