# テストケース: requestPasswordReset

[usecases/identity.md](../../usecases/identity.md) の requestPasswordReset に対するテストケース。

**中心的な検証点は「登録済み / 未登録 / SSO 専用 / スロットル中の4ケースが、同じ窓の状態に対して一様に落ちること」である。** その窓での最初の依頼なら4ケースとも必ずちょうど1行イベント行を書き（0行でも2行でもない）、既に発行済みの窓なら4ケースとも1行も書かない。どちらでも同じ起床を張り、同じ応答を返す。**分岐の材料は `PasswordResetThrottlePort.claimWindow(windowKey, now)` の戻り値だけであり、クレデンシャルの登録有無・認証方式・宛先の存在を一切参照しない** — 参照すると行の書き込みそのものが測定可能な差になり、登録済みメールの列挙オラクルになる。**窓ストア（`reset_request_windows`）の行のほうは登録の有無に関係なく必ず作る。** 配送機構そのもの（relay / Queue / DLQ / prune）のテストは [async/outboxDelivery.md](../async/outboxDelivery.md) が持つ。**「4ケース」は互いに素な分割ではない** — 4ケース目の「スロットル中」は窓が消費済みである状態そのものを指し、クレデンシャル3状態（登録済み / 未登録 / SSO 専用）と直交しないので、実際の分割は**クレデンシャル3状態 × 窓2状態**である。本ファイルの一様性はすべて**窓の状態を固定したうえでの命題**として読む（[usecases/identity.md](../../usecases/identity.md)）。本ユースケースが4ケースすべてで投入する `sweep-reset-tokens` の**掃除側**（期限切れのトークン行と窓行の削除）は表の末尾3ケースが持つ。

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| パスワードの検証材料を持つクレデンシャルが登録済み。その窓での最初の依頼 | 登録済みメールでリセットを依頼する | 同じ `transactionSync` の中で、`claimWindow` が `true` を返して窓行が1行作られ、リセットトークンが発行され、`identity.passwordResetRequested` のイベント行が**ちょうど1行**書かれ、`sweep-reset-tokens` が投入される。配送後に `MailSender.sendPasswordResetMail(to, resetToken, providerIdempotencyKey)` が同メール宛にリセットメールを送る（**`providerIdempotencyKey` は `event.id` から決定的に導かれた値である**）。正常終了（`void`） | |
| 該当メールのクレデンシャルが未登録。その窓での最初の依頼 | 未登録メールでリセットを依頼する | **窓行・イベント行・ジョブの投入・起床・応答のすべてが登録済みの場合と一致する。** トークンは発行されないが**イベント行の形は一字も違わない**（`tokenId` には宛先の有無から独立に生成した不透明値が入る）。送信材料 RPC が `nothing-to-send` を返すので何も送られない | |
| 同一メールのクレデンシャルは存在するが、パスワードの検証材料を持たない（SSO 専用アカウント）。その窓での最初の依頼 | そのメールでリセットを依頼する | **送らない側**である。窓行・イベント行・ジョブの投入・起床・応答は上の2ケースと完全に一致する。`kind = 'email'` の mapping 行は SSO 登録でも置かれるので、**判定は「mapping の有無」ではなく「`passwordVerifier` の有無」で行う** | |
| 登録済み / 未登録 / SSO 専用 / スロットル中の4ケース | それぞれの応答と処理経路を比較する | **同じ窓の状態に対して一様に落ちる** — 最初の依頼なら4ケースとも必ずちょうど1行、既に発行済みの窓なら4ケースとも1行も書かない。応答はすべて同一の成功応答であり、登録有無・認証方式・スロットル状態のいずれも区別できない。**差が無いのは測定対象4つ**（`outbox_events` の行数 / `reset_request_windows` の行数 / Alarm の起床の有無 / `sweep-reset-tokens` の投入の有無）**についてであり、総書き込み行数と実測処理時間の一致は主張しない** — 送る側だけがリセットトークンの発行（未使用行の全削除 + 挿入）を追加で行うためである。**その差が応答から観測できないことは、応答が配送の完了を待たず依頼のトランザクションの確定で即返ることが担保する** | |
| — | メール形式不正な入力でリセットを依頼する | `BusinessRuleError(IdentityErrorCode.InvalidEmail)` | |
| パスワードの検証材料を持つクレデンシャルが登録済み（メールは canonical 化して保存） | 大文字混在の同一メールでリセットを依頼する | 正規化後の一致で送る側になり、イベント行が書かれてメールが配送される。**`windowKey` は canonical から導くので、表記違いは同じ窓に落ちる** | |
| `PasswordResetTokenPort.issue` がストア障害で失敗する | リセットを依頼する | `SystemError`（宛先の実在性に起因する失敗は応答に反映しない） | |
| Queue の consumer が呼ぶ `MailSender.sendPasswordResetMail` が送信基盤障害で失敗する | リセットを依頼する | **送信基盤の失敗は依頼の応答に現れない。** 依頼のトランザクションが確定した時点で配送はまだ始まっておらず、失敗は Queue の retry → DLQ が扱う（[async/outboxDelivery.md](../async/outboxDelivery.md)） | |
| `CredentialMappingRepository.findByEmail` で DB 例外が発生する | リセットを依頼する | `SystemError` | |
| パスワードの検証材料を持つクレデンシャルが登録済み | 同一の canonical なメールへ短時間に連打する | **2回目以降は `claimWindow` が `false` を返し、イベント行もリセットトークンも書かれない。** 窓行は窓ごとに1行で、2回目以降は `last_requested_at` だけを更新する冪等な更新である。**書き込みと起床の回数は依頼回数ではなく時間の窓の数に比例し**、応答は毎回同一である | |
| 同一メールへの依頼がスロットル中（同じ窓の行が既にある） | そのメールでリセットを依頼する | `claimWindow` が `false` を返す。**一致するのは4つ** — (1) 応答、(2) 起床の有無、(3) `sweep-reset-tokens` の投入、(4) 窓行が1行のままであること（新しい行は作られず `last_requested_at` だけが更新される）。**差が出るのは2つ** — イベント行を1行も書かないこと（0行）と、リセットトークンを発行しないこと。**他の3ケースとの一致は、それらを同じ窓の状態（既に発行済みの窓）に置いたときについてであり、「その窓での最初の依頼」の3ケースとの比較ではない**（あちらは3ケースとも1行イベント行を書く）。**この「4つ」は下段の未登録アドレス比較ケースが挙げる測定対象4つとは別の集合である**（あちらは `outbox_events` の行数を含み、応答を含まない）。スロットル中であることを応答から観測できない | |
| 送る側のイベント行が書かれた | イベント行の payload を確認する | 載っているのは `tokenId` / メール種別の**2つだけ**であり、**メールアドレス・生のトークン・`userId` は載らない**。**発行元 bucket の routing key も payload に入らない** — routing key は relay が publish 時に Queue メッセージへ押す項目であって、ドメインの payload の項目ではない（`EventId` と同じ扱い）。生のトークンは送信材料 RPC の中（= DO の中）で `tokenId` から導出される | |
| 未使用のリセットトークンを既に保有するクレデンシャル。**新しい窓での**最初の依頼 | 同じクレデンシャル宛に新しいトークンを発行する | **新しい発行がそのクレデンシャル宛の未使用トークンをすべて置き換える。** 古いリンクは以後効かない。**全置換が起きるのは窓での最初の依頼のときだけである** | |
| パスワードの検証材料を持つクレデンシャルが登録済み | 同一 canonical・同一窓へ2回依頼する | **有効なリンクを含むメールが1通届く（0通でも2通でもない）。かつ1通目のリンクが2回目の依頼後も有効である** — 2回目は `PasswordResetTokenPort.issue()` を呼ばないので未使用トークンが置き換わらない | |
| 窓をまたいで積まれた新旧2件のイベント行がある | **逆順で** consumer へ届かせる | 新しいほうについての送信材料 RPC は `send` を返して送信され、古いほうは **`nothing-to-send`** を返して no-op になる。**期待値は「`nothing-to-send` が返る」までであり、理由は期待値に書けない** | |
| 該当メールのクレデンシャルが未登録 | 未登録アドレスへ同一窓で2回依頼し、登録済みアドレスへ同一窓で2回依頼した場合と比較する | **測定対象4つがすべて一致する** — (1) `outbox_events` の行数、(2) `reset_request_windows` の行数、(3) Alarm の起床の有無、(4) `sweep-reset-tokens` の投入の有無。**「総書き込み行数」では測らない**（登録済み側は `password_reset_tokens` の発行行を追加で書くので総数では一致しない） | |
| `PasswordResetThrottlePort.claimWindow` がストア障害で失敗する | リセットを依頼する | `SystemError`（トークンストア障害と同じ扱い。宛先の実在性に起因する失敗は応答に反映しない） | |
| 4ケースのいずれかでイベント行が書かれた | 行の `aggregate_id` を確認する | **`claimWindow` に渡した `windowKey` が入っている。** 4ケースのどれでも同じ導出で必ず決まり、鍵付きハッシュ済みなので原本を含まない。**`credentialId` は入らない** — 未登録の宛先には存在せず、有無が観測可能な差になる | |
| 期限切れの `password_reset_tokens` の行と期限切れの `reset_request_windows` の窓行が同じ bucket にある | `sweep-reset-tokens` を1回起床させる | **同じ起床で両方が削除される** — トークン行だけ・窓行だけが消える形にならない（1つの `jobs.kind` が2目的を持ち、`kind` は増えない）。掃除は `prt_expires_idx` / `rrw_expires_idx` の両方を引く | |
| 期限内の窓行と期限切れの窓行が同じ bucket に混在する | `sweep-reset-tokens` を起床させる | **`expires_at` を過ぎた窓行だけが削除され、期限内の窓行は残る。** 残った窓行は以後も `claimWindow` の判定に効き、掃除がスロットルを解除しない | |
| **未登録アドレスだけへ依頼を投げ続けた bucket**（`password_reset_tokens` の行が1行も無く、窓行だけがある） | `sweep-reset-tokens` の投入と掃除の結果を観測する | **窓行が掃除される。** 投入は4ケースすべてで起きるので、トークン行が1行も無い bucket でもジョブが投入され、期限切れの窓行が削除される — **未登録側だけ `reset_request_windows` が単調増加する状態にならない**（投入をトークン行の書き込みに紐づけた実装はこのケースで落ちる） | |
