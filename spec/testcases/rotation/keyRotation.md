# テストケース: keyRotation

[rotation/index.md](../../rotation/index.md) が定める鍵ローテーション（写像鍵の移送 `rotate-remap` とメール暗号鍵の `rotate-encryption`）に対するテストケース。**どのユースケースにも属さない機構のテストである** — ここで検証するのは移送の順序・CAS・見送り・checkpoint・直列化・注入鍵の検証の契約であって、単一世代でも成立する規則（到達性検査が `credentialId` だけを見ること等）は各ユースケースのテストケース（例: [identity/loginWithPassword.md](../identity/loginWithPassword.md) の両世代並存ケース）が持つ。

**期待値の書き方の前提。** 移送は operator 専用 maintenance 経路のチャンク駆動であり、テストは `remap-chunk` 相当の呼び出しを直接発行して観測する。「鍵を永続化しない」「平文を境界の外へ出さない」（C1 / C2）と鍵コミットメントの生成規則は実行時に観測できないので**期待値に入れず、実装レビューの確認項目とする** — 規約の正本は rotation/index.md「鍵の配布とコミットメント」である。

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| 注入する keyring エントリがコミットメントと一致しない（鍵・世代・`bucketCount` を偽るケースと、**active / previous のラベルを入れ替えるケース**を個別に再現する） | `remap-chunk` / `import-remapped-mappings` を呼ぶ | **どれも拒否され、行は1つも動かない。** 照合は役割（active / previous）・`generation`・`keyDigest`（定数時間比較）・`bucketCount` の4点で、1つでも欠ければ使われない。**役割入れ替え（正しい鍵2件のラベルだけを逆にして移送を逆向きに駆動する）も役割の照合で拒否される。previous 世代鍵の所持を認可材料にする分岐がどこにも無い** | |
| 移送元 bucket の世代が、注入された previous エントリの世代と一致しない | `remap-chunk` を呼ぶ | 拒否される（自分が退役対象の世代であるときだけ移送元になれる） | |
| `import-remapped-mappings` に、`encryptedCanonical` の復号または HMAC 再計算が行の `hmac`・自 bucket index と一致しない行を渡す（暗号鍵を持たない主体が組んだ行を再現する） | import を呼ぶ | **その行は受け入れられない**（自己検証 (iii)）。binding 到達性だけでは任意の写像行を注入できない | |
| 暗号鍵 keyring に previous 世代が載っている / 自 bucket に `encryptionGeneration` ≠ active の行がある / `done` でない `rotate-encryption` ジョブがある（3つを個別に再現する） | `remap-chunk` を呼ぶ | **3条件のいずれでも拒否される**（直列化ガード）。暗号鍵ローテーションが完了するまで移送は始まらない | |
| コミットメントに previous 写像世代が存在する（写像鍵ローテーション進行中） | `rotate-encryption` の起動 RPC を呼ぶ | **拒否される。** 2種類のローテーションは同時に進行しない | |
| 通常の active 行（saga 進行中でない）を1件持つ移送元 bucket | `remap-chunk` を1回実行する | **s3（`record-remapped-locator` による逆引きの先行記録）→ s4（移送先へ INSERT）→ s5（移送元の削除）の順で完了する。** 移送先の行は `hmac` / `generation` だけが新しく他の列はそのまま、`credentialId` / `callerToken` は再採番されず、`credentialVersion` は増えない。`credential_locators` には `(credentialId, 新世代)` の行が upsert され、旧世代の locator 行は**残る** | |
| s5 と同じトランザクションの観測 | 移送元の行の削除を観測する | **同じ `transactionSync` でその `credentialId` の `password_reset_tokens` 行が全削除される**（写像を失った行を残さない）。checkpoint はチャンク末尾（s6）に `(remap, 自 bucket index, 退役世代)` の snapshot 置換で書かれ、`previousCount` は見送り行を含む残行数・衝突3列はそのチャンクの再検出数の snapshot（累積しない）である | |
| `status = 'reserved'` の行、または `changeState IS NOT NULL` の行がある | `remap-chunk` を実行する | **どちらも読み出し時点で見送られ、移送先にも複製が作られない**（s1 の行ローカル述語）。`previousCount` に数えられて残る | |
| 対象 `credentialId` の `credential_locators` 行が0件（signup の逆引き記録前 / SSO 連携の記録前 / SSO 解除の削除後を個別に再現する）、または `account.status != 'active'`（退会中） | `remap-chunk` を実行する | **s3 が「見送り」を返し、その行を残して次へ進む — 複製は作られず、`credential_locators` に新世代の行も記録されない。** **削除進行中の印を `credential_mappings` に持たなくても、削除対象のスナップショットと移送が競合しない**（この競合はこの形で閉じる） | |
| SSO 解除が `targetLocators` を退避して逆引きを消した直後に移送が走り、その後 `deleteMapping` が発行される | 一連を実行する | 移送は s3 見送りで複製を作らず、`deleteMapping` は `targetLocators` の全世代へ「無ければ成功」で発行されて**孤児の写像がどの世代にも残らない** | |
| 両在状態（s4 完了・s5 未了）で、クレデンシャル変更 saga の phase 1 が**移送先**の行に着地する（lookup が active を先に引く） | 続きのチャンクを実行する | **移送先の複製がそのまま正本になり、saga はそこで完走する — 破棄という操作は存在しないので中間状態が壊れる経路が無い。** 再実行のチャンクでは述語1（`changeState IS NULL` を含む）が上書きを0行で拒否し、正本判定 (b) 相当へ縮退して収束する。移送元は述語2で消えるか、`changeState` が立っていれば残って saga 完走後に分岐 (b)/(c) で収束する | |
| 移送元で見送られた行のクレデンシャル変更 saga が完走し、移送元の `credentialVersion` が移送先（に古い複製が残っている場合）より進む | 続きのチャンクを実行する | 正本判定 **(c)** — 述語1の CAS で移送先が移送元の値へ上書きされ、その後 s5 で移送元が消える。**「移送先に行があれば書かない」実装はこのケースで落ちる**（旧 `passwordVerifier` の復活経路） | |
| 中断からの再実行（s4 は完了済み・s5 未了・両行の `credentialVersion` が等しい） | 同じチャンクを再実行する | 正本判定 **(d)** — 冪等な上書きとして収束し、行数・値とも1回実行と同じ終状態になる | |
| 移送先に**別の `userId`** の同 `(kind, hmac)` 行がある（PITR 残骸などの異常を再現する） | `remap-chunk` を実行する | 正本判定 **(e)** — 見送られ、移送元・移送先とも変更されず、`rotation_checkpoints` の衝突3列（`conflictCount` / `lastConflictAt` / `lastConflictCredentialId`）に記録される。**`previousCount` が0にならないので退役条件が成立しない**（fail safe） | |
| s5 の CAS（述語2）が0行になる（読み出し後に移送元へ書き込みが入った） | チャンクの継続を観測する | **移送元の行は消えずに残り、次のチャンクで再評価される。** 取り違えて無条件 DELETE する実装はこのケースで落ちる | |
| 両在状態で login する（複製が陳腐でないケースと、片側だけ credential 変更が完走した直後のケース） | `loginWithPassword` を実行する | 前者は通る（lookup は active → previous、到達性検査は `credentialId` のみ）。後者は `credentialVersion` 照合で **fail closed に拒否**され、認可は開かない。次のチャンクの収束後に通る | |
| 移送開始後の新規登録・SSO 連携 | 予約を観測する | **予約は常に active 世代の bucket に取られ、previous 世代に新しい行は生まれない**（行を作る経路は予約と import の2つで、どちらも active のみ — `previousCount = 0` の恒久性の根拠） | |
| 全 previous bucket の checkpoint が `previousCount = 0` になる前に退役を判定する / なった後に判定する | `read-rotation-checkpoint` を全 bucket 分集計する | **退役条件は「`rotationKind` で絞った対象世代の checkpoint が全 bucket に存在し、すべて `previousCount = 0`」でのみ成立する。** 1 bucket でも欠け・非0なら不成立。**`rotationKind` で絞らずに数える実装は、`rotate-encryption` の完了記録で写像鍵の退役条件を誤成立させるのでこのケースで落ちる**（`rotationKind = 'encryption'` の `previousCount = 0` 行を混ぜて判定させる） | |
| `rotate-encryption` が完走した bucket | checkpoint を観測する | 各チャンク完了で `(encryption, 自 bucket index, 退役暗号世代)` が snapshot 置換され、残件0の完了時に `previousCount = 0`。**投入点は operator 経路の起動だけであり、移送側からの再投入は存在しない**（直列化により `encryptionGeneration` ≠ active の行は移送されない） | |
| 巻き戻し（active = g、previous = g+1 に入れ替えた keyring / コミットメントを配布） | g+1 の bucket に対して `remap-chunk` を実行する | **順方向とまったく同じ機構（s1〜s6・CAS 2述語・正本判定5分岐）で g へ移送される。** checkpoint は `generation = g+1` の行として記録される。専用の状態・専用の分岐を持つ実装はレビューで落とす | |
| 移送済みクレデンシャルの世代退役後 | `credential_locators` を観測する | 旧世代の locator 行が**残っている**が、到達性検査・ログイン手段の数え上げ（distinct `credentialId`）・`getCurrentUser` の一覧のいずれの結果も変わらない。credential の解除・退会では `deleteByCredentialId` が全世代を消す | |
| 移送の一連の実行 | `rotation_checkpoints` への書き込み経路と、ログ・`terminalReason` を確認する | checkpoint の書き込みは UoW の `rotationCheckpointStore` 経由だけであり、bucket の外から書けない。ログ・エラー・トレースに canonical / HMAC / 鍵 / 復号結果が現れない（**RPC の引数・戻り値ロギングを有効化する構成そのものが禁止である** — 構成の検証は実装レビューの確認項目） | |
| 両在状態で、s1 の読み出し後に移送元へ照合結果の書き戻し（ログイン失敗 / 現在パスワード照合の失敗によるカウンタ更新）が遅延して届き `failedAttempts` / `nextAttemptAllowedAt` が動く | チャンクを継続する | **述語1・述語2は濫用抑止カウンタを含まないので外れず、移送は収束する。** 移送先はスナップショット時点のカウンタを持ち、遅延分の増分は失われる（受容した残余の観測）。`nextAttemptAllowedAt` が未来の行はスナップショットのまま移送され、ロックアウト状態は維持される。**カウンタを述語に含めた実装はこのケースで収束せず落ちる** | |
| s3（先行記録）の完了後・s4（import）の着地前に SSO 解除 / 退会が完走し、g+1 への `deleteMapping` が「無ければ成功」の no-op で終わった後に、遅延した import が複製を書く | 削除 saga の完了判定と再発行を観測する | **退避座標が2世代を含むので「削除の no-op 確定」が効き、no-op だった世代の削除は最小再開間隔（cross-DO RPC の実行寿命の上限より長い）の後にもう一度発行されてから確定する — 2回目の発行が遅延着地した複製を実在削除し、無音の残留にならない。** no-op を即確定して `phase = 'done'` にする実装は、複製がどの削除経路からも到達不能に残るのでこのケースで落ちる。逆引きの記録を import の後に置いた実装は、複製が座標退避に載らない窓を作るので同じく落ちる | |
| 新規登録（メール）と SSO 連携それぞれの予約直後 | 予約行を観測する | **`encrypted_canonical` / `encryption_generation` / `encryption_nonce` と `caller_token` が非 NULL であり、復号すると `kind` 別の canonical 形式（メール canonical / `provider + U+0000 + subject`）の原本が得られる**（NOT NULL 化の成立条件 = 予約時点の書き込み。canonical の形式と `caller_token` の値の同一性（`account.caller_token` と一致）はスキーマ制約では検証されないので、このケースが担う） | |
| ローテーション開始後、保存済みの世代つき座標（`locators` / `targetLocators`）を再駆動する saga（`resume-signup` の非コーディネーター予約 / `resume-link` の予約の取り直し）が previous 世代の bucket へ予約を書こうとする | 予約 RPC の応答と bucket の行を観測する | **予約の世代ガード（自 bucket の世代 = コミットメントの active 世代）が拒否し、previous 世代に新しい行は生まれない。** saga は前進不能として**終端モードへ入る**（`terminalReason` を前倒しで書き `status` は `pending` のまま。**即 `poison` にする実装はこのケースで落ちる**）。**そのあとの後始末の段と材料の扱いは [recovery/index.md](../../recovery/index.md) が正本である** — 本ケースが観測するのは previous 世代に行が生まれないことと、突入までである。**ガードの無い実装は previous に行を作り、`previousCount = 0` の checkpoint を偽にするのでこのケースで落ちる** | |
| 順方向の移送で checkpoint が `previousCount = 0` になった世代 g へ、行を増やす書き込みが起きる（**import（巻き戻し）と、再活性化後の新規予約の2経路を個別に再現する**） | 書き込みと `rotation_checkpoints` を観測する | **どちらの経路でも、行を書く同じトランザクションで増えた行の属する世代の checkpoint 行（`(remap, 自 index, g)` と `(encryption, 自 index, その行の暗号世代)`）が削除され**、stale な `previousCount = 0` による早期退役が不成立に戻る（退役証明の無効化の一般規則）。`rotate-encryption` の書き換えチャンクも同じ規則で `(encryption, 自 index, active 暗号世代)` を削除する。**import 側だけに削除を掛けた実装は、予約経路の再現で stale checkpoint が残って落ちる** | |
| チャンクが途中で中断する（DO リセット・エビクション） | `rotation_checkpoints` と退役判定を観測する | **s6 の checkpoint は書かれず、前回の snapshot が残る。** `previousCount` が 0 でない限り退役条件は成立しない（fail safe）。再実行は正本判定 (d) の冪等性で1回実行と同じ終状態に収束する | |
| 直列化ガードを通ったあとの import に、`encryption_generation` ≠ active の行を直接渡す（上流ガードをすり抜けた行を再現する） | `import-remapped-mappings` を呼ぶ | **ガード (iv) が単独でその行を拒否する**（per-row 応答「拒否」）。他の行の受け入れは止まらない | |
| 退役対象世代の `bucketCount` = 4・active 世代の `bucketCount` = 8（またはその逆）の構成で、退役条件を判定する | `read-rotation-checkpoint` を集計して退役を判定する | **remap の N は退役対象世代のエントリの `bucketCount`（= 4）であり、bucket `0..3` の checkpoint × `previousCount = 0` で成立する。** active 側の `bucketCount` で数える実装は、bucket 4〜7 の checkpoint 欠落により恒久に退役不能（逆構成では未走査 bucket を残した早期成立）になるのでこのケースで落ちる。**encryption 側の N は active 写像世代の `bucketCount` であり、取り違えた実装も同じ形で落ちる** | |
| デプロイスキュー中（request Worker の keyring と state Worker のコミットメントの active 世代が食い違う）に、利用者リクエスト起点の新規登録・SSO 連携が予約を書こうとする | 同期の予約 RPC を観測する | **予約の世代ガードが拒否し、`SystemError` として利用者へ返る（既存の「DB 例外」系と同じ扱い。新しい kind は増えない）。`poison` 行もジョブの終端も生じない**（一様な終端へ落ちるのは保存済み座標を再駆動するジョブ側だけである）。収束後の再試行は通る | |
| `record-remapped-locator` に、行側と一致しない / `NULL` / 空 / 規定長未満の `callerToken` を渡す（4形を個別に再現する） | s3 相当の呼び出しを観測する | **どの形でも照合の前または照合で不一致となり「見送り」1値が返る**（理由を分けない — 分けると呼び出し元のログに退会状態や照合の内訳が漏れる）。複製は作られず、locator も記録されない | |
| 移送先でない bucket（世代 ≠ コミットメントの active 世代）へ `import-remapped-mappings` を呼ぶ | import を観測する | **ガード (ii) が単独でエントリレベルに拒否し、`SystemError` が値エンベロープで返る**（per-row の「拒否」ではない）。行は1つも書かれない | |
| 見送り行（進行中 saga・分岐 (e) の衝突行）が走査順の先頭側に件数上限以上並んでいる bucket | `remap-chunk` を、前回応答の `afterCredentialId` を渡して反復発行する | **カーソルが前進し、見送り行の先で未処理の行に到達して移送が進む**（件数上限は走査した行数に掛かる）。カーソルを渡さず毎回先頭から走査する実装は、恒久見送り行の壁で未処理行に届かず収束しないのでこのケースで落ちる。**カーソルを失って先頭からやり直しても冪等に収束する**（移送済みの行は消えているので先頭側は空振りで縮む） | |
| 写像行が previous 世代の bucket に**のみ**存在する（未移送）利用者 | パスワード / SSO でログインし、照合結果の書き戻しを観測する | **stub 選択アダプターが active で外れて previous を引き、ログインが成立する**（lookup の世代順序。database/index.md `credential_mappings`）。書き戻しはヒットした previous の行へ着地する。**active だけを引く実装は未移送の全利用者を締め出すのでこのケースで落ちる** | |
| 未移送の利用者と未登録の宛先それぞれからのリセット依頼（ローテーション中） | 依頼一式の完結先 bucket を観測する | **未移送の依頼は previous 側の bucket に**（窓行・イベント行・トークン行がすべて previous 側に立ち、リンクは有効）、**未登録の依頼は active 側の bucket に**完結する。どちらの世代でも4ケース一様性（同じ bucket の1トランザクション）が保たれる | |
| `rotate-encryption` のチャンクが行を読み出した後・書き込みの前に、その行が削除され同じ canonical で再予約される（別の `credentialId`・active 暗号世代の新しい行） | 書き換えの UPDATE を観測する | **UPDATE は `(kind, hmac)` に `encryptionGeneration = 退役対象世代` を条件として含むので 0 行で素通りし、新しい行を壊さない**（0 行はその行の完了として次へ進む）。条件の無い実装は旧 `credentialId` を AAD に持つ暗号文で新しい行を上書きし、恒久復号不能を作るのでこのケースで落ちる | |
| s4 の直前の読み直しと import の発行の間に、credential 変更の phase 1 が移送元へ着地する | 移送と login を観測する | 変更前スナップショットの複製が active 側に立ち、**phase 2 が `credentialVersion` を進めるまでは旧パスワードの照合が成立しうる**（受容した残余の観測）。phase 2 の前進後は login step の `credentialVersion` 照合が fail closed に拒否し、次チャンクの分岐 (c) で複製が正本へ収束する。**読み直し自体を省いた実装は、この窓が in-flight 窓より大きく開くのでこのケース（読み直し前の着地の再現）で落ちる** | |
| 移送チャンクの s1（スナップショット読み・版 v）と s3（先行記録）の間に、credential 変更の phase 2（`advanceCredentialVersion`）が割り込み移送元世代の行を v+1 へ進める | s3 の記録後の `credential_locators` を観測する | **新世代行の `credentialVersion` は v ではなく v+1 になる** — `record` の単調非減少は同じ `credentialId` の**全行の最大**に対して取られ、新規行の作成にも掛かるからである（世代間で版が分岐せず、`advanceCredentialVersion` の戻り値は常に一意）。スナップショットの v をそのまま新規行へ書く実装は版の分岐を作り、login の版照合が実装裁量になるのでこのケースで落ちる | |
