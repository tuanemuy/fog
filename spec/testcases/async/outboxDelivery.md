# テストケース: outboxDelivery

[async/index.md](../../async/index.md) が定める DO ローカル Outbox の配送機構に対するテストケース。**どのユースケースにも属さない機構のテストである** — ここで検証するのは relay・Queue・consumer・DLQ の契約であって、イベントを発行する側の振る舞い（4ケース経路一致・連打の収束）は [identity/requestPasswordReset.md](../identity/requestPasswordReset.md) が持つ。

**中心的な検証点は3つである。** (1) 業務データ・FTS5 projection・Outbox 行が**同じ `transactionSync` で一度に確定し、rollback すると3つとも巻き戻る**こと。(2) 配送が **at-least-once・順序保証なし**であり、重複と順序逆転を受け入れたうえで正しく終わること。(3) 失敗の記録先が「**Queue に入る前か後か**」の1本で分かれ、同じ失敗が2箇所に現れないこと。**順序逆転と重複配送の期待値は、送信材料 RPC の2分岐（`send` / `nothing-to-send`）で書く** — `nothing-to-send` は理由を1つも載せない空なので、「なぜ送らなかったか」は期待値に書けない。 **ただし (1) を3点そろえて測れる DO クラスは今日ひとつも無い。** FTS5 projection は User Data DO にしか無く、定義されているイベント型（`identity.passwordResetRequested`）は Identity Directory DO にしか無い（[async/index.md](../../async/index.md) の全数表。**User Data DO のイベント型は初期0件である**）。そこで表の先頭2ケースは「**その DO クラスに存在する要素の全部**」を測る形で書いてあり、対象は User Data DO では業務行 + FTS5 projection、Identity Directory DO では業務行（窓行・リセットトークン行）+ イベント行である。**3点が同時に成立するのは User Data DO のイベント型が1つでも定義された時点であり、そのとき本ケースを3点版へ拡張する。** 契約そのもの（3つが同じ `transactionSync`）は `spec/database/index.md` / `spec/usecases/*` / `CLAUDE.md` が持ち、ここでは動かさない。

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| **DO クラスごとに実行する** — (a) User Data DO: メモまたはドキュメントを作成・更新するユースケース、(b) Identity Directory DO: イベント行を書くユースケース（**送る側の** `requestPasswordReset` の、その窓での最初の依頼。窓行とリセットトークン行の両方が書かれる組み合わせを選ぶ） | その DO クラスに存在する要素の全部を観測する — (a) では業務データの書き込みと FTS5 projection の更新、(b) では業務データ（窓行・リセットトークン行）の書き込みと `enqueueEvent` によるイベント行の追加 | **観測した要素の全部が同じ `transactionSync` の中で一度に確定する。** (b) のイベント行は別ストアへの RPC でも遅延書き込みでもなく、同じ DO の `outbox_events` への INSERT である。**FTS5 projection とイベント行が同居する DO クラスは存在しないので、(a) と (b) を別々に実行する**（両方が揃う DO クラスが現れたら3点版へ拡張する。表の直前の解説） | |
| **DO クラスごとに**、同じトランザクションの後段で業務データの書き込みが失敗する — (a) User Data DO、(b) Identity Directory DO（**送る側の**、その窓での最初の依頼） | トランザクション全体をロールバックさせる | **その DO クラスに存在する要素の全部が巻き戻る** — (a) では業務データと FTS5 projection、(b) では業務データ（窓行・リセットトークン行）と `outbox_events` の行。**イベント行だけが残って存在しない更新の配送が起きる、という状態にならない**（この破れは (b) で検出する） | |
| メモまたはドキュメントを作成・更新する | 直後に検索する | **FTS5 projection は Outbox の配送を待たず、同じトランザクションで反映済みである。** relay が動いたか否か・Queue が滞留しているか否かと**独立**にヒットする（検索インデックスに consumer は存在しない） | |
| `pending` のイベント行が1件以上あり、**lease 未満了の `publishing` 行が1件も無い** | Alarm が起床する | 相1で実行可能な行が上限件数まで claim され、`status` が `publishing`、`lease_until` と `owner_token` が CAS で書かれる。**claim は `transactionSync` の中で完結する。`next_run_at` の昇順で claim される** — 上限件数で打ち切られたとき、**claim に成功した行の集合について**、残るのは常に `next_run_at` がより後の**実行可能かつ claim 可能な**行である（同じ行が毎回取り残される実装はこのケースで落ちる）。**lease 未満了で CAS に弾かれた行は、より早い `next_run_at` を持ったまま残りうるので、この期待値の射程の外である** — 実行可能集合は `status IN ('pending','publishing')` なので lease 中の行も索引順では先頭に並び、行ごとの CAS が 0 行更新で飛ばす（`TC-outboxDelivery-007` が作るのはまさにその状態である）。前提でその状態を排除しているのはこのためであり、**排除せずに「残るのは常により後の `next_run_at`」を測ると仕様どおりの実装が落ちる** | |
| claim 済みの行がある | 相2で Queue へ publish し、相3で終端させる | **Queue への送信だけがトランザクションの外にある。** 成功すると相3の `transactionSync` で `status` が `published`、`completed_at` が入り、`lease_until` / `next_run_at` が `NULL` になる。**`owner_token` は `NULL` にしない**（送信材料 RPC の照合材料として残す） | |
| `jobs` と `outbox_events` の両方に実行可能な行がある | Alarm の起床時刻を確認する | **4本の min の合成**（`min(jobs.next_run_at) WHERE status='pending'` / `min(jobs.lease_until) WHERE status='running'` / `min(outbox_events.next_run_at) WHERE status='pending'` / `min(outbox_events.lease_until) WHERE status='publishing'`）**が張られる。`min(max(next_run_at, lease_until))` を1本の SQL として発行する実装はこのケースで落ちる** — 式を key にした索引が無く実行可能集合の全走査になるので、4本とも宣言済みの索引で引ける形に分解してある（`max(next_run_at, lease_until)` は意味の説明であって発行する式ではない）。**両方の実行可能集合が空のときだけ `deleteAlarm()` される** | |
| 過去の `next_run_at` を持つ `publishing` の行だけが残っている（lease は未満了） | Alarm を起床させる | **lease 中の行は `max(next_run_at, lease_until)` で算入される。** 過去の `next_run_at` をそのまま採って「起床 → 1行も claim できない → 同じ過去時刻へ張り直す」の空転にならない | |
| **送る側の**（パスワードの検証材料を持つクレデンシャル宛で、そのトークンが未使用かつ期限内の）イベント行について、相2（publish）の直後・相3（`published` への落とし込み）の前に DO がリセットする（未登録宛や消費済みトークンの行で組むと、正しい実装でも新しいメッセージ側が `nothing-to-send` になる — 呼び出しガードの3条件は `send` の必要条件であって十分条件ではない） | `lease_until` の満了を待って次の起床を観測する | **同じ行が再 claim され再 publish される**（at-least-once の根拠）。再 claim で `owner_token` が書き換わるので、**リセット前に publish された古いメッセージについての送信材料 RPC は `nothing-to-send` を返す**（呼び出しガード (c) の不一致）。新しいメッセージの側は `send` を返す | |
| **送る側の**（パスワードの検証材料を持つクレデンシャル宛で、そのトークンが未使用かつ期限内の）イベント行について、同じ `event.id` のメッセージが consumer へ2回届き、どちらも `owner_token` が一致している（前提を締める理由は上のケースと同じ — ガードの3条件は `send` の必要条件であって十分条件ではない） | 2回とも送信材料 RPC を打つ | どちらも `send` を返す。**provider へ渡す `providerIdempotencyKey` は `event.id` から決定的に導かれるので2回とも同じ値**であり、provider 側で抑止される。**consumer は処理済み `EventId` を保持しない**（冪等化は provider 側のキーと RPC の再確認の2段） | |
| 窓をまたいで積まれた新旧2件のイベント行があり、**古いほうが後に** consumer へ届く（順序逆転） | それぞれ送信材料 RPC を打つ | 新しいほうは `send`、古いほうは `nothing-to-send` を返す。**期待値は「`nothing-to-send` が返る」までであり、理由は期待値に書けない**（応答は理由を1つも載せない空である）。consumer はどちらも ack し、`nothing-to-send` は失敗ではない | |
| relay の相2で Queue への publish が失敗する（binding 障害等） | 相3を観測する | **その行だけ**が `attempt` を1つ進め、backoff で `next_run_at` を先送りされる。**上限未到達の失敗なので、同じトランザクションで行は `pending` へ戻り、`lease_until` と `owner_token` が `NULL` に解放される**（`publishing` のまま `next_run_at` だけを先送りする実装はこのケースで落ちる）。**先送りされた行は、その `next_run_at` が到来するまでの起床では再 claim されない** — claim 対象を選ぶ `SELECT` の述語に `next_run_at <= now` が掛かるためであり、掛け忘れると backoff が無効化される（CAS は `status` と `lease_until` しか見ない）。**backoff は行ごとであり、1件の失敗が同じ起床の他の行の配送を止めない** | |
| 1行の relay が例外で失敗する | `alarm()` の戻りを観測する | **`alarm()` から throw しない。** per-row の catch が失敗を吸収し、同じ起床の残りの outbox 行も、続く (3-b) の `jobs` パスも実行される。Alarm は最後に両表から再計算して張り直される | |
| publish の失敗が backoff の上限回数を超える | その行を観測する | `status` が `quarantined` になり `terminal_reason` が入る。**`terminal_reason` に PII と再利用可能な秘密が入らない**（運用者が読む場所である）。`owner_token` は残る。**以後の起床で再 claim されない** — 相1の実行可能集合は `status IN ('pending','publishing')` であり `quarantined` を含まないので、`terminal_reason` を上書きしながら回り続けることがない。**同じ起床の他の行の配送は止まらない** | |
| `quarantined` の行がある | その `event.id` について送信材料 RPC を打つ | **呼び出しガード (b) により `nothing-to-send` を返す**（理由は返さない） | |
| `quarantined` の行がある | operator 専用 maintenance 経路の `list-quarantined-events` を呼ぶ | 隔離された行が一覧できる。**このエントリは `jobs.kind` にも `event.type` にも入らない**（ジョブでもイベントでもなく RPC である） | |
| **`quarantined` の行だけが残っている DO**（実行可能集合が空なので、直前の起床で `deleteAlarm()` されて Alarm が張られていない） | `requeue-quarantined-event` で再駆動する | 同じトランザクションで `status='pending'` / `next_run_at = 現在時刻` / `attempt = 0` / `completed_at = NULL` が書かれ、**そのトランザクションのあと4本の min の合成で `setAlarm` が張り直される — `deleteAlarm()` 済みの DO でも起床が張られる**（張らない実装では、再駆動した行が次の投入まで動かないのでこのケースで落ちる）。次の起床で relay の対象になる。**`terminal_reason` は残り**（隔離の記録を消さない）、**`owner_token` は採番し直される** — 再採番により、隔離前に Queue / DLQ へ渡っていた古い `(event.id, owner_token)` の対は呼び出しガード (c) で弾かれる（**副作用として、そのイベントの古い DLQ メッセージを再駆動すると `nothing-to-send` になるが、行そのものは次の claim と publish で配送されるので配送は失われない**）。**consumer 側の失敗の導線はここではなく DLQ ハンドラである**（責務分界は「Queue に入る前か後か」の1本） | |
| 保持期間を過ぎた `published` の行と `quarantined` の行がある | ジョブランナーの起動末尾の prune を観測する | **`published` の行だけが上限件数まで削除され、`quarantined` の行は残る**（運用者の検査材料）。prune 専用の `kind` は増えない | |
| prune が `published` の行を消した後、その `event.id` のメッセージを DLQ から再駆動する | 送信材料 RPC を打つ | **呼び出しガード (a)（行の存在）を満たさないので `nothing-to-send` になる。** これが恒久的に起きないよう、運用値は `Queue の最大 retry 期間 + DLQ の保持期間 ≤ published 行の保持期間` を満たす（もう1本は `Queue の最大 retry 期間 + DLQ の保持期間 < リセットトークンの TTL`。**2本は左辺が同じ `Queue の最大 retry 期間 + DLQ の保持期間` で、上限として置く相手だけが違う** — `published` 行の保持期間とリセットトークンの TTL であり、相手は独立に決まる運用値なので片方から他方は導けない。**`DLQ の保持期間` だけを左辺に採った形では、DLQ 滞在の末期の再駆動が TTL の内側に収まることを導けない**（再駆動の時点でトークンが経過しているのは DLQ の滞在時間だけではなく、その前に Queue が retry を焼き切るまでの時間も含む）。**制約は2本でこれが全数**。実値の確定は #38） | |
| consumer が処理に失敗する | Queue の retry を焼き切らせる | メッセージが **DLQ へ落ちる**。**発行元 DO の `outbox_events` は `published` のまま変わらない** — `published` は「Queue へ渡した」の意味であり「処理された」ではない。**consumer からの ack を発行元 DO へ書き戻さない** | |
| DO のコードが期待するスキーマバージョンより DO 側が進んでいる（fail-closed） | Alarm を起床させる | migration ゲートで戻るので **(3-a) の relay パスに到達せず、outbox 行が滞留する**。**滞留は失われた配送ではない** — 行は残り、コードが揃った次の起床で流れる。ゲート呼び出しは `alarm()` の中で catch され、Alarm は**張ったまま**にされる（`deleteAlarm()` しない） | |
| fail-closed になる**前に** publish 済みのメッセージが Queue に残っている | consumer がそれを処理しようとする | 送信材料 RPC が migration ゲートで `SystemError` を返し、**retry を焼き切って DLQ へ落ちる。** DO 側の滞留が「失われない」のとは**非対称な挙動**である。デプロイのスキュー期間に限られ、復旧は DLQ の再駆動 | |
| 任意のイベント行が Queue へ publish される | `outbox_events.payload` / Queue メッセージ / DLQ メッセージ / ログ / `terminal_reason` を確認する | **PII と再利用可能な秘密がどこにも載らない**（**`owner_token` は衛生規則が定める明示的な例外である** — 呼び出しガードの成立に必要だからであり、その代償として (i) Queue メッセージ全体をログへ出さない（載せてよいのは `event.id` と `type` まで）・(ii) DLQ のメッセージを外部の監視基盤・ログ集約先へ転送しない、の2条が掛かる）。Queue メッセージが運ぶのは `event.id` / `type` / `payload` / 宛先 DO の routing key / `owner_token` の**5項目だけ**であり、**行の他の列は載せない — メッセージは行の写しではない**（**特に `aggregate_id`（窓キー）は載せない。** 同一アドレス・同一窓に対して安定した仮名なので、載せると DLQ 上で複数のメッセージを同一の宛先へ相関させる材料になる）。各項目は行の値をそのまま運び、Queue 側で組み立て直さない。**routing key だけは relay が publish 時に押す項目であり、行にもドメイン payload にも無い**。宛先メールアドレスと生トークンは**送信材料 RPC の応答と provider へのリクエストにのみ存在し、どこにも永続化されない**（「境界を出ない」ではない） | |
| **送る側の**（パスワードの検証材料を持つクレデンシャル宛で、そのトークンが未使用かつ期限内の）イベント行が `published` に落ちている（consumer が RPC を打つのは relay が `published` へ落とした後である） | 送信材料 RPC を打つ | **`status` は照合条件に入らないので `send` が返る。** `status = 'publishing'` を条件にすると正常系の配送が全滅する。**二重送信の抑止は `status` ではなく `providerIdempotencyKey` が担う。呼び出しガードの3条件は `send` の必要条件であって十分条件ではない**ので、前提のほうで宛先とトークンの状態まで締めてある（未登録宛や消費済みトークンの `published` 行で組むと、正しい実装でも `nothing-to-send` が返る） | |
| 同じ内容のイベントを同じ窓の外で2回発行する | `outbox_events` の行を確認する | **2行になる。** `outbox_events` は例外なく「1イベント1行・不変」であり、`jobs` の `operation_key` のような収束は起きない（`dedupe_key` も部分 UNIQUE 索引も無い）。2回起きた事実を1行に畳むと片方が配送されない | |
| `jobs` 側に大量の実行可能な行があり、outbox 側にも実行可能な行がある | Alarm を1回起床させる | **(3-a) と (3-b) の両方を必ず1回通る。** 件数上限は各パスが独立に持ち、片方が上限を使い切っても他方は必ず走る（共有すると片方の滞留がもう片方を飢えさせる） | |
| 同じ起床で2行以上のイベント行が claim される | 各行の `owner_token` を比較する | **互いに異なる。** `owner_token` は claim ごと・行ごとに一意な capability であり、**1回の relay パスにつき1個の値を全 claim 行へ書く実装にならない**（`jobs` からの引き写しで実装すると落ちる）。**本ケースが PASS / FAIL を判定するのは測れる3点だけである** — (i) 同じ起床で claim した行どうしが相異すること（重複0件）、(ii) 長さが 128 bit 以上であること、(iii) 起床をまたいでも同じ値が現れないこと。**生成源の要件（暗号論的乱数から採り、起床時刻・連番・DO 識別子など推測可能な材料から導かない）は実行時に検証できないので期待値に入れず、実装レビューの確認項目とする** — 規約の正本は `spec/database/index.md` の `owner_token` の列定義と [async/index.md](../../async/index.md)「`owner_token` の生成要件」である。共有させると、DLQ に落ちた1件から得た `(event.id, owner_token)` の対で同じバッチの他の行の呼び出しガードを通せる | |
| `owner_token` が `NULL` の `pending` 行がある（`enqueueEvent` の INSERT 直後、または上限未到達の失敗で `pending` へ戻った直後。**どちらも正常系で頻出する状態である**） | その `event.id` について、`owner_token` を伴わない（あるいは `null` の）送信材料 RPC を打つ | **`nothing-to-send` を返す。行側が `NULL` の照合は引数の値にかかわらず不一致である**（`password_reset_tokens.change_auth_token` と同じ規則）。`null === null` を一致として通す実装はこのケースで落ちる — 通すと「`event.id` を知る者が送信材料を引ける」ことになり、`event.id` は Queue と DLQ を通って DO の外へ出る。**引数側の `owner_token` も、欠落・空文字・規定長（128 bit）未満は照合の前に不一致として扱う** | |
