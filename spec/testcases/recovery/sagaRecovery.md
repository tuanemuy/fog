# テストケース: sagaRecovery

[recovery/index.md](../../recovery/index.md) が定める cross-DO saga の終端モードと自動回収に対するテストケース。**どのユースケースにも属さない機構のテストである** — ここで検証するのは終端モードの印・段の順序・材料の寿命・operator 経路・空 DO の非実体化の契約であって、各 saga の正常系と利用者から観測できることは各ユースケースのテストケース（`spec/testcases/identity/`）が持つ。

**期待値の書き方の前提。** 終端の発火にはバックオフ上限までの到達が要るので、テストは上限値を小さく設定するか、前進不能の確定（`ConflictError`）を直接再現して観測する。「`terminal_reason` に非露出対象が載らない」ことは列の内容として観測できるが、**ログ・トレース・メトリクスへの非出力は実行時に観測できないので期待値に入れず、実装レビューの確認項目とする**（規約の正本は recovery/index.md「`terminal_reason` の理由トークン」）。

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| 後始末を持つ `kind` のジョブが前進不能を確定させる（`ConflictError` とバックオフ上限到達の2形を個別に再現する） | その完了トランザクションを観測する | **`poison` にはならない。** 同じ `transactionSync` で `terminal_reason` に前進の理由トークンが書かれ、`status` は `pending` のまま、`attempt` は 0 に戻り、`next_run_at` は**通常の backoff 規則が `attempt = 0` について定める値**（**突入のための待ちを挟まない**。挟む実装は予約 TTL の右辺を押し上げ、`change_state='pending'` の利用者のログイン不能をその分だけ延ばす）、`lease_until` / `owner_token` は解放され、**`completed_at` は書かれない**。**その場で `poison` へ落とす実装は後始末が一度も走らないのでこのケースで落ちる** | |
| 終端モードの行（`status IN ('pending','running')` かつ `terminal_reason IS NOT NULL`）**のうち、後始末の段が実在するもの**（`resume-signup` / `resume-link`、および `change_state='pending'` の `resume-credential-change`） | 次の起床を観測する | **前進の段が1つも実行されず、後始末の段だけが実行される。** 印を読まずに前進から再開する実装は、前進不能が確定した相手を叩き続けるのでこのケースで落ちる。**段が実在しない行（後始末を持たない2 `kind` と `change_state='advanced'`）では逆に前進を実行する**（下の再駆動のケース） | |
| 終端モードの後始末が失敗する（上限未到達） | ジョブ行を観測する | 通常の backoff と同じ形で `attempt` が進み `next_run_at` が先送りされ、`status` は `pending`、`lease_until` / `owner_token` は解放される。`terminal_reason` は変わらない | |
| 終端モードの後始末がバックオフ上限を超える | ジョブ行を観測する | `poison` へ落ちて `completed_at` が書かれ、`terminal_reason` が `cleanup-exhausted:` を冠した値へ差し替わる。**前進の理由が値の中に残っている**（`forward-conflict` と `forward-exhausted` を個別に再現し、それぞれ対応する値になることを確認する） | |
| 終端モードの後始末が完走する | ジョブ行を観測する | `done` へ落ちて `completed_at` が書かれ、**`terminal_reason` は残る**（前進はできなかったが後始末は完走したという記録である）。この行は保持期間を過ぎたら prune の対象になる | |
| 終端に落ちた各 `kind` のジョブ行 | `terminal_reason` の内容を観測する | **載っているのは理由トークン（6値のいずれか）と `operationId` だけである。** canonical / 全長 HMAC / locator（世代・bucket index を含む）/ `callerToken` / `changeAuthToken` / `passwordVerifier` / リセットトークン / メールアドレス / `userId` のいずれも含まれない | |
| 新規登録 saga が phase 2 成功後・phase 3 の途中で終端する（`active` な孤児写像と未昇格の予約行が残る） | 後始末を観測する | **段の順序が S2（アカウント候補の放棄）→ S3（写像の解放）である。** 逆順の実装はこのケースで落ちる — canonical を先に解放すると「ログイン手段を持たない `active` アカウント」だけが残り、`credential_locators` が空なので bucket 走査からも到達できない（発見不能な残渣を作る向きには倒さない） | |
| 新規登録 saga のコーディネーター予約行を locator の PK で引けない状態で後始末が走る（operator の反応が予約 TTL より遅く、期限切れ掃除が先に消した形） | 後始末を観測する | **段 S1 が材料の不在を観測し、ジョブを `poison` へ落として記録を残す（`done` にしない）。`terminal_reason` は `cleanup-material-lost:` を冠した値へ差し替わり、前進の理由が値の中に残る。`attempt` が上限未満でも落ちる。** `done` にする実装は、残渣が残ったまま唯一の記録が prune の対象へ移るのでこのケースで落ちる。**`cleanup-exhausted:` を冠する実装は、再投入で回復しうる行と回復しない行を同じ値に畳んで operator の手順を誤らせる** | |
| 新規登録 saga の後始末が S3 まで進む | コーディネーター予約行とジョブ行を観測する | **S4 が予約行の削除（写像行 + その `credentialId` 宛のリセットトークン行）とジョブ行の `done` を1つの `transactionSync` で行う。** 別トランザクションに分けた実装は「材料は消えたが後始末が残っている」状態を作りうるのでこのケースで落ちる | |
| 新規登録 saga が phase 2 を一度も成功させずに終端し、候補 `userId` の User Data DO が未初期化である | 後始末の S2 を観測する | **空の User Data DO が作られない**（migration ゲートの初期化分岐が走らない）。応答は `nothing-to-abandon` で、後始末は**それを成功として** S3 へ進む。**失敗として再試行する実装は回収可能な残渣まで巻き添えにして `poison` へ落ちるのでこのケースで落ちる** | |
| `abandon-account` が進めない2条件（DO 未初期化 / 手続きの記録が無い）を個別に再現する | 応答を観測する | **どちらでも同じ `nothing-to-abandon` 1値が返り、後始末はそれを成功として S3 へ進む**（理由を分けない） | |
| `abandon-account` に一致しない `callerToken`（不一致・`NULL`・空・規定長未満の4形）を渡す | 応答と後始末を観測する | **分岐に畳まれず `SystemError` が返り、後始末は失敗として backoff する**（fail safe）。**`nothing-to-abandon` に畳む実装は、束縛の材料が欠けている環境で完走したアカウントに対して S3 / S4 を走らせるのでこのケースで落ちる**。**照合の位置は評価順序のとおりで、(1) 未初期化・(2) `deleting` / `deleted` の後、破壊的な作用 (6) と完走の検出 (5) より前である**（前提として `account` 行があり `status='active'` であること） | |
| `abandon-account` が進める（手続きの記録があり `callerToken` が一致し、記録が完了していない） | User Data DO を観測する | `account.status` が `deleting` になり `sessionEpoch` が進み、`finalize-withdrawal` が投入される（**退会の起点とまったく同じ書き込みである**）。2回呼んでも結果は同じで、投入は `operation_key` で同じ行に収束する | |
| SSO 登録 saga の2つの canonical が**別の** bucket に落ちた終端 saga | 後始末の S3 / S4 を観測する | コーディネーター行以外の全要素へ取り消しが発行され、コーディネーター行だけが S4 まで残る。除外の述語は `credentialId` の一致である | |
| SSO 連携 saga が手順3→4 の落下点で終端する（`active` な孤児写像が残る） | 後始末を観測する | **段 L2 が退避済みの写像材料の全世代へ `cancel-reservation` を発行し、`reserved` 行と `active` な孤児写像を同じ1つのエントリで消す。** `deleteMapping` を使う実装は `reserved` 行（`userId` が未確定）のガードを通れず手順2〜3 の落下点を回収できないのでこのケースで落ちる | |
| SSO 連携 saga の後始末が L2 まで進む | 手続きの記録とジョブ行を観測する | **L3 が `phase` を完了にするのとジョブ行の `done` を1つの `transactionSync` で行い、退避した写像材料（`targetLocators`）は空にしない** | |
| credential 変更 saga が `changeState = 'pending'` のまま終端する | 後始末を観測する | **自 bucket の1つの `transactionSync` で `pendingVerifier` / `changeState` / `changeOrigin` / `operationId` が `null` に戻り、同じトランザクションでジョブ行が `done` になる。cross-DO RPC を1本も発行しない。** 旧検証材料は正本のまま残り、`sessionEpoch` / `credentialVersion` には触れない | |
| credential 変更 saga が `changeState = 'advanced'` のまま前進不能を確定させる | ジョブ行と mapping 行を観測する | **終端モードへ入らず、その場で `poison` + `terminal_reason` に落ちる**（後始末が無い）。mapping 行は巻き戻されず `'advanced'` のまま残る。**巻き戻す実装は認証情報側だけを旧材料へ戻して版照合を外し、新しい締め出しを作るのでこのケースで落ちる** | |
| `changeState = 'pending'` の行が別の `operationId` の依頼に後勝ちで差し替えられた後に、古い saga の後始末が走る | mapping 行を観測する | **巻き戻しの CAS が0行になり、何も書かずにジョブが `done` になる。** 新しい依頼の `pendingVerifier` / `changeState` は残る | |
| 後始末が `cancel-reservation` を発行する対象クレデンシャルに、未使用のリセットトークン行が存在する（`active` な孤児写像が検証材料を持ち、リセット依頼が解決してトークンを発行した形） | 削除を観測する | **写像行の削除と同じ `transactionSync` でその `credentialId` 宛のリセットトークン行が全削除される**（写像を失ったトークン行を残さない） | |
| 後始末を持たない2種（`finalize-withdrawal` / `sweep-orphan-mapping`）が前進不能を確定させる | ジョブ行を観測する | **終端モードへ入らず、その場で `poison` + `terminal_reason` に落ちる。** 前進そのものが回収なので巻き戻す先が無い（退会は不可逆な意思、解除はユーザー単位設定側で既に確定している） | |
| `poison` に落ちた行が保持期間を過ぎる | prune の後にジョブ行を観測する | **`poison` の行は消えない**（prune の対象は `done` だけである）。**両方を消す実装は残渣だけが残って記録が消えるのでこのケースで落ちる**。同じ起動の prune で `done` の行は消えている | |
| `poison` の行が残っている DO | `list-poisoned-jobs` を呼ぶ | 返る列は `operation_key` / `kind` / `attempt` / `completed_at` / `terminal_reason` の5つで、**`payload` は返らない**。順序は `completed_at` の昇順で、件数上限を超えた分は続きとして引ける。読みのみなので Alarm は張り直されない | |
| `poison` の行しか残っていない DO（定義上 `deleteAlarm()` 済み） | `requeue-poisoned-job` を呼ぶ | `status='pending'` / `next_run_at = 現在時刻` / `attempt = 0` / `completed_at = NULL` の4列が書かれ、**`terminal_reason` は残り**、そのトランザクションのあと4本の min の合成で `setAlarm` が張り直される。**張り直さない実装は「行は `pending` に戻ったが誰も起こさない」状態を残すのでこのケースで落ちる** | |
| 後始末を持つ `kind` の `poison` 行を `requeue-poisoned-job` で再駆動する | 次の起床を観測する | **後始末から再開する** — その行に後始末の段が実在する以上（`resume-signup` / `resume-link` は常に、`resume-credential-change` は `change_state='pending'` のとき）、`terminal_reason` の値にかかわらず段の選択は後始末を選ぶ。前進はやり直されない。**段の選択を `terminal_reason` の値で決める実装は、`'advanced'` 残渣や後始末を持たない `kind` の再駆動で「実行すべき段が無いのに前進もしない」状態を作るのでこのケースと次のケースで落ちる** | |
| 前進も後始末も焼き切れた新規登録 saga | 予約行と `sweep-reservations` の関係を観測する | **期限切れ掃除が後始末の完走（S4）より先に走らない**（予約 TTL の右辺が「前進の総経過時間 + 後始末の総経過時間」の2項 + マージンであること）。**右辺を前進の総経過時間だけで見積もった設定は、材料が S4 の前に掃除されて孤児写像が記録なしで残るのでこのケースで落ちる**（S3 は `locators` を、S4 は `caller_token` を要求する） | |
| 正しく署名された、`account` 行が存在しない `userId` のセッション | アプリの保護経路を1つ開く | **DO は0バイトのままで、テーブルも `_meta` の行も作られない**（初期化分岐は `initialize-account` だけが実行してよい）。応答は fail closed（`SystemError`）である。**ゲートが無条件に初期化する実装は空の DO を作り、それは写像を持たないので bucket 走査からも発見できないのでこのケースで落ちる** | |
| 退会が完走したアカウントの有効なセッション cookie | アプリの保護経路を1つ開く | tombstone（`account.status = 'deleted'`）が残っているので従来どおり epoch ガードが拒否し、**DO は復活も再作成もされない**（退会は `account` 行を残す） | |
| `initialize-account` の本体（`account` / `user_settings` の書き込み）が失敗する | DO を観測する | **初期化分岐の DDL ごとロールバックされ、DO は0バイトへ戻る**（初期化分岐は本体と同じ `transactionSync` で確定する）。ゲート自身のトランザクションで先に確定させる実装は、回収経路の無い空 DO を残すのでこのケースで落ちる | |
| 新規登録 saga の終端後・後始末の完了前に、その canonical へリセット依頼が届く（`active` な孤児写像が検証材料を持つ場合） | 依頼とリンクの利用を観測する | 依頼はトークンを発行しメールも届く（**受容した残余**）。ただしリンクを踏んでも `credential_locators` が空なのでログインの到達性検査が拒否し、**認可はどの向きにも開かない**。後始末の S3 / S4 が写像行とトークン行を同じトランザクションで消した後は依頼も空振りになる | |
| 完走した新規登録 saga（手順7 までコミット済み）のジョブが、応答の喪失と対象 User Data DO の一時的な到達不能を経て終端モードへ入る | DO が回復したあとの後始末を観測する | **`abandon-account` が `already-completed` を返し、後始末はそこで打ち切られてジョブが `done` になる。写像もアカウントも1つも壊れない。** **コーディネーター予約行の存在だけで後始末の可否を判定する実装は、完走したアカウントの写像を全削除して恒久的にログイン不能にし、しかも `done` で終わるので記録も残らない** — このケースがその実装を落とす | |
| 新規登録 saga の手続きの記録（`operations`）のライフサイクル | 初期化（phase 2）と逆引きの記録（phase 4）を観測する | **phase 2 の業務書き込みと同じ `transactionSync` で行が作られ、phase 4 の逆引きの記録と同じ `transactionSync` で完了になる。** 2つを別トランザクションに分けた実装は「ログインできるのに手続きは未完了」という安定した中間状態を作り、上のケースの防壁（`already-completed`）を無効化するので落ちる | |
| credential 変更 saga の phase 2 がコミットした直後に応答が失われ、`changeState` が `'pending'` のまま終端して巻き戻る | 巻き戻し後のログインとリセット再依頼を観測する | **旧パスワードでのログインは版照合で拒否される**（認可は開かない）。**リセットの再依頼は通り、その1回の完走で両側の版が揃って回復する**（**受容した残余**）。巻き戻さない実装は `changeState` が `'pending'` のまま脱出経路を3つとも閉じたままにするので、こちらのほうが悪い | |
| 未使用の Identity Directory bucket（`_meta` の行が無い）へ最初の予約またはリセット依頼が届く | その bucket を観測する | **初期化されて通常どおり処理される。** 初期化分岐の制限は User Data DO にだけ掛かる（bucket 名は `bucketCount` で有界かつ利用者入力から独立なので、空 bucket が無制限に作られる経路が無い）。**制限を両クラスへ掛けた実装は、どの bucket も初期化できず登録もリセット依頼も成立しないのでこのケースで落ちる** | |
| 新規登録 saga が終端モードへ入ったあと、後始末の待ち時間のあいだにその canonical 宛のリセットが始まり、写像行の `operation_id` が別の手続きの値へ上書きされる | 次の起床の S1 を観測する | **後始末は材料を見失わない** — S1 は locator の PK で引くので行が取れ、S2 → S4 が通常どおり進む。**`operation_id` で引く実装は0行を観測して残渣を恒久化する（しかも `done` で終わるので記録も残らない）のでこのケースで落ちる**。同じ理由で `cancel-reservation` のガードにも `operation_id` を含めない | |
| `change_state = 'advanced'` のまま `poison` に落ちた行を、原因を解消したうえで `requeue-poisoned-job` で再駆動する | 次の起床を観測する | **前進から再開して phase 3 が完走する**（実行すべき後始末の段が存在しないので、段の選択規則が前進を選ぶ）。**phase 2（`advanceCredentialVersion`）は再発行されず**、phase 3 が揃える版は `findByCredentialId` の読み直しで取られる — **phase 2 を再発行する実装は、冪等でないカウンタを1つ余分に進めて昇格直後に両側の版をずらし、ログインを閉じるのでこのケースで落ちる**。**完走した行は `done` に落ち、`terminal_reason` は前進の理由トークンのまま残る**（冠は付かない。契機の表の「前進の完走」の行）。**`terminal_reason` の有無だけで「後始末しか実行しない」と判定する実装は、実行すべき段が無いまま止まって受け口が閉じないのでこのケースで落ちる** | |
