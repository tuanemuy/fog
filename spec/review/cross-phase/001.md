# クロスフェーズ検証 001

設計成果物全体（requirements / scenario / pages / adr / domains / usecases / database / testcases）の横断検証。

検証範囲と結果の概要:

- トレーサビリティ（上流 → ユースケース、ユースケース → ドメイン、エンティティ → DB、ポート → ユースケース、ユースケース → テストケース）
- アーキテクチャ適合性（インフラ非依存 / ロジック配置 / 集約間ID参照 / ポート抽象化 / 非循環）
- 実装可能性（設計書のみでコードを書けるか）

検証の結果、重大な欠落・矛盾はなし。以下の 3 件のみ対応を要する。

## 指摘事項

### 1. 未使用のリポジトリメソッド（ゴミ箱一覧系）

- 対象: [domains/memo.md](../../domains/memo.md) `MemoRepository.listTrashed`、[domains/knowledge.md](../../domains/knowledge.md) `DocumentRepository.listTrashedByUser` / `TopicRepository.listTrashedByUser`
- 問題: いずれも「trash ドメインが利用」と注記されているが、trash の全ユースケース（usecases/trash.md）はゴミ箱一覧・単体確認を `TrashQueryPort`（listTrashItems / findTrashItem / listExpiredItems）で行い、書き込み対象の再取得は `findByIdIncludingTrashed` / `listTrashedByTopic` を使う。上記 3 メソッドを呼ぶユースケース・ワーカーは存在せず、同一テーブルへの読み取り契約が二重定義になっている（trash.md「書き込みポートについて」が二重定義を避けると明言している方針とも不整合）
- 修正提案: 3 メソッドをポート定義から削除する。もしくは「`TrashQueryPort` アダプターの内部実装（UNION 枝）としてのみ使用し、application 層からは呼ばない」旨を明記して利用者を確定させる

### 2. search indexer 専用読み取り経路のシグネチャ未定義

- 対象: [domains/search.md](../../domains/search.md)「インデックス更新フロー」、[usecases/search.md](../../usecases/search.md) maintainSearchIndex の依存
- 問題: consumer の読み直し・出典逆引きは「userId を持たない indexer 専用の読み取り実装（アダプター実装詳細。DI で与える）」とだけ記され、インターフェース（メソッド名・引数・戻り値・エラー）が一切定義されていない。他のすべてのポートがシグネチャ付きで定義されている中で、maintainSearchIndex（テストケース 40 件超の対象）だけが依存の型を持たず、この設計書だけではワーカーコンテナの型定義とユースケースの実装・テストが書けない
- 修正提案: search ドメインのポートとして indexer 用読み取りインターフェースを定義する。例:
  `IndexerReadPort { findMemoById(id: MemoId): Promise<Memo | null>; findDocumentById(id: DocumentId): Promise<Document | null>; listSourceLinksByMemo(memoId: MemoId): Promise<readonly SourceLink[]>; listSourceLinksByDocument(documentId: DocumentId): Promise<readonly SourceLink[]> }`
  （userId スコープなしであることと「Outbox 由来の信頼済み ID 専用・application からは配線しない」制約をポートのコメントに明記）

### 3. AI `list_topics` の `includeArchived` が未規定

- 対象: [usecases/knowledge.md](../../usecases/knowledge.md) listTopics（入力 DTO で `includeArchived` は必須）
- 問題: 人間 UI は「アーカイブ済みを含めて取得し完了済みセクションに畳む」と明記されているが、AI 側 presentation（MCP `list_topics`）が渡す値、またはツール入力として公開するかが規定されていない。AI はアーカイブ済みトピックの解除（update_topic の archived: false。S-AI-06）や「完了済みトピックも検索対象」の前提を持つため、値の選択は挙動に直結する
- 修正提案: MCP `list_topics` の挙動を明記する。推奨: AI 側 presentation は `includeArchived: true` に固定する（アーカイブは「一覧の主要領域から退く」だけで AI から不可視にする要件はなく、解除操作の前提として ID を発見可能にする必要がある）。ツールパラメータとして公開する場合はその旨と既定値を記す

## 問題なしを確認した主な検証項目

- requirements 4.5 の全公開動詞（search / get / list_topics / recent_memos / post_memo / update_memo / create_topic / update_topic / create_document / edit_document / delete）→ ユースケースに 1:1 で対応。非公開インターフェース（ハードデリート・ゴミ箱・履歴・ロールバック）は ★ ユースケースとして AI 側 presentation から構造的に排除
- 全シナリオ（S-AC / S-TL / S-DT / S-SE / S-TR / S-AI / S-ST）・全画面（P-01〜P-14）の操作がユースケースの組み合わせで実現可能（ADR-001 の 3 分岐、S-TL-04 / S-DT-05 の競合警告、P-04 の指定メモ位置表示を含む）
- 全ユースケースのフロー内メソッド（エンティティ振る舞い・ドメインサービス・ポートメソッド）を機械的に突き合わせ、上記 1 以外の未定義・未使用なし
- 全エンティティ・永続化対象 VO は DB テーブルに対応（直和型は status + CHECK、Actor はリビジョン行のスナップショット、trash / search / export はテーブルなしの方針どおり）。主要クエリとインデックスの対応表も整合
- ユースケース ↔ テストケースファイルは 6 ドメイン全 42 ユースケースで 1:1 に対応（identity 13 / memo 14 / knowledge 15 / search 2 / trash 7 / export 1）
- アーキテクチャ: ドメイン層に I/O・`new Date()`・ID 生成なし、ドメイン間はID参照のみ（knowledge → MemoId、trash → identity の TrashRetentionDays 等、宣言された方向のみで循環なし）、ビジネスロジックは VO・エンティティ・ドメインサービスに配置、ポートはシグネチャ・エラーケース付きで定義済み
