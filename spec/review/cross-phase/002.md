# クロスフェーズ検証 002（ゼロベース横断検証）

検証日: 2026-07-21。対象: requirements / idea / scenario 全件 / pages / ADR-001〜006 / domains 全件 / usecases 全件 / database / testcases（ファイル一覧照合 + サンプリング）。

検証結果の要約: トレーサビリティ（シナリオ→ユースケース→ドメイン→DB→テストケース、AI 公開動詞の 1:1 対応、フロー内のポートメソッド名の突き合わせ、イベント発行/購読の対応）はすべて整合しており、実装可能性も各ドメインで確認できた。対応が必要な問題は以下の 1 件のみ。

## 問題点

### 1. [中] TokenScope の「型レベル強制」の主張がユースケース設計の入力 DTO と噛み合わない

- 該当箇所:
  - `spec/domains/identity.md`「TokenScope」節: 「ハードデリート・ゴミ箱・履歴系のユースケース（trash / memo / knowledge の該当ユースケース）は**引数型を `HumanScope`（または `UserActor`）に限定して定義する。`AiScope` を渡すことは型エラーであり、実行時チェックに依存しない**」
  - `spec/usecases/trash.md` 共通事項: 「identity の `TokenScope`（**引数型を `HumanScope` / `UserActor` に限定。`AiScope` を渡すことは型エラー**）で構造的に排除する」
- 矛盾の内容: 実際の ★ ユースケースの入力 DTO 定義には、この型制約を担うフィールドが存在しない。
  - `listTrash` / `restoreMemo` / `restoreDocument` / `restoreTopic` / `hardDeleteTrashItem` / `emptyTrash`（usecases/trash.md）、`listMemoRevisions` / `diffMemoRevisions` / `softDeleteMemo`（usecases/memo.md）、`listDocumentRevisions` / `diffDocumentRevisions` 等（usecases/knowledge.md）は入力が `userId: string`（+ 対象 ID）のみで、`HumanScope` / `UserActor` 型の引数が現れない
  - `rollbackMemo` / `editDocument` / `rollbackDocument` は `actor: Actor`（`UserActor | AiClientActor` の直和）を受けており、「`UserActor` に限定」になっていない
- 影響: 実装者が trash / 履歴系ユースケースを書く際、「型エラーで AiScope を排除する」設計をどう実現するか設計書からは決められず手が止まる（DTO どおりに書くと配線分離＝一重目の防壁のみになり、ドメイン設計が明記する二重目の構造的防壁が実装されない）。
- 対応案（いずれか一方に揃える）:
  - a. ★ ユースケースの入力（または `ServiceArgs` の認証コンテキスト）に `UserActor`（あるいは `HumanScope`）型のフィールドを追加し、`actor` を受ける ★ ユースケースは型を `Actor` → `UserActor` に狭める（usecases/trash.md・memo.md・knowledge.md の該当 DTO を修正）
  - b. 型レベル強制の主張を取り下げ、identity.md / trash.md / domains/index.md の記述を「application 層の公開範囲（配線）による構造的排除」のみに修正する
- **対応済み（2026-07-21、a と b のハイブリッド）**: 「型で守れるところは型で守り、残りは配線分離」に統一した
  - `actor` を入力に持つ ★ ユースケース（postMemo / editMemo / rollbackMemo / editDocument / rollbackDocument）: 入力 DTO の `actor` を `UserActor` に狭め、`AiClientActor` は型エラーと明記（usecases/memo.md・knowledge.md）
  - `actor` を持たない ★ ユースケース（trash 全件 / 履歴閲覧・diff 系 / getTopic / exportAll 等）: 型による強制は主張せず、AI 側 presentation への非配線（配線分離）＋ AI トークン認可ミドルウェアの許可ユースケース列挙で担保する表現に修正（usecases/trash.md・export.md、domains/trash.md・memo.md）
  - domains/identity.md「TokenScope」と domains/index.md「権限の非対称性」をこの二層構成の記述に統一

## 問題なしと確認した主な観点（記録）

- ユースケース→テストケース: usecases 全 52 ユースケース（identity 13 / memo 14 / knowledge 15 / trash 7 / search 2 / export 1）とテストケースファイルが 1:1 で存在
- AI 公開面: requirements 4.5 の公開動詞 11 と AI 向けユースケースが 1:1 対応。非公開（ハードデリート・ゴミ箱・履歴・ロールバック・エクスポート・identity 全件）は配線上すべて ★
- フロー内メソッド名: usecases が参照する全ポートメソッド（MemoRepository / TopicRepository / DocumentRepository / UserRepository / AiClientConnectionRepository / TrashQueryPort / SearchIndexPort / IndexerReadPort / ExportSourceReader / ArchiveWriter / PasswordHasher / PasswordResetTokenPort / MailSender）はドメイン側ポート定義に完備。シグネチャ（userId 第一引数・Versioned/ExpectedVersion）も一致
- イベント: memo 6 種 / knowledge 13 種 / identity 5 種の発行元と search consumer・トークン失効 consumer の購読対応が domains ↔ usecases ↔ ADR-005 で一致（ファンアウト・sourceLinksChanged の同一 UoW 発行を含む）
- エンティティ・VO→DB: 全エンティティが users / ai_client_connections / memos / memo_revisions / topics / documents / document_revisions / source_links に対応。直和は status + CHECK で表現、`documents.topic_id` に FK を張らない判断は ADR-001 と整合、source_links の消去系 JOIN 制約（documents 側限定）も ADR-003 の手順と整合
- アーキテクチャ: インフラ非依存（OAuth/セッション/埋め込み/zip はポート境界の外）、ドメインロジック配置（now/id 注入・純関数ファクトリ）、集約間 ID 参照のみ、循環依存なし
- ADR-001/002/003/005/006 の帰結（復元先選択・エクスポート範囲・リンク同期消去・冪等 consumer・メモ全文置換）はシナリオ・ユースケース・テストケースまで一貫
