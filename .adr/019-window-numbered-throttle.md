# 019. 依頼のスロットルは滑走窓ではなく窓番号の比較で行い、記録は無条件にする

## ステータス

承認済み

## コンテキスト

パスワードリセットの依頼のような未認証経路には、2つの要求が同時に掛かる。

- **スロットル** — 同じ宛先への連続した依頼を抑える。
- **配送の保証** — トークンを発行したなら必ずメールが出る。

素直な実装は「最後の依頼時刻 + 窓 <= 現在時刻」という滑走窓の判定と、依頼のたびに最後の依頼時刻を更新する記録の組み合わせである。この形は2つの問題を持つ。

- **恒久ロックアウト。** 窓より短い間隔で依頼を送り続けるかぎり、その宛先は永久に適格にならない。未認証の第三者が victim のアドレスへ投げ続けるだけで、victim はパスワードリセットを恒久的に受け取れなくなる。応答は4ケースで一様（`.adr/018-uniform-unauthenticated-paths.md`）なので、**victim にもオペレーターにも観測できない。** 同じファイルのログイン失敗カウンタは、まったく同じ問題を認識して「スロットル中の試行はカウンタを進めない」と塞いでいた。リセット側だけが逆向きだった。
- **配送ジョブとの衝突。** 配送ジョブの同一性キーが「対象と時間窓」から導かれるとき、発行の判定（滑走窓）とキーの窓（floor 分割）がずれる。発行は通るが投入が既存の完了行に弾かれ、**利用者が手元に持っている生きたリンクだけが壊れて新しいリンクは届かない**、という応答からは区別できない失敗が生まれる。トークンの発行は同じ対象の未使用行を全削除してから書くためである。

「適格なときだけ記録する」という解は採れない。配送キーの一意性は「最後の依頼時刻が**全依頼で**前進すること」に依存しており、条件付きにすると別の入口から同じ衝突が再発する。

## 決定

- **判定式を窓番号の比較へ変える。** `floor(最後の依頼 / 窓) < floor(現在 / 窓)`。記録は無条件のまま残す。
- **発行スロットルと配送ジョブのキーが同じ窓の定数を共有する。** これが不変条件を厳密にする — ある窓の最初の依頼は必ず適格であり（最後の依頼はそれより前の窓にある）、そのときその窓のキーの行はまだ存在しない。2回目以降は同じ窓なので必ず非適格。したがって**適格な依頼は必ず未使用のキーに着地する。**
- **その不変条件を「行が無い間」も成立させる。** 対象の行が新しく作られるとき、最後の依頼時刻を空にせず**作成時刻で埋める**。空のまま作ると、同じ窓の中で「未登録宛の依頼 → その宛先で登録 → 再度の依頼」が起きたときに、判定が通ってトークンが発行されるのに配送キーは既に使われている、という穴が開く。行を消して同じ窓で作り直す経路も同型である。
- **完了したジョブ行の保持期間を窓と等しくする。** 蓄積が有界（最大でも直近1窓ぶん）になり、かつ窓が変われば必ず新しいキーになる。
- 記録が無条件であることの理由は「再試行で窓を開け続けられないため」ではなく、**「この無条件性が配送キーの窓一意性を成立させているため」**である。理由を逆向きに書かない。

## 検討した代替案

**滑走窓のまま、非適格な依頼では記録を更新しない** — 配送キーの不変条件が壊れ、生きたリンクだけが黙って壊れる形が別の入口から再発する。

**滑走窓のまま、配送キーから窓を落とす** — 同じ宛先への依頼が永久に1行へ収束し、2回目以降のメールが出なくなる。

**宛先単位のスロットルを消し、抑制を別の軸（呼び出し元単位のレート制限など）だけに寄せる** — 1つのアドレスへ大量のメールを送らせる経路が開く。

## 影響

- 未認証の第三者が回復経路を恒久的に封じる攻撃が成立しなくなる。**消えたのは「恒久」であって「1窓ぶんの遅延」ではない。** 依頼レートそのものの抑制は別の課題として残る。
- 窓境界をまたいだ2つの依頼が実質同時でも両方発行され、直前のリンクが失効する。滑走窓では「同じ生きたリンクの再送」になっていた性質が変わる。
- **登録直後の窓ではリセット依頼が適格にならない**（最大で窓1つぶん）。パスワードを設定した直後の利用者がリセットを必要とする確率と、無言の未達を残す確率を較べての判断である。
- 窓の実値は運用調整の対象だが、**判定式と配送キーの導出が同じ定数を読む形を崩してはならない。** 崩すと上の不変条件が消える。
