# 012. パスワードリセットの完了時に新しいセッションを確立する

## ステータス

承認済み

## コンテキスト

リセット完了画面は**未ログインで到達する画面**である。一方、この画面がその場で提供する操作 — 覚えのない SSO 連携の解除、AI クライアント接続の一括失効、現在のアカウント状態の確認 — は、いずれもセッション由来の `userId` を要求する。

しかもリセットの完了はセッションの世代を前進させるので、**リセット前に張っていたセッションも同時に死ぬ**。結果として、完了画面が約束した導線は誰からも呼べない。リセットは「アカウントを取り戻す」経路であり、直後の失効操作こそ最も必要な局面なので、ここを一手遠くするのは筋が悪い。

## 決定

**リセットのユースケースが `{ userId }` を返し、presentation 層が世代を前進させた後にセッションを張る。** 扱いはログインと同じである。

これは「リセットの完了**前**にセッションを発行する」案とは別物である。前者は中間状態で発行したセッションが旧世代のまま生き残るため採らない。前進の**後**に張れば、生き残るのは新しいセッションだけになる。

## 検討した代替案

**完了画面から手動でログインし直させる** — ユースケースの出力を変えずに済むが、完了画面の導線が仕様の上で閉じない。リセット直後に最も必要な失効操作が一手遠くなる。

**完了画面だけ `userId` をセッション以外の材料から取る** — 「`userId` はセッションまたはトークン由来のものだけを使う」という全体の宣言に例外が要る。公開入力から対象オブジェクトを選ばせない、という分離の前提（`.adr/002-cloudflare-workers-and-user-data-durable-objects.md`）に穴を開ける。

## 影響

- 完了画面が認証済み画面になり、`userId` の出どころに例外を書かずに済む。仕様・手順書から「ログインし直す」という手順が消える。
- ユースケースの出力が void から `{ userId }` へ増える。
- **presentation 層に順序の責務が乗る。** 世代を進めた後に張らないと、新しく張ったセッションも旧世代として弾かれる。
