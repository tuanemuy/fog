# 013. Durable Object の永続化を素の SQL で書き、クエリビルダを依存から外す

## ステータス

承認済み

## コンテキスト

旧構成は共有 DB に対してクエリビルダとバッチ API を使い、スキーマ定義とマイグレーション生成も同じツールチェーンに乗せていた。

`.adr/002-cloudflare-workers-and-user-data-durable-objects.md` で利用者データを Durable Object へ移し、`.adr/004-do-local-commit-and-alarm-jobs.md` でローカル同期コミットへ移した結果、永続化 API が `exec(query, ...bindings)` を返す SQLite ストレージになった。このドライバに対応するクエリビルダは存在しない。

加えて、書きたい SQL の一部はクエリビルダでは表現できない。external-content 構成の全文索引の更新は `INSERT INTO … VALUES('delete', …)` という特殊コマンド構文を要求し（`.adr/005-search-projection-inside-write-transaction.md`）、楽観ロックの一致判定は `UPDATE … RETURNING 1` の行有無で行う。スキーマ移行も、スナップショットの差分ではなく forward-only のステップ配列が正本である。

## 決定

**クエリビルダとマイグレーション生成ツールを依存から外し、DDL とクエリを素の SQL 文字列として書く。**

- 発行は薄いラッパを経由する。ラッパが担うのは (i) カーソルから行を取り出す、(ii) bind パラメータ上限を超える呼び出しを開発時に検出する、(iii) ドライバ固有のエラーを共有のエラー契約へ翻訳する、の3つだけである。それ以上のことをさせない。
- スキーマの正本はデータベース設計（`spec/database/index.md`）で、コード側の正本は DDL 文字列そのものである。生成ツールを介さない。
- **列名を定数として宣言し、クエリ側がそれを参照する形は採らない。** 代わりに、各テーブルの全列を1回ずつ読み書きする統合テストを DDL と対で置く。

## 検討した代替案

**クエリビルダで書ける部分だけ使い、全文索引と楽観ロックだけ生の SQL にする** — 2つの記法が混在し、設計ドキュメントの DDL とコードを逐語で突き合わせるという最大の利点が失われる。

**Durable Object のストレージ API 向けのドライバを自作してクエリビルダを載せる** — 型付きのクエリが戻る代わりに、ドライバの保守が丸ごと自前になる。得られるものが「列名のタイポを型で捕まえる」だけであるのに対して払う額が大きすぎる。

**列名を定数として宣言する** — タイポは減るが、SQL 文字列がテンプレートリテラルの継ぎ接ぎになって読めなくなる。逐語の突き合わせができなくなるので、目的と手段が逆転する。

## 影響

- 依存が2つ減り、設計ドキュメントの DDL とコードが逐語で突き合わせられる。特殊コマンド構文も自然に書ける。
- **型付きのクエリビルダが無いので、列名のタイポが実行時まで出ない。** 全列を往復する統合テストがその代償であり、テーブルを足すときは DDL と対でテストも足す義務が生まれる。
- 別のランタイムへ移す場合、アダプター群の書き直しは SQL 文字列の書き直しになる。`.adr/004-do-local-commit-and-alarm-jobs.md` が受け入れたロックインの具体の1つである。
