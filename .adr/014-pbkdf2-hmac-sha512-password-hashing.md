# 014. パスワードハッシュを PBKDF2-HMAC-SHA512 + 210,000 反復に切り替える

## ステータス

承認済み

`.thread/1/adr.md` の ADR-003「パスワードハッシュ方式」が採った PBKDF2-HMAC-SHA256 + 210,000 を、**方式だけ** SHA-512 へ変更する。反復回数 210,000・salt 16 byte・出力 32 byte・「反復回数はファクトリ引数、環境変数からは設定できない」はいずれも据え置きであり、そちらの ADR はこの1点を除いて有効である。

## コンテキスト

`DEFAULT_PBKDF2_ITERATIONS = 210_000` に付いていた「OWASP の PBKDF2-HMAC-SHA256 推奨」というコメントは取り違えだった。210,000 は OWASP Password Storage Cheat Sheet の **PBKDF2-HMAC-SHA512 の行**の数字であり、PBKDF2-HMAC-SHA256 の行は **600,000** である。**誤っていたのは「210,000 が SHA-256 の推奨である」という帰属だけで、数字そのものは動いていない。** SHA-256 のままなら推奨の約 1/3 のコストで運用していたことになり、「OWASP 推奨だから安全」という ADR-003 の前提がそこだけ崩れていた。

出典: OWASP Password Storage Cheat Sheet — <https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html>（PBKDF2 節。2026-08-07 参照）。参照日時点で同節が挙げる3行は次のとおりで、どれがどれかは表の全体を見れば一意に決まる。**取り違えが起きた原因は元の記述が出典を持たなかったことなので、訂正の側は出典と3行の対応を残しておく。**

| アルゴリズム | 推奨反復回数 |
|---|---|
| PBKDF2-HMAC-SHA1 | 1,300,000 |
| PBKDF2-HMAC-SHA256 | 600,000 |
| PBKDF2-HMAC-SHA512 | **210,000** |

**チートシート自身は行ごとの回数の理由を述べていない。** 回数がこの順に少なくなるのは1反復あたりの CPU コストがこの順に高くなるからだが、「OWASP が GPU / ASIC 耐性を理由に SHA-512 の回数を低くした」という帰属も、「各アルゴリズムで防御側の所要時間が揃うようキャリブレートされている」という説明も、**どちらも出典の文言ではなく我々の読みである**。誤引用を正す文脈で別の未出典の断定を置けば、次に誰かがこの一文を引用したときに同じ経路で帰属が滑る。

そのうえで **SHA-512 を採る理由は我々の側に別途成立する**。SHA-512 は 64bit 演算主体で、32bit 演算に最適化された GPU / ASIC での並列効率が SHA-256 より低いと一般に言われており、**同じサーバー負荷あたりの攻撃者コストが高い**。これは我々の採用理由であって、OWASP が当該行の回数を設定した理由ではない。

選択肢は2つだった。**案 A: SHA-512 + 210,000** と **案 B: SHA-256 + 600,000**。どちらも OWASP 推奨を下回らないが、1導出あたりのコストは実測しないと比較できない。しかも**実測値を見た実装者が主観で案を選べてしまうと、この修正が是正しようとしている「根拠のない数字が定着する」という失敗が形を変えて再発する**。

比が測定環境で反転しうることも分かっていた。SHA-256 は SHA-NI / ARMv8 crypto extension でハードウェア加速されるが SHA-512 は一般にその対象外で、開発機の Apple Silicon は ARMv8.2 の FEAT_SHA512 を実装しうるため、**ローカル実測は SHA-512 に系統的に有利な方向へ偏る**。

## 前提

**この変更を初回本番デプロイ前に閉じた。** したがって旧コストで書かれたハッシュは本番に1行も存在せず、**ハッシュの移行処理が発生しない**。前提の確認とその限界は `.adr/015-legacy-pbkdf2-sha256-read-only-branch.md` にある。

この前提が崩れる場合（＝デプロイ後に同じ変更を行う場合）、rehash-on-login（[#18](https://github.com/tuanemuy/fog/issues/18)）が任意の追随策ではなく**ハード依存**になる。本 ADR を読み直すのはそのときである。

## 決定

**案 A（PBKDF2-HMAC-SHA512 + 210,000）を採る。** 保存形式は `pbkdf2-sha512$<iterations>$<saltBase64>$<hashBase64>`。`DERIVED_BITS = 256` は据え置く — PBKDF2 のブロック数は `ceil(dkLen / hLen)` で、32 byte 出力は SHA-256（hLen 32）でも SHA-512（hLen 64）でも 1 ブロックだからである。

**案の選択は、実測値に対する事前定義の判定ゲートへ委ねて機械的に行った。** ゲートの本体は `t_A ≤ 2.0 × t_B` なら案 A、それ以外は案 B の1行で、その前段に疎通（`deriveBits` が workerd で例外になれば案 B）と計測不能（中央値が `0` のままなら案 B。`0` は「速い」ではない）を置いて全域にしてある。

- **`2.0×` は価値判断であり、実測から導かれた数字ではない。**「SHA-512 の GPU / ASIC 耐性を買うために、ログイン1回あたりのサーバー CPU コストを最大2倍まで許容する」という判断そのものである。**しきい値は実装者が動かしてよい数字ではなく、変えるなら本 ADR を書き直す。**
- **絶対値の上限は置かない。** 比なら同一ランで取った2つの中央値の割り算なのでランナーの速さが約分されて消えるが、絶対値は測定環境のアーティファクトであり、そこに線を引けば本 ADR が最も避けたい「根拠のない数字が定着する」に形を変えて戻る。
- **比較は x86（GitHub Actions `ubuntu-latest` の workerd）で取る。** 再測定の唯一の目的は「SHA-NI で比が反転するか」なので、ローカル（ARM）では答えられない。x86 は SHA-256 だけが加速される**案 A にとって保守側（不利側）の条件**であり、そこで案 A が勝つなら実機でも成立する側に倒れる。

**実測（CI / x86_64。1導出あたりの中央値）は `SHA-512 @ 210,000` = 127.2ms、`SHA-256 @ 600,000` = 86.2ms、比 1.476** で、ゲートの `t_A ≤ 2.0 × t_B` の行に落ちて案 A が確定した（参考: [#20](https://github.com/tuanemuy/fog/issues/20) 以前の出荷構成 `SHA-256 @ 210,000` は 30.2ms）。**比は測定環境で実際に反転した** — ローカル（Apple Silicon / ARM）では 0.974 だったものが x86 では 1.476 になり、SHA-NI が SHA-256 側だけを加速するという想定どおりに動いた。**独立した2組の計測**（同一ランの attempt 3 が比 1.508、attempt 4 が比 1.476）が**どちらも同じゲートの行に落ちている**。数値の全文と測定条件は `.thread/1/adr.md` ADR-003 の「実測結果（#20 / 2026-08-07）」節にある。

**アルゴリズム識別子にも、反復回数と同じ `typeof` ピンを掛ける。** application 層の `DUMMY_PASSWORD_HASH_ALGORITHM_ID` / `DUMMY_PASSWORD_HASH_ITERATIONS` に対して、アダプター側が `ALGORITHM_ID: typeof DUMMY_PASSWORD_HASH_ALGORITHM_ID` / `DEFAULT_PBKDF2_ITERATIONS: typeof DUMMY_PASSWORD_HASH_ITERATIONS` と宣言し、**片方だけ動かすとコンパイルが通らない**ようにする。`loginWithPassword` はパスワードアカウントが見つからない経路でもダミーハッシュを1回 `verify` して応答時間を等時化する（`.thread/1/adr.md` ADR-026）ので、**等時化が成立する条件は「ダミーの宣言する計算量 == 実際に配線されたハッシャーの計算量」**である。今回の変更は反復回数を動かさずアルゴリズムだけを動かすため、反復回数だけのピン（`.thread/1/adr.md` ADR-034）はすり抜ける。定数の所在を application 層に置くのは依存方向の都合であり、逆向きの import は依存方向違反になる。

**ダミーハッシュの salt と digest は流用する。** 識別子と反復回数さえ現行に合わせれば計算量は一致し、salt / digest は「誰も一致させるつもりのない任意のバイト列」なので、新方式で真正に導出し直しても何も買えない（むしろ後の読み手が「意味のある値だ」と誤解する余地が生まれる）。

## 検討した代替案

**案 B（PBKDF2-HMAC-SHA256 + 600,000）** — 変更が定数1つに閉じ、`parse()` にもテストの大半にも手が入らない。1導出あたりの絶対コストも案 A より安い（86.2ms vs 127.2ms）。採らなかったのは、その差が事前に置いた許容枠（`2.0×`）の内側に収まったからであり、**枠の内側であれば差分は GPU / ASIC 耐性の対価として払う**というのが `2.0×` に込めた価値判断そのものである。

**反復回数を OWASP 推奨より下げる** — `.thread/1/adr.md` ADR-003 が代替案として挙げていた「100,000 に下げる」。セキュリティ上の後退であり、採るなら独立した ADR と Issue が要る。このスコープ固定は、絶対値の上限を判定ゲートに置かない判断の前提でもある（上限に触れるのは案 A が重い場合だが、その領域では比較が既に案 B を選んでいるので、上限が結論を変える入力の組み合わせが存在しない）。

**実測値を見て実装者が案を選ぶ** — 手順は最短だが、是正しようとしている失敗そのものの再演になる。判定をゲートへ委ねたことで、「なぜその案なのか」が後から数値で再現できる。

**ローカル（Apple Silicon）実測で確定する** — CI を1周待たずに済むが、ISA の問いには一段も近づかない。先行実測の比 0.974 が縮めたのは疎通と計測可能性の不確実性であって、SHA-NI の有無ではない。

## 影響

- 書き出す識別子が `pbkdf2-sha512` の1種類になる。読み取り側は非対称に広く、旧 `pbkdf2-sha256$` は読み取り専用の枝として残る（`.adr/015-legacy-pbkdf2-sha256-read-only-branch.md`）。`.thread/1/adr.md` ADR-003 が謳っていた「識別子付きエンコードによる無停止移行」を初めて実際に行使した変更である。
- **未認証経路の CPU コストが 30.2ms → 127.2ms（4.2 倍）になる。** 等時化により未登録アドレスへのログイン試行にも同じ1導出を払わせるので、**この増幅を引き出すのにアカウントの存在すら要らない**。1リクエストは CF Paid の 30 秒予算に対して問題にならないが、同時実行と CPU 時間課金の増幅は別問題であり、レート制限の受け皿は #18 である。
- `MAX_PBKDF2_ITERATIONS = 10_000_000` は据え置く。この上限に張り付いた行を1回 verify する最悪ケースは実測からの外挿で約 1.4 秒 → 約 6.0 秒に伸びるが、脅威モデルは変わっていない — 6.0 秒は 30 秒予算に収まり、そこへ到達するには DB への書き込み権限が要るので、この定数が守っているのは攻撃者ではなくデータ破損である。
- **型ピンには穴が1つ残る。** ピンが覆うのは `DEFAULT_PBKDF2_ITERATIONS`（＝既定値）であって、**ファクトリ引数 `iterations` を渡して構築されたハッシャーではない**。本番の配線が引数を渡した瞬間にダミー（210,000）のほうが高くなって**オラクルが反転**し、その経路は型検査にもテストにも一切引っかからない。防護は「本番の配線は既定値をそのまま使い引数を渡さない」という**運用規約だけ**である（現状 `serverCloudflare.ts` は引数なしで正しいが、それを固定しているものは無い）。塞ぐ案は本番強度の実導出を踏むテストを増やすことになるため採らず、残穴として記録する。アルゴリズム側は対応するファクトリ引数が無いので同じ穴は無い。
- application 層がアダプター実装知識（保存形式の文字列・反復回数・アルゴリズム識別子）を3つ抱える。**この写し取り方式には寿命がある** — 4つ目が要るとき（例: Argon2id のメモリ・並列度パラメータ）に破綻するので、そのときは `PasswordHasher` 側がダミー材料を供給する形への作り替えを検討する。
- 前提が生きている限り、既存ハッシュの移行処理は発生しない。前提が崩れた状態で同じ変更を行うなら、rehash-on-login が先に要る。
