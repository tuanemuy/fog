# 017. 同期ポートが要る暗号処理は Durable Object の RPC エントリで済ませ、導出済みの値をトランザクションへ渡す

## ステータス

承認済み

## コンテキスト

`.adr/004-do-local-commit-and-alarm-jobs.md` の帰結として、ドメインとアプリケーションのポート契約は同期である。トランザクションのコールバックは `await` を許さない。

一方、実行環境が提供する暗号 API は非同期である。したがって「暗号化した値を書く」「照合用のハッシュを書く」を素直に実装しようとすると、次のどれかに倒れる。

1. 同期で計算できる非暗号学的ハッシュで代用する。
2. 平文のまま書く、あるいは列を空のまま残す。
3. トランザクションの外にアダプターが独自の経路を作る。

**実際に (1) と (2) の両方が起きた。**

- リセットトークンは、発行・配送・検証の3者がそれぞれ別の値を扱う状態になった。メールに載る値からは行へ辿り着けず（機能として死んでいる）、逆に保存している識別子をそのまま提出すれば必ず一致する。保存に使っていたのは第二原像耐性の無いハッシュで、「生トークンを保存しない／保存値の漏えいでトークンは使えない」という仕様とポートの JSDoc の主張は、どちらも成立していなかった。
- 宛先アドレスの暗号文は**読む側だけが実装され、書き手がどこにも無かった**。実際の登録で作られる行は暗号文の列が空のまま作られ、統合テストが緑だったのはテスト自身が暗号文を仕込んでいたからである。症状が出るのは最初のリセット依頼のとき、つまり登録よりずっと後になる。

行き止まりに見えた理由は2つの制約の組み合わせだった。**平文を持つのは request 側 Worker だが暗号鍵は state 側 Worker にしか配られず**（`.adr/002-cloudflare-workers-and-user-data-durable-objects.md` の非重複配布）、**鍵を持つ Durable Object 側はトランザクションの中にいるので非同期 API を呼べない。**

## 決定

- **Durable Object の RPC エントリ自身は非同期である、という事実で抜ける。** エントリの中で `await` して暗号処理を済ませ、結果を**値として**同期のトランザクションへ渡す。トランザクションのコールバックの中では相変わらず何も `await` しない。**秘密の配布境界は動かさない。**
- **導出鎖を1本に確定し、1つの共有モジュールへ閉じる。** 行に載せるのは照合材料だけで、利用者へ渡す値からは照合材料を導出できるが逆は成立しない向きにする。ポートの契約は「導出済みの値を受け取る」ことを明文化する — トークンを返すのではなく、導出済みの材料を引数で受け取る。
- **暗号文とその付随情報（世代・nonce）は、個別の任意フィールドではなく1つの必須の値に畳む。** 任意フィールドの並びは「一部だけ書かれた行」を型で許してしまい、その行は二度と開けない。
- **鍵が未設定なら、その操作そのものを失敗させる。** 黙って空の値を書くと、症状が出るのが何日も後になる。鍵の読み取りはコンストラクタではなく各実行時に行う — コンストラクタで失敗させると、鍵を要さない診断経路や起床処理まで道連れになる。
- **非暗号学的ハッシュを使ってよいのは、取り違えの検出であって改ざんの検出ではない用途に限る。** 値がサーバー側で組み立てられクライアントから来ないこと、衝突の帰結が権限昇格にならないことの両方が成立する場合である。両者を混同しない旨を関数の JSDoc に書く。
- **読む側だけを先に実装しない。** 対になる半分を欠いた暗号モジュールは、付加認証データ・nonce・世代の規則が「テストと将来のローテーション処理だけが知っている」状態を作る。

## 検討した代替案

**ポートを非同期にする** — `.adr/004-do-local-commit-and-alarm-jobs.md` のローカル同期コミットそのものを引き直すことになる。非同期ポートの列挙（外部送信とパスワードハッシュ）は「非同期な API でしか実装できないもの」という基準で閉じており、そこに例外を足す根拠が無い。

**暗号処理を request 側 Worker で行い、暗号文だけを RPC で渡す** — 鍵を request 側にも配ることになり、非重複配布が崩れる。

**同期で計算できるハッシュで代用する** — 第二原像耐性が無く、「保存値の漏えいでトークンが使える」状態になる。実際にそうなった。

**書き込み側を後続の課題として残す** — 実際に一度そう残し、本番経路が壊れていることが後から判明した。

## 影響

- **暗号鍵が該当操作の必須バインディングになる。** 未設定のデプロイはその操作が失敗する。従来は「操作は通るが、後で黙って壊れていることが分かる」だった。
- RPC エントリの一部だけがトランザクションの外で仕事をする、という非対称な形になる。理由をクラスの JSDoc に残す。
- 未認証で起動できる経路では、**導出は不適格な入力に対しても無条件に実行する**（`.adr/018-uniform-unauthenticated-paths.md`）。結果は不適格なら捨てる。
- 鍵ローテーションを実装する側は、同じ導出モジュールをそのまま再利用できる。付加認証データと nonce の規則が1箇所にあるためである。
