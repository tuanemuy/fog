# 003. 検索は SQLite FTS5 の全文検索のみとする

## ステータス

承認済み

`spec/adr/005-search-index-via-outbox.md`「検索インデックスの更新方式」を `.adr/004-do-local-commit-and-alarm-jobs.md` と共同で supersede する。本 ADR が覆すのは**根拠側**であり、更新方式そのものを置き換えるのは `.adr/004-do-local-commit-and-alarm-jobs.md` である。

## コンテキスト

`spec/requirements.md` は検索を「キーワード検索とベクトル検索のハイブリッドを単一の検索として提供する」と定めている。これは初期アイデアの「ハイブリッド検索」を具体化したものだが、**ベクトル検索を必須とする利用上の根拠と評価データはどこにも記録されていない**。

一方で `spec/adr/005-search-index-via-outbox.md` は、インデックス更新を非同期にする根拠を「埋め込み生成は外部API呼び出しを伴い、書き込みトランザクション内で同期実行すると投稿の快適さ（要件: 直接操作は人間にとっても快適であること）を損なう」に置いている。つまり非同期化の理由はベクトル検索の存在から直接導かれている。

利用者ごとの Durable Object が持つ SQLite は FTS5 を提供し、本体データと索引を同じトランザクションで更新できる。ベクトル検索を採らなければ、外部 API 呼び出しそのものが検索インデックス維持から消える。

## 決定

**検索は SQLite FTS5 による全文検索のみとする。** ベクトル検索・Vectorize・embedding・RRF によるハイブリッド結果統合を、設計と実装の両方から除外する。

日本語を空白分割に依存せず扱えること、検索結果の順位付けが説明可能であることは、全文検索側の構成（正規化、トークナイザ、短語のフォールバック）で満たす。その成立根拠は `.thread/34/design.md` の第7.2節にある。

## 検討した代替案

**FTS5 とベクトル検索を統合する** — 元の要件どおりハイブリッドを維持する案。採らなかった理由は、ベクトル検索を必須とする利用上の要求が記録されておらず、それを維持するために払う代償（外部 API への依存、埋め込み生成の失敗と遅延、非同期インデックス維持、結果統合の説明不能性、運用と費用）が根拠なしに発生し続けるため。

**外部の全文検索エンジンを使う** — 検索だけを別サービスへ出す案。採らなかった理由は、利用者データの物理分離（`.adr/002-cloudflare-workers-and-user-data-durable-objects.md`）と正面から衝突すること、そして本体と索引の整合を保つために非同期の配送機構が再び必要になること。

**空白分割のトークナイザだけで済ませる** — 全文検索は採るがトークナイザを既定のままにする案。採らなかった理由は、日本語が空白で語を区切らないため実用にならないこと。

## 影響

- 検索の整合性・説明可能性・運用・費用が単純になる。本体と索引が同じ保存領域にあるので、外部インデックスとの結果整合を運用する必要が消える。
- **意味類似検索は提供しない。** 表記が異なり字面が重ならない語での想起はできなくなる。
- Vectorize と埋め込み生成の費用は消えるが、代わりに**全文索引の書き込み行数と容量が本体の数倍になる**トレードオフを負う。仮想テーブルへの書き込みも課金対象の書き込み行数に算入されるためで、容量の見積りと費用試算は本体の行数ではなく索引の行数で行う（`.thread/34/design.md` の第4.6節・第7.1節）。
- `spec/adr/005-search-index-via-outbox.md` が非同期更新の根拠としていた「埋め込み生成が外部 API を伴う」が失効する。これにより同期更新を妨げる理由が無くなる。
- 本決定は、公式ドキュメントに記載の無い FTS5 の挙動（トークナイザとランキング関数）が実行環境で動くことに依存している。裏付けは先行ブランチの spike で得た実測に限られ、実装着手時に再確認する（`.thread/34/design.md` の第2.1節の事実表・第2.1.1節・第11.2節）。再確認が覆れば本決定そのものが成立しない。
- **#37 の着手時に再確認済み（2026-08-03）。決定は成立する。** external-content の `tokenize='trigram'` 仮想表が作れ、3文字の日本語キーワードが期待どおりヒットし、`bm25(search_fts, 3.0, 1.0)` が例外なく順位を返した（値は負で昇順が良い順）。**2文字のクエリは `MATCH` で 0 件になる**ことも実測し、短語フォールバックの閾値を3文字に確定した（`instr()` 側で 1〜2 文字を拾う）。ページングが `LIMIT`/`OFFSET` で重複も欠落もなく割れることも確認している。これらは使い捨ての spike ではなく**常設の統合テスト** `packages/core/src/adapters/cloudflare/search/__tests__/tokenizer.integration.test.ts` として残してあるので、workerd のバージョンが上がった際の再検証は CI が自動で行う。実測の詳細は `spec/database/index.md`「FTS5 の tokenizer 方針」の #37 節にある。
- 将来、全文検索では満たせない具体的な利用要求と評価データが得られた場合は、別の Issue と ADR で改めて判断する。
