# 008. identity を認証情報側とユーザー単位設定側へ分割し、非集約ストアをドメインの契約として置く

## ステータス

承認済み。ただし「決定」欄のうち**クレデンシャル集合を操作する `addCredential` / `removeCredential` を置く**という部分だけは `.adr/022-credential-authority-and-projection.md` に superseded されている。それ以外の決定は有効である。

## コンテキスト

`.adr/002-cloudflare-workers-and-user-data-durable-objects.md` により、認証の権威（メールアドレスや SSO 主体から利用者を解決する）は利用者が確定していない経路を担う Durable Object に、利用者単位の設定は当人の Durable Object に置かれる。**物理境界が2つに割れた。**

ところが identity ドメインは単一の `UserRepository` と `User = PasswordUser | SsoUser` の判別共用体で、1つの境界と「1利用者1認証手段」を前提にしていた。パスワードのハッシュや SSO 主体は、もう利用者単位設定側の集約が持つ値ではない。

もう1つ、集約に属さないが必ず必要な状態がドメインの契約に現れていなかった。セッション失効の世代、リセットの世代、クレデンシャルの逆引き情報（到達性検査の権威）である。これらは物理スキーマにしか定義が無く、上位の層が名前だけを使う状態になっていた。

## 決定

- **`UserRepository` を2つに割る。** 利用者単位設定側を `UserSettingsRepository`、認証情報側を `CredentialMappingRepository` とする。
  - `UserSettingsRepository` は `findById` を持たず `find()` で足りる。その Durable Object の中には1人分の設定しか無いので、`findById` を残すと「他の `userId` を渡せる」という読み方が残る。
  - `CredentialMappingRepository` は読み取りだけを持つ。一意性の獲得と確定は単一のメソッドに畳めない手続きなので、ユースケース側の手順として書く。
- **`User` を判別共用体からクレデンシャル集合へ読み替える。** パスワード変更はエンティティの遷移から外す（`passwordHash` はこの集約のフィールドではなくなったので、遷移として定義できない）。代わりにクレデンシャル集合を操作する `addCredential` / `removeCredential` を置き、後者は最後のログイン手段の解除を拒否する。
- **クレデンシャルの参照に `usableForLogin` を持たせる。** 「ログイン手段が最低1つ残る」という不変条件は、種別でも要素数でも判定できない（SSO 専用のアカウントは、ログイン手段ではないメールを併せ持つ）。判定に必要な材料を型に載せることで、`removeCredential` が純関数のまま判定できる。
- **集約に属さない状態は、専用のストアをドメインのポートとして置く。** アカウントの状態とセッション・リセットの世代を扱う `AccountStore`、クレデンシャルの逆引き情報を扱う `CredentialLocatorStore` である。**`UserSettingsRepository` に畳まない** — 失効の権威を設定の集約に入れると楽観ロックの対象に入り、セッション失効が設定更新と競合する。
- **ポート名が `AccountStore` であっても `account` は集約ルート側である。** 非集約ストア（ジョブ、操作記録、移行進捗、逆引き、リセットトークン、鍵ローテーションの進捗）には数えない。名前の接尾辞ではなく、同一性と不変条件を持つ集約かどうかで分類する。
- **ドメイン層のポート名を永続化側の都合で変えない。** 物理テーブルと名前が食い違う場合は、どちらかへ寄せるのではなく対応関係を1行で示す。

## 検討した代替案

**判別共用体のまま維持する** — 1利用者が複数のクレデンシャルを持てない。SSO 連携の追加（`.adr/012-sso-credential-linking-scope.md`）が表現できず、パスワードと SSO の併用も表せない。

**ログイン可否を種別（`kind`）から導く** — SSO 専用アカウントが持つ「ログイン手段ではないメール」を種別だけでは区別できず、不変条件の判定が実際の権威（逆引き側の可否フラグ）と食い違う。

**非集約ストアの契約をデータベース設計側に預ける** — ドメインからの依存方向が外向きになる。上位の層が物理スキーマにしか定義の無い名前を使い続けることにもなる。

**失効の世代を利用者設定の集約に持たせる** — ポートは1本で済むが、セッション失効という頻度の高い書き込みが設定更新と同じ楽観ロックの対象に入る。

## 影響

- 認証に関わるユースケース（登録、SSO 登録、パスワード変更、リセット完了）が**単一のトランザクションに収まらなくなる。** 2つの物理境界をまたぐ手続きとして、順序と「中間状態・終端でそれぞれ何が観測されるか」を書く形になる。
- 中間状態では旧新どちらのパスワードでもログインできない。可用性の問題は残るが、認可は開かない方向へ倒れる。
- 集約ではないストアがドメイン層の契約として並ぶ。ポートの本数は増えるが、上位の層が使う名前がすべてドメイン側にアンカーを持つようになる。
- クレデンシャル一覧の出力に可否フラグが1つ増える。識別子ではない真偽値なので、同一性を表す値を露出させない方針とは衝突しない。
- **`addCredential` / `removeCredential` は置かないことに改めた**（#37 / `.adr/022-credential-authority-and-projection.md`。2026-08-03）。上の「決定」欄の当該2文は取り消されている。`credentials` は `CredentialLocatorStore` の射影であって集約が書く遷移を持たないので、集合を書き換えるメソッドは永続化されない no-op になる。**「クレデンシャルの参照に `usableForLogin` を持たせる」という決定自体は維持される** — 根拠が `removeCredential` の純粋性から、`User.loginCredentialCount`（述語。ドメイン側）と解除ユースケース `unlinkSsoCredential`（検査の所在。#12）の組に移っただけである。
