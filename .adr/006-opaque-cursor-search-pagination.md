# 006. 検索のページングを不透明カーソルに一本化する

## ステータス

承認済み

## コンテキスト

検索は複数種別（メモ / ドキュメント）を横断して順位付けする読み取りで、結果の並びは全文検索のスコアに依存する。ページ番号方式では、ページをまたぐあいだに本体が書き変わると同じ項目が2回現れたり、1回も現れなかったりする。検索は投稿直後の反映が同期になった（`.adr/004-do-local-commit-and-alarm-jobs.md`）ぶん、閲覧中に集合が動く頻度はむしろ上がる。

順位の同点をどう決めるかも決まっていなかった。同点のまま実装依存の順序に任せると、同じクエリでもページ間で並びが揺れる。

## 決定

**ページングを不透明カーソル方式に一本化し、ページ番号方式を残さない。**

- 最初の問い合わせで結果集合を**期限付きのスナップショットへ固定**し、以後は不透明なカーソルから同じ集合を読む。同じカーソルからは同じ集合が読め、期限切れのカーソルは拒否される。
- 順位の同点は `timestamp DESC, type, id` で決定する。
- **カーソルの検証責任を2つに分ける。** 形式（非空の不透明文字列であること）は値オブジェクトの構築が見る。中身と有効期限はポートの実装が見る。どちらも同じエラー（`InvalidCursor`）を返す — 利用者から見た対処は「先頭から検索し直す」で同じなので、区別する必要が無い。
- **スナップショットの物理形は決めない。** 期限付きのテーブル / Durable Object のストレージ上の一時キー / クエリ再実行と決定的な同点解決による安定化、のいずれを採ってもよい。寿命・粒度・退避先はストレージ上限と実測に依存する判断であり、固定するのは契約だけとする。
- **カーソルの返却は検索の出力にだけ足す。** 共有型 `PaginationResult` は広げない。総件数は返し続ける（固定した集合の件数として算出できる）。

## 検討した代替案

**ページ番号方式を維持する** — 実装は単純だが、ページ間の重複・欠落を防ぐ手段が無い。トピック絞り込みと組み合わせると、利用者が「消えた項目」を追う手段も無い。

**共有の `PaginationResult` に `nextCursor` を足す** — 検索だけの都合で共通型を広げると、カーソルを持たない読み取り（ゴミ箱一覧など）にも意味の無いフィールドが生える。

**期限判定も値オブジェクトの構築に寄せる** — 値オブジェクトは現在時刻もカーソルの復号手段も持たないので、原理的に判定できない。判定させるにはドメインへ ambient time を持ち込むことになる。

**逆に、カーソルの規則を値オブジェクトから消してすべてポートへ寄せる** — 空文字のカーソルが transport 境界を通ってポートまで届く経路が残り、「構築できた時点で最低限の形が保証される」という値オブジェクトの性質が失われる。

## 影響

- ページ間で重複・欠落が出ないことが契約になる。代わりにカーソルには寿命があり、放置した一覧からの追加取得は失敗しうる。
- スナップショットの実現手段を後から選び直しても、契約を変えずに済む。逆に、契約を読んだだけでは実際の保存場所は分からない。
- 検索の出力だけが共通のページング形から1フィールドはみ出す。
- クライアントは受け取ったカーソルをそのまま次の要求へ渡す。中身の解釈は検索ポートの実装に閉じる。
