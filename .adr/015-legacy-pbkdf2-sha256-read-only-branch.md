# 015. 旧 pbkdf2-sha256 形式を読み取り専用の枝として残す

## ステータス

承認済み

## コンテキスト

`.adr/014-pbkdf2-hmac-sha512-password-hashing.md` で書き出す識別子が `pbkdf2-sha512` に変わったため、既存の `pbkdf2-sha256$` 形式を `parse()` が引き続き読めるようにするかどうかが判断点になった。

- **捨てる場合** — 本番データが存在しないので誰も締め出さない。`parse()` は単一アルゴリズム前提のままで、変更は識別子と `derive()` に渡す digest 名だけで済む。**書き手の居ない枝という死にコードを抱え込まない**
- **残す場合** — `.thread/1/adr.md` の ADR-003「パスワードハッシュ方式」が謳った**「識別子付きエンコードによる無停止移行」の実証**になる。開発用ローカル D1 のデータも生き残る。一方、書き手が居ない以上その枝を実際に踏むのはテストだけになる

ADR-003 は「将来 Argon2id へ移行する際は `verify` に分岐を1本足し、rehash-on-login するだけで無停止移行できる」と書いているが、その主張はこれまで一度も実行されていない。

## 前提

**本番に `pbkdf2-sha256$` 形式の行が1行も存在しない。** 方式の切り替えを初回本番デプロイ前に閉じたためであり、着手前に次の2つで確認した（2026-08-07）。

- `gh api repos/tuanemuy/fog/deployments` が**空配列 `[]`** を返した（GitHub 側にデプロイ履歴が1件も無い）
- `.github/workflows/` にあるワークフローは `ci.yml` の1本だけで、ジョブは `lint-typecheck-unit` / `integration` / `build` の3つ。**デプロイジョブは存在しない**（デプロイは手動の `wrangler` 実行のみ）

**限界。** この2つが示すのは「このリポジトリ経由でデプロイされた痕跡が無い」ところまでである。**Cloudflare アカウント側の実状態（Workers / D1 に本番デプロイが存在しないこと）は確認できていない。** したがって前提が崩れるとすれば「リポジトリ外で手動デプロイが行われていた」場合であり、その可能性を潰す確認は実施していない。

## 決定

**残す。** `parse()` を「**読める識別子は複数・書き出す識別子は1つ**」という非対称な形にし、`pbkdf2-sha256` を読み取り専用の枝として置く。

- その非対称は「読み取り経路は部分関数・書き出し経路は全域」としてコードに現れる。読み取り側は全域関数 `hashFor(algorithm: string): "SHA-256" | "SHA-512" | null`、書き出し側は保存形式に書く識別子（`ALGORITHM_ID`）と WebCrypto に渡す digest 名（`SHIPPED_HASH`）を直に持ち、`hashFor` を一度も引かない。
- **対応表（`Map` / 素の object）は導入しない。** 素の object を**利用者由来の `string`** で引くと `constructor` などプロトタイプ由来のキーが truthy を返し、`constructor$1000$…$…` という保存値が未知アルゴリズムの拒否をすり抜ける。読み取り側を `===` の比較で書けばこの穴は構造的に開かない。
- **決め手は開発用データの延命ではなく、ADR-003 の移行戦略が机上の主張のままか、実際に一度通した経路かの差である。** Argon2id への移行は現実の選択肢として残っており、そのときに初めて2方式の `parse()` を書くより、本番データが無い今のうちに形を確定させておくほうが安い。

**退役条件。** この枝が守っているのは (a) 開発用ローカル D1 のデータ、(b) 将来 Argon2id を足すときの `parse()` の形、の2つだけである。よって次のいずれか早い時点で**削除してよい**（削除に「全ユーザーが一度ログインしたか」の確認は要らない — 対象の行が本番に存在しないため）。

1. [#18](https://github.com/tuanemuy/fog/issues/18)（rehash-on-login）が**走り終えて**、旧形式の行が残っていないことを確認した時点
2. 開発用ローカル D1 の該当行の寿命が尽きた時点（誰も既存の開発用アカウントでログインしなくなった時点）

**条件1を「#18 が入った時点」と書いてはならない。** #18 の rehash-on-login は**旧枝で `verify` できることを前提に**旧行を新形式へ書き直すので、#18 の着地と同時に旧枝を消せば #18 自身が旧行を掃き出す手段を失う。**枝は #18 より長く生き残る必要がある。** #18 が塞ぐのは「旧形式の行が生まれ続けること」ではなく「既存の旧行が残り続けること」なので、削除してよいのは**掃き終えた後**である。2つの条件は同じ状態（旧形式の行がどこにも無い）へ収束し、違うのはそこへ到達する手段（rehash-on-login か自然消滅か）だけである。**本番についてはどちらの手段も要らない** — 上の前提が正しければ本番だけを見るなら即時に削除してよく、2条件が縛っているのは開発用ローカル D1 のほうである。

**削除時に1点だけ確認する: `derive()` の鍵素材を守る外部固定ベクターが失われないこと。** 旧形式のフィクスチャを持つリグレッションテストは「旧枝の生存確認」と「`derive()` が WebCrypto に何を食わせるかの外部固定」の2役を兼ねており、後者は往復テストでは代替できない（`hash()` 側と `verify()` 側が一緒に動くので、鍵素材の作り方を変えても往復は常に成立する）。出荷形式 `pbkdf2-sha512$` の golden vector が別に1件あるので旧フィクスチャを落としても固定は残るが、**その1件が現存することを削除時に確認する**（両方が同時に消えれば、保存済みハッシュが全件検証不能になるクラスの変更を止めるテストがゼロになる）。

## 検討した代替案

**旧枝を捨てる** — 本番データが無いので誰も締め出さず、死にコードも抱えない。採らなかったのは、無停止移行を実証する機会がここにしかないためである。本番データが1行も無い今は、その形を確定させるコストが最も低い局面でもある。

**読み取りを対応表で書く** — 分岐が方式の数に比例して伸びない代わりに、プロトタイプ由来キーの穴が開く。リテラル型をキーにした表なら全域にできるが、方式が2つしかない現状では表を維持するコストが上回る。**方式が3つ目に増えたらこの比較を引き直す** — 表の維持コストは方式の数に比例せず、ドリフトの起こりうる組み合わせのほうが先に増えるからである。

**#18 の着地時点で削除する** — 退役の判断が1点に決まって分かりやすいが、#18 自身が旧行を掃き出す手段を失う。

## 影響

- ADR-003 の「識別子付きエンコードによる無停止移行」が主張から実装へ変わる。Argon2id 導入時には `parse()` の多方式化が既に済んでいる。
- 開発用ローカル D1 に既存データを持つ開発者がログインできなくなる事故が起きない。
- **書き手の居ない枝が残る。** 実際に踏むのはテストだけなので、旧形式のフィクスチャをハードコードしたリグレッションテスト1件が**旧枝の唯一の生存確認**になる。`parse()` の分岐が1本増え、拒否ケースのテスト表も1件（プロトタイプ由来キー）増える — 後者は実装上そもそも通らなくなった後も、`parse()` が将来表引きに戻ったときの回帰網として残す。
- **旧形式の行に対する誤パスワードは、未登録アドレスより約 97ms 速い**（CI / x86_64 実測で `SHA-256 @ 210,000` = 30.2ms に対しダミーは `SHA-512 @ 210,000` = 127.2ms）。等時化の残差はネットワークノイズに埋もれる量ではなく、「そのアドレスは登録済みで、かつ方式変更より前に作られた」を判別しうる**列挙オラクル**である。**受容できる理由は残差が小さいことではなく、上の前提（本番にその形式の行が1行も存在しない）が成立していることである。** 前提が崩れればこの受容も同時に崩れる。
- アダプターの JSDoc は等時化の残差の向きを「コスト」から「コストまたはアルゴリズム」へ広げるに留め、**実測値そのものは渡さない。** 数字は測定環境に依存して陳腐化する一方、JSDoc にはドリフトを止める仕掛けが無く、`CLAUDE.md`「Default to no comments」の下では大きさをコメントに持たせるのが割に合わない。大きさの記録は本 ADR と `.thread/1/adr.md` が担う。
