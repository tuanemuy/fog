# 026. クライアントへ返さないサーバ側自由文を kind で分類し、落とす kind は必ずログへ残す

## ステータス

承認済み

## コンテキスト

エラーはそれぞれ `kind` タグ付きの直列化形を持ち、presentation 層が構造的に直列化する（`CLAUDE.md`「Error handling」）。直列化形には、サーバー側で組み立てた自由文のメッセージが載る。

**そのメッセージには、内部の識別子・キー・語彙が混ざりうる。** 実際に、ジョブの競合エラーが宛先由来のハッシュを含むキーをメッセージへ埋め込んでいた。到達不能ではあったが、それは構造ではなく偶然だった（payload がたまたまキーの関数だった）。

素直な対処は「見せてよいコードの allowlist へ反転する」だが、そのまま採ると壊れる。表示側は一部の `kind` について**コード別の文言が無いときメッセージへフォールバックする**設計であり、メッセージまで潰すと新しいエラーが黙って空表示になる。

逆に、メッセージをワイヤから落とすとサーバー側のログ条件も同時に見直す必要がある。落としただけだと、その `kind` の自由文が**ワイヤからもログからも消える**。実害が出るのは楽観ロックの競合のように、他に痕跡が残らないまま境界まで上がってくるものである。

## 決定

- **`kind` を網羅する `switch` で3分類にする。**
  - **全部潰す**（システム／未知）— コードも落として固定文言にする。
  - **メッセージだけ潰す** — コードは残し、メッセージを固定文言へ置き換える。対象は**表示側が固定文言の枝しか持たず、メッセージを一度も読まない** `kind` である。したがって潰しても UI は変わらず、サーバー側の自由文だけが落ちる。
  - **素通し** — 表示側がメッセージへフォールバックする `kind`（業務ルール違反、入力検証）。
- **ログ条件を `kind` の列挙ではなく「メッセージを落とすか」から導く。** 同じ網羅 `switch` を読む述語を1つ置き、境界のミドルウェアがそれを呼ぶ。ワイヤに message が残る `kind` はログしない — フォームの却下を運用インシデントにしない。
- **対称性をテストで固定する。** 「落とす述語の結果」と「実際に置き換えが起きたか」を全 `kind` について突き合わせる。
- 網羅 `switch` なので、`kind` を足す人は**分類を選ぶまでコンパイルが通らない。** ログの有無も同時に強制される。

## 検討した代替案

**見せてよいコードの allowlist へ反転する** — メッセージへフォールバックする表示経路が黙って空になる。

**メッセージを組み立てる側だけを直す** — 個別の修正は同じ形で再発する。分類は二重の防御として、組み立て側の修正と独立に成立させる。

**ログ条件を `kind` の列挙のまま維持する** — 分類を変えるたびに列挙も直す義務が生まれ、実際に一度食い違って「ワイヤにもログにも無い」kind が生まれた。

## 影響

- 一部の `kind` のサーバー側メッセージが、ブラウザの開発者ツールからも読めなくなる。運用側は直列化前の値をログで見る。
- **クライアント都合でも起きる `kind`（不在、未認証）がログに載るので、ログ量が増える。** `kind` 付きなのでフィルタできる、という前提で受け入れる。量が問題になったら、この分類ではなくログレベルの側で解く。
- 「運用側は直列化前の値を見られる」という前提は、ログ条件を分類から導いて初めて成立する。分類とログ条件のどちらか片方だけを変えてはならない。
