# 024. 起動時制約は成果物を起動するスモークで検出し、合成ルートは実行部モジュールを value-import しない

## ステータス

承認済み

## コンテキスト

実行環境（workerd）は、モジュールのトップレベルで乱数生成・タイマー・外部呼び出しを行うことを禁じている。違反はビルドを通り、型検査も lint も統合テストも通り、**Worker を起動した瞬間に落ちる。**

統合テストが検出できない理由は構造的である。Workers プールはテストモジュールをハンドラ相当のコンテキストで評価するので、そもそもトップレベルの制約に当たらない。`.adr/001-integration-tests-single-workers-pool.md` が集約したスイートはこの性質を持つので、そこへ何を足しても検出しない。

実際にこの形の障害が起き、開発サーバ以外の起動経路がすべて塞がった。原因は**依存の向き**だった。合成ルート（DI）がチューニング定数をワーカー実装モジュールから value-import しており、**その1本の import が、トップレベル Worker にワーカー実装モジュールを評価させる唯一の流入経路になっていた。** 定数そのものは無害で、評価されたモジュールの副作用が問題だった。

## 決定

- **ビルド成果物を実際に起動するスモークスイートを、統合テストとは別のレイヤーとして置く。** 各 Worker の成果物のパスを実行環境のエミュレータへ渡して起動させ、応答するところまでを見る。検出対象は乱数生成に限らず、トップレベルの禁止操作全般である。
- **`.adr/001-integration-tests-single-workers-pool.md` の「統合テストは Workers プール1本」は破られない。** スモークは「アイソレートへ import したコードを検証する」統合テストとは問いが違う（**成果物が起動するか**）。プールではなくレイヤーの違いであることを、設定ファイル冒頭のコメントに残す。
- **チューニング定数は import を1つも持たない leaf モジュールに置き、合成ルートも実行部もそこからだけ読む。** 逆に、実行部モジュールが定数を export する形を禁じる。これで合成ルートが実行部を推移的に評価する経路が構造的に消える。
- **スモークは成果物の鮮度も見る。** 存在確認だけだと、前回のビルド結果が残っている状態にも緑を返す。ソースの最新更新時刻より成果物が新しいことを検査し、失敗時のメッセージでビルドを指示する。

## 検討した代替案

**統合テストへ足す** — プールの性質上トップレベルの制約に当たらないので、何を足しても検出しない。

**lint ルールで禁止する** — 直接の呼び出しは捕まえられるが、推移的に評価されるモジュールの中の呼び出しは捕まえられない。実際の障害は推移的な経路だった。

**定数を実行部モジュールに置いたまま type-only import にする** — 定数は値なので type-only にできない。

**スモークのスクリプト自体にビルドを内包させる** — 継続的インテグレーションが既にビルド後に実行しているので、ビルドが2回走る。

## 影響

- テスト設定ファイルが増える。`.adr/001-integration-tests-single-workers-pool.md` が畳んだばかりの分割が別の軸で1本増える形なので、それぞれの冒頭に「何のための設定か」を1行書く。
- ビルドを前提とするので実行コストが上がる。ビルド工程に相乗りさせて追加コストを抑える。
- **ソースを触っただけでもスモークは赤くなる。** 誤診を防ぐため、メッセージがビルドコマンドを指示する形にする。
- 定数の値が、それを使う実装から離れる。表のキーを対象の型で型付けして対応を落とさない。
- 起動時制約の違反は、どの Worker で起きても捕まる。Worker を増やすときは、スモークの対象にも同時に足す。
