# 011. ポートの同期契約の例外は「非同期 API しか無いもの」に限る

## ステータス

承認済み

## コンテキスト

`.adr/004-do-local-commit-and-alarm-jobs.md` により、Durable Object のローカル SQLite を触るポートは同期契約になった。すべてのポートが同期になるわけではなく、`Promise` のまま残るものがある。問題は**その線引きの理由**である。

当初の理由は「トランザクションの外（リクエスト処理 / ジョブ実行）で動くから」と書かれていた。結論として挙がっていたポートの一覧は正しかったが、**理由が判定基準として機能しない。** エクスポートの書き出しポートも Durable Object の外で動くが同期契約である。この一文を基準として適用した実装者は、同期でよいポートを `Promise` へ戻す。

## 決定

**理由を実際の線へ差し替える。** `Promise` が残るのは、**暗号計算と外部 I/O であり、実装できる API が非同期しか無い**ポートに限る。

- **トランザクションの外で動くことは `Promise` の根拠にならない。** 反例（エクスポートの書き出し）とともに明記する。
- **例外は列挙であって導出規則ではない。** 新しいポートを足すときの問いは「外で動くか」ではなく「**同期で書けるか**」である。
- 非同期ポートを Unit of Work のコンテキストへ載せない。

## 検討した代替案

**実行位置で決める** — 判定は簡単だが、既存のポートと食い違う。食い違いを例外として書き足していくと、基準そのものが機能しなくなる。

**すべてのポートを非同期のまま残す** — 基準を考える必要が無くなるが、`.adr/004-do-local-commit-and-alarm-jobs.md` がローカル同期コミットで得た利点（同一 Unit of Work 内で書いた結果を読み直せる、`async` を型で弾ける）を捨てることになる。

## 影響

- 例外が増えにくくなる。「外で動くか」より「同期で書けるか」のほうが厳しい問いである。
- 判定基準が実際に判定できる形になり、既存のポート定義と矛盾しなくなる。
- ポートを追加する側は、非同期 API しか無いことを示せない限り同期契約で書く。
