# 014. spec/ を単独で読めるようにし、CLAUDE.md には規則だけを置く

## ステータス

承認済み

## コンテキスト

設計の検討は Issue 単位の作業ディレクトリ（`.thread/{番号}/`）で行い、恒久ドキュメントは `spec/` と `CLAUDE.md` が担う。この関係が曖昧なまま運用すると、次の3つの壊れ方をする。

- **`spec/` が作業ディレクトリへ内容を預ける。** 作業ディレクトリは Issue が閉じたあとも残るが、恒久ドキュメントとして索引に載っているわけではない。名指しで参照して内容を預けると、`spec/` が単独で読めなくなる。
- **`CLAUDE.md` と `spec/` が同じものを二重に持つ。** 員数や具体形を両方に書くと、片方を直した人がもう片方に気づかない限り**両方が嘘になる**。しかもどちらが正本かは文面からは決まらない。
- **索引の件数が概数で書かれる。** 「約750ケース」は 700 でも 782 でも成立してしまうので、嘘になったことを検出できない。

加えて、設計の結論を実装より先にドキュメントへ落とす局面がある。規則だけを新構成で断定すると、`CLAUDE.md` が「いまこのリポジトリで作業するためのガイド」としては嘘になる。

## 決定

1. **`spec/` は単独で読める。** 恒久ドキュメントから作業ディレクトリを名指しで参照して内容を預けない。実装の根拠になるもの（テーブルの全数など）は `spec/` 側へ写し、`spec/` を正本と明記する。
2. **`CLAUDE.md` は規則だけを持つ。** 員数（ストアが何本か）、per-table の具体形（条件付き更新の条件句の形）、全数表（ジョブ種別と投入点）は書かず、`spec/` を正本として指す。`CLAUDE.md` が持つのは**列挙と構造と例外の形**までである。
3. **実測に依存する調整値は `spec/` に固定しない。** 検索の重み付けやページサイズ、試行制限の回数や減衰の時定数のように、実環境の測定と運用調整で決まる値は、規則（「タイトルを本文より重く見る」「天井と時間減衰と非加算の3規則が存在する」）だけを書き、値そのものは実装・運用側が持つ。
4. **索引の件数は台帳の実測を正本とし、概数を使わない。** 実数なら数え直しで突き合わせられる。
5. **規則は実装に先行して断定してよい。** ただし実装が追いつくまでの差分は**1箇所へ集約して注記**し、各節へ「ただし現状は」を散らさない。裏づけとなるコードや JSDoc がまだ無い項については、`spec/` が唯一の正本であることを述べる。

## 検討した代替案

**作業ディレクトリを恒久参照として扱う** — 転記の手間は無くなるが、`spec/` を開いた実装者が Issue の作業ログまで降りないと実装できなくなる。正本が閉じた Issue の中にある状態は、その Issue を見ていない読み手に対して説明がつかない。

**`CLAUDE.md` に全数を持たせる** — 読み手が数で確認できる利点はあるが、正本が二重になる。名簿が動くたびに2箇所を同時に直す義務が生まれ、片方が古くなったことを検出する手段が無い。

**規則の改訂を実装 Issue まで遅らせる** — `CLAUDE.md` が常に現況と一致する利点はあるが、確定した設計判断の置き場所が無くなる。判断が実装の直前まで作業ログの中に留まり、実装者が設計を再開させる。

**注記を各節に散らす** — 読む場所と現況が近くなるが、実装が追いついたときの消し漏れが必ず出る。1箇所なら撤去が1行で済む。

## 影響

- 同じ情報が `spec/` と `CLAUDE.md` の両方に現れるときは、`CLAUDE.md` 側が必ずポインタになる。追加・削除で直すのは列挙1箇所だけで済む。
- **`CLAUDE.md` だけを読んでも具体的な形は決まらない。** 正本へのポインタで代替する。
- 索引の件数はテストケースを1件足すたびに古くなる。ただし台帳を直さずにテストケースだけ足す運用は既に禁じているので、更新はその作業に1行足す形で済む。
- **移行中の注記は消し忘れると害になる。** 実装が追いついた後も「移行中」と読まれ続けるので、実装側の Issue に撤去を完了条件として持たせる。
- 転記した内容は正本が2箇所に見えうる。どちらが `spec/` 側の正本かをファイル冒頭で宣言し、以後は `spec/` を直す側が正しいという順序を固定する。
