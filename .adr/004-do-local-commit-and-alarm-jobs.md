# 004. ローカル同期コミットと Alarm ジョブへ移行し、Outbox 配送を廃止する

## ステータス

承認済み

`spec/adr/005-search-index-via-outbox.md`「検索インデックスの更新方式」の**更新方式**部分を `.adr/003-sqlite-fts5-only-search.md` と共同で supersede する。

## コンテキスト

現行はドメインイベントを Outbox へ書き、relay が Queue へ配送し、consumer が受け取って処理し、失敗は DLQ へ落ちる、という構成になっている。この構成が必要だったのは、更新の一部が別の保存領域（検索インデックス）にあり、そこへの反映が外部 API 呼び出しを伴っていたためである。

`.adr/002-cloudflare-workers-and-user-data-durable-objects.md` で利用者データを1つの Durable Object へ集約し、`.adr/003-sqlite-fts5-only-search.md` でベクトル検索を採らないと決めた結果、この前提が両方とも消えた。本体と検索索引は同じ SQLite にあり、更新に外部呼び出しは要らない。

にもかかわらず Outbox を全更新の transport として使い続けると、**同一保存領域の中の整合まで非同期化してしまう**。投稿した直後に検索でヒットしない、という体験上の欠点を、技術的な必然が無いまま抱え込むことになる。

一方で、外部 I/O を伴う処理（メール送信）と、要求処理から分離すべき期限処理（ゴミ箱の保持期限）は残る。これらは要求処理の外へ出し、失敗しても再起動後に回復できる形にする必要がある。

## 決定

**Durable Object のローカル SQLite トランザクションと Alarm で完結できる処理は、Outbox / relay / consumer / DLQ から移行する。**

- 本体データと検索索引は同一トランザクションで同期的に確定させる。コミットが成功したときにだけ、両方が同時に変わる。
- 外部 I/O を伴う処理と期限処理だけを永続的なジョブとして残し、オブジェクトごとに1本の Alarm で処理する。ジョブは冪等キーと再試行の状態を持ち、途中で失われても再開できる形にする。
- ドメインイベントを配送の transport として扱うのをやめ、業務・監査の表現としても残さない。Unit of Work からのイベント収集そのものを廃止する。

## 検討した代替案

**全更新を Outbox 経由にする** — 現行構成を維持する案。採らなかった理由は、同じ保存領域の中の整合まで結果整合にしてしまい、体験上の欠点（投稿直後に検索へ反映されない）を技術的な必然なしに抱えること、そして relay / consumer / DLQ の運用が理由を失ったまま残ること。

**トランザクションの中で外部 I/O を行う** — ジョブ機構を持たずメール送信をその場で行う案。採らなかった理由は、外部の遅延と障害が利用者の操作の成否に直結すること、そして同期トランザクションのコールバックがそもそも外部呼び出しを許さないこと。

**インメモリのキューを使う** — 永続化せずプロセス内で遅延実行する案。採らなかった理由は、リセットや退避で失われた仕事を回復する手段が無く、少なくとも1回の実行を保証できないこと。

## 影響

- 本体と検索がコミット成功時にだけ同時に変わる。結果整合の運用と、非同期インデックス維持のための読み直し・ファンアウトの設計が丸ごと不要になる。
- 外部副作用は少なくとも1回の実行になる。プロバイダ側の冪等キー、実行権の期限監視、繰り返し失敗するジョブの隔離運用が必要になる。
- D1 固有の遅延バッチ方式による Unit of Work と、それに付随する楽観ロック用のガードテーブルが不要になる。同一 Unit of Work 内で書いた結果を読み直せるようになる。
- **ドメインイベントの機構そのものが無くなる。** Unit of Work の契約からイベント収集が外れ、Outbox / 配送トリガ / 冪等性ストアのポートも消える。`CLAUDE.md` が中核概念として挙げる「Outbox / domain events」と、イベント定義に依存していた仕様の記述は改訂対象になる。廃止範囲の具体は `.thread/34/design.md` の第7.3節にある。
- **ローカルの同期コミットを採る帰結として、ドメイン層のリポジトリポートの `Promise` 契約が変わる。** ランタイムを差し替えても domain / application / presentation が無傷、という前提（`CLAUDE.md`「Reference runtime」）は成立しなくなる。具体は `.thread/34/design.md` の第8.2.1節にある。
- 契約と機構の詳細（新しい Unit of Work、ジョブの持ち方、Alarm の再設定規則、保持期限の処理、外部 I/O を残す境界）は `.thread/34/design.md` の第7章から第9章にある。
