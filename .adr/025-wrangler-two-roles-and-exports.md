# 025. デプロイ設定を要求 / 状態の2系統に分け、Durable Object クラス宣言の権威を状態側の `exports` に閉じる

## ステータス

承認済み

## コンテキスト

`.adr/002-cloudflare-workers-and-user-data-durable-objects.md` の構成では Worker が2本になる。HTTP を提供し CPU 仕事をする**要求側**と、Durable Object のクラスを所有する**状態側**である。

Durable Object クラスの lifecycle を宣言する方法は2つあり、**排他**である。宣言的な `exports` と、`[[migrations]]` の配列である。両方を含む設定は検証で拒否される。

1つの設定ファイルに複数の環境を並べる形（named environment）は使えない。実測で、ビルド成果物への redirect が全環境に効き、環境を指定した検証がその環境の入口を無視することが分かっている。

インフラのコードは Durable Object の namespace を作る役目を持つとも読めた。しかし namespace は Worker の script に紐づくもので、**Worker 自体がインフラのコードの管轄外**（デプロイ CLI が配る）である以上、namespace だけをインフラのコードに持たせる形は成立しない。持たせると宣言が2箇所になり、どちらが権威か決まらない。

## 決定

- **設定を役割ごとに分け、環境の並記を使わない。** 生成テンプレートは「環境 × 役割」の2次元になる。
- **Durable Object クラスは宣言的な `exports` で宣言し、migration の配列を書かない。** 生成される namespace が常に SQLite バックエンドになるので、バックエンドの取り違えが起きない。
- **クラス宣言の唯一の権威は状態側 Worker の設定である。** インフラのコードは namespace を provision しない。要求側の設定は、状態側で定義されたクラスを名前で参照するだけにする。
- **デプロイに使う設定の入口はビルド成果物を指す。** redirect が効かない経路（明示的に設定を指定した検証、テンプレートから生成した設定の直接利用）でも設定単体が成立する必要があるためである。ローカル開発用の設定だけはソースの入口を指し、その1本は**デプロイに使えない**ことをファイル冒頭と手順の両方に書く。
- **成果物の形を経路によらず一致させる。** フレームワークが生成する設定（再バンドルの抑止と module 解決規則）を、明示指定の経路でも同じ内容で持つ。持たないと、起動確認した形と出荷する形が違う状態になる。

## 検討した代替案

**migration の配列でクラスを宣言する** — `exports` と排他であり、`exports` のほうが namespace のバックエンドを取り違えない。**ただし `exports` を一度デプロイすると配列へ戻せない**ので、稼働中の namespace を持たないうちに決める必要があった。

**1つの設定ファイルに環境を並べる** — redirect が全環境に効くという実測済みの問題を踏む。

**インフラのコードで namespace を provision する** — 権威が二重になる。Worker が管轄外である以上、そもそも成立しない。

**ローカル設定の入口も成果物にする** — 開発サーバのプラグインが入口をソースとして解決するため、起動しない。

## 影響

- 設定ファイルの本数が増える。
- **`exports` でデプロイした後に migration の配列へは戻せない。**
- `exports` 経由で削除した namespace には復元手段が無いので、削除の保護をインフラのコード側で掛けられない。**撤去の前にデータを退避する運用手順**が要る。
- インフラのスタック出力に Durable Object の情報が無いので、設定テンプレートの差し込みには固定文字列を使う。
- **フレームワークが生成する設定を手で複製している箇所が残る。** 生成側が変わると乖離するので、出所をテンプレートのコメントに書き、ビルド設定を触るときはそこを見比べる。
