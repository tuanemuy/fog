# 010. 永続ジョブの投入点を全数で固定し、再投入の収束規則を定める

## ステータス

承認済み

## コンテキスト

`.adr/004-do-local-commit-and-alarm-jobs.md` により、要求処理の中で完結させられない処理は、オブジェクトごとに1本の Alarm で駆動する永続ジョブになった。この機構には Queue のような外部からの定期投入が無い。**次の起床を張るのは、ジョブ自身か、業務のトランザクションである。**

したがって、周期・反復するジョブの投入点を1つ書き落とすと、そのジョブは1回完走した時点で**恒久的に停止する**。ゴミ箱が二度と空にならない、期限切れの予約が二度と掃除されない、といった形で現れる。停止は例外もログも出さないので、動いていないことに気づく契機が無い。

同じ機構で、同じ仕事が何度も依頼される場合の扱いも決まっていなかった。素朴に毎回新しい行を作ると、連打のたびに起床が増える。

## 決定

- **ジョブ種別の全数表に投入点の欄を持たせ、欄が空でないことを不変条件とする。** 種別を足すときは投入点も同時に埋める。これにより「投入されるが二度と起きないジョブ」が表の空白として検出できる。
- **投入点は数え上げ可能な全数として書く。** 正本の表と、実際に投入する各ユースケースの両方に書き、片方だけが増減したら矛盾として読み取れるようにする。
- **投入口は Unit of Work コンテキストの `enqueueJob` に一本化する。** 「いつ起こすべきか」の材料を提供するドメインと、投入を実行するユースケースは別でよい。ゴミ箱ドメインは書き込みポートを持たない原則を維持したまま、起床時刻の材料だけを提供し、投入は memo / knowledge / identity のユースケースが行う。
- **起床時刻の投入は早める方向にのみ効く。** 既存の起床より遅い時刻では張り直さない。
- **同じ同一性のジョブの再投入は、既存の行へ収束させる。** 収束規則は3つで、状態による (2)(3) が (1) に優先する。
  1. 次回実行時刻は早める方向にのみ動かす
  2. 恒久失敗として隔離された行は実行待ちへ戻し、試行回数を 0 に戻す
  3. 完了済みを実行待ちへ戻すのは、再武装する種別に限る。**その種別は類型からの導出ではなく名指しで列挙する**（類型の分類軸と再武装の有無は直交しており、類型欄からは引けない）
- **ジョブの同一性キーは生成せず、ジョブの同一性から決定的に導く。** 単一 TEXT 主キーは生成 ID という規則に対する明示的な例外である。収束、外部プロバイダへ渡す冪等キーの導出、同じ依頼の連打の吸収は、すべて「同じ入力から同じキーが出る」ことに依存しており、生成 ID では成立しない。
- ペイロードの不一致による拒否は、実行待ち・実行中の行に限る。完了済み・隔離済みからの再投入は収束規則が定めるものであり、ペイロードの差で弾かない。

## 検討した代替案

**投入点を散文の中に書く** — どこにも書かれていないことが読み取れない。実際、正本と一部のユースケースにだけ書かれ、他の投入点が抜けたまま矛盾として現れなかった。

**再投入のたびに新しい行を作る** — 収束規則が要らなくなる代わりに、同じ時間帯の連打で起床回数が依頼回数に比例する。冪等キーの導出先も失われる。

**同一性キーを生成 ID にする** — ID 規則に例外を作らずに済むが、収束も冪等キーも成立しない。規則の一貫性より、機構が成り立つことを採る。

**再武装する種別を類型欄から導く** — 表が1列狭くなるが、実際には導けない。導出できると誤って書くと、導出しきれない種別が静かに落ちる。

## 影響

- **投入点が増減したら、全数宣言と各投入点を同時に直す義務が生まれる。** 機械的な検査は無く、レビューでしか守れない。
- ジョブ種別を見る軸が2つになる（何の類型か / 再武装するか）。種別を足すときに埋める欄が増える。
- 恒久失敗として隔離された行からの復旧手順が一意に決まる。別ペイロードでの再投入が規則の衝突なく通る。
- 主キーの規則に例外が並ぶ。規則としての強さは下がるが、例外が全数として宣言されているので、3件目が要るときは同じ場所を直すことになる。
