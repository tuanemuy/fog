# 005. 検索インデックスの書き込みをポートにせず、本体を書くトランザクションの中で更新する

## ステータス

承認済み

## コンテキスト

`.adr/003-sqlite-fts5-only-search.md` と `.adr/004-do-local-commit-and-alarm-jobs.md` で、検索は同一 SQLite の FTS5 のみとし、本体データと索引を同じトランザクションで同期的に確定させると決めた。残っていたのは、索引を書く経路をどう表すかである。

従来の設計は、検索ドメインに読み書き両用の `SearchIndexPort`（`query` / `upsert` / `remove`）を置き、ドメインイベントを受けて索引を更新する専用ユースケースを持っていた。前者はポートである以上 DI で単独注入でき、**トランザクションの外から索引だけを書く経路が構造的に残る。** 後者はイベント配送機構そのものの名前であり、その機構は `.adr/004-do-local-commit-and-alarm-jobs.md` で消えた。

規約で守らせるには失敗の仕方が悪い。external-content 構成の FTS5 の更新は「旧値で delete → 新値で insert」の2段を要求し、踏み外しても**例外が上がらず索引だけが黙って壊れる**。実行時に何のシグナルも出さない。

## 決定

- **`SearchIndexPort` を読み取りの `query` 1本に縮小し、書き込み側をポートにしない。** 索引の更新は、本体（メモ / ドキュメント）を書くリポジトリ実装が同じトランザクションの中で行う projection 処理である。
- **イベント駆動の索引維持ユースケースは名前ごと廃止する。** 索引が作り直される契機は「本体の書き込み」と「トークナイザ・正規化規則を変えたときの全件再構築」の2つだけで、後者は application 層のユースケースではなくスキーマ移行に属する。
- **projection には原文もトピック名も持たせない。** 索引に入れるのは正規化後の値だけで、スニペットの材料は本体テーブルから、トピックは正規化した事実の join から引く。出典リンクの相手側 ID だけは、絞り込みに使わない付随列として JSON で持つ。
- **索引の物理形の正本はデータベース設計である。** 主キーの取り方、`'delete'` コマンド構文を含む更新手順、索引の定義はそちらが持ち、検索ドメインが持つのは契約（更新の契機と「旧値 delete → 新値 insert」であること）だけとする。

## 検討した代替案

**`upsert` / `remove` をポートに残す** — 契約としては最も素直だが、「本体更新と索引更新が同一トランザクションに入っていること」を型で保証する手段が無くなる。静かに壊れる失敗モードに対して規約頼みの保証では足りない。

**読み取りポートと書き込みポートに分け、書き込み側は単独 DI を禁止する** — 名前を分けても禁止は規約のままで、到達経路そのものは残る。「載せてよいものを禁止の形で書く」のではなく「到達手段を無くす」という Unit of Work の設計態度と一致しない。

**トピック名を projection に複製する** — join を省けるが、リネームが検索結果へ反映されるまで再インデックスが要り、複製の整合を別途保つ必要が生じる。

**原文を projection に持つ** — スニペット生成が索引だけで閉じるが、本体と同じ Durable Object の中にあるので往復の節約にならず、索引の書き込み行数と容量（どちらも課金対象）が二重になる。

## 影響

- トランザクションの外から FTS5 を書く経路が構造的に存在しなくなる。
- 検索ドメインの責務が「問い合わせ」に一点集中し、代わりに **projection の実装が memo / knowledge のリポジトリ実装側へ散る。** 検索ドメイン側には行き先の明示（書き込み側はポートではなく本体を書くトランザクション内の処理である）を残す必要がある。
- トピックのリネームが検索結果へ即座に反映される。複製を持たないことの直接の帰結である。
- 索引の全件再構築はスキーマ移行の一部として運用する。application 層の設計からは見えなくなるので、検索ドメイン側に導線を残す。
- 索引の DDL 変更が1箇所で閉じる。ドメイン側は物理形を宣言しないので、片方だけ直して静かに食い違う状態が生じない。
