# 020. 条件付き書き込みは一致行数を読み戻し、0行の意味を分解しない

## ステータス

承認済み

## コンテキスト

`.adr/004-do-local-commit-and-alarm-jobs.md` の同期トランザクションでは、競合の直列化を条件付き `UPDATE` の一致で行う。楽観ロックも、複数のオブジェクトにまたがる手続きの前進（予約 → 確定 → 昇格）も、同じ形に乗る。

**「これらの書き込みはすべて条件付きである」と宣言しながら、一致行数を読み戻していない**状態が実際に生まれた。0行に当たっても呼び出し側は成功として先へ進む。帰結は沈黙する — 手続きは完走し、行は前の状態のまま残り、**利用者は理由が分からないまま以後その経路を通れなくなる。**

宣言と実装の食い違いが検出されなかった理由は、宣言の側にもあった。「これらは条件付きである」という列挙が全数の一部しか挙げておらず、**列挙のどちらの群にも属さないメソッドが1つ、素通しのまま残っていた。** 読み手は列挙を全数として読む。

もう1つ、束縛の材料も弱かった。ある操作が手続きの識別子だけを条件にしており、その識別子は未認証のログに出ることを設計自身が許容している。**識別子を知っているだけで書けるなら、ログに出た値が capability になる。**

区別の粒度も決まっていなかった。0行は「行が存在しない」と「版が古い」の両方を意味する。

## 決定

- **条件付き書き込みは一致行数を読み戻し、0行を競合として呼び出し側へ返す。** 例外は「対象が無いことが成功と同義」である操作（取り消し、削除、結果の記録）に限り、なぜ扱いが違うのかをモジュールの JSDoc に書き分ける。
- **分類の列挙は全数で書く。** 「読み戻す群」と「対象が無いのが成功である群」の両方を挙げ、どちらにも入らないメソッドが残らないようにする。
- **0行の理由を分解しない。** 「行が存在しない」と「版が古い」を区別しない。どちらも呼び出し側が持っている版がストレージと食い違っていることを意味し、解消手段（読み直して先頭からやり直す）も同じで、区別を返しても読む者がいない。区別するには追加の問い合わせが要り、1文で完結するという条件付き書き込みの設計上の利点を削る。**この同一視をテストで固定する** — 後から別の種類のエラーを足すと赤くなる形にする。
- **未認証の呼び出し元に返す0行の理由も割らない。** 「飛行中の変更がある」と「その対象が無い」を区別すると、その境界の中身を報告することになる。認証済みのエントリを持つ側が答えを細分化するかは、そちらの判断に残す。
- **束縛は capability として使える値で行う。** 手続きの識別子だけでなく、別途配られた秘密（定数時間で比較する）と、期待する結果の同一性を条件に含める。秘密は SQL の中で定数時間比較できないので、同一トランザクションの中で読んでから条件付き更新を行う形にする。
- **手続きの再入は明示的に扱う。** 同じ手続きが既に確定させた行は成功として返す。前進の際に条件列が消える設計だと、素朴な条件付き書き込みでは再入が競合になる。

## 検討した代替案

**条件付き書き込みに再試行のデコレータを掛ける** — `.adr/004-do-local-commit-and-alarm-jobs.md` と全体の再試行方針が、競合を呼び出し側まで届けると決めている。

**0行を「行が無い」と「版が古い」に分ける** — 追加の問い合わせが要り、呼び出し側の対処は変わらない。

**すべての書き込みを「対象が無いのは成功」に揃える** — 手続きの前進が沈黙して完走する。実際にその形で壊れた。

**列挙を代表例に留め、全数は正本のドキュメントに任せる** — 読み手は列挙を全数として読む。実際に1つ落ちた。

## 影響

- 「すべて条件付きである」という全数主張が実際に全数になる。分類を増やすときは列挙も同時に直す義務が生まれる。
- **「消えた行を更新した」ことを呼び出し側が知る手段は無いまま。** 必要になったら仕様変更として扱う。
- 束縛の引数が増える。呼び出し側が既に持っている値なので、追加の採番は生じない。
- 手続きを前進させる操作を後から足す側は、この分類のどちらに属するかを選ぶことになる。
