# 007. 到達可能性によるテナント分離を Durable Object の内部契約へ適用する

## ステータス

承認済み

## コンテキスト

`.adr/002-cloudflare-workers-and-user-data-durable-objects.md` で、テナント分離の保証を「列条件（`user_id` 述語）」から「到達可能性（他利用者の Durable Object のスタブを得る経路が存在しない）」へ移した。その帰結として、スキーマから `user_id` 列が消え、Durable Object 内のリポジトリ・ポートは `userId` を引数に取らなくなる。

決めきれていなかったのは、その内側で何を前提に書くかである。

- 列が消えたのに `Memo.userId` のようなエンティティのフィールドは残るのか。残るならその値は何を意味するのか。
- 読み取りのユースケースが行っていた「ユーザーが実在するか」の確認は残すのか。確認の材料（利用者テーブルの引き当て）はもう Durable Object の中に無い。
- 分離が効いていることを仕様やテストの期待値で述べるとき、何を根拠として書くのか。

これらを決めずにおくと、「消えた機構を根拠に名指しする記述」と「新しい根拠で書かれた記述」が同じドキュメントの中に併存し、境界が経路ごとに割れる。

## 決定

- **ポートの引数から `userId` を落とす。例外を置かない。**
- **エンティティの `userId` フィールドは残す。** ただしその値は**所属する Durable Object の同一性そのもの**であり、行ごとの絞り込みには用いない。この限定をフィールドの定義に添える。
- **Durable Object の中で利用者の実在確認を行わない。** 未初期化の Durable Object は**空の状態として振る舞う** — 一覧は空配列、件数は 0 を返す。読み取り系のエラーから「ユーザー不在」という発生源が消える。
- 仕様・期待値で分離の根拠を述べるときは、列条件ではなく**到達可能性**を根拠として書く。「自分の Durable Object の中に他利用者の行が原理的に存在しない」が標準の言い回しである。

## 検討した代替案

**エンティティからも `userId` を落とす** — 列の消滅に忠実だが、波及が大きい（生成の引数、各ドメインの契約、多数のテストケースが同時に動く）。加えて「この行がどの Durable Object に属していたか」を持たないと、エクスポートや移行のようにオブジェクトの外へ出るデータで所属を再構成できない。

**実在確認を残す** — 防御的には見えるが、到達可能性で済んでいる保証を中で二重に検査することになる。しかも空の Durable Object に対して失敗を返すと、初回アクセスの扱いが経路ごとに割れる（ある画面は空表示、別の画面はエラー）。

**分離の根拠は上位のドキュメント1箇所にだけ書き、個々の記述は触らない** — 消えた機構（第一引数の `userId`、`user_id` 述語）を根拠に名指しする記述が残り、実装者が存在しない引数付きクエリを探すことになる。

## 影響

- 存在しない利用者 ID で呼んでも成功応答が返る。認証済みセッション由来の `userId` しか入らないので実害は無いが、防御的なコードを書く実装者の直感には反する。
- Durable Object の内側は「自分のデータしか無い」ことを無条件に前提にできる。読み取りの契約からスコープ引数と不在エラーが同時に消え、エラーの一覧が実際に到達しうるものだけになる。
- エンティティのフィールドとスキーマの列が1対1で対応しなくなる。`userId` はその唯一の例外であり、その旨をフィールド定義に明記して食い違いを黙って残さない。
