# 016. ルーティング座標の導出は request 側 Worker に閉じ、Directory の Durable Object は `(種別, ハッシュ)` だけで引く

## ステータス

承認済み

## コンテキスト

`.adr/002-cloudflare-workers-and-user-data-durable-objects.md` は、利用者が確定していない経路の解決を別の Durable Object に置き、その識別子に正規化値の鍵付きハッシュを使うと決めた。鍵の配布は非重複で、HTTP を受ける request 側 Worker にだけ配り、Durable Object を所有する state 側 Worker には配らない。

ところがドメインのポートは「メールアドレスで引く」「SSO の主体で引く」という署名を持つ。**この署名を字面どおり Durable Object の中で実装することは原理的にできない** — 行のキーは鍵付きハッシュであり、その材料になる鍵が Durable Object 側に無い。ポートを読んだ実装者はここで止まるか、**state 側 Worker へ鍵を配る**という誤りに倒れる。後者は非重複配布そのものを壊す。

正規化の規則にも非対称があった。メール側には正規化を行う値オブジェクトがあるのに、SSO 側には対応するものが無く、canonical を組み立てるコードがどこにも存在しないまま「SSO 主体から解決できる」という要求だけが立っていた。

さらに、**外部入力が座標になる経路が1つだけ存在する。** パスワードリセットのリンクは未ログインで踏まれるので、宛先の Durable Object を名指しする材料をリンク自身が運ぶ以外にない。これは「公開入力から対象オブジェクトを選ばせない」という原則の唯一の例外であり、座標を無検査で通すと、未認証の呼び出し元が**任意個の新規 Durable Object を生成できる**（生成のたびにスキーマ適用と初期化が走る）。座標の妥当性を判定する材料（世代ごとの bucket 数）は鍵リングにしかなく、座標そのものは運ばない。

## 決定

- **責務を境界で切る。** 正規化と鍵付きハッシュの導出、そこからの座標の決定は request 側 Worker の責務。行の引き当ては Durable Object の責務で、受け取るのは `(種別, ハッシュ)` だけである。**state 側 Worker にルーティング鍵を配らない。**
- **ドメインのポート署名は変えない。** 契約が「メールで引ける／SSO 主体で引ける」であること自体は正しく、変えるべきは実装の置き場ではなく読み方である。実装側は1本のメソッドへ畳み、対応関係を実装ファイルの JSDoc に明記する。
- **SSO 側の正規化規則を関数として置く。** プロバイダ名だけを小文字化し、主体はプロバイダ由来の不透明値として素通しし、区切り子で連結する。メール側だけが正規化を持つ非対称を残さない。
- **区切り子はソースにエスケープ表記で書き、生の NUL バイトを埋めない。** 埋めるとバージョン管理も検索も対象ファイルをバイナリとして扱い、**そのファイルに対する機械検査が無言で 0 件を返す。** 実際にこれを踏み、漏えい検知モジュール自身の検査が黙って空振りしていた。
- **トークンが運ぶ座標は、パース時に鍵リングで範囲検査する。** 宣言に無い世代、宣言された bucket 数以上の index は「解析不能」として扱う。解析不能なトークンは未知のトークンと同じ応答へ均されているので、応答の一様性は変わらない。**検査に使う鍵リングは任意引数にせず必須にする** — 「後で足す」を呼び出し側に選ばせない。

## 検討した代替案

**state 側 Worker へルーティング鍵を配る** — ポート署名どおりに実装できるが、鍵の非重複配布という分離の前提を壊す。ポートの読みにくさを、設計の中核を崩して解決することになる。

**ポート署名を実装形に合わせて書き換える** — ドメインの契約が「どう保存されているか」に汚染される。契約としては「メールで引ける」が正しい。

**座標の範囲検査を Durable Object を選ぶ側（合成ルート）に置く** — 検査の有無が呼び出し点ごとに割れ、型では強制されない。

**リセットの消費経路も座標をトークンから取らない** — 未ログインで到達する経路なので、宛先を決める材料が他に無い。

## 影響

- ドメインのポート署名と実装署名が一致しない箇所が1つできる。JSDoc の1行で吸収する。
- 座標のパーサが純粋な文字列処理ではなくなり、鍵リングを要求する。呼び出し元は鍵リングを持つ側なので、追加の配布は生じない。
- Durable Object 側は自分の名前を平文から導けない。これは制約ではなく保証であり、bucket に相乗りした他の利用者の座標を bucket の中から計算する経路が存在しないことを意味する。
- **生の制御文字をソースへ埋めると機械検査が無言で壊れる**、という教訓は区切り子に限らない。同じ形の検査をリポジトリ全体に対して常設し、1ファイル限定のガードにしない。
