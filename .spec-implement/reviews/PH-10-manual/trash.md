## 不合格の詳細

### TC-21（軽微・文言 / 設計判断要）
- 再現: 同じユーザーで `/trash` を 2 タブ（A / B）で開く。両方にゴミ箱内のメモ（`ゴミ箱テスト用メモM1` / `並行操作テストメモ`）がある。A でそのメモを `完全に削除`。B（再読込しない）で同じメモの `復元`。
- 観測: `restoreMemoFn` の応答は HTTP 404 `{kind:"notFound", code:"MEMO_NOT_FOUND", message:"The memo is not in the trash"}`。B は行を消し、`router.invalidate()` で一覧を取り直し、`<p class="fog-notice" role="status">「ゴミ箱テスト用メモM1」は既に処理済みです</p>` を出す。role=alert のエラーも `再試行` ボタンも出ない。
- 期待との差: 手順書は「エラーが表示される（対象が見つからない旨）。リトライ・再読み込みの導線がある」を期待する。画面は壊れず、最新状態への回復は自動で起きる（手順 4 は満たす）。しかし文言が「既に処理済み」なので、復元しようとした利用者は **復元された** と読みうる。実際にはメモは完全に削除されていて戻らない。P-12 の状態定義（`spec/pages/index.md`「操作失敗: エラー＋リトライ」）とも形が違う。
- 原因の当たり: `apps/web/app/components/trash/TrashBoard/index.tsx` の `act()` の catch 節。`serialized.kind === "notFound"` を「他のタブや purge ジョブが既に処理した」とみなし、`dropRows` → `setNotice({ text: \`「${titleOf(item)}」は既に処理済みです\` })` → `settle()` に分岐している（コメント: `Somebody else already handled it (another tab, the purge job).`）。notFound には「完全に削除された」「別タブで復元された」の 2 通りがあり、この文言は後者（TC-22 では妥当）にしか合わない。直すなら、notFound のときに「ゴミ箱に見つかりません（完全に削除されたか、既に復元されています）」のように両方を含む文言にするか、手順書の期待を実装の設計（自動再同期 + 中立の通知）に合わせて改める。

## 保留ケースの SQL と前提
- 共通: dev を止めてから、対象ユーザーの User Data DO の sqlite（`apps/web/.wrangler/state/v3/do/*UserDataDurableObject*/<hash>.sqlite`）を開く。ファイルは下の各ユーザーに固有のメモ本文で特定する（例: `SELECT count(*) FROM memos WHERE body='期限切れテストメモ'` が 1 になるファイル）。時刻は epoch ms。以下の `N` は SQL を流す時点の現在時刻 `CAST(strftime('%s','now') AS INTEGER)*1000`。
- **`trashed_at` と `purge_after` は必ず `purge_after = trashed_at + 保持日数×86400000` を保つこと。** `purge-trash` ジョブのフェーズ 1（`packages/core/src/adapters/cloudflare/stores/memoRepository.ts` の `recalculatePurgeAfter`）は `purge_after <> trashed_at + retention` の行を「再計算の残り」とみなして `trashed_at + retention` に書き戻してから期限判定する。`purge_after` だけを動かすと、ジョブが走った瞬間に元の期限へ戻り、期限切れにならない。
- 再起動後に `purge-trash` を走らせる手段: ソフトデリートと保持期限の変更は、コミット後に `armPurgeTrash`（`packages/core/src/application/trash/armPurgeTrash.ts`）で「最も早い `purge_after`」へ `jobs` の `purge-trash` 行を前倒しし、`rearm()` で Alarm を張り直す。最も早い期限が過去なら Alarm は即時に発火する。読み取り（ゴミ箱を開く等）では Alarm は張り直されない。

### TC-13（`ph10-trash-expire@example.com`、保持期限は 1 日に設定済み）
- SQL:
  - `UPDATE memos SET trashed_at = N - 90000000, purge_after = N - 3600000 WHERE body = '期限切れテストメモ' AND status = 'trashed';`（25 時間前に削除、期限は 1 時間前。差はちょうど 1 日）
  - `期限内テストメモ` は触らない（`purge_after` ≈ 2026-09-12 12:21 JST。**これより前に確認すること**。過ぎると正当に期限切れになり「期限内は残る」の対照にならない）
- 再起動後:
  1. `/trash`: `期限切れテストメモ | まもなく削除 | （SQL 時刻の 25 時間前）に削除`、`期限内テストメモ | 残り1日`
  2. 手順 5（ジョブを走らせる）: タイムラインで `発火用メモ（TC-13 の purge-trash 起動用）` を削除する。`purge-trash` が 1 時間前の期限へ前倒しされ Alarm が即時発火する（念のため SQL で `UPDATE jobs SET next_run_at = N WHERE operation_key = 'purge-trash';` を足しても良い）
  3. 手順 6: 数秒後に `/trash` を再読込 → `期限切れテストメモ` が消え、`期限内テストメモ` と `発火用メモ…` が残る。P-11 で `期限切れテストメモ` が見つからない。`operator.ts list-poisoned-jobs --locator <userId>` が空（`userId` は `list-bucket-user-ids` を dir:g1:b0..b15 に回して探す）
  4. 手順 7: P-13 で保持期限を `30` に戻す → `保存しました`、ゴミ箱の 2 件が `残り30日`

### TC-23（`ph10-trash-edge@example.com`、保持期限 30 日）
- SQL: `UPDATE memos SET purge_after = N + 3600000, trashed_at = N + 3600000 - 2592000000 WHERE body = '期限直前テストメモ' AND status = 'trashed';`（期限は 1 時間後、削除日時は期限の 30 日前）
- 再起動後（SQL から 1 時間以内に）:
  1. `/trash`: `期限直前テストメモ | 残り1日`（`remainingLabel` は `ceil(残り / 1日)` なので 1 時間でも「残り1日」と出る。0 以下なら「まもなく削除」）、削除日時は SQL 時刻の約 30 日前（2026/08/12 付近）
  2. `復元` → `メモを復元しました`。タイムラインで `期限直前 後のメモ` > `期限直前テストメモ`（12:22）> `期限直前 前のメモ` の並び
- 確認ポイントの「`trashed_at` を動かしても残り日数は変わらない」: 表示は保存済みの `purge_after` をそのまま使う（`TrashBoard` の `remainingLabel(item.expiresAt, now)`）。ただし不変条件を崩すと上記の再計算がジョブ実行時に元へ戻すので、別途試すなら表示だけを見てジョブを走らせないこと

### TC-24（`ph10-trash-extend@example.com`、保持期限 30 日）
- SQL:
  - `UPDATE memos SET trashed_at = N - 3456000000, purge_after = N - 3456000000 + 2592000000 WHERE body = '延長テストメモ' AND status = 'trashed';`（40 日前に削除、期限は 10 日前）
  - `UPDATE jobs SET next_run_at = N WHERE operation_key = 'purge-trash' AND status = 'pending';`（手順 4 用。次に Alarm を張り直すのは手順 2 の保持期限変更なので、再計算の直後にジョブが走る）
- 再起動後、**保持期限を変える前にこのユーザーでソフトデリートをしないこと**（Alarm が張り直されて期限切れの `延長テストメモ` が先に消える）:
  1. `/trash`: `延長テストメモ | まもなく削除 | 2026/08/02 付近 に削除`（ゴミ箱を開くだけでは Alarm は張り直されない）
  2. 手順 2: P-13 で保持期限 `60` → `保存しました`
  3. 手順 3: `/trash` → `延長テストメモ | 残り20日`
  4. 手順 4: 手順 2 のコミット後の再武装で `purge-trash` が即時に走る。数秒後に再読込しても `延長テストメモ` が残る。止めてから `SELECT status, next_run_at, attempt FROM jobs WHERE operation_key = 'purge-trash';` を見て、`next_run_at` が SQL で入れた `N` より後（新しい最早期限 ≈ +20 日）に進んでいるか `done` であり、`poison` でないことを確認する
  5. 手順 5: 保持期限を `30` に戻す → `保存しました`。この時点で `延長テストメモ` の期限は `trashed_at + 30日` = 10 日前へ戻り、次の Alarm で消える（手順書の範囲外）
