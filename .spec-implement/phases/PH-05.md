### 1.3 restoreDocument の procedure（spec 手順の写し。分岐の要点だけ）

1. `findTrashItem({ kind: "document", id })` → null で `NotFoundError`
2. `topicRepository.findByIdIncludingTrashed(item.topicId)` → `TopicStatusForRestore`（Live → `active`、trashed → `trashed`、null → `hardDeleted`）→ `plan`
3. `restoreAlone`: `findById(topicId)`（Live のみ）が null なら**現況から再判定**（trashed → 確認要求 / 不在 → 選択要求を返す。書き込みなし）→ `topicRepository.save(topic, expectedVersion)` で touch（内容不変、version +1 = `createDocument` と同じ）→ `documentRepository.findByIdIncludingTrashed` → trashed でなければ `NotFoundError` → `Document.restore` → `save` → `{ result: "restored", restoredTopicId: null }`
4. `restoreWithTopic`: `confirmSetRestore !== true` なら `{ result: "setRestoreConfirmationRequired", topicId, topicName }`。true なら `findByIdIncludingTrashed(topicId)` を再取得し trashed でなければ再判定（Live → 手順 3 相当、null → 選択要求）→ `listTrashedByTopic` → `restoreTopicSet` → `topicRepository.save` + `restoredDocuments` の `save` → 対象が `skippedDocuments` に居れば追加で `Document.restore` → `save` → `{ result: "restored", restoredTopicId: topicId }`
5. `selectDestination`: `destination` 無しなら `{ result: "destinationSelectionRequired" }`。`existing` は `findById` → null で `NotFoundError("TOPIC_NOT_FOUND")` → touch。`new` は `Topic.create({ id: newTopicId, userId, name, description }, now)` → `insert`（touch 不要）→ `findByIdIncludingTrashed(documentId)` → `Document.moveToTopic` → `Document.restore` → `save` → `{ result: "restored", restoredTopicId }`

facade は `newTopicId = idGenerator.next()` を常に採番して渡す（`new` 以外では捨てる。採番は副作用なし）。

### 1.4 pruneExpiredTrashItems と `purge-trash` handler（`adapters/cloudflare/jobs/purgeTrash.ts`）

`createPurgeTrashHandler({ run, logger })`（`run` = DO の `runUnitOfWork`）。handler:

```
budget = tuning.jobsMaxChunkIterations
// 再計算フェーズ
days = run(ctx => ctx.userSettingsRepository.find()?.entity.trashRetentionDays)  // 未初期化なら null → 再計算スキップ
while budget > 0:
  r = run(ctx => memo.recalc(days, rows) + topic.recalc + document.recalc)   // 1 tx = 1 チャンク（3 表を 1 回ずつ）
  budget -= 1
  if !(r.memo.hasMore || r.topic.hasMore || r.document.hasMore): break
if 残件あり: return { kind: "yield", nextRunAt: now }        // 削除フェーズへ進まない（延長方向の誤削除防止）
// 削除フェーズ
while budget > 0:
  items = run(ctx => ctx.trashQueryPort.listItemsToPurge(new Date(now), rows))
  if items.length === 0: break
  for item of items: try run(ctx => executeHardDeletePlan(ctx, expandTargets(item))) catch → logger.warn, failedCount++
  budget -= 1
  if items.length < rows: break
next = run(ctx => ctx.trashQueryPort.findEarliestPurgeAfter())
if budget === 0 && (再計算残件 or 直前のチャンクが満杯): return { kind: "yield", nextRunAt: now }
if next === null: return { kind: "finished" }               // ゴミ箱が空。次の投入点まで待機
return { kind: "rearm", nextRunAt: max(next, now + 1) }     // 期限切れが残る（OCC 失敗の先送り）なら再武装は少なくとも次の pass
```

- `processedCount` / `failedCount` / `hasMore` は `pruneExpiredTrashItemsProcedure` 側の戻り値（`application/trash/pruneExpiredTrashItems.ts` に **1 チャンク分**を同期関数として置き、handler が `run` で包んで反復する。`chunkLimit` / `maxChunks` の検証（1 以上の整数）はここ）
- 1 起床あたりの件数上限は tuning の 2 階層（`jobsMaxChunkIterations` × `jobsMaxRowsPerChunk`）。経過時間で測らない
- `yield` は `releaseForNextWakeUp`（`attempt` 不変、`pending` へ戻す）、`rearm` は `releaseWithBackoff(attempt 0, nextRunAt)`、`finished` は `done`。`JOB_KIND_POLICY["purge-trash"].revivesFromDone` があるので、`done` からは投入点 5 つの `enqueueJob` で復帰する（既存 `armPurgeTrash`）
- 失敗した項目（OCC / 行不在以外の例外）は `logger.warn` で先送り。行不在は no-op（`processedCount` に数えない）
- 同一 tx で消すもの: 本体行 / リビジョン / 出典リンク / `search_entries` + `search_fts`（delete コマンド）/ 相手側の再射影（§1.5）
- 10 GB 逼迫: △-8
- **Verifier の DO に残る `purge-trash` 行**（`pending`、`next_run_at` 2026-09-09 11:27 JST）: handler が無い現在、起床すると `JobHandlerMissing` → backoff（`jobsMaxAttempts` まで）→ `poison`。**PH-05 の handler が入れば**: まだ `pending` なら次の起床で普通に走る。既に `poison` なら収束規則 (2) により **どの投入点（ソフトデリート 1 件、または保持日数の変更）でも `pending` に戻る**（`terminal_reason` は残る）。operator の `requeue-poisoned-job` は PH-09 なので、検証手順では「メモを 1 件削除する」を再起動手段として使う

### 1.5 ハードデリートの共通手順（`application/trash/hardDeleteSteps.ts`、同期・UoW 内）

`executeHardDeletePlan(ctx, plan): { deleted: number }`:

1. `plan.documentIds` の各件: `documentRepository.findByIdIncludingTrashed(id)` → null は no-op → `documentRepository.delete(id, expectedVersion)`（cascade: リビジョン / documentId 側リンク / entry 除去 / 出典メモ再射影）
2. `plan.memoIds` の各件: `memoRepository.findByIdIncludingTrashed(id)` → null は no-op → `memoRepository.hardDelete(id, expectedVersion)`（本体 + リビジョン + entry 除去）→ `documentRepository.deleteSourceLinksByMemo(id)`（memo_id 側リンク削除 + 影響ドキュメント再射影）
3. `plan.topicIds` の各件（配下の後）: `topicRepository.findByIdIncludingTrashed(id)` → null は no-op → trashed でなければ no-op（active トピックを消さない）→ `topicRepository.delete`
4. 戻り値は実際に消した本体行の数（`emptyTrash` の `deletedCount` は項目単位で数え直す）

OCC 失敗（`ConflictError`）は投げる（呼び出し側が項目単位で先送りする）。

### 1.6 emptyTrash の facade

```
total = run(ctx => ctx.trashQueryPort.countTrashItems())
loop: items = run(ctx => listTrashItems({ page: 1, limit: 100 }))   // 消した分は一覧から消えるので常に page 1
      if items.length === 0 break
      sets = expandTargets を種別ごとに和集合
      for each (kind,id) in sets: try run(ctx => executeHardDeletePlan(ctx, 単体 plan)) → deleted++ catch → logger.warn, failed++
      if 今回 1 件も消せなかった（全件失敗）: break    // 無限ループ防止
return { deletedCount: deleted, failedCount: failed }
```

`deletedCount` は spec どおり「ゴミ箱項目数」（トピック 1 + 配下 2 = 3）。

| ドキュメントの復元 | `documentRepository.save` は doc の再射影 + 出典メモの再射影（PH-03） | 変更なし（`moveToTopic` 後の `save` も同じ経路で `topic_id` が新しい値で射影される） |
| ドキュメントのハードデリート | `delete` が cascade 済み | 変更なし |
| トピックのセット復元 | 配下 `documentRepository.save` ×n | 変更なし |

integration で 5 契機とも `search` 経由で固定する（§5）。

### 3.2 P-12 `TrashBoard`（client island = **一覧の所有者**。復元 / 完全削除は行を一覧から外す list-membership の変更なので owner が実行する）

- 状態: `items`（`useState`、`initial` で seed、`router.invalidate()` 後に re-base）、`totalCount`、`page`、`useOptimistic` で「操作中」の行に `pending`（`aria-busy`、ボタン非活性）、行ごとの `error`
- ヘッダ: 「ここにある項目は N 日後に完全に削除されます」は出さない（保持日数を feed に載せない。代わりに各行の残り日数）。「空にする（{totalCount}）」は `totalCount === 0` で `disabled`（P-12「空: 非活性」）
- 一覧（△-2 のグルーピング）: 行 = 種別バッジ（メモ / ドキュメント / トピック）+ 表示名（memo: `excerpt`、document: `title`、topic: `name` + 「ドキュメント n 件」）+ `残り N 日`（△-3）+ 復元 / 完全に削除。配下行（`deletedWithTopic` で親が一覧にある）は親の下にインデントし「トピックとセットで削除」
- 空: 「ゴミ箱は空です」（`role=status`）
- もっと読む: `totalCount > items.length` のとき `listTrashFn({ page: page + 1, limit: 100 })`（GET）で追記
- 操作（すべて owner の server fn 呼び出し。楽観: 行を pending にし、成功で行を外す。失敗で戻して行内に alert + 再試行）:
  - 復元（memo）: `restoreMemoFn` → 成功で行を外し「メモを復元しました。タイムラインで見る」（`/?memo=`）の通知
  - 復元（topic）: `restoreTopicFn` → 親と配下行を外す
  - 復元（document）: `restoreDocumentFn({ documentId })` → `restored` なら行を外す（`restoredTopicId` があれば配下行も外す）。`setRestoreConfirmationRequired` なら `ConfirmDialog`（「トピック「{topicName}」とセットで復元しますか？」/ 説明「このトピックと、一緒に削除されたドキュメントがすべて復元されます」/ 確認「セットで復元」）→ 確認で `{ confirmSetRestore: true }` で再呼び出し。`destinationSelectionRequired` なら **復元先ダイアログ**（§3.3）
  - 完全に削除: `ConfirmDialog`（danger。「完全に削除しますか？」/ 「履歴ごと消え、元に戻せません」。topic は「セットで削除されたドキュメント n 件も対象です」を付ける）→ `hardDeleteTrashItemFn({ kind, id })`
  - 空にする: `ConfirmDialog`（danger。「ゴミ箱の {totalCount} 件をすべて完全に削除しますか？」）→ `emptyTrashFn()` → `{ deletedCount, failedCount }`。`failedCount > 0` なら alert「n 件は削除できませんでした。もう一度お試しください」+ 再試行
  - 二重送信: 行ごとの `pending` と `ConfirmDialog` の `pending`
- 並行して消えた項目（TC-21）: `NotFoundError` は「既に処理済みです」として行を外し `router.invalidate()`

### 3.3 復元先トピック選択ダイアログ（`components/trash/RestoreDestinationDialog`、ADR-001）

## 4. spec の記述で判断が要る点（△ の詳細）

- △-1（決定）: design の `trash.html` のナビに「ゴミ箱」が無いが、P-12 への導線が他に無い（P-13 にもリンクは無い）。plan.md の完了条件が「ナビに「ゴミ箱」」なので足す。design 側の更新は Manager
- △-2: spec の `listTrash` は page/limit だが、P-12 のグルーピングはセット単位。先頭 100 件で通常は 1 ページに収まる。ページ境界でセットが割れる場合の表示は「親が無い配下行は単独行 + メタ」で機能は保たれる
- △-3: 残り日数は表示上の丸め。`ceil` にすると「残り 1 日」は「24 時間以内」を意味し、TC-13 手順 3 の「残り 1 日以内」に合う
- △-4: `TrashRetentionDays` は 1 以上の整数のみ。上限を UI に置くと spec に無い規則が増えるので transport の DoS 上限だけにする
- △-5: 復元先候補を feed に同梱すると P-12 を開くたびにトピック全件を運ぶ。ADR-001 の分岐は稀なので遅延取得
- △-6: `TrashedMemoItem.excerpt` の切り詰めは実装詳細。既存関数を再利用
- △-7: spec は「項目ごとの UnitOfWork」を明記。1 facade で `run` を逐次に複数回呼ぶのは `run` の入れ子禁止に抵触しない
- △-8: 上記。同一 tx を崩さない。limit を報告に残す
- △-9: PH-03 の `documentRepository.delete` が spec の手順 1〜4 を内包している。spec の「影響先を消去前に確定」は満たしており、ユースケースから重ねて呼ぶと同じドキュメント / メモを 2 回射影するだけ
