## 要約

- **サブフェーズに分ける（△-0）**: **PH-09A = recovery + jobRunner + operator（poison / quarantined / 診断 / HTTP 面）**、**PH-09B = rotation（keyring `previous` / コミットメント / 4 RPC / `rotate-encryption` / 世代ガード / lookup 順序）+ `reindex` / `migrate-bulk`**。A は B の前提（`requeue-poisoned-job` と HTTP 面が無いと B の起動 RPC を叩けない、B の世代ガードは A の終端モードを使う）。各サブフェーズが独立に完了候補になり、Verifier の検証単位も分かれる
- **jobRunner（A）**: 失敗の分類を runner に持たせる — `ConflictError` は**その場で前進不能確定**（`attempt` 上限を待たない。spec 前提 2）、その他は backoff → 上限で確定。確定時に `terminalStage(row, sql)` が段を返せば終端モードへ突入（既存の書き込み。`terminal_reason = "<forward-token> <operationId>"`）、返さなければ `poison`（`forward-*`）。終端モードの行は段が実在すれば段だけを実行し、段の `{ kind: "poison", reason: "material-lost" }` は `attempt` によらず `cleanup-material-lost:<forward-token>` で `poison`、段の失敗は backoff、段の上限超過は `cleanup-exhausted:<forward-token>`、段の `finished` は `done`（`terminal_reason` 残す）。段が無い終端モード行は前進し、完走 `done` / 再確定 `poison`（新しい `forward-*` に差し替え）。**`terminal_reason` の値域は 6 トークン + `operationId`（空白区切り）だけ**（error code はログへ）
- **後始末（A）**: `resume-signup` S1〜S4（S2 `abandon-account` → S3 `cancel-reservation` × 非コーディネーター → S4 自 bucket 予約行削除 + `done` を 1 tx）、`resume-link` L1〜L3、`resume-credential-change` C1（`'pending'` のみ）。新 RPC は **`abandon-account`（User Data）1 本**（`cancel-reservation` は実装済み。リセットトークン同時削除を確認）
- **`finalize-withdrawal`（A）**: 投入点 2 つ = 退会の起点（**本フェーズでは `abandon-account` (6) だけ**。利用者向け退会ユースケースは spec/usecases に無い → △-3）。handler は `credential_locators` の全 locator へ `deleteMapping`（全世代）、未完了 `operations(link/unlink)` の `target_locators` へ `cancel-reservation` → `phase='done'`、`ai_client_connections` を revoke、`credential_locators` 全削除、`account.caller_token = NULL` / `status='deleted'` / `deleted_at` を最終 tx で。多世代の no-op 確定（rotation）は B で足す。後始末なし → 前進不能は即 `poison`
- **operator（A）**: DO facade に `listPoisonedJobs(cursor)` / `requeuePoisonedJob(operationKey)` / `deletePoisonedJob` / `deleteQuarantinedEvent` / `readDeliveryBacklog`（両クラス）、`purgeUserMappings(userId)`（Directory）を追加。**HTTP 面 `POST /__operator/<entry>`** は `apps/web/app/worker/cloudflare/operatorHandlers.ts`（bare handler、`server.cloudflare.ts` で `/__diagnostics/` の隣に先取り）。保護は **`OPERATOR_TOKEN`（request Worker の secret、定数時間比較、未設定なら 404）**。本番は Cloudflare Access を前段に置く運用（docs §8.2 (b)）。監査ログは allow-list 4 項目（`entry` / `locator` / `outcome` / `eventId|operationKey`）
- **rotation（B）**: keyring を JSON 変数で 2 世代化（`DIRECTORY_ROUTING_KEYRING` request / `DIRECTORY_KEY_COMMITMENT` state / `IDENTITY_MAIL_ENCRYPTION_KEYRING` state。従来の単一変数は「単一世代の短縮形」として残す。△-6）。`rotationCheckpointStore`（replace / delete）を Directory UoW ctx に、予約 3 箇所に世代ガード + 無効化、`remap-chunk` / `import-remapped-mappings` / `read-rotation-checkpoint`（Directory）と `record-remapped-locator`（User Data）、`rotate-encryption` handler（チャンク UPDATE 条件付き）+ 起動 RPC `start-rotate-encryption`、`resolveLoginCredential` 経路の lookup を active → previous → active 再プローブに
- **`reindex` / `migrate-bulk`（B）**: v1 → v2 の DDL 変更は**無い**ので本番 plan は v1 のまま。handler 2 本を User Data の registry に登録し（`reindex` = `search_entries` を `memos` / `documents` から 1 行ずつ delete → insert、カーソル = `migration_progress(target_version, step)`; `migrate-bulk` = `plan.steps[].bulk` の関数表を歩く汎用 runner。v1 には step が無いので `finished`）、**integration ではテスト専用の plan v2（seed 付き）でゲート投入 → Alarm → 完走 → `migration_progress` の cursor** と、**fail-closed（`_meta.schema_version = 2` を書いた DO が `SchemaVersionAhead` を返し `failClosedRearmIntervalMs` で Alarm を残し、plan を v2 にした「デプロイ後」に回復）** を踏む
- **DLQ（A）**: `handleDlqBatch` を「1 回だけ再配送を試みてから ack」に変える（△-8）。再配送 = consumer と同じ経路（`getResetMailMaterials(eventId, ownerToken)` → send）。`owner_token` が再採番されていれば `nothing-to-send` で ack。手動の再駆動口は作らない（メッセージは DLQ 保持期間後に消えるので「再駆動の形」は消える前の自動 1 回）

### 1.1 語彙（`adapters/cloudflare/terminalReason.ts`、新設）

export const FORWARD_TOKENS = ["forward-conflict", "forward-exhausted"] as const;
export type ForwardToken = (typeof FORWARD_TOKENS)[number];
export const TERMINAL_REASON_TOKENS = [
  ...FORWARD_TOKENS,
  "cleanup-exhausted:forward-conflict", "cleanup-exhausted:forward-exhausted",

### 1.2 `JobHandlerResult` と `TerminalStageSelector`

```ts
export type JobHandlerResult =
  | { kind: "finished" } | { kind: "rearm"; nextRunAt: Date } | { kind: "yield"; nextRunAt: Date; commit? }
  | { kind: "poison"; reason: "material-lost" };          // 後始末の段だけが返す

```

- 前進 handler が `poison` を返した場合は契約違反として `SystemError(UnclassifiedError)` 扱い（backoff）— 前進の確定は runner だけが判定する

### 1.3 `runJobsPass` / `applyJobFailure` / `applyJobResult` の分岐（7 契機 + 前進側）

| 状況 | 判定 | 書く |
|---|---|---|
| 前進（`terminal_reason IS NULL`）が `ConflictError` | 確定 | 段あり → 突入（既存の UPDATE、`terminal_reason = forward-conflict <op>`）/ 段なし → `poison`（`forward-conflict <op>`） |
| 前進が他の失敗、`attempt + 1 < max` | 継続 | backoff（既存） |
| 前進が他の失敗、上限 | 確定 | 同上で `forward-exhausted` |
| 終端モード・段あり・段が `finished` | 後始末完走 | `done`、`terminal_reason` 不変（`finalizeRow(..., "completed", null)` は `COALESCE` で残す — 既存） |
| 終端モード・段あり・段が `{ kind: "poison" }` | 材料喪失 | `poison`、`cleanup-material-lost:<forwardTokenOf(current)> <op>`。`attempt` を見ない |
| 終端モード・段あり・段が失敗、上限未満 | 継続 | backoff、`terminal_reason` 不変 |
| 終端モード・段あり・段が失敗、上限（`ConflictError` 含む — 段は cross-DO RPC で `ConflictError` を返しうるが、後始末に「確定」の概念は無いので backoff を使い切る） | 焼き切れ | `poison`、`cleanup-exhausted:<forward> <op>` |

- `runJobsPass` の段の選択に `sql` を渡す（△-5）。`applyJobFailure` も同じ selector を呼ぶ

## 8. △ の詳細

- △-0: A だけで R-REC-01 と R-OPS-01 の大半（`reindex` / `migrate-bulk` を除く）が閉じる。B は鍵材料の運用（`.dev.vars` の 2 世代化）を伴い、検証の段取りが別物

- △-2: spec 前提 2「前進不能の発火条件 = `ConflictError` で確定 / バックオフ上限到達」。現行 runner は両方 backoff で上限まで回す（PH-06 実装）。即確定に変えると `resume-credential-change` の OCC `ConflictError` も即確定 → `'pending'` なら C1 へ入る（spec の意図どおり: 巻き戻して利用者の再操作へ）

- △-5: `change_state` は行の状態で、payload には無い。突入判定は `applyJobFailure` の tx 内、実行時判定は claim 後。どちらも `sql` を持つ
- △-6: JSON 変数は `wrangler secret put` で 1 値として置ける。単一変数 fallback で dev / CI / 既存テストを壊さない。コミットメントは state Worker だけ、keyring は request Worker だけ（非重複配布）。**dev の `.dev.vars` は両 Worker に全変数が渡る**（PH-06 の観測）— dev では非重複が成立しないが、これは既存の限界

- △-9: docs §8.2 は Cloudflare Access 採用、`OPERATOR_TOKEN` は単独では不採用。本フェーズの HTTP 面はローカル検証と Access 前段の背後で使う想定なので token を実装し、Access は運用（`infra/` の外）。未設定 404 は「経路が存在しない」を既定にする（`DIAGNOSTICS_ENABLED` の流儀を再利用しない）
