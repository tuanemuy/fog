## 要約

- **認可（S-AC-05）**: AI クライアントは `POST /oauth/register`（stateless DCR。`client_id` = 署名済みメタデータ）→ `GET /oauth/authorize`（PKCE S256 必須。検証済み要求を署名付き `request` blob にして P-14 `/ai-clients/authorize?request=…` へ 302。未ログインは `_app` のガードで `/login?redirect=` を経て戻る）→ P-14 で「許可する」（server fn → `approveAiClientAuthorization` → `AiClientConnection` を作成 → 認可コード（署名済み自己完結値、`jti`、TTL 10 分）を `redirect_uri?code&state` で返す）/「拒否する」（`redirect_uri?error=access_denied&state`）→ `POST /oauth/token`（`authorization_code` + `code_verifier`。User Data DO の `consumeAuthorizationCode` が `oauth_consumed_codes` に `jti` を INSERT（重複 = 使用済み）し同 tx で期限切れを掃除）→ access（TTL 1 時間）+ refresh（TTL 30 日）

- **一覧・失効（S-AC-06）**: `AiClientConnectionRepository`（`insert` / `save` / `findById` / `listByUserId` / `findActiveById` / `recordUsage`）を User Data の UoW ctx に置き、PH-06 の `aiClientConnectionRevoker` を置き換える。P-13 に active な接続の一覧（名前・接続日時・最終利用）と「接続を解除」（確認あり、楽観除去）、P-03 は一覧 + 「すべて失効」（`revokedCount` / `failedCount`、部分失敗でも続行）。失効後のトークンは次のリクエストで 401

## 1. OAuth 2.1

### 1.1 鍵とトークンの形

- `AI_CLIENT_TOKEN_SECRET`（request Worker、≥32 文字。`.dev.vars.example` の帰属表に追記、`wrangler secret put ... --config wrangler.<stage>.toml`）。`readRequestServerConfig` が `requireAiClientTokenSecret` で検証し `secrets.aiClientTokenSecret`（branded）に置く。**`queue()` は読まない**
- 派生鍵（△-1）: `deriveKey(secret, label)` = HMAC-SHA256(secret, label) を HMAC 鍵として import（`adapters/webcrypto/derivedHmac.ts` に共通化。`ssoStateCodec` も同じ関数へ寄せる）
- 署名値の形は既存 codec と同じ `<base64url(JSON)>.<base64url(HMAC-SHA256)>`。`adapters/webcrypto/aiTokenCodec.ts` に `createAiTokenCodec({ secret, clock })`:

| 種別 | payload | ラベル | TTL |
|---|---|---|---|
| access | `{ typ: "access", uid, cid, scope: "ai", exp }` | `fog:ai-access` | 3,600 s |
| refresh | `{ typ: "refresh", uid, cid, exp }` | `fog:ai-refresh` | 30 日 |
| code | `{ typ: "code", jti, uid, cid, client, redirect, challenge, exp }`（`method` は S256 固定なので持たない） | `fog:ai-code` | 600 s |
| client_id | `fog_<base64url(JSON)>.<sig>`、JSON = `{ name, redirect_uris, iat }` | `fog:ai-client` | なし |
| authz（P-14 往復用） | `{ typ: "authz", client, name, redirect, state, challenge, scope: "ai", exp }` | `fog:ai-authz` | 600 s |

- `verify` は `typ` 一致 + 署名 + `exp` を検査し、どれが外れても `null`（理由を返さない）。`uid` / `cid` は不透明文字列
- `jti` は `TokenGenerator.next()`（128 bit 以上。D-08）

### 1.2 エンドポイント（`apps/web/app/presentation/ai/oauth/*.ts`、`server.cloudflare.ts` の fetch で TanStack より前に配線）

| パス | メソッド | 処理 |
|---|---|---|
| `/.well-known/oauth-authorization-server` | GET | RFC 8414: `issuer: APP_URL`、`authorization_endpoint` / `token_endpoint` / `registration_endpoint`、`response_types_supported: ["code"]`、`grant_types_supported: ["authorization_code","refresh_token"]`、`code_challenge_methods_supported: ["S256"]`、`token_endpoint_auth_methods_supported: ["none"]`、`scopes_supported: ["ai"]`。`Cache-Control: public, max-age=3600` |
| `/.well-known/oauth-protected-resource` | GET | RFC 9728: `resource: APP_URL`、`authorization_servers: [APP_URL]`、`bearer_methods_supported: ["header"]`、`scopes_supported: ["ai"]` |
| `/oauth/register` | POST | stateless DCR（RFC 7591 の部分集合）。body `{ client_name, redirect_uris, token_endpoint_auth_method?: "none", grant_types?, response_types? }`。`client_name` は `ClientName` の規則（trim 後 1〜100）、`redirect_uris` は 1〜10 件で △-11 の形。応答 201 `{ client_id, client_name, redirect_uris, token_endpoint_auth_method: "none", grant_types: [...], response_types: ["code"], client_id_issued_at }`。`client_secret` は出さない。不正は 400 `{ error: "invalid_client_metadata" \| "invalid_redirect_uri", error_description }` |
| `/oauth/authorize` | GET | `client_id`（検証 → name / redirect_uris）、`redirect_uri`（登録と完全一致）、`response_type=code`、`code_challenge`（43〜128 文字 base64url）、`code_challenge_method=S256`、`state`（任意、≤512）、`scope`（省略 or `ai`）。`client_id` 検証不能 / `redirect_uri` 不一致 → 302 `/ai-clients/authorize?error=invalid_request`（△-3）。その他の不正 → 302 `redirect_uri?error=invalid_request&error_description&state`。正常 → authz blob を作り 302 `/ai-clients/authorize?request=<blob>`。**ここでは認証を見ない**（P-14 が `_app` 配下なので未ログインは `/login?redirect=/ai-clients/authorize?request=…` を経て戻る。`toSafeRedirect` の 2048 文字以内に収まる: blob は ≈ 600 文字） |
| `/oauth/token` | POST（`application/x-www-form-urlencoded`。JSON body も受ける） | `grant_type=authorization_code`: `code` / `code_verifier` / `client_id` / `redirect_uri` を検証（署名・`exp`・`client` 一致・`redirect` 一致・`S256(code_verifier) === challenge`）→ User Data DO `consumeAuthorizationCode({ jti, expiresAt, connectionId })`（§1.3）→ `{ access_token, token_type: "Bearer", expires_in: 3600, refresh_token, scope: "ai" }`。失敗はすべて 400 `{ error: "invalid_grant" }`（`client_id` 不正は `invalid_client` 401）。`grant_type=refresh_token`: refresh を検証 → `authorizeAiClient({ connectionId })` が `null` なら `invalid_grant` → 新 access + 新 refresh。`Cache-Control: no-store`、`Pragma: no-cache` |

- 認可コードは `redirect_uri` を含むので `redirect_uri` パラメータの照合は交換時にも行う（OAuth 2.1）
- `state` は素通し（P-14 の往復は authz blob が運ぶ）
- `consumeAuthorizationCode` のあと `access` を発行するので、**コードの一回性と接続の実在を同じ tx で見る**（接続が既に失効なら `invalid_grant`）

### 1.4 認可ミドルウェア（`presentation/ai/auth.ts`）

1. `Authorization: Bearer <token>` を取り出す（無い / 形が違う → 401 + `WWW-Authenticate: Bearer resource_metadata="${APP_URL}/.well-known/oauth-protected-resource"`）
2. `aiTokenCodec.verifyAccess(token, now)` → `{ uid, cid }`（null → 401 `error="invalid_token"`）
3. `identityGateway.authorizeAiClient(uid, cid)`（△-4。`userData(uid).authorizeAiClient({ connectionId, now })` → `findActiveById` が null なら `null`、あれば `recordUsage(id, now)` を try/catch（失敗は `logger.warn`）→ `{ clientName }`）。`null` → 401 `invalid_token`（失効・不在・`NOT_INITIALIZED` はすべて同じ 401）。`account.status !== "active"` も 401
4. `AiClientActorDto = { kind: "aiClient", userId: uid, connectionId: cid, clientName }` を組み、`AiToolContext = { container, userId, actor }` としてツール handler へ渡す
- `TokenScope` の導出は固定（`AiClientActor` ⇔ `AiScope`）。`TokenScope.allows(ai, "hardDelete" | "trash" | "history")` が false であることは domain の unit（既存）で固定済み。presentation は `allows` を呼ばない — 許可リストが列挙そのものである

### 2.3 MCP（`presentation/ai/mcp.ts`）

- `POST /mcp`: 認可（§1.4）→ body は JSON-RPC 2.0 の単一メッセージ（配列 = batch は `-32600`）→ `method` でディスパッチ:
  - `initialize` → `{ protocolVersion: "2025-06-18", capabilities: { tools: { listChanged: false } }, serverInfo: { name: "fog", version: <package version> }, instructions: AI_GUIDANCE }`。クライアントが送った `protocolVersion` は無視（stateless。合意は応答側の値）
  - `notifications/initialized`（通知。`id` 無し）→ 202 空 body。その他の通知も 202
  - `ping` → `{}`
  - `tools/list` → `{ tools: [{ name, description, inputSchema, annotations }] }`（`cursor` は無視。11 本は 1 ページ）
  - `tools/call` → `{ name, arguments }`。未知 → `-32601`。`inputSchema.safeParse` 失敗 → `-32602`（`data` に `fieldErrors`）。成功 → `{ content: [{ type: "text", text: JSON.stringify(result) }], structuredContent: result, isError: false }`。usecase の失敗（`kind` が business / notFound / conflict / validation）→ `{ content: [{ type: "text", text: JSON.stringify({ kind, code, message }) }], isError: true }`（△-6）。system / unknown → JSON-RPC error `-32000`（message は redact 済み）
  - その他の `method` → `-32601`
- 応答は常に `Content-Type: application/json`（SSE を使わない）。`Accept` は検査しない（`text/event-stream` しか受けないクライアントは想定しない）
- `GET` / `DELETE` → 405（`Allow: POST`）
- 認可失敗は JSON-RPC ではなく HTTP 401（MCP Authorization 仕様どおり `WWW-Authenticate` 付き）

### 2.5 ガイダンス（`presentation/ai/guidance.ts`。R-AI-02）

`AI_GUIDANCE`（`instructions`）の骨子（日本語。実装時に文面を確定）:

- fog はユーザー個人のメモ / トピック / ドキュメント。あなたはユーザーの代理として読み書きする。すべての書き込みはユーザー名義の履歴に「AI クライアント名」付きで残り、ユーザーはいつでも人間 UI で確認・ロールバックできる
- できること: `search`（全文検索、`topicId` で絞り込み）、`get`（全文）、`list_topics`（構成の把握。完了済みも含む）、`recent_memos`（直近の文脈）、`post_memo` / `update_memo`（メモは全文置換）、`create_topic` / `update_topic`（完了 = `archived`）、`create_document`（出典メモ ID を必ず渡す）、`edit_document`、`delete`（ゴミ箱へ移すだけ。復元は人間が行う）
- できないこと（ツールが存在しない）: 完全削除、ゴミ箱の閲覧・復元・空にする、履歴の閲覧・ロールバック。ゴミ箱の中身は見えない（`NotFound` になる）
- 推奨する振る舞い: 議論が深まったらドキュメント化を提案する / 作成先は `list_topics` で確認し、合うものが無ければ `create_topic` / `edit_document` は `mode: "patch"`（一意な `oldText` に十分な前後文脈を含める）を原則とし、`replaceAll` はユーザーが明示的に全面書き直しを求めたときだけ / `changeReason` に「なぜ」を書く / `PATCH_TARGET_NOT_FOUND` は `get` で最新を取り直して再試行、`PATCH_TARGET_AMBIGUOUS` は文脈を広げて再試行 / 空本文のドキュメントは `replaceAll` で書く / 削除は必ずユーザーの明示的な依頼で
- 各ツールの `description` にも同じ要点を短く書く（`tools/list` だけ見るクライアント向け）
