## Manager 判断が必要な事項（当初の報告。上の対応で全て決着済み）

- **J-01 dev サーバーでの SSR ストリーミング**: `vite dev`（`@cloudflare/vite-plugin` + `@tanstack/react-start-rsc` 0.0.44）では、loader が返す `renderServerComponent(...)` を含む SSR 応答が `$_TSR.e()`（ストリーム終端）を出さず、Deferred 配下の RSC が**ハイドレートされない**（投稿欄が無反応）。`pnpm build && pnpm preview` では正常にハイドレートし投稿できることを確認した（02:18）。dev だけの現象なので、両ストリーミングルートに `ssr: !import.meta.env.DEV`（dev ではクライアント側で loader を実行 = RPC 経由の RSC。スケルトン → 内容の流れは同じ）を入れた。本番経路は変えていない。判断: この dev 限定の回避策を残すか、上流（TanStack）の問題として調査/issue 化するか
- **J-02 `router.invalidate()` と Suspense**: 投稿後の `router.invalidate()` で loader の promise が差し替わると、`use(promise)` がフォールバックに落ち楽観エントリが一瞬消える（preview で観測）。`Deferred` を `use(useDeferredValue(promise))` に変更し、解決済み内容を保持したまま新しい payload を待つようにした（CLAUDE.md の「楽観リストは再取得データへ re-base」の意図に沿う）。判断不要だが `components/ui/Deferred` の共有部品を変えたので報告
- **J-03 `knowledgeGateway`**: 既存テストが固定していた `RequestContainer.knowledgeGateway` は PH-03 まで外した（design D-03 の「フェーズごとに同じ階層へ足す」、D-05 の「スタブを置かない」を優先）。`session.test.ts` / `errorResponseMiddleware.test.ts` から `trippingKnowledgeGateway` を除去。PH-03 で `knowledgeGateway` と `fakeKnowledgeGateway` を足す
- **J-04 request 側の ID 採番**: design D-08「request 側は ID を生成しない」に対し、`registerWithPassword` は spec/usecases/identity.md 手順 1 のとおり `userId` / `credentialId` / `operationId` を request 側で採番している（`userId` で DO を選ぶ前に値が要るため）。エンティティ ID（メモ）は DO 側で採番。D-08 の文言をこの解釈で読んでよいか
