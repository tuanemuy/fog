## 2. 永続化

### 2.1 `stores/topicRepository.ts`

`memoRepository.ts` と同じ形（`TopicRow` 型・`TOPIC_COLUMNS` 定数・`rehydrate` で VO を通し `RehydrationError`・`versioned()`・`updateMatchedRow` + `occConflict()`）。

- `insert`: `INSERT INTO topics (…) VALUES (?, ?, ?, 'active', NULL, NULL, NULL, ?, ?, ?)`。projection なし
- `save`: `UPDATE topics SET name, description, status, trashed_at, purge_after, was_archived, version, updated_at WHERE id = ? AND version = ?`（trashed のとき `was_archived` は 0/1）。projection なし
- `delete`: `DELETE FROM topics WHERE id = ? AND version = ? RETURNING 1`。配下の消去は trash usecase の責務（PH-05）。projection なし
- `findById`: `WHERE id = ? AND status IN ('active','archived')`。`findByIdIncludingTrashed`: `WHERE id = ?`
- `listByUser({ includeArchived })`: `WHERE status IN ('active'[,'archived']) ORDER BY name ASC, id ASC`（`topics_live_idx (status, name)` に乗る。`id` は同名の tie-breaker）
- `listTrashedByUser`: `WHERE status = 'trashed' ORDER BY trashed_at DESC`
- `listSummariesByIds`: `SELECT id, name, status FROM topics WHERE status IN ('active','archived') AND id IN (…)` を `bindChunks` で分割。`Versioned` を付けない
- `recalculatePurgeAfter`: memo と同文（表名だけ違う）

### 2.2 `stores/documentRepository.ts`

3 表（`documents` / `document_revisions` / `source_links`）を 1 ストアで扱う（集約の境界 = ストアの境界。memo の `memos` + `memo_revisions` と同じ）。

- `insert`: `documents` 行 + `projectDocument(sql, doc)`（この時点の `source_ids` は空。直後の `insertSourceLinks` で作り直す）
- `insertRevision`: `document_revisions` に `id` / `document_id` / `revision_number` / `title` / `body` / actor 3 列 / `change_reason` / `created_at`。`doc_revs_doc_rev_uq` 違反を `ConflictError("OPTIMISTIC_LOCK_FAILURE")` に翻訳する。**確認済み**: 現状は `adapters/cloudflare/unitOfWork.ts` が driver 例外を一律 `SystemError(DatabaseError)` に畳み、memo 側の `insertRevision` も一意制約違反を翻訳していない（`memo_revisions` の PK 違反も `DatabaseError` になる）。PH-03 で `stores/occ.ts` に `isUniqueViolation(error)`（SQLite のメッセージ `UNIQUE constraint failed` / `PRIMARY KEY` で判定）を足し、memo / document 両方の `insertRevision` を `try { … } catch (e) { if (isUniqueViolation(e)) throw occConflict(); throw e }` にする（spec/domains/memo.md・knowledge.md の両方が要求）。integration で「`version` を直接進めたのち同じトークンで save → OCC」に加え、「`memo_revisions` に同番号の行を先に入れて insertRevision → `OPTIMISTIC_LOCK_FAILURE`」を固定
- `insertSourceLinks(links)`: `INSERT INTO source_links` を `bindChunks`（3 列 × n ≤ 100 パラメータ → 33 行ずつ）→ **`projectDocument(sql, doc)` を作り直し**（`source_ids` に active メモを載せる）→ **各 `memoId` を `reprojectMemo(sql, memoId)`**（`sourceOfDocumentIds` の反映）。ドキュメントを引数に取らないので、`documents` から `id` で読み直して射影する（links が空なら何もしない）
- `save(doc, expectedVersion)`: `UPDATE documents SET topic_id, title, body, latest_revision_number, status, trashed_at, purge_after, trashed_with, version, updated_at WHERE id = ? AND version = ?` → `projectDocument` or（trashed なら）`removeSearchEntry(doc.id)` + **出典メモ全件を `reprojectMemo`**（`listSourceLinksByDocument` 相当の SQL で `memo_id` を引く。`Document.softDelete` / `restore` のファンアウト。`edit` / `rollback` は出典側に影響しないが、常に再射影しても結果は同じなので分岐は `status` だけにする）
- `delete(id, expectedVersion)`: 出典メモ ID を先に確定 → `DELETE FROM documents … RETURNING` → `DELETE FROM document_revisions WHERE document_id = ?` → `DELETE FROM source_links WHERE document_id = ?` → `removeSearchEntry` → 確定しておいた各メモを `reprojectMemo`（ADR-003 の document 側。FK CASCADE は defense-in-depth）。PH-05 の消費者
- `findById` / `findByIdIncludingTrashed` / `listActiveByTopic`（`docs_topic_active_idx`、`Versioned`）/ `listTrashedByTopic`（`docs_topic_trashed_idx`）/ `listTrashedByUser`（`docs_trash_idx`）
- 射影読み: `listActiveSummariesByTopic`（`SELECT id, topic_id, title, updated_at, status … WHERE topic_id = ? AND status = 'active' ORDER BY updated_at DESC, id ASC`）、`listActiveSummariesByTopics`（`topic_id IN (…)` を chunk）、`listSummariesByIdsIncludingTrashed`（`id IN (…)` を chunk）。いずれも `Versioned` なし、`title` は VO を通す（`DocumentTitle.create`。本文は読まない）
- `listRevisionSummaries`（`SELECT id, document_id, revision_number, actor_type, actor_connection_id, actor_client_name, change_reason, created_at … ORDER BY revision_number ASC`。本文列を読まない。memo 側と同じく `RevisionNumber` / `ChangeReason` / actor を VO に通す）/ `findRevision`（1 件、全文込み）。`listRevisions` は置かない（△-10）
- `listSourceLinksByDocument` / `listSourceLinksByDocuments`（PK 前方一致）/ `listSourceLinksByMemo` / `listSourceLinksByMemos`（`source_links_memo_idx`）/ `deleteSourceLinksByMemo`（冪等。projection の作り直しは呼び出し側 = PH-05 の trash usecase が影響ドキュメントを先に確定して行う。**ただし projection はポートでないので、ここでも `document_id` を確定してから `projectDocument` を呼ぶ**）

### 2.3 `searchProjection.ts` の拡張

- `projectDocument(sql, doc: ActiveDocument)`: `upsertSearchEntry(sql, { id, type: "document", topicId, title, body, timestamp: updatedAt, sourceIds: activeSourceMemoIds(sql, doc.id) })`
- `activeSourceMemoIds(sql, documentId)`: `SELECT m.id FROM source_links sl JOIN memos m ON m.id = sl.memo_id WHERE sl.document_id = ? AND m.status = 'active' ORDER BY m.id`（既存 `activeSourceDocumentIds` の鏡像）
- `reprojectMemo(sql, memoId)`: `memos` から `body` / `posted_at` / `status` を読み、active なら `upsertSearchEntry({ type: "memo", …, sourceIds: activeSourceDocumentIds(sql, memoId) })`、trashed / 不在なら何もしない（trashed のエントリは既に無い）。`memoRepository.ts` の `projectMemo` と重複しないよう、`projectMemo` の中身をこの関数に寄せる（`memoRepository` は自分の `Memo` を持っているので `reprojectMemo` の「行を読む」段だけを飛ばす薄い分岐にする）
- `search_entries.body` の NFKC 膨張の切り詰めは spec が「別途決定」としているので PH-03 では入れない（PH-04 で search と一緒に判断）

### 4.6 P-09 ドキュメント編集（`components/documents/DocumentEditor`）

- 1 つの island を `mode: "create" | "edit"` で使う。`create` は `{ topicId, topicName }`、`edit` は `{ document: DocumentView, topicName, sourceMemos }`

- `edit`: `editDocumentFn({ documentId, title, body, changeReason, expectedVersion })`。`expectedVersion` は `document.version`（`getDocument` の値）を state に持つ。結果分岐: `saved` → P-08 へ（`invalidate` は遷移先 loader が再実行するので不要）; `unchanged` → P-08 へ（リビジョンは積まれない。TC-24）; `conflict` → `.fog-conflict`（`role="alert"`: 「編集を開いた後に <actor> が編集しました（<formatDateTime>・<changeReason>）」+ 現在のタイトル / 本文を折りたたみで表示）+「そのまま保存」（`expectedVersion = conflict.currentVersion` で再送。TC-25 手順 4）/「編集をやめる」（P-08 へ）。`OPTIMISTIC_LOCK_FAILURE`（レア）は alert + リトライ
- 変更理由欄（edit のみ）: `<input placeholder="手動編集">`、空送信は `changeReason: null`。文言は `errorDisplay.ts` に PH-01 で用意済み（`FIELD_LABELS` に `title` / `body` / `changeReason` / `name` / `description` を足す）
- **出典欄**: `create` では `SourceMemoPicker`（下）で選んだメモを `.fog-origin` に列挙 + 「出典から外す」（ローカル state から除去）+「出典を追加」。`edit` では `sourceMemos` を読み取り専用で列挙（△-4）
- **`SourceMemoPicker`**（`create` 専用、`<dialog>`）: 検索欄（`q`）→ `useTransition` で `loadTimelinePageFn({ cursor: null, direction: "older", limit: 20, keyword: q })`（PH-02 で `keyword` が入る。△-2）→ 候補行（`formatDateTime(postedAt)` + `snippetOf(body)`（△-9。閲覧側と同じ規則）+ 「追加」/「追加済み」。TC-09 手順 4 の文言）。空欄では直近 20 件。「もっと読む」は `nextCursor` で 1 段だけ
- 失敗（`business` / `system`）: 入力保持 + alert + 再送（同じ「保存」）。離脱（TC-33）は何もしない（`beforeunload` は付けない）
- 保存成功のトースト（design の `.toast`）: P-08 側に `?saved=1` で出す形は URL を汚すので採らない。遷移だけで完了とする（判断不要）

## 5. spec の記述で判断が要る点（△ の詳細）

△-1〜△-9 は **Manager 決定済み（design.md D-10、2026-09-08）**。各項目の末尾に決定を記す。△-10 は本改訂で起票（未決）。

- △-1 **`DocumentBody` の transport 上限**: VO は `codePointLength ≤ 400,000`、zod `.max(n)` は UTF-16 コード単位。`.max(400_000)` だとサロゲートペアを含む正当な本文（例: 絵文字混じり 350,000 コードポイント = 最大 700,000 単位）が transport で `INVALID_INPUT` になり、業務エラーの文言（「本文は400,000文字以内で…」）に届かない。推奨: `.max(800_000)`（2 単位/コードポイントの上界）。DoS 上限としても 1.6 MB で `memos` の 100,000（10,000 の 10 倍）より厳しい。TC-39 の 400,001 文字（BMP）は zod を通り VO で落ちる。**Manager 決定**: zod `.max(800_000)`。業務上限は VO だけが判定する
- △-2 **出典メモ選択の検索手段**: spec P-09「出典メモの検索・選択」、TC-09 は「検索欄に `打ち合わせ` と入力して検索し、`メモA` の『追加』」。search ユースケース（FTS5 / trigram、3 文字以上）は PH-04。推奨: PH-02 で `keyword` が入る `getTimeline` を `loadTimelinePageFn` 経由で再利用（LIKE 部分一致、1 文字から効く、active のみ = ゴミ箱内は候補に出ない）。PH-04 後も差し替えない（出典候補は「自分のメモの本文に含まれる語」で十分で、順位付けは不要）。代替: PH-04 の `searchFn` に `type: "memo"` 絞り込みで差し替える — 3 文字未満のフォールバック挙動が候補 UI に漏れるので推奨しない。**Manager 決定**: PH-02 の `getTimeline`（keyword、limit 20）を `loadTimelinePageFn` 経由で再利用。PH-04 後も差し替えない。実装注記: `loadTimelinePageFn` の入力は PH-02 で `{ cursor, direction, limit, keyword: string | null }` になっており、空欄は `keyword: null`（直近 20 件）。照合は `LIKE`（`%` `_` `\` エスケープ、ASCII 大小無視）
- △-3 **新規作成の変更理由**: spec P-09 は編集モードだけに変更理由欄を書き、`createDocument` の `changeReason` は任意で既定「作成」。推奨: 新規モードは欄を出さない（TC-16 手順 1 が「リビジョン1（変更理由 `作成`）」を前提にしている）。**Manager 決定**: 新規作成では欄を出さない。編集モードのみ欄を出し、省略時は「手動編集」
- △-4 **design HTML（P-09 編集）の出典操作**: `document-edit.html` は編集モードにも「出典から外す」「出典を追加」を描くが、`spec/domains/knowledge.md` SourceLink は「生成はドキュメント作成時のみ。後からの追加・削除の操作は提供しない」。推奨: 編集モードは出典を読み取り専用で表示（削除 / 追加ボタンを出さない）。**Manager 判断**: design HTML を spec に合わせて直すか（spec-revise の範囲）、PH-03 は spec を正として進める（本書の前提）。**Manager 決定**: spec（出典は作成時のみ）を正とし、編集モードの出典欄は読み取り専用。`document-edit.html` は Manager が PH-03 受け入れ時に直す
- △-5 **P-10 の操作形**: `document-history.html` は「版を開いた閲覧画面（現在との差分。復元はこの画面で行う）」= 1 版選択 → 最新との差分 → 戻す。`spec/pages/index.md` P-10 は「任意二点の差分表示」+「過去リビジョンへの『この内容に戻す』」。P-05（PH-02）は二点選択で 1 点目が比較元。推奨: 二点選択を基本にし、1 点目選択時に「最新との差分」を即表示することで design の体験を包含する（1 タップで戻せる = S-DT-06 の「ワンタップで戻す」）。**Manager 判断**: P-05 と揃えるか design のとおり 1 版選択にするか。**Manager 決定**: P-05 と同じ二点選択。1 点目（比較元）を選んだ時点で最新との差分を出し、2 点目で切り替える。「この内容に戻す」は比較元に対して出す（§4.7）
- △-6 **archived トピック配下への作成**: `createDocument` の testcases「`archived` トピック配下に作成する → 正常に作成される」。P-07 の UI で「新しいドキュメント」を archived でも出すか。推奨: 出す（完了は「一覧の主要領域から退く」だけ。隠すと spec に無い規則を UI が作る）。**Manager 決定**: 許可。P-07 の「新しいドキュメント」は archived でも出す
- △-7 **`listDocumentsReferencingMemo` の消費者**: タイムライン / 位置指定表示は `getTimeline` 系の一括逆引きが担い、単一メモ版を呼ぶ画面が PH-03 の範囲に無い。推奨: usecase / procedure / facade / gateway / integration テストまで実装し（spec testcases がある）、画面配線は無し。候補は P-05 のヘッダに「→ ドキュメント」を出すこと（PH-10 の監査で決める）。**Manager 決定**: usecase / facade / gateway / integration テストまで実装し、画面からは呼ばない
- △-8 **`ActorView` の置き場**: PH-02 は `application/memo/view.ts` に `ActorView` / `toActorView`。knowledge が memo を import するのはドメイン間依存（spec: RevisionNumber すら共有しない）。推奨: `application/identity/view.ts` へ移し、`memo/view.ts` は `export { ActorView, toActorView } from "../identity/view"` で互換を保つ。PH-02 マージ後に PH-03 が行う。**Manager 決定**: `application/identity/view.ts` に置き、memo / knowledge が import（`memo/view.ts` は再 export で互換）。実装注記: PH-02 の `application/memo/view.ts` は `ActorView` 型と `toActorView` / `toRevisionSummaryView` を持つ。移すのは `ActorView` と `toActorView` だけ（`toRevisionSummaryView` は memo 固有）。dom / unit の import 元は `application/memo/view` のままで動く
- △-9 **`snippet`**: spec は「本文抜粋」とだけ。推奨: application 層 `toSnippet`（先頭 120 コードポイント、`\r?\n` → 空白、超過は末尾「…」）。design の `.o-text` は 1〜2 行なので 120 で足りる。presentation で切ると DTO に全文が乗って P-07 の関連メモ n 件 × 10,000 文字になるため application 側で切る。**Manager 決定**: `lib/text.ts` の `snippetOf`（140 コードポイント + `…`）を使い、`\r?\n` → 空白の畳み込みを同関数に足す。新しい定数は作らない。`snippetOf` の JSDoc が「editor の候補と閲覧側で同じ規則」を求めているので、`SourceMemoPicker` の候補行も同じ関数で切る（`lib/text` は web から import 可能）
- △-10 **`DocumentRepository.listRevisionSummaries`（§1.2）**: 起票時点では `spec/usecases/knowledge.md` listDocumentRevisions が「メタデータのみ」を要求しつつ手順 3 で全文込みの `listRevisions` を名指していた。**Manager 決定（spec 反映済み: `121ffe7` = spec/domains/knowledge.md・spec/usecases/knowledge.md・spec/testcases/knowledge/listDocumentRevisions.md）**: `listRevisionSummaries(documentId): readonly DocumentRevisionSummary[]`（`Pick<DocumentRevision, "revisionNumber" | "actor" | "changeReason" | "createdAt">`）を採用し、`listRevisions` は置き換える（残さない。entity 全体を要る呼び出し元が無く、差分・ロールバックは `findRevision` で 1 件ずつ引く）。実装は memo 側 `MemoRepository.listRevisionSummaries` と同じ形。integration は「本文を含まない」を `Object.keys` の集合で固定する
