## 2. `purge-trash` の投入（最小の形）

spec/domains/trash.md「保持期限」手順 2: ソフトデリートと同じ `transactionSync` で `TrashQueryPort.findEarliestPurgeAfter()` を読み、現在予定の起床より早ければ `enqueueJob`。

- **UoW ctx に載せるもの**: `trashQueryPort: TrashQueryPort` を `UserDataUnitOfWorkContext` に追加する（spec/database の roster の一員。読み取り専用ポートなので「スタブを置かない」に反しない）。PH-02 で実装するメソッドは **`findEarliestPurgeAfter()` だけ**にし、他 4 メソッド（`listTrashItems` / `findTrashItem` / `countTrashItems` / `listItemsToPurge`）はインターフェースに宣言せず PH-05 で足す（PH-01 の `CredentialMappingWriter` 3 段と同じやり方: インターフェースは実装済みの範囲だけを持つ）。**△ Manager 判断**: spec のポート全体を先に宣言し未実装分を `throw` で置く形は D-05 に反するので採らない — この読みでよいか
- `findEarliestPurgeAfter` の SQL: `SELECT min(purge_after) FROM (SELECT purge_after FROM memos WHERE status='trashed' UNION ALL SELECT purge_after FROM documents WHERE status='trashed' UNION ALL SELECT purge_after FROM topics WHERE status='trashed')`（3 表の `*_purge_idx` を各枝で使う。PH-02 時点で documents / topics は常に空だが表は既にあるので最初から 3 枝で書く）
- 「現在予定されている起床より早ければ」は **`enqueueJob` の収束規則 (1)（runnable 行の `next_run_at` は早める方向にのみ動く）と (3)（`purge-trash` は `done` から復帰する）で実現される** — 呼び出し側は比較せず常に `enqueueJob({ operationKey: "purge-trash", kind: "purge-trash", payload: {}, nextRunAt: earliest })` を呼べばよい（`jobWriter.ts` が既に実装）。`payload` は `{}` 定数（digest 不一致を起こさない）。`earliest` が null になることは無い（今ソフトデリートした行がある）
- 起床時の handler（`jobs/purgeTrash.ts`）は PH-05。PH-02 では未登録なので、起床すると「No handler registered」で失敗 → backoff → 5 回で `poison`。**△ Manager 判断**: PH-02 の期間だけ `purge-trash` に「何もせず駆動源を読み直して rearm する」暫定 handler を置くか（`poison` 行を残さない利点 / スタブ禁止との整合）、それとも PH-05 まで `poison` を許容して PH-05 の integration テストで `requeue` を含めて確認するか。推奨: 暫定 handler は置かず、PH-02 の integration テストは「`jobs` に `purge-trash` 行が `nextRunAt = purgeAfter` で入ること」までを固定する
- 投入点はソフトデリートのみ（`changeTrashRetentionDays` は PH-05、AI `delete` は PH-07、knowledge は PH-03）。`softDeleteMemoProcedure` は `ctx.enqueueJob` を必ず呼ぶ

以下は判断依頼時の原文。

- △ **J-A `TrashQueryPort` の段階的宣言**（§2）
- △ **J-B `purge-trash` の暫定 handler**（§2）: 推奨は「置かない」
- △ **J-C 日付ジャンプの pivot**（§3）: `findTimelineAround` の date アンカー実装は「`posted_at <= date` の最新」。「その日の先頭位置」にするため presentation が日の終端を渡す。spec/domains/memo.md L334「指定日の先頭位置（その日にメモがなければ前後で最も近いメモの位置）」の「前後で最も近い」は、PH-01 実装では「その瞬間以前の最新、無ければ全体の最古（= 未来側で最も近い）」。**過去側にメモがあれば過去側を優先**しており「前後どちらが近いか」は測っていない。spec の testcases（過去日 → 最古付近、未来日 → 最新付近）は満たす。厳密に近い方を選ぶ実装（前後 1 件ずつ引いて `|Δt|` 比較）に変えるか
- △ **J-D ロールバック後の遷移先**（§3）
- △ **J-E `showMemoInTimeline` の `notFound` / `trashed` フォールバック**: spec は「通常タイムライン表示にフォールバック」。loader 1 回で両方（対象探索 + 通常ページ）を返すため `TimelineFeed` が 2 ユースケースを呼ぶ形にする（server fn 1 回・RPC 2 回）。RPC を 1 回にまとめる facade（`showMemoInTimelineOrTimeline`）は spec に無いので作らない
- △ **J-F `editMemo` の `expectedVersion` の transport 検査**: spec は「0 以上の整数」を入力 DTO のバリデーションとして書く。zod（transport）で `int().min(0)` にし、application では再検査しない（CLAUDE.md の 2 点）でよいか
- △ **J-G `diffMemoRevisions` の同一番号**: `ValidationError` を transport（zod `refine`）と application の両方に置くと二重。推奨: application（usecase）に置き、transport は形だけ
- △ **J-H P-05 の `ActorView.kind: "user"` の表示名**: 「あなた」（spec は presentation 責務とだけ言う）
- △ **J-I 絞り込み中の日付ジャンプ**（spec testcases: keyword 継続）: `?q=&date=` の両立を認める。`memo` 指定時は `q` を無視（spec: `keyword: null`）
- △ **J-J `keyword` の照合**: PH-01 の `instr(body, ?)` は大文字小文字・NFKC を区別する（spec/database: `body LIKE '%…%'` のスキャン、search.md は NFKC を索引側に適用）。タイムライン絞り込みは本文の**部分一致**であって検索ではないので、大小区別ありのまま（`LIKE` は既定で ASCII 大小無視なので `instr` の方が一貫）。要確認
- 判断不要（spec で決まっている）: `rollbackMemo` は `expectedVersion` を受けない / `listMemoRevisions` と `diffMemoRevisions` は trashed でも読める / `softDeleteMemo` の二重削除は `NotFoundError` / `editMemo` の conflict は書かずに返す
