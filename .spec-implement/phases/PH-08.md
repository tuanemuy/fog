## 要約

- **実行位置は spec どおり 2 つ。** User Data DO は `readExportSource()` 1 RPC で `ExportSourceDto`（全メモ・全トピック・全ドキュメント・出典 ID）を**1 回の `transactionSync` で読み切って値で返す**（書き込み・`enqueueJob` / `enqueueEvent` なし）。request Worker が `ExportRenderer.render`（純関数）→ `zipSync`（`fflate`）→ `Response`（`application/zip`、`Content-Disposition: attachment`）。ページング RPC は採らない（一貫性。spec が明示的に禁止）
- **上限は DO 側で本文バイト数の合計に置き、超過は読み切る前に拒否する**（△-1）。値は運用値 `EXPORT_MAX_SOURCE_BYTES = 24 MiB`（Workers RPC の直列化上限 32 MiB の 3/4。frontmatter・見出し等の付加分と `Date` / ID の直列化オーバーヘッドの余裕）。超過は `SystemError(ExportTooLarge)`（新 code、`retryable: false`）で、zip も部分アーカイブも返らない
- **配線**: `POST /export` は TanStack より前の bare handler（`presentation/export/handler.ts`。SSO / AI と同じ形）。理由: server fn は JSON 応答の契約で、バイナリ + `Content-Disposition` を返す面ではない。セッションは `ssoHandlers.ts` の `readSessionUserId` を `presentation/requestSession.ts` に切り出して共用（△-3）。同一オリジン検査（`Origin` / `Sec-Fetch-Site`）で CSRF を閉じる
- **UI（P-13「データ」節）**: `ExportPanel`（client island）が `fetch("/export", { method: "POST", body: FormData(timezone) })` → 生成中 `<span class="spinner">生成中…</span>` → 完了で `Blob` → `URL.createObjectURL` → `<a download="fog-export-YYYYMMDD.zip">` を 1 回自動クリック + 「ダウンロード」ボタンを残す（design HTML「生成完了」状態）。失敗は行内 `role="alert"` + 「エクスポート」ボタンに戻る。タイムゾーンは `Intl.DateTimeFormat().resolvedOptions().timeZone` を hidden 入力（D-09）
- **AI 経路から到達不能**: `presentation/ai/` は `application/export/*` を import しない（PH-07 の import 許可リスト `tools.test.ts` に `application/export/` を FORBIDDEN_FRAGMENTS として追記）。`/export` はセッション cookie 必須で Bearer を見ない
- **10 GB 逼迫時**: 経路上の書き込みは 0（セッション判定 `readAccountState` は読み、`readExportSource` は読み、schema gate は読み、`recordUsage` 相当は無い）。CLAUDE.md の「recovery path must work without a single write」を満たす。**限界**: `enterRpc()` の migration gate が「未適用の migration がある DO」で書き込みを試みる点は既存の設計どおり（PH-09 の `migrate-bulk` の領分）
- **P-13 の突き合わせ**: spec/pages P-13 の機能 7 項目のうち未実装は「データエクスポート」のみ。「読み込み中 → 表示」（Suspense skeleton）、AI 0 件案内、SSO 不成立表示、試行制限の明示、項目別の保存中 / エラー / 成功は実装済み（PH-06 / PH-07）。節の順序を design HTML（データ → アカウント）に寄せるかは △-6

### 1.2 `valueObject.ts`

- `ExportRequest.create({ userId: UserId, timezone: string })`: `timezone` を trim せず、空文字 → `InvalidTimezone`。解決は `new Intl.DateTimeFormat("en-US", { timeZone })` を try し `RangeError` → `InvalidTimezone`。`resolvedOptions().timeZone` を正規名として保持（`asia/tokyo` → `Asia/Tokyo`。manifest には正規名を書く。テストは大文字小文字の違いを 1 行固定）
- `ExportSource`（`memos` / `topics` / `documents` の readonly 配列。型のみ。検査は renderer）、`MemoExportEntry` / `TopicExportEntry` / `DocumentExportEntry`（spec の表どおり。ID は各ドメインの VO を再構築せず **string のまま**持つ — export → memo / knowledge の依存は「ID と読み取り専用ビュー」に限る（ADR-004）、VO の再構築はエクスポートに意味を足さない。spec の型名 `MemoId` 等は「その ID である」の意で読む。△ には挙げない: spec/domains の「他ドメインの型は ID 参照のみ」の範囲内）
- `ExportFile.create(path, content)`: 空 / 先頭 `/` / `..` セグメント / 空セグメント / 拡張子 `.md` 以外 → `InvalidArchivePath`。`\` は禁止文字としてスラッグ側で落ちるので path 検査には含めない
- `ExportArchive.create({ rootDirName, files, exportedAt })`: `files` を `path` の辞書順（コードポイント順 `<`）にソートした新配列を持つ。重複 → `DuplicateArchivePath`
- `ArchiveBinary`（`filename` / `contentType: "application/zip"` / `data: Uint8Array`。型のみ）
- `slugOf(name: string): string`（spec の手順 1〜6）と `resolveSlugs(items: { name, createdAt, key }[]): Map<key, slug>`（手順 7: `createdAt` 昇順、同値は `key`（ID）昇順で安定化。衝突は `-2`, `-3`… を付し、付与後にも既存と衝突すれば次の番号へ。**切り詰めは番号付与の前に済んでいる**ので `-N` を付けて 50 文字を超えることは許容する（spec 手順 7「切り詰め後に再衝突しても同様」の読み）。△ には挙げない）

### 1.3 `exportRenderer.ts`（純関数）

`render(source, exportedAt, timezone): ExportArchive`

1. `topicIds = new Set(topics.map(t => t.topicId))`。`documents` に無い `topicId` → `OrphanDocument`
2. 日時整形: `formatIsoWithOffset(date, timezone)` = `Intl.DateTimeFormat("en-US", { timeZone, hourCycle: "h23", year/month/day/hour/minute/second: "2-digit"/"numeric", timeZoneName: "longOffset" })` の parts から `YYYY-MM-DDTHH:mm:ss±hh:mm` を組む（`longOffset` は `GMT+09:00` → `+09:00`、`GMT` → `+00:00`）。`dayKey(date)` = 同じ parts の `YYYY-MM-DD`、`hhmm(date)` = `HH:mm`。**`Intl` は `nodejs_compat` の workerd と Node 24 で ICU full**（PH-01 で `Intl.DateTimeFormat` を `presentation/time.ts` が既に使用）
3. `rootDirName = fog-export-${dayKey(exportedAt).replaceAll("-", "")}`
4. manifest `index.md`（spec の YAML と本文。`counts` は配列長）
5. メモ: `postedAt` 昇順（同値は `memoId` 昇順）で `dayKey` ごとにグループ → `memos/YYYY-MM-DD.md`。本文は `## HH:mm (memoId)\n\n${content}\n`。ファイル末尾は 1 つの LF。本文中の CRLF は LF に正規化（「全ファイル改行 LF」）
6. トピック: `resolveSlugs` で `topics/{slug}/index.md`（frontmatter `name` は YAML ダブルクォート + エスケープ `"` `\` 制御文字）。`description` は本文（null なら frontmatter のみ、末尾 LF）
7. ドキュメント: トピックごとに `resolveSlugs`（同一階層のみ）→ `topics/{topic-slug}/{document-slug}.md`。`sources` は `sourceMemoIds` の順（`source_links.created_at, memo_id` 昇順。DTO の順を保つ）で、`memos` に見つかれば `memoId` / `postedAt` / `file: ../../memos/YYYY-MM-DD.md`、無ければ `memoId` + `deleted: true`。空なら `sources: []`
8. `ExportArchive.create`（ソート・重複検査）

YAML 出力は自前の最小関数 `yamlString(s)`（ダブルクォート。`\` `"` `\n` `\r` `\t` と U+0000–U+001F を `\uXXXX`）。ID・日時・boolean・整数は素で書く。ライブラリは入れない。

### 2.3 `readExportSourceProcedure`（DO 側。`application/export/readExportSource.ts`）

```ts
export function readExportSourceProcedure(sql: SqlStorage, maxBytes: number): ExportSourceDto
```

- 先に `SELECT COALESCE(SUM(length(body)),0) FROM memos WHERE status='active'` + `documents WHERE status='active'` + `SUM(length(COALESCE(description,'')))` + `SUM(length(name))` / `SUM(length(title))` を 1 文で合計（`length()` は文字数なので UTF-8 バイトは `length(CAST(body AS BLOB))`）。`> maxBytes` → `SystemError(ExportTooLarge, "The export exceeds the size limit")`（メッセージに件数もバイト数も入れない。ログに `bytes` を warn）
- `memos`: `SELECT id, body, posted_at, updated_at FROM memos WHERE status='active' ORDER BY posted_at ASC, id ASC`（`memos_timeline_idx` の逆走査）
- `topics`: `SELECT id, name, description, status, created_at FROM topics WHERE status IN ('active','archived') ORDER BY created_at ASC, id ASC`（`archived = status === 'archived'`）
- `documents`: `SELECT id, topic_id, title, body, created_at, updated_at FROM documents WHERE status='active' ORDER BY created_at ASC, id ASC`
- `source_links`: `SELECT sl.document_id, sl.memo_id FROM source_links sl JOIN documents d ON d.id = sl.document_id WHERE d.status='active' ORDER BY sl.document_id, sl.created_at, sl.memo_id` → document ごとに配列。**ゴミ箱内メモの ID は含める**（`deleted: true` の材料）、ハードデリート済みは CASCADE で行が無い
- 実装は `adapters/cloudflare/stores/exportSourceReader.ts` の `createExportSourceReader(sql, maxBytes)`（`ExportSourceReader` 実装。`SqlStorage` の直読み）。procedure は薄い（reader を呼び DTO 化）。ドメインの `ExportSource` は request 側で組む（DTO → VO）ので DO 側では組まない（二重変換を避ける）。spec 「ポート実装が範囲規則を満たす」は reader の integration で固定

### 2.4 facade（`UserDataDurableObject.readExportSource(): Promise<RpcEnvelope<ExportSourceDto>>`）

```ts
return this.envelope(() =>
  this.runUnitOfWork(() => readExportSourceProcedure(this.ctx.storage.sql, this.config.exportMaxSourceBytes)),
```

## 6. △ の詳細

- △-1: 上限を「本文バイトの合計」に置く理由は、それが zip 前のアーカイブサイズの主成分で、集計が索引付き列を走査するだけで済むから（`length(CAST(body AS BLOB))` は行を読むが本文を JS に渡さない）。frontmatter 分は総量の数 % で、24 MiB は 32 MiB に対し 25 % の余裕。`ExportSourceDto` の直列化は文字列が UTF-16 でなく UTF-8 相当で乗る（v8 serializer は one-byte / two-byte string を latin1 / UTF-16 で書く: 日本語本文は UTF-16 = UTF-8 の約 2/3〜同程度）。安全側として **日本語主体でも 24 MiB の本文が 32 MiB を超えない**（UTF-16 は 3 バイト文字を 2 バイトに縮める）。ASCII 主体は latin1 で等量。したがって 24 MiB は保守的で足りる
- △-2: `system` の固定文言（「システムエラーが発生しました」）は「再試行しても意味が無い理由をユーザーに隠す」ものではなく、内部情報を出さないためのもの。上限超過は内部情報ではなく利用者の状態なので文言を持たせる。`retryable: false` なので UI は「再試行」を勧めない
- △-3: `readSessionUserId` の切り出しは PH-06 コードの移動のみ（`ssoHandlers.test.ts` は import 先を変えるだけ）。`presentation/currentUser.ts`（TanStack の `getRequest` 経由）と二重実装になる点は PH-06 のまま
- △-4: `<a download>` の自動 click は同一オリジン Blob URL なので Safari / Chrome / Firefox で動く。ポップアップブロックの対象外（ユーザー操作起点の transition 内）。設計 HTML の「生成完了 → ダウンロード」状態を残すのは、自動保存が拒否された環境（企業ポリシー）でも受け取れるようにするため
- △-5: `mtime` を固定するとテストが zip バイトで比較できる（決定性）。`fflate` の zip は DOS 時刻（2 秒粒度、ローカル TZ）なので `exportedAt` を UTC として書く。展開後のファイル時刻がエクスポート時刻になるのは利用者にとって自然
- △-6: 節を design HTML の順に並べ替えると PH-06 の dom テスト（見出し順を見ているもの）を触る。並べ替えは PH-10 の docs / 統合検証で design との差分として扱う方が安全
- △-7: `MemoView` 等の既存は `Date` を structured clone で運ぶ。export だけ number にするのは「最大 24 MiB の配列」という量の違いから。usecase 側で `new Date(n)` に戻すので View / ドメインの型は spec どおり `Date`
- △-9: integration の `setPostedAt`（`memoFixtures.ts`）で `postedAt` を過去へ動かせる。ブラウザは今日の 1 ファイル。TC-03 手順 4 の「投稿日数ぶん」は integration で担保し、実装報告に「ブラウザは単日」と記す
