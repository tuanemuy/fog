## 1. ユースケース → request 側関数 / DO 側 procedure / facade / gateway

| ユースケース | request 側（`application/search/search.ts`） | DO 側 procedure（同ファイル） | facade（`UserDataDurableObject`） | `SearchGateway` |
|---|---|---|---|---|
| search | `search({ container, input: { userId, keyword, topicId?, cursor?, limit } })`: `SearchQueryDto` に詰めて `container.searchGateway.search(userId, dto)`。形の検証は transport（zod）に任せ、ここでは何もしない（D-08。値オブジェクトは DO 側で再構築） | `searchProcedure(ctx, dto)`: `TopicId.create`（指定時）→ `SearchQuery.create({ keyword, topicId, limit, cursor })` → `ctx.searchIndex.query(q)` → document 項目の `topicId` を重複除去 → `ctx.topicRepository.listSummariesByIds(ids)` 1 回 → `SearchResultItemView[]` へ射影（`topicName` 付与）→ `{ items, count, nextCursor }` | `search(input: SearchQueryDto): Promise<RpcEnvelope<SearchOutputView>>` | `search(userId, input): Promise<SearchOutputView>` |

- `SearchQueryDto = { keyword: string; topicId: string | null; cursor: string | null; limit: number }`（primitives のみ）
- `NotFoundError("TOPIC_NOT_FOUND")` は `ctx.searchIndex.query` が投げる（ポートの契約）。`listSummariesByIds` が空を返すことは無い（spec 手順 4 の理由）が、型上 `undefined` になるので `topicName` 欠落時は `SystemError(DataIntegrityError)`
- `SearchIndexUnavailable` は `stores/searchIndex.ts` が SQL 例外を `SystemError(SearchIndexUnavailable, retryable)` に翻訳する（adapter → application）。UoW 側の一括 `DatabaseError` 翻訳より内側で捕まえる

### 1.2 ドメイン（`domain/search/`）

- `valueObject.ts`: `SEARCH_KEYWORD_MAX_CODE_POINTS = 500`、`SearchCursor`（branded string。`create` は非空のみ検証 = `TimelineCursor` と同じ流儀）、`SearchQuery.create`（trim → 空で `EmptyKeyword`、コードポイント数 > 500 で `KeywordTooLong`、`limit` は 1〜100 の整数でなければ `BusinessRuleError(InvalidLimit)`… spec は「バリデーションエラー」としか言わないので application の `ValidationError("INVALID_LIMIT")` を **usecase 側で** 投げる（`normalizeLimit` と同じ位置づけ）。VO は整数範囲を再検証しない）、`SearchResultItem` / `SearchPage` / `IndexEntry` 型
- `ports/searchIndexPort.ts`: `interface SearchIndexPort { query(query: SearchQuery): SearchPage }`

### 1.3 ストア（`adapters/cloudflare/stores/searchIndex.ts`）

`createSearchIndex(sql, nowMs): SearchIndexPort`。`query` の手順:

1. `topicId` 指定時: `SELECT id FROM topics WHERE id = ? AND status IN ('active','archived')` が無ければ `NotFoundError("TOPIC_NOT_FOUND")`
2. `cursor` 指定時: デコード（§1.3.1）。失敗・期限切れ・`keyword` / `topicId` の不一致 → `BusinessRuleError(InvalidCursor)`。一致すれば埋め込みの集合をそのまま使う（**再検索しない**）
3. 先頭ページ: `normalizeForSearch(keyword)`（NFKC + trim。projection と同じ関数）。コードポイント数 ≥ 3 なら FTS 経路、< 3 なら短語経路
   - FTS: `SELECT e.type, e.id FROM search_fts f JOIN search_entries e ON e.rowid = f.rowid [JOIN … topic 絞り込み] WHERE search_fts MATCH ? ORDER BY bm25(search_fts, 3.0, 1.0), e.timestamp DESC, e.type, e.id LIMIT 500`。MATCH 引数は `"` を `""` に倍化して全体を 1 フレーズに引用（△-2。演算子・`*` を解釈させない）。bm25 の重みは title 3.0 / body 1.0（実装側の値。spec の「実測値」= integration の順位テストで固定）
   - 短語: `SELECT type, id FROM search_entries e [絞り込み] WHERE instr(e.title, ?) > 0 OR instr(e.body, ?) > 0 ORDER BY e.timestamp DESC, e.type, e.id LIMIT 500`（索引なしの全走査。対象列は 2 列、件数は上限で制限）
   - トピック絞り込み（S-SE-02）: `(e.type = 'document' AND e.topic_id = ?) OR (e.type = 'memo' AND EXISTS (SELECT 1 FROM source_links sl JOIN documents d ON d.id = sl.document_id WHERE sl.memo_id = e.id AND d.topic_id = ? AND d.status = 'active'))`
4. ページ: 集合の `offset`〜`offset + limit` の (type, id) を取り、`search_entries`（`source_ids`）と原文（`memos.body, posted_at` / `documents.title, body, updated_at, topic_id`）を `IN (…)` で引く（≤ 100 件 = 100 バインド以内）。**ページ時点で行が無い ID（削除された項目）は飛ばす**（集合は固定だがゴミ箱の内容は出さない）。順序は集合の順序を保つ
5. `SearchResultItem` へ: スニペットは `searchSnippet.ts` の `buildSnippet(original, keyword)`（§1.3.2）。`sourceOfDocumentIds` / `sourceMemoIds` は `search_entries.source_ids`（active のみ。projection が保証）
6. `nextCursor`: `offset + limit < 集合の件数` のときだけ（§1.3.1 でエンコード）。`count` = 集合の件数

#### 1.3.1 snapshot cursor（△-1 = B、Manager 決定）

- 内容: `{ v: 1, k: keyword(正規化後), t: topicId | null, x: expiresAtMs, o: offset, ids: [type-bit + uuid 16 byte …] }`。エンコード: `type` 1 byte（0 = memo, 1 = document）+ UUID 16 byte を連結したバイナリと、先頭のメタ（JSON）を `base64url` に。上限 500 件 → バイナリ 8.5 KB、base64url で約 11.4 KB。期限 30 分（`SEARCH_SNAPSHOT_TTL_MS`）
- 「同じカーソルからは同じ集合」: 集合は ID 列で固定。ページ間の追加は集合に入らず、更新は同じ ID なので落ちず、削除はページ時点で飛ぶ（欠落ではなく「ゴミ箱は出さない」の適用）
- 「期限切れは拒否」: `x < nowMs` で `InvalidCursor`。改竄は自分の DO の中で自分の ID を読めるだけで、存在しない ID は飛ぶ
- 不正形式（base64 でない・v 不一致・keyword 不一致・長さ不整合）も同じ `InvalidCursor`
- 集合が上限で切れる場合、`count` は切った後の件数（△-3）

#### 1.3.2 スニペット（`stores/searchSnippet.ts`、純粋関数・unit）

- 入力: 原文（メモ = `body`、ドキュメント = `title + "\n" + body`）と正規化済みキーワード。`Intl.Segmenter("ja", { granularity: "grapheme" })` が使えればそれで、無ければ `Array.from` で書記素列にし、各書記素の NFKC + 小文字化を連結して正規化文字列と書記素境界の対応表を作る。キーワードの出現位置を書記素 index に写像し、その 40 書記素前から 140 書記素の窓を切る（前後に `…`）。見つからなければ先頭 140 書記素。改行は空白に畳む
- 返る値は原文そのもの（全角のまま）。切り詰め幅は表示予算であり業務規則ではない

### 3.1 ルートと検証（`routes/_app/search.tsx`）

### 3.2 `SearchPanel`（client island、`components/search/SearchPanel`）

- フォーム: `<search><form>` に `input[type=search]`（`aria-label="メモとドキュメントを検索"`、`maxLength=500`、`defaultValue=q`）+ 検索ボタン。submit で trim → 空なら `preventDefault` して何もしない（TC-09 / 10）→ `navigate({ to: "/search", search: { q, topic } })`
- チップ（`fog-chips`）: 「すべて」+ `topics`（完了済みは名前の後に `<span class="fog-badge">完了</span>`）。`Link` で `search={{ q, topic }}`（q が無いときは topic だけ変えて入力待ちのまま）、`aria-pressed`
- 状態:
  - `idle`（q 無し）: 案内「キーワードを入力するとメモとドキュメントを横断して検索します」
  - `results`: 「n件」+ 行。行は `Link`（メモ → `/` `search={{ memo: id }}`、ドキュメント → `/documents/$documentId`）。行の中身: 種別バッジ（メモ / ドキュメント）、スニペット（`<mark>` で一致部分。クライアントで大小無視の `indexOf`、見つからなければ無印）、日時（`formatDateTime`）、ドキュメントは `topicName`
  - `empty`: 「「q」に一致するメモ・ドキュメントは見つかりませんでした」
  - `topicMissing`: 「絞り込み対象のトピックが見つかりません。削除されたか、URL のトピック ID が正しくありません」+ `Link`「絞り込みを解除して検索する」（`search={{ q }}`）

## 4. spec の記述で判断が要る点（△ の詳細）

- △-1 snapshot の物理形。spec/database「決めていないこと」は 3 形を等価に許す。**B（カーソル埋め込み）を推奨**: 表・索引・schema テストを変えない、読みで書かない（10 GB 上限の近傍で読みだけは動く = CLAUDE.md の「復旧経路は書き込み無しで動く」に沿う）、期限の掃除が要らない。欠点: 集合の上限 500（A なら 1 行 2 MB で ~50,000 件）、カーソルが 8.5 KB になる（POST の本文なので URL 長には掛からない）。A を採るなら `search_snapshots(token PK, expires_at, keyword, topic_id, ids)` + `expires_at` 索引 + 各 query 冒頭の掃除 + roster 更新（spec/database の表一覧は Manager が更新）
- △-2 キーワードの意味論。spec は「キーワード」「全文一致」「部分一致（日本語）」までで、複数語の扱いを書いていない。全体 1 フレーズ = 利用者が入力した文字列そのものの部分一致で、TC-14 の `<script>alert(1)</script>` / 絵文字も引用で安全。空白区切り AND は将来の拡張として残す
- △-3 `count` と上限。spec は `count` を「固定した集合の総件数」とするので、集合を上限で切った時点で `count` = 切った後の件数とするのが整合的。「1,000 件以上」のような表示は持たない
