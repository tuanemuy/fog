## 1. ユースケース → request 側 / DO 側 procedure / facade / gateway

配置は D-08 のとおり（`application/identity/<usecase>.ts` に request 側と procedure を並置）。**request 側が 2 つの DO を跨いで orchestrate する**（PH-01 の `registerWithPassword` の形）。`IdentityGateway` に以下を足す（primitives のみ）。

### 1.1 requestPasswordReset（R-AC-07）

- request 側 `requestPasswordReset({ userId 不要, email })`: `Email.create` → `deriveCredentialLocator("email", canonical, "")`（既存。hmac / generation / bucketIndex）→ **世代順序のプローブ**（`identityGateway` の `probe` と同じく active → previous → active 再プローブ。ヒットした世代の bucket、無ければ active）→ `identityGateway.requestPasswordReset(locator, { hmac })` → `void`
- Directory procedure `requestPasswordResetProcedure(ctx, { hmac, keyGeneration }, now, tuning)`（**1 tx**）:
  1. `windowKey = ${hmac}:${floor(now / tuning.resetRequestWindowMs)}`（合成は連結のみ。鍵付き再導出なし）
  2. `first = ctx.resetThrottleStore.claimWindow(windowKey, now)`（行が無ければ INSERT（`expires_at = 窓の終端 + grace`、`key_generation`）して `true`、あれば `last_requested_at` 更新で `false`）
  3. `first` のときだけ: `record = ctx.credentialMappingReader.findByLocator("email", mapping)`、`tokenId = record?.passwordVerifier ? ctx.resetTokenStore.issue(record.credentialId, now).tokenId : ctx.resetTokenStore.mintDecoyTokenId()`、`ctx.enqueueEvent([passwordResetRequestedDraft({ windowKey, tokenId, mailKind: "password-reset", now })])`
  4. 4 ケースとも `ctx.enqueueJob({ operationKey: "sweep-reset-tokens", kind: "sweep-reset-tokens", payload: {}, nextRunAt: 窓の終端 })`
- facade `requestPasswordReset(input: { hmac: string; keyGeneration: number })`（locator は stub 選択で消費済み）

### 1.2 executePasswordReset（R-AC-07）

- request 側 `executePasswordReset({ token, newPassword })` → `{ userId }`:
  1. `PlainPassword.create(newPassword)`（消費前）
  2. **どの bucket か**: token は bucket を指さない。**生トークンの先頭に bucket locator を埋めない**（トークンは不透明）。→ 代わりに **リセット URL に `b=<generation>:<bucketIndex>` を付けない**という選択肢もあるが、consumer が知る routing key を `MailSender` に渡していない。**採る形**: `PasswordResetTokenPort.issue` が返す生トークンを `${generation}.${bucketIndex}.${secret}` の形にし、request 側は先頭 2 区画で bucket を選ぶ（bucket 名は個人を指さない粒度なので露出しても衛生規則に触れない。`secret` 部分だけが照合対象）
  3. `identityGateway.consumeResetToken(bucket, { token, now })` → Directory procedure: `verifyAndConsume(token, now)`（`token_hash` 一致・`used_at IS NULL`・`expires_at > now` の条件付き UPDATE で `used_at = now`、`change_auth_token` を採番して返す）→ `null` なら `ValidationError("RESET_TOKEN_INVALID")`。同じ RPC で `findByCredentialId` の記録（`userId` / `hasVerifier` / mapping / `credentialId`）を返す。`hasVerifier` 偽は `BusinessRuleError(PasswordNotSupported)`
  4. `container.passwordHasher.hash(newPassword)`
  5. `identityGateway.beginCredentialChange(locator, { operationId, pendingVerifier, origin: "reset", changeAuthToken })` → Directory 1 tx: CAS（`change_auth_token = ? → NULL`、`credential_id` 一致）で `pending_verifier` / `change_state='pending'` / `change_origin` / `operation_id` を書き、そのクレデンシャルの未使用トークンを全削除、`enqueueJob({ operationKey: "resume-credential-change:" + operationId, kind: "resume-credential-change", payload: { credentialId, locator, userId }, nextRunAt: now + signupResumeDelayMs })`
  6. phase 2: `identityGateway.applyCredentialChange(userId, { credentialId, resetVersion: true })` → User Data 1 tx: `advanceSessionEpoch`、`credentialVersion = advanceCredentialVersion(credentialId)`、`after = advanceResetVersion()` → `aiClientConnectionRevoker.revokeCreatedAtResetVersion(after - 1)`（△-2）→ `{ credentialVersion }`
  7. `identityGateway.markCredentialChangeAdvanced(locator, { operationId })`（CAS `change_state='pending' AND operation_id=?` → `'advanced'`）
  8. `identityGateway.promoteVerifier(locator, { operationId, credentialVersion })`（CAS `change_state='advanced' AND operation_id=?` → `password_verifier = pending`、`pending/state/origin/operation_id = NULL`、`credential_version = ?`、`failed_attempts = 0`、`next_attempt_allowed_at = NULL`）。同じ tx でジョブ行 `resume-credential-change:<op>` を `done`（`finalizeRow` 相当の facade 内処理。ジョブが先に走っていた場合は 0 行で無視）
  9. `{ userId }` → presentation が `startSession(userId)`（`sessionEpoch` は前進後の値を読む）
- 6〜8 のどれかが落ちたら例外を返さず？ → **返す**（利用者には「処理中です。しばらくしてから新しいパスワードでログインしてください」= `SystemError`）。前進はジョブが引き取る（§1.7）

### 1.3 changePassword（R-AC-07）

- request 側 `changePassword({ userId, currentPassword, newPassword })`:
  1. `PlainPassword.create` ×2
  2. `identityGateway.readCurrentUser(userId)` → `credentials` から `kind === "email" && usableForLogin` を選ぶ。無ければ `PasswordNotSupported`
  3. `identityGateway.findCredentialLocator(userId, credentialId)` → locator → `identityGateway.readCredentialForChange(locator)`（Directory: `findByCredentialId` の record = verifier + `failedAttempts` + `nextAttemptAllowedAt` + `changeState`）。`changeState !== null` は `ConflictError("OPTIMISTIC_LOCK_FAILURE")`（進行中）
  4. ロックアウト: `decayed = decayedFailedAttempts(...)`; `nextAttemptAllowedAt > now` なら **`ValidationError("TOO_MANY_ATTEMPTS")`（照合せず、カウンタも進めない）**
  5. `passwordHasher.verify(current, verifier)` → 不一致は `recordAttemptOutcome(coordinate, failure{...})`（`loginWithPassword` と同じ算式）+ `ValidationError("CURRENT_PASSWORD_MISMATCH")`
  6. `hash(new)` → `beginCredentialChange(locator, { operationId, pendingVerifier, origin: "password-change", changeAuthToken: null })`（CAS は `change_state IS NULL`）→ `applyCredentialChange(userId, { credentialId, resetVersion: false })` → `markAdvanced` → `promoteVerifier`（成功時 `failed_attempts = 0`）
- 「制限中はその旨を明示」= 手順 4 のエラーをフォームがそのまま表示（△-7）

### 1.4 registerOrLoginWithSso（R-AC-02）

- request 側 `registerOrLoginWithSso({ provider, providerSubject, email })` → `{ userId, isNewUser }`:
  1. `SsoProvider.create` / `Email.create` / `providerSubject` 非空
  2. `identityGateway.resolveSsoIdentity(provider, subject)`（新規: `probe("sso", ssoCanonical(provider, subject))` → `{ userId } | null`。`status='active'` のみ）→ あれば `{ userId, isNewUser: false }`
  3. 無ければ PH-01 の登録 saga を **2 予約**で: `userId` / `operationId` / `callerToken` 採番、`credentialId` ×2、`deriveCredentialLocator("sso", …)` と `("email", …)`、`reserveCredential(ssoLocator, { … coordinatorRole: "coordinator", locators: [両方] })` → `reserveCredential(emailLocator, { coordinatorRole: "member", coordinatorLocator })`。敗北は `ConflictError`（sso → `SSO_IDENTITY_ALREADY_REGISTERED`、email → `EMAIL_ALREADY_REGISTERED`。email 側で負けたら sso の予約を `cancelReservation` で戻す（呼び出し元束縛あり））
  4. `initializeAccount(userId, { credentials: [sso(usableForLogin true), email(false)], … })` → `commitSignupSaga` → `activateReservation` ×2 → `recordSignupLocator(userId, 2 locators)` → `{ userId, isNewUser: true }`
- **既存の `registerWithPassword` の 4 phase を関数に括り出して共有する**（`signupSaga.ts`: `runSignupSaga(container, { userId, operationId, callerToken, credentials: [{ locator, dto }], … })`）。`resume-signup` は locators を持つので複数 credential を既に扱える（PH-01 の実装が `locators` 配列）

### 1.5 linkSsoCredential（R-AC-09）

- request 側 `linkSsoCredential({ userId, provider, providerSubject })` → `{ credentialId }`:
  1. `credentialId` / `operationId` 採番、locator 導出
  2. `identityGateway.beginLink(userId, { operationId, credentialId, locator })` → User Data 1 tx: `find()` → `recordOperation({ operationId, kind: "link", phase: "reserving", targetLocators: [locator] })` + `enqueueJob({ operationKey: "resume-link:" + operationId, kind: "resume-link", payload: { operationId }, nextRunAt: now + signupResumeDelayMs })`。`callerToken` は `account.caller_token` を返す（`readCallerToken`）
  3. `reserveCredential(locator, { operationId, candidateUserId: userId, callerToken, sealedCanonical, passwordVerifier: null, coordinatorRole: "coordinator", locators: [locator] })` → 敗北は `SSO_IDENTITY_ALREADY_REGISTERED`（自分のも同じ）。敗北時は `identityGateway.finishLink(userId, { operationId, outcome: "failed" })` で `updateOperation(phase: "done")` + ジョブを `done`（材料が無いので後始末も無い）
  4. `activateReservation(locator, operationId, userId)`
  5. `identityGateway.completeLink(userId, { operationId, credentialId, locator, label: provider })` → User Data 1 tx: `User.addCredential` → `save`、`credentialLocatorStore.record({ credentialId, kind: "sso", mapping, credentialVersion: INITIAL, usableForLogin: true, label })`、`updateOperation({ phase: "done" })`、ジョブ `resume-link:<op>` を `done`
- `sessionEpoch` は進めない

### 1.6 unlinkSsoCredential（R-AC-09）

- request 側 `unlinkSsoCredential({ userId, credentialId })`:
  1. `identityGateway.beginUnlink(userId, { credentialId, operationId })` → User Data 1 tx: `find()` → `User.removeCredential`（`kind: "email"` / 最後のログイン手段は `BusinessRuleError`、不在は `NotFoundError("CREDENTIAL_NOT_FOUND")`）→ `save` → `locators = credentialLocatorStore.listAllGenerations(credentialId)`（**新規メソッド**: 全世代の行）→ `recordOperation({ kind: "unlink", targetLocators: locators, phase: "deleting" })` → `deleteByCredentialId` → `advanceSessionEpoch` → `enqueueJob({ operationKey: "sweep-orphan-mapping", kind: "sweep-orphan-mapping", payload: {}, nextRunAt: now + signupResumeDelayMs })`。戻り `{ locators, callerToken }`
  2. 各 locator へ `identityGateway.deleteMapping(locator, { userId, callerToken })`（Directory: `DELETE credential_mappings WHERE (kind,hmac)=? AND credential_id=? AND user_id=? AND caller_token=?` + トークン行の全削除。「無ければ成功」）
  3. `identityGateway.finishUnlink(userId, { operationId })` → `updateOperation(phase: "done")`
- presentation は解除後に `startSession` し直す（自分のセッションも epoch で切れるため。P-13 / P-03 で操作した本人は続けて使える）

### 1.8 送信材料 RPC と mail consumer

- Directory facade `getResetMailMaterials({ eventId, ownerToken }): RpcEnvelope<SendMailMaterials>`（**migration ゲートの内側**）: `SELECT status, owner_token, payload FROM outbox_events WHERE id = ?` → 3 条件（行あり / `quarantined` でない / `owner_token` 非 NULL・引数 ≥ 22 文字（128 bit base64url）・定数時間比較で一致）→ `payload.tokenId` の `password_reset_tokens` 行（`used_at IS NULL AND expires_at > now`）→ その `credential_id` の mapping 行（`status='active'`、`password_verifier IS NOT NULL`）→ `openCanonical`（`IDENTITY_MAIL_ENCRYPTION_KEY`）→ `{ kind: "send", to, resetToken: derive(tokenId), providerIdempotencyKey: HMAC(PROVIDER_IDEMPOTENCY_KEY, eventId) hex }`。どれか外れれば `{ kind: "nothing-to-send" }`
- **生トークンの導出**: `resetToken = "${generation}.${bucketIndex}." + base64url(HMAC-SHA256(IDENTITY_RESET_TOKEN_KEY, "reset:" + tokenId))`、`token_hash = hex(SHA-256(secret 部分))`。`issue` は `tokenId`（CSPRNG 16 byte → base64url 22 文字）を採番し、その `token_hash` を書く。`verifyAndConsume` は `secret` 部分の SHA-256 で引く。`mintDecoyTokenId` は同じ生成器で 22 文字を返すだけ（行は書かない）。鍵 `IDENTITY_RESET_TOKEN_KEY` は **state Worker の秘密**（`.dev.vars.example` の帰属表に追記）
- `queueHandlers.ts`（`apps/web/app/worker/cloudflare/`）: `export async function runQueueBatch(batch, env)`: DLQ（`batch.queue.endsWith("-dlq")`）なら `handleDlqBatch`（各 message: `logger.warn("dlq", { eventId, type })` + `ack()`。batch 例外は `ackAll()`）。events なら `handleEventsBatch`: message ごとに `type` を roster で判定（`identity.passwordResetRequested` 以外 → `retry()`）、`routingKey` を `^dir:g\d+:b\d+$` で判定（外れ → `retry()`）→ `directoryStub(...).getResetMailMaterials({ eventId, ownerToken })` → `send` なら `mailSender.sendPasswordResetMail(...)` → `ack()`、`nothing-to-send` → `ack()`、例外 → `retry()`。**ログは `eventId` / `type` まで**
- `server.cloudflare.ts` に `queue(batch, env)` を export（`createQueueContainer(env)` → `{ mailSender, logger, bindings }`）
