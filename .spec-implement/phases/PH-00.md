### (b) SSO の開発用アダプター

spec の事実: `SsoProvider` は値オブジェクト（`"google" | "apple"`）。IdP との往復（リダイレクト、code 交換、assertion 検証）はアダプター責務で、ユースケースは検証済みの `{ provider, providerSubject, email }` を受け取る（usecases/identity.md L72, L80–82, L527）。初回 SSO で既存メールと一致しても自動リンクしない（`EMAIL_ALREADY_REGISTERED`）。キャンセルはエラーではなく初期状態へ（P-01）。

決めること: presentation 側ポート（例 `SsoIdentityProvider { buildAuthorizationUrl(provider, state, returnTo): URL; exchangeCode(provider, code, state): Promise<{ providerSubject; email } | "cancelled"> }`）と、開発用アダプターの形。候補: `SSO_DEV_STUB="true"`（`.dev.vars`、deployed configs には無い — `wranglerConfig.test.ts` の `DIAGNOSTICS_ENABLED` と同じ固定方法）で `/__dev/sso/:provider/authorize` に「subject と email を入力して許可 / キャンセル」のフォームを出し、`/auth/sso/:provider/callback?code=` に戻す。`state` は署名付き cookie に持つ。実アダプター（Google OIDC / Apple）は資格情報がある時だけ動く契約テストを置く（brief Q-01）

### (c) 開発用 MailSender

spec の事実: `MailSender.sendPasswordResetMail(to, resetToken, providerIdempotencyKey)`（非同期）。URL 組み立てと本文レンダリングはアダプター（request Worker）責務、base URL は env（`APP_URL`）のみ。ログに載せてよいのは provider の状態と `providerIdempotencyKey` の有無だけ。docs の前回アダプター `adapters/console/mailSender.ts` は「宛先もトークンもログに出さない」ので、**S-AC-07 のブラウザ検証でリンクを取り出せない**。

決めること: 開発用の出口。候補: (i) `MAIL_DEV_SINK="console"` のときだけ `[dev-mail] to=<addr> url=<reset url>` を console に出すアダプター（hygiene 規則の**意図的な例外**として `spec/async` に宣言する必要がある — spec は例外を silent に増やすなと言う）、(ii) メモリ / DO に貯めて `/__dev/mailbox` で読む（queue consumer と fetch が同じ isolate である保証が Miniflare に無い）、(iii) ファイル出力（Workers に fs が無いので不可）。Verifier が `pnpm dev` のログからリンクを拾う (i) が最小。本番アダプター（`MAIL_PROVIDER_API_KEY`）は契約テストのみ

### (d) セッションと `sessionEpoch` / `resetVersion` の整合

spec の事実: 3.4 のとおり。`sessionEpoch` を進めるのはパスワード変更 / リセット完了 / SSO 解除 / 退会の 4 つだけ、`resetVersion` はリセット完了のみ。毎リクエスト DO を読む（キャッシュしない）。

決めること: `apps/web/app/presentation/currentUser.ts` の実装（cookie → `sessionCodec.verify` → `identityGateway.readAccountState(userId)` → epoch 比較 → 全拒否を `null` に畳む、`requireUserId` は `redirect({ to: "/login", search: { redirect } })`）。`readAccountState` が未初期化 DO（`NOT_INITIALIZED`）を `null` に畳む場所（gateway か currentUser か）。cookie TTL 7 日と codec TTL 7 日の整合（既存どおり）。`SameSite=Lax` は OAuth の GET リダイレクトで cookie が届くので P-14 も動く。`_app.tsx` の `beforeLoad` で `readAuthStateFn` を使う（`noStoreMiddleware` が全保護ルートに `no-store` を付ける既存設計）

### (e) Markdown レンダリングと差分表示のライブラリ

spec の事実: メモは「Markdown 軽装飾」（箇条書き・コードブロック）で表示、データは非構造テキスト（pages L82、memo.md L220）。ドキュメントは Markdown/HTML 互換の構造化テキストで「整形表示・差分計算は presentation の責務」（knowledge.md L79）。リビジョンは全文スナップショット、差分は表示時計算（memo.md L13）。設計 HTML は行単位の unified 風（`.diff-line.removed/.added`、`spec/design/pages/memo-history.html` L800–810）。**ライブラリ名は無い**。

決めること: Markdown — 候補 `react-markdown` + `remark-gfm`（RSC でそのまま React 要素に描ける、`dangerouslySetInnerHTML` 不要で XSS 面が小さい）／ `marked` + サニタイザ（Workers に DOM が無いので `DOMPurify` は使いづらい）／ 軽装飾に限った自前レンダラ。差分 — `diff`（jsdiff）8.x が間接依存として store にあり、`diffLines` で行単位差分が取れる。明示依存に昇格して行レンダリングを自前で書くのが最小。AI の `DocumentPatch`（`oldText` → `newText` の hunk 適用）はドメイン内の文字列置換で、ライブラリ不要

### (f) DO クラスの配置と RPC facade の形

固定済み: クラス名 `UserDataDurableObject` / `IdentityDirectoryDurableObject`（`wrangler.state.toml` の `new_sqlite_classes`、`wrangler.toml` の bindings、`wranglerConfig.test.ts`、`env.d.ts`）。モジュール `packages/core/src/adapters/cloudflare/{userDataDurableObject,identityDirectoryDurableObject}.ts`（`state.ts` の import）。`AsyncWorkDurableObject<TCtx>` を継承し、`constructor(ctx, env)` で `DurableObjectRuntimeConfig`（plan / allowInitialize / clock / idGenerator / logger / jobRegistry / terminalStage）を組む。RPC は primitives のみ・`RpcEnvelope<T>` を返す・先頭で `enterRpc()`（診断 2 本を除く）。

決めること:
1. **ユースケースの実行位置**。CLAUDE.md は「VO の再構築は DO の中で行い、それが第二の検証点」と言う ⇒ VO 生成 + ドメイン遷移 + リポジトリ操作は DO 内の `runUnitOfWork` で走る。docs の前回形は「request 側の usecase（`ServiceArgs`）が gateway RPC を呼び、DO 側で procedure 関数が UoW を回す」。推奨: `application/<domain>/<usecase>.ts` に request 側関数（`ServiceArgs<TInput>` → gateway 呼び出し → View）と DO 側 `xxxProcedure(ctx, input, now, ids)`（同期）を並置し、DO の facade method が `this.envelope(() => this.runUnitOfWork(ctx => xxxProcedure(...)))` を呼ぶ
2. facade の粒度: ユースケースごとに 1 メソッド（memo 14 + knowledge 16 + search 1 + trash 7 + export 1 + identity の User Data 側 + saga 内部 + operator）か、`execute(kind, input)` のような単一入口か。前者が型で追えるが数が多い（60 超）。`DurableObjectNamespace<UserDataDurableObject>` の型付きスタブで RPC 署名を追える
3. スタブ選択アダプター `adapters/cloudflare/doStubs.ts`（`userId` → `USER_DATA.idFromName(userId)`、canonical → `deriveLocator` → `IDENTITY_DIRECTORY.idFromName(dir:g1:b<idx>)`）と `callDurableObject`（envelope 展開 → `rebuildRpcError`、スタブ呼び出し自体の失敗 → `SystemError(DatabaseError)`）
4. `jobRegistry` / `terminalStage` の組み立て場所（DO クラスのコンストラクタ内で kind → handler を束ねる）。handler は cross-DO RPC を打つので DO の `env` バインディング（`USER_DATA` / `IDENTITY_DIRECTORY`）が state Worker 側にも要る（`wrangler.state.toml` に自己参照 bindings を追加 = 設定変更 + `wranglerConfig.test.ts` の更新）
5. 両 DO の `MigrationPlan` v1（spec/database の全 DDL）をどのファイルに置くか（`schema/userDataPlan.ts` / `schema/identityDirectoryPlan.ts`）。「初回デプロイまで v1 を in-place で拡張」の規則を維持

### (g) ゲートウェイ / DI の形と spec との差

既存テストが固定する `RequestContainer`（2.4 #1）は `identityGateway` / `memoGateway` / `knowledgeGateway` / `identityTuning` / `passwordHasher` / `sessionCodec` / `config` / `clock` / `idGenerator` / `logger`。spec の 6 ドメインに対して search / trash / export の入口が無い。

決めること:
1. gateway の分割: `searchGateway` / `trashGateway` / `exportGateway` を足すか、memo / knowledge に相乗りか、User Data DO 全体を 1 つの `userDataGateway` にまとめて memo/knowledge/… を名前空間にするか。テストの `trippingXGateway((name) => …, overrides?)` の形（全メソッドが trip する total 実装 + overrides）は 3 つ分は必須
2. `IdentityGateway` のメソッド roster（docs は列挙しない）: 少なくとも `readAccountState(userId)`。registerWithPassword の saga（reserve → initialize-account → activate → record locator）、login の行解決、reset 系、AI 接続系、SSO 連携系
3. `application/di/serverCloudflare.ts`: `createRequestContainer(config: RequestServerConfig)` / `createQueueContainer(env)` / `readRequestServerConfig()`。`RequestServerConfig` に `secrets`（`RequestSecrets`）をネストする既存規約（`secrets.ts` の JSDoc）。`AppConfig` = `head.ts` が読む 6 フィールド、`@repo/core/config` の `content`
4. `IdentityTuning`（`reservationTtlMs` / `loginLockoutThreshold` / `loginLockoutBaseMs` / `loginLockoutMaxMs` / `loginAttemptDecayMs` / `resetRequestWindowMs` / `resetRequestWindowGraceMs`）の既定値（docs 12.2 / 12.4 の値を採るか）
5. `PasswordHasher` 実装: WebCrypto PBKDF2（docs `createPbkdf2PasswordHasher({ iterations })`）と iteration 数（Workers の CPU 予算内）

### (h) drizzle の扱い

既存 DO stores は全て `sql.exec` の生 SQL（`updateMatchedRow` で `RETURNING 1`）で、spec の CAS / 部分索引 / FTS5 特殊構文は drizzle で表現しにくい。drizzle は `adapters/d1/`（legacy `users`）だけ。

推奨: DO 側は生 SQL で統一。D1 一式（`adapters/d1/*`、`drizzle.config.ts`、`drizzle-orm` / `drizzle-kit` 依存、`wrangler.toml` の `[[d1_databases]]`、`vitest.config.d1.ts` と `vitest.config.integration.ts` の projects、root / web の `db:*` スクリプト、`worker-configuration.d.ts` の `DB`）を PH-01 で削除するか、触らず残すか。削除すると `pnpm test:integration` は DO プロジェクトだけになる。Pulumi の D1 リソースは対象外なので残してよい
