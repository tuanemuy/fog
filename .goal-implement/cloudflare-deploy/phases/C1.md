## 実装契約

### Workers entry

`apps/web/app/server.cloudflare.ts` は module Worker の `fetch` と `scheduled` を公開する。boot は remote client、UoW、Google identity、Email binding、fog services を isolate 内で再利用する。request container は AsyncLocalStorage で request scope に閉じる。schema migration は boot と request から実行しない。

`apps/web/app/serverHttp.ts` は health、Google callback、AI HTTP、TanStack rendering の順序を Node/Workers で共有する。Node entry は listener、signal、filesystem、SMTP、process timer を維持する。Cloudflare entry はそれらを import しない。

Cloudflare build は `apps/web/dist-cloudflare` を使う。Vite config は build 前にこの専用 directory だけを削除する。Node build artifact が Wrangler upload に混入しない。

### Remote libSQL

`packages/core/src/adapters/libsql/client.web.ts` は `@libsql/client/web` を直接 import する。Workers env とclient factoryは共通validatorを使う。URLはTLS既定の `libsql:`、`libsql:?tls=1`、`https:`、`wss:`だけを許可する。`http:`、`ws:`、`tls=0`、重複・未知query、URL内credential、fragment、local URLを拒否する。`DATABASE_AUTH_TOKEN` はtrim後non-emptyを必須とし、正規化値をclientへ渡す。`DATABASE_ENCRYPTION_KEY` は受理しない。

`FogUnitOfWorkProvider` は `read()` と `run()` を持つ。libSQL adapter は `transaction("read")` と `transaction("write")` を選ぶ。同じ repository contract を両 runtime で使う。

### KDF と login

scrypt は `N=32768, r=8, p=3, key length=64, maxmem=64 MiB` を維持する。Cloudflare runtime は `createBoundedSecretCrypto` で active KDF を1件に制限する。待機は2件までで、4件目は `CAPACITY_EXCEEDED`、`retryable: true`、HTTP 503になる。

dummy hash は有効な固定 scrypt hash である。未知 email の login も同じ verify 経路を通る。isolate boot は dummy hash を生成しない。

login は次の順序で処理する。

1. read transaction で user、credential hash、attempt state を取得する。
2. transaction を閉じて scrypt verify を実行する。
3. write transaction で同じ state を再取得する。
4. snapshot と一致する場合だけ session を保存するか、attempt を更新する。
5. 不一致は新しい snapshot と KDF で再試行する。

同時失敗2件の attempt count は2になる。同時の成功1件と失敗1件は、成功 session と認証失敗をそれぞれ返す。password reset による credential hash 変更も state 不一致になる。

### Retention と empty trash

`deleteTrashBatch` は1 transactionの変更行を合計100行、statementを最大9本に制限する。削除対象は `purging=1` へ移行し、source link、memo revision、document revision、document、memo、参照のないtopicの順に排出される。親は全従属行が0になるまで削除しない。処理途中の再実行は残った子行から継続し、active contentへ履歴欠損状態を復元しない。既存DBにはmigrationが `purging` 列を追加する。

`purging` は不可逆なillegal-transition境界である。DB CHECKは `purging=1` とactive状態の共存を拒否する。repository restoreは対象とtopic descendantをwrite transaction内で再検査し、競合を型付き `PURGE_IN_PROGRESS` または `OPTIMISTIC_LOCK_FAILURE` として返す。trash projectionは処理中項目を隠さず、topic descendantの処理中状態も親へ集約する。

topic groupはtarget hard delete、generic empty trash、retentionのいずれも、最初のbounded transactionでtopic root自身を `purging=1` にする。root marker用の行予算をchild処理より先に予約し、最後のchildを削除した境界でもmarkerを連続保持する。topic DELETEは共通の `purging=1 AND NOT EXISTS(document)` 経路だけを通る。target専用のrestorable topic直接DELETEは存在しない。

個別hard deleteも同じbounded protocolを使う。topicは同じdeletion groupのdocumentを子から排出し、先に個別削除されたdocumentを安全にdetachしてから、参照documentが0のときだけ親を削除する。呼出上限後は `EmptyTrashResult` のpartialを返す。UIはpartial、競合、例外の全経路でinvalidateし、処理中件数と「削除を続ける」を表示する。

retention はownerを25件ずつ読み、各ownerを最大4 transaction処理する。大きいbacklogは日次invocationで段階的に解消する。topicは参照documentが残る間は削除しない。

`emptyTrash` は最大40 transaction、最大4,000変更行を1 requestで処理する。戻り値は `{ status, deletedCount, remainingCount }` である。上限後に残件があれば `status: "partial"` を返し、完了済みbatchを保持する。UIはpartial successと例外の双方で必ず `router.invalidate()` を実行し、削除済み件数・残件数・再実行操作を表示する。処理中項目だけが残る場合も「空にする」を有効に保つ。
