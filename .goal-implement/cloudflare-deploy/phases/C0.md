# C0 Cloudflare 配備方式調査

## 結論

Cloudflare の本番実行基盤には Workers を使い、永続化は環境別の remote libSQL を使う。staging と production は Worker、DB、認証情報、公開 URL を分離する。

この方式は、現行の `LibsqlFogUnitOfWork` と全 repository を保つ。D1 への移行は約 1,600 行の repository と transaction 制御を作り直す。Durable Objects はさらに RPC とデータ配置を設計し直す。Containers はディスクが永続化せず、プロセス内 timer も sleep 中に動かない。いずれも今回の配備要件には不要である。

推奨構成は次のとおり。

| 項目 | staging | production |
| --- | --- | --- |
| Worker | `fog-staging` | `fog-production` |
| Custom Domain | `staging-fog.${domain}` | `fog.${domain}` |
| DB | staging 専用 remote libSQL | production 専用 remote libSQL |
| `APP_URL` | `https://staging-fog.${domain}` | `https://fog.${domain}` |
| 定期処理 | Cron Triggers | Cron Triggers |
| 復旧メール | Cloudflare Email Service の `send_email` binding | 同左 |
| リリース | `main` の検証済み SHA を自動配備 | Release Please PR の merge 後、同じ SHA を配備 |

Cloudflare Email Service は 2026-09-06 時点で Beta である。対象 account で Email Sending を利用できない場合だけ、`ResetMailer` の Workers adapter を Resend 等の HTTPS API に差し替える。SMTP と Nodemailer は Workers entry から読み込まない。

## 現行実装

### Runtime

fog は Node.js 22.12 以上の常駐 process を採用する。`apps/web/app/server.node.ts` が次を一つの process に持つ。

- TanStack Start の HTTP / RSC / SSR
- `/healthz` の DB readiness
- remote または file libSQL client
- 起動時 schema migration
- Google OAuth callback と AI client HTTP API
- 60 秒周期の trash retention runner
- 5 秒周期の reset mail runner
- SMTP mailer
- SIGINT / SIGTERM 時の drain

`packages/core/src/adapters/fog/unitOfWork.ts` は `client.transaction("write")` を使う。use case callback は transaction 中に read と write を交互に実行する。DB adapter の規模は次のとおり。

| 対象 | 行数 |
| --- | ---: |
| `accountRepository.ts` | 280 |
| `aiRepository.ts` | 234 |
| `contentRepositories.ts` | 395 |
| `dataRepository.ts` | 237 |
| `unitOfWork.ts` | 211 |
| 合計 | 1,357 |

schema と client を含む fog/libSQL adapter は約 1,600 行である。application 内には `unitOfWork.run` と transaction context の利用箇所が 139 個ある。

### Node 固有部分

| 機能 | Node 依存 | Workers での扱い |
| --- | --- | --- |
| request scope | `node:async_hooks` | Workers の Node compatibility で利用可能 |
| password / token crypto | `node:crypto`, `Buffer`, scrypt | Workers が scrypt を含む `node:crypto` を提供する。実 runtime 検証は必要 |
| DB | bare `@libsql/client` | Workers では `@libsql/client/web` を明示する |
| SMTP | Nodemailer | Workers 専用 `ResetMailer` adapter へ差し替える |
| 定期処理 | `setInterval` | `scheduled()` と Cron Triggers へ移す |
| migration | process boot + CLI | deploy workflow の CLI だけで直列実行する |
| local backup | `node:fs`, `VACUUM INTO` | Node 運用 CLI として残す。cloud DB は provider の PITR / export を使う |
| listener / signal | Node HTTP, SIGINT/SIGTERM | Workers では不要 |

現行 scrypt (`N=32768, r=8, p=3, maxmem=64 MiB`) はローカル実測で 188.9 ms、process の peak memory footprint は約 66 MiB だった。Workers Free の HTTP CPU 上限 10 ms では動かない。Workers Paid を前提とし、C1 で同時 login を含む workerd test を先に通す。

`createFogServices()` は初期化時に dummy password hash を毎 isolate 一度生成する。この scrypt は cold start の CPU と latency を増やす。既知の有効な dummy hash を設定または定数として読み、検証時だけ scrypt を実行する構成を C1 で検討する。register/login の password hashing 強度は変えない。

### Migration と backup

`migrateFog()` は idempotent な `CREATE TABLE/INDEX IF NOT EXISTS` と、旧 `fog_documents.topic_id NOT NULL` を直す table rebuild を含む。複数 isolate の初回 request から同時実行してはならない。各 deploy workflow が対象 DB の資格情報を渡して一度だけ実行し、Worker は request boot 時に migration しない。

ローカル backup は filesystem 上の SQLite に `VACUUM INTO` を実行する。remote libSQL の backup には使えない。`docs/backup_restore.md` は Turso PITR、新 DB への復元、固定 DB の dump、別保管 snapshot を既に定義する。staging / production の実 DB に対する復元訓練は未検証である。

## `_hollow` から再利用する設計

`_hollow` の commit `cb0cdf1` は Cloudflare D1 / R2 / Queues に配備されている。次の配備設計を fog に適用する。

- Release PR の merge で version tag と GitHub Release を作る。

- `wrangler deploy` の前に build と migration を実行する。

- secrets は environment ごとに分離する。
- `wrangler deploy --dry-run` を資格情報なしの検証に使う。

- D1 / Queues / R2 / relay / consumer は fog の要件に存在しない。

- `_hollow` は 2026-08-28 時点で `googleapis/release-please-action@v4` と Wrangler 4.90.1 を固定する。fog は導入時の現行 major を lockfile と workflow で固定する。
- `_hollow` の production workflow は `v*.*.*` tag push を別 workflow で受ける。fog は staging 成功後に Release Please を実行し、同じ workflow run の `release_created` output で production を開始する。この順序は release SHA が staging smoke を通ったことを保証する。

## 候補比較

| 候補 | transaction / correctness | 変更量 | 定期処理・mail | backup | 運用リスク | 判定 |
| --- | --- | ---: | --- | --- | --- | --- |
| Workers + remote libSQL | 現行 interactive UoW を保持 | 小 | Cron + mail adapter | Turso PITR / export | 外部 DB latency、scrypt resource | 採用 |
| Workers + D1 | `batch()` 用に UoW と全 repository を再設計 | 大 | Cron / Email binding | D1 Time Travel | transaction 回帰、migration 二重管理 | 不採用 |
| Workers + single SQLite DO | `transactionSync()` は強いが同期 repository / RPC が必要 | 大 | DO Alarm または Cron | DO PITR | 単一 object bottleneck、強い lock-in | 不採用 |
| Workers + per-user SQLite DO | owner 内 transaction は強い | 最大 | DO Alarm | object 単位 PITR | email uniqueness/login directory、export を再設計 | 不採用 |
| Cloudflare Containers + remote libSQL | Node runtime を多く保持 | 中 | sleep 中に timer 不動。Cron 経由が必要 | Turso PITR | cold start、非 atomic rollout、Paid、2026-08 時点で新しい基盤 | 不採用 |
| Containers + local SQLite | process 内 transaction | 中 | timer は sleep 中に不動 | 独自 | container disk は ephemeral | 禁止 |

### Workers + remote libSQL

`@libsql/client` 0.17.3 の package export は `workerd` condition を `lib-esm/web.js` に割り当てる。Turso 公式文書は edge/serverless で `@libsql/client/web` を使う。web client は HTTP/WebSocket remote URL と interactive transaction を提供し、file URL は扱わない。

Workers entry は remote URL のみを受理する専用 env schema を持つ。`file:` と `:memory:`、`DATABASE_ENCRYPTION_KEY` は Node entry に限定する。この境界で誤配備を拒否する。

remote libSQL の interactive write transaction は DB の writer lock を commit/rollback まで保持し、timeout は 5 秒である。Worker と DB の配置、1 use case 当たりの round trip 数、transaction latency を staging で計測する。高 latency が確認された場合は D1 へ急いで置き換えず、SQL statement 数と use case transaction を先に短くする。

### Workers + D1

D1 の `batch()` は statement 群を atomic に実行する。D1 は callback 形式の interactive SQL transaction を提供しない。次の fog 操作は read 後の分岐を同じ transaction に含むため、単純な adapter 置換にならない。

- email 重複確認後の user 作成
- login attempt と credential 検証後の session 作成
- revision/version 検査を含む memo/document 更新
- topic と document の集合復元
- retention owner と trash の走査後の削除
- reset mail claim / delivered / retry lease

D1 を採用するには、条件付き SQL、CTE、trigger、事前収集 command、または application contract の変更で各 use case の atomicity を証明し直す。今回の配備作業の範囲を超える。

### Durable Objects

SQLite-backed Durable Objects は `transactionSync()`、強整合 storage、Alarm、30 日 PITR を持つ。single DO は全 user の email uniqueness と cross-owner worker を保てるが、全 request を一つの single-threaded object に直列化する。per-user DO は水平分割できるが、email lookup、unique 制約、全 owner retention、data export の global index が別途必要になる。

DO は将来、remote DB を廃止して Cloudflare 内へデータを寄せる要求が出た場合の候補である。今回の初回配備には使わない。

### Containers

Containers は既存 Node server を image に入れられる。全 disk は ephemeral であり、local SQLite は system of record にできない。container sleep と rollout は Node 常駐 process の前提と一致しない。Cron / mail adapter / remote DB は結局外出しになるため、Workers より利点がない。

## 採用設計

### Runtime boundary

`apps/web/app/server.cloudflare.ts` は一つの module Worker として `fetch` と `scheduled` を公開する。

`fetch` は次を行う。

1. Workers env を Zod で検証する。
2. remote libSQL client、`LibsqlFogUnitOfWork`、crypto、Google identity、fog services を isolate 内で再利用する。
3. request ごとの `RequestContainer` を `AsyncLocalStorage` に設定する。
4. Google callback、health、AI API、TanStack Start entry を現行 Node entry と同じ順序で処理する。

共通 HTTP routing を pure function に抽出し、Node と Workers entry の分岐漏れを防ぐ。Node の filesystem、listener、signal、SMTP、timer は共通 module に入れない。

`scheduled` は `controller.cron` で処理を分ける。

- `* * * * *`: `dispatchResetEmails()`。配送遅延の上限は通常 1 分になる。
- `0 3 * * *`: `purgeExpiredTrash()`。時刻は UTC である。

reset mail の DB lease は重複 invocation を許容する。retention は再実行可能である。5 秒以内の配送が必須になった場合は Cloudflare Queues で transactional outbox を relay する別フェーズが必要になる。Cron を 5 秒 timer の代用にはしない。

### Mail

`CloudflareResetMailer` が `ResetMailer` を実装する。送信元 domain は Cloudflare Email Service に onboard し、Worker に `send_email` binding を与える。reset URL の origin/path 検証、秘密 payload の削除、lease/retry は現行 application code を保つ。

Cloudflare の structured email API は provider 側 `messageId` を返す。fog の outbox ID は `X-Fog-Message-ID` 等の許可された custom header に入れ、ログ相関に使う。custom header が account 設定で拒否される場合は header を外し、DB outbox ID と返却 `messageId` の対応だけを構造化ログへ出す。at-least-once 配送は保つ。

### Environment config

committed template と deterministic render script を source of truth にする。render script は `DOMAIN` と stage を受け取り、stage ごとの Wrangler config を ignored file として生成する。未展開 placeholder、不正な hostname、staging/production の同名 resource を拒否する。

Wrangler の `env.staging` と `env.production` は binding と vars が継承されないため、生成結果の両方に明記する。Worker 名、Custom Domain、`APP_URL` は stage ごとに固定する。実 `DOMAIN` がなくても example domain で C1/C2 の build、local runtime、dry-run を検証できる。実 account への deploy には repository variable `DOMAIN` の設定が必要である。

secret 値は Wrangler config と Git に置かない。local Cloudflare 開発は `.dev.vars` を使う。

### Delivery workflow

通常の `main` push は次の順序で処理する。

1. checkout 対象 SHA
2. frozen install
3. lint、format check、typecheck、unit/integration、Cloudflare build
4. staging DB migration
5. `fog-staging` deploy
6. `https://staging-fog.${domain}/healthz` smoke
7. Release Please の PR 更新
8. `release_created == true` の場合だけ production job を開始
9. GitHub `production` Environment の required reviewer 承認
10. production DB migration
11. 同じ checkout SHA から `fog-production` deploy
12. `https://fog.${domain}/healthz` smoke

Release PR 以外の main push では step 8 以降を実行しない。Release PR の merge commit は production より先に staging smoke を通る。production job は tag 名と `github.sha` の対応を記録する。

staging と production は別 concurrency group を使い、`cancel-in-progress: false` にする。migration と deploy の途中で別 run を重ねない。production の再実行は同じ tag/SHA を明示する `workflow_dispatch` input を持たせる。

Release Please が default `GITHUB_TOKEN` で作る PR は、GitHub の現在の仕様では CI 実行に手動承認が必要になる。自動 CI が必要なら、最小権限の GitHub App installation token または fine-grained PAT を `RELEASE_PLEASE_TOKEN` として使う。

## 資格情報と外部設定

### Cloudflare

- Workers Paid plan
- `${domain}` の active Cloudflare zone
- Custom Domain と衝突する既存 CNAME/DNS record がないこと
- staging / production Worker
- Email Service に onboard 済みの送信 domain、SPF、DKIM、bounce 設定
- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_API_TOKEN`
  - Account: Workers Scripts Write
  - Zone: Workers Routes Write
  - 対象 account と対象 zone だけに scope を限定

Wrangler が実際に要求する permission は初回 dry deploy の error と Cloudflare の permission-group API で再確認する。D1/R2/Queues permission は remote libSQL 方式には与えない。

### DB provider

- staging と production の別 database
- environment ごとの `DATABASE_URL`
- environment ごとの最小権限 `DATABASE_AUTH_TOKEN`
- PITR 保持期間、region、容量、監視、復元手順
- migration 用 token と runtime token を分離できる場合は分離

### GitHub

- `staging` Environment
- `production` Environment と required reviewers
- environment secret: `CLOUDFLARE_API_TOKEN`
- environment secret/var: `CLOUDFLARE_ACCOUNT_ID`
- environment secret: `DATABASE_URL`, `DATABASE_AUTH_TOKEN`
- environment secret: `FOG_GOOGLE_CLIENT_SECRET`
- environment var/secret: `FOG_GOOGLE_CLIENT_ID`
- environment var: `FOG_AI_CLIENTS`
- repository secret: `RELEASE_PLEASE_TOKEN`。GitHub App token を優先
- repository var: `DOMAIN`

Cloudflare Worker の runtime secrets は environment ごとに投入する。GitHub environment secret を build log や generated config に書かない。

### Google / client registration

- staging callback: `https://staging-fog.${domain}/auth/google/callback`
- production callback: `https://fog.${domain}/auth/google/callback`
- AI client redirect URI は各 environment の client ID とともに明示登録
- cookie は HTTPS、host-only、stage 間で共有しない

## リスクと gate

| リスク | 影響 | gate / 対策 |
| --- | --- | --- |
| scrypt が 128 MB isolate で同時実行時に不足 | register/login の 1102 | C1 最初に workerd concurrency test。Paid CPU limit を明示。強度は無断で下げない |
| remote libSQL transaction が 5 秒 timeout | 高 latency / busy error | staging で p95 と rollback を計測。transaction 内 I/O を DB 以外へ増やさない |
| Email Service Beta が account で使えない | reset mail 不通 | C2 前に onboarding を確認。不可なら HTTPS mail adapter へ差し替え |
| Cron は最短 1 分 | Node の 5 秒配送より遅い | 1 分を受け入れる。5 秒 SLA が必要なら Queue/outbox relay を追加 |
| migration が旧 Worker と非互換 | deploy 中断・rollback 不能 | expand/contract migration、staging、PITR bookmark/backup、直列 deploy |
| Release Please token に過大権限 | repository 改変 | GitHub App または fine-grained PAT、対象 repo 限定、rotation |
| custom domain の既存 DNS と衝突 | 初回 deploy 失敗 | 事前 inventory。Custom Domain を Wrangler だけで管理 |
| staging と production の secrets 混線 | data 漏えい | GitHub Environments、別 DB/token、config invariant test |
| global isolate cache が別 env を保持 | 誤 DB 接続 | stage ごとに別 Worker。env を引数で boot cache に結び付ける test |
| cloud DB backup が未検証 | 復旧不能 | production 前に別 DB への restore drill を実行 |

## Manager が確定する判断

1. 実 deploy 前に `${domain}` の実値。
2. Workers Paid plan を使うこと。
3. reset mail の最大 1 分遅延を受け入れること。
4. Cloudflare Email Service Beta を使えること。使えない場合の HTTPS mail provider。
5. remote libSQL の staging / production database を新規作成するか、既存を使うか。
6. production GitHub Environment の required reviewer。
7. Release Please 用に GitHub App token、fine-grained PAT、手動承認付き `GITHUB_TOKEN` のどれを使うか。

1 と外部 account に依存しない C1 実装と local verification は先行できる。3、4 は mail adapter の acceptance に必要である。
