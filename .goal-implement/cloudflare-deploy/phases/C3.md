## 実装

### main から staging

- `.github/workflows/cloudflare-delivery.yml` は `push.main` と引数必須の `workflow_dispatch` だけを受理する。tag push、pull request、release PR 作成では起動しない。
- main push は `Verify release candidate` で frozen pnpm install、lint、format、typecheck、全 test、Node build を完了してから `Deploy staging` へ進む。
- staging job は `environment: staging`、job concurrency `fog-staging`、`cancel-in-progress: false` で直列化する。full `github.sha` を checkout/config `DEPLOYMENT_SHA`/provenance/health に一貫して使用する。
- config render → Cloudflare build/provenance → Wrangler dry-run → staging deployment record `in_progress` → migration → secret sync → deploy → HTTPS smoke → deployment `success` の順である。失敗時は作成済み deployment を `failure` にする。
- runtime `/healthz` は DB `SELECT 1` 成功後に `status`、`deploymentSha`、`deploymentEnv`、`databaseIdentity` を no-store JSON で返す。smoke は独立した `DOMAIN` authorityからstage originを生成し、ASCII・exact URL/hostだけを許可する。suffix/subdomain/trailing-dot/IDN/credential/port driftを拒否し、10秒/request、既定18回・5秒間隔で4項目すべてを照合する。応答本文は失敗表示へ反映しない。

### Release Please と production

- staging job が成功した後だけ root component の Release Please v5 を実行する。root `release_created`、`tag_name`、`sha` を正規化した job outputs とし、release 作成時は `sha === staged SHA` を必須にする。
- `release_created == true` のときだけ `Validate production release publicly` が起動する。この job は Environment、environment vars/secrets、production secrets を参照せず、GitHub token の read 権限だけで検証する。
- 公開検証は GitHub Release が非 draft・非 prerelease、tag が最大5段の peel 後に指定 commit、commit が main ancestorであることを照合する。deployments/statuses/workflow-attempt jobsは100件/page、最大10 pageのsame-origin・same-endpoint paginationで全件検査し、最新deploymentとその最新statusだけをauthorityにする。payloadのrun/SHA/workflow/attempt、runのrepository/main push、exact `Deploy staging` job一意性/SHA/success、GitHub Actions bot creatorも必須であり、unrelated jobは許可する。
- `Deploy production` だけが `environment: production` と required secrets を参照する。job concurrency は `fog-production`、cancel=false。approval 後にも Release ID/update time、tag object SHA、最新deployment/status、run/attempt/jobを再取得し、公開検証 outputと完全一致しなければmigration前に停止する。同一 SHA を明示 checkoutして、render → build/provenance → dry-run → migration → secret sync → deploy → smoke を実行する。
- runtime secrets は install/checkout/build job scopeへ置かず、render の `DATABASE_URL` と side-effect 3 step の完全な C2 secret setだけに step scopeで渡す。migration/secret/deploy は各再実行時に C2 common preflightを再実行する。production approval 前の jobには `secrets.*` が存在しない。

### recovery

- `workflow_dispatch` は `release_tag` と full `release_sha` の両方を要求する。入力 SHA は checkout や shellへ渡す前に、default branchの信頼済み validatorから GitHub APIで検証する。
- Release、peeled tag、main ancestry、successful staging deployment、payload run、workflow path、repository/head repository、main push、staging job successの全条件を通常 release経路と同じ関数で検査する。不一致は production Environment評価前に停止する。
- validation後も production approval 後に再検証し、release mutation、tag移動、新しいdeployment/status、run attempt変化を fail closedにする。production partial failure は同じ release tag/SHAの再 dispatchだけが回復経路となる。

### permissions と secret 契約

- 全 action ref を40桁 SHAへ固定した。`permissions: {}` を workflow defaultとし、job単位に contents/actions/deployments/pull-requests/issues のread/write最小権限だけを付与した。既存 CI も immutable pin、persist-credentials=false、default permissions空へ更新した。
- Release Please token は `RELEASE_PLEASE_TOKEN || github.token`。default tokenで root release PR/Releaseを作れる構成であり、追加 tokenは branch policyや既定 tokenでは不足する組織設定のときだけ repository secretとして使う。Release Please自身が作ったイベントが通常 workflowを再起動しない制約は、release PRを人が mergeした main pushを起点とするため production迂回にならない。
- staging/production Environment variablesは `DOMAIN`、`DATABASE_IDENTITY`、初回のみ `DATABASE_IDENTITY_BOOTSTRAP`。required secretsは `DATABASE_URL`、`DATABASE_AUTH_TOKEN`、`FOG_GOOGLE_CLIENT_ID`、`FOG_GOOGLE_CLIENT_SECRET`、`CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`、optional secretは `FOG_AI_CLIENTS`。両stageでkey setは同一、value scopeは別 Environmentである。
- `DEPLOYMENT_ENV`、`DEPLOYMENT_SHA`、`APP_URL` は workflow/stageから決定し、OAuth callback、sender、worker名、routeは C2 config rendererが決定する。

根拠は GitHub の [Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)、[deployment status API](https://docs.github.com/en/rest/deployments/statuses?apiVersion=2026-03-10)、[workflow run API](https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2026-03-10)、[workflow job API](https://docs.github.com/en/rest/actions/workflow-jobs?apiVersion=2026-03-10)、[Release Please outputs](https://github.com/googleapis/release-please-action#outputs) である。Environment secretsは required reviewer承認前に jobから利用できず、deployment statusは最新状態が現状態、workflow job responseは `head_sha/name/conclusion` を提供するという公式契約を採用した。
