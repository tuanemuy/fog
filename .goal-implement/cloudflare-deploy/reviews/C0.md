# C0 独立レビュー

## 判定

**FAIL（方式は成立するが、C0 を設計確定として受け入れるには修正が必要）**。

Workers + remote libSQL、`fetch` + Cron、Cloudflare Email Service、`main` → staging + Release Please → production という大枠は、現行 fog と 2026-09-06 時点の公式仕様に対して成立する。D1 へ fog repository を全面移植するより変更量が小さいという選択も妥当である。

ただし、現行の scrypt と libSQL write transaction の組み合わせには、C0 報告が gate として挙げるだけでは足りない具体的な不成立条件がある。`login()` は scrypt 検証中も remote libSQL の writer lock を保持する。scrypt は同一 Node process で 3 件同時に実行すると独立実測で最大 RSS 137,822,208 bytes となり、Workers の isolate 上限 128 MB と同じ数値域を超えた。Node process RSS と Workers isolate accounting は同一ではないため本番超過の直接証明ではないが、無制限 concurrency を安全と扱えない十分な反証である。Workers Paid は CPU 上限を解決するが、memory 上限は Free/Paid とも 128 MB のままである。C1 は「テストして問題なら検討」ではなく、KDF の同時実行数と待ち行列を制限し、CPU 処理を remote write transaction の外へ出して認証状態を安全に再検査する設計を必須とする。

また Release Please の production 判定には、`release_created` だけでなく action の `sha` を引き渡し、その SHA を checkout・tag と照合して配備する必要がある。`github.sha` と同じであることを暗黙に仮定しない。

## 必須修正

### 1. scrypt と write transaction を分離する

`packages/core/src/application/fog/services.ts:67-93` は `unitOfWork.run()` の内側で `verifyPassword()` を待つ。`packages/core/src/adapters/fog/unitOfWork.ts:152` は callback 開始前に `transaction("write")` を開始する。この組み合わせは remote DB latency と無関係に約 0.2 秒以上 writer lock を延長し、別 isolate の login と通常 write も競合させる。

C1 の完成条件へ次を追加する。

- credential/attempt の読み取りと scrypt を write transaction 外で行う。
- 成功時の session 作成、失敗時の attempt 更新では、読み取った状態を transaction 内で再検査するか conditional SQL を使い、rate limit と session 発行の競合安全性を維持する。
- remote libSQL で「同一 email の同時成功/失敗 login」と「login と通常 write」の競合を実測する。
- `SQLITE_BUSY` retry は 10/20/40 ms 固定のまま採用せず、provider の error code と retry-after/timeout を実 runtime で確認する。

### 2. scrypt concurrency を設計で制限する

`packages/core/src/adapters/fog/crypto.ts:4-15` の設定値を無断で弱める必要はない。ただし同一 isolate での KDF 同時実行を制限し、無制限に待機 request を蓄積させない admission policy が必要である。

- まず workerd で 1/2/3 件の hash/verify concurrency と memory/CPU/error を測る。
- safe concurrency を 1 とする保守的な実装、短い bounded queue、過負荷時の明示的な再試行可能 error を候補とする。
- Cloudflare 実環境で 3 件以上の同時 register/login を再検証する。local workerd 成功だけで production memory 安全性を確定しない。
- isolate boot の dummy hash は事前生成した有効 hash を secret ではない定数として固定し、起動ごとの KDF を除くという C0 提案を採用する。

### 3. 長い UoW を分割する

`purgeExpiredTrash()` は全 owner と trash を一つの write transaction で走査する。interactive transaction の 5 秒上限に対してデータ量依存で失敗するため、owner/page ごとの bounded transaction に分割する。`emptyTrash()` 等の集合操作も statement 数と最大データ量を確認し、5 秒以内を観測値だけでなく構造上 bounded にする。

### 4. production は Release Please の SHA を配備する

Release Please job から少なくとも `release_created`、`tag_name`、`sha` を job outputs にする。production job は `actions/checkout` の `ref` に `needs.<job>.outputs.sha` を指定し、tag がその SHA を指すこと、必要ならその SHA が当該 run の staging smoke 対象 SHA と一致することを検証してから migration/deploy する。

root component 以外の manifest 構成を採用する場合は `release_created` の名前が path prefix 付きになる。今回 root component とすることを Release Please config と workflow test で固定する。

### 5. Release Please の部分成功から復旧可能にする

Release Please は release/tag 作成後の後続処理失敗で action step 全体が failure になり、downstream output consumer が skipped になる既知の報告がある。C0 の `workflow_dispatch` 復旧経路は残し、入力 tag/SHA の GitHub Release 対応、main 到達性、staging 成功記録を検査する。任意の SHA を production に投入できる dispatch にしない。
