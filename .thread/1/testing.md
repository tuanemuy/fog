## 確認環境

このIssueの変更を確認するために必要な手順のみ記載する。ターゲットランタイムは **Node + libSQL**（`pnpm dev` / `pnpm db:migrate` の既定。→ plan.md ADR-004）。

### 環境変数の準備

`apps/web/.env` はテンプレート由来のものが既に存在し、`DATABASE_URL=file:./data/app.db` と `APP_URL=http://localhost:3000` が入っている（`apps/web/.env.example` と同じ内容）。**本 Issue で `SESSION_SECRET` を新設する**（plan.md ステップ11）ので、`apps/web/.env` に1行追記する。値は32文字以上。

```
SESSION_SECRET=local-dev-session-secret-please-change-me
```

既定のままなら `http://localhost:3000` で待ち受ける（`PORT` 未設定時の既定は 3000）。

### 検証環境の起動

```bash
# 1. ローカル DB を作り直す
#    本 Issue は初期マイグレーションを todos 抜きで再生成する（plan.md ステップ7）ため、
#    テンプレート時代の app.db をそのまま使うと既存テーブルと衝突する
rm -f apps/web/data/app.db apps/web/data/app.db-shm apps/web/data/app.db-wal

# 2. マイグレーション適用（= tsx apps/web/scripts/migrate.node.ts）
pnpm db:migrate

# 3. 開発サーバー起動（= vite dev --config vite.config.node.ts）
pnpm dev
```

起動後 `http://localhost:3000` を開く。

### シードデータ

**不要。** 本スライスは `/signup` から自分でユーザーを作れる。ただし `spec/manual-tests/account.md` の多くの TC が `test@example.com` / `password123` の存在を前提にしているので、**確認項目1〜2（登録）を先に実行し、その中で `test@example.com` / `password123` を作る**。SSO テスト用アカウント・開発用メールボックス（Mailpit 等）は本スライスでは不要（SSO / パスワードリセット本体が対象外のため）。

### デプロイ方法

**なし。** 本 Issue の確認はローカルの Node ランタイムで完結する。fog はまだどの環境にもデプロイされておらず（plan.md ADR-001 / ADR-004）、`pnpm deploy:staging` 系（Cloudflare）・`pnpm deploy:aws:staging`（CDK）は本 Issue の確認手順に含めない。

### 対象外（確認しないこと）

`spec/manual-tests/account.md` のうち、**SSO 関連（TC-03 / 04 / 17 / 18 / 21 / 33）・OAuth 認可関連（TC-07〜09 / 24〜28）・パスワードリセット本体（TC-10 / 29〜31 / 37）・パスワード変更（TC-11 / 32）は本スライスの対象外**（plan.md スコープ節）。また **TC-01 の確認ポイントのうち「SSOボタンが表示されている」も対象外** — 本スライスは SSO 未実装のため、動かないボタンを意図的に描画しない（plan.md スコープ節 / ステップ25）。`spec/manual-tests/account.md` の「事後処理（TC-11 でパスワードを戻す）」も実行不能なので行わない。

## 確認項目

### 1. 未ログインでトップにアクセスするとログイン画面に誘導される

- **対応する受け入れ基準:** AC-9（manual TC-01）
- **目的:** 未ログイン状態のエントリーポイントが `/login` になり、認証必須レイアウトの先回りリダイレクトが効くことを確認する
- **手順:**
  1. シークレットウィンドウで `http://localhost:3000/` を開く
  2. アドレスバーの URL と画面を確認する
- **期待結果:** `/login` へリダイレクトされ、見出し「ログイン」・「メールアドレス」入力欄・「パスワード」入力欄・送信ボタン「ログイン」・「アカウント登録」リンク・パスワードリセットへのリンク（「パスワードを忘れた」等）が表示される
- **確認ポイント:** SSO ボタン（「Google で続ける」等）が**表示されないこと**（本スライスでは意図的に描画しない）。タイムラインの中身が一瞬でも見えないこと

### 2. `/signup` でメール＋パスワード登録ができ、タイムラインへ遷移する

- **対応する受け入れ基準:** AC-12 / AC-3（manual TC-02）
- **目的:** 登録 → セッション発行 → 認証後シェルの導線が end-to-end で成立することを確認する
- **手順:**
  1. `/login` で「アカウント登録」リンクを押す（URL が `/signup` になる）
  2. 「メールアドレス」欄に `test@example.com`、「パスワード」欄に `password123` を入力する
  3. 送信ボタン「登録する」を押す
  4. 遷移後、ブラウザを再読み込み（F5）する
- **期待結果:** 送信中はボタンが無効化され進行表示が出る。完了後 `/`（タイムライン）へ遷移し、空状態のタイムラインとグローバルナビが表示される。再読み込みしてもログイン状態が維持され `/login` へ戻されない
- **確認ポイント:** 再読み込み後もログイン状態であること（= Cookie が `HttpOnly` で保存され、`SESSION_SECRET` による署名検証が通っていること）。DevTools の Application → Cookies でセッション Cookie に `HttpOnly` / `SameSite=Lax` / `Path=/` が付いていること

### 3. `/login` でメール＋パスワードログインができる

- **対応する受け入れ基準:** AC-10（manual TC-05）
- **目的:** `loginWithPassword` → セッション発行 → タイムライン遷移を確認する
- **手順:**
  1. 確認項目2でログイン済みなので、まず `/settings` を開き「ログアウト」を押す
  2. `/login` で「メールアドレス」欄に `test@example.com`、「パスワード」欄に `password123` を入力する
  3. 送信ボタン「ログイン」を押す
- **期待結果:** 送信中はボタンが無効化され、完了後 `/`（タイムライン）へ遷移する
- **確認ポイント:** 送信中に連打してもエラーにならないこと

### 4. ログアウトすると `/login` に戻り、以後保護画面にアクセスできない

- **対応する受け入れ基準:** AC-15（manual TC-06 / TC-23）
- **目的:** セッション破棄と、破棄後の保護画面アクセス不能（履歴・キャッシュ経由も含む）を確認する
- **手順:**
  1. ログイン済みの状態でグローバルナビの「設定」を押す（`/settings`）
  2. 「ログアウト」を押す
  3. ブラウザの戻るボタンを押す
  4. アドレスバーに `http://localhost:3000/` を直接入力して開く
- **期待結果:** 手順2で `/login` へ遷移する。手順3では保護画面の操作可能な状態に戻れない（`/login` へ誘導される。一瞬キャッシュ表示された場合も操作するとログイン画面へ誘導される）。手順4も `/login` へリダイレクトされる
- **確認ポイント:** 履歴に保護画面が残らないこと（ログアウト遷移が `replace` であること）。DevTools の Cookies でセッション Cookie が消えている（`Max-Age=0` で失効している）こと

### 5. 未ログインで保護 URL に直アクセスするとログイン後に元の URL へ戻る

- **対応する受け入れ基準:** AC-9（manual TC-22）
- **目的:** `?redirect=` による復帰経路を確認する
- **手順:**
  1. ログアウト状態でアドレスバーに `http://localhost:3000/settings` を直接入力して開く
  2. 遷移先の URL を確認する
  3. 「メールアドレス」欄に `test@example.com`、「パスワード」欄に `password123` を入力して「ログイン」を押す
- **期待結果:** 手順1で `/login?redirect=/settings` へ誘導され（設定画面の中身は表示されない）、手順3のログイン後は**タイムラインではなく `/settings`** へ戻る
- **確認ポイント:** URL に `?redirect=/settings` が付いていること。`/trash` など別の保護 URL でも同じ挙動になること

### 6. グローバルナビの全項目から遷移でき、現在地が示される

- **対応する受け入れ基準:** AC-14（PAGE-common-001）
- **目的:** 認証後の全画面が共通シェルを共有し、5項目すべてが実在するルートへ遷移することを確認する
- **手順:**
  1. ログイン状態で `/` を開く
  2. ナビの「タイムライン」「トピック」「検索」「ゴミ箱」「設定」を順に押し、都度 URL と画面を確認する
- **期待結果:** それぞれ `/`・`/topics`・`/search`・`/trash`・`/settings` へ遷移し、404 やエラー画面にならない（`/topics` `/search` `/trash` はプレースホルダー表示で可）。遷移先の項目に現在地表示（`aria-current="page"` と視覚的な強調）が付く
- **確認ポイント:** どの画面でもナビが同じ位置に出ていること（シェルがリーフに含まれず崩れないこと）。押しても何も起きない項目が無いこと

### 7. `/settings` に現在のユーザー情報が表示される

- **対応する受け入れ基準:** AC-15（UC-identity-013）
- **目的:** `getCurrentUser` の実呼び出し地点が動き、資格情報を露出しないことを確認する
- **手順:**
  1. ログイン状態で `/settings` を開く
- **期待結果:** ログイン中のメールアドレス（`test@example.com`）と認証方式（パスワード）が表示され、「ログアウト」の項目がある
- **確認ポイント:** パスワードハッシュ・平文パスワード・SSO 主体 ID の類が画面にも HTML ソース（DevTools の Elements / ページのソース）にも現れないこと

### 8. 認証画面どうしの導線がすべて機能する

- **対応する受け入れ基準:** AC-11 / AC-13（PAGE-login-004 / 005・PAGE-signup-004）
- **目的:** プレースホルダーを含むリンク先がすべて実在し、押して何も起きないコントロールが無いことを確認する
- **手順:**
  1. ログアウト状態で `/login` を開き、「アカウント登録」リンクを押す
  2. `/signup` で「ログイン」リンクを押す
  3. `/login` でパスワードリセットへのリンク（「パスワードを忘れた」等）を押す
  4. 遷移先から `/login` への戻り導線を押す
- **期待結果:** 手順1で `/signup`、手順2で `/login`、手順3で `/password-reset`（「準備中」の表示と `/login` への戻り導線）、手順4で `/login` に遷移する
- **確認ポイント:** `/password-reset` が 404 にならないこと。リセットフォーム自体は本スライス対象外なので「準備中」表示で正しい

### 9. レスポンシブ（PC はサイドバー / モバイル幅は下部シート）

- **対応する受け入れ基準:** AC-14 / AC-18
- **目的:** 承認済みデザイン（`spec/design/pages/timeline.html`）どおりに幅で表示形態が切り替わることを確認する
- **手順:**
  1. ログイン状態で `/` を開き、ブラウザ幅を 1280px にする
  2. 幅を 375px にする（DevTools のデバイスツールバー）
  3. 375px の状態でヘッダーの「メニュー」ボタンを押す
  4. 開いたナビから「設定」を押す
- **期待結果:** 1280px（>= 1024px）では常設サイドバーにナビ5項目が並ぶ。375px ではサイドバーが消え、ヘッダーに「メニュー」ボタンが出る。押すと下部シートのナビが開き、5項目から遷移できる
- **確認ポイント:** 横スクロールが発生しないこと。フォーム（`/login` / `/signup`）も 375px で崩れないこと

## エッジケース・異常系

### 1. 登録済みメールでの登録は重複エラーになり、ログインへの導線が出る

- **対応する受け入れ基準:** AC-12（manual TC-14）
- **目的:** `EMAIL_ALREADY_REGISTERED` の日本語表示とログイン導線を確認する
- **手順:**
  1. ログアウト状態で `/signup` を開く
  2. 「メールアドレス」欄に登録済みの `test@example.com`、「パスワード」欄に `password123` を入力して「登録する」を押す
  3. 表示されたログインへの導線を押す
- **期待結果:** メールアドレス欄付近に「このメールアドレスは登録済みです」（登録済みである旨）が表示され、登録されない。ログイン画面への導線が示され、押すと `/login` へ遷移する
- **期待結果（追加）:** 英語の生メッセージ（`EMAIL_ALREADY_REGISTERED` / `UNIQUE_VIOLATION` 等）が画面に出ないこと

### 2. 弱いパスワード（7文字）でエラーになり、8文字なら登録できる

- **対応する受け入れ基準:** AC-12（manual TC-34）
- **目的:** Issue「検証」節が名指しする「弱パスワードのエラー表示」を確認する
- **手順:**
  1. ログアウト状態で `/signup` を開く
  2. 「メールアドレス」欄に未登録の `boundary1@example.com`、「パスワード」欄に7文字の `abcd123` を入力して「登録する」を押す
  3. 「パスワード」欄をちょうど8文字の `abcd1234` に直して「登録する」を押す
- **期待結果:** 手順2で**パスワード欄の直下**に「パスワードは8文字以上128文字以下で入力してください」が表示され、登録されない。手順3では登録が成功し `/` へ遷移する
- **期待結果（追加）:** 手順2のエラーがフォーム上部の汎用エラーではなく**項目ごとの表示**であること

### 3. メールアドレスの形式不正でエラーになる

- **対応する受け入れ基準:** AC-12（manual TC-13）
- **目的:** `IDENTITY_INVALID_EMAIL` の日本語表示と、エラー後のリトライ可能性を確認する
- **手順:**
  1. ログアウト状態で `/signup` を開く
  2. 「メールアドレス」欄に `invalid-email`（`@` なし）、「パスワード」欄に `password123` を入力して「登録する」を押す
  3. 「メールアドレス」欄を `local@`（ドメインなし）に変えて「登録する」を押す
  4. 「メールアドレス」欄を未登録の `new-user+tc13@example.com` に直して「登録する」を押す
- **期待結果:** 手順2・3ともメールアドレス欄の直下に「メールアドレスの形式が正しくありません」が表示され、登録されない。手順4では登録が成功し `/` へ遷移する（エラー後に入力値が保持され、修正して再送信できる）

### 4. 必須項目が未入力だとエラーになる

- **対応する受け入れ基準:** AC-12（manual TC-12）
- **目的:** transport 境界のスキーマ検証が項目ごとに表示されることを確認する
- **手順:**
  1. ログアウト状態で `/signup` を開く
  2. 「メールアドレス」欄を空のまま、「パスワード」欄に `password123` を入力して「登録する」を押す
  3. 「メールアドレス」欄に `new-user+tc12@example.com` を入力し、「パスワード」欄を空にして「登録する」を押す
- **期待結果:** 手順2はメールアドレス欄に、手順3はパスワード欄に必須エラーが表示され、いずれも登録されない
- **確認ポイント:** エラー表示後も入力済みの値が保持されていること

### 5. メールアドレスの正規化（前後空白・大文字）が効く

- **対応する受け入れ基準:** AC-12（manual TC-16）
- **目的:** trim + 小文字化が登録・ログイン・重複検出のすべてに一貫して効くことを確認する
- **手順:**
  1. ログアウト状態で `/signup` を開き、「メールアドレス」欄に `  New-User2@Example.COM  `（前後に半角スペース・大文字混在）、「パスワード」欄に `password123` を入力して「登録する」を押す
  2. `/settings` からログアウトし、`/login` で「メールアドレス」欄に小文字の `new-user2@example.com`、「パスワード」欄に `password123` を入力して「ログイン」を押す
  3. `/settings` からログアウトし、`/signup` で「メールアドレス」欄に `NEW-USER2@EXAMPLE.COM`、「パスワード」欄に `password123` を入力して「登録する」を押す
- **期待結果:** 手順1は登録成功して `/` へ遷移。手順2はログインできてタイムラインが表示される。手順3は正規化後の比較で重複が検出され、登録済みエラーが表示される
- **確認ポイント:** `/settings` に表示されるメールアドレスが小文字・空白なしの `new-user2@example.com` になっていること

### 6. ログイン失敗時に原因を明かさない同一メッセージが出る

- **対応する受け入れ基準:** AC-10（manual TC-19 / TC-20）
- **目的:** パスワード誤り・未登録メール・形式不正がすべて同一メッセージに潰れることを確認する
- **手順:**
  1. ログアウト状態で `/login` を開き、`test@example.com` / `wrongpassword` で「ログイン」を押し、表示メッセージを控える
  2. 未登録の `no-such-user@example.com` / `password123` で「ログイン」を押し、メッセージを比較する
  3. 形式不正の `invalid-email` / `password123` で「ログイン」を押し、メッセージを比較する
  4. `test@example.com` / `password123` に直して「ログイン」を押す
- **期待結果:** 手順1〜3のすべてでフォーム上部に**まったく同じ文言**「メールアドレスまたはパスワードが正しくありません」が表示される。「ユーザーが存在しません」「パスワードが違います」等の区別できる文言や、メール形式に固有のエラーが出ない。手順4ではログインできる
- **確認ポイント:** 3ケースの文言・表示位置が完全に一致すること（クライアント側の形式チェックで手順3を送信前に弾く実装の場合は、そのエラーが登録有無を示さないことを確認する）

### 7. 登録ボタンの連打で二重登録されない

- **対応する受け入れ基準:** AC-12（manual TC-15）
- **目的:** 送信中のボタン無効化で二重送信が防止されることを確認する
- **手順:**
  1. ログアウト状態で `/signup` を開き、未登録の `new-user+dup@example.com` / `password123` を入力する
  2. 「登録する」を素早く3回以上連打する
- **期待結果:** 送信中はボタンが無効化され、登録は1回だけ実行されて `/` へ遷移する。重複エラー等は表示されない

### 8. パスワード最大長の境界（129文字 / 128文字）

- **対応する受け入れ基準:** AC-12（manual TC-35）
- **目的:** transport スキーマの上限を 1024 に緩めた判断（129文字が `validation` ではなくドメインの `PasswordTooWeak` として項目直下に出る）を UI で確認する
- **手順:**
  1. ログアウト状態で `/signup` を開き、未登録の `boundary2@example.com` と `a` を129個並べたパスワードを入力して「登録する」を押す
  2. パスワードを `a` 128個に直して「登録する」を押す
  3. `/settings` からログアウトし、`/login` で `boundary2@example.com` と `a` 128個でログインする
- **期待結果:** 手順1は**パスワード欄の直下**に「パスワードは8文字以上128文字以下で入力してください」が表示され登録されない。手順2は登録成功して `/` へ遷移。手順3はログインできる
- **確認ポイント:** 手順1のエラーが「入力形式が不正です」のような transport 由来の汎用文言になっていないこと

### 9. メールアドレス最大長の境界（321文字 / 320文字）

- **対応する受け入れ基準:** AC-12（manual TC-36）
- **目的:** email 側の上限も同様にドメイン側のエラーとして出ることを確認する
- **手順:**
  1. ログアウト状態で `/signup` を開き、全体が321文字になる形式上有効なメールアドレス（ローカル部を `a` の繰り返しで調整した `aaa...a@example.com`）と `password123` を入力して「登録する」を押す
  2. メールアドレスをちょうど320文字に調整して「登録する」を押す
- **期待結果:** 手順1はメールアドレス欄の直下に形式エラー（「メールアドレスの形式が正しくありません」）が表示され登録されない。手順2は登録成功して `/` へ遷移する

### 10. `SESSION_SECRET` 未設定・不正時の起動時エラー

- **対応する受け入れ基準:** AC-17（plan.md ステップ11の「秘密鍵の検証は `createXxxRequestContainer` で行う」）
- **目的:** 秘密鍵の欠落が黙って通らないことを確認する
- **手順:**
  1. `pnpm dev` を停止し、`apps/web/.env` の `SESSION_SECRET` を短い値（例: `short`）に変更する
  2. `pnpm dev` を起動して `http://localhost:3000/login` を開く
  3. `SESSION_SECRET` を32文字以上に戻し、`pnpm dev` を再起動する
- **期待結果:** 手順2でリクエスト処理時に明確なエラー（サーバーログに秘密鍵の長さ不足を示す例外）になり、**セッションが不正な鍵で発行されてしまうことはない**。手順3で正常に戻る
- **確認ポイント:** エラーメッセージに秘密鍵の値そのものが出力されないこと

### 11. セッション Cookie の改ざん

- **対応する受け入れ基準:** AC-15 / AC-9
- **目的:** HMAC 署名検証が効き、改ざんされたトークンで保護画面に入れないことを確認する
- **手順:**
  1. ログイン状態で `/` を開く
  2. DevTools の Application → Cookies でセッション Cookie の値の末尾数文字を書き換える
  3. `/settings` を再読み込みする
- **期待結果:** `/login` へリダイレクトされる（改ざんトークンは検証に失敗し `null` 扱いになる）。500 エラー画面やスタックトレースは出ない
