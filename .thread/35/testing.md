## エッジケース・異常系

### 1. commit 前に検証して AC-17 が空振りで通る

`git diff --name-status main...HEAD` は commit していなければ空になり、確認項目14 の手順1 が「0 行」で通ってしまう。**必ず commit 後に実行し、手順2 の一覧が実際の変更を列挙していることを目で見る。**

### 2. `V-3` の除外が外れる / 効きすぎる

`spec/index.md` の ADR 一覧表のセルを組み替えると、除外パターン（`^spec/index\.md:[0-9]*:| \[005\]`）が一致しなくなり `V-3` が 1 行残る。逆に、**同じ形の行を新たに増やす**（`| [005](...)` で始まる行を別の表に作る）と、その行も一緒に射程から外れる。確認項目9 の手順2 で「ファイル名の残存が1行だけ」を測っているのはこのためで、**`V-3` が 0 行でも手順2 が 2 行以上なら失敗である。**

### 3. 新しく書いた文言が `V-1` に当たる

設計 第7.1節の「同一の**埋め込み** SQLite」をそのまま写すと、正しい記述が `V-1` のベクトル残存として検出される。**このときヒット行を消すのではなく「DO 内蔵の SQLite」へ言い換える**（adr.md ADR-016）。`V-1` の走査語のほうは変更しない — 語形の揺れた既存の残骸を取りこぼすためである。

### 4. 着手前から期待値を満たしている検査を「通った」と読む

- **`P-8`（期待 0 / 着手前 0）** — アンカー実在の**回帰ガード**であって完了検出ではない。ステップ8 / 10 の節構成変更で壊れないことを見るもので、0 行でも「台帳を直した」証明にはならない。確認項目5 の手順2〜6 と併せて読む。
- **#13 の `MISSING:`（期待 0 / 着手前 0）** — 確認項目10 の但し書きのとおり、**着手後に増える性質**を利用した検査である。

### 5. `P-10` / `P-9` が散文のヒットで通る

どちらも「名前が1回でも出れば通る」検査なので、テーブル名や `kind` 名を散文で1回書いただけで 0 行になる。**定義の実在は確認項目4 の手順4 の目視でしか判定できない。**

### 6. 台帳の連番を詰めてしまう

削除した ID の連番を繰り上げると、#10 / #13 が参照する ID が別の要素を指すようになる。**AC-14 / AC-15 は「実在する」ことしか見ないので機械検査では検出できない**（確認項目5 の手順4 が唯一の防御）。

### 7. `spec/manual-tests/{search,trash}.md` の `D1` を直してしまう

`V-2b` がこの2ファイルを射程から外しているのは、10 行すべてがテストデータのドキュメント名だからである（plan.md の除外根拠）。**改名は本 Issue のスコープ外**で、直すと `spec/testcases/` 側の期待値と食い違う。

### 8. 件数の同期を先にやる

確認項目13 は最後に実行する。`spec/manual-tests/` へのケース追加（ステップ15 / 16）より先に数えると、完了時点で再び嘘になる。
