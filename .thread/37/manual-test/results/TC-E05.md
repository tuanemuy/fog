# TC-E05: セッション cookie を改ざんしても他人のデータに到達できない

**結果**: PASS（手順4 の「見え方の比較」だけは判定不能。理由は下記）
**対応する受け入れ基準**: AC-4

## 準備

2アカウントを UI から作成した。

| | メールアドレス | `userId` | User Data DO のファイル |
|---|---|---|---|
| A | `do-check@example.com` | `019fc580-74f8-7100-ba6d-20ac519b2c9e` | `6888c96a….sqlite` |
| B | `do-check2@example.com` | `019fc58c-38dd-7799-a14d-4be405b47af8` | `52a94247….sqlite` |

セッション cookie は `fog_session=<payloadBase64url>.<HMAC-SHA256 Base64url>` で、payload は `{"typ":"session","uid":…,"ep":0,"exp":…}`。`document.cookie` は空（HttpOnly）なので、改ざんは CDP 経由の cookie 差し替えと `curl -H "Cookie: …"` の両方で行った。

## 実行ログ

| # | 操作 | 期待結果 | 実際の結果 | 判定 |
|---|------|---------|-----------|------|
| 1 | B の cookie の**署名末尾1文字**を書き換えて `/settings` をリロード | ログイン画面へ | ブラウザ・`curl` とも `307` → `http://localhost:3000/login?redirect=%2Fsettings`。ログインフォームが表示される | PASS |
| 2 | **payload の `uid` を A のものに差し替え、署名は B のまま**にして `/settings` | 署名検証で落ちる | ブラウザ・`curl` とも `307` → `/login?redirect=%2Fsettings`。**A のデータには到達しない** | PASS |
| 3 | cookie を消して `/settings` をリロード | ログイン画面へ | `307` → `/login?redirect=%2Fsettings` | PASS |
| 4 | B のセッションに **A の正しい cookie** を貼って `/settings` を開く | 貼り替えた側（A）の情報しか見えない | `/settings` が 200 で描画され、`アカウント / 認証方式 / メールアドレスとパスワード / ログアウト` が出る。**ただし A と B で表示内容が完全に同一のため、「A の情報が出ている」ことを画面から確認する手段が無い**（下記） | 判定不能 |

## 追加で行った検証（AC-4 の主張を別角度から確かめる）

手順4 が画面から判定できない代わりに、**`userId` 以外の入力から DO を選べない**という AC-4 の主張を、`SESSION_SECRET` を使って正しく署名した cookie を作って直接突きに行った。

| # | 細工 | 結果 | 判定 |
|---|------|------|------|
| 5 | A の `userId` に対し **`ep: 5`**（DO 側の `account.session_epoch` は 0）で正しく署名した cookie | `/settings` は 200 だが**パネルだけが失敗**し、`SettingsErrorScreen`（「エラーが発生しました」＋「再読み込み」＋「タイムラインへ」＋「ログアウト」）になる。内部詳細は一切出ない | PASS（epoch ガードが DO 側で効いている） |
| 6 | **存在しない `userId`**（`019fc000-0000-7000-8000-000000000000`）で正しく署名した cookie | 同じく `SettingsErrorScreen`。アカウント情報は出ない | PASS |

5 は「認可の権威が DO 側の epoch ガードへ移った」（`requireUserId()` はトークン真正性の前段チェックに降格）ことの直接の裏付けになる。**cookie の署名が正しくても、DO が持つ epoch と食い違えば拒否される。**

## 判定不能の理由（手順4）

`CurrentUserPanel` は設計上 PII を出さないので（`credentials[].label` は空、メールアドレスは非表示）、**アカウント A と B の `/settings` は文字列として完全に同一**になる。さらにネットワーク上にも識別子が出ない — 遷移中の HAR（212 リクエスト）を A / B の `userId` で grep しても**両方 0 件**だった。したがって「貼り替えた側のアカウントの情報しか見えない」ことを肯定的に示す観測点が、この時点の実装には存在しない。

否定側（他人のデータに到達できないこと）は手順1〜3 と追加検証5・6 で押さえられているので、**AC-4 の主張自体は満たされている**と判断した。#12 で識別可能な表示が入った時点で手順4 を再実施すべき。

## 検証中に見つかった問題（テストケースに無い）

**正しく署名されただけの存在しない `userId` で、空の User Data DO が丸ごと1個作られる。**

追加検証6 のあと `apps/web/.wrangler/state/v3/do/fog-state-UserDataDurableObject/` を数え直すと、ファイルが 5 → 6 に増えていた。増えたファイルは:

```
ffdfb464….sqlite | do=019fc000-0000-7000-8000-000000000000 | tables=16 | accountRows=0 | 約 236 KB
```

つまり **migration ゲートがアカウント存在チェックより先に走り、実在しないユーザーの DO に 16テーブルの DDL を一通り作ってから、その後で「アカウントが無い」と失敗している。**

- 実害の前提として `SESSION_SECRET` が必要なので、未認証の攻撃者が任意に作れるものではない。
- ただし**秘密を要しない到達経路がある** — 退会でアカウントを消したユーザーの cookie がまだ有効な間にアプリを開くと、同じことが起きて空の DO が再生成される（`finalize-withdrawal` が消したはずの DO が復活する）。
- 生成された空 DO を回収する仕組みは（少なくともこの経路では）見当たらない。ストレージ課金と `sweep-orphan-mapping` の想定範囲に照らして、設計上意図された挙動かどうかの確認が要る。

`.thread/37` の範囲外の判断なので、ここでは事実の記録に留める。
