# TC-E02: 誤ったパスワードでログインするとフォーム内にエラーが出る

**結果**: PASS
**対応する受け入れ基準**: AC-2 / AC-4（`lookupCredential` の応答均一化）

## 実行ログ

| # | 操作 | 期待結果 | 実際の結果 | 判定 |
|---|------|---------|-----------|------|
| 1 | `/login` で `do-check@example.com` + 誤パスワード | 画面遷移せずフォーム内エラー | URL は `/login` のまま。`main` に **「メールアドレスまたはパスワードが正しくありません」** | PASS |
| 2 | `/login` で未登録 `no-such-user@example.com` + 任意パスワード | 同じエラー | 同じく `/login` のまま、**まったく同じ**「メールアドレスまたはパスワードが正しくありません」 | PASS |
| 3 | 2つのレスポンスを見比べる（HAR で採取、各3回ずつ） | 区別がつかない | 両者ともに HTTP **422**、ボディは**バイト単位で同一**:<br>`{"kind":"validation","code":"INVALID_CREDENTIALS","message":"Invalid email or password","retryable":false}` | PASS |
| 4 | 所要時間が極端に違わないこと | 均一 | サーバー関数の往復時間（HAR の `time`、交互に3回ずつ計測）<br>登録済み+誤パス: **31 / 26 / 29 ms**<br>未登録メール: **30 / 25 / 26 ms**<br>差は誤差の範囲で、どちらが速いかも一定しない | PASS |

## 確認ポイントの結果

- **メール登録の有無が漏れないこと** — 漏れない。HTTP ステータス・エラーコード・メッセージ・所要時間のいずれでも区別できない。ダミー材料による計算量均一化が効いている。

## 副次的に確認できたこと（テストケースに無い挙動）

**失敗回数のバックオフが存在し、そのレスポンスも `INVALID_CREDENTIALS` に潰されている。**

誤パスワードを短時間に6回投げた直後、**正しいパスワード**でログインしようとしたところ 422 `INVALID_CREDENTIALS` で拒否された。Identity Directory DO の `credential_mappings` を実測すると:

| 時点 | `failed_attempts` | `next_attempt_allowed_at` |
|---|---|---|
| 連続失敗の直後 | 2 | 未来の時刻（約15秒後） |
| その時刻を過ぎてから再試行し成功した後 | 0 | NULL |

つまり `next_attempt_allowed_at` を過ぎるのを待てば正しいパスワードで通る（実際に通った。TC-E04 の手順3）。**セキュリティ上は正しい設計**（スロットリング中であることすら区別できない）だが、以下2点は記録に値する:

1. **利用者にはロックアウト中であることが一切分からない。** 正しいパスワードなのに「メールアドレスまたはパスワードが正しくありません」と出るので、体験としては行き詰まる。UX として意図どおりかは #37 の範囲外だが、確認しておく価値がある。
2. **自動テスト・手動テストの順序依存を生む。** ログイン失敗系のケースを回した直後に正常ログインを試すと、この検証でも実際に起きたとおり「原因不明のログイン失敗」として現れる。テスト手順書に注意書きがあると安全。
