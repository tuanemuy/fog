# 実装計画 — Issue #37: [実装] D1 + Outbox から SQLite-backed Durable Objects + Alarm へ移行する

**Issue:** #37
**作成日:** 2026-08-03
**複雑度:** 中〜大規模
**実装方針:** steps.md

---

## 目的

永続化を D1 の共有 DB からユーザー単位の SQLite-backed Durable Object へ移し、Outbox + relay / consumer / pruner / DLQ による非同期処理を DO のローカル同期トランザクションと Alarm ジョブへ置き換える。#34 が設計し #35 が spec に反映した構成を、本番の永続データが SQLite-backed DO だけに存在する状態まで実装する。

## スコープ

### 含まれないもの

- **検索 usecase・検索ページの実装** → #10。#37 は DO 内 FTS5 schema と同期 projection、および tokenizer 検証に必要な最小の読み（`search/probe.ts`）までを提供する。不透明カーソルのスナップショットの物理形も #10 へ委譲する（`spec/database/index.md`「本ファイルで定義しないテーブル」の主体を書き換える）。

- **`spec/database/index.md` と `.thread/34/design.md` は「1つの節だけを読んで実装しない」ことを前提に書かれている**（`.thread/34/handoff.md` 第5節）。断定の適用先が別の節にあるため、節が名指しする参照先まで辿ること。とくに `jobs` の収束規則3つ・再武装分類 (A)(B)(C)・`kind` の全数表・投入点欄は相互に依存する。
- **`transactionSync` のコールバックは完全同期でなければならない**（F-7）。ドメインポートの `Promise` 契約を剥がす変更はドメイン層に及ぶので、`CLAUDE.md`「Reference runtime」の「ランタイムを差し替えても domain / application / presentation は無傷」という前提が実際に破れる。#35 が既に CLAUDE.md を改訂済みかを確認し、残っていれば #37 で直す。
- **FTS5 の external-content は踏み外しても例外が上がらず索引だけが黙って壊れる。** `DELETE FROM search_fts WHERE rowid = ?` と書くと壊れる。projection モジュールを唯一の書き込み点にし、テストで「delete → insert の2段が発行されること」ではなく「更新後に旧値でヒットしないこと」を検証する。
- **`Date.now()` は Workers では凍結している**（F-32）。チェックポイント予算の打ち切り条件に経過時間を使うと、まさに保護が必要な CPU バウンドの列で発火しない。件数だけで有界にする。ただし lease・backoff・`completed_at`・prune の保持期間・最小再開間隔は**起床をまたいだ絶対時刻の比較**なので `Date.now()` で成立する。射程を取り違えないこと。
- **CPU 予算超過はエラーではなくエビクションとリセットである。** 「例外が上がるから検出できる」を前提にした設計にしない。`finally` に再武装を置かない（isolate ごと殺されるので走らない）。
- **`setAlarm` / `getAlarm` / `deleteAlarm` の戻り値は公式ドキュメント内で食い違っている**（F-30）。永続化の確認は `await ctx.storage.sync()` だけに依拠する（F-31）。既存 alarm との比較は `getAlarm()` ではなく DO インスタンスのフィールドで行う。
- **駆動源クエリを作業述語より狭く読むと1回で `done` に落ちて止まり、広く読むと恒久起床ループになる。** 前者は「dormant な DO のゴミ箱の保持期限が黙って無期限に伸びる」、後者は「`setAlarm` 1回=1行の書き込み課金が全ユーザー分で永久に増える」。(1-A) / (1-B) の表を逐語で実装する。
- **`exports` をデプロイした後に `[[migrations]]` 配列へ戻せない**（F-21）。`exports` 経由で削除した namespace に Trash は無い。
- **`.wrangler/deploy/config.json` の redirect が全 env に効く**（#40 §5 の実測）。named environment を使わない構成にすることで避けるが、`--dry-run` で実際に確認する。

  - 古い成果物がある状態: プラグインが前回のビルド出力をエントリとして扱い（`\0virtual:cloudflare/worker-entry ← dist/server/index.js`）、`UNRESOLVED_IMPORT: Could not resolve '../rsc/index.js'` で失敗する。
  - **したがって `main` は経路で分ける** — ローカル `wrangler.toml` はソースエントリのまま、`wrangler.state.toml`（vite プラグインの管轄外）と `.tpl` からレンダリングする4ファイルだけが成果物を指す。Issue #37 の2番目のコメントが要求しているのは「redirect が効かない経路で設定単体が成立すること」であって、vite プラグインが読む設定までは含まない。AC-19 の文面もこの形に揃えてある。
- **`exports` が pinned wrangler（`^4.90.1`）で通らなかった場合の巻き戻しを、着手時の最初の作業で確定させる。** ADR-006 / ADR-011 / AC-19 / AC-26 とステップ25 / 27 が全部この1点に乗っている。**`exports` をデプロイした後に `[[migrations]]` 配列へ戻せない**（F-21）が、逆方向にはその制約が効かないので「先に `[[migrations]]` を試して後から `exports` へ移る」ことはできない — **判断は最初の1回で確定する。** 手順と巻き戻し先は steps.md ステップ25 の「最初の作業」に置いた。
- **ステップ間の順序依存が3つあり、いずれも「後のステップの成果物を先のステップが要求する」形だったので手順側で解消済みである。** (i) ステップ12（イベント機構の撤去）は `adapters/d1/repositories/{outboxRepository,idempotencyStore}.ts` と `application/di/serverCloudflare.ts` を同じステップで処理しないと単独で typecheck-clean にならない（分割の唯一の価値が消える）。(ii) ステップ10 の `registry.ts` は `MailSender` の型を要求するので、**ポート定義だけをステップ10 へ前倒しし**、実装2本をステップ11 に残す。(iii) ステップ24 の起動スモークは `dist/state/index.js` を要求するので、**state Worker のビルド設定（`vite.config.state.ts` + `build:cf` の2段化）をステップ6 が持つ**（adr.md ADR-017）。**`build:cf` は現状 `vite build --config vite.config.cloudflare.ts` の1段だけで、どのステップの対象ファイルにも `package.json` が入っていなかった。**
- **`registerWithPassword` の `catch` は deferred-batch 前提**（UNIQUE 違反が `insert` の呼び出しフレームの外で上がる）。同期 commit では `insert` のその場で上がるので、翻訳点をアダプターへ戻す。
- **逆流依存が2件あり、向きも定数も別なので移動は2つ要る。** (a) `adapters/webcrypto/pbkdf2PasswordHasher.ts:2` → `application/identity/loginWithPassword`（`DUMMY_PASSWORD_HASH_ITERATIONS`。adapters → application）、(b) `application/di/secrets.ts:5` → `adapters/webcrypto/hmacSessionCodec`（`MIN_SESSION_SECRET_LENGTH`。application → adapters）。**`DUMMY_PASSWORD_HASH_ITERATIONS` を移すだけでは (a) しか断てない。** #37 では両方を `packages/core/src/lib/`（`passwordHashing.ts` / `secretLengths.ts`）へ移す。とくに (b) は `application/di/__tests__/secrets.test.ts` 冒頭コメントが「長さはアダプターの export 定数から読む。ここで 32 を再掲するとフロアが上がったときに2つの検査が割れる」と**意図的な設計として正当化している**依存なので、`secrets.ts` の書き直しでリテラル `32` を再掲すると、その不変条件が黙って失われる。
- **`SerializedError` の union は presentation 層が組み立てている**（`apps/web/app/presentation/errorResponse.ts:29-37` の8バリアント。`CLAUDE.md` も「assembled here」と明記）。`packages/core/` からこれを型に取ると**依存方向が逆流する。** エンベロープの型は `packages/core/src/lib/error.ts` の `SerializedErrorBase` を土台にとどめる。
  - **ただし置き場は `adapters/` ではなく `packages/core/src/lib/rpcEnvelope.ts` である**（adr.md ADR-014）。`kind` → 例外クラスの復元は application 層（`packages/core/src/application/rpc/restoreError.ts`）に置くので、型を `adapters/cloudflare/platform/envelope.ts` に置くと **`application → adapters` の逆流**が生まれ、AC-25 の「逆流 import 0件」と自分で衝突する。これは `MIN_SESSION_SECRET_LENGTH` の逆流（下記 (b)）と**同じ形**であり、同じ手段（`lib/` の leaf へ移す）で断つ。`adapters/.../envelope.ts` に残すのは `toSerialized()` を叩く `ok` / `err` ヘルパだけである。
  - **未知の `kind` を黙って `unknown` へ潰さない**（`SystemError(DataIntegrityError)` にする）。復元表のキー集合が union と一致することは presentation 側の unit テストで固定する（権威が presentation にあるので、検査もそちらに置くのが正しい）。
- **`grep` に生の NUL バイトを埋め込まない。** SSO canonical の区切り子は `U+0000` だが、**ソースには JS のエスケープ表記（バックスラッシュ + `u0000` の文字列リテラル）で書く**。ドキュメントには `U+0000` と表記する。生のバイトを埋め込むと `grep` がそのファイルをバイナリ扱いして無言で0件を返し、引き継ぎ項目の検索と機械検証が同時に壊れる（`.thread/34/design.md` 第5.2.1節 (c)）。

## テスト方針

- **unit（Node プール、`vitest.config.ts`）** — 値オブジェクトの canonical 化（NFKC の適用範囲・local 部の非 ASCII 拒否・punycode 後の長さ再チェック）、`User` のクレデンシャル集合の不変条件、`jobKind` / `jobBudgets` の全数、ジョブの収束規則3つと再武装分類の純関数、`hmacSessionCodec` の `typ` / `ep` 検証、`directoryLocator` の bucket index 導出、`platform/stubErrors` の翻訳表、projection の正規化関数。
- **integration（Workers プール、`vitest.config.integration.ts`。DO バインディング）** — スキーマ作成・migration ゲート・fail-closed、OCC（0行検出と誤帰属の不在）、FTS5 projection の同一トランザクション整合、trigram / bm25 / `instr()` フォールバック / ページング、job table の CAS・backoff・poison・prune・lease reclaim、Alarm の起動セマンティクス、`purge-trash` の再計算→削除の2フェーズ、`send-mail` の enqueue→実行→完了 E2E（4ケース）、signup saga の phase 別再開と冪等性、login の3本 RPC と到達性検査、epoch ガード。
- **smoke（Node プール、`vitest.config.smoke.ts`。miniflare `scriptPath`）** — ビルド成果物（request / state）が workerd で起動し、`dispatchFetch` が応答すること。global scope 制約違反の検知。
- **既存テストの扱い** — `apps/web/app/worker/cloudflare/__tests__/handlers.integration.test.ts` は移植先が無いので削除し、後継を job table + Alarm の DO 統合テストとして書き直す。`packages/core/src/adapters/d1/__tests__/` 8本と `application/di/__tests__/serverCloudflare.test.ts` の `readRelayTuning` / `readPruneTuning` 検証、`application/identity/__tests__/eventDecoders.test.ts` は対象消滅で削除。`application/__tests__/helpers.ts` は DO 用ハーネスとして作り直す。
- **削除ではなく拡張するテスト2本** — `application/di/__tests__/requestContainerConfig.test.ts`（秘密が rest-spread で `container.config` に載らないことの恒久ガード。`secrets.ts` を「フラットに置かない」と決めている根拠そのもの）と `application/di/__tests__/secrets.test.ts` は、`RequestServerConfig` から `binding` が落ちて `secrets` が3本になると**必ず壊れる**。**同じ不変条件を新しい本数へ拡張して残す。** `StateSecrets` 側にも同形を1本足す。
- **テスト間クリーンアップ** — integration の `setupFiles`（`packages/core/src/adapters/cloudflare/__tests__/setup.ts`）は `afterEach` で `reset()` → `evictAllDurableObjects()` の2本を呼ぶ。**自動ロールバックには依拠しない**（`isolatedStorage` は現行版に存在しない。上記リスク欄）。射程が違う2本なので、なぜ両方要るかを setup 冒頭のコメントに残す。
- **数の記録** — 削除前後のテストファイル数・ケース数を実測して PR 本文に残す（#36 / PR #39 と同じ運用）。
