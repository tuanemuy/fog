## DO 境界・ルーティング

### Blockers

- **[B-001]** `rotation_checkpoints` を routing ローテーションと暗号化鍵ローテーションが共有しているのに、両者を区別する列が無い。`generation` 列が独立した2つの番号体系の値を同じ列に載せるため、**片方の完了記録がもう片方の「旧鍵を破棄してよい」条件を誤って成立させる。**
  - 場所: `.thread/34/design.md:380`（E-1 の `rotation_checkpoints` 行）/ `:398`（E-2 の書き込み口表）/ `:946`（第6.2.1節 (b-1)）/ `:1252`・`:1265`（第6.8節 手順4・retirement 表）/ `:1257`（`rotate-encryption` の `previousCount = 0` 置換記録）/ `:1254`（「2つのローテーションは独立に走らせてよい」）
  - 理由:
    - 第4.1.1節が定める `rotation_checkpoints` の列は `bucketIndex` / `generation` / `previousCount` / `scannedAt` / `conflictCount` / `lastConflictAt` / `lastConflictCredentialId` の7つで、**「どちらのローテーションの記録か」を示す列が無い。**
    - ところが本文は両方にこの表を使わせている。routing 側は第6.8節 手順4 と retirement 表（`:1265`）が「同一 generation の全 `0..N-1` について `previousCount = 0` の記録が揃っていること」を旧鍵破棄条件にし、暗号化側は第6.2.1節 (b-1)（`:946`）が「同一 `encryptionGeneration` の全 `0..N-1` bucket について `previousCount = 0` の記録が揃っていること」を旧鍵破棄条件にする。書き込みは `:1257` が「`done` にして `rotation_checkpoints` に `previousCount = 0` を置換記録する」と明記している。
    - そして第6.2.1節 (b-1) 自身が「routing secret 側の世代（locator の世代）とは**独立した番号体系**である」と断定している（`:945`）。**独立な番号体系の値が同じ `generation` 列に入るので、`encryptionGeneration = 3` の完了記録と routing `generation = 3` の進捗記録が同一キーに落ちる。**
    - 物理的な同居も成立する。routing ローテーションが走査・記録するのは previous 世代の bucket DO（`dir:g{prev}:b{i}`）であり、暗号化ローテーションが走るのはその時点の bucket DO である。routing ローテーション**開始前**は世代が1つしか無いので両者は同じ DO インスタンスであり、routing ローテーション G → G+1 が始まると、その走査対象 `dir:gG:b{i}` には暗号化ローテーションが残した行がそのまま載っている。
    - 加えて置換のキーが `(bucketIndex, generation)` なのか `bucketIndex` だけなのかが決まっていない。本文の表現は「**bucket ごとの** snapshot 置換」（`:946`・`:1265`）で、素直に読むと bucket DO につき1行になる。その読みでは世代番号が一致しなくても**常に**両ローテーションが互いの記録を上書きする。
    - 帰結（どちらの読みでも成立する）: routing ローテーション進行中に同じ bucket の `rotate-encryption` が完走して `previousCount = 0` を書くと、routing 手順4 の退役条件が全 bucket で成立し、**operator が previous 世代の routing 鍵を、移送が終わっていない状態で破棄する。** その鍵が無いと未移送利用者の canonical から `HMAC_k{prev}(canonical)` を作れないので、`lookup-credential` も `request-password-reset` も恒久的に解決不能になる。第6.9節が `rotate-remap` の鍵注入について「移送元 bucket の全利用者が login も `request-password-reset` も解決不能になり、復旧は 256 bucket の PITR しか無い」と登録しているのと同じ被害が、**悪用ではなく設計が明示的に許可している通常運用（`:1254`「独立に走らせてよい」）で成立する。** しかも `rotate-remap` の1チャンク駆動ガード (i)（自 DO 名の `gen` が引数の previous 世代と一致）は鍵破棄後の再開を救わない。
    - **第1.4節の検査がこれを拾わない理由も明確である。** 検査6（I-4）はテーブル**名**が E-1 に実在するかだけを見て、本文が要求する**列**が E-1 にあるかを見ない。検査3（I-5）は E-2 の行数と第8.2節に口があるかだけを見て、E-2 の「主な書き込み箇所」欄が本文と一致するかを見ない。実際 `:398` の E-2 は `rotation_checkpoints` の書き込み箇所を「`rotate-remap` チャンク完了時の snapshot 置換と競合の記録（第6.8節 手順2・手順4）」だけとしており、**`rotate-encryption`（`:1257`）が漏れている。** この漏れが、2つのローテーションが同じ表を共有している事実を設計の視界から外していた。
  - 提案: 次のいずれかに倒し切る。(a) `rotation_checkpoints` に `rotationKind`（`'remap' | 'encryption'`）を1列足し、置換キーを `(rotationKind, bucketIndex, generation)` と明記する。E-1 の列と E-2 の「主な書き込み箇所」欄（`rotate-remap` / `rotate-encryption` の両方）も同時に直す。(b) 暗号化側を別テーブル（例 `encryption_rotation_checkpoints`）に分け、E-1・E-2・第8.2節の口（`rotationCheckpointStore` を2本にするか、テーブル指定を引数に取る形にするか）まで反映する。**あわせて `:1254` の「2つのローテーションは独立に走らせてよい」を、その前提が何によって成立するのかを明記した形に書き直す。** どちらを採っても第1.4節に「I-4 の逆向き検査（本文が要求する列が E-1 にあるか）」と「E-2 の書き込み箇所欄と本文の一致」を検査手順として足さないと、同じ形の破れが再発する。

- **[B-002]** routing ローテーションの移送が、**古い `encryptionGeneration` を持つ行を、`rotate-encryption` が既に完走した active bucket へ運び込む。** 運び込まれた行を再暗号化する経路が無いまま暗号化旧鍵の退役条件が成立したままになる。
  - 場所: `.thread/34/design.md:1236`（移送は暗号文系3列をそのまま運ぶ）/ `:1257`（`rotate-encryption` は残件が無ければ `done` + `previousCount = 0`）/ `:1256`（投入点は operator 専用 maintenance 経路のみ）/ `:1474`（第7.4節 (7)「投入点の無い周期・反復ジョブは、1回完走した時点で恒久的に停止する」）/ `:1254`（独立に走らせてよい）
  - 理由:
    - 第6.8節 手順2 は「暗号文系の3列（`encryptedCanonical` / `encryptionGeneration` / `encryptionNonce`）は再暗号化せずにそのまま運ぶ」と決め切っている（`:1236`）。AAD が世代非依存なのでこれ自体は正しい。
    - `rotate-encryption` は分類 (B) 残件駆動で、残件条件は「`credential_mappings` に `encryptionGeneration` が active 世代でない行が存在する」（`:1463`）。残件が無くなった時点で `done` へ落ち、`previousCount = 0` を記録する（`:1257`）。**`done` から `pending` へ戻す唯一の手段は投入点である operator の起動 RPC であり**（`:1256`・第7.4節の再投入規則）、行が外から移送されてきたことを検知して自動で再武装する経路は設計のどこにも無い。第7.4節 (7) がまさにこの依存関係を不変条件の根拠として書いている。
    - したがって「暗号化ローテーションを先に完走させ、その後（または並行して）routing ローテーションを走らせる」という、設計が明示的に許可した順序（`:1254`）で次が成立する — 未移送 bucket に残っていた旧 `encryptionGeneration` の行が active bucket へ移送される → その bucket の `rotate-encryption` は既に `done` で `previousCount = 0` を記録済み → 全 bucket で `previousCount = 0` が揃っているので **operator が `IDENTITY_MAIL_ENCRYPTION_KEY` の previous 世代を破棄する** → 移送されてきた行の `encryptedCanonical` が**恒久的に復号不能**になる。
    - 帰結は第6.2.1節 (b-2) が AAD について自ら列挙している3つと同一である — (i) パスワードリセットメールの宛先組み立て、(ii) 設定画面の自メールアドレス表示（`read-own-canonical`）、(iii) **次回 routing ローテーションの再 HMAC** が壊れる。(iii) が壊れるのでその行は以後どの世代へも移送できず、しかも復号失敗は `SystemError(DataIntegrityError)` で fail closed に止める規則なので、**当該利用者はアカウント回復手段（リセット経路）を失う。** 第5.2.1節 (a) が「所有の唯一の証明はパスワードリセット経路である」と断定している以上、これは所有の証明そのものの喪失である。
    - login は `hmac` で解決するので通り続ける。つまり**最初のリセット依頼まで顕在化しない** — 第6.2.1節 (b-2) が AAD について「移送直後は誰も復号しないため最初のリセット依頼まで顕在化しない」と書いている失敗モードと同型で、そちらは塞がれているのにこちらは残っている。
  - 提案: 次のいずれかを設計として決め切る。(a) **2つのローテーションの同時進行を禁じ**、`:1254` の「独立に走らせてよい」を「routing ローテーションの previous 世代が退役するまで暗号化ローテーションを開始しない（逆も同様）」へ改める。#38 の運用手順にも制約として送る。(b) 同時進行を許すなら、**移送先 bucket が (2) で行を書いた同じ `transactionSync` の中で、その行の `encryptionGeneration` が active でなければ `enqueueJob('rotate-encryption', <定数 operationKey>, {}, now)` を発行する**（第7.4節の再投入規則により `done` / `poison` の行は `pending` へ戻る）。この場合 `rotate-encryption` の投入点は「operator 専用 maintenance 経路」だけではなくなるので、`kind` 全数表（`:1429`）の投入点欄も同時に直す。(c) 移送時に再暗号化する（第6.2.1節 (b-2) が棄却済みなので、採るなら棄却理由の撤回を明記する）。
