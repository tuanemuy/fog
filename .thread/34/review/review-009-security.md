## セキュリティ

### Blockers

- **[B-001]** `changeAuthToken` に**失効経路が無い**。「一回性」は「使われたら消える」ことしか保証せず、**未使用のまま残った `changeAuthToken` は、被害者のパスワード変更・リセット完走をまたいで `expiresAt` まで有効な「任意 `pendingVerifier` 昇格権」として生き残る**。前ラウンドが起点 B に課した束縛は、塞ぎたかった奪還経路を塞ぎ切っていない。
  - 場所: `.thread/34/design.md:1003`（無効化を発行する3箇所）/ `:1256`（phase 1 は**未使用**トークン行の削除だけ）/ `:1267`・`:1275`（一回性が後勝ち規則を守る、という主張）/ `:1276`（「phase 1 の削除がこの経路を閉じる」）/ `:515`・`:721`・`:722`（列と両エントリの定義）
  - 理由:
    - 本書は `:1276` で奪還経路（乗っ取り → リセット依頼 → トークン保持 → 被害者が復旧 → 古いトークンで再度リセット完走）を特定し、**「phase 1 で対象 credential の未使用リセットトークンを全削除する。これが無いと後勝ち規則が奪還経路になる」**と断定して閉じている。無効化の全数は `:1003` の3箇所（phase 1 / unlink 手順3 / 退会 手順3）で、**phase 1 が消すのは「未使用」トークン行だけ**である。
    - ところが `consume-reset-token` は行を消さず `usedAt` を立てるだけで（本書自身が `:765` (iv) で「行が消えるのは `sweep-reset-tokens` の期限切れ掃除だけ」と書いている）、**その同じ行に `changeAuthToken` を載せて返す**。したがって「消費済み・`changeAuthToken` 未使用」の行は **phase 1 の削除対象に入らず、`expiresAt` まで残る**。
    - この行を持つ者は、被害者が origin A（通常のパスワード変更）でも origin B（新しいトークンでのリセット完走）でも復旧した**後に** `begin-credential-change`（起点 B）を叩ける。ガードは「引数の `changeAuthToken` が行の値と一致」「行の `credentialId` が対象と一致」の2つだけで、**`credentialVersion` も `changeState` も `usedAt` も被害者の復旧の事実も見ない**。その後は `resume-credential-change` が phase 2 / 3 を自走させ、終状態は `:764` (i) が「乗っ取り原始関数」と呼んだ状態そのもの（攻撃者のパスワードで正規にログインでき、`sessionEpoch` も攻撃者側で前進済み）になる。
    - 「消費済み・未使用の `changeAuthToken`」という状態は**公開面から到達する**。`consume-reset-token` は成功しているのに続く `begin-credential-change` が失敗すれば残る — `.overloaded`（第6.2.2節が「攻撃者は任意の1 bucket を選んで soft limit へ追い込める」と認めており、**bucket index はリセット URL に載っているので攻撃者は狙う bucket を知っている**）、DO のリセット、`ctx.abort()`（第4.7節）のいずれでも発生する。リトライは `usedAt` により不可能なので、**この状態は「事故」ではなく安定した中間状態である**。
    - `:1275` の「同じ依頼の材料を後から再提示して差し替えることはできない」は成立しているが、**攻撃に要るのは「再提示」ではなく「まだ一度も使っていない材料の温存」**である。一回性は失効ではない。
    - 悪用に要る能力は「リセットトークンを1度得たこと」＋「`begin-credential-change` へ到達できること（= 第5.1節 (3-b) が明示的に守る対象としている『binding には到達できるが `SESSION_SECRET` を持たない呼び出し元』）」である。**`changeAuthToken` はまさにこの脅威クラスのために導入された**のに（`:764`・`:765`）、その脅威クラスに対して失効側が空いている。`:765` は「認可が開く向きの原始関数は1つも受容していない」と宣言しているので、受容済みリスクにも該当しない。
  - 提案: 第6.1節 (d) の無効化規則を**行の削除ではなく列にも掛ける**。具体は「**phase 1 は同じ `transactionSync` で、対象 `credentialId` の `password_reset_tokens` 行について (1) 未使用行を全削除し、(2) 残る全行の `changeAuthToken` を `NULL` にする**」の2段にする（起点 A / 起点 B の両方に課す。起点 B は自分が照合した行も含めて `NULL` になるので既定の一回性がそのまま満たされる）。あわせて `:515` の「credential 変更 / unlink / 退会が**未使用**トークンを一括削除」という記述と、`:1318`・`:1337` の「その `credentialId` の行も**全削除**」の食い違いも同時に直す（unlink / 退会側は全削除なので本件の穴は無い）。**`changeAuthToken` に独立した短い有効期限を持たせる案でも塞げるが、列を1つ増やすうえ「被害者の復旧で失効する」性質が得られないので、上の (2) を推す。** 第6.9節の締め出し・認可経路一覧（`:1466` の行）にも「一回性 ≠ 失効」の1行を足すこと。

### Warnings

- **[W-001]** credential 変更 saga の**起点（リセット完了か通常の変更か）がどこにも永続化されていない**。`resetVersion` 前進と AI クライアント接続の自動失効という侵害復旧の補償が、Alarm 再開経路で発火するか決まらない。
  - 場所: `.thread/34/design.md:1257`（phase 2「**起点がリセットトークンの消費だった場合に限り** `resetVersion` を進め、`createdAtResetVersion` が前進前の値と等しい接続を `revoked` にする」）/ `:514`（`credential_mappings` の列の全数）/ `:229-290`（検査8 の `テーブル:列` 一覧61件）/ `:1274`（前進の駆動は Directory bucket の Alarm）
  - 理由: phase 2 は常に Directory bucket → User Data DO の RPC（`advance-credential-change`）であり、再開は `resume-credential-change` が mapping 行だけを入力に駆動する。ところが `credential_mappings` の列の全数（`:514`）に起点を表す列が無く、検査8 の一覧にも無い。**第1.4節 I-4 は「本文が要求する列が E-1 に無ければ違反であり、直す向きは E-1 の側」と定めている**ので、これは I-4 の破れである。帰結は2つで、どちらも実装者が任意に倒せる — (i) 起点を復元できないまま「常に進めない」に倒すと、**被害者のリセット完走後も攻撃者が持ち込んだ AI クライアント接続が `exp` まで生き残る**（第5.4節 (i) が `credentialVersion` ではなく `resetVersion` を新設してまで塞いだ経路が、再開経路でだけ再び開く）。(ii)「常に進める」に倒すと通常のパスワード変更でも接続が切れ、`:924` の断定に反する。さらに `advance-credential-change` は `payloadDigest` の CAS を課すので、**起点が payload に含まれるなら再開時に digest を再構成できず `ConflictError` で saga が `pending` のまま止まる**（旧新どちらのパスワードも通らない ＝ 第6.9節が塞いだはずの恒久ロックアウト）。
  - 提案: `credential_mappings` に起点を持つ1列（例 `changeOrigin`: `'password-change' | 'reset'`）を足し、`:514` と検査8 の一覧の両方に載せる。**`password_reset_tokens.consumedByOperationId` から導出する形は採らない**か、採るなら明示する — `:722` が同列を「監査用であって束縛材料ではない」と格下げしているうえ、`sweep-reset-tokens` が行を消した後は導出が偽になるので、判定の権威が期限に依存してしまう。

- **[W-002]** `changeAuthToken` の**`NULL` と引数欠落の扱いを断定していない**。束縛の実体がこの1列だけである以上、`NULL == NULL` が通る実装が起点 B を無条件開放にする。
  - 場所: `.thread/34/design.md:721`（起点 B のガード）/ `:515`（`値 → NULL` の CAS）/ `:764`
  - 理由: 本書は同種の欠落について、セッションの `ep` 欠落（`:784`「`ep` 欠落は `verify` が `null` を返す」）と `typ` 欠落（`:904`「欠落は拒否する」）を**明示的に fail closed と断定している**。ところが「束縛の実体はこの列だけ」（`:515`）と宣言した `changeAuthToken` については、消費後の値が `NULL` であることだけを書き、`NULL` 行に対する照合の扱いと引数側の欠落・空文字の扱いを書いていない。定数時間比較を素直に「両辺をバイト列化して比較」と実装すると、`NULL`（または空）同士が一致し、**`changeAuthToken` を1つも持たない呼び出し元が任意 credential の起点 B を開始できる**（= B-001 の終状態に、トークン所持すら不要で到達する）。第5.1節の他エントリと同じ強さで断定を置くべき箇所である。
  - 提案: 起点 B のガードに「**行の `changeAuthToken` が `NULL` の場合は常に不一致とする。引数が欠落・空の場合も比較に入る前に拒否する**」を1文足す。`callerToken`（退会 手順4 で `NULL` になる。`:1339`）についても同じ規則が要るので、第5.1節 (3-b) 側に共通の1文として置くのが良い。

### Notes

- **[N-001]** 前ラウンドで導入した `changeAuthToken` は、**採番・保存・返却・比較・消去のうち「消去（失効）」以外は正しく閉じている。** 採番は bucket 側の128ビット乱数で新しい秘密も配布経路も増えない（`:764`）。保存と比較は同一 bucket・同一 `transactionSync` なので DO の直列実行で競合しない。返却先は request Worker のみで、第5.2節 (c) の非露出リストに入っている（`:796`）。`begin-credential-change` の応答喪失で再提示できなくなっても saga は `resume-credential-change` が前進させるので詰まらない（`:1274`）。`:1267` が「一回性がリセットのやり直しを壊さないこと」を先に検証しているのも妥当である。**残る欠けは失効の1点（B-001）と `NULL` 規則（W-002）だけである。**
- **[N-002]** `operationId` を束縛の実体として使うエントリが**本当に1本も残っていない**ことを表側から確認した。クラス (3) は12行で (3-a) 5 + (3-b) 2 + (3-c) 3 + (3-d) 2 = 12 と一致し（I-6）、CAS も phase 条件も持たない5本（`read-own-canonical` / `delete-mapping` / `check-previous-generation` / `purge-user-mappings` / `rotate-encryption` の起動）はそれぞれ `callerToken`・真偽1ビットの読み取り専用・到達制御と監査・keyring 突き合わせに割り当てられている。`cancel-reservation` への `callerToken` 追加（`:756`）も、材料が既に予約行にある値なので配布境界を増やしていない。
- **[N-003]** テナント分離は構造で閉じている。`idFromName` の材料は3経路（署名済みトークン / signup で `IdGenerator` が採番した候補 `userId` / Directory の RPC 戻り値）に限定され（`:959-962`）、DO 側の locator 材料は「自分の SQLite に永続化済みの locator」に限られる（`:963-966`）。外部入力が locator の材料になる唯一の例外（リセットトークンの `generation` / `bucketIndex`）には**DO を叩く前**の範囲検査3点が課されており（`:994`）、第6.2節の判断軸 (iv) が真になる条件として明記されている。unlink がクライアントから受け取る `credentialId` も、自 DO の `credential_locators` を引くだけなので他ユーザーの行に届かない。
- **[N-004]** 単一世代（generation が1つ）での各 saga の部分失敗を追ったが、悪用可能な残りは見つからなかった。とくに次の3点が効いている — (i) 削除・数え上げ・到達性検査のキーを `credentialId` に統一したことで、退会中に canonical を取り直した**別**アカウントの mapping を古い `finalize-withdrawal` が消せない（`credentialId` 不一致で「無ければ成功」に落ちる）。(ii) 退会 手順4 が `account.callerToken` の削除を「未完了 unlink 0件」でゲートしている（`:1340`）ので、`delete-mapping` の束縛材料が先に消えて孤児 mapping が固定化する経路が閉じている。(iii) tombstone に `callerToken` が残らないため、`deleted` なアカウントに対する `advance-credential-change` が束縛不成立で拒否され、退会 × credential 変更の競合が fail closed に倒れる。
- **[N-005]** PITR の3系統（`sessionEpoch` の巻き戻し / AI クライアント接続の復活 / リセットトークン行の復活）はいずれも独立した穴として特定され、restore 直後の必須ステップが DO クラス別に割り当てられている（`:2103-2113`・`:2434`）。とくに `:2111` が「復活したトークンを持つ攻撃者には `changeAuthToken` の束縛が効かない」と自ら明記しているのは正しい評価である（B-001 は、その同じ限界が**PITR を経ない通常経路**にも及んでいるという指摘である）。
- **[N-006]** #44 への委譲は #37 を壊していない。第6.1.1節が (A)(R1)〜(R5)(R8)＝単一世代でも定義され成立する6条と (B)(R6)(R7)(R9)＝移送前提の3条に分けられ（`:1015-1017`）、第6.8節の境界表（`:1405-1416`）が #37 の実装範囲を列・キー・冪等キー・起動 RPC 単位で確定させている。第5.1節の RPC 全数表から移送を外した際に「射程の限定」を表に添え（`:739`）、第6.9節では経路の列挙を残して塞ぎ方だけを #44 へ渡している（`:1444`）ので、#37 が「移送を実装しない」まま着手して後から移送が入れられなくなる4点（`:1416`）も名指しされている。**#44 待ちの7行はいずれも「移送が進行中である」を条件節に持つので、単一世代の #37 では発火しない**という判定も検証した結果と一致する。
