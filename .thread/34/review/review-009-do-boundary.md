## DO 境界・ルーティング

### Blockers

- **[B-001]** 退会 saga が「未完了の SSO link」を引き取らないため、退会後に回収不能な `active` 孤児 mapping が残り、その SSO 主体が恒久的に再登録不能になる
  - 場所: `.thread/34/design.md:1338`（退会 手順3 の引き取り節）/ `:1340`（手順4 の前提条件）/ `:1205`（第6.4節 cross-DO 操作表の SSO link 行）/ `:1467`（第6.9節の unlink×退会 行）
  - 理由:
    - R8 の指摘を受けて追加された退会側の引き取りは、対象が **`kind = 'unlink'` の行に限定されている** — `:1338` は「`operations` に **`kind = 'unlink'`** かつ `phase != 'done'` の行があれば、その行の `targetLocators` が持つ全世代の locator へも `delete-mapping` を発行し」、`:1340` の手順4 の前提条件も「`operations` に**未完了の unlink 行**が1件も無いこと」である。
    - ところが **link も unlink とまったく同じ盲点を持つ**。link 手順1（`:1297`）は `operations` に `{ kind: 'link', phase: 'reserving', targetLocators }` を記録するが、`credential_locators` へ行を書くのは**手順4** である（`:1297` の「対象はまだ `credential_locators` に無い。記録は手順4」）。したがって **手順1〜3 のあいだ、link 対象の credential は退会 手順3 の削除対象集合（`credential_locators` 由来）に一切現れない。**
    - 単一世代・ローテーション未実行でも成立する順序は次のとおり。(1) 利用者が SSO link を開始（手順1 で `operations` 行 + `resume-link` 投入）→ (2) 手順2 で予約、手順3 で `active` へ昇格 → (3) 手順4 の直前で落ちる → (4) 利用者が退会（手順1 で `deleting`、`finalize-withdrawal` 投入）→ (5) 手順3 は `credential_locators` を引くので link 対象の mapping を**削除しない**。引き取り節は `kind = 'unlink'` しか見ないので link 行も拾わない → (6) 手順4 の前提条件（未完了 unlink が0件）は満たされるので**そのまま通過**し、`credential_locators` と **`account.callerToken` を削除**して `deleted` にする。
    - 帰結は第6.9節の unlink×退会 行が列挙している3点と**同一**である。(i) `encryptedCanonical` を持つ `credential_mappings` 行が bucket に残り、第6.2.1節 (d)「退会が完了した時点で bucket 側には何も残さない」が破れる。(ii) その SSO 主体が**恒久的に再登録不能**になる（次の signup / link は `reserve-credential` が既存 `active` 行との一意制約で敗北する）。(iii) 回収経路が1つも無い — `sweep-reservations` は `status = 'reserved'` しか見ず、`sweep-orphan-mapping` の残件条件（`:1637`）は `kind = 'unlink'` の行だけ、`finalize-withdrawal` は `credential_locators` と unlink 行だけを見る。`resume-link` は `record-credential-locator` の束縛材料（`account.callerToken`）を失っているので前進できず `poison` に落ちるだけである。復旧手段は `purge-user-mappings`（256 bucket 走査）しか残らない。
    - 認可は開かない（login は第5.3節 step 5 (i) の `account.status` 照合で fail closed になる）ので、破れは締め出しと PII 残存の側だけである。**ただしそれは第6.9節が Blocker 級として塞いだ unlink×退会 の破れとまったく同じ性質であり、同じ基準で塞がなければ非対称が残る。**
    - なお `resume-link` が手順3 まで走れる点も効いている — `activate-reservation` のガードは「予約行の `operationId` 一致」だけで `callerToken` を要らないので（`:726`）、退会が `callerToken` を消した**後でも**予約は `active` へ昇格できる。つまり (3) の落下点が手順2 と手順3 のあいだであっても、最終状態は同じ `active` 孤児 mapping に収束する。
  - 提案: 退会 手順3 の引き取り述語と手順4 の前提条件を、unlink 限定から **「`operations` に `phase != 'done'` の cross-DO saga 行（`kind IN ('link','unlink')`）が存在するか」** へ広げる。link 行は削除ではなく「`targetLocators` の locator へ `delete-mapping` を発行し、成功したらその link 行を `phase = 'done'` にする」で足りる（退会するアカウントに対する link の正しい終端は前進ではなく回収であり、`delete-mapping` は「無ければ成功」の冪等操作なので手順4 が完走している場合と二重発行になっても無害である）。あわせて第6.4節の cross-DO 操作表・第6.9節の締め出し経路一覧・第7.4節 (1-B) の残件条件（`sweep-orphan-mapping` が link 行も減らす手段を持つか）を同時に直す。**「退会の起点で未完了 link を先に完走させる」に倒す形は採れない** — 手順1 は `sessionEpoch` を進めて `deleting` へ倒す同期処理であり、link の完走を待てないからである。

- **[B-002]** SSO link 手順2 が作る予約行に `reservedUntil` が書かれず、`sweep-reservations` の投入点も link 経路に無いため、`resume-link` が前進できなくなった時点で `reserved` 行が恒久的に残る（かつ `sweep-reservations` の再武装演算が壊れる）
  - 場所: `.thread/34/design.md:1298`（link 手順2）/ `:540`（`reservedUntil` の型と用途の確定）/ `:1596`（第7.4節 E-3 の `sweep-reservations` 投入点欄）/ `:1629`（(1-A) 駆動源クエリ）
  - 理由:
    - `reservedUntil` を書く箇所は**signup phase 1a / 1b の2つだけ**である。`:1157` / `:1158` が `{ ..., reservedUntil }` を明示し、`:1226` が「予約行の `reservedUntil` は **phase 1a / 1b で** `now + TTL` として書く」と断定している。一方 link 手順2（`:1298`）は「active 世代の bucket に予約を取る（`credentialId` と `callerToken` 付き。既に他アカウントで `active` なら `ConflictError`）」であり、`reservedUntil` に一言も触れない。
    - `sweep-reservations` の投入点も同じく signup 限定である。E-3 の投入点欄（`:1596`）は「**第6.3節 phase 1a / 1b**（予約行と同じ `transactionSync`。予約を書いた bucket が自分に投入する）」で、link 手順2 は投入点として名指しされていない。
    - この2つが揃うと、第7.4節 (7)（`:1650`）が自ら「**投入点の無い周期・反復ジョブは、1回完走した時点で恒久的に停止する**」と断定している失敗モードが link 経路で発火する。定常状態では対象 bucket の `sweep-reservations` は残件0で `done` に落ちているので、link が新しい `reserved` 行を作っても誰も `pending` へ戻さない。
    - さらに `reservedUntil` が NULL のままだと、`sweep-reservations` 自身の再武装演算が壊れる。作業述語は `reservedUntil < ?` なので NULL 行は永久に掃除対象にならないが、**駆動源クエリ（`WHERE status = 'reserved' AND sagaCommitted IS NULL` の `min(reservedUntil)`）の集合には入る**。つまり「残件はあるが `min(...)` が NULL」という状態が作れ、第7.4節 (1-A) の「残件があれば `nextRunAt` をその `min(...)` へ設定して `pending` へ戻す」が `nextRunAt = NULL` を書くことになる。これは同節が `done` / `poison` について `nextRunAt` を NULL にする規定（`:1656`）と衝突し、`deleteAlarm()` の述語（実行可能集合が空か）と最早 `nextRunAt` の読み直しの両方が未定義の値を掴む。
    - 発火条件は単一世代でも通常事象である。link の前進は `resume-link`（分類 (C) 一回性）だけが担い、失敗は `attempt` のバックオフを経て `poison` に落ちる（`:1656`）。`poison` に落ちた時点で予約行は誰の回収対象でもなくなり、その SSO 主体は恒久的にロックされる（B-001 と同じ (ii) の帰結）。B-001 の順序で退会が絡む場合も、手順3 の直前で落ちれば同じ `reserved` 行が残る。
  - 提案: link 手順2 の予約行にも `reservedUntil`（`now + TTL`）を書き、**予約行を書くのと同じ `transactionSync` で対象 bucket へ `sweep-reservations` を投入する**（signup phase 1b とまったく同じ形。第6.3節「コーディネーターかどうかにかかわらず、予約行を書いた bucket が自分に投入する」の規則を link にも適用する）。第7.4節 E-3 の `sweep-reservations` 投入点欄に「第6.6節 link 手順2」を追記し、第6.4節の cross-DO 操作表の SSO link 行の「中間状態で残るもの」に**手順2〜3 の `reserved` 行**を足す（現在は手順3→4 の `active` 孤児しか書かれていない）。あわせて第6.3節 phase 1a の TTL 不等式（`:1226`）が link にも掛かることを明記する。**「`reservedUntil` を NOT NULL にする」だけでも駆動源の破れは閉じるが、投入点が無いままでは (7) の恒久停止が残るので両方が必要である。**

- **[B-003]** signup saga のどの phase も `credential_mappings.passwordVerifier` を書かないため、第6.3節 phase 4 の `usableForLogin` 述語が構造的に真になりえない — パスワード signup が「ログインもリセットもパスワード変更もできないアカウント」を作る
  - 場所: `.thread/34/design.md:1154-1161`（第6.3節 phase 表）/ `:1163`（phase 4 の `usableForLogin` 判定）/ `:717`（第5.1節 `reserve-credential` の引数）/ `:514`（`credential_mappings` の列全数）
  - 理由:
    - `passwordVerifier` を**書く**箇所として本書が名指ししているのは第6.5.1節 phase 3（`pendingVerifier` からの昇格。`:1258`）だけである。文書全体を走査しても、signup 経路で検証材料を計算する記述も書き込む記述も存在しない。
    - 対照的に credential 変更 saga の phase 0（`:1255`）は「`PasswordHasher.hash` で**新しい検証材料を計算する**」を明示している。signup の phase 0（`:1156`）は「`IdGenerator` が `operationId` / 候補 `userId` / `callerToken` / credential ごとの `credentialId` をそれぞれ新規に採番する。…全 credential の canonical を確定し、locator を安定ソートしてコーディネーター bucket を決める」で、ハッシュ計算に触れない。第5.1節の `reserve-credential`（`:717`）も「予約行には `credentialId` と `callerToken` を載せる」までで、検証材料を運ぶとは書いていない。`initialize-account` / `activate-reservation` / `record-credential-locator` の各行も同様である。
    - これは単なる記述漏れではなく**述語の自己矛盾**である。phase 4 の `usableForLogin`（`:1163`）は「`kind = 'sso'` であるか、または **`kind = 'email'` かつその mapping 行が `passwordVerifier` を持つ**」と定義されているので、パスワード signup で真になるには phase 1〜3 のどこかが `passwordVerifier` を書いていなければならない。書く phase が無いのだから、この述語はパスワード signup に対して**必ず偽になる**。
    - 帰結が広い。#37 が本書のとおり実装すると、(i) login は step 3 が `passwordVerifier` を持たない行を返すので step 4 の照合が成立しない（`:873`）、(ii) 第7.6節（`:1767`）が「送るか送らないかの判定は `passwordVerifier` の有無で行う」と決め切っているので**リセットメールも送られない**（SSO 専用扱いに落ちる）— つまり第5.2.1節 (a) が「所有の唯一の証明はパスワードリセット経路」と断定した復旧手段も存在しない、(iii) 第6.5.1節 起点 A の A-1（`:1262`）は `usableForLogin = true` の行だけを読むのでパスワード変更も成立しない、(iv) 第6.6節 unlink (1-b) のログイン手段の数え上げが常に0になる。**パスワード signup で作られたアカウントは一度もログインできず、自己回復手段も持たない。**
    - 第4.1.1節（`:514`）は列として `passwordVerifier` を持ち、第6.1節 (d)（`:992`）は「パスワードの検証材料は `credential_mappings` の `kind: 'email'` 行に持つ」と**所在**を決めているが、どちらも**書き込み点**を決めていない。第4.1.1節が「#37 が実テーブルと実列を判断する根拠はこの表である」と宣言している一方、saga の正本である第6.3節に書き込み手順が無いので、#37 はここで手を止める。
  - 提案: 第6.3節 phase 表に検証材料の計算点と書き込み点を明記する。自然な形は **phase 0 で request Worker が `PasswordHasher.hash` を実行し（第4.8節の「DO の外で回す」に合致）、phase 1a の `reserve-credential` の引数として予約行へ載せる** である。あわせて次の3点を決める。(1) 第5.1節の `reserve-credential` 行の引数一覧に `passwordVerifier` を足す（同表は全数を宣言しているので、引数が漏れるとガードの評価もできない）。(2) **`reserved` 行の `passwordVerifier` を `lookup-credential`（クラス (2)、未認証から無条件応答）が返してよいか**を決める — 返すと未活性の signup の検証材料が未認証経路へ出る。第5.3節 step 3 は `status` も返すので、`status != 'active'` の行はダミー材料へ倒す規則を第6.5.1節 phase 1 の `changeState = 'pending'` と同じ形で足すのが整合する。(3) SSO signup がメール一意性のために置く行には `passwordVerifier` を載せない（`usableForLogin = false` が正しく出るための条件であり、第7.6節・第6.1.1節 (R4) がこれに依存している）。

### Warnings

- **[W-001]** 「epoch 前進の冪等性は `operations` 行の存在で判定する」という第6.5節の断定が、4つの前進操作のうち退会には当てはまらない
  - 場所: `.thread/34/design.md:1242`（第6.5節）/ `:1335`（第6.7節 手順1）/ `:533`（E-2 の `recordOperation` 書き手欄）
  - 理由: 第6.5節は「パスワード変更・リセット完了・SSO の**解除**・退会は、同じ `operationId` の再送では `sessionEpoch` を**一度だけ**進める。**判定は `operations` 行の存在で行う**」と断定している。ところが第6.7節 手順1 は「`account.status = 'deleting'` を書き、`sessionEpoch` を進める。…同時に `kind: 'finalize-withdrawal'` のジョブを投入する」だけで `operations` 行を記録しない。E-2 の `recordOperation` の書き手欄（`:533`）も「signup phase 2 / link 手順1 / unlink 手順2 / credential 変更 phase 2」の4つで、退会を含まない（検査9 もこの欄と本文の整合を確認するが、`recordOperation` は E-3 の `kind` を走査対象にするので退会の不在は検出されない）。実際の冪等性は `account.status` の遷移（`active` 以外では起点が epoch ガードで拒否される）が担保しているので**悪用可能な穴ではない** — 再度の退会要求で epoch が二度進んでも単調増加のカウンタが1つ余分に進むだけである。問題は「4操作に共通の判定機構」を名乗る断定が実際には3操作にしか掛かっていないことで、#37 が文面どおりに「退会にも `operations` 行がある」前提で実装すると、E-2 の書き込み口（`recordOperation`）の呼び出し点が本書のどこにも無いまま宙に浮く。
  - 提案: 第6.5節の当該文を「判定は `operations` 行の存在で行う（**退会だけは `account.status` の遷移がこれを兼ねる** — 起点が `active` のときしか通らないため）」に直す。あるいは第6.7節 手順1 に `recordOperation(operationId, 'withdrawal', ...)` を足して4操作を揃え、E-2 の書き手欄にも行を足す。**どちらでもよいが、片方だけを直すと第6.5節と E-2 の非対称が残る。**
