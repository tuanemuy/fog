## DO 境界・ルーティング

### Blockers

- **[B-001]** `hmac` は世代依存の値なのに、`(kind, hmac)` を「世代をまたいで安定な credential の同一性」として使っている。ローテーション中の unlink が第6.9節で塞いだはずの自己ロックアウトを再現し、かつ unlink の削除対象を選択する手段が設計に存在しない。
  - 場所: `.thread/34/design.md:244`（第4.1.1節 `credential_locators` の列定義）/ `:704`（第6.1.1節 (R4)）/ `:703`（同 (R3)）/ `:956-958`（第6.6節 unlink 手順1・2）/ `:1063`（第6.9節の締め出し経路表）。矛盾の相手は `:496`（`HMAC-SHA-256(DIRECTORY_ROUTING_SECRET[generation], canonical)`）/ `:529`（「世代付き secret で HMAC する」）/ `:1002`（第6.8節 手順2「active 鍵で**再 HMAC**して新しい世代の bucket へ移す」）
  - 理由: locator の全長 HMAC は `DIRECTORY_ROUTING_SECRET[generation]` を鍵とする HMAC-SHA-256 の出力である（第5.2節 (b)・第5.2.5節 (a)）。鍵が世代ごとに違う以上、**同じ canonical でも世代が違えば `hmac` の値は違う**。第6.8節 手順2 の (1)「新 locator を追加」/ (4)「旧 locator を消す」も、2つの異なる locator が並存することを前提に書かれている。ところが第4.1.1節・第6.1.1節・第6.6節はそろって `(kind, hmac)` を世代非依存の識別子として扱っており、この2つは両立しない。具体的な破れは2つある。
    - **(a) 「最後のログイン手段」検査がローテーション中に発火しない。** 第6.1.1節 (R4) と第6.6節 unlink 手順1 は「`usableForLogin = true` かつ active な行の **distinct な `(kind, hmac)`** の個数」を数えるが、2世代の行は `hmac` が異なるので distinct として **2 と数えられる**。SSO 専用ユーザー（`usableForLogin = true` の行は SSO 1件だけ。メール予約行は偽）が自分の移送窓中に unlink を実行すると、残り1件と誤判定して検査を通過し、**ログイン手段が0のアカウントが完成する**（第5.3節 step 5 (ii) の到達性検査は fail closed に働くので、以後どの経路でも入れない）。これは第6.9節の表が「検査述語を distinct `(kind, hmac)` に変える」で塞いだと宣言している経路そのもので、`usableForLogin` 列は第6.6節が挙げる原因 (a)（SSO 専用ユーザーの行数が常に2）は閉じるが、原因 (b)（ローテーション中の2世代並存）は閉じていない。第6.6節 unlink 手順1 が「どちらもローテーションの有無にかかわらず、あるいは通常運用の中で成立する」と書いている以上、(b) を閉じないままにはできない。
    - **(b) unlink の削除対象を選ぶ手段が無い。** 第6.1.1節 (R3) と第6.6節 手順2 は「対象 `(kind, hmac)` の**全世代の行**を削除する」と書くが、世代ごとに `hmac` が違うので「同じ credential の別世代の行」を突き合わせるキーが `credential_locators` に1つも無い。さらに第4.1.1節が定める同テーブルの列は `kind / hmac / generation / bucketIndex / credentialVersion / status / usableForLogin` だけで、**どの credential の行かを示すラベル（provider 名や安定した credential id）を持たない**。第6.1.1節 (R5)(ii) により認証済み経路は canonical から locator を導出できず、第11.1節（`:1760`）は `getCurrentUser` が `provider` / `providerSubject` を返さない現行の期待を維持すると決めているので、「Google の連携を解除する」という操作が対象行を特定する経路が設計上どこにも無い。第6.6節が link/unlink の前提として掲げる「クレデンシャルの集合を持つ」形が、`kind` と件数までしか表現できていない。
  - 提案: `credential_locators` と `credential_mappings` に**世代非依存の credential 識別子**を1列足し、それを (R3)(R4)・unlink の対象選択・到達性検査の突き合わせキーにする。第5.2.2節 (a) が `userId` について採ったのと同じ理屈（鍵に依存しない locator を分離する）を credential 側にも適用する形が最も素直で、たとえば `HMAC(鍵に依存しない固定 salt, canonical)` ではなく **signup / link 時に `IdGenerator` が採番する不透明な `credentialId`**（`callerToken` と同じ扱い。移送は行ごと引き継ぎ再採番しない）にすれば、第5.2.1節 (d) の canonical 規則変更にも耐える。あわせて (a) 用に「distinct な `credentialId`」へ述語を書き換え、(b) 用に UI へ出す非 PII のラベル（`kind` + provider 名。SSO subject は出さない）の所在を決める。第4.1.1節はテーブル・列の全数の正本を名乗っているので、この列が入らないと #37 がここで手を止める。

- **[B-002]** `encryptedCanonical` の AAD が `hmac` を束縛しているのに、鍵ローテーションの移送はその `hmac` を作り替える。第6.8節 手順2 は移送時の再暗号化を規定していないので、**移送された全行の canonical が復号不能になる**。
  - 場所: `.thread/34/design.md:758`（第6.2.1節 (b-2)「AAD に `(kind, hmac, encryptionGeneration)` を束縛する」）/ `:253`・`:1838`（同じ AAD 定義の再掲）/ `:1002`・`:1016`・`:1022`（第6.8節 手順2。移送で引き継ぐものとして `credentialVersion` と `callerToken` だけを名指ししている）/ `:1034`（「暗号化鍵のローテーションは別の走査」「locator が変わらないので移送が発生せず、行を同じ bucket の中で再暗号化するだけ」）
  - 理由: AAD に `hmac` が入っている以上、暗号文は「その世代の locator を持つ行」に束縛されている。移送先の行は `hmac` が新世代の値なので、暗号文をそのまま運ぶと復号時の AAD が暗号化時の AAD と一致せず、AES-256-GCM の認証が必ず失敗する。第6.2.1節 (b-2) は復号失敗を `SystemError(DataIntegrityError)` に翻訳して**その行を使う操作を fail closed で止める**と定めているので、移送完了後に次の3つが恒久的に壊れる — (i) パスワードリセットメールの宛先組み立て（第7.6節。第5.2.1節 (a) が「所有の唯一の証明はリセット経路」と書いている以上、アカウント回復手段そのものが失われる）、(ii) 設定画面の自メールアドレス表示（第6.2.1節 (c) 4 / `read-own-canonical`）、(iii) **次回のローテーションの再 HMAC**（第6.2.1節の動機2「新しい世代の locator は canonical からしか計算できない」）。(iii) が壊れるので、1回目のローテーション完了時点で2回目が原理的に実行不能になる。しかも移送直後は誰も復号しないため、最初のリセット依頼まで顕在化しない。
    第6.8節 手順2 は bucket の中で `encryptedCanonical` を復号している（再 HMAC のため）ので平文はその場にあり、再暗号化のコストは無い。にもかかわらず本文は移送で引き継ぐ値を `credentialVersion` と `callerToken` に限って列挙し、(3) の CAS 対象列にも暗号文系の列を含めていない。第6.2.1節 (b-1) は再暗号化を `rotate-encryption` ジョブ**だけ**の仕事として定義し、第6.8節末尾は「2つのローテーションは独立に走らせてよい」と明言しているので、本文どおりに実装すると暗号文はそのままコピーされる。
  - 提案: 第6.8節 手順2 (2) に「**移送先の行を書くときは、復号済みの canonical を新しい nonce と新しい AAD `(kind, 新 hmac, encryptionGeneration)` で再暗号化して書く**」を明示する（`encryptionGeneration` は据え置き。暗号化鍵のローテーションとは独立のまま保てる）。あわせて第6.2.1節 (b-2) の AAD 定義に「`hmac` は行が現に載っている世代の値であり、移送時は再暗号化される」の但し書きを付け、第11.2節の「本設計が新しく導入した列」表の `encryptionNonce` 行にも移送時の再生成を書く。あるいは AAD から `hmac` を外して B-001 の提案にある世代非依存の `credentialId` を束縛対象にすれば、AAD が移送で変わらなくなり (b-2) の付け替え防止と両立する — B-001 を解くならこちらのほうが整合が取れる。

### Warnings

- **[W-001]** 第6.1.1節 (R5) は locator 解決の正本を名乗っているが、SSO link を「`credential_locators` に永続化済みの行から取る」側に分類している。link の対象は新しい credential なので永続化済みの行が存在せず、この規則では手順が決まらない。
  - 場所: `.thread/34/design.md:705`（第6.1.1節 (R5)(ii)。「認証済み経路（パスワード変更 / **link** / unlink / 退会）は `credential_locators` に永続化済みの行から取る」「認証済み経路が canonical から locator を導出することは無い — 認証済みリクエストはそもそも canonical を持たず（メールアドレスは送られてこない）」）/ 矛盾の相手は `:944`（第6.6節 link 手順2「previous 世代が keyring に載っている間はその bucket を読んで既存行の不在を確認し、active 世代の bucket に予約を取る」）
  - 理由: link で予約する SSO credential は定義上まだ `credential_locators` に無い。しかも第5.3節 の SSO 経路（`:592-593`）が定めるとおり、link の起点では検証済み IdP アサーション由来の `subject` が request Worker の手元にあるので、canonical は**存在する**。したがって (R5) が挙げる論拠（「認証済みリクエストはそもそも canonical を持たない」「復号平文を request Worker へ運ぶことになる」）はいずれも link には当てはまらない。第6.6節 手順2 は 2 世代ぶんの locator を導出することを前提に書かれているので、本文と正本が食い違っている。#37 が (R5) を字句どおりに型・モジュール境界へ落とすと link 手順2 が書けなくなる（第5.5節 1 の3経路列挙で同じ理由の数え落としが起きたのと同型の問題である）。
  - 提案: (R5) を4分類に直す — (i) 未認証経路（canonical から active → previous）、(ii) 認証済み経路のうち**既存 credential を対象にするもの**（パスワード変更 / unlink / 退会。`credential_locators` から取る）、(iii) 認証済み経路のうち**新しい credential を登録するもの**（SSO link。検証済みアサーション由来の canonical から導出する。第5.3節 SSO 経路 2 の「クライアントが POST した値・リダイレクト URL のクエリから読んだ値は使わない」がここでも効くことを明記する）、(iv) リセット完了（トークン本体の `{generation}.{bucketIndex}`）。あわせて第6.6節 link 手順2 から (R5)(iii) への参照を張る。

- **[W-002]** 第5.1節 (3-b) が `callerToken` を「request Worker 内でのコード実行を得た攻撃者に対して効く2層目」と位置づけているが、第6.5.1節 phase 0 が同じトークンを request Worker へ返す設計になっているため、名指しした脅威に対しては成立しない。
  - 場所: `.thread/34/design.md:472`（第5.1節 (3-b)「これは多層防御の2層目である。1層目は「state Worker が公開ルートを持たない」ことで、request Worker 内でのコード実行を得た攻撃者に対してだけ2層目が効く」）/ 矛盾の相手は `:910`（第6.5.1節 phase 0 起点 A-1「同じ RPC で `account.callerToken` も返す」）と `:161`（`SESSION_SECRET` は request Worker が持つ）
  - 理由: request Worker でコード実行を得た攻撃者は `SESSION_SECRET` を握っているので、任意の `userId` について有効なセッショントークンを署名できる。`sessionEpoch` は単調増加の小さなカウンタなので数回の試行で一致させられる。そのうえで A-1 の class (1) エントリを叩けば、被害者の `account.callerToken` がそのまま返る。つまり2層目は、まさにそれが守るとされた攻撃者に対しては1回の追加 RPC で越えられる。`callerToken` が実際に意味を持つのは「binding には到達できるが `SESSION_SECRET` を持たない呼び出し元」（同一アカウント内の別 script、誤配線された内部経路、将来 state Worker が別の Worker から呼ばれる構成）に対してであり、その範囲では第5.1節 (3-b) が指摘した復号オラクル／ロックアウト原始関数の問題は正しく塞げている。本 Warning は機構の廃止を求めるものではなく、**脅威モデルの記述が実際の到達性と食い違っている**ことに対するものである。
  - 提案: 第5.1節 (3-b) の「1層目 / 2層目」の説明を、`callerToken` が守る相手を「`SESSION_SECRET` を持たない binding 保有者」に限定する形へ書き直す。あわせて残余リスク（request Worker のコード実行を得た攻撃者に対しては `callerToken` は防壁にならない）を第6.9節または第11.3節の #38 向け項目へ1行送る — 第5.1節 (3-c) が `purge-user-mappings` について同じ性質の残余リスクを正直に書いているので、扱いを揃えられる。

- **[W-003]** 第2.1節 F-4b が「Alarm 起動が CPU 予算の枠に含まれるかは公式に肯定も否定もされていない」としているが、同じ limits ページの FAQ が Alarm を invocation の一種として明示している。事実表の正本としての正確さの問題（結論は動かない）。
  - 場所: `.thread/34/design.md:71`（第2.1節 F-4b。種別欄「**未確認: Alarm / RPC が CPU リセットの契機に当たるか — 記載の不在による推論**」、出典欄「記載の不在」）。波及先は `:1208`（第7.4節）・`:1506`（第9.2節）・`:1905`（第11.4節の spike 一覧）
  - 理由: `https://developers.cloudflare.com/durable-objects/platform/limits/` を取得して確認したところ、footnote 4 が挙げるリセット契機は確かに "incoming HTTP request" と "WebSocket message" の2つだけで、そこは F-4b の記述どおりである。ただし同ページの FAQ に次の一文がある — 「By default, the maximum CPU time per Durable Objects invocation (**HTTP request, WebSocket message, or Alarm**) is set to 30 seconds」。**Alarm は 30秒の CPU 予算を持つ invocation として名指しで列挙されている。** 「記載の不在による推論」という種別付けは、この文を見落としている。設計の結論（保守的に読んで3階層とも件数で有界にする）は、残り CPU を読む API が無いことと `Date.now()` の凍結（F-32。原文の実在を確認済み）だけで独立に成立するので、**判断は一切変わらない**。変わるのは #37 が着手時に走らせる spike の内容で、この一文を出発点にすれば「Alarm ごとに 30秒が与えられるのか、着信間で共有されるのか」という一段細かい問いから始められる。
  - 提案: F-4b の出典欄を「記載の不在」から「limits ページ FAQ の当該文（Alarm を invocation として列挙するが、リセットの契機としては footnote 4 に挙げていない）」へ差し替え、種別は「未確認」のまま残す。第11.4節の該当行にも同じ一文を引く。
