## DO 境界・ルーティング

### Blockers

- **[B-001]** signup phase 2（`initialize-account`）のガードが「`account` 行が既に存在するなら**無条件で**拒否」と「phase 2 は冪等（同じ `operationId` なら成功を返す）」で正面から矛盾しており、前者を実装すると **phase 2 の応答喪失が「正常に作られたアカウントの破棄」に直結する**
  - 場所: `.thread/34/design.md:443`（第5.1節の RPC エントリ表）/ `:665`（第5.5節 5）/ `:837`（第6.3節 phase 2）/ `:867` — いずれも「無条件で拒否」。対する `.thread/34/design.md:893`（第6.4節）は「phase 2 は冪等（`account` 行があり同じ `operationId` なら成功として返す）」
  - 理由:
    - **同一セル内で既に破綻している。** `:837` は「`account` 行が既に存在するなら無条件で拒否する」と書いた直後に「同じ `operationId` で違う digest なら `ConflictError`」と書いているが、無条件拒否が先に効く以上 `operationId` / `payloadDigest` の比較には**到達しない**。`:443` の「無条件で拒否 + `operationId` / `payloadDigest` の CAS」も同じ理由で片方が死ぬ。
    - **saga の前進経路が phase 2 の冪等性に依存している。** 第6.4節は「User Data の初期化が完了した時点（phase 2 の成功）以降は前進」を規則として掲げ（`:897`）、`resume-signup` が phase 1b → 2 → 3 → 4 を前進させると定めている（`:899`）。ところがコーディネーターが phase 2 の成功を知る唯一の手段は**戻り値**である（`:904`「コーディネーターは phase 2 の**戻り値を受けて**自分の行に…印を書く」）。phase 2 が commit した後に応答が失われれば（DO のリセット、`.overloaded`、`ctx.abort()` — 第4.7節が「stub 呼び出し自体が throw する」と認めている経路）、`sagaCommitted` 印は立たず `resume-signup` は phase 2 を再送する。無条件拒否ならここで永久に前進できない。
    - **帰結は「到達不能アカウントが残る」ではなく「正常なアカウントが破棄される」である。** 再試行上限に達すると第6.4節 3 の終端規則が発火し、(3-i) `cancel-reservation` で全 mapping を回収したうえで (3-ii) `abandon-account` が `account.status` を `deleting` へ倒す（`:905-907`）。`abandon-account` のガードは「`operations` 行の `operationId` 一致 + `kind = 'signup'` + `phase` が `done` でないこと」（`:457`）で、phase 2 は `phase: 'activating'` を書くのでこの条件を満たす。**利用者から見ると「登録は成功したのに数分後にアカウントが消える」**。第6.4節が signup について「黙って到達不能アカウントを残すだけは選ばない」と決めた基準を、この経路が真逆の形で破っている。
    - **第5.5節 5 の主張も同時に偽になる。** 「これは 1 が破れた場合の二重の防波堤であり、**1 が成立している限り発火しない**」（`:665`）は誤り。locator 導出が正しくても、同じ正しい DO への phase 2 再送でこのガードは必ず発火する。
  - 提案: ガードを**条件付き**に書き直し、3箇所（`:443` / `:665` / `:837`。および `:867` の要約文）を揃える。第5.5節 5 が本当に欲しい保証は「**他人の**アカウントの DO に signup が書き込まない」ことなので、述語は「`account` 行が存在し、かつ同じ `operationId` の `operations` 行（`kind = 'signup'`）が**存在しない**なら拒否する。存在して `payloadDigest` が一致するなら成功として返す（no-op）。一致しないなら `ConflictError`」になる。この形なら (i) 第5.5節 5 の防波堤としての効き目は落ちず（他人の DO には自分の `operationId` の `operations` 行が無いので必ず拒否される）、(ii) 第6.4節の前進規則が成立し、(iii) `:837` の digest 比較が到達可能になる。あわせて第5.5節 5 の「1 が成立している限り発火しない」を「1 が成立している限り**他人の DO に対しては**発火しない」へ訂正する。

### Warnings

- **[W-001]** 鍵ローテーション移送の**巻き戻し経路**で移送先行を無条件に破棄する規則が、同じ設計が (R7) で掲げた「移送は移送元・移送先の両側を CAS で守る」に従っておらず、移送先に着地した credential 変更の中間状態を破壊しうる
  - 場所: `.thread/34/design.md:1062-1064`（第6.8節 手順2 の (3) CAS と巻き戻し）。対する規則は `:710`（第6.1.1節 (R7)）
  - 理由:
    - (3) の CAS は**移送元 P** に対してだけ定義されており、0行削除時の巻き戻しは「(2) で書いた**移送先 A** の行を破棄する」「(1) が追加した `credential_locators` 行を破棄する」と**無条件**に書かれている。移送先への書き込みなのに (R7) の CAS が掛かっていない。
    - この破棄が壊しうる状態が実在する。(2) が A に行を書いた時点で active 世代の lookup は A にヒットするので（`:1049` が自ら述べている）、以後の書き経路は A へ向かう —— 第6.5.1節 phase 1（`begin-credential-change` は起点 A なら `credential_locators` の両世代から選ぶので A を選びうる、起点 B なら (2) 以後に発行されたトークンが A 世代を運ぶ）、`report-login-result` の `failedAttempts`、`lastResetRequestedAt`。一方 (3) の CAS が失敗する条件は P 側の変化で、**(2) より前に step 3 を終えた login が (2) より後に step 7 を報告する**だけで成立する（step 4 の `PasswordHasher.verify` は PBKDF2 210,000 回で数百 ms 掛かる。第4.8節）。この2つが重なると、A に載った `changeState = 'pending'` / `pendingVerifier` が巻き戻しで消える。
    - 消えた後の状態は fail-closed ではなく**ログイン不能**に倒れる。phase 2（`advance-credential-change`）が先に走っていれば `sessionEpoch` は前進し `credential_locators` の `credentialVersion` は n+1 になっている一方、A の行は消え P の行は n のままなので、第5.3節 step 5 (iii) の照合が恒久的に不一致になる。既存セッションも epoch 前進で死んでいる。`resume-credential-change` は A の `jobs` にあるが対象行が無いので `poison` へ落ちる。復旧はパスワードリセットのやり直しだけである。
    - 設計自身が破棄を「**最適化であって正しさの拠り所ではない**」（`:1063`）と書いているが、それは「破棄しなくても (R9) が収束させる」という主張であって、「破棄が壊しうる」ことの否定になっていない。(R9) の新旧比較は `credentialVersion` の大小だけを見るので、`changeState` / `pendingVerifier` の消失は救わない。
  - 提案: 巻き戻しの移送先破棄を CAS 化する。「(2) が書いたスナップショットと**完全に一致する場合にだけ**削除する」とし、一致しなければ**破棄せずそのまま残す**（(R9) の新旧比較が次の走査で正本側へ収束させる）。第6.1.1節 (R7) の本文にも「移送先への書き込みは (2) だけでなく巻き戻しの破棄も含む」を明記し、(R6)（pending 行を移送しない）が**読み出し時点**の判定であって (2) 以後に pending が着地する窓を塞がないことを併記する。`credential_locators` 側の破棄についても同様で、`:1064` が既に「(R8) の単調性により値は正本以上に保たれている」と認めているので、こちらは「破棄しない」に倒しても不変条件は壊れない。

- **[W-002]** `credential_mappings` の `credentialId` を一意にしない根拠が、同じ設計が定めた Directory DO の命名規則（`dir:g{generation}:b{index}`）と矛盾する。「同じ bucket に2世代の行が並ぶ」状況は構造上発生しない
  - 場所: `.thread/34/design.md:253`（第4.1.1節。テーブル・列の正本）/ `:731`（第6.1.2節 (C3)。`credentialId` の正本）/ `:455`（第5.1節 `delete-mapping`）
  - 理由:
    - `:253` は「**`(credentialId, generation)` にも UNIQUE を張るが、`credentialId` 単独は一意ではない** — 新旧2世代の locator が偶然同じ bucket index に落ちると、同じ bucket に同じ `credentialId` の行が2つ並ぶためである」と書き、`:731` (C3) も同じ理由を繰り返している。
    - ところが Directory DO の名前は `dir:g{generation}:b{index}` で**世代を含む**（`:202` の概念図、`:685` 第6.1節 (d)「bucket の DO 名が `dir:g{generation}:b{index}` であり index だけでは DO を特定できない」、`:761` 第6.2節）。世代が違えば bucket index が一致しても**別の DO インスタンス**であり、1つの Directory DO の `credential_mappings` に載る行は常に同一世代である（第6.8節 手順2 も「previous 世代の bucket を走査して**新しい世代の bucket へ移す**」と、世代ごとに別 DO であることを前提に書かれている）。したがって bucket 内では `(credentialId, generation)` UNIQUE ≡ `credentialId` UNIQUE であり、非一意にする根拠が存在しない。
    - `:455` の `delete-mapping`「削除対象は引数の `credentialId` に一致する行（**同じ bucket に2世代の行が落ちていれば両方消える**）」も同根の誤り。正しい記述は第6.7節 手順3（`:1008`）の「**両世代の bucket に対して**削除を発行し、『無ければ成功』の冪等操作にする」の側であり、2つの節が「2世代 = 1 bucket 内の2行」と「2世代 = 2つの bucket」で食い違っている。
    - 実害は小さい（`(kind, hmac)` UNIQUE が canonical 重複を捕まえるので認可は緩まない）が、**正本を名乗る2節の根拠が誤っている**ので、#37 が本来張れる UNIQUE を「設計が非一意と断定しているから」と落とす。`record-credential-locator` / `reserve-credential` / 移送の (2) がバグで同一 bucket に同じ `credentialId` の行を2つ作っても、DB 側が検出しない状態になる。
  - 提案: `:253` / `:731` の根拠を差し替え、`credential_mappings` の `credentialId` に **bucket 内 UNIQUE** を張る（`(credentialId, generation)` UNIQUE は世代列が DO 名と冗長なので残しても害はない）。あわせて `:455` の括弧書きを「同じ credential の別世代の行は**別 bucket**にあるので、呼び出し元が世代ごとに `delete-mapping` を発行する（第6.1.1節 (R3)・第6.7節 手順3）」へ訂正する。`credential_locators`（User Data DO 側）は1 DO に両世代が同居するので `(credentialId, generation)` UNIQUE / `credentialId` 非一意で正しく、**訂正の対象は Directory 側だけ**である。

- **[W-003]** unlink のガードが `kind` を区別しないため、`kind = 'email'` のクレデンシャルを解除でき、アカウントから**回復手段（パスワードリセットの宛先）を恒久的に失わせられる**。第6.9節の締め出し経路一覧にこの行が無い
  - 場所: `.thread/34/design.md:987`（第6.6節 unlink 手順1）/ `:735`（第6.1.2節 (C5)）/ `:438`（第5.1節 クラス (1) の行）
  - 理由:
    - 手順1 の検査述語は「`usableForLogin = true` かつ active な行の distinct な `credentialId` を数え、対象 `credentialId` を除いた残りが0件なら拒否」（`:987`）で、`kind` を一切見ない。パスワード + SSO のアカウントで `kind = 'email'` を対象に指定すると、残りが SSO の1件になるので**検査を通過する**。
    - (C5)（`:735`）は設定画面のクレデンシャル一覧に `kind` を問わず `{credentialId, kind, label}` を出し、「unlink は `credentialId` を指定して発行する」と定めているので、UI 上も指定材料が揃っている。第11.1節の `getCurrentUser` DTO（`:1817`）も同じ3つ組の集合を返す。
    - 通過した結果は手順2〜3 が忠実に実行される —— `credential_locators` からメール行を全世代削除し、Directory の `credential_mappings` 行（`encryptedCanonical` を含む）と `password_reset_tokens` 行を削除する。以後そのアカウントは (i) `read-own-canonical` の対象行を失い自分のメールアドレスを表示できず、(ii) `request-password-reset` が mapping 不在の空振り経路へ落ちるので**リセットが恒久的に不能**になり、(iii) 第6.5.1節 起点 A のパスワード変更も対象行が無く成立しない。設計には「メールクレデンシャルを追加する」フローが存在しない（link は SSO 専用。第6.6節）ので、**利用者自身にも復旧手段が無い**。
    - 第5.2.1節 (a)（`:519`）は「所有の唯一の証明はパスワードリセット経路であり、リセットトークンの安全性がアカウント所有の安全性の上限になる」と断定している。その唯一の証明を、セッションを握った攻撃者が1回の unlink で消せる。以後 SSO 側で被害者が締め出されれば回復経路はゼロになる。第6.9節の一覧（`:1098-1111` の12行）にこの経路は無い。
    - 一方で第5.1節（`:438`）と第6.6節の見出しはいずれも「**SSO** link・unlink」と書いており、**設計の意図は SSO 限定である**と読める。つまり意図とガードの記述が食い違っている。
  - 提案: 手順1 の検査に「対象 `credentialId` の `kind` が `'sso'` であること」を追加し、`kind = 'email'` の解除経路が存在しないことを明示する（`BusinessRuleError`）。UI 側で出し分けるだけにしない —— 第6.6節自身が「この検査を最初に置くのは、ここが**唯一のアカウント到達性の権威**だから」（`:987`）と述べており、権威は DO 側にある。あわせて (C5) に「一覧に `kind = 'email'` も出すが解除操作は `kind = 'sso'` のみ」を書き、#35 の画面仕様（`:1817`）へ同じ制約を送る。将来メールアドレスの変更／再登録を入れる場合は unlink ではなく credential 変更 saga の一種として設計する旨も残しておくとよい。

### Notes

- **[N-001]** **`credentialId` 導入は、それが塞ぐと宣言した穴を実際に塞いでいる。** 世代非依存の同一性が要求される5箇所すべてで `credentialId` がキーになっており、`hmac` を使う箇所（bucket index 導出・bucket 内一意性・未認証経路の canonical → 行の解決）と役割が正しく分離されている（第6.1.2節 (C4)）。個別に追跡した結果は次のとおり。
  - **到達性検査**（第5.3節 step 5 (ii)、`:579`）— 照合が `credentialId` だけになり「世代を条件に含めるか」という問い自体が消えている。第6.8節 手順2 の移送窓（`credential_locators` に両世代が並存する）で login が落ちない、という §6.9 の主張と整合。
  - **ログイン手段の数え上げ**（(R4)、`:707` / `:987`）— `usableForLogin = true` × distinct `credentialId` の2条件で、(a) SSO signup がメール一意性のために置く行と (b) ローテーション中の2世代行の両方を正しく除外できる。`(kind, hmac)` では (b) が閉じないという説明も正しい（`hmac` は世代依存なので distinct 2件になる）。
  - **削除対象の選択**（(R3)、`:706` / `:990` / `:1008`）— unlink・退会とも `operations.targetLocators` / `credential_locators` から全世代分を引く形で揃っている。
  - **`credentialVersion` の更新範囲**（(R8)、`:711-714`）と**移送の新旧比較**（(R9)、`:715`）— upsert + 単調非減少 + 全世代同時更新の3点が揃っており、片方だけを入れると失敗モードが「旧パスワード復活」と「恒久ロックアウト」で入れ替わるだけ、という指摘も正しい。
  - **`encryptedCanonical` の AAD**（第6.2.1節 (b-2)、`:785-787`）— `hmac` を外して `(kind, credentialId, encryptionGeneration)` を束縛することで移送時の再暗号化が不要になり、付け替え防止は `credentialId` の一意性で維持される。移送で暗号文系3列をそのまま運ぶ（`:1060`）とも整合。
  - **`record-credential-locator` の冪等キー**（`(credentialId, generation)`）— 第5.1節 `:450`、第6.3節 phase 4 `:839`、第6.6節 手順4 `:979`、第6.8節 手順2 (1) `:1048`、第11.2節 `:1893` の**5箇所すべてで一致**している。`(kind, hmac)` に戻っている箇所は1つも無い。
  - **`credentialId` 自体が外部入力になる経路は無い。** 採番点は request Worker（第6.1.2節 (C1)、第6.3節 phase 0 `:834`「いずれもクライアントからは受け取らない」、第6.6節 手順1 `:973`）で、移送では再採番しない。unlink が `credentialId` を利用者から受け取るが（`:987`）、それは自 DO 内の `credential_locators` の**引き当てキー**として使われるだけで locator の材料にならないので、第5.5節の構造的保証は破れていない。
