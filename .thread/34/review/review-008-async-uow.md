## 非同期処理・UoW・migration

### Blockers

- **[B-001]** 第6.8節 手順2 の **(2)「移送先の bucket に active 行を書く」を担う RPC エントリが第5.1節の「クラス (2)(3) の全数」表に存在せず、(X3) が要求する「同じ `transactionSync` での `enqueueJob('rotate-encryption', ...)`」を実行する主体が定義されていない。**
  - 場所: `.thread/34/design.md:1363`（手順2 の4段）/ `:1391`（手順3「(1) と (4) は…RPC」）/ `:1373`（(X3) の enqueue）/ `:702-727`（第5.1節の全数表）/ `:1417`（`rotate-encryption` の投入点 (b)）
  - 理由:
    - **移送先は別 DO インスタンスである。** 移送元は `dir:g{prev}:b{i}`、移送先は `dir:g{active}:b{HMAC_active(canonical) mod bucketCount}` で、DO 名が世代を含むため（第6.1節 (d)・第4.1.1節が自ら断定）必ず別オブジェクトになる。したがって (2) は Directory → Directory の cross-DO RPC でしか実現できない。ところが第6.8節 手順3 は **「手順2 の (1) と (4) は Directory bucket → User Data DO の RPC である」と (1)(4) だけを RPC として名指しし、(2) を扱っていない。**
    - **第5.1節の表に該当エントリが無い。** 実際に表の全エントリを機械抽出したところ23本（クラス (2) が10本、クラス (3) が13本）で、`credential_mappings` の **`active` 行を丸ごと書く／読み比べる／巻き戻しで破棄する**エントリは1本も無い（`activate-reservation` は `reserved` → `active` の昇格で、移送は第6.1.1節 (R6) により `reserved` 行を対象外にしているので流用できない）。同表は `:729` で「**本表は「クラス (2)(3) の全数」を宣言している。本文が新しい RPC エントリを導入したら、本表にも必ず行を足す**」と自ら更新規則を置いており、その規則の破れである。
    - **本レビューの射程で問題になるのは (X3) の実行可能性である。** (X3) は「移送先 bucket が (2) で行を書いたのと**同じ `transactionSync` の中で** `enqueueJob('rotate-encryption', <定数 operationKey>, {}, now)` を発行する」ことを要求し、第7.4節の `kind` 全数表もこれを投入点 (b) として載せている（`:1584`）。ところが第8.2節は `enqueueJob` を `UnitOfWorkContext` のメソッドとして定義し、`ctx.storage.sql` の直接使用を usecase に対して禁じている（`:1839`）。**`enqueueJob` へ到達できるのは移送先 DO の内側で `UnitOfWorkProvider.run` を回す実行点だけ**であり、それは「移送先 bucket 上の RPC エントリ」以外に存在しない。エントリが未定義のままだと、#37 は (2) を「maintenance 経路が移送先へ直接書く」形で実装しうる（`rotate-remap` は maintenance 経路が1チャンクずつ駆動する同期 RPC だと第6.8節 手順2 で決め切っているので、この実装は自然な読みである）。その形では移送先 DO の内側でトランザクションが開かないので **(X3) が丸ごと実装されず、第6.9節の締め出し経路一覧の行18（`encryptedCanonical` の恒久的な復号不能 = アカウント回復手段の喪失、しかも最初のリセット依頼まで顕在化しない）に対する構造側の保険が消える。** 第6.8節 `:1417` は「(b) は (X2) が守られていれば発火しない保険だが、投入点として全数表に載せる（**載せないと #37 が (X3) を実装しない**）」と書いているが、投入点欄に載せるだけでは実行主体が決まらない。
    - あわせて、このエントリのガードが未定義である。`operations` 行を作らないので phase 条件は効かず（第5.1節 (3-d) が `record-credential-locator` について同じ問題を扱っている）、第5.1節 (3-c) は「`callerToken` はこの経路に流用できない — `callerToken` はアカウント単位の値で、チャンクは bucket 単位の操作だからである」と述べている。**`active` な `credential_mappings` 行を全列上書きできる無束縛の書き口は、(3-d) が `record-credential-locator` について閉じた「任意アカウントへ攻撃者のクレデンシャルを注入する」経路と同型である。** さらに移送先 locator は「注入された `activeKey` から導出する」値なので、第5.5節 1 の総則「呼び出し側の DO が**自分の SQLite に永続化済み**の locator だけ」にも当てはまらない（例1〜例3 のいずれでもない）。ガードと locator 規則の側は do-boundary / security 観点の担当だが、**(X3) の実行主体が決まらない限り本観点の結論（暗号鍵ローテーションの retirement 証明が fail closed に倒れる）も成立しない**ので、ここに記録する。
  - 提案:
    1. 第5.1節の表に **移送先 bucket 上のエントリを1本追加する**（例: `accept-remapped-mapping`。クラス (3)）。ガード欄には「移送する行が持つ `callerToken` の定数時間比較 + 第6.1.1節 (R9) の新旧比較 + 巻き戻し破棄の全列一致 CAS」のように、bucket 側が手元の材料だけで検証できるものを明記する（`callerToken` は移送対象の行そのものが持っているので、移送先が新規に書く場合は照合相手が無い点に注意 — 新規書き込みでは (3-c) と同じく「到達制御と監査」に落ちることを正直に書くか、別の材料を決める）。あわせて第5.1節の4群（(3-a)〜(3-d)）のどこに属するかを割り当て、第1.4節 検査5（クラス (3) の行数と4群の合計の一致）の期待値 13 を 14 へ直す。
    2. 第6.8節 手順3 の「(1) と (4) は…RPC である」を「(1)(2)(4) が cross-DO RPC であり、(3) だけが移送元ローカルである」に直し、(2) の**実行主体を「移送元 bucket → 移送先 bucket」に確定させる**（maintenance 経路が直接書く形を明示的に棄却する。棄却理由は (X3) が移送先 DO 内のトランザクションを要求すること）。
    3. 第5.5節 1 に**ローテーション移送の例外**を1つ足す（「一時注入された active 鍵と自分の行の復号 canonical から導出した移送先 locator」）。総則を書き換えるか例外として明示するかは第5.5節の担当に委ねる。
    4. 第11.2節の新設対象に、このエントリと (X3) の enqueue を実装対象として1行足す。

### Warnings

- **[W-001]** 第9.2節 条件2 が **`INSERT INTO search_fts(search_fts) VALUES('rebuild')` を選択肢として挙げているが、`'rebuild'` は分割不能なので「そのときは必ず分割する」という同節の要求と両立しない。**
  - 場所: `.thread/34/design.md:2010`（条件2）/ `:2012`（条件4 の同型の扱い）/ `:1649,1661`（`reindex` の (iii) 対象・チャンク上限）
  - 理由: 条件2 は「既存行を載せるには `INSERT INTO search_fts(search_fts) VALUES('rebuild')` … または projection の全行再実行が要り、**そちらが本条件に当たる**」と書いており、条件2 に当たる作業は `:2007` の宣言により「必ず分割する」対象になる。ところが `'rebuild'` は**1文で全文索引を削除して全行から作り直す単一 SQL 文**であり（SQLite 公式 `fts5.html`: "This command first deletes the entire full-text index, then rebuilds it based on the contents of the table or content table."）、中断・再開の単位が存在しない。`SAVEPOINT` も使えない（第2.1節 F-8。公式 `sql-storage` ページで実確認）。すなわち **`CREATE INDEX` について条件4 が「SQLite ではこれをチャンク分割できないので、`migrate-bulk` への逃がし先が無い」と特定した性質が、`'rebuild'` にもそのまま当てはまる。** 帰結も同じで、10 GB まで育った User Data DO で `reindex` が `'rebuild'` を発行すると CPU 予算超過 →（エラーではなく）エビクションとリセットで**途中まで進んで黙って落ちる**（第2.1節 F-4 / 第9.2節 `:1996` が自ら書いている失敗モード）。しかも第7.4節は `reindex` に (iii-a)（1チャンク1,000行）/ (iii-b)（20チャンク）の上限と `migration_progress` の永続カーソルを与えているので、**`'rebuild'` を選ぶ実装ではその3つがすべて空振りする。** 条件4 は同じ形の危険を明示的に名指しして回避策 (a)(b) を決め切っているのに、条件2 だけが分割不能な手段を無注記で並べている。
  - 提案: 条件2 の記述を「**`'rebuild'` は採らない**（1文で全索引を作り直すため分割不能で、条件4 の `CREATE INDEX` と同じ理由で逃がし先が無い）。`reindex` は projection の全行再実行として実装し、進捗は `migration_progress` の `(targetVersion, step)` カーソルに乗せる」に直す。第11.4節の spike 一覧に足す必要は無い（分割不能性は SQLite の仕様から確定している）。

- **[W-002]** 第7.4節 (iii-b) が中断時にジョブを `pending` へ戻すことと、**「次の Alarm へ回す」/ 第9.2節「外側の『25件』は `migrate-bulk` 1件に対して一度も発火しない」が、同一 Alarm 起動内での再 claim について矛盾する。** 1起動あたりの CPU 上界が読みによって25倍変わる。
  - 場所: `.thread/34/design.md:1649-1651`（(iii-b) と `pending` 復帰の論拠）/ `:1633`（claim 述語）/ `:1700`（上界 = 25 × 中間 × 内側）/ `:1998`（「25件は一度も発火しない」「効く保護は中間と内側の2つだけ」）
  - 理由: (iii-b) は「進捗カーソルのコミットと同じ `transactionSync` で `status` を `pending` へ戻し、`ownerToken` と `leaseUntil` を解放してから**次の Alarm へ回す**」と定める。ところが claim 述語は `WHERE operationKey=? AND (status='pending' OR (status='running' AND leaseUntil < ?))` で、**解放直後の行は `status='pending'` かつ `nextRunAt` は過去のまま**である。ジョブランナーは同じ起動の中で「1件ずつ処理し、25件まで」進むので、**次の反復で同じ行を再 claim してさらに20チャンク回せる。** 同節の `pending` 復帰の論拠は「次の Alarm 起動での再 claim 述語がリース満了まで一致しない」＝**次回起動**についてのものだけで、同一起動での再 claim を禁じる規則がどこにも無い。
    - 第9.2節 `:1998` は「外側の25件は `migrate-bulk` 1件に対して**一度も発火しない**（1件の巨大ジョブだから）ので、`migrate-bulk` に実際に効く保護は中間の反復回数上限と内側の行数上限の2つだけである」と断定している。これは「同一起動では再 claim しない」を前提にした読みである。
    - 一方 `:1700` は「1回の Alarm 起動で触る行数の上界は **25 × 中間上限 × 内側上限**で静的に決まる」と書いており、これは「同一起動で25回まで再 claim しうる」を前提にした読みである。
    - **どちらか一方しか成立しない。** 再 claim される読みだと、単一の `migrate-bulk` が1起動で 25 × 20 × 1,000 = 500,000 行を触れることになり、(iii-b) を新設した動機（「『1,000 行ずつ 100 万回』が (i)(ii)(iii-a) のどれにも違反せずに書ける」`:1653`）の圧縮率が20チャンク相当から500チャンク相当へ緩む。安全側に倒れる誤りではあるが、**CPU 予算超過の帰結がエビクションで「黙って落ちる」ことである以上、上界の見積りが25倍ずれるのは実装判断に直接効く。**
  - 提案: (iii-b) の規則に1文足して確定させる。「**(iii-b) で解放したジョブは、同じ Alarm 起動の中で再 claim しない**（ジョブランナーはその起動で解放した `operationKey` を除外する）」とすれば `:1998` の断定と整合し、上界は「25 × 中間 × 内側」ではなく「起動あたり最大25ジョブ、各ジョブは高々 中間 × 内側」になるので `:1700` の表現もそれに合わせる。逆に再 claim を許す設計にするなら `:1998` の「一度も発火しない」を撤回する。

- **[W-003]** 第7.4節が **`operationKey` の「収束」の意味を「次の1規則で両方を説明する」と宣言しているが、`send-mail` について挙げた説明（「同じ `nextRunAt` を渡すので何も起きず（＝重複が捨てられ）」）が、同節の `done` / `poison` → `pending` 再投入規則と衝突し、優先順位が書かれていない。**
  - 場所: `.thread/34/design.md:1592`（「収束」の意味を1つに固定する）/ `:1594`（早める方向にのみ）/ `:1599`（`done` / `poison` の行は `pending` へ戻す）/ `:1746`（同じ canonical の連打は行1本に収束する）
  - 理由: `:1594` は「既存行の `nextRunAt` より早い値で再投入されたら更新し、**同じか遅ければ何も書かずに成功を返す**」とし、`send-mail` については「連打は同じ窓に対して同じ `nextRunAt` を渡すので**何も起きず**（＝重複が捨てられ）」と説明する。ところが `:1599` は「**`status = 'done'` / `'poison'` の行に対する再投入は、同じ行を `pending` へ戻して `attempt` を0にし、`nextRunAt` / `payload` / `payloadDigest` を引数の値で置き換える**」と、`nextRunAt` の方向に関係なく行を復活させると定める。`send-mail` は Alarm が数秒で拾って `done` へ落ちる (C) 一回性ジョブなので、**同じ窓での2回目以降の依頼は「`pending` に対する再投入」ではなく「`done` に対する再投入」になるのが通常事象である。** すなわち `send-mail` について「何も起きず」は成立せず、行は毎回 `pending` へ戻され、Alarm が再度起きてジョブが再実行される。
    - 二重送信そのものは起きない（第6.2.2節 (b) により窓内の再依頼は「宛先を持たない側」の payload で書かれるので、復活した行は何も送らずに `done` へ落ちる）。したがって**利用者影響は無く、Blocker ではない**。しかし `:1592` が「`kind` によって逆の更新が要求される」問題を1規則で解決したと宣言している当のその例が、実は2規則の衝突で決まっていない。
    - 実害は課金と DoS 面に出る。復活は `setAlarm` 1回（＝1行の書き込みとして課金。第2.1節 F-24、公式 pricing ページで実確認）と Alarm 起動1回を毎回の再依頼につき生む。第7.6節 `:1747` が「同じ canonical への連打はジョブ行1本に収束する」ことを DoS 面の緩和として挙げているが、**収束するのは行数だけで、起床回数と rows written は依頼回数に比例する。**
  - 提案: `:1594`〜`:1599` の並びに優先順位を1文で明記する。たとえば「**`status` 別の規則が「早める方向にのみ」より優先する。ただし `done` / `poison` からの復帰は、引数の `nextRunAt` が現在時刻以降であるか、または `payloadDigest` が既存行と異なる場合に限る**」とすれば、`send-mail` の同窓連打（同じ `nextRunAt`・同じ digest）は復活せず `:1594` の説明どおりになり、周期ジョブの再投入（`:1599` が守りたいケース。定数キーの (A)(B) ジョブが平常時に `done` へ落ちた後の復帰）は引き続き通る。あわせて `:1746-1747` の「収束」の主張を「行数は1本に収束するが、起床と書き込みは依頼回数に比例する（第一防壁は第6.2.2節 (c) の WAF）」と限定する。

- **[W-004]** 第7.4節の **「時計を読む実装を1箇所も置かないので、凍結の影響を受けない」は、同節自身が要求している `leaseUntil` / backoff / `completedAt` / clamp / prune と矛盾する。** 字義どおり実装すると同節の機構が組めない。
  - 場所: `.thread/34/design.md:1645`（当該文）/ 矛盾する側は `:1633`（`leaseUntil < ?` の claim）/ `:1634-1635`（backoff の `nextRunAt` 先送りと `completedAt` に現在時刻）/ `:1637`（保持期間を過ぎた `done` / `poison` の prune）/ `:1620`（`now + 最小再開間隔`）/ `:1675`（`now + 再開間隔`）/ `:1687`（現在時刻+1秒への clamp）

It does not advance during code execution.」は正確な引用である。**したがって「経過時間で打ち切らない」という結論そのものは正しい**（打ち切りは同一コード実行中の差分に依存し、そこは進まない）。一方 `leaseUntil` / `nextRunAt` / `completedAt` は起動をまたいだ絶対時刻の比較なので、起動ごとに I/O を経て進む `Date.now()` で十分機能する。**この非対称を1文で書けば矛盾は解消する。**
  - 提案: 当該文を「**チェックポイント予算の打ち切り条件に時計を読まない**ので、凍結の影響を受けない。時刻列（`nextRunAt` / `leaseUntil` / `completedAt` / prune の保持期間）は**起動をまたいだ絶対時刻の比較**であり、`Date.now()` は起動ごとに I/O を経て進むのでそちらは成立する — 成立しないのは『同一コード実行中の経過時間の差分』だけである」に直す。
