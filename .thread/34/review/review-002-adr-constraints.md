## Warnings

- **[W-001]** `.adr/003` の影響節に、決定が「Cloudflare が公式に文書化していない workerd 上の FTS5 挙動」に依存しているというトレードオフが残っていない
  - 場所: `/Users/hikaru/github.com/tuanemuy/fog/.adr/003-sqlite-fts5-only-search.md:31-37`（影響節全体）
  - 理由: `.thread/34/design.md:98` は「trigram / `bm25` は公式ドキュメントに一語も無い（#10）ため、**この実測が `.adr/003-sqlite-fts5-only-search.md` の唯一の根拠**である」と明記し、しかもその実測の出典（`.thread/19/spike/fts5.integration.test.ts`）は先行ブランチ上にしか存在せず、`#37` に着手時の再確認 spike を課している（design.md 第11.2節）。この依存は寿命テスト・波及テストをどちらも明確に通る — trigram が使えなければ「FTS5 のみ」という決定そのものが成立せず、検索ドメイン・スキーマ・#35 の spec 改訂まで一斉に巻き戻る。ところが `.adr/003` の影響節は5項目とも「単純になる」「意味類似検索を提供しない」「索引の行数が増える」という**決定が成立した前提での帰結**だけで、決定の足元が未文書化のプラットフォーム挙動に懸かっていることが読めない。`.adr/` しか読まない読み手（`adr-guide.md` が名指しする architecture-audit / spec-sync）にとっては、この決定がリスクゼロに見える
  - 提案: 影響節に1行足す。仕組みは書かず「本決定は公式ドキュメントに記載の無い FTS5 の挙動（トークナイザとランキング関数）が実行環境で動くことに依存しており、その裏付けは実測1件である。実装着手時に再確認する（`.thread/34/design.md` の第2.1.1節・第11.2節）」程度で足りる。`.adr/004` がドメインポートの `Promise` 契約変更を影響節1行に留めたのと同じ扱い（`.thread/34/adr.md` ADR-022）で、AC-6 の粒度制約は破らない

- **[W-002]** `.adr/002` の影響節にある `.thread/1/adr.md` ADR-002 の去就が、決着済みなのに条件形のまま残っている
  - 場所: `/Users/hikaru/github.com/tuanemuy/fog/.adr/002-cloudflare-workers-and-user-data-durable-objects.md:40`
  - 理由: 当該行は「**認証権威の所在によっては**、…トレードオフ…が変わる。所在の決定と、それがセッション方式そのものを扱う**別 ADR を要するかの判断は** `.thread/34/design.md` の第3.1節と第5.1節に**ある**」と書かれている。しかし design.md 第3.1節は「`sessionEpoch` の照合を導入するので『サーバー側失効の手段が無い』というトレードオフは**解消する**」「セッション方式そのものは**変えない**」「したがって `.thread/1/adr.md` ADR-002 を supersede する**別 ADR は起こさない**。この判断は本 Issue で下し、結果を第5.1節に書いた」と断定しており、第5.1節も同じ結論を繰り返している（AC-21 の要求どおり本 Issue で決着済み）。この条件形は `.thread/34/plan.md:937` が計画した文言そのままで、当時はトポロジーが未決だったため妥当だったが、design.md で決着した後に更新されていない。結果として `.adr/` は「所在次第で変わりうる（＝まだ分からない）」としか語らず、**「4件目の ADR は不要」という台帳にとって最も重要な結論だけが作業ログ側にある**。ステータス節が「承認済み」と断定している ADR の影響節に、決着済みの事項が未決の体で残るのは自己整合性としても弱い
  - 提案: 条件形をやめて断定に直す。例:「`.thread/1/adr.md` の ADR-002 が受け入れたトレードオフのうち『サーバー側失効の手段が無い』は、認証権威を利用者ごとの Durable Object に置くことで解消する。ステートレスなセッション方式そのものは変えないため、セッション方式を扱う別 ADR は起こさない（判断の根拠は `.thread/34/design.md` の第3.1節・第5.1節）」。行数も語数もほぼ変わらず、AC-6 にも触れない

- **[W-003]** `.adr/002` の影響節が「利用者ごと1オブジェクトへの直列化」というトレードオフを挙げていない
  - 場所: `/Users/hikaru/github.com/tuanemuy/fog/.adr/002-cloudflare-workers-and-user-data-durable-objects.md:37-41`（影響節全体）
  - 理由: 影響節が挙げる代償は「ベンダーロックイン」と「オブジェクト単位の移行・容量・PITR・エクスポート・退会削除の運用」の2つで、いずれも運用面である。一方 design.md は、この決定から**実行モデル上の強い制約**を導いている — 第4.8節は「PBKDF2 210,000 回を single-threaded な DO の中で回してはいけない。User Data DO で回せばそのユーザーの全リクエストが止まり、Directory bucket で回せば同じ bucket に写像される全ユーザーの認証が止まる」と結論し、第3.2節はそれを受けて `passwordHasher` を request Worker 側の DI に残す設計にしている（`.thread/34/adr.md` ADR-023）。「1利用者のリクエストが1オブジェクトに直列化する」は物理分離を選んだことの裏面であり、CPU を使う処理をどこに置いてよいかを横断的に縛る。寿命テスト・波及テストとも通る
  - 提案: 影響節に1行足す。「1利用者のリクエストが1つのオブジェクトに直列化するため、重い計算を利用者データの内側で回せなくなる（具体は `.thread/34/design.md` の第4.8節）」程度。既存 `.adr/001` の影響節が「失うもの」も明示しているのと同じ水準に揃う
