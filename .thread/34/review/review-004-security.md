## セキュリティ

### Blockers

- **[B-001]** 鍵ローテーション手順2 の「移送先に既に行がある場合は書かずに (3)(4) だけ行う」規則が、**移送先の行が古い場合**を区別しない。結果として、リセット完了で設定した新パスワードが黙って捨てられ、**旧 `passwordVerifier` が正本に戻る**（＝パスワードリセットの無効化 / 旧パスワードでのログイン成立）。
  - 場所: `.thread/34/design.md:1019-1024`（(2) の CAS 規則と (3) の CAS 規則）、`.thread/34/design.md:693`（「まだ移送されていない credential のトークンは旧世代 bucket で有効なままでよい」）、`.thread/34/design.md:913`（起点 B の locator はトークンが運ぶ世代で確定する）
  - 理由: 設計自身が「(2) の後・(3) の前でのクラッシュと再実行は想定内の経路」と宣言している（`:1019`）。その中断状態では同じ credential の mapping 行が**移送元（previous）と移送先（active）の両方に生きて**いる。ここで credential 変更 saga が**移送元の行に着地**すると、移送先の行は古いスナップショットのまま取り残される。着地先が移送元になるのは偶然ではなく、**起点 B（リセット完了）では構造的に必然**である — トークンは発行時の `{generation}.{bucketIndex}` を運び（`:682`）、`consume-reset-token` は「同 bucket に mapping 行が存在すること」を確認するだけなので（`:447`）、旧世代 bucket に行が残っている限り必ずそちらに着地する。
    具体的な列: (a) rotation が credential C について (1) を実行し新世代 locator を記録、(b) (2) で active bucket に旧状態のコピー（`passwordVerifier` = 旧, `credentialVersion` = n）を書く、(c) **(3) の前にクラッシュ**、(d) 利用者が旧世代 bucket 宛に発行済みのトークンでリセットを完走 → previous bucket の行が `passwordVerifier` = 新 / `credentialVersion` = n+1 になる、(e) rotation が再実行される → 読み出した移送元は n+1 だが **(2) は「移送先に同一 `userId` の行があるから書かない」を選ぶ** → (3) の CAS は「今回の読み出し（n+1）と一致するか」しか見ないので**成功して移送元を削除**、(4) が旧世代 locator を削除。
    終状態は「active bucket に旧 `passwordVerifier` / `credentialVersion` = n」「`credential_locators` は active 世代の行だけ（cv = n）」であり、第5.3節 step 5 (ii)(iii) は**どちらも通る**。**旧パスワードでログインでき、リセットで設定した新パスワードは通らない。** 第6.8節が (2) の CAS を導入した根拠（`:1020`「再実行が新 bucket の新しい値を previous 行の古い値で上書きし、旧パスワードが復活する」）は**上書き方向だけ**を塞いでおり、**移送先が陳腐化する方向**は無防備である。移送元の CAS（`:1024`）も同じ理由で救わない — 移送元は「そのチャンクの読み出し値」と一致しており、正しく削除されてしまう。
  - 提案: (2) の分岐条件を「行の有無 + `userId` 一致」から**世代間の新旧比較**に変える。`credentialVersion` は credential ごとの単調増加カウンタなので（`:926`）判定材料は既に揃っている。
    - **(2) の規則**: 移送先に行が無ければ書く。あって `userId` が同じなら `credentialVersion` を比較し、`source.credentialVersion > dest.credentialVersion` なら **移送先を移送元のスナップショットで上書きする**（`passwordVerifier` / `changeState` / `operationId` / `failedAttempts` / `nextAttemptAllowedAt` / `lastResetRequestedAt` / `encryptedCanonical` / `encryptionGeneration` / `encryptionNonce` / `callerToken` を含む行全体）。`source.credentialVersion < dest.credentialVersion` なら**移送元を消すだけ**（既に移送先が正本）。等しい場合だけ現行の「書かずに (3)(4)」でよい。
    - あわせて **(3) の CAS 失敗時に「(2) で書いた移送先の行を破棄する」（`:1024`）の対象を、中断後の再実行でも成立する形にする** — 現行の文言は同一チャンク内でしか成り立たない（クラッシュすると破棄の実行主体が消える）。上の新旧比較を入れれば再実行が自動的に収束するので、破棄は最適化として残せる。
    - 第6.1.1節に規則として昇格させる（例: 「(R8) 2世代に行が並存する状態では `credentialVersion` が大きい側が正本であり、移送は必ず正本の側へ収束させる」）。第6.9節の締め出し／破れ経路一覧にも行を足す。

- **[B-002]** `credential_locators` 側の `credentialVersion` / `usableForLogin` 更新に**世代の規則が無い**。第6.1.1節 (R3) が全世代を対象にしているのは**削除だけ**で、更新は第6.5.1節 phase 2 の「当該行」1行に閉じている。さらに `record-credential-locator` の冪等述語が本文内で食い違っており、どちらの解釈を採っても**ログイン不能**（片方は恒久）に落ちる。
  - 場所: `.thread/34/design.md:905`（phase 2「`credential_locators` の当該行の `credentialVersion` を1つ進め」）、`.thread/34/design.md:703`（(R3) は削除のみ）、`.thread/34/design.md:1016`（rotation (1) は「旧行は残す」＝世代違いの行を**追加**する）、`.thread/34/design.md:450`（`record-credential-locator` は「無ければ成功」の冪等操作）、`.thread/34/design.md:949`（link 手順4 は「`credential_locators` に同じ `(kind, hmac)` の行があれば成功として返す」）、`.thread/34/design.md:577`（step 5 (iii) の `credentialVersion` 照合）
  - 理由: 2点ある。
    1. **世代スキュー**。rotation が (1) を実行した直後（active 世代の locator 行 cv = n を追加済み、(2) 未実行）に credential 変更が走ると、起点 A の A-2 は active bucket に mapping が無いので previous bucket に着地し（`:910`「両方が返り…先に成功したほうを採る」）、phase 2 は **previous 世代の locator 行だけ**を n+1 に進める。active 世代の locator 行は n のまま取り残される。その後 rotation が再実行されると (1) は既存行を見て no-op、(2) が n+1 の mapping を active bucket へ書き、(4) が previous 世代の locator 行を削除する。終状態は **Directory 側 n+1 / `credential_locators` 側 n** で、step 5 (iii) が恒久的に不一致になり **login が拒否され続ける**。しかも phase 2 は `sessionEpoch` も進めているので既存セッションも死んでおり、利用者は「パスワードを変えた直後から一切ログインできない」状態になる。脱出はパスワードリセットのみ（起点 B なら現世代の行に着地して cv が揃うため）で、第6.9節が「fail closed が締め出す方向へ働く経路は列挙して塞ぐ」と宣言している一覧に**この行が無い**。
    2. **冪等述語の自己矛盾**。第6.6節 link 手順4 は述語を `(kind, hmac)` と明記するが（`:949`）、`credential_locators` の一意性は `(kind, hmac, generation)` であり（`:244`）、rotation (1) は同じ `(kind, hmac)` で**世代違いの行を追加する**ことを前提にしている（`:1016`「旧行は残す」）。第6.6節の述語をそのまま実装すると **rotation の (1) が常に no-op** になり、(4) が旧世代行を消した時点で `credential_locators` にその credential の行が1つも無くなる。step 5 (ii) の到達性検査が落ちて**恒久ログイン不能**になり、しかもリセット完了（phase 2 の「当該行」が存在しない）でも復旧しない。第4.1.1節は「本表と第6〜9章の本文が食い違ったら本表を直す」という更新規則を持つが、この矛盾は**述語の定義そのもの**なので表の更新では解消しない。
  - 提案:
    - 第6.1.1節に更新側の規則を足す（(R3) と対にする）。例: **「(R8) `credential_locators` の `credentialVersion` / `usableForLogin` の更新は、その credential の**全世代の行**に対して行う」**。第6.5.1節 phase 2 の「当該行」を「同じ `(kind, hmac)` を持つ全世代の行」に書き換える。第6.6節 link 手順4 と第6.8節 (1) は世代違いの行を足す操作なので、これと矛盾しない。
    - `record-credential-locator` の冪等述語を **`(kind, hmac, generation)`** に確定させ、既存行があった場合は「成功して何もしない」ではなく **`credentialVersion` / `usableForLogin` を引数の値で上書きする upsert** にする。第5.1節の表（`:450`）と第6.6節（`:949`）の両方を揃える。
    - 上書きにしないと B-001 の修正も完結しない — (2) を新旧比較にして Directory 側が n+1 に収束しても、`credential_locators` 側が n のままなら step 5 (iii) で締め出しに変わるだけである。**B-001 と B-002 は片方だけ直すと失敗モードが入れ替わるので、対で直すこと。**

### Warnings

- **[W-001]** 第5.1節 (3-a) が掲げる「**CAS と phase 条件が守る**（存在しない saga を前進させることも、記録されていない `operationId` で phase を飛ばすこともできない）」という保証が、**`operations` 行を新規作成する側のエントリには成立しない**。そのため `callerToken` による束縛が「読み」にだけ掛かり「書き」に掛かっていないという非対称が残っている。
  - 場所: `.thread/34/design.md:466-473`（(3-a)/(3-b)/(3-c) の3群）、`.thread/34/design.md:446`（`begin-credential-change` のガード欄）、`.thread/34/design.md:449`（`advance-credential-change`）、`.thread/34/design.md:450` と `.thread/34/design.md:1031`（rotation 経路の `record-credential-locator`）
  - 理由: 該当は3本ある。
    - **`begin-credential-change`** — ガード欄は「認可の判定は呼ぶ前に request Worker が済ませる」「Directory はここで認可を再判定しない」であり、**DO 側の束縛が1つも無い**（`callerToken` も CAS も phase 条件も無い）。ところが同じ locator に対する**読み**（`lookup-credential-by-locator`）は `callerToken` の定数時間比較を要求している（`:444`）。すなわち「検証材料は読めないが差し替えはできる」という状態になっている。差し替えれば `resume-credential-change` の Alarm が phase 2 / 3 を自走させるので、**任意アカウントのパスワードを攻撃者のものへ置き換えられる**（乗っ取り原始関数）。
    - **`advance-credential-change`（phase 2）** — 第6.5.1節 phase 2 は「`operations` に記録し」と定義しており（`:905`）、**このエントリが `operations` 行を作る側**である。したがって (3-a) の「記録されていない `operationId` で phase を飛ばせない」は当てはまらず、任意の新規 `operationId` で呼べる。単独で呼ぶと `sessionEpoch` と `credentialVersion` だけが前進して Directory 側と不一致になり、**恒久ロックアウト原始関数**になる（B-002 の 1. と同じ終状態）。
    - **rotation 経路の `record-credential-locator`** — 第6.8節 手順3 は「同じ saga・同じ冪等キー機構を使う」としか書いていない（`:1031`）が、rotation は User Data DO 側に `operations` 行を作る手順を**持たない**。#37 が「phase 条件は `operations` 行を新規作成して満たす」と実装すると、このエントリも無束縛になり、`reserve-credential` + `activate-reservation`（どちらも `callerToken` 検証を持たない）と組み合わせて**任意アカウントへ攻撃者のクレデンシャルを追加**できる（第5.3節 step 5 (ii) の到達性検査は `credential_locators` を見るので、そこへ注入できれば検査は通る）。逆に「既存の `operations` 行を要求する」と実装すると rotation が動かない。どちらに倒すかが未決である。
  - 悪用の前提は「request Worker 内でのコード実行（binding 到達性）」であり、**これは設計自身が第5.1節 (3-b) で採用した2層目の脅威モデル**（「1層目は state Worker が公開ルートを持たないこと。request Worker 内でのコード実行を得た攻撃者に対してだけ2層目が効く」）そのものである。その脅威モデルのために `read-own-canonical`（復号オラクル）と `delete-mapping`（ロックアウト）を `callerToken` で束縛しておきながら、より強い3本を無束縛のまま残しているのは設計の自己矛盾である。
  - 提案:
    - **`begin-credential-change` に起点別の束縛を課す。** 起点 A（パスワード変更）は A-1 で既に `account.callerToken` を取得しているので（`:910`）、引数に載せて mapping 行の値と定数時間比較する。起点 B（リセット完了）は `consume-reset-token` が**同じ bucket**で走るので、消費したトークン行に `operationId` を記録し、`begin-credential-change` は「その `operationId` で直前に消費されたトークンが当該 credential のものであること」を条件にする（あるいは2本を1 RPC に統合する）。どちらも新しい材料を必要としない。
    - **`advance-credential-change` に `callerToken` を要求する。** Directory 側の mapping 行は `callerToken` を持っているので（`:253`）、phase 2 の引数に載せて User Data DO の `account.callerToken` と比較すればよい。
    - **rotation 経路の `record-credential-locator` について「`operations` 行を誰が作るか」を確定させる。** `callerToken` を mapping 行から運んで `account.callerToken` と比較する形にすれば、`operations` 行を作らずに束縛できる（rotation は認証状態の変更ではないので `operations` を持たせる必然が無い）。
    - 第5.1節 (3-a) の文言を「CAS と phase 条件が守る」から「**既存の saga 状態を前提とするエントリ**は CAS と phase 条件が守る」へ改め、**saga を新規に開始できるエントリを別群として明示**する。

- **[W-002]** 第5.1節の表は「クラス (2)(3) の全数」を宣言し、#37 への正本かつ更新規則付きの表と位置づけられている（`:462`）が、**SSO link 手順2 の予約が呼び出し元欄から漏れている**。
  - 場所: `.thread/34/design.md:442`（`reserve-credential` の呼び出し元欄）と `.thread/34/design.md:944`（link 手順2）
  - 理由: `reserve-credential` の呼び出し元は「request Worker（未認証）または コーディネーター bucket（`resume-signup` の phase 1b）」としか書かれていないが、link 手順2 は **User Data DO（および `resume-link` の Alarm）**が Directory bucket の予約を呼ぶ経路である。同表は `activate-reservation` について「コーディネーター bucket（signup）/ User Data DO（link）」と両方を書き分けており、`check-previous-generation` も `record-credential-locator` も link 由来の呼び出し元を明記しているので、`reserve-credential` だけが非対称である。また link 手順2 は `callerToken` を予約行に載せる（`:943`）のに、表のガード欄にその記述が無い。
  - ガード自体（既存 active 行との一意制約 + `operationId` / `payloadDigest` の CAS）は link でも同じなので、直ちに悪用可能な穴にはならない。ただし表が「全数」を名乗り、しかも「本表と本文が食い違ったら本表を直す」という更新規則を持つ以上、#37 が信頼境界の全数を表だけから読むときに1経路を数え落とす。
  - 提案: `reserve-credential` の行に「User Data DO（link 手順2 / `resume-link`）」を足し、ガード欄に「link 経路では予約行に `callerToken` を載せる（第6.6節 手順1〜2）」を書く。
