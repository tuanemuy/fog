- **[B-001]** OAuth 2.1 認可コード / PKCE / `jti` 一回性テーブルの引き取り先 Issue 番号が事実と食い違う
  - 場所: `.thread/34/design.md:256`（第4.1.1節）、`.thread/34/design.md:598`（第5.4.1節）
  - 理由: 両箇所とも「**#12 の範囲**であり本書では名前を確定させない」と書いているが、**#12 は「SSO・パスワードリセット」**で、その実装チェックリスト54行に OAuth 2.1・認可コード・PKCE・AI クライアント認可は1行も無い（`gh issue view 12` で確認）。OAuth 認可を実際に持つのは **#13「AIクライアント接続（OAuth認可・一覧・失効）」**である。第4.1.1節は「**本表はテーブルの全数と…列の全数の両方の正本である。#37 が実テーブルと実列を判断する根拠はこの表である**」と宣言しているので、その表に載る唯一の「定義を他 Issue へ預けたテーブル」の預け先が実在しないことになる。#37 の担当者が「この短命テーブルは誰が定義するのか」を #12 に確認しに行っても該当項目が無く、ここで手が止まる。第5.4.1節が「放置すると #12 が Directory 側に別の解決表を足す方向へ流れる」という予防目的でこの節を書いている以上、宛先違いは目的そのものを失わせる。
  - 提案: 第4.1.1節・第5.4.1節の「#12 の範囲」を **#13** に訂正する。あわせて第5.4.1節が予防している「Directory 側に別の解決表を足す方向へ流れる」の宛先も #13 に直す。#13 のチェックリストは `spec/inventory/` 由来なので、第11.1節の `spec/inventory/frontend.md` 行と同じ枠で「#13 のチェックリストとの照合」を #35 側へ送るとなお良い。

- **[W-004]** 第4.1.1節（列の全数の正本）に AES-256-GCM の nonce の置き場所が無い
