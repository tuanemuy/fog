## セキュリティ

### Blockers

- **[B-001]** 鍵ローテーション中、クレデンシャルの一意性が世代をまたいで保証されない（重複アカウント / 到達性の奪取）
  - 場所: `.thread/34/design.md:534`（第6.1節 (c)）、`:616`（第6.3節 phase 1）、`:750`（第6.8節 手順2）、`:708`（第6.6節 link 手順2）
  - 理由: 第6.1節 (c) は「同じ canonical は必ず同じ bucket に落ちる（同一世代・同一鍵なら決定的）ので、bucket 内の一意制約がグローバル一意性と等価になる。**bucket 間の調整は要らない**」と断定している。しかし括弧内の但し書き「同一世代・同一鍵なら」が、結論の側に反映されていない。読み経路（login）は `:465` で「active → previous の順に引く」と2世代を見るのに対し、**書き経路（signup phase 1 / SSO link 手順2）は active 世代の locator しか導出せず、previous 世代の bucket を一切見ない**。第6.8節のローテーションは 256 bucket をチェックポイント走査する長時間の保守作業なので、この窓は現実に数時間〜数日オーダーで開く。
    帰結は2つあり、どちらも認証境界の破れである。(i) 未移送の canonical（previous 世代にしか行が無い）に対して新規 signup / SSO link が**成功する** — 既存利用者のメールアドレス・SSO 主体で第三者がアカウントを作れる。しかも `:465` の login は active を先に引くので、以後は正規利用者ではなく後発アカウントが解決先になる（正規利用者は自分のアドレスでログインできなくなる）。(ii) その後 `rotate-remap` が旧行を移送しようとすると移送先に別ユーザーの active 行があり、`:750`「移送先の bucket に active 行を書いてから、元の previous 行を消す」に衝突時の規則が無い。
    設計自身は他の箇所で2世代並存を認識している — `:732`（退会）は「鍵ローテーション中は active 世代と previous 世代の両方に行が存在しうるので、両世代の bucket に対して削除を発行し」と明記している。退会だけがこれを見て、一意性登録が見ていないのは非対称であり、実装（#37）は第6.1節 (c) の断定をそのまま読むので穴のまま入る。
  - 提案: 第6.1節 (c) の結論を「一意性の検査は keyring に載っている**全世代**の bucket に対して行う」へ改める。具体的には signup phase 1 / link 手順2 を、(1) active 世代 bucket に予約を取る、(2) previous 世代が存在する間は previous 世代 bucket に対しても「既存行が無いこと」を確認し、無ければ**トゥームストーン付きの予約**を置く、の2段にする（DO 間分散トランザクションを使わないので、決定順の予約 + 敗北時の冪等補償という第6.5節の既存機構にそのまま乗る）。あわせて第6.8節 手順2 に「移送先に既に active 行がある場合の規則」（同一 `userId` ならスキップ、異なる `userId` なら移送せず poison + 運用エスカレーション）を書く。ローテーション中は signup / link を停止する運用回避を採るなら、それを設計の制約として明記し #38 へ送ること（「告知して失敗を想定する」は `:538` でリセット依頼についてだけ書かれており、登録側には及んでいない）。

- **[B-002]** 発行済みパスワードリセットトークンを無効化する手段が設計から消えている（credential 変更後もトークンが生き残る）
  - 場所: `.thread/34/design.md:231`（第4.1.1節の `password_reset_tokens` 行）、`:535-540`（第6.1節 (d)）、`:678-690`（第6.5.1節 credential 変更 saga）、`:728-733`（第6.7節 退会）
  - 理由: 第4.1.1節は `password_reset_tokens` を「リセットトークンのハッシュと TTL（bucket 内で一意）」と定義しており、**どの credential / どの `userId` のトークンかを引く列が無い**。現行 spec（`spec/database/index.md:77-101`）は `user_id` 列と `prt_user_idx`（用途欄に「ユーザーの既存トークン**無効化**・整理」と明記）を持っているので、これは既存設計からの明確な後退である。
    その結果、credential 変更 saga（第6.5.1節）の phase 1〜3 のどこにも「対象 credential の未使用リセットトークンを消す」手順が置けない。攻撃シナリオは設計自身が第6.5.1節冒頭（`:673`）で挙げている典型経路そのものである — 攻撃者がアカウントを乗っ取ってリセットを1回依頼しトークンを保持 → 正規利用者が気づいてパスワードをリセット（`sessionEpoch` 前進、`credentialVersion` 前進、`passwordVerifier` 差し替え）→ **攻撃者の古いトークンは TTL 内なら依然有効なので、もう一度リセットを完走して奪い返せる**。さらに `:690` の「別の `operationId` による変更依頼が `pending` 中に来た場合は後勝ちで `pendingVerifier` と `operationId` を差し替える」規則が、この上書きを設計として認めてしまっている。
    退会（第6.7節 手順3）も同様で、削除対象は `credential_mappings` 行だけであり `password_reset_tokens` 行に触れない。第6.2.1節 (d)「退会が完了した時点で bucket 側には何も残さない」が守られない。
  - 提案: `password_reset_tokens` に対象 credential のキー（`kind` + 全長 HMAC。`userId` でもよいが bucket 内では credential 単位のほうが自然）を持たせ、それに対する索引を定義する。そのうえで (1) 第6.5.1節 phase 1 の同じ `transactionSync` で「対象 credential の未使用トークンを全消費（`used_at` を立てるか物理削除）」を必ず行う、(2) 第6.6節 unlink 手順3 と第6.7節 手順3 でも同じ削除を行う、を手順として書く。`verifyAndConsume` の使い捨て性（`spec/database/index.md:92`）だけでは「別のトークンがもう1本ある」ケースを塞げないことを明記すること。

- **[B-003]** メールアドレス local 部への NFKC + lowercase 正規化が、登録者の所有しないメールボックスにアカウントとリセットメールを紐づけうる
  - 場所: `.thread/34/design.md:409-412`（第5.2.1節 (a)）、`:575`（第6.2.1節 (a) — 保持するのは canonical のみ）、`:937-941`（第7.6節 — 宛先は bucket が持つ原本 = canonical）
  - 理由: 正規化手順は「NFKC 正規化 → …→ local 部を lowercase 化」と定めており、**local 部にも NFKC を適用する**。NFKC は互換等価な文字を ASCII へ畳むので、全角英数（U+FF41 等）・合字（U+FB01 `ﬁ` → `fi`）・上付き文字などが別の文字列に変わる。一方 SMTP の local 部はオクテット単位で不透明であり、`ａｂｃ@example.com`（全角）と `abc@example.com` は**別のメールボックス**である。
    そして第6.2.1節 (a) は原本として `encryptedCanonical`（＝正規化後の値）しか保持せず、第7.6節のメール送信ジョブはその復号結果を宛先に使う。したがって **利用者が打鍵した実アドレスは復元不能で、メールは正規化後の別アドレスへ送られる**。日本語 IME で全角のままアドレスを入力する事故は、本プロダクトの想定利用者において十分現実的である。
    さらに悪いのは、signup にメールアドレス所有確認の phase が存在しないこと（第6.3節の saga は phase 0〜4 のいずれにも確認手順を持たず、`packages/core/src/application/identity/registerWithPassword.ts` にも無い）。すると、A が全角で入力して作ったアカウントの canonical が B の実アドレスに一致した場合、**A のアカウントのリセットリンクは B のメールボックスに届き、B が A のアカウントを乗っ取れる**。逆に A 自身はリセット導線から締め出される。
    設計は第5.2.1節 (c) で SSO subject について「provider 由来の opaque 値であり、正規化すると provider 側の同一性判定とずれる」と正しく判断している。メールの local 部にも同じ理屈（配送側の同一性判定とずれる）が当てはまるのに、そこだけ判断が反転している。
  - 提案: いずれかに倒し、理由を第5.2.1節に書く。(i) **NFKC を domain 部に限定し、local 部は `trim()` + lowercase までに留める**（現行 `packages/core/src/domain/identity/valueObject.ts:47` の `trim().toLowerCase()` からの変更を最小にする案）。(ii) local 部に非 ASCII を含む入力を `BusinessRuleError(InvalidEmail)` で拒否する（構造チェックの拡張として `EMAIL_PATTERN` と同じ検証点に置ける）。(iii) canonical は一意性判定にのみ使い、**配送用の原本を正規化前の値として別に暗号化保持する**（ただし PII の保持形が1つ増えるので (i)/(ii) より重い）。あわせて「所有確認が無いこと」を設計の既知の前提として明記し、B-002 と合わせてリセット経路が唯一の所有証明であることを #35 / #38 へ引き継ぐこと。

- **[B-004]** `sessionEpoch` ガードの網羅性主張が、現行の認可ゲート実装に対して成立しない。しかも #37 への引き継ぎがその修正を明示的に禁じている
  - 場所: `.thread/34/design.md:381-383`（第5.1節）、`:1378`（第11.2節 `apps/web/app/presentation/` の行）／実装 `apps/web/app/presentation/currentUser.ts:17-26,34-54`、`apps/web/app/presentation/authState.ts:18-23`
  - 理由: 第5.1節は「User Data DO 側の全 RPC エントリの先頭で `account` テーブルの現在値と照合する」「**epoch ガードを通らない RPC エントリは signup の1本だけである**」を #37 への断定として置き、`:391` で「この照合は追加の往復を生まない — 認証済みリクエストはどのみち自分の User Data DO を叩くからである」としている。この前提が現行実装で成立していない。
    `currentUser.ts:17-26` の `getCurrentUserId` は `sessionCodec.verify` の戻り値だけで `userId` を確定し、DB も DO も触らない。同ファイル `:28-33` の JSDoc は `requireUserId()` を「**The authoritative guard**」と宣言している。そして `authState.ts:18-23` の `readAuthStateFn` は `getCurrentUserId()` の結果だけで `{ authenticated: true }` を返し、これが `_app.tsx` の `beforeLoad` から全保護ルートで走る。つまり **epoch を進めて失効させたはずのセッションが、認証済みシェルの描画とルーティング判定を通過する**。データ取得は DO を叩くので最終的には拒否されるが、「認可の権威がどこか」が実装と設計で食い違ったまま残る構造であり、DO を叩かない画面・サーバー関数を1つ足した時点で本物のバイパスになる。
    これを塞ぐには `currentUser.ts` / `authState.ts` の役割を「トークン真正性の前段チェック」に格下げし、権威を DO 側へ移す改修が要る。ところが第11.2節（`:1378`）は `apps/web/app/presentation/` について「**server-function エントリとエラー応答ミドルウェアは残る。変わるのは usecase の直接呼び出しが DO facade 呼び出しになる点だけである**」と書いており、#37 の担当者はこの2ファイルを変更対象と認識できない。
  - 提案: 第5.1節に「`requireUserId()` / `readAuthStateFn` は DO を叩かないので epoch ガードの外側にある」を明記し、(1) `requireUserId()` の JSDoc から "authoritative guard" の位置づけを外して DO 側ガードが権威であることを書き換える、(2) `readAuthStateFn` を epoch 照合込みにする（＝ DO への1往復を許容する）か、`beforeLoad` の判定を「ナビゲーションの利便であって認可ではない」と明示して保護データの描画が必ず DO を経由することをテストで固定する、のいずれかを #37 の作業として第11.2節に追加する。「認証済みリクエストはどのみち DO を叩く」を設計の不変条件として掲げるなら、それを破る経路（DO を叩かないサーバー関数）を作らない規約もあわせて書くこと。

- **[B-005]** 濫用抑止の機構がそのまま標的型のアカウントロックアウトに転用でき、脱出経路も同じ設計で塞がれている
  - 場所: `.thread/34/design.md:605-606`（第6.2.2節 (a)(b)）
  - 理由: (a) は「login の照合失敗ごとに `failedAttempts` を進めて**指数的に** `nextAttemptAllowedAt` を先送りする」「`nextAttemptAllowedAt` 未到達の照合は…ダミー材料経路へ倒して」「成功時に `failedAttempts` をリセットする」と定める。カウンタの単位は canonical credential（`credential_mappings` 行）であり、IP・デバイス・セッションではない。
    したがって被害者のメールアドレスを知る攻撃者は、誤ったパスワードを投げ続けるだけで `nextAttemptAllowedAt` を無限に先送りできる。ロックアウト中の試行はダミー経路へ倒れる（＝失敗）ので `failedAttempts` は減らず、正規利用者が正しいパスワードを入れても「成功時のリセット」に到達できない。**上限も、時間経過による自動減衰も、失敗が本人由来か攻撃者由来かを分ける鍵も設計に無い。**
    脱出経路であるはずのパスワードリセットも同じ節の (b) が塞ぐ — 「同じ `credential_mappings` 行に `{ lastResetRequestedAt }` を持ち、一定間隔内の再依頼は**ジョブを投入せずに成功を返す**」。攻撃者がリセット依頼を打ち続ければ `lastResetRequestedAt` は常に新しく、被害者の依頼は「成功」表示のままメールが届かない。しかも第7.6節（`:944-950`）が列挙オラクル対策として応答の均一化を要求しているので、被害者は自分がスロットルされていることを知る手段が無い。
    第6.2.2節は「未認証経路の濫用抑止」を主題に掲げ、bucket レベルの `overloaded` を (c) で WAF へ送っている。その同じ節が個別アカウントに対する恒久的 DoS を新設しているのは、抑止策の設計として不整合である。
  - 提案: (a) について「カウンタは credential 単位と発信元単位の**両方**を持ち、ロックアウトは発信元単位で先に効かせる」「credential 単位のバックオフには天井（例: 一定時間で頭打ち）と時間減衰を置き、ロックアウト中の試行はカウンタを進めない」を設計の制約として固定する（具体値は #38 でよいが、**天井と減衰の存在自体は #38 へ送らない**）。(b) について「リセット依頼のスロットルは、直前の依頼が実際にメール送信まで到達した場合にのみ更新する」「スロットル状態でもトークンの再発行を伴わない再送を一定回数許す」など、被害者の脱出経路を残す規則を書く。あわせて (c) の WAF が発信元単位の第一防壁であることを (a) の天井設計の前提として明記すること。

### Warnings

- **[W-001]** `rotate-remap` の再実行が、より新しい `passwordVerifier` を古い値へ巻き戻しうる
  - 場所: `.thread/34/design.md:750`（第6.8節 手順2）、`:757`
  - 理由: 手順2 は「移送先の bucket に active 行を書いてから、元の previous 行を消す」とだけ書いてあり、**移送先に既に行がある場合の規則が無い**。ジョブは at-least-once（第7.7節 3）で、`alarm()` は CPU 予算超過時に「途中まで進んで黙って落ちる」（`:902`）ため、書き込み後・削除前のクラッシュと再実行は想定内の経路である。その間に当該 credential へパスワード変更（第6.5.1節）が完走していると、再実行が新 bucket の新しい `passwordVerifier` / `credentialVersion` を previous 行の古い値で上書きし、**旧パスワードが復活する**。`credentialVersion` も巻き戻るので login step 5 (iii) の照合は「Directory も User Data も古い値」で通ってしまう可能性がある。
  - 提案: 手順2 に CAS 条件を書く — 移送先に行がある場合は `credentialVersion` を比較し、移送先が同値以上ならスキップ（冪等成功）、`userId` が異なるなら移送せず poison + エスカレーション（B-001 と同じ受け口）。あわせて「移送は `credentialVersion` を保存する（増やさない）」ことも明記すること。

- **[W-002]** 生のパスワードリセットトークンが発行からメール送信までどこに置かれるかが未定義で、`jobs.payload` に恒久化される方向に倒れている
  - 場所: `.thread/34/design.md:869`（第7.4節 `payload` 列 —「**PII を入れない**」とのみ規定）、`:537`（第6.1節 (d) — 保存するのはハッシュ）、`:944-950`（第7.6節）
  - 理由: `password_reset_tokens` はハッシュしか持たず、外部 I/O（メール送信）は必ず「トランザクションでジョブ行を書く → コミット後に Alarm が拾う」形になる（第7.6節 冒頭）。したがって**生トークンはジョブ行に載るしかない**が、`payload` の制約は「PII を入れない」だけで「秘密を入れない」ではない。結果として、DB 漏えい時にトークンを使えなくするための設計（`spec/database/index.md:79` が明示的に理由を書いている）が、ジョブ行の側から無効化される。しかも DO の書き込みは PITR の durable log に30日残る（第2.1節 #20）ので、`done` 後に行を prune しても消えない。
  - 提案: 第7.4節の `payload` 制約を「PII **および再利用可能な秘密**を入れない」へ広げ、リセットトークンの扱いを明示する。実現案としては (i) 生トークンを送信直前に bucket 内で決定的に導出する（`HMAC(bucket 内の秘密, tokenId)` の形にし、`payload` には `tokenId` だけを載せる）、(ii) ジョブ行に生トークンを載せる場合は送信成功時に同じトランザクションで payload を消去し、PITR 窓に残る事実を第10.1節と #38 のリスク記述に含める、のいずれか。

- **[W-003]** 「epoch ガードを通らない RPC エントリは signup の1本だけ」が、DO ↔ DO の saga RPC 面を数え落としている
  - 場所: `.thread/34/design.md:383`（第5.1節）、`:520`（第5.5節 1 の但し書き）、`:651`（第6.4節）、`:689`（第6.5.1節）、`:754`（第6.8節 手順3）、`:730-733`（第6.7節）
  - 理由: 第5.1節は「それ以外のすべての RPC エントリは epoch ガードを通る、を #37 への断定として置く」と書く。しかし第3.2節で state Worker に `USER_DATA` / `IDENTITY_DIRECTORY` の両 binding を配線した結果、User Data DO には**セッションを持たない内部エントリ**が少なくとも4系統ある — signup 前進（phase 2 / 4）、credential 変更 phase 2（`sessionEpoch` と `credentialVersion` を進める）、`rotate-remap` の `credential_locators` 更新、退会の手順3〜4。これらは照合すべき epoch を持ちようがないので、断定は文字どおりには実行不能である。#37 が断定を素直に読めばこれらのエントリで実装が詰まり、逆に例外扱いすれば「ガードの無いエントリの集合」が誰も列挙していない状態でコードに入る。しかもこれらは `sessionEpoch` の前進・`account.status` の書き換え・`credential_locators` の削除という**最も強い権限**を持つエントリである。
  - 提案: 第5.1節を「RPC エントリを (i) 利用者由来（epoch ガード必須）、(ii) signup（`account` 行不在ガード）、(iii) saga 内部（session を持たない。ガードは binding 到達性 + `operationId`/`payloadDigest` の CAS + phase 条件）の3クラスに分ける」と書き直し、(iii) を第4.1.1節と同じ「全数の正本」形式で列挙する。あわせて (iii) が request Worker からは呼ばれないこと（呼べてしまう binding 構成なら、なぜ許容するのか）を明記すること。

- **[W-004]** 新設する3つの秘密が、既存の `secrets.ts` が持つ構築境界の保証をどれも引き継いでいない（クライアント漏えい経路を含む）
  - 場所: `.thread/34/design.md:150-153`（第3.2節の配布境界表）、`:428-438`（第5.2.3節）、`:577-584`（第6.2.1節 (b)(b-1)）／実装 `packages/core/src/application/di/secrets.ts`
  - 理由: 現行の `SESSION_SECRET` は3つの保証を持つ。(1) `MIN_SESSION_SECRET_LENGTH = 32` の下限チェック（`hmacSessionCodec.ts:21,68-72`）、(2) ブランド型 `SessionSecret` + `requireSessionSecret` により「チェックを通した値しか型を得られない」構築境界、(3) `RequestSecrets` を**入れ子**に置くことで `createRequestContainer` の rest-spread が秘密を `container.config` へ運ばず `loadAppContext` 経由でクライアントへ出ないようにする不変条件（`secrets.ts` の JSDoc がこの3点を明示的に書いている）。
    設計は `AI_CLIENT_TOKEN_SECRET` と `DIRECTORY_ROUTING_SECRET` の keyring を request Worker 側の DI に載せることを決めているが、この3点のどれにも言及がない。とくに (3) は実害が直接的で、**keyring 配列を `RequestServerConfig` にフラットに置いた実装はブラウザへ routing keyring を配ってしまう**（型エラーは出ない、と `secrets.ts` の JSDoc が明言している）。`IDENTITY_MAIL_ENCRYPTION_KEY` は state Worker 側だが、鍵長・世代の妥当性チェックの置き場所は同じ問題である。
  - 提案: 第3.2節または第5.2.3節に「新設する秘密は `RequestSecrets` / 対応する state 側の秘密型の**入れ子**に置き、それぞれブランド型 + 構築時チェック（最小長、世代の一意性、active が1件であること）を通す」を制約として書き、第11.2節の `改修` に `packages/core/src/application/di/secrets.ts` を追加する。あわせて `SESSION_SECRET` / `AI_CLIENT_TOKEN_SECRET` が世代付き keyring なのか単一鍵なのかを確定させる — `:152` の表現は3つとも keyring と読めるが、`:428-438` は `DIRECTORY_ROUTING_SECRET` についてしか世代解決を書いておらず、セッション検証側の多世代照合は未定義である。

- **[W-005]** 退会の「bucket 側には何も残さない」が PITR の30日窓と両立しないことが、削除の完全性として書かれていない
  - 場所: `.thread/34/design.md:599`（第6.2.1節 (d)）、`:728-741`（第6.7節）、`:1181-1195`（第10.1節）
  - 理由: 第6.2.1節 (d) は「退会が完了した時点で `encryptedCanonical` を含む `credential_mappings` 行を**物理削除する**。bucket 側には何も残さない」と断定する。しかし PITR は SQLite-backed DO の DB 全体を過去30日まで戻せる（第2.1節 #20）ので、**削除は30日間は取り消し可能であり、消去の完了時点は退会時点ではない**。設計はこの事実を第6.2節 (iv) の議論（`:561`「PITR の durable log も30日残る」）では正しく使っているのに、退会の消去範囲では使っていない。第10.1節も「どちらか一方の restore だけでアカウントが復活することは無い」までで、**両方を戻せば復活すること**と、運用者が単独で実行できることには触れていない。
  - 提案: 第6.7節 または 第10.1節 に「退会による削除は即時消去ではなく、PITR 保持期間（30日）が経過して初めて不可逆になる」「退会済み `userId` の DO に対する PITR 実行は禁止し、承認手続きの対象とする」を設計上の結論として書き、手順と監査は #38 へ送る（第11.3節の PITR の項に1行足す）。#38 のセキュリティ・運用ドキュメントが利用者へ「削除しました」と説明する際の正確さに直結する。

- **[W-006]** credential 変更が AI クライアントトークンを一切失効させない決定に対し、補償手段が「ドキュメントに書く」しか無い
  - 場所: `.thread/34/design.md:491-499`（第5.4節）、`:688`（第6.5.1節）
  - 理由: 決定自体（利用者の期待に合う、接続ごとの独立した認可である）は妥当で、`.thread/34/design.md:499` は帰結を隠さずに書いている点で誠実である。ただし補償手段が「#38 の運用ドキュメントと利用者向け導線に明記する」だけであり、**インシデント復旧の実効性が利用者の読解に依存する**。攻撃者がパスワードを握っている間に AI クライアント接続を1本作れば、被害者がリセットを完走しても攻撃者のアクセスは `exp` まで（または被害者が接続一覧に気づいて個別 revoke するまで）残る。侵害復旧としては不完全である。
  - 提案: 少なくとも1つの構造的な補償を設計側で決めておく。案は (i) リセット完了画面で AI クライアント接続の一覧と「すべて失効」を**必須の導線**として出す（画面要件なので #35 の `spec/pages/` へ送る）、(ii) `ai_client_connections` に接続作成時の `credentialVersion` を記録し、リセット完了時に「そのバージョンより後に作られた接続」だけを自動失効させる（利用者の期待を壊さずに攻撃者の持ち込み分だけを切れる）、のいずれか。(ii) は同じ DO 内の1列で済み、追加の往復が無い。

- **[N-001]** 第5.2節 (c)（`:399-401`）の非露出リストは、現行実装より一段厳しく、質が高い。とくに **未認証経路では `userId` もログに出さない**（`:400`）を「ログ閲覧権限を持つ内部者に対する列挙オラクル」として理由づけている点、`passwordVerifier` が未認証リクエストに応答して script 境界を越える値であることから **RPC の引数・戻り値ロギングを有効化する構成そのものを禁止**している点は、実装時に効く具体性がある。#38 のログ設計はここを起点にすればよい。

- **[N-002]** 第8.3節 (e)（`:1076-1087`）が DO への RPC を新しい信頼境界として正面から扱い、「ブランドは型レベルにしか存在せず構造化クローンで失われるので、facade はブランド型を受け取らない」と結論づけているのは正しい。`packages/core/src/domain/identity/valueObject.ts:19,37,111,125,142,168` を確認したところ、実際に全 VO が `string & { readonly [brand]: true }` 形式であり、記述は事実と一致する。`CLAUDE.md`「validated at exactly two points」を「transport 境界 + DO 内側の値オブジェクト構築」として維持する整理も無理がない。

- **[N-003]** 第6.2.1節 (b-2)（`:586-590`）の AEAD 設計は妥当である。行ごと・書き込みごとのランダム96ビット nonce、**AAD に `(kind, hmac, encryptionGeneration)` を束縛**して bucket 内での暗号文付け替え（「B のメールアドレスを A の原本にすり替えてリセットメールを別アドレスへ送らせる」）を検出可能にする、復号失敗を `SystemError(DataIntegrityError)` で fail closed にして黙って未登録扱いにしない、の3点はいずれも正しい判断である。暗号鍵の世代管理と再暗号化ジョブ（(b-1)）を routing secret の世代体系と**独立した番号体系**にした点も、2つのローテーションが別の理由で走ることを踏まえた妥当な設計である。

- **[N-004]** 第5.4節の「`scope` はトークンを信頼せず、保存された現在値との**積**を有効 scope とする」（`:489`）は、失効（`status`）が全否定にしか効かず権限**縮小**に効かないという穴を正しく指摘したうえで塞いでいる。`typ` audience タグを鍵分離に**加えて**課す判断（`:487`）も、現行 `hmacSessionCodec.ts:30-42` の `parsePayload` が `uid` / `exp` の存在しか見ていないという実装事実に基づいており、記述は正確である。

- **[N-005]** 第5.3節 step 3〜4 のダミー検証材料は、現行実装 `packages/core/src/application/identity/loginWithPassword.ts:34-45,74-89` の `DUMMY_PASSWORD_HASH` / `burnVerificationTime` をそのまま移せる形になっている。ただし現行は `DEFAULT_PBKDF2_ITERATIONS` を `typeof DUMMY_PASSWORD_HASH_ITERATIONS` として宣言することで**片方だけ上げるとコンパイルが通らない**という結合を型で作っており（`pbkdf2PasswordHasher.ts:15-29`）、さらに「過去の低コストで書かれたハッシュは rehash-on-login まで等化が崩れる」という既知の限界も JSDoc に記録されている。設計はダミー材料を「request Worker 側の定数でもよい」と書くだけでこの結合と限界を引き継いでいないので、#37 の引き継ぎ（第11.2節）に1行足しておくと失われずに済む。
