## DO 境界・ルーティング

### Blockers

- **[B-001]** cross-DO saga の前進ジョブ（分類 (C)）が `poison` に達したときの終端が定義されておらず、設計自身が Blocker 級と判定した「`active` な孤児 mapping + `credential_locators` 行なし」の状態が単一世代のまま再生する
  - 場所: `.thread/34/design.md:1491`（第6.9節 SSO link の行）/ `.thread/34/design.md:1332-1339`（第6.6節「前進の駆動」）/ `.thread/34/design.md:1250-1254`（第6.4節 3 の終端規則）/ `.thread/34/design.md:1699`（第7.4節「backoff と poison」）/ `.thread/34/design.md:1657`（第7.4節 分類 (C) は `done` から復帰しない規則）
  - 理由:
    - 第7.4節は**すべての**ジョブについて「失敗時は `attempt` を進め、指数バックオフで `nextRunAt` を先送りする。**上限回数を超えたら `status='poison'` にして** `terminalReason` を残し」と断定しており、`resume-link` / `resume-signup` に例外を置いていない。第7.7節 項5 も同じ（「上限超過は `poison` にして `terminalReason` を残す」）。
    - **第6.9節 SSO link の行が自己矛盾している。** 同じ1行の中で、塞ぎ方を「**`resume-link` で常に前進させる**」と書きながら、末尾で「**`resume-link` は分類 (C) なのでバックオフ上限で `poison` に落ち、それ以降は誰も予約行を見ない**」と認めている。後半の認識は `reserved` 行側の回収（`reservedUntil` + `sweep-reservations`）を正当化するためだけに使われており、**手順3→4 の落下で残る `active` な孤児 mapping の側には適用されていない**。ところが `resume-link` が poison に落ちれば、その状態はまさに第6.6節が「この孤児は誰にも回収されない…結果はその SSO 主体の永久ロックである」と書いて `resume-link` を新設して塞いだ状態そのものである。
    - **回収経路が1本も無いことは設計自身が列挙済みである。** 第6.4節 3 が「この孤児は `sweep-reservations`（`status: 'reserved'` の行しか見ない）・`sweep-orphan-mapping`（`operations.targetLocators` は link / unlink 用で signup には書かれない）・`finalize-withdrawal`（`deleting` 前提）のいずれの対象でもない」と書いている。link の場合、`sweep-orphan-mapping` の残件条件は第7.4節 (1-B) で **`kind = 'unlink'` 限定**と決め切ってあるので（`.thread/34/design.md:1679`・`:1685`）link 行は拾われない。
    - **利用者による再試行も効かない。** 再 link は request Worker が**新しい `credentialId`** を採番する（第6.1.2節 (C1)）ので、手順2 の `reserve-credential` は同じ `(kind, hmac)` に既存の `active` 行がある状態で走る（第5.1節 `reserve-credential` のガード「既存 active 行との一意制約」）。`resume-link` の `operationKey` は対象 `operationId` を含む（第7.4節、分類 (C) の `operationKey`）ので、poison 行の復活（`.thread/34/design.md:1656`）も掛からない。したがって**利用者側に自己回復手段が無い**。設定画面のクレデンシャル一覧は `credential_locators` 由来（第6.1.2節 (C5)）なので、その SSO は「未連携」に見えたまま連携できない。
    - **発火は現実的で、しかも攻撃者が誘導できる。** `resume-link` は再開のたびに手順2・手順3 の Directory RPC を通る（`operations.phase` は `'reserving'` と `'done'` しか定義されていないので中断点はこの粒度である）。第6.2.2節が「攻撃者は単一のメールアドレス／主体を狙って撃てるので、任意の1 bucket を選んで 1,000 req/s の soft limit へ追い込み `overloaded` にできる」と断定しており、`overloaded` は第4.7節でリトライ禁止なので `resume-link` の失敗としてカウントされる。**手順3 が1度成功した直後にその bucket を overload させ続ければ、バックオフ上限まで押し切って上記の状態を作れる。** 攻撃者不在でも SQLITE_FULL（第4.7節 行2）や連続エビクション（第2.1節 F-4）で同じ状態になる。
    - **同じ穴が signup にもある。** 第6.4節 3 の終端規則は発火条件を「**再開が `ConflictError` で確定する**」場合に限定して書いてある。phase 3 / phase 4 が `.overloaded` などで失敗し続けてバックオフ上限に達する経路では `ConflictError` が出ないので 3-i（`cancel-reservation` による回収）も 3-ii（`abandon-account`）も走らず、**同節が「恒久的に再登録不能」と書いた状態がそのまま残る**。SSO signup は常に2 bucket を跨ぐ（第6.3節）ので、これは例外構成ではない。
    - **credential 変更と退会には同じ穴が無い**（対称性の確認）。credential 変更は `resume-credential-change` が poison に落ちても、`request-password-reset` → `consume-reset-token` → `begin-credential-change` が**新しい `operationId` の新しいジョブ行**を作るので回復する（第6.2.2節 (a) の脱出経路 (i)）。退会は `purge-user-mappings`（第6.7節「最後の砦」）が operator 経路として明記されている。**link と signup だけが、poison 後の回復手段を設計側に持たない。**
  - 提案: **分類 (C) の cross-DO saga 前進ジョブに、`ConflictError` に限らない「バックオフ上限到達時の終端規則」を1つ置く。** 材料は既にあるので新しい RPC も列も要らない。
    - **link**: `resume-link` が上限に達したら、`operations.targetLocators` の全世代 locator へ `delete-mapping`（引数は `credentialId` + `account.callerToken`。「無ければ成功」の冪等操作）を発行して mapping を回収し、`operations` 行を `terminalReason` 付きで `phase = 'done'` にしてから poison 化する。link は「常に前進」が原則だが、**終端では巻き戻しが正しい** — 利用者から見て「連携に失敗した」であり、canonical が解放されるので再 link で回復できる（第6.6節が手順2 敗北時に既に採っている扱いと同じ）。`account.callerToken` は退会していない限り生きているので束縛材料も揃っている。
    - **signup**: 第6.4節 3 の終端規則の発火条件を「`ConflictError` で確定した場合」から「**前進不能が確定した場合（`ConflictError` またはバックオフ上限到達）**」へ広げる。手順（3-i → 3-ii）はそのまま流用できる。
    - あわせて第6.9節 SSO link の行の塞ぎ方を「`resume-link` で常に前進させる」から「前進させる。ただし上限到達時は上記の終端規則で回収する」へ直し、同じ行が持つ「`poison` に落ちる」という認識と整合させる。

### Warnings

- **[W-001]** E-3（`kind` 全数表）の `finalize-withdrawal` の投入点欄が `abandon-account` を取りこぼしており、E-2 が委譲した「`jobs` への投入点の全数」が実際には全数になっていない
  - 場所: `.thread/34/design.md:1632`（E-3 の `finalize-withdrawal` 行）/ `.thread/34/design.md:538`（E-2 の `jobs` 行の委譲宣言）/ `.thread/34/design.md:740`（第5.1節 `abandon-account` のガード欄）/ `.thread/34/design.md:1252`（第6.4節 3-ii）
  - 理由: E-2 の `jobs` 行は「全ジョブの投入点（第7.4節の `kind` 全数表の「投入点」欄へ**委譲する。本欄が唯一の委譲である**）」と宣言しており、E-3 の投入点欄が `jobs` への書き手の全数の正本になっている。ところが E-3 の `finalize-withdrawal` 行は「第6.7節 手順1」だけを挙げているのに対し、第5.1節の `abandon-account` の行は「`account.status` を `deleting` へ倒して **`finalize-withdrawal` を投入する**」と明記しており、第6.4節 3-ii も「回収は退会と同じ経路（第6.7節）に乗る」と書いている。**投入点は2箇所ある。**

- **[W-002]** 第1.4節の検査8 / 検査9 をファイルから逐語で実行すると、ヒアドキュメントの2スペース字下げが値に混入して**全項目が誤検出になる**
  - 場所: `.thread/34/design.md:225-291`（検査8 の `while IFS=: read -r t c` + `COLS` ヒアドキュメント）/ `.thread/34/design.md:303-308`（検査9 の `/tmp/e2skip.txt` の `SKIP` ヒアドキュメント）
  - 理由: どちらのコードブロックも箇条書きの中にあるため、実ファイル上ではヒアドキュメントの本文行が2スペース字下げされている（`  account:status` / `  operations:rotate-encryption`）。`IFS=:` の分割は先頭の空白を取り除かないので、`$t` が `"  account"` になり `grep -E "…\`$t\`"` が必ず外れる。**実測: 検査8 を逐語で実行すると `MISSING column in 4.1.1:` が62行すべて出る**（`  account.status` のように先頭に空白が残る形で出力される）。同じ理由で検査9 の除外リストも `grep -qx "$s:$w"` に一致しなくなり、除外済み4件が「E-2 の欄に無い書き手候補」として出る。**字下げを剥がせば両検査は完全にパスする**（本レビューで確認済み）ので、検査本体のロジックは正しく、**壊れているのは再現手順だけ**である。
    - 第1.4節は「**すべて「出力が期待どおりであること」で判定し、目視の読み下しに依存しない**」と宣言している節であり、しかも同節は R8（注記の `-> 10` が実測と食い違い）と R9（再カウント awk が自己参照で 2,242 行を出した）で**2回続けて検査そのものが壊れていた**箇所である。62行の偽陽性は「E-1 に列が1つも無い」という見え方をするので、次の改訂者が Blocker として報告して1ラウンド消費する現実的な危険がある。
  - 提案: 検査8 / 検査9 のヒアドキュメントを読む側で字下げを剥がす。検査8 は `while IFS=: read -r t c; do … done < <(sed -E 's/^ +//' <<'COLS' … COLS)` の形にするか、ループ本体の先頭に `t=${t# }; t=${t# }` ではなく `t=$(echo "$t" | tr -d ' ')` 相当を1行入れる。検査9 は `cat > /tmp/e2skip.txt` のあとに `sed -i '' -E 's/^ +//' /tmp/e2skip.txt` を足す。あるいは**2つのコードブロックを箇条書きの外（字下げのないフェンス）へ出す**のが最も確実で、`tbl()` / `cells1()` の定義ブロックと同じ扱いに揃う。

  - `changeAuthToken` の「一回性 ≠ 失効」の切り分けと、phase 1 の2段（未使用行の全削除 + 残る全行の `NULL` 化）を起点 A / 起点 B の両方に課す規定が、`consume-reset-token` が行を消さず `usedAt` を立てるだけであるという設計事実から正しく導かれている。第10.1節との非対称（PITR 経路だけを塞いで RPC 側が開いていた）の解消も確認した。
  - `purge-user-mappings` が `callerToken` で束縛できない唯一のエントリであること（トークンが失われた行と一緒に消えている）を隠さず書き、到達制御と監査だけが守ることと残余リスクを #38 へ送っている。`callerToken` が request Worker のコード実行を得た攻撃者には防壁にならない（`SESSION_SECRET` があれば phase 0 の A-1 で取得できる）という残余リスクの明記も、初版の誤った脅威モデルを訂正したものとして正しい。
