## DO 境界・ルーティング

### Blockers

- **[B-001]** unlink / 退会の削除対象が「スナップショット」なのに、`rotate-remap` の移送はその外側へ新しい mapping 行を作れる。**解除済みクレデンシャルでのログイン**と**その canonical の永久ロック**が、どちらも成立する。
  - 場所: `.thread/34/design.md:1302`（unlink 手順2 の `targetLocators` 退避）/ `:1303`（手順3 の削除範囲）/ `:1312`（`sweep-orphan-mapping` の逆引き情報）/ `:1009`（(R3)）/ `:1012`（(R6)）/ `:1322`（退会 手順3）/ `:1363`（ローテーション 手順2 の (1)(2)）
  - 理由:
    - 第6.6節 unlink は **手順2 の時点で `credential_locators` から読んだ locator を `operations.targetLocators` へ退避し、手順3 と `sweep-orphan-mapping` はその退避値だけを対象に `delete-mapping` を発行する**（`:1302` / `:1303` / `:1312`）。つまり削除対象集合は手順2 時点のスナップショットで凍結される。
    - 一方 `rotate-remap` の 手順2 は、`changeState = 'pending'` と `status = 'reserved'` の行だけをスキップする（(R6)。`:1012`）。**「unlink 進行中」を表す印は `credential_mappings` 行に存在しない**（unlink は mapping に何も書かずに削除する）ので、移送はその行を通常どおり運ぶ。
    - 結果、**手順2 の後に (2) が移送先 bucket `dir:g{active}:b{j}` へ active 行を書くと、その行は `targetLocators` に入っていない**ため 手順3 も `sweep-orphan-mapping` も永久に到達できない。分岐は2つで、どちらも第6.9節が「塞いだ」と宣言している事象である。
      - **(a) (1) が手順2 の削除より後に着地した場合** — `credential_locators` に当該 `credentialId` の active 行が復活し、移送先 bucket には `passwordVerifier`（または SSO 行）を持つ active mapping が残る。login step 2 は active 世代の locator で移送先にヒットし、step 5 (ii) の到達性検査は `credentialId` の一致だけを見るので通り、(iii) の `credentialVersion` も一致する。**解除済みクレデンシャルで新しいセッションが発行される**（`:1306`・`:1308` が「起き得ない」と断定している事象そのもの）。
      - **(b) (1) が手順2 の削除より前に着地した場合** — `credential_locators` 側は空になるので login は fail closed で止まるが、移送先の孤児 active mapping が残る。同じ SSO 主体を再 link しようとすると 手順2 の予約が `(kind, hmac)` の一意制約に敗北し、**その SSO 主体は恒久的に再 link 不能**になる（第6.6節が「Blocker 級」と呼んだ永久ロック）。
    - **(3) の CAS が0行になって巻き戻す経路でも解消しない。** `:1383` は「(1) がその走査で新規に追加した `credential_locators` 行は破棄しない」と決め切り、その根拠を「次の走査で (1) が同じ `(credentialId, generation)` へ upsert するか、完了後の (4) が旧世代行を消すことで自然に整合する」に置いている。**credential が unlink で消えている場合は次の走査が存在せず、(4) は旧世代行しか消さない**ので、`usableForLogin = true` の孤児 locator 行が恒久的に残り、(R4) のログイン手段カウントを恒久的に1件かさ上げする（利用者が最後の SSO を外して自己ロックアウトできる）。
    - **退会にも同じ根が効く。** 第6.7節 手順3 は `credential_locators` を実時点で読むので手順3 前の移送は拾えるが、**手順3 と 手順4 の間に (1)(2) が着地すると 手順4 が locator を消して `finalize-withdrawal` の残件条件（「`deleting`/`deleted` なのに `credential_locators` が空でない」）が偽になり**、移送先 bucket に `encryptedCanonical` を持つ孤児 mapping が残る。第6.2.1節 (d) の「退会完了時点で bucket 側には何も残さない」が破れ、そのメールアドレスは再登録不能になる（自動回収は無く、`purge-user-mappings` の operator 手作業しか残らない）。
    - **第6.9節が自ら課した検査規則（`:1432`「cross-DO 操作表に載っている操作の組み合わせについても、片方が中間状態を持つ間に他方が走る場合を検査する」）が、unlink / 退会 × 鍵ローテーションの組み合わせについて未実施である。** `:1304` は「初版は手順2 が1行、手順3 が1 bucket だけを消していた」という**静的な2世代並存**を塞いだだけで、**移送が進行中に新しい世代の行を生む**動的な競合は扱っていない。
  - 提案: 削除側と移送側の両方に印を導入して、スナップショット依存を切る。最小の形は次の2点で、どちらも既存の列と規則で書ける。
    - **(i) (R6) のスキップ条件に「削除進行中」を足す。** unlink 手順2 / 退会 手順3 は、`delete-mapping` を発行する前に対象 `credentialId` の mapping 行へ削除意図の印（既存の `changeState` に `'deleting'` を1値足す、または `operationId` + 専用 `status` 値）を CAS で立て、`rotate-remap` はその印のある行を `pending` / `reserved` と同じくスキップして `previousCount` に残す。移送されないので `targetLocators` の外に行が生まれない。
    - **(ii) 削除の対象集合をスナップショットに閉じない。** `delete-mapping` を「`targetLocators` の全世代」に加えて **keyring に載っている全世代（active / previous）の locator へも発行する**（`credentialId` キーの「無ければ成功」操作なので追加コストは RPC 1本）。`sweep-orphan-mapping` の残件条件も同じ規則で引き直す。
    - あわせて **(1) が追加した `credential_locators` 行の孤児化に回収経路を与える**（`sweep-orphan-mapping` が `operations` の unlink 行を根拠に「対象 `credentialId` の locator 行が1件でも残っていたら消す」まで担う、など）。第6.9節の締め出し経路一覧にも行を足す。

- **[B-002]** ローテーション 手順2 の **(2)「移送先 bucket に active 行を書く」が、クラス (2)(3) の「全数」を宣言している RPC エントリ表に存在せず、ガードが未定義**である。設計自身が (2) を DO 間 RPC と明記している。
  - 場所: `.thread/34/design.md:1363`（(2) の定義）/ `:1377`（「(1) と (2) はいずれも DO 間 RPC なので `await` を挟み」）/ `:1379`（巻き戻し時の移送先行の破棄。これも移送先への書き込み）/ `:702`〜`:727`（RPC エントリ表）/ `:729`（「本表は『クラス (2)(3) の全数』を宣言している…本文が新しい RPC エントリを導入したら、本表にも必ず行を足す」）
  - 理由:
    - 手順2 の (1) と (4) は `record-credential-locator` として表に載っているが、**(2) と「巻き戻し時の破棄」に対応するエントリが1つも無い**。表は 24行（クラス (1) の集約1行 + (2) 10行 + (3) 13行）で、検査5（I-6）は表の内部整合しか見ないため**この欠落は第1.4節の検査をすり抜ける**。
    - 欠落しているのは「`credential_mappings` 行を `passwordVerifier` / `status = 'active'` / `userId` / `credentialId` / `callerToken` つきで任意の bucket へ書き込む」エントリである。第5.1節 (3-d) は `record-credential-locator` を無束縛にすると「`reserve-credential` + `activate-reservation` と組み合わせて任意アカウントへ攻撃者のクレデンシャルを注入でき、第5.3節 step 5 (ii) の到達性検査を通せる」として `callerToken` を必須にした。**(2) は予約と昇格を経由せずに active な mapping を直接書けるので、その原始関数より強い。** ガードが未定義のまま #37 へ渡ると、(3-d) が閉じた穴が (2) 側に開いたまま実装される。
    - **(X3) は実装不能になる。** `:1412` は「移送先の bucket は、手順2 の (2) で行を書いたのと同じ `transactionSync` の中で … `enqueueJob('rotate-encryption', …)` を発行する」と要求しているが、その `transactionSync` を持つのは移送先 DO の RPC ハンドラである。エントリが表に無いということは、その契約（引数・ガード・冪等キー）がどこにも定義されていないということである。
    - `callerToken` は「移送先に行が無い」分岐では照合材料にならない（新規行なので比較相手が存在しない）ので、既存エントリの守り方をそのまま流用できない。**設計側の判断が要る箇所であり、実装者に委ねる形になっていない。**
  - 提案: RPC エントリ表にクラス (3) の行を1本（または前進と破棄で2本）足し、群 (3-a)〜(3-d) の本数も同時に直す（検査5 の期待値も更新する）。ガードは第5.1節 (3-c) の `rotate-remap` と対称に、**移送先 bucket が自分の手元の材料だけで検証できる形**が取れる —— 移送先は active 世代なので、自分の `credential_mappings` 行1件について `HMAC(activeKey, decrypt(encryptedCanonical)) == 行の hmac` を確認して `activeKey` の所持を検証できる（自 DO 名の `gen` が `activeGeneration` と一致することの照合と併せる）。行が0件の bucket では検証できないという限界と、漏えい鍵起因のローテーションでは所持証明を数えないという射程も、`rotate-remap` と同じ書き方で明記する。行が存在する分岐では加えて `callerToken` と `userId` の一致を課す。

- **[B-003]** (X3) が謳う「構造側の fail closed」が成立しない。**`rotate-encryption` は `previousCount` を「残件が尽きた時点の 0」しか書かないので、移送で運び込まれた行があっても退役条件は崩れない** —— 旧暗号鍵の誤退役をこの機構では止められない。
  - 場所: `.thread/34/design.md:1412`（(X3) の断定「`previousCount` が0でなくなって退役条件が崩れる」）/ `:1418`（`rotate-encryption` の記録規則）/ `:528`（E-2 の書き込み箇所欄）/ `:1084`（第6.2.1節 (b-1) の退役条件）/ `:2406`（#38 への検知指示）
  - 理由:
    - `rotate-encryption` が `rotation_checkpoints` に書くタイミングと値は2箇所で同一に定められている —— `:1418`「残件があれば最小再開間隔だけ先へ `nextRunAt` を置いて `pending` へ戻し、**無ければ `done` にして** `rotation_checkpoints` へ `rotationKind = 'encryption'` の **`previousCount = 0`** を置換記録する」、`:528`「**残件が尽きた時点の** `rotationKind = 'encryption'` の **`previousCount = 0`** の置換記録」。**残件がある間は1行も書かない。したがって `previousCount` が 0 以外になる規則が本書に存在しない。**
    - よって (X3) が `enqueueJob` で `done` → `pending` へ戻しても、(encryption, bucketIndex, generation) の checkpoint 行は**以前の完了時に書かれた `previousCount = 0` をそのまま保持する**。`:1084` の退役条件（「`rotationKind = 'encryption'` かつ同一 `encryptionGeneration` の全 `0..N-1` bucket について `previousCount = 0` の記録が揃っている」）は**再暗号化ジョブが `pending` で待っている状態でも成立し続ける**。operator が条件を確認して旧暗号鍵を破棄すると、運び込まれた行の `encryptedCanonical` は恒久的に復号不能になる —— (X3) が防ぐと宣言した帰結そのものである（`:1411` が列挙する「リセットメールの宛先組み立て・自メールアドレス表示・次回ローテーションの再 HMAC が壊れ、`hmac` での login は通り続けるので最初のリセット依頼まで顕在化しない」）。第5.2.1節 (a) の「所有の唯一の証明はパスワードリセット経路」に照らせば、これは**アカウント所有の証明そのものの喪失**である。
    - **本書内の自己矛盾でもある。** `:1084` は「走査・チェックポイント・retirement 証明は第6.8節と**まったく同じ**『bucket ごとの snapshot 置換』に乗せる」と書いている。`rotate-remap` 側は `:1400` / `:1387` のとおり**チャンク完了ごとに実測の残件数（0 以外を含む）を置換記録する**ので、「まったく同じ」なら `rotate-encryption` も残件数を記録するはずである。`:1418` / `:528` はそう書いていない。**(X3) と `:2406` の検知指示（「`previousCount` が0に戻らないことを検知する」= 一度0以外になることが前提）は前者の読みに、`:1418` / `:528` の規則は後者の読みに立っている。**
    - `:1452` の第6.9節 締め出し経路一覧の該当行も「移送先 bucket が (2) で行を書いた同じ `transactionSync` で `rotate-encryption` を再投入する」を塞ぎ方として登録しているので、同じ前提の上に乗っている。
  - 提案: どちらかに寄せて1つの規則にする。
    - **(案A・推奨) `rotate-encryption` を `rotate-remap` と本当に同じ形にする** —— 各チャンク完了時に `rotationKind = 'encryption'` の `previousCount` を**実測の残件数（`encryptionGeneration` が active でない行の数）で置換記録する**。`:1084` の「まったく同じ snapshot 置換」がそのまま真になり、(X3) の再投入が次のチャンクで `previousCount ≥ 1` を書くので退役条件が実際に崩れ、`:2406` の検知指示も成立する。
    - **(案B) (X3) 側で checkpoint 行を無効化する** —— 移送先 bucket が (2) と同じ `transactionSync` の中で `enqueueJob` に加えて `(rotationKind = 'encryption', bucketIndex, 当該 encryptionGeneration)` の行を `previousCount ≥ 1` で置換（または削除）する。`rotationCheckpointStore` の口は既にあるので新しい機構は増えない。
    - いずれの案でも `:528`（E-2 の書き込み箇所欄）・`:1418`・`:1084`・`:2406` を同時に直す。第4.1.1節 `rotation_checkpoints` 行の `previousCount` の意味も「`rotationKind` ごとの残件数」に統一する。
