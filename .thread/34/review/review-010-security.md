## セキュリティ

### Blockers

- **[B-001]** **認証済みパスワード変更経路の「旧パスワード照合」に試行制限が1つも無い。** 濫用抑止の機構（`failedAttempts` / `nextAttemptAllowedAt`）は設計されているのに、その更新経路が login（step 7）1本に限定されていて、同じ credential に対して**同じ照合を行うもう1つの経路**が数えられていない。WAF の射程も未認証エンドポイントに限定されている。結果として、セッションを1つ手に入れた攻撃者が旧パスワードを**無制限・無記録**にオンライン総当たりでき、成功すれば「セッション奪取」から「パスワードを握った完全な乗っ取り（正規利用者の締め出し）」へ昇格する。
  - 場所: `.thread/34/design.md:1144`（「更新経路は第5.3節 step 7（`report-login-result`）である」）/ `:1159`（(c) 「WAF / Rate Limiting Rules を**未認証エンドポイント（login / signup / password reset）**に当てる」）/ `:727`（`lookup-credential-by-locator` のガード。`nextAttemptAllowedAt` を条件に持たない）/ `:1290`（起点 A の A-1 → A-2 → A-3）/ `:719-743`（RPC 全数表。変更経路の照合結果を bucket へ報告するエントリが無い）/ `:2498`（#38 への引き継ぎも「未認証経路のレート制限」だけ）
  - 理由:
    - 第6.5.1節 phase 0 の起点 A は **(A-1) `credential_locators` と `account.callerToken` を読む → (A-2) `lookup-credential-by-locator` で `passwordVerifier` を得る → (A-3) request Worker が `PasswordHasher.verify` で旧パスワードを照合する** の3段である。これは **login step 3〜4 とまったく同じ「1回のパスワード認証試行」**であり、第5.1節も「パスワード変更はセッション + 旧パスワード照合」と書いて、旧パスワード照合を**認可の構成要素**として扱っている。
    - ところが第6.2.2節 (a) は `failedAttempts` の更新経路を「第5.3節 step 7（`report-login-result`）である」と**単一に確定**しており、変更経路の照合結果を bucket へ報告する手段が RPC 全数表（第5.1節）に1本も無い。`lookup-credential-by-locator` のガードにも `nextAttemptAllowedAt` 未到達の条件が無い（login の `lookup-credential` にはある。`:722`）。したがって **A-2 / A-3 は何回失敗してもカウンタに触らず、ロックアウトにも掛からない。**
    - 第6.2.2節 (c) は「**どのレイヤーで当てるかだけは本 Issue で決着させる**」と宣言しているが、当てる先を **login / signup / password reset の3つ**に限定している。パスワード変更は認証済みエンドポイントなのでこの列挙に入らず、第11.3節（`:2498`）の #38 への引き継ぎも同じ3つしか挙げていない。**したがって #37 も #38 も、この面に抑止を置く根拠を本書から得られない。**
    - 悪用の系列は「セッション奪取（XSS / 共有端末 / Cookie 盗取）→ 変更フォームへ旧パスワードを連投 → 当たったら自分のパスワードへ変更」である。1試行あたり PBKDF2 210,000 回（`:683`）を request Worker で回すが、Workers は水平に並ぶので同時実行で秒あたり数百〜数千試行が出る。`PlainPassword` の下限は8文字だけで強度要件が無い（`packages/core/src/domain/identity/valueObject.ts:78-89` を実読。`PASSWORD_MIN_LENGTH = 8` / `PASSWORD_MAX_LENGTH = 128` の長さ検査のみ）ので、よく使われるパスワードは現実的な時間で当たる。
    - **「セッションを握った攻撃者には既に残余リスクがある」では言い訳にならない。** 本書が受容しているのは `:709` の SSO link 経路（「自分の SSO 主体を link すれば、その後リセットされても入り続けられる」）だけで、そこには**補償（リセット完了画面の必須導線でクレデンシャル一覧を提示して解除させる）が対で置いてある**。旧パスワードの総当たりには補償も検知も無い — `failedAttempts` が進まないので**痕跡が1つも残らず**、`:1147` の時間減衰も `:1146` の天井も発火しない。しかも終状態は「攻撃者がパスワードを変更して正規利用者を締め出す」であり、`:709` の残余リスク（攻撃者が入り続けられる）より1段強い。
    - **同時に CPU の攻撃面でもある。** 第4.8節はパスワードハッシュ化を「DO を占有させないため request Worker で回す」と決めているので DO は止まらないが、A-1（User Data DO）と A-2（Directory bucket）の RPC が1試行につき2本発生する。標的の bucket は攻撃者が選べる（第6.2.2節冒頭）ので、`overloaded`（リトライ禁止）へ追い込む経路が**未認証エンドポイントの WAF を通らずに**成立する。
  - 提案: 第6.2.2節 (a) の射程を「login の照合」から「**その credential に対するパスワード照合の全数**」へ広げ、次の3点を断定する。
    1. **A-3 の照合結果も bucket へ報告する。** RPC 全数表にエントリを1本足す（`report-verify-result` 相当。ガードは `lookup-credential-by-locator` と同じ `callerToken` の定数時間比較でよく、材料は A-1 が既に返しているので増えない）。成功で `failedAttempts` をリセットし、失敗で前進させる。**login step 7 と同じく「応答を返す前に完了させる」**を課す（接続を切ってカウンタを回避させない）。
    2. **`lookup-credential-by-locator` に `nextAttemptAllowedAt` 未到達の条件を課す。** 未到達ならダミー材料を返すか拒否する。login の `lookup-credential`（`:722`）と非対称にしない。**ここに置かないと「数える前に materials が出てしまう」ので、天井・減衰・非加算の3規則（`:1146-1148`）が変更経路では意味を持たない。**
    3. **第6.2.2節 (c) の「当てるレイヤー」の結論に認証済み再認証エンドポイントを加える。** 「未認証エンドポイント（login / signup / password reset）」を「**パスワード照合を行う全エンドポイント**（login / signup / password reset / パスワード変更）」へ書き換え、第11.3節（`:2498`）の #38 への引き継ぎも同じ列挙に揃える。
    - 脱出経路との整合も1行足す。1 の失敗カウントは第6.2.2節 (a) の脱出経路 (i)（リセット完走で `failedAttempts` を0に戻す。`:1280`）でそのまま解消するので、新しい恒久 DoS は生まれない。**逆に足さないと、変更経路だけが「数えない・止めない」面として残る。**

### Warnings

- **[W-001]** **`abandon-account` の束縛が `operationId` の知識だけである。** 同じ終端規則のもう半分である `cancel-reservation` には本ラウンドで `callerToken` を課したのに、**破壊的操作という性質がまったく同じ `abandon-account`** には課していない。結果、本書自身の断定「**現在、`operationId` を束縛の実体として使っているエントリは1本も無い**」が偽になっている。
  - 場所: `.thread/34/design.md:740`（`abandon-account` のガード = 「`operations` 行の `operationId` 一致 + `kind = 'signup'` + `phase` が `done` でないこと」）/ `:757`（(3-a) 群に含まれている）/ `:764`（`cancel-reservation` にだけ `callerToken` を課した論拠）/ `:765`（「`operationId` を束縛の実体として使っているエントリは1本も無い」）/ `:1252`（終端規則 3-ii）/ `:1176`（phase 4 の内容）
  - 理由:
    - `:764` が `cancel-reservation` に `callerToken` を課した論拠は「**(3-a) の論拠は『前進』についての主張だが、`cancel-reservation` は破壊的な補償である**」＋「**第5.2節 (c) は未認証経路のログに `operationId` を出してよいと明記しており、signup は未認証経路である**」の2点である。`abandon-account` は `account.status` を `deleting` へ倒して `finalize-withdrawal` を投入する（`:740`）ので、**破壊的という性質は同じで、しかも `cancel-reservation` と対で1つの終端規則を構成している**（`:1251-1252` の 3-i / 3-ii）。**同じ規則の2手順のうち片方だけを束縛する形は設計の自己矛盾である。**
    - `phase != 'done'` が限定条件として働くことに依拠しているが、**この条件は「秘密」ではなく「状態」であり、必要な知識は依然 `operationId` だけである。** しかも phase が `done` になるのは phase 4（`:1176`）で、その phase 4 は表側では「`operations.phase = 'done'` と `credential_locators` の記録」の2つの作用を持つ一方、RPC 全数表の `record-credential-locator`（`:733`）は**コーディネーター bucket が呼ぶ汎用 upsert**（link とローテーションでも共有する）である。**#37 が phase 4 を「locator の記録」と「`phase = 'done'`」の2本の RPC として実装すると、`credential_locators` が書かれて login が通るのに `phase` が `activating` のままという状態が生じ、`resume-signup` が `poison` に落ちればそれが安定状態になる。** その状態の口座は `abandon-account` で破壊できる。
    - 悪用に要る能力は `cancel-reservation` の件と完全に同じ「**binding には到達できるが `SESSION_SECRET` を持たない呼び出し元**」＋「未認証経路のログの閲覧」であり、これは (3-b) が「正しく塞げている」と宣言した脅威クラスそのものである（`:771`）。
    - **ただし B-001 と分けて Warning にしたのは、`phase = 'done'` が原子的に書かれる限り射程が「進行中の signup（データが空のアカウント）」に留まり、利用者が再登録で回復できるからである。** 上の非原子実装に倒れた場合は Blocker 相当になる。
  - 提案: `abandon-account` のガードに **`callerToken` の定数時間比較**を足す（`:764` と同じ形。材料は増えない — コーディネーター bucket の予約行が `callerToken` を持ち、`account.callerToken` は phase 2 の `initialize-account` が書いている）。あわせて **(3-a) の群の説明に「破壊的な作用を持つエントリは `operationId` の知識だけに束ねない」を規則として書き**、`activate-reservation` / `promote-verifier` / `propagate-saga-committed` の3本が**前進のみで破壊的でない**ことを群の正当化として明示する（現在は「CAS と phase 条件」という一括の説明しかなく、破壊的かどうかで線を引いている事実が本文に現れていない）。**あわせて phase 4 の2つの作用を「同じ `transactionSync` で書く」と明記する** — 書かないと上の非原子実装の余地が残る。

- **[W-002]** **第9.5節と第11.3節が「Identity Directory bucket の全走査で `credential_mappings.userId` を集める」ことを唯一の対象特定手段として要求しているが、その RPC エントリが第5.1節の全数表に無く、ガードも未定義である。** 同表は「クラス (2)(3) の全数」を宣言し、射程の限定を**鍵ローテーションの移送1点だけ**に絞っている。
  - 場所: `.thread/34/design.md:2133`（「**対象を特定する唯一の経路は Identity Directory bucket の全走査である。** `0..N-1` の全 bucket を舐めて `credential_mappings.userId` を集めれば全 `userId` を列挙できる」）/ `:2134`（「その判定には全ユーザー分の RPC が要る」）/ `:2489`（#38 への引き継ぎ「**対象 DO の特定手段（Identity Directory bucket の全走査で `credential_mappings.userId` を集める）を手順の第1項に置く**」）/ `:745`（全数宣言と更新規則）/ `:747`（全数の射程の限定は移送1点だけ）/ `:742`（`purge-user-mappings` = 同種の operator 専用エントリ）
  - 理由:
    - `:2133` / `:2489` が要求しているのは **(i) Directory bucket から `userId` の一覧を返す読み RPC** と **(ii) 各 User Data DO の `_meta.schema_version` を読む operator RPC** の2本である。どちらも第5.1節の12本のクラス (3) には無い。`:2133` は「第6.7節の operator 経路と第6.8節の retirement 走査が既に同じ前提に立っている」と書いているが、**これは事実として合っていない** — `purge-user-mappings` は `userId` を**引数に取る**エントリ（`:742`）で一覧を返さず、retirement 走査が数えるのは `previousCount`（bucket ごとの行数）であって `userId` の集合ではない。
    - (i) は性質上 `callerToken` で束縛できない（`purge-user-mappings` と同じ理由で、対象を特定する前に呼ぶ）ので、**到達制御と監査だけが守るエントリがもう1本増える**。しかも返るのは**その bucket に写像される全利用者の `userId` の一覧**で、第5.2節 (c) が「未認証経路では `userId` も出さない」と扱いを揃えた値の bulk 取得である。#34 R8 do-boundary B-002（移送先書き込みが全数表に無くガード未定義）と同じ形の欠けである。
    - **Blocker にしないのは、read-only であり、`purge-user-mappings` に既に与えている守り（公開ルートを持たない operator 専用 maintenance 経路 + 対象の存在確認 + 実行監査）をそのまま流用すれば閉じるからである。** 必要なのは行を足して守り方を割り当てることであって、新しい判断ではない。
  - 提案: 第5.1節の表にクラス (3) の operator 専用エントリを2行足し、(3-c) 群（到達制御と監査が守る群）へ割り当てて群の本数を **3 → 5** に直す（第1.4節 I-6 の検査対象なので、直さないと機械検査が `NG` になる）。守りは `purge-user-mappings` と同じ「maintenance 経路の到達制御 + 実行監査」とし、**加えて (i) には「返す `userId` をログ・トレースに出さない」「1回の呼び出しで返す件数に上限を置く」を課す**（第6.2.1節 (c) が復号経路に課しているチェックポイント制約と同じ形）。あわせて `:2133` の「第6.7節の operator 経路と第6.8節の retirement 走査が既に同じ前提に立っている」を、実体に合う記述へ直す。

- **[W-003]** **リセットトークンの無効化点の全数（3箇所）と、第6.2.2節 (b) / 第11.1節が主張する「新しいトークンの発行が未使用トークンを全部置き換える」が食い違っている。** 悪用可能な穴には至らないが、**無効化点の全数は前ラウンドで Blocker になった箇所そのもの**なので、誤った主張を残すと次の改訂で判断の根拠になる。
  - 場所: `.thread/34/design.md:1014`（「**無効化を発行する箇所は3つ**で、いずれも同じ `transactionSync` の中で行う。第6.5.1節 phase 1 / 第6.6節 unlink 手順3 / 第6.7節 手順3（退会）」）/ `:1158`（「**発行される新しいトークンは、第6.1節 (d) の無効化規則によりその credential の未使用トークンを全部置き換える**ので、連打が古いトークンを増やすことも無い」）/ `:542`（E-2 の `password_reset_tokens` の書き込み箇所欄。発行は「発行」としか書かれておらず削除の書き手に入っていない）/ `:2345`（#35 へ送るテストケースに「**新しいトークンの発行がその credential の未使用トークンを全部置き換える**」を足すよう指示している）
  - 理由:
    - `:1014` の全数（3箇所）に**発行時**は入っていない。したがって `:1158` の「発行が未使用トークンを全部置き換える」は第6.1節 (d) からは導けず、実際には**同じ credential について複数の未使用トークン行が窓ごとに1本ずつ並存する**（`lastResetRequestedAt` のスロットルが窓を刻み、`sweep-reset-tokens` が期限で掃除するだけである）。`:1158` が支えようとしていた主張（連打が古いトークンを増やさない）は成立しない。
    - **奪還経路そのものは閉じている** — 第6.5.1節 phase 1 の2段（未使用行の全削除 + 残る全行の `changeAuthToken` の `NULL` 化。`:1015-1017`・`:1304-1306`）が、被害者が起点 A / 起点 B のどちらで復旧しても**その credential の全トークン行**を対象にするからである。したがって並存は攻撃者の保持本数を増やすだけで、被害者の1回の復旧で全部落ちる。**Blocker / B-001 相当ではない。**
    - それでも Warning に置くのは2点の理由による。(i) `:2345` が **#35 のテストケースとして誤った期待値を送っている**ので、#35 / #37 は「発行時にも消す」実装へ倒すか、テストが落ちるまで気づかない。(ii) `:1014` は「無効化点の全数」を名乗る列挙であり、**列挙が実体と食い違っている状態は前ラウンドで Blocker になった形そのものである**（一回性を失効と混同していた件）。
  - 提案: どちらかに倒して1箇所で断定する。**推奨は「発行時にも同じ credential の未使用行を削除する」を無効化点に足して4箇所にすること** — `:1158` の主張がそのまま真になり、トークン行の並存という状態が構造的に消え、`:2345` のテストケースも成立する。E-2 の書き込み箇所欄（`:542`）にも発行時の削除を書き足す。倒さない場合は `:1158` から当該の一文を削り、`:2345` のテストケース指示も撤回する。

### Notes

- **[N-001]** **`changeAuthToken` の失効経路（前ラウンドの修正）は単一世代で正しく閉じている。Blocker / Warning 相当ではない。** 追跡した結果、(i) 攻撃者が `consume-reset-token` に成功して `begin-credential-change` が失敗し「消費済み・`changeAuthToken` 未使用」の行が安定して残る経路（`:1306`）は、被害者が起点 A（`callerToken` + 旧パスワード）でも起点 B（新しいトークン）でも復旧すれば phase 1 の2段目で `NULL` になる。(ii) 未消費トークンは1段目の全削除で消える。(iii) 起点 B 自身も2段目の対象に含めてあるので既定の一回性（`値 → NULL` の CAS）が二重に満たされ、同一 `transactionSync` なので観測可能な中間状態が無い。(iv) 共通規則（`:768`）の「行側 `NULL` は常に不一致 / 引数の欠落は比較前に拒否」が `callerToken` と `changeAuthToken` の両方に掛かるので、`NULL == NULL` で束縛の実体を持たない呼び出し元が通る経路も閉じている。**射程を2列に限定したことも妥当である** — 本書内で定数時間比較の対象になる不透明値はこの2つだけである（下記 N-005 の1件を除く）。
- **[N-002]** **`passwordVerifier` の書き込み点（前ラウンドの修正）は全数として閉じており、対になる守りも揃っている。Blocker / Warning 相当ではない。** 書き込み点は signup phase 1a の予約行と credential 変更 phase 3 の昇格の2つ（`:520`・`:1185`）で、予約行が検証材料を持つことに対して `lookup-credential` の `status != 'active'` → ダミー（`:722`・`:1184`）が対で置かれている。**SSO signup のメール行に載せない**ことが `usableForLogin = false`（`:1178`）→ 第7.6節の「リセットメールを送らない」→ 第6.6節 unlink (1-b) の数え上げ、という3箇所の前提として一貫している。`usableForLogin` の false → true 遷移が本設計に存在しない（`:1815`）ことも確認した — これがあると SSO 専用アカウントの奪取条件が IdP 認証からメールボックス到達性へ下がる。
- **[N-003]** **`callerToken` を戻り値として返す RPC が、クラス (2)(3) の22エントリに1本も無いことを表から全数確認した。Blocker / Warning 相当ではない。** これが `callerToken` による束縛が「binding には到達できるが `SESSION_SECRET` を持たない呼び出し元」に対して実効を持つための前提であり、破れると (3-b) / (3-d) の全エントリが同時に無束縛になる。返すのは第6.5.1節 phase 0 の A-1（クラス (1)、epoch ガード）だけである。**`initialize-account` が `callerToken` を引数で受け取る側でありながら「`account` 行があって同じ `operationId` の `operations` 行が無いなら拒否」（`:726`）を持つので、既存アカウントの `callerToken` を上書きする経路も無い**（`payloadDigest` 不一致は `ConflictError`）。ただし **`callerToken` は credential 変更でも再採番されない**ので、セッションを1度奪われた利用者はパスワード変更後もその値を握られ続ける。公開面から提示する経路が無いので穴ではないが、`:772` の残余リスク（request Worker のコード実行）と同じ枠にある。
- **[N-004]** **テナント分離は構造で閉じている。Blocker / Warning 相当ではない。** `idFromName` の材料は3経路（署名済みトークンの検証結果 / signup で `IdGenerator` が採番した候補 `userId` / Directory の RPC 戻り値）に限定され（`:970-973`）、DO 側は「自分の SQLite に永続化済みの locator」だけを使う（`:974-977`）。外部入力が locator の材料になる唯一の例外（リセットトークンの `generation` / `bucketIndex`）には **DO を叩く前**の範囲検査3点が課されており（`:1005-1006`）、第6.2節の判断軸 (iv) が真になる条件として明記されている。クライアントから受け取る唯一の識別子である unlink の `credentialId`（`:1067`・`:1345`）も、自 DO の `credential_locators` を引くだけなので他ユーザーの行に届かない。`delete-mapping` / `read-own-canonical` / `lookup-credential-by-locator` はいずれも行側の `callerToken`（アカウント単位）との一致を要求するので、別アカウントの `credentialId` を渡しても不一致で落ちる。第8.3節 (e)（RPC 境界でブランド型を受け取らず DO 内で値オブジェクトを再構築する）により `CLAUDE.md`「validated at exactly two points」も維持されている。
- **[N-005]** **`exchange-authz-code` の PKCE 照合について、`codeChallenge` が署名済みコードから欠落した場合の扱いが (3-b) の共通規則の射程外である。Blocker / Warning 相当ではないと判定した。** 第5.1節の表は同エントリのガードを「完結した集合」として宣言し（`:731`・`:961`）、`code_verifier` → challenge の定数時間比較を含めているが、`:768` の共通規則の射程は `callerToken` / `changeAuthToken` の2列に限定されている。コードは**サーバーが署名した値**なので欠落の可否を決めるのは `/authorize` 側であり、そこは #13 へ明示的に委譲されている（`:959`）うえ OAuth 2.1 が PKCE を必須としているので、実際に開くには #13 が仕様に反する必要がある。**閉じるなら1文で足りる** — 「`codeChallenge` / `codeChallengeMethod` を持たないコードは交換前に拒否する（`typ` 欠落と同じ fail closed。`:915`）」を同エントリのガードに足す。
