# ADR — Issue #34: [設計] Cloudflare Workers + ユーザー単位 Durable Objects への集約を ADR 化し、DO の境界とルーティングを設計する

本 Issue の成果物そのものである永続 ADR 3件（ランタイム・データ配置 / 検索方式 / 非同期処理）は `.adr/002〜004` に置く。このファイルには、その3件には含めない**計画段階のメタな判断**だけを記録する。

## ADR-001: 先行ブランチの `.adr/` 8件を3件へ縮約し、残りを design.md に吸収する

### Status

Proposed

### Context

分割元 Issue #19 のブランチ `issue/19/cloudflare-do-fts` には、DO 実装一式とともに `.adr/001〜008` の8件が既に存在する（`git show issue/19/cloudflare-do-fts:.adr/00N-*.md` で全文が読める）。

| 先行 | 主題 |
|---|---|
| 001 | Cloudflare Workers + 利用者単位 DO への集約 |
| 002 | 検索は SQLite FTS5 のみ |
| 003 | ローカル更新は同期 commit、外部処理は Alarm job |
| 004 | Identity Directory の秘密鍵付き分割と DO 間 saga |
| 005 | DO class lifecycle は宣言的 exports で管理 |
| 006 | usecase は DO 内で実行し、Worker RPC は値だけを運ぶ |
| 007 | PITR は staging smoke、local は wrapper contract で検証 |
| 008 | Account Home を認証と session のオンライン権威にする |

一方、Issue #34 は「`.adr/` に置くのは3件だけ」「それ以外は `.thread/34/`」「採番は既存の `001-integration-tests-single-workers-pool.md` の続きから」と明示している。先行の 001〜003 は #34 の3件と主題が一致するが、採番が衝突する。先行の 004〜008 は #34 の3件に含まれない。

選択肢は3つあった。

1. 先行8件をそのまま採用する
2. 先行 001〜003 を 002〜004 に採番し直し、004〜008 は 005〜009 として `.adr/` に置く
3. 先行 001〜003 を 002〜004 に採番し直し、004〜008 の内容は `.thread/34/design.md` に吸収して `.adr/` には昇格させない

### Decision

**3 を採る。**

1 は `.adr/001` を上書きし ADR が8件になるため、Issue の受け入れ条件（`.adr/002` 以降に3件、それ以外が増えていない）を機械的に破る。

2 は採番の衝突こそ避けられるが、「`.adr/` はプロダクトの意思決定だけの薄い台帳」という Issue の明示的な指示に反する。先行 004〜008 は寿命テスト（本 Issue を見ていない人にも意味を持つか）は通るものの、Issue が挙げた判断例（「Identity Directory DO をハッシュ何分割にするか」は `.thread/34/` に留める）に照らせば、分割方式・saga・exports・RPC 形状・PITR の検証境界・認証権威の所在はいずれも「決定の実現手段」の側にある。Issue 自身が「迷ったら `.thread/34/` に書く — `.adr/` を薄く保つほうが、後続 Issue の担当者にとって価値が高い」と優先順位を示している。

3 では内容を捨てない。先行 004〜008 の言語化された論点は design.md の次の章へ吸収する。

| 先行 | 吸収先（design.md） |
|---|---|
| 004 Directory 分割と saga | 第6章（Identity Directory DO）全体 |
| 005 宣言的 exports | 第9.1節（DO class lifecycle と object 内 schema version の分離） |
| 006 値のみの Worker RPC | 第3.2節（Worker 分割）・第8.3節（ユースケースの実行位置と RPC） |
| 007 PITR の検証境界 | 第10.1節（運用上の論点。詳細は #38） |
| 008 Account Home 認証権威 | 第3.1節（クラス構成と責務分界）・第5.1節（認証済みリクエスト） |

将来これらを永続 ADR へ昇格させる必要が生じたら、そのときに `.adr/005` 以降として別途起こす。

### Consequences

- 良い点:
  - `.adr/` が薄いまま保たれ、architecture-audit / spec-sync など後続の読み手が「プロダクトの意思決定」だけを短時間で把握できる
  - 先行ブランチの検討成果を捨てずに済む
  - 採番が `001` の続きになり、既存 ADR を壊さない
- トレードオフ:
  - Account Home の導入や Directory の分割方式といった波及の大きい判断が `.adr/` に現れないため、`.thread/34/design.md` を読まないと全体像が掴めない。緩和として `.adr/002` の影響節から design.md へのポインタを1行置く

## ADR-002: design.md を先に書き、`.adr/` の3件を後から抽出する

### Status

Proposed

### Context

実装ステップの順序として、(a) `.adr/` の3件を先に書いて design.md で詳細化する、(b) design.md を先に書き切って決定部分だけを `.adr/` へ抽出する、の2案があった。

(a) は「決定 → 詳細」という文書の依存方向と一致し、直感的に見える。

### Decision

**(b) を採る。**

(a) の順序で書くと、ADR を書いている最中に「なぜそう決めたか」を説明するために実現手段（分割方式、saga の phase、migration 手順、スキーマ断片）を書き足したくなり、詳細が `.adr/` へ流れ込む。これは受け入れ条件「`.adr/` にはその詳細が流れ込んでいない」を直接破る失敗経路である。

design.md を先に書き切れば、`.adr/` へ抽出するときの操作が「決定文と代替案と影響だけを取り出し、詳細は design.md へのポインタに置き換える」という減算になる。減算のほうが混入を起こしにくい。

### Consequences

- 良い点: `.adr/` が薄いまま仕上がる。ADR の各節が design.md の裏付けを持つ
- トレードオフ: design.md を書いている間、`.adr/` に置く3件の決定文が確定しない。3件の主題は Issue が指定済みなので、実質的な手戻りリスクは低い

## ADR-003: supersede の正本は新 ADR 側に置き、旧側にはステータス行の1行ポインタだけを置く

### Status

Proposed

### Context

supersede される旧 ADR は2件あり、性質が異なる。

- `.thread/1/adr.md` の ADR-004 — Issue #1 当時の**作業ログ**。1662行の巨大ファイルの一部。Issue は「本文は書き換えない。追記するとしても1行ポインタまで」と明示
- `spec/adr/005-search-index-via-outbox.md` — 旧運用の ADR 置き場。`spec/index.md:42`・`spec/database/index.md:6`・`spec/domains/{search,memo,knowledge}.md`・`spec/usecases/search.md:3` の計6箇所から相対リンクで参照されている（実測）。Issue は「本文を保持したままステータス行に superseded ポインタを付ける」と指示

書き方として、(a) 旧側に「何が変わったか」を含む説明を書く、(b) 旧側は「→ `.adr/00N` に supersede された」の1行に留め、supersede の理由と範囲は新 ADR 側にだけ書く、の2案があった。

### Decision

**(b) を採る。** 旧側は1行ポインタのみ。「何を supersede したか」は新 `.adr/` のステータス節または影響節に書く。

理由は3つ。

1. Issue が「supersede の正本は新しい `.adr/` 側に書く」と明示している
2. 説明を両側に置くと、後から決定が変わったときに2箇所を同期する必要が生まれる。ポインタは1方向にしておけば正本が1つに保たれる
3. `.thread/1/adr.md` は過去の作業ログであり、改変量を最小化するほど「当時の記録」としての価値が保たれる。1行に限定すれば `git diff` の削除行がゼロであることを機械的に確認でき、誤って本文を壊していないことを検証できる

### Consequences

- 良い点: 正本が1箇所に定まる。旧ファイルの差分が最小になり、意図しない改変を検出しやすい
- トレードオフ: 旧 ADR だけを読んだ人は「supersede された」ことしか分からず、新 ADR へ辿らないと理由が分からない。ADR の読み方として妥当な非対称性と判断した

## ADR-004: `.thread/1/adr.md` の ADR-002 / ADR-015 には supersede ポインタを付けない

### Status

Proposed

### Context

Issue の「参照」節は旧 ADR として ADR-002 / ADR-004 / ADR-015 の3件を挙げている。一方「対応項目2」で supersede を明示的に指示しているのは ADR-004 と `spec/adr/005` の2件だけである。残る2件にポインタを付けるかを決める必要があった。

- **ADR-002（セッション管理方式 — HMAC 署名付きステートレス Cookie）** — セッションを DB を触らずに検証する決定。`SessionCodec` ポートとアダプター1本の交換で差し替え可能な構造になっており、ランタイム集約とは独立している。DO 構成でも `userId` をリクエスト先頭で確定できる点はむしろ好都合で、決定が覆るわけではない。ただし Account Home を認証の権威に据える設計（先行 ADR-008）を採ると、「サーバー側から失効できない」というトレードオフの前提が変わる可能性がある
- **ADR-015（AWS の `SESSION_SECRET` は Secrets Manager 参照で配る）** — AWS 固有のシークレット配布方法。AWS ランタイム自体が #36 で撤去済みなので、対象が既に存在しない

### Decision

**どちらにも supersede ポインタを付けない。**

ADR-015 は supersede ではなく**対象消滅**である。撤去は #36 で完了しており、本 Issue の3件が覆した決定ではない。ここにポインタを付けると「#34 が AWS の何かを決め直した」という誤読を招く。これは無条件の判断である。

ADR-002 についてはこの判断が **design.md 第3.1節の結論に条件付き**である。ここで確定形で「覆されていない」と書くと、まだ下していない設計判断を先取りすることになる。

- **design.md 第3.1節が Account Home を採用しない場合** — ADR-002 は覆されていない。セッション方式の決定は DO 構成でもそのまま生きるので、ポインタを付けない
- **Account Home を採用する場合** — session は「発行時 `sessionEpoch` を署名し、protected execution point ごとに Account Home と照合」になり、ADR-002 の「DB を触らずに検証する / サーバー側失効の手段が無い」というトレードオフが実質的に覆る。ただしそれを覆したのは `.adr/002〜004` の3件のいずれでもなく、セッション方式そのものを扱う別 ADR の仕事になる。したがって**本 Issue でもポインタは付けない**が、トレードオフが変わる事実を design.md 第5.1節に明記する

いずれの分岐でも「本 Issue では `.thread/1/adr.md` の ADR-002 に手を入れない」という結論は変わらない。変わるのは design.md 第5.1節に何を書くかである。

**「セッション方式そのものを扱う別 ADR を起こす必要があるか」の判断は、本 Issue が下す。** 実施タイミングは **design.md 第3.1節（Account Home の採否）の結論が出た時点**で、結論は design.md 第5.1節に書く。

初版はこれを「#37 の着手前に判断する」としていたが、それでは3つの穴が空く。(a) 判断の記録が `.adr/` に残らない、(b) 判断の実行主体と場所が誰にも割り当てられない、(c) AC-21 が「design.md の『未決事項』に Account Home が現れない」ことを要求している一方で、実質的な未決事項が `.thread/34/adr.md` 側に残る。第3.1節の結論が出れば判断材料は揃うので、先送りする理由が無い。

あわせて、この帰結が `.adr/` しか読まない読み手（architecture-audit / spec-sync）に見えるよう、`.adr/002` の影響節に1行だけポインタを置く — 「認証権威の所在によっては、`.thread/1/adr.md` ADR-002 のステートレスセッションのトレードオフが変わる。所在の決定と、別 ADR を要するかの判断は `.thread/34/design.md` 第3.1節 / 第5.1節」。仕組みを書かないので AC-6 は破らない。

### Consequences

- 良い点: supersede の関係が「本 Issue の3件が実際に覆した決定」だけに限定され、履歴が正確に読める。`.thread/1/adr.md` への変更が1行に収まる。分岐を明示したので、design.md 第3.1節の結論がどちらでも判断の再検討が不要。判断の実行主体・タイミング・記録先がすべて本 Issue 内に閉じる
- トレードオフ: Account Home を採用した場合、ADR-002 のトレードオフ変更が `.thread/1/adr.md` 側からは追えない。design.md 第5.1節が唯一の詳細記録で、`.adr/002` の1行がその入口になる

## ADR-005: Account Home DO の採否は本 Issue で決着させ、未決事項に落とさない

### Status

Proposed

### Context

計画初版は「リスクと注意点」で、Account Home の採否について「決めきれない場合は『未決事項』に落とし、#37 の着手前に決める期限を書く」という逃げ道を用意していた。設計 Issue で難所を先送りする選択肢を残すこと自体は一般には妥当な保険である。

しかし本 Issue の受け入れ条件9は「後続 Issue（#35 / #37）が本 Issue の成果物だけを見て着手できる」であり、Account Home の採否は次のすべてを決める最上流の分岐にあたる。

- DO クラス数（2クラスか3クラスか）
- アカウント作成 saga の phase 数と、部分失敗時に残る状態の種類
- session 検証が per-request の RPC になるかどうか（`.thread/1/adr.md` ADR-002 のトレードオフが覆るか）
- PITR の restore 対象境界（何を1単位として戻すか）

未決のままでは #37 は1行も書けない。つまりこの逃げ道は、受け入れ条件9 と直接衝突する。

### Decision

**逃げ道を削る。** design.md 第3.1節で理由付きで結論づけ、第11.4節「未決事項」には落とさない。計画側には AC-21 として「第3.1節に採否の断定があり、第11.4節に Account Home が現れない」を検証可能な基準で立てる。

判断材料は揃っている。先行ブランチが「Directory mapping だけでは signup 部分失敗・退会中・古い PITR mapping・credential 変更後の session を区別できない」という理由で3クラス構成を採っており（`.thread/19/adr.md`）、採る／採らないのどちらに倒すにせよ、この理由に対する態度を書けば結論になる。

### Consequences

- 良い点: #37 が設計の再検討なしに着手できる。受け入れ条件9 が実質的に満たされる
- トレードオフ: design.md 第3章の執筆コストが上がる。ただし先送りしても #37 の着手前に同じ判断が必要になるので、総量は増えない

## ADR-006: `spec/adr/005` の supersede 先を `.adr/003` と `.adr/004` の両方にする

### Status

Proposed

### Context

計画初版は `spec/adr/005-search-index-via-outbox.md` の supersede 先を `.adr/003`（検索方式）単独に固定していた。

`spec/adr/005` の決定は「検索インデックスの更新を Outbox 経由の consumer で非同期に行う」であり、その根拠は「埋め込み生成が外部 API を伴うから同期にできない」である。この決定を覆すには2つの判断が要る。

- **根拠を消す** — ベクトル検索をやめれば埋め込み生成が不要になり、非同期にする理由が消える（`.adr/003`）
- **更新方式そのものを置き換える** — ローカル更新は DO の同期 commit にし、Outbox を transport として使わない（`.adr/004`）

更新方式を実際に置き換えるのはむしろ後者である。`.adr/003` 単独に固定すると、履歴上「検索方式の変更だけで更新方式が変わった」という読みになり、非同期処理側の決定が supersede 関係から抜け落ちる。

### Decision

`spec/adr/005` のステータス行のポインタは **`.adr/003` と `.adr/004` の両方**を指す。新 ADR 側にも対応する記述を置く — `.adr/003` の影響節に「`.adr/004` と共同で supersede する（覆すのは根拠側）」、`.adr/004` の影響節に「`spec/adr/005` の更新方式部分を supersede する」。

AC-7 / AC-10 の検証欄も両方を指していることを見る形に直す。

### Consequences

- 良い点: supersede の関係が実態と一致する。`spec/adr/005` から辿った読み手が、検索方式と更新方式の両方の変更に到達できる
- トレードオフ: 旧側のステータス行が1行では収まらない可能性がある。本文には手を入れないという制約は守れるので、実害はない

## ADR-007: 検索方式の設計詳細は本 Issue の決着対象から外し、#35 への入力として位置づける

### Status

Proposed

### Context

計画初版の design.md 構成案は第7.2節「検索方式の設計詳細」に、正規化（NFKC）・トークナイザ（trigram）・短語フォールバック・topic filter・trash 除外・安定順位・snippet・ページングを並べ、すべてを AC-5（断定形で終える）の対象に含めていた。

Issue の対応項目4が検索について求めているのは「FTS5 を本体更新と同一 SQLite transaction で同期更新できるか。できる場合、Outbox consumer を介したインデックス維持は不要になる」の1点だけで、これは第7.1節が引き受ける。

一方、7.2 の項目は性質が2つに分かれる。

- **正規化・トークナイザ・短語フォールバック** — 「日本語で FTS5 のみで足りる」という `.adr/003` の決定を支える根拠。本 Issue に必要
- **topic filter / trash 除外 / 安定順位 / snippet / ページング** — 検索 API の仕様設計。`spec/domains/search.md` の改訂（#35）か実装（#37）の領分

計画自身が「`spec/domains/search.md` の 271行が総崩れになる」ことを #35 の作業量として認識しているので、後者をここで先取りすると #35 と設計が二重管理になる。

### Decision

第7.2節を「FTS5 のみで日本語全文検索が成立する根拠」に絞り、検索 API の仕様は第7.2.1節で **#35 へ委譲すると明記する**。第7.2.1節は AC-5 の対象外とする。

先行実装が既に決めている内容（snippet の `<mark>`、安定ページング等）は捨てず、第11.1節の #35 引き継ぎ表に「決めるべき論点」として送る。

### Consequences

- 良い点: 本 Issue と #35 のスコープ境界がきれいになる。二重管理と、先取りした設計が #35 で覆される手戻りを避けられる
- トレードオフ: design.md だけを読んだ #37 の担当者は検索 API の仕様を知れない。#35 の成果物が先に必要になるという依存が1本増えるが、これは元々の Issue の分割構成（#37 は #34 / #35 の両方に依存）どおりである

## ADR-008: プラットフォーム事実の確定を独立した先頭ステップに置く

### Status

Proposed

### Context

計画初版はプラットフォーム制約の確認を design.md 第2.1節（実装ステップ1の中の1節）として扱い、事実誤認は「リスクと注意点」に列挙するに留めていた。

しかし DO のストレージ上限・単一 Alarm・`transactionSync` の同期性・カーソルの `await` 跨ぎ・FTS5 とトークナイザの可用性・`blockConcurrencyWhile` の30秒・`overloaded` のリトライ禁止は、design.md の第4章から第9章までの結論の土台になる。誤認したまま書くと全成果物に波及し、`.adr/` に書かれた場合は後続 Issue まで汚染する。

「書きながら調べる」構造では、調査と執筆が混ざって誤認が紛れ込みやすい。

### Decision

**プラットフォーム事実と先行資料の確定を実装ステップ1として独立させ、design.md の執筆（ステップ2以降）はその上で行う。**

## ADR-009: 受け入れ基準は design.md の節番号ではなく節タイトル（論点名）で参照する

### Status

Proposed

### Context

計画初版の受け入れ基準は design.md の**節番号**に強く結合していた（AC-4「第4〜6章の全節」/ AC-5「第7.1 / 7.3 / 7.4 / 7.5 / 7.6 節・第8章・第9章」/ AC-13「第6.1節」/ AC-14「第5.2節」/ AC-21「第3.1節と第11.4節」/ AC-22「第4.3節」/ AC-23「第5.2節・第6章」）。

design.md はまだ1行も書かれていない。構成案は約50節あり、執筆中に節を足し引きする可能性は高い（実際、2周目のレビューで第5.2.5節・第5.4.1節を追加することになった）。節番号を1つずらすだけで、実装ステップ10 の機械的検証が全滅する。

選択肢は3つあった。

1. 節番号のまま維持し、構成を変えたら AC 表も追随して直す
2. 節番号を捨て、論点名だけで参照する
3. 論点名を主にし、節番号を括弧付きの参考として併記する

### Decision

**3 を採る。** AC の検証欄は「canonical 化の定義（正規化手順 / `Email.create` を唯一の出所にするか / SSO subject の扱い / 規則変更の位置づけ）が結論として書かれている」のような**論点名**で書き、節番号は `（参考: 第5.2.1節）` の形に落とす。

1 は二重管理になる。design.md を書きながら AC 表を直し続けることになり、レビュー中に不整合が生まれる。

2 は執筆者・レビュアーが該当箇所を探すコストが上がる。構成案が存在するのだから、初期対応としての節番号は残したほうが速い。

3 なら、検証の実体（「その論点に結論があるか」）と AC の記述が一致し、design.md の構成に自由度が戻る。

**AC 番号（AC-1〜AC-23）自体は動かさない。** レビューファイル（`.thread/34/plan-review/*`）と指摘台帳がこの番号を参照しているため、付け替えると過去のレビュー記録が読めなくなる。追加が必要なら AC-24 以降を末尾に足す。

### Consequences

- 良い点: design.md の章立てを変えても AC が壊れない。AC の意味（何を検証するのか）が読み手に明確になる
- トレードオフ: 検証欄の文字数が増える。節番号だけの短い記述より読むコストが上がるが、機械的検証が空振りするコストのほうが大きい

## ADR-010: design.md の各節に「Issue 要求 / 派生 / 参考」の3ラベルを付け、AC-5 の対象を前2つに絞る

### Status

Proposed

### Context

Issue の対応項目3・4 が求めている決着項目は12項目程度である。一方、計画の design.md 構成案は11章・約50節あり、Issue 本文に対応する要求が無い節がいくつも含まれる（プラットフォームエラー翻訳表 / 鍵の所有者と世代管理 / location hint と jurisdiction / `getContainer()` の去就 / `SerializedError` の RPC 越し維持 / 運用上の論点の章）。

- 執筆時: Issue 未要求の節を「AC-5 の断定形要求が掛かる節」と誤認し、根拠の薄い断定を書き込む

### Consequences

- 良い点: 執筆の優先順位が明確になる。レビューで「これは根拠が要る断定か」を判定できる。Issue のスコープを超えた分量が見える化される
- トレードオフ: ラベルの判定自体に裁量が入る。迷った節は `.thread/34/adr.md` に記録する（実装ステップ9）

## ADR-011: 「ユーザー境界に閉じない処理」の網羅性は `spec/inventory/adapter.md` の `ADP-*` 台帳走査で担保する

### Status

Proposed

### Context

AC-22 は「ユーザー境界に閉じない処理が**全数**棚卸しされ、各行に行き先が割り当てられている」を要求している。この表が design.md 第4.3節の入力になるので、漏れたものは誰の関心事にも割り当てられないまま #37 に落ちる。

ところがこの表は2周のレビューで2回拡大した。

- 計画初版: 7件
- 1周目のレビュー後: 6カテゴリ・16行
- 2周目のレビュー後: 8カテゴリ・25行

2周目で見つかった漏れは `PasswordResetTokenPort.verifyAndConsume`（グローバルなトークン空間から user を解決するポート）/ `UserRepository.findByEmail`・`findBySsoIdentity` / `SearchIndexPort.upsert*` / `AiClientConnectionRepository.insert`・`save` / 期限切れ列挙用インデックス3本 / indexer 専用 WorkerContainer など。**「全数」を名乗る表が2回連続で全数でなかった**ことになる。

原因は取り方にある。「思いついたものを列挙する」方式では、列挙者が意識していないカテゴリが構造的に落ちる（たとえば「ポートは挙げたがスキーマ側の実現手段は挙げていない」「読みは挙げたが書きは挙げていない」）。

### Decision

**手作りの列挙を捨て、`spec/inventory/adapter.md` の `ADP-*` 要素台帳の全件走査に切り替える。**

同ファイルは `spec/database/` と `spec/domains/`（ポート定義）から生成された台帳で、スキーマ14件 + ポート実装 identity 16 / memo 13 / knowledge 27 / search 9 / trash 4 / export 2 を `ADP-*` の ID 付きで持つ。ここに機械的な述語をかける。

- **(a) userId を第一引数に取らないポート**
- **(b) `user_id` 列を持たない・PK に含まないテーブル**

台帳の粒度では捕まらない次元（DI 構成・ジョブ・spec 上の未設計領域）だけを、末尾のカテゴリで手動補完する。

AC-22 の検証も2段にする。**主判定**は「表の25行すべてに行き先が入っている」、**網羅性の再検査**は「`ADP-*` を全件走査して漏れがゼロ」。カテゴリ数（8）は補助扱いにする — 括り方を変えても検証が壊れないようにするため。

design.md 執筆前（実装ステップ2）にもう一度台帳を走査し、出た漏れは表に足す。

### Consequences

- 良い点: 網羅性の根拠が「列挙者の記憶」から「台帳 + 述語」に変わり、再現可能になる。spec 側の追加は台帳の更新として現れるので、将来の乖離も検出できる。台帳が `spec/inventory/*` として既に存在していたのに本 Issue が使っていなかった（「#35 の改訂対象」としか扱っていなかった）のを是正できる
- トレードオフ: 台帳自体が古い可能性がある（`最終同期: 2026-07-25`）。走査時に `spec/domains/` と突き合わせる手間が残るが、ゼロから列挙するよりは軽い。台帳の更新自体は #35 のスコープ

### Status

Proposed

2周目のレビューで「AC 表を23件 → 19件へ統合する」提案があった。重複しているとされたのは3組。

## ADR-014: AC-22 の主判定を「行数」から「台帳走査」へ入れ替え、述語を明文化する

### Status

Proposed

### Context

ADR-011 で網羅性の担保方法を「列挙者の記憶」から「`spec/inventory/adapter.md` の `ADP-*` 台帳 + 述語」へ移した。方法自体は正しかったが、**3周目のレビューで表からさらに4件の漏れが出た** — `ADP-export-002`（`ArchiveWriter.write`）/ pruner 専用の拡張 `WorkerContainer`（`spec/usecases/trash.md:315`）/ `ai_client_connections` のスキーマ側の行 / `ADP-search-001`（`SearchIndexPort.query`）。「全数」を名乗る表が **3周連続で全数でなかった**ことになる。

原因は2つある。

1. **述語が判定として機能していなかった。** 述語 (b)「`user_id` 列を持たない・PK に含まないテーブル」は、設計上すべてのテーブルが単一列 TEXT の `id` を PK にしている以上、**全件が該当してしまう**。実際に適用されていたのは「`user_id` 列が無い、または当該の引き方（ユニーク索引 / 期限切れ索引 / PK 素引き）の経路に `user_id` が入っていない」だった。また述語 (a)「userId を第一引数に取らないポート」の適用も揺れていた — `SearchIndexPort.query(query: SearchQuery)` は除外されているのに、userId が引数オブジェクトの中にある点でまったく同じ `upsertMemo(entry)` / `upsertDocument(entry)` は表に入っていた
2. **AC-22 の主判定の置き方が構造的に漏れを見逃す。** 主判定が「25行すべてに行き先が入っている」である限り、**表そのものが不完全なケースは主判定では捕まらない**。網羅性は補助扱いの「再走査」に依存していた

### Decision

**AC-22 の主判定と再走査を入れ替える。**

- **主判定**: `ADP-*` 全85件を走査して述語を当て直し、**該当する全件が表にある**こと + 各行に行き先が入っていること
- **補助**: 行数（29）とカテゴリ数（8）。走査の結果として導かれる値であって、判定基準ではない

**あわせて述語を明文化し、表より先に置く。**

- (a) `userId` を第一引数に取らないポート。**引数オブジェクトの中に `userId` があるものも該当する** — 規約（`spec/domains/index.md:32`）が求めているのは第一引数による構造的保証であり、オブジェクトの中に埋まっていると型レベルで保証されないため
- (b) `user_id` 列を持たない、**または当該の引き方の経路に `user_id` が入っていない**テーブル。見るのは列の有無ではなく引き方の経路
- (c) 台帳の粒度では捕まらない次元（DI 構成・ジョブ・spec 上の未設計領域）

述語の定義は plan.md の調査結果と design.md 第4.3節の**両方**で、表より前に置く。

### Consequences

- 良い点: 「表が不完全」という失敗モードが主判定で捕まるようになる。述語が明文なので、走査を別の人がやっても同じ結果になる。`ADP-search-001` と `upsertMemo(entry)` のような同型のものが片方だけ落ちる事故が防げる
- トレードオフ: 主判定のコストが上がる（85件の走査が毎回必要）。ただし2周連続で行数判定が漏れを見逃した以上、このコストは払う価値がある。行数を補助に落としたので、台帳が更新されて数が動いても検証は壊れない

## ADR-015: AC-5 の断定形要求の対象を、節の列挙ではなくラベルで定義する

### Status

Proposed

### Context

ADR-010 で design.md の各節に `［Issue 要求］` / `［派生］` / `［参考］` の3ラベルを付け、AC-5 の対象を前2つに絞ることを決めた。ところが **AC-5 の本文はラベルによる定義と節の列挙を併記しており、その2つが食い違っていた。**

3周目のレビューで、列挙から漏れている節が2つ見つかった。

- **「FTS5 のみで日本語全文検索が成立する根拠」（第7.2節・ラベル［派生］）** — AC-5 が**明示的に除外**していた。除外理由は「`.adr/003` を支える根拠だから」。しかし正規化（NFKC）・トークナイザ（trigram）・短語フォールバックが結論に至らないと、`.adr/003`「FTS5 のみを採用する」の妥当性そのものが宙に浮く。しかも trigram の可用性は公式ドキュメントに記載が無く実測だけが根拠という、**最も結論の明記が要る部類**である。結果として `.adr/003` の根拠に結論を要求する AC が1つも無い状態になっていた
- **「分割方式」（第6.2節・ラベル［Issue 要求］）** — 列挙に含まれていなかった。AC-13 の検証欄は「『分割方式』にも節がある」「単一グローバル DO を無条件採用していない」なので、**「(b) が有力だが最終決定は #37」で書かれても通ってしまう**。Identity Directory の分割方式は #37 の前提であり、決着5論点のうちこれだけが断定形を要求する AC を持っていなかった

実装ステップ10 の自己検証は「ラベル前2つの節がすべて断定形」と広く書けているので実運用では拾えるが、**AC-5 本文の節リストと食い違っている**。

### Decision

**AC-5 の「対象」をラベルだけで定義する。** `［Issue 要求］` または `［派生］` が付いた節**すべて**が対象。節の列挙は「したがって次はいずれも対象に含まれる」という**例示**に格下げする。

対象外は次の2つだけにする。

- `［参考］` ラベルの節
- 「検索 API の仕様 → #35 へ委譲」（第7.2.1節）— 本文で明示的に委譲を宣言している節

## ADR-016: AC-8 は「追加はポインタ1行のみ（前後の空行を除く）」で判定し、挿入書式を固定する

### Status

Proposed

### Context

AC-8 は `.thread/1/adr.md` の ADR-004 への supersede ポインタ追記を「削除行が0・**追加行が1**」で判定していた。

実測すると該当箇所は `:160` 見出し / `:161` 空行 / `:162` `### Status` / `:163` 空行 / `:164` `Proposed` / `:165` 空行 / `:166` `### Context` である。ポインタ段落を通常どおり前後に空行を置いて挿入すると**追加行は2**（本文1 + 空行1）になり、AC-8 が落ちる。

空行を足さずに1行だけ挿すことは CommonMark 上は有効（見出しは段落を中断できる）なので**達成は可能**だが、それは**リポジトリの Markdown スタイル（ブロック要素の前後に空行）に反する書き方を実装フェーズに強いる**形になる。`markdown-style` の方針とも衝突する。

選択肢は2つあった。

1. 判定を「追加行が1〜2」に緩める
2. 判定を「削除行がゼロ、かつ追加が supersede ポインタ1行のみ（前後の空行を除く）」に書き換え、あわせて挿入書式を指定する

### Decision

**2 を採る。** 判定の意味を「追加された**内容**は1行だけ」に置き、空行は数から除外する。あわせてステップ8 に挿入書式を書き込む — **`Proposed`（`:164`）の直後に空行1行 + ポインタ1行**。したがって `git diff` 上の追加行は2になる。

1 は数値を緩めるだけで、「なぜ2なのか」が残らない。実装フェーズが「3行でもいいのか」と迷う余地を残す。2 なら判定の意図（本文を1行しか足していない）が読めるので、書式を守っている限り迷わない。

### Consequences

- 良い点: Markdown の規約と AC が両立する。挿入位置まで指定してあるので実装フェーズで判断が要らない。「削除行がゼロ」という本質的な保証（本文を壊していない）は変わらない
- トレードオフ: 判定が「行数を数える」から「差分の中身を見る」に少し重くなる。ただし差分は2行なので目視で済む

## ADR-017: AC-20 の既知 untracked は実測で作り、`.thread/36/` を含める

### Status

Proposed

### Context

2周目に AC-20 へ足した「`git status --porcelain` に既知の untracked 以外の未コミット変更がゼロ」という検査は、commit 漏れによる空振りを塞ぐためのものだった。ところがホワイトリストを**実データを見ずに書いた**ため、`.thread/36/` が漏れていた。

実測した `git status --porcelain` は次の6エントリを返す。

```
?? .artifacts/
?? .thread/34/
?? .thread/36/
?? apps/web/wrangler.request.production.toml
?? apps/web/wrangler.request.staging.toml
?? apps/web/wrangler.state.production.toml
?? apps/web/wrangler.state.staging.toml
```

`.thread/34/` は本 Issue の成果物として commit されるので残らないが、**`.thread/36/` は残る**。#36 はマージ済みだが、その作業ログ（`adr.md` / `plan.md` / `testing.md` / `manual-test/`）が commit されていない。

- 放置すれば AC-20 後半（未コミット変更ゼロ）が**誤検知**で落ちる
- commit すれば AC-20 前半（差分は `.adr/00{2,3,4}` / `.thread/34/**` / `spec/adr/005-*` / `.thread/1/adr.md` に限る）を破る

**ホワイトリスト方式を維持し、実測値で作り直す。** 既知の untracked は `.artifacts/` / **`.thread/36/`** / `apps/web/wrangler.{request,state}.{production,staging}.toml` の4本。

1. **否定形は commit 漏れを検出できない。** この検査の主目的は「成果物の commit し忘れ」を捕まえることで、成果物は `.adr/` と `.thread/34/` に置かれる。`.thread/34/` を否定形の対象に含めれば検出できるが、そうすると `.thread/36/` を含む `.thread/` 全体の扱いを結局ホワイトリストで書き分けることになり、同じ問題に戻る
2. **untracked の残骸が増えたら気づくべきである。** ホワイトリストは「作業ツリーに何が残っているか」を明示する副作用を持つ。実測で作り直す運用（下記）とセットなら、残骸の増加が検査の失敗として現れるのはむしろ望ましい

**`.thread/36/` 自体には本 Issue で触らない。** #36 は完了済みで、その作業ログの commit 要否は本 Issue の判断対象ではない。調査結果に「untracked のまま残っている / 本 Issue では触らない」と記録するだけに留める。

**ホワイトリストは着手時点で `git status --porcelain` を実際に実行して作り直す。** 計画に書いてある6エントリは計画時点のスナップショットである。

### Consequences

- 良い点: ステップ10 の検査が実データで通る。「検出装置を書くときに実データを見る」という規律が明文化される
- トレードオフ: 着手までの間に untracked が増減するとホワイトリストが再びずれる。「着手時点で実行して作り直す」を手順に入れて対処する。`.thread/36/` を本 Issue で commit しないので、#36 の作業ログはしばらく untracked のまま残る

## ADR-018: ステップ2 → ステップ3 の前方依存は「暫定判定 + ステップ3 で確定」で解消する

### Status

Proposed

### Context

実装ステップ2（design.md 第1〜6章）には、ステップ3（第7〜11章）の結論への**前方依存**がある。

- 第4.3節で「そもそも不要になる」に倒れる行は、**第7.1節（FTS5 同期更新の可否）と第7.3節（Outbox 廃止範囲）の結論が出るまで確定しない**
- 第5.4.1節 (b)（失効の到達手段）は本文自身が「Outbox 前提が 7.3 で消えるので決め直しが要る」と書いている

ステップ7（`spec/adr/005` の supersede）は同種の従属を「**前提**: 第7.1節が肯定的結論を出した場合に実施する」として扱えているのに、ステップ2 には同じ扱いが無い。単一ファイルを1人で書くので実務上は往復で吸収できるが、**順序の宣言としては逆流している**。

選択肢は2つあった。

1. ステップの順序を依存順に並べ直す（第7章を第4〜6章より先に書く）
2. 依存がある旨と解消手順をステップ2 に明記する

**2 を採る。** 具体的には3段階にする。

1. ステップ2 では従属する行・項目を「**7.1 / 7.3 の結論に従属。暫定判定: 〜の見込み**」と、暫定と分かる形で書く
2. ステップ3 で第7章を書き終えた**直後に**第4.3節 / 第5.4.1節 (b) / 第6.4節へ戻り、暫定を確定に置き換える
3. ステップ10 の自己検証で「暫定」「見込み」「〜次第」という語が第4〜6章に残っていないことを確認する

1（順序の入れ替え）を採らない理由は、第7章のほうが第4〜6章に依存する部分も相当あるためである — 第7.5節（trash retention）は第4.3節の帰属判断を前提にし、第7.4節（Alarm ジョブの所有者）は第3.1節のクラス構成と第6.4節の補償設計を前提にする。**依存は相互であって一方向ではない**ので、並べ替えでは解けない。解けるのは「どちらを先に書くか」ではなく「暫定をいつ確定に変えるか」を決めることである。

### Consequences

- 良い点: 依存が文書に現れるので、着手時に「なぜ第4.3節が埋まらないのか」で止まらない。ステップ7 の「前提」節と同じ扱いになり、計画内で表現が揃う。ステップ10 に機械的な検査（暫定を示す語が残っていない）が1つ増える
- トレードオフ: 第4〜6章に一度書いた箇所を書き直す往復が明示的なコストとして現れる。ただしこれは依存の実態であって、隠しても消えない

## ADR-019: プラットフォーム事実は「裏取り済み」でも主張の実在と裏付けの種別から点検する

### Status

Proposed

### Context

ADR-008 で「ステップ1 はゼロからの再調査ではなく差分確認」と決め、2周目のレビューで「プラットフォーム事実14項目は公式ドキュメントで全件一致が再確認された」と記録した。にもかかわらず、**3周目に3件の誤りが見つかった**。

1. **「`idFromName` に渡した名前は復元できない」は誤り。** 公式（`/durable-objects/api/id/`）は `name` を `DurableObjectId` の optional property と定義し、「especially useful inside **alarm handlers**, where there is no calling client to pass the name as an argument」と、本 Issue が設計する Alarm ジョブそのものを用例に挙げている
2. **「仮想テーブルは原則禁止だが FTS5 のみ例外」は出典が無い。** 該当ページを取得しても相当する記述が無く、仮想テーブルに言及するもう一箇所は課金の一文で、むしろ一般に使える前提の書き方になっている
3. **`bm25` / `snippet` / `highlight` は公式ドキュメントに一語も現れない**（workerd の allowlist ソースには存在するが、それは実装ソースであってドキュメントではない）のに、「公式にサポート明記」の側に書かれていた

3件に共通するのは「**値は合っているか**」ではなく「**その主張が出典ページに実在するか**」「**裏付けの種別（公式記載 / 実測 / 未確定）が正しいか**」の誤りだという点である。差分確認は前者しか見ない。

さらに悪いことに、計画が「この表は裏取り済み。ステップ1 は再取得ではなく差分確認」と宣言していること自体が、**再点検を止める作用**を持っていた。誤りは点検されずに design.md 第2.1節（#35 / #37 が読む正本）へ転記される経路にあった。

計画は「公式に記載が無い事項は『実測』または『未確定』と明示して区別する」という規律を自分で立てており、トークナイザにはそれを適用していたのに、**同じ行の他の主張には適用できていなかった**。

### Decision

**ステップ1 の差分確認に「主張の実在」と「裏付けの種別」の点検を含める。** 各行について次の3つを見る。

1. 値が変わっていないか（従来の差分確認）
2. **その主張が出典ページに実在するか**（原文を引ける表現になっているか）
3. **裏付けの種別が正しいか** — 公式記載 / 実測（`.thread/19/spike/fts5.integration.test.ts` 等）/ 未確定 のどれか

**裏取りできないものは「未確定」または「ステップ1 で実測して確定する」項目へ落とす。** 具体的には trigram トークナイザ・`bm25`・`snippet`・`highlight` の4つを実測項目に落とし、spike が触れていない関数があれば「未確定」のまま残して、第7.2節と `.adr/003` はその関数に依存しない書き方にする。

**事実の訂正が設計判断を再オープンするかは、判断ごとに切り分けて書く。** `ctx.id.name` の訂正では第6.2節 (c) の不採用理由と第6.8節の結論は再オープンしない — そこで効いているのは「namespace を実行時に列挙できない」という別の（確認済みで正しい）事実だからである。一方、第6.3 / 6.8 / 7.4節の「DO に自分の routing key を明示的に渡す」配線は不要になりうるので、そこは設計に反映する。**訂正のたびに「何が動いて何が動かないか」を1行添える。**

### Consequences

- 良い点: 誤認が design.md 第2.1節へ転記される経路を塞げる。「公式保証だと誤認する」という #35 / #37 側の失敗が防げる。訂正の波及範囲が明示されるので、事実が1つ直るたびに設計全体を疑い直さずに済む
- トレードオフ: ステップ1 のコストが「値の差分確認」より上がる。ただし18項目・各1行の確認であり、誤認が全成果物に波及するコストのほうが桁違いに大きい。3周のレビューで実際に3件出た以上、経験的にも正当化される

### Context

## ADR-028: signup の `operationId` と候補 `userId` をサーバー採番に固定し、リクエスト跨ぎの冪等性を Directory 予約行へ寄せる

### Status

Accepted

### Context

design.md 第6.3節 phase 0 と第6.5節は「`operationId` は request Worker が採番し、再送中は同じ値を保持する」「その値をそのまま候補 `userId` として使う」と書いていた。しかし request Worker はステートレスでリクエストを跨いで値を保持できない。保持を成立させる手段はクライアント供給（hidden field / `Idempotency-Key`）しか無く、それを採ると外部入力がそのまま `idFromName()` の引数になり、第5.2.2節 (a)(ii) と第5.5節 1 の「外部入力が locator の材料にならない」という中核の構造的保証が偽になる。攻撃者が被害者の `userId` を `operationId` として送れば、未認証のまま他人の User Data DO へ書き込める。

### Decision

**`operationId` と候補 `userId` を分離し、どちらも request Worker がリクエストごとに `IdGenerator` で新規採番する。クライアントからは受け取らない。**

- ブラウザからの再 POST は毎回新しい値になる。**「リクエスト跨ぎの再送」という概念を signup に持ち込まない。**
- 落ちた saga を前進させるのは Alarm による再開だけである（`resume-signup`）。
- リクエスト跨ぎの冪等性は **Directory bucket の予約行**が担う。同じ canonical への予約は勝者決定規則で1本に収束するので、再 POST が2つ目のアカウントを作らない。
- 二重の防波堤として、signup の RPC エントリに「対象 DO に `account` 行が既に存在するなら無条件で拒否する」ガードを置く。第5.5節 4（他ユーザーの行が存在しない）は**読み取りには効くが書き込みには効かない**ので、書き込み側のガードを別に立てる必要がある。
- `HMAC(SIGNUP_SECRET, canonical)` による決定的導出は「どうしても跨リクエストの `operationId` が要る場合の唯一許される形」として design.md に書き残すが、本設計では採らない。`userId` には決して使わない（第5.2.2節 (a) の「鍵に依存しない locator」を壊すため）。

### Consequences

- 良い点: 第5.5節の構造的保証が signup を含めて成立する。#37 が冪等キーをクライアントに持たせる実装へ倒れる余地が消える
- トレードオフ: 同じ canonical への同時 signup で敗北した候補 `userId` は捨てられる。ただし phase 順を入れ替えた（ADR-029）ので、敗北側は User Data DO を作る前に止まり、捨てられるのは予約の試行だけになる

## ADR-029: signup saga の phase 順を入れ替え、Directory 予約を User Data DO 生成より先にする

### Status

Accepted

### Context

design.md 第6.2節は「(iv) 未認証経路からの DO 生成」を独立した判断軸として立て、credential 1件 = DO 1個の案を「任意の未認証文字列が新しい DO 名を引く」「資源枯渇の攻撃面」として棄却していた。ところが**同じ軸を User Data DO に当てていなかった**。第6.3節の phase 順は「User Data DO に operation 行を書く → Directory 予約」であり、メールが既に登録済みかを判定する前に User Data DO が1個作られて書き込みが発生する。しかもこの順序は第3.1節で Account Home を採らない根拠の一部として意図的に選ばれていた。

### Decision

**phase 1 と phase 2 を入れ替える。「Directory 予約 → User Data DO 初期化 → mapping 昇格 → reverse locator 記録」の4 phase にする。**

- saga のコーディネーター状態は予約行が持てるので、跨ぐ DO 数も補償の相手も増えない。
- 前進の駆動も Directory bucket 側へ移す（`resume-signup` を bucket の job table に置く）。phase 1 が起点なので、落ちたときに操作を知っているのは予約行だけだからである。
- 補償の境界規則は「phase 3 以降は前進」から「**User Data の初期化完了（phase 2 の成功）以降は前進**」へ言い直す。境界の意味（利用者から見てアカウントが存在し始める点）は変わらない。
- 第3.1節の Account Home 比較の記述も新しい phase 順に合わせる。

### Consequences

- 良い点: 重複チェックに勝った signup だけが User Data DO を作る。判断軸 (iv) が両 namespace に一貫して適用される
- トレードオフ: 「異なる canonical を大量に投げる」攻撃では依然として DO が増える。これは順序では解けないのでレート制限（ADR-034）へ送った。設計はその残余リスクを隠さず書く

## ADR-030: login に到達性検査と `credentialVersion` 照合を組み込む

### Status

Accepted

### Context

design.md 第6.6節・第6.7節は「fail closed で拒否する」根拠に login 時の「到達性検査」を置いていたが、第5.1節にも第5.3節にもその検査が定義されていなかった。epoch ガードは「トークンが持つ epoch と現在値の照合」であり、**login は新規にトークンを発行する側なので照合対象が存在しない**。しかもパスワード検証材料は残存 mapping 行そのものに載っているため、unlink 後の孤児 mapping で login 手順が全部通り、解除済みクレデンシャルでセッションが発行される。加えて、login の step 3（Directory から検証材料取得）と step 5（User Data DO から epoch 取得）の間に credential 変更が完走すると、旧パスワードでの照合が成功したまま新しい epoch を載せた有効なセッションが発行される TOCTOU があった。

### Decision

**login の step 5 を「1回の RPC で3つを確認する」形に確定する。** (i) `account.status` が `active`、(ii) **到達性検査** — bucket から得た locator が `credential_locators` に active 行として存在する、(iii) **`credentialVersion` の一致**。

- `credentialVersion` は **credential ごとの単調増加カウンタ**で、Directory 側 `credential_mappings` と User Data 側 `credential_locators` の両方に持つ。アカウント単位にしない — SSO link で新しい credential を足したときに既存 credential のバージョンが取り残されてログインできなくなるためである。
- 追加の往復は発生しない。step 5 は既に叩いている DO の中の2テーブルを読むだけである。
- **この検査は Account Home を採らない設計の成立条件そのものである。** 「権威はすべて `userId` で引ける」（第3.1節）が成立するのは、到達性検査を login に組み込んだときだけである。

### Consequences

- 良い点: unlink 後の孤児 mapping・credential 変更の TOCTOU がどちらも fail closed で塞がる。Account Home 不採用の論証が完結する
- トレードオフ: `credential_locators` が login のホットパスに入る。ユーザー1人あたり数行なので実コストは無視できる

## ADR-031: state Worker に両 DO binding を置き、第5.5節を「外部入力からの導出点は1箇所」へ言い直す

### Status

Accepted

### Context

design.md 第5.5節 1 は「`idFromName` を呼ぶのは request Worker の1モジュールだけにする」と断定していた。一方で第6.4節（saga の前進）・第6.6節（孤児 mapping の削除）・第6.7節（退会の mapping 削除）はいずれも DO の側から他 DO を操作することを要求しており、両立していなかった。第3.2節・第3.3節も state Worker 側の binding の有無を述べていなかったため、#37 は「binding を足すか、Alarm から request Worker へ折り返すか、Directory 側から pull させるか」で手が止まる。

### Decision

**state Worker に `USER_DATA` と `IDENTITY_DIRECTORY` の両方の binding を置き、DO 間の相互呼び出しを許す。** そのうえで第5.5節 1 を「**locator を外部入力から導出するのは request Worker だけ。DO 側は自分の SQLite に永続化済みの locator しか使わない**」へ言い直す。

- User Data DO → Directory bucket は `credential_locators` に記録済みの locator、Directory bucket → User Data DO は `credential_mappings` 行が持つ `userId` を使う。どちらもサーバーが過去に採番・記録した値であり、その呼び出しの外部入力に由来しない。
- state Worker は公開ルートを持たない。到達手段は binding 経由の RPC だけである。
- input gate の再入は第6.9節に3制約（トランザクション外で呼ぶ / phase を永続化してから呼ぶ / 各 phase を冪等にして再入を吸収する）として書く。**ロックで止めるのではなく冪等性で吸収する** — 非同期区間の排他はそもそも取れないからである。

### Consequences

- 良い点: 第6章の全 saga が実装可能になり、wrangler 設定・DI・再入設計が確定する
- トレードオフ: 「locator の導出点は1箇所」というスローガンが1文で言えなくなる。代わりに「外部入力からの導出点は1箇所」＋「DO 側は永続化済み locator のみ」の2文になる

## ADR-032: credential 変更 saga を Directory 起点で新設し、旧検証材料の即時無効化を先頭に置く

### Status

Accepted

### Context

パスワード変更とリセット完了は「新しい検証材料を Directory に書く」＋「User Data DO の `sessionEpoch` を進める」の2 DO をまたぐ操作なのに、design.md には順序も補償も無かった。Alarm の `kind` 一覧にも前進ジョブが無く、落ちたら誰も拾わない。Directory 先なら旧セッションが7日生き残り、epoch 先なら旧パスワードが通り続ける。

### Decision

**第6.5.1節として credential 変更 saga を新設し、4 phase（新検証材料の計算 → Directory で旧材料を即時無効化 → User Data で epoch と `credentialVersion` を前進 → Directory で昇格）にする。**

- **phase 1 で `changeState: 'pending'` を立てた瞬間から旧検証材料での照合を拒否する。** 中間状態では旧も新も通らない（可用性は落ちるが認可は開かない）。
- 前進の駆動は **Directory bucket の Alarm（`resume-credential-change`）**。phase 1 が起点なので、落ちたときに操作を知っているのは mapping 行だけである。
- リクエスト跨ぎの冪等性は `changeState` + `operationId` が担う。別 `operationId` の変更依頼が `pending` 中に来たら後勝ちで差し替える（利用者がリセットをやり直すケースが自然に通る）。
- TOCTOU は ADR-030 の `credentialVersion` 照合で塞ぐ。

### Consequences

- 良い点: 「パスワードを変えたのに攻撃者のセッションが残る」「epoch は進んだのに旧パスワードが通る」の両方が消える
- トレードオフ: saga 中は当該クレデンシャルでログインできない期間ができる。可用性より認可を優先する判断であり、利用者にはリセットのやり直しを案内する

## ADR-033: 退会の削除順序を入れ替え、`credential_locators` を最後に消す

### Status

Accepted

### Context

design.md 第6.7節は「`account.status = 'deleted'` にする。`credential_locators` はこの時点で消す」→「Directory bucket の mapping 行を物理削除する」の順だった。`credential_locators` は「世代 + bucket index + 全長 HMAC」を持つ唯一の逆引き情報なので、これを先に消すと mapping 削除の前に落ちた場合に所在を知る手段が消える。HMAC は一方向で、canonical 原本は削除対象の行の中にしかない。結果、`encryptedCanonical`（PII）が無期限に孤児として残り、そのメールアドレスは永久に再登録できなくなる。Alarm の `kind` 一覧にも回収ジョブが無かった。

### Decision

**「tombstone 先行 → mapping 削除 → `credential_locators` 削除」の順にする。**

- 削除対象は `credential_locators` に記録された**全世代分**とし、鍵ローテーション中に備えて「active / previous の両世代へ削除を発行し、無ければ成功」の冪等規則を置く。
- 回収は `kind: 'finalize-withdrawal'` ジョブが担う。予約 TTL 掃除は `reserved` 行しか見ないので、`active` な孤児 mapping には専用ジョブが要る。
- 最後の砦として「`userId` を指定して自 bucket 内の全 mapping 行を削除する」冪等 RPC を bucket に持たせ、256 bucket 走査による operator 復旧経路を #38 へ送る。

### Consequences

- 良い点: 第6.2.1節 (d)「bucket 側には何も残さない」が実際に守られる。永久ロックが消える
- トレードオフ: mapping を先に消すので、`deleted` になる前の短い期間だけ「mapping は無いが User Data は残っている」状態が生じる。`account.status = 'deleting'` が既にゲートになっているので認可上の穴は開かない

## ADR-034: 未認証経路の濫用抑止を3層で置き、標的型 `overloaded` は DO の外で止める

### Status

Accepted

### Context

bucket 分割は一様分布を前提とした緩和策で、標的型攻撃には効かない。攻撃者は単一のメールアドレスを狙えるので任意の1 bucket を `overloaded` に追い込め、リトライ禁止（第2.1節 #19）と相まって約 1/256 のユーザーを締め出せる。パスワード総当たりに対する試行回数制限も設計に無かった。単一グローバル DO 案を棄却した理由が soft limit だったので、この論点は設計自身の判断軸に直結する。

### Decision

**第6.2.2節を新設し、3層で抑止する。**

1. `credential_mappings` 行に `{ failedAttempts, nextAttemptAllowedAt }` を持たせ、指数バックオフでロックする。DO 化で「同じ canonical への試行が必ず同じ行に集まる」という**カウントに最適な構造**が手に入っているので使う。ロックアウト中の応答はダミー材料経路へ倒し、ロックの有無を列挙オラクルにしない。
2. リセット依頼は canonical 単位でレート制限する。
3. **標的型の `overloaded` は DO に届く前に止める** — Cloudflare の WAF / Rate Limiting Rules を未認証エンドポイントに当てる。**bucket 数を増やしても解決しない**（攻撃者は同じ canonical を狙う）。

具体値（試行回数・バックオフ係数・依頼間隔・WAF の閾値）は #38 へ送るが、**「どのレイヤーで当てるか」は本 Issue で決着させる** — DO 側で受けてから数える設計は、数える前に `overloaded` になるという順序で破れるためである。

### Consequences

- 良い点: 判断軸 (iv) の残余リスクに具体的な受け皿ができる
- トレードオフ: 認証の可用性が Cloudflare のエッジ機能に依存する。ロックイン（`.adr/002`）の一部として受け入れる

## ADR-035: メール暗号鍵に世代管理と AEAD を定め、再 HMAC を bucket の中で行う

### Status

Accepted

### Context

design.md 第6.2.1節 (b) は鍵分離の論拠として「routing secret はローテーションのたびに世代が増えるが**暗号化鍵はそうではない**」と書いており、`IDENTITY_MAIL_ENCRYPTION_KEY` にローテーション経路が無いことを宣言してしまっていた。暗号方式（AEAD かどうか、nonce 規則、AAD）も未定義で、AC-23 (c) の「保護方式」が未決だった。さらに第6.2.1節 (c) の復号経路2 は「このときだけ canonical が request Worker 側へ渡る」としており、**全ユーザーのメール平文が bulk で Worker 境界を越える**のに保護規定が無かった。

### Decision

**(a) 暗号化鍵も世代管理する。** `{ generation, key }` の keyring を state Worker に配り、`credential_mappings` 行に `encryptionGeneration` を記録する。再暗号化は `kind: 'rotate-encryption'` の bucket Alarm ジョブで、retirement 証明は第6.8節と同じ「bucket ごとの snapshot 置換」に乗せる。routing secret の世代とは独立した番号体系にする。

**(b) 暗号方式を AES-256-GCM に確定する。** 行ごと・書き込みごとにランダム96ビット nonce、**AAD に `(kind, hmac, encryptionGeneration)` を束縛**する。束縛しないと bucket 内で暗号文を別の mapping 行へ付け替えられ、「リセットメールを別アドレスへ送らせる」経路が開く。復号失敗は `SystemError(DataIntegrityError)` で fail closed。

**(c) 再 HMAC は bucket の中で行い、平文を Worker 境界の外へ出さない。** maintenance 経路が active 世代の routing key を RPC 引数として**一時注入**し、bucket が復号 → 再 HMAC をローカルに完結させる。第3.2節の配布境界が禁じているのは state Worker が routing secret を**バインディングとして保持する**ことであって、operator が明示的に起動した保守経路で鍵が一度だけ引数として渡ることではない。**鍵1本の一時的な越境と全 PII の bulk 越境を天秤にかけ、前者を選ぶ。**

### Consequences

- 良い点: AC-23 (c) が保持場所と保護方式の両方で決着する。鍵漏洩時の再暗号化経路ができる。ローテーション時の PII 越境が消える
- トレードオフ: state Worker 側に「一時的に鍵を受け取る RPC」が生まれる。ログ・トレースの無効化と平文の非永続化を運用要件として #38 へ送ることで補う

## ADR-036: AI クライアントトークンを別鍵 + audience タグ + scope 突き合わせにし、credential 変更では失効させない

### Status

Accepted

### Context

design.md 第5.4節はトークンを「セッショントークンと同じ方式」とだけ書き、署名鍵が第3.2節の秘密配布表に無かった。`scope` はトークン内の自己完結値で、DO 側が保存値と突き合わせるとは書かれていなかった。さらに第6.7節が「`sessionEpoch` を進める ⇒ AI トークンも全部無効」と書いていたが、トークンに epoch が無いのでこれは事実と違う（実際に効いているのは `account.status` ガード）。

### Decision

1. **`AI_CLIENT_TOKEN_SECRET` を別鍵として立てる。** TTL も失効機構も発行契機も違う2種類を同じ鍵で署名しない。
2. **audience タグ `typ` を両方のペイロードに必須で入れ、検証側で厳密一致を要求する（欠落は拒否）。** 鍵分離だけに頼らず構造でも弾く。現行 `parsePayload` が `uid` / `exp` の存在しか見ないため、型混同が実装依存で成立しうるからである。
3. **`scope` はトークンを信頼せず、`ai_client_connections` の保存値との積を有効 scope とする。** トークン内 `scope` は早期拒否の最適化に留める。失効（`status`）は全否定にしか効かず、権限**縮小**には効かないためである。
4. **credential 変更（パスワード変更・リセット・SSO 解除）で AI クライアント接続を一括失効させない。** AI 接続は利用者が接続ごとに管理する独立した認可であり、パスワード変更がその取り消し意思を意味しない。**帰結（侵害からの復旧には個別 revoke が必要）を隠さず書き、#38 の運用ドキュメントと設定画面の文言へ送る。**
5. 第6.7節の因果説明を「セッションは epoch 不一致、AI トークンは `account.status` ガード」と機構別に書き分ける。

### Consequences

- 良い点: 型混同と scope 格上げが塞がる。#37 が epoch だけを実装して AI トークン側のガードを落とす危険が消える
- トレードオフ: 「パスワードを変えれば全部切れる」という直感に反する挙動を、文言で補う必要がある

## ADR-037: リセットトークンに世代を含め、ローテーション時は移送せず無効化する

### Status

Accepted

### Context

トークン形式 `{bucketIndex}.{random}` は bucket index だけを埋め込むが、bucket の DO 名は `dir:g{generation}:b{index}` で世代が要る。第6.8節の移送対象も `credential_mappings` 行だけで、リセットトークン行は入っていなかった。結果、ローテーション中に発行済みのトークンはどの世代を引けばよいか決められず、引けても行が旧 bucket に取り残される。加えて、URL に bucket index を出すことが第5.2節 (c)「locator を URL に出さない」と矛盾していた。

### Decision

**トークン形式を `{generation}.{bucketIndex}.{random}` にする。ローテーション時にトークン行は移送せず、世代が previous へ落ちた時点で発行済みトークンを無効にする。**

- TTL が時間オーダーなので利用者影響は「リセットをやり直す」だけであり、移送機構を1つ増やす価値が無い。旧 bucket に残った行は同 bucket の Alarm が TTL 掃除で消す。
- **世代 + bucket index の URL 露出は第5.2節 (c) の明示的な例外として記録する。** 漏れるのは世代番号と約 8 ビットで、canonical との照合には routing secret が要る。残余リスク（複数リセット URL の弱い名寄せ）は受容する。独立ルーティングタグ案は、対応表の置き場所がまた「どの bucket にあるか分からない行」になるので採らない。

### Consequences

- 良い点: ローテーション中の到達不能が消え、(c) との矛盾が設計文に自覚される
- トレードオフ: ローテーション開始直後のリセット依頼が失敗しうる。#38 の運用手順で告知する

## ADR-038: `ctx.storage.transaction()` を代替案 (c) として記録し、明示的に棄却する

### Status

Accepted

### Context

第8.2.1節は選択肢を (a) 同期化 / (b) `SemanticCommitPort` の2つに閉じていたが、公式には `ctx.storage.transaction(closure)` という **`Promise` を返し、コールバックを `async` にできる**トランザクション API が存在する。第2.1節の事実表にもこの API が載っていなかった。ドメインポートから `Promise` を剥がす決定は本 PR で最も高価で、`CLAUDE.md`「Reference runtime」の不変条件を破棄する唯一の理由なので、検討していない選択肢が残っていると #37 が着手直後に設計を再開させる。

### Decision

**第2.1節に fact #27 として `transaction()` を追加し（種別: 公式記載）、第8.2.1節の選択肢を (a)(b)(c) の3つにして (c) を棄却する。結論（同期 UoW）は維持する。**

棄却理由は「`transaction()` が非同期でも原子性を保つことを意味しないから」である。同じ公式ページが「**明示的なトランザクションはもはや必要ない。`await` を挟まない書き込み列は自動的に原子的に提出される**」「SQLite-backed では `txn` は obsolete で、`ctx.storage` への操作がトランザクションの一部として扱われる」と述べており、原子性の条件は `await` の不在の側にある。`await` を挟めば input gate が開き、割り込んだ別ハンドラの `ctx.storage` 書き込みまで同じトランザクションに巻き込まれる。カーソルのスナップショット安定性も失われる（fact #9）。結局「コールバック内で `await` しない」を人手で守ることになるので、`async` を型で排除して**言語の規則として守らせる**ほうが強く、実行時コストも同じである。

### Consequences

- 良い点: 最重量の意思決定の根拠が完結する。#37 の再燃を防ぐ
- トレードオフ: 事実表と第8.2.1節が長くなる。棄却の記録は残す価値があるので許容する

## ADR-039: Alarm の再武装をハンドラ先頭で行い、チェックポイント予算を固定値で近似する

### Status

Accepted

### Context

第7.4節は再武装を `finally` に置いていたが、同じ節が支配的な失敗モードとして自ら定義した「CPU 予算超過はエラーではなくエビクション / リセットとして現れる」条件では isolate ごと殺されるので `finally` は走らない。フォールバックの「次の DO 入力で再計算」は、未認証トラフィックが常時来る Directory bucket では機能するが、**dormant な利用者の User Data DO では次の入力が来ない** — その `purge-trash` は恒久的に停止し、誰も気づかない。加えて第7.4節は「判定基準は CPU 予算」と繰り返す一方、実行時に残り CPU を読む API が無く、具体値も消えていた。

### Decision

1. **`alarm()` の先頭で、仕事を始める前に `now + チェックポイント予算` へ `setAlarm` する。** 正常完了時に DB の最早 `nextRunAt` へ張り直す。`finally` での再設定は最適化として残すが、**正しさの拠り所にしない**。
2. **`alarm()` から throw しない。** 公式のリトライ（2秒から最大6回）を使い切ると alarm が消えるので、ジョブランナーが個々の失敗を `try / catch` で吸収して `attempt` / `nextRunAt` を進める。公式の「別マシンで再インスタンス化され**うる**（may）」には寄りかからない。
3. **チェックポイント予算は「ジョブ25件 または 累積経過時間10秒」の固定値で近似する。** 測っているのが CPU ではなく経過時間であることを承知の上で、CPU ≤ 経過時間を使って安全側に倒す。値は先行案（第1.3節で採用済み）から引き継いだ。見直しの契機は #38。

### Consequences

- 良い点: 自ら定義した失敗モードと設計が一致する。dormant DO の retention 停止が消える
- トレードオフ: 予算が尽きなかった場合に無駄な alarm 発火が1回入りうる。`setAlarm` 1回は1行書き込み相当の課金（fact #24）なので許容範囲

## ADR-040: lazy migration のゲートと fail-closed を `alarm()` へ広げ、ゲートを同期関数にする

### Status

Accepted

### Context

第9.2節はゲートを「全 RPC エントリの先頭」に限定していたが、dormant な User Data DO が次に起きる契機は `purge-trash` の Alarm しか無い。ゲートが `alarm()` に掛かっていないと、未 migrate の DO に対して新コードのジョブ実行部が新スキーマ前提の SQL を投げる。第9.4節の fail-closed（コードより新しい version）も同じく alarm 経路に掛かっていなかった。また `blockConcurrencyWhile` を明示的に棄却した以上、代わりの排他条件が必要だが、それが書かれていなかった。

### Decision

1. **ゲートを「全 RPC エントリ**および** `alarm()` の先頭」に置く。** 第7.5節の「アクセスが無くても期限処理が走る」という主張は、このゲートが `alarm()` に掛かって初めて成立する。
2. **第9.4節の fail-closed も `alarm()` に掛ける。** 止まった DO の `alarm()` はジョブを実行せずバックオフ付きで `setAlarm` を張り直して戻る。**poison にはしない** — 原因はデータではなくデプロイ状態であり、正しいコードが戻れば回復すべきだからである。
3. **ゲート関数は同期関数とし、`schema_version` の読み取りから全 DDL ステップの適用まで `await` を挟まない。** これで input gate が排他を保証する。`await` が入るとステップ間に並行 RPC が割り込み、順序依存のある migration で途中の観測が壊れる。重い部分を `migrate-bulk` ジョブへ逃がす方針とは両立する（ジョブ投入は同期の1行書き込み）。

### Consequences

- 良い点: B-002 / W-005 が同じ「alarm 経路を RPC と同格に扱う」で同時に塞がる
- トレードオフ: `alarm()` の先頭処理が増える。1行の `SELECT` なので無視できる

## ADR-041: 短語フォールバックの結論を実測に合わせて `instr()` に確定する

### Status

Accepted

### Context

第7.2節は「1〜2文字のクエリは `LIKE` / `GLOB` へフォールバックする」と結論し、そこから「LIKE / GLOB パターンの 50 バイト上限（fact #16）により実質16文字が上限」を導いていた。しかし裏付けとされている先行実装は `instr(title, ?) > 0 OR instr(body, ?) > 0` を使っており、LIKE も GLOB も使っていない。`instr()` に 50 バイト上限は掛からない。つまり**実測されていない機構を結論に採り、その機構にしか効かない制約から数字を導いていた**。`.adr/003` を支える根拠の一部がここに載っているので放置できない。あわせて「2文字の `東京` でも2件ヒット」を trigram の実測として挙げていたが、2文字クエリは trigram ではなく短語フォールバック側を通る。

### Decision

**結論を `instr()` に確定する。50 バイト上限からの導出は削除し、実測の帰属を付け替える。**

- fact #16 の効き先を「短語フォールバックに LIKE / GLOB を**採らない**根拠」へ書き換える。

- `東京` の2件ヒットを短語フォールバックの実測として付け替え、trigram 側の実測は3文字の `東京駅` とページングに限る。

### Consequences

- 良い点: `.adr/003` の足元が実測と一致する。#37 が LIKE / GLOB で実装して 50 バイト制約に悩む経路が消える
- トレードオフ: 入力長の上限根拠が1つ減る。長さ制限は transport 境界の DoS 対策として別に置く（`CLAUDE.md`「Input validation」）

## ADR-042: DO facade はブランド型を受け取らず、RPC 境界を3点目の検証点にしない

### Status

Accepted

### Context

第8.3節 (d) が扱っていたのは RPC の**戻り値**だけで、引数側の検証について記述が無かった。state Worker は独立した script で、その DO クラスは binding を持つ任意の Worker から呼べる。ドメインの値オブジェクトはすべてブランド付き `string` / `number` で、ブランドは型レベルにしか存在しない。RPC は構造化クローンで値を運ぶのでブランドは境界を越えた時点で失われ、生の `string` が `Email` 型として通る。facade が `Email` を受け取る形で書かれると、型システムが「検証済み」と嘘をつき、`CLAUDE.md` の「値オブジェクト構築で検証する」が構造的に無効化される。

### Decision

**第8.3節に (e) を追加し、「DO facade のメソッド署名はブランド型を取らない。プリミティブだけを受け取り、DO の内側で値オブジェクトを再構築する」を断定する。**

- これで `CLAUDE.md`「validated at exactly two points」は「transport 境界（request Worker）」と「値オブジェクト構築（DO 内）」の2点として維持され、RPC 境界は3点目にならない。
- **信頼境界は「script 分離 + binding」に置く**と明文化する。state Worker は公開ルートを持たない。将来ここに公開ルートを足すと前提が崩れる、と書き残す。
- 戻り値側も同じ理由でブランド型を返さない（先行案から採用した「RPC は primitive DTO と値エンベロープだけ」を引数側へ対称に広げたもの）。

### Consequences

## ADR-043: PITR 復旧手順に `sessionEpoch` の強制前進を必須ステップとして加える

### Status

Accepted

### Context

第10.1節は PITR の帰結を4点挙げていたが、**epoch そのものが巻き戻る**ケースが無かった。セッションはステートレス HMAC + TTL 7日で失効の唯一の手段が epoch 照合なので、User Data DO を N 日前（N ≤ 7）へ restore すると、その間にパスワード変更・リセット・SSO 解除で失効させたセッショントークンが**再び有効になる**。「侵害 → リセットで締め出す → 障害で PITR」という順序で現実に起こりうる。

### Decision

**PITR で User Data DO を戻した直後に、`sessionEpoch` を restore 前の最大値より大きい値へ強制的に進める。これを復旧手順の必須ステップにする。** restore 前の値は運用記録から拾えないので、**現在時刻由来の十分大きな単調値へ飛ばす**形にして、前の値を知らなくても必ず上回るようにする。

`sessionEpoch` を Directory 側にも持たせる案は**採らない** — 第3.1節の「権威はすべて `userId` で引ける」を崩し、Account Home を畳んだ判断の前提を壊すからである。**運用手順側で閉じるほうが設計に整合する。**

`credentialVersion` も同じく巻き戻るが、Directory 側との不一致で login が fail closed に倒れるので安全側である。

### Consequences

- 良い点: 復旧作業が「失効済みセッションの再有効化」を伴わなくなる
- トレードオフ: restore のたびに当該ユーザーの再ログインが1回発生する。失効済みセッションの復活より軽い

## ADR-050: RPC エントリを3クラスに分け、epoch ガードを通らないエントリを全数で列挙する

### Status

Accepted

### Context

design.md 第5.1節は「epoch ガードを通らない RPC エントリは signup の1本だけであり、それ以外のすべては epoch ガードを通る」を #37 への断定として置いていた。ところが同じ文書の中に epoch を構造的に運べないエントリが複数ある — login の step 5 は epoch を**取得する**側で照合対象のトークンがまだ存在せず（第5.3節が自らそう書いている）、DO 間 saga の前進（signup phase 2 / 4、credential 変更 phase 2、`rotate-remap` の locator 更新、退会の手順3〜4）は Alarm 起点でセッションを持つ主体が存在しない。断定をそのまま実装すると login と全 saga が epoch 不一致で拒否され、逆に場当たりに穴を空けると「どのエントリが認証を要求しどれが要求しないか」の一覧が設計側に存在しない状態になる。しかもガードの無いエントリは `sessionEpoch` の前進・`account.status` の書き換え・`credential_locators` の削除という最も強い権限を持つ。

### Decision

**RPC エントリを3クラスに分け、(2)(3) を全数の表として第5.1節に置く。**

- (1) 利用者由来 — epoch ガード必須（AI クライアントトークンは接続状態ガード）
- (2) 未認証 bootstrap — `account` 行の有無 / `account.status` / 到達性検査 / `credentialVersion` / トークン照合が守る
- (3) 内部エントリ（saga 前進・Alarm・operator maintenance）— **binding 到達性 + `operationId` / `payloadDigest` の CAS + phase 条件**が守る

**(3) が request Worker からも binding 上は呼べる構成を許容する**と明記した。理由は、(3) のガードが「呼び出し元が DO であること」に依存しておらず、存在しない saga を前進させることも記録されていない `operationId` で phase を飛ばすこともできないからである。binding を絞る形は saga の前進経路そのものを塞ぐので採らない。

あわせて、現行の認可ゲート（`apps/web/app/presentation/currentUser.ts:17-26` / `authState.ts:18-23`）が DO を叩かないため epoch ガードの外側にある事実を第5.1節に書き、#37 の作業3点（JSDoc の位置づけ変更 / `readAuthStateFn` は DO を叩かないまま + テストで固定 / 「DO を叩かない server function は保護データを返さない」規約）を割り当てた。第11.2節の当該行がこの改修を範囲外と読ませる書き方だったので、**本節を変更対象の根拠として扱う**（第4.7節と同じ扱い）と明記した。

### Consequences

- 良い点: #37 が「どのエントリに何のガードを置くか」を表から直接読める。認証境界の定義が設計側に全数で存在する
- トレードオフ: 表が長い。新しい RPC エントリを足すたびに更新が要るが、第4.1.1節（テーブル全数）と同じ運用なので追加の規律ではない

## ADR-051: SSO link では `sessionEpoch` を進めない

### Status

Accepted

### Context

epoch を進める操作の一覧が節ごとに食い違っていた。第5.1節と第6.5節は「パスワード変更・リセット・SSO の解除・退会」の4つを列挙し link を含めていない一方、第6.6節の link 手順4 は epoch を1つ進めると書いていた。#37 はどちらを実装すべきか決められない。

### Decision

**link では進めない。正本は第5.1節とし、第6.5節・第6.6節をそこへ揃える。**

あわせて残余リスクを第5.1節に明記した — セッションを握った攻撃者が自分の SSO 主体を link すると、その後パスワードをリセットされても SSO 経由で入り続けられる。**ただし epoch を進めても link 済みクレデンシャルは消えないので、これは link で epoch を進める案を採っても塞がらない。** 塞ぐのはリセット完了画面の必須導線（クレデンシャル一覧 + 覚えの無いものの解除）であり、画面要件として #35 へ送る。

### Consequences

- 良い点: 一覧が1箇所に定まり、#37 が迷わない。UX 上の害を避けられる
- トレードオフ: 攻撃者が持ち込んだ SSO 連携の回収が画面導線に依存する。#35 が導線を落とすと残る

Accepted

### Context

design.md 第6.3節は「跨ぐ DO は User Data DO と Directory bucket の2つだけ」と断定しながら、同じ節で「全 credential（メール、SSO 主体）の locator を安定ソートして決定順に予約する」と書いていた。両立しない。しかもこれは仮定ではなく現行 spec の要求である — `spec/usecases/identity.md` の `registerOrLoginWithSso` は `findBySsoIdentity` に加えて `findByEmail` によるメール重複検証を必須にしており、`0000_initial.sql` の `users_email_uq` / `users_sso_identity_uq` が示すとおりメールの一意性は SSO ユーザーにも掛かる。したがって SSO signup は2つの canonical に行を置く必要があり、別 HMAC なので原則別 bucket に落ちる。

帰結は3つあった。(i) どちらの bucket が phase 2 → 3 → 4 を前進させるか決まらない（両方が前進すると、片方が落ちたまま他方が phase 4 まで完走できる）。(ii) request Worker が bucket A に予約を書いた直後に落ちると **bucket B にこの signup の痕跡が一切残らない**ので、メールが予約されないまま `active` なアカウントが完成しうる。(iii) `sagaCommitted` 印が起動側の bucket にしか付かず、他方だけ TTL 掃除が先行する。

### Decision

**複数 bucket を認め、「跨ぐ DO は2つだけ」を撤回する。** 代替案「signup を1 credential に限る」は、SSO signup のメール一意性を保証する手段が結局メール bucket への行の設置になり同じ形へ戻るので採らない。そのうえで5つの規則を置いた。

1. コーディネーター bucket は **安定ソート後の先頭 locator の bucket**。ソートキーは `(kind, 全長 HMAC)` の辞書順、`kind` は `'email' < 'sso'`。決定的なので調停が要らない
2. 予約は必ずコーディネーターから取る（phase 1a → 1b）。**コーディネーター予約行が全 credential の `locators[]` を保持する**ので、1本目が書かれた時点で操作の全体像を知る主体が必ず存在する（(ii) が閉じる）
3. `resume-signup` は**コーディネーター bucket の job table にだけ**投入する（(i) が閉じる）
4. `sagaCommitted` 印はコーディネーターが `propagate-saga-committed` で全 bucket へ伝播する（(iii) が閉じる）
5. 非コーディネーター bucket の孤立予約は `sweep-reservations` が TTL 経過後に回収する

第6.1節 (c) の「bucket 間の調整は要らない」は「**一意性の判定には**要らない。複数 credential を1操作で登録する signup の**saga の調整は要る**」へ条件付きに書き直した。

### Consequences

- 良い点: SSO signup の一意性が保証される。前進の駆動主体が1つに定まる
- トレードオフ: phase が 1a / 1b に割れ、bucket 間 RPC（`activate-reservation` / `propagate-saga-committed`）が2本増える。メール単独 signup では bucket が1つなので、これらは自 bucket 内の操作に退化する

## ADR-053: SSO link を saga として扱い、`resume-link` を User Data DO に置く

### Status

Accepted

### Context

link の4手順には前進ジョブが無かった。手順3（予約を `active` へ昇格）と手順4（User Data DO に reverse locator を追加）の間で落ちると、**`status: 'active'` の mapping 行が `credential_locators` に対応行を持たない**状態で恒久的に残る。この孤児は誰にも回収されない — `sweep-reservations` は `reserved` の行しか見ず、`sweep-orphan-mapping` は unlink 時の locator 退避に依存し、しかも **link に対する正しい修復は削除ではなく前進**なので同じジョブでは直せない。結果はその SSO 主体の永久ロックで、利用者は自分でリンクし直すこともできない（予約が `ConflictError` で敗北する）。第6.4節が signup について「黙って到達不能アカウントを残すだけは選ばない」と決めた基準が link にだけ効いていなかった。

### Decision

**link を4 phase の saga として明示し、`kind: 'resume-link'` を第7.4節の全数表と第4.1.1節の `jobs` 行に足す。所有者は User Data DO。** 起点が手順1（`operations` への記録）なので、第7.4節の「起点側が所有する」規則にそのまま乗る。`operations` 行に `targetLocator`（世代 + bucket index + 全長 HMAC + `kind`）を持たせることが、前進を可能にする条件である。手順2〜4 はすべて冪等にし、`operations.phase` から中断点を再開する。

あわせて第6.4節の部分失敗表を signup 専用から **cross-DO 操作の全数**（signup / link / unlink / credential 変更 / 退会 / ローテーション）へ広げ、各行に「残るもの / 片付ける主体 / 前進か巻き戻しか」を書いた。散在していたせいで抜けが検出できない構造だったのが、link の穴の原因である。

### Consequences

- 良い点: 到達不能な SSO 主体が構造的に生まれなくなる。cross-DO 操作の網羅性が1つの表で検査できる
- トレードオフ: ジョブ種別が1つ増える。表の更新を怠ると同じ抜けが再発するので、「新しい cross-DO 操作を足したら行を足す」を本文に明記した

## ADR-054: 一意性の検査を全世代へ広げ、previous 世代は読むだけにする

### Status

Accepted

### Context

第6.1節 (c) は「同じ canonical は必ず同じ bucket に落ちるので bucket 内の一意制約がグローバル一意性と等価になる」と断定していたが、括弧内の但し書き「同一世代・同一鍵なら」が結論に反映されていなかった。読み経路（login）は active → previous の2世代を引くのに対し、書き経路（signup phase 1 / link 手順2）は active 世代しか見ない。ローテーションは 256 bucket のチェックポイント走査なので窓は数時間〜数日開く。その間、**previous 世代にしか行が無い canonical に対する新規 signup / link が成功し**、既存利用者のメールアドレス・SSO 主体で第三者がアカウントを作れる。login は active を先に引くので、以後は後発アカウントが解決先になる。第6.7節（退会）は「両世代に行が存在しうる」を既に見ているのに、登録側だけが見ていなかった。

### Decision

**一意性の検査を keyring の全世代に対して行う。ただし previous 世代は読むだけにする。**

1. previous 世代が keyring に載っている間は previous 世代の bucket を読み、既存行の不在を確認する（`check-previous-generation`）
2. active 世代の bucket に予約を取る

**トゥームストーン予約は書かない。** previous 世代の行に起きる書き込みはローテーションによる削除だけで、しかも第6.8節の移送は「新世代へ書いてから旧世代を消す」順序なので**両世代とも不在になる窓が存在しない**。したがって 1 をすり抜けた競合は必ず 2 の一意制約が捕まえる。読み1回で足り、saga が補償すべき相手も増えない。

「ローテーション中は signup / link を停止する」という運用回避は採らない — 停止期間が数時間〜数日になり、止め忘れが一意性の破れに直結するからである。

### Consequences

- 良い点: 世代跨ぎの重複アカウント・到達性の奪取が構造的に消える。書き込み先は active 世代のままなので補償の設計が変わらない
- トレードオフ: previous 世代がある間だけ signup / link に Directory への RPC が1本増える。単一世代の平常時はゼロ

## ADR-055: 鍵ローテーションの移送を4段順序にし、`credential_locators` に両世代の並存を許す

### Status

Accepted

### Context

第6.8節の初版は「移送先の bucket に active 行を書いてから元の previous 行を消す」→「その後 `credential_locators` を更新する」という順序だった。ところが移送先に書いた時点で active 世代の lookup が新 locator にヒットするので、login step 3 が返す `usedLocator` は新世代になる。`credential_locators` の更新は別 DO への RPC なので、その間 User Data DO 側には旧世代の locator しか無い。step 5 (ii) の到達性検査が世代まで一致を要求すると、**この窓に入った login がすべて拒否される**。ローテーションは全 bucket 走査なので窓は全ユーザーに順次開く。

加えて、移送先に既に行がある場合の規則が無かった。ジョブは at-least-once で、`alarm()` は CPU 予算超過時に途中まで進んで黙って落ちるので、「書き込み後・削除前のクラッシュ + 再実行」は想定内の経路である。その間にパスワード変更が完走していると、**再実行が新しい `passwordVerifier` / `credentialVersion` を previous 行の古い値で上書きし、旧パスワードが復活する**。

### Decision

**移送を4段にする。(1) 新 locator を `credential_locators` に追加（旧行は残す）→ (2) 移送先 bucket に active 行を書く → (3) 元の previous 行を消す → (4) 旧 locator を `credential_locators` から消す。** `credential_locators` は移送中、同じ credential について新旧2世代の行を同時に持つ。**到達性検査は `(kind, 全長 HMAC)` の一致だけを見て世代を条件に含めない**（第5.3節 step 5 (ii)）。一意性の権威は Directory 側にあるので、User Data 側が2行持っても認可は緩まない。

**(2) は「移送先に行が無い場合にだけ書く」CAS にする。** 行がある場合は `userId` を照合し、同一なら何も書かずに (3)(4) だけ行う（冪等成功）。`userId` が異なる場合は移送せず `poison` + 運用エスカレーション（ADR-054 の世代跨ぎ検査が破れた場合の受け口）。**移送は `credentialVersion` を保存する（増やさない）。**

あわせて第6.9節に第2の規則「**fail closed が利用者を締め出す方向へ働く経路は列挙して塞ぐ**」を置き、初版の「1つだけ」を4経路の表に直した。

### Consequences

- 良い点: ローテーション中も login が通る。再実行による認証材料の巻き戻しが構造的に起きない。締め出し経路が一覧で検査できる
- トレードオフ: `credential_locators` の行数が移送中だけ増える。retirement 証明では `status` を問わず previous 世代の行を数える必要があり、その条件を第6.8節 手順4 に明記した

## ADR-056: メールアドレスの local 部に NFKC を掛けず、非 ASCII local 部を拒否する

### Status

Accepted

### Context

第5.2.1節 (a) の正規化手順は「NFKC 正規化 →（分割）→ local 部を lowercase 化」と定めており、**local 部にも NFKC を適用**していた。NFKC は互換等価な文字を畳むので、全角英数（`U+FF41` 等）・合字（`ﬁ` → `fi`）・上付き文字が別の文字列に変わる。一方 SMTP の local 部はオクテット単位で不透明であり、`ａｂｃ@example.com` と `abc@example.com` は別のメールボックスである。しかも原本として保持するのは canonical だけで（第6.2.1節 (a)）、メール送信ジョブはその復号結果を宛先に使う。したがって**利用者が打鍵した実アドレスが復元不能になり、メールが正規化後の別アドレスへ送られる**。signup にメールアドレスの所有確認が無いので、A が全角で作ったアカウントの canonical が B の実アドレスに一致すると、**A のリセットリンクが B に届き B が A を乗っ取れる**。第5.2.1節 (c) が SSO subject について「正規化すると provider 側の同一性判定とずれる」と正しく判断しているのに、メールだけ判断が反転していた。

### Decision

**NFKC は domain 部にだけ掛ける（IDNA / punycode 変換の前処理として必要）。local 部は `trim()` + `toLowerCase()` に留める。** さらに **local 部に非 ASCII（`U+0080` 以上）を含む入力は `BusinessRuleError(InvalidEmail)` で拒否し、SMTPUTF8 に対応しないことを設計の制約として宣言する。**

拒否まで踏み込む理由は、正規化しない方針と両立する唯一の形だからである — 正規化せずに受け入れると `ａ` と `a` が別アカウントになり、利用者が自分のアドレスを取り違える。拒否すれば全角打鍵の事故が登録前に利用者へ返る。検証点は `EMAIL_PATTERN` と同じ `Email.create` の中（構造チェックの拡張）で、transport 境界ではない。

local 部の lowercase 化は残す。RFC 5321 上は区別しうるが実運用のプロバイダは区別せず、区別すると重複アカウントができる。現行実装（`valueObject.ts:47`）と同じ妥協であり、**変えるのは NFKC の適用範囲だけ**である。

あわせて「signup にメールアドレスの所有確認が無い」ことを設計の既知の前提として第5.2.1節に明記し、**所有の唯一の証明がリセット経路であること**を #35 / #38 へ引き継ぐ。

### Consequences

- 良い点: canonical が配送可能な実アドレスと一致し続ける。所有していないメールボックスにアカウントが紐づく経路が消える
- トレードオフ: 非 ASCII local 部のアドレスを持つ利用者を受け入れられない。想定利用者に実需が無いと判断した。所有確認 phase の新設は本 Issue のスコープ外なので、前提として明記するに留めた

## ADR-057: 生のリセットトークンを DB にもジョブ行にも置かず、`tokenId` から導出する

### Status

Accepted

### Context

`password_reset_tokens` はハッシュしか持たず、外部 I/O（メール送信）は必ず「トランザクションでジョブ行を書く → コミット後に Alarm が拾う」形になる。したがって素朴に組むと**生トークンはジョブ行に載るしかない**。ところが `jobs.payload` の制約は「PII を入れない」だけで「秘密を入れない」ではなかった。結果として、`spec/database/index.md:79` が生トークンを保存しない理由として明示している「DB 漏えい時にトークンを使えなくする」が、ジョブ行の側から無効化される。しかも DO の書き込みは PITR の durable log に30日残るので、`done` 後に prune しても消えない。

あわせて、トークンに埋め込む `{generation}.{bucketIndex}` に範囲検査が無かった。リセット URL は未認証で叩ける経路であり、2つの値はそのまま `idFromName("dir:g{gen}:b{index}")` の材料になる。ハッシュ照合は bucket の中で行われるので**照合に失敗する前に DO インスタンスが起きる**。検査が無ければ任意の未認証文字列で新しい DO を無制限に生成でき、第6.2節が案 (c) を棄却した理由 (iv) がそのまま (b) にも当たってしまう。

### Decision

**(i) 生トークンを送信直前に bucket の中で決定的に導出する。** `password_reset_tokens` 行が持つのは `tokenId`（bucket 内で採番する不透明値）と `tokenHash` だけで、`{random}` 部は `HMAC(IDENTITY_RESET_TOKEN_KEY[generation], tokenId)` から導出する。`jobs.payload` に載るのは `tokenId` だけ。導出鍵は state Worker にだけ配る世代付き keyring（第3.2節）で、**DB に一切載らない**ので DB 漏えいだけではトークンを再現できない。第7.4節の `payload` 制約を「PII **および再利用可能な秘密**を入れない」へ広げた。

代替案「ジョブ行に生トークンを載せ、送信成功時に payload を消去する」は採らない。PITR の30日窓に残る事実が消えないためである。

**(ii) `generation` / `bucketIndex` / `{random}` の範囲検査を、locator を導出する前に request Worker の transport 境界で行う。** 検査は「`generation` が keyring に存在する世代のいずれか」「`0 ≤ index < bucketCount(generation)`」「`{random}` が規定の長さと文字種」の3つで、外れたトークンは **DO を一切叩かずに拒否する**。`bucketCount` は keyring のエントリが既に持っているので追加の材料は要らない。第6.2節 (iv) の欄に「この検査が前提」と注記した。

### Consequences

- 良い点: DB / PITR log のどちらにも再利用可能な秘密が残らない。未認証入力から任意の DO 名を引く経路が消え、判断軸 (iv) が真になる
- トレードオフ: 秘密が1つ増える（`IDENTITY_RESET_TOKEN_KEY`）。世代退役時に未使用トークンが無効になるが、TTL が時間オーダーなので影響は「リセットをやり直す」に留まる

---

## ADR-058: `password_reset_tokens` に対象 credential のキーを持たせ、credential 変更 / unlink / 退会で一括無効化する

### Status

Accepted

### Context

第4.1.1節は `password_reset_tokens` を「リセットトークンのハッシュと TTL（bucket 内で一意）」と定義しており、**どの credential のトークンかを引く列が無かった**。現行 spec（`spec/database/index.md:77-101`）は `user_id` 列と `prt_user_idx`（用途欄に「ユーザーの既存トークン**無効化**・整理」と明記）を持っているので、既存設計からの明確な後退である。

その結果、credential 変更 saga のどこにも「対象 credential の未使用トークンを消す」手順が置けない。攻撃シナリオは第6.5.1節が自ら挙げている典型経路そのもので、攻撃者がリセットを1回依頼してトークンを保持 → 正規利用者がリセットを完走 → **攻撃者の古いトークンが TTL 内なら依然有効なので奪い返せる**。第6.5.1節の「別の `operationId` による依頼が `pending` 中に来たら後勝ち」という規則が、この上書きを設計として認めてしまっていた。退会（第6.7節 手順3）も `credential_mappings` 行しか消さず、第6.2.1節 (d) の「bucket 側には何も残さない」が守られていなかった。

### Decision

**`password_reset_tokens` に対象 credential のキー（`kind` + 全長 HMAC）を持たせ、それに対する索引を定義する。** bucket 内では `userId` より credential 単位のほうが自然なのでこちらを採る。**無効化を発行するのは3箇所で、いずれも同じ `transactionSync` の中で行う** — 第6.5.1節 phase 1（credential 変更の起点）/ 第6.6節 unlink 手順3 / 第6.7節 手順3（退会）。

**`verifyAndConsume` の使い捨て性だけでは塞げない**ことを明記した。使い捨てが保証するのは「同じトークンが二度使えない」ことだけで、「別のトークンがもう1本ある」ケースには効かない。

### Consequences

- 良い点: credential 変更後にトークンが生き残る経路が消える。退会時の消去範囲が第6.2.1節 (d) の宣言と一致する
- トレードオフ: 索引が1本増える。bucket 内の行数は利用者数に対して十分小さいので実害は無い

## ADR-059: 濫用抑止に天井・時間減衰・非加算を課し、レート制限時もジョブ行を必ず書く

### Status

Accepted

### Context

第6.2.2節 (a) は「login の照合失敗ごとに `failedAttempts` を進めて指数的に `nextAttemptAllowedAt` を先送りする」「成功時にリセットする」と定めていたが、カウンタの単位は canonical credential であって IP でもデバイスでもない。したがって被害者のメールアドレスを知る攻撃者は誤ったパスワードを投げ続けるだけで先送りを無限に更新でき、ロックアウト中の試行もダミー経路へ倒れて「失敗」になるため、正規利用者が正しいパスワードを入れても「成功時のリセット」に到達できない。**上限も時間減衰も、本人由来と攻撃者由来を分ける鍵も無かった。** 脱出経路であるリセットも同じ節の (b) が「一定間隔内の再依頼はジョブを投入せずに成功を返す」で塞いでいた。

加えて (b) は第7.6節の「mapping が無い場合もジョブ行を書いて即 `done` にする」（＝処理時間差を列挙オラクルにしない規則）と**正面から矛盾**していた。未登録 canonical にはレート制限状態の置き場も無い。

さらに `failedAttempts` の更新経路そのものが login の手順に無かった — 照合は request Worker で行われる（第4.8節）ので、bucket は結果を知らない。

### Decision

**(a) に3点を制約として固定する。** (1) `nextAttemptAllowedAt` の先送り幅に**天井**を置く、(2) 最終失敗からの経過で `failedAttempts` を**時間減衰**させる、(3) **ロックアウト中の試行は `failedAttempts` を進めない**。具体値は #38 へ送るが、**3点の存在自体は #38 へ送らない**。脱出経路を2本残す — リセット完走時に `failedAttempts` を0にし `nextAttemptAllowedAt` を過去へ戻す（第6.5.1節 phase 3）、SSO は別 credential なのでカウンタが独立している。発信元単位のカウンタは (c) の WAF が持ち、それが第一防壁であり (a) に天井を置ける前提でもある。

**(b) は「行を書かない」ではなく「書いた行を送らない側に倒す」で表現する。** 登録済み / 未登録 / スロットル中の3ケースで処理経路が完全に一致する。**未登録 canonical にレート制限の状態は置かない**（置くための行を新設すると未認証入力で無制限に行を作れる）。代わりに `send-mail` の `operationKey` を「対象 canonical の全長 HMAC + 依頼の窓」から決定的に導き、連打を行1本に収束させる。

**このスロットルは被害者の脱出経路を塞がない**ことを明記した — リセットメールの宛先は常に canonical の所有者であって依頼者ではないので、`lastResetRequestedAt` を「実際に送信可能な行として書かれたときだけ」更新すれば**窓ごとに必ず1通が被害者へ届く**。

**`failedAttempts` の更新経路として login に step 7（`report-login-result`）を追加した。** login の RPC 本数は成功時3本・失敗時2本になり、「追加の往復は発生しない」は step 5 の内部についての記述であると訂正した。未登録 canonical のスロットルは (c) の責務であることを明記した。

### Consequences

- 良い点: 標的型の恒久ロックアウトが構造的に成立しなくなる。矛盾していた2節が1つの結論に収束し、列挙オラクルが再び開かない
- トレードオフ: login が1往復増える。カウンタを DO の外（request Worker）で更新する選択肢は、認証状態の権威を分散させるので採らない

## ADR-060: OAuth 2.1 認可コードを自己完結の署名値にし、鍵は `AI_CLIENT_TOKEN_SECRET` を `typ` で分離して流用する

### Status

Accepted

### Context

第5.4.1節は認可コードと PKCE 検証子の置き場所を User Data DO と決め、その根拠を「認可フローは既にログイン済みのユーザーが同意する経路なので `userId` が確定している」に置いていた。しかし `userId` が確定しているのは `/authorize` までである。**token エンドポイント（`code` + `code_verifier` を POST する交換）はクライアント資格情報だけを持つ未認証リクエスト**で、セッションを持たない。認可コードから `userId` を引く手段が無ければどの User Data DO を叩けばよいか決まらず、第6章が Directory を必要としたのとまったく同じ構造の問題が再発する。放置すると #12 が Directory 側に別の解決表を足す方向へ流れる。

### Decision

**結論（User Data DO に置く）は維持し、根拠を差し替える。** 認可コードを `{ typ: "authzCode", userId, connectionId, scope, codeChallenge, codeChallengeMethod, exp }` の HMAC 署名済み自己完結値とし、**token エンドポイントは署名検証で得た `userId` から User Data DO を選ぶ**。第5.4節が AI クライアントトークンについて採った手法と対称になり、Directory を1つも増やさずに済む。

**コード本体の一回性は DO 内の短命な `jti` 記録で担保する** — 署名済み値は再送できるので署名だけでは足りない。PKCE の照合はコードに署名済みの `codeChallenge` と `code_verifier` の定数時間比較で行う。

**署名鍵は `AI_CLIENT_TOKEN_SECRET` を流用し、`typ` audience タグで分離する。** 鍵を別に立てない理由は、認可コードの TTL が分オーダーで鍵差し替えの巻き添えが「進行中の認可フローのやり直し」に留まるからである。セッションと AI トークンを別鍵にした理由（TTL も失効機構も発行契機も違う）は、認可コードと AI トークンの間には当てはまらない — 認可コードは AI クライアントトークンの発行過程そのものである。

第4.1.1節の記述も「永続化するのは交換済みコードの `jti` を記録する一回性テーブルだけ」へ直した。

### Consequences

- 良い点: routing の根拠が第5.4節と同型になり、Directory が増えない。#12 が別の解決表を足す余地が消える
- トレードオフ: 認可コードが長くなる（署名済み値なので）。URL / POST body で運ぶ範囲では問題にならない

## ADR-061: 新設する秘密を入れ子 + ブランド型 + 構築時チェックに乗せ、セッション鍵と AI トークン鍵を単一鍵に確定する

### Status

Accepted

### Context

現行の `packages/core/src/application/di/secrets.ts` は `SESSION_SECRET` について3つの保証を持つ — (1) `MIN_SESSION_SECRET_LENGTH = 32` の下限チェック、(2) ブランド型 `SessionSecret` + `requireSessionSecret` による「チェックを通した値しか型を得られない」構築境界、(3) `RequestSecrets` を**入れ子**に置くことで `createRequestContainer` の rest-spread が秘密を `container.config` へ運ばず `loadAppContext` 経由でクライアントへ出ないようにする不変条件。同ファイルの JSDoc は (3) について「フラットに置くと型エラーが1つも出ないままブラウザへ配られる」と明言している。

### Consequences

- 良い点: routing keyring がブラウザへ漏れる経路が型と構造で塞がる。keyring の不変条件が1箇所で検査される
- トレードオフ: セッション鍵のローテーションが全ユーザー再ログインを伴う。多世代照合を入れれば避けられるが、失効の権威を epoch に一本化した設計（第5.1節）と噛み合わないので採らない

## ADR-062: パスワードリセット完了に限り、直近世代の AI クライアント接続を自動失効させる

### Status

Accepted

### Context

第5.4節は「credential 変更で AI クライアント接続を一括失効させない」と決めており、決定自体は妥当である（接続ごとの独立した認可であり、パスワードを変えたことが取り消し意思を意味しない）。しかし補償手段が「#38 の運用ドキュメントと利用者向け導線に明記する」だけで、**インシデント復旧の実効性が利用者の読解に依存していた**。攻撃者がパスワードを握っている間に接続を1本作れば、被害者がリセットを完走しても攻撃者のアクセスは `exp` まで（または被害者が一覧に気づいて個別 revoke するまで）残る。

### Decision

**構造的な補償を2つ置く。**

- **(i) `ai_client_connections` に `createdAtCredentialVersion` を1列足す。** パスワード**リセット完了に限り**、第6.5.1節 phase 2 の同じ `transactionSync` で「`createdAtCredentialVersion` が前進前の値と等しい接続」を `revoked` にする。同じ DO 内の1列で済み、追加の往復が無い
- **(ii) リセット完了画面に接続一覧と「すべて失効」を必須の導線として出す**（#35 へ）。(i) が切るのは1世代分だけなので、それより前に持ち込まれた分は利用者の判断で切る

**通常のパスワード変更（旧パスワードを知っている経路）には (i) を適用しない。** リセットは「アカウントの制御を失った」という申告であり、変更は日常操作である。区別することで「パスワードを変えたら最近作った連携だけ切れる」という説明のつかない挙動を避けられる。失効対象が「前回の credential 変更以降に作られた接続」に限られるので、長く使っている接続は生き残る。

### Consequences

- 良い点: 侵害復旧が利用者の読解に依存しなくなる。利用者の期待（連携が勝手に切れない）を壊さずに攻撃者の持ち込み分だけを切れる
- トレードオフ: リセット直前に正規利用者が作った接続も切れる。(ii) の導線で再接続できるので、失効漏れより安全側である

## ADR-063: 退会の消去が不可逆になるのは PITR 30日経過後であると明記し、退会済み DO への PITR を承認手続きの対象にする

### Status

Accepted

### Context

第6.2.1節 (d) は「退会が完了した時点で `encryptedCanonical` を含む `credential_mappings` 行を物理削除する。bucket 側には何も残さない」と断定していた。しかし PITR は SQLite-backed DO の DB 全体を過去30日まで戻せる（第2.1節 #20）ので、**削除は30日間は取り消し可能であり、消去の完了時点は退会時点ではない**。設計はこの事実を第6.2節 (iv) の議論では正しく使っているのに、退会の消去範囲では使っていなかった。第10.1節も「どちらか一方の restore だけでアカウントが復活することは無い」までで、**両方を戻せば復活すること**と、それを運用者が単独で実行できることに触れていなかった。

### Decision

**3点を設計上の結論として第6.7節と第10.1節に置く。**

- **退会による削除は即時消去ではなく、PITR 保持期間（30日）が経過して初めて不可逆になる。** 第6.2.1節 (d) の「何も残さない」は**論理的な到達性についての主張**であって記録の消滅についての主張ではない、と限定を明記する
- **退会済み `userId` の User Data DO と、その credential が載っていた Directory bucket への PITR 実行を禁止し、承認手続きの対象とする**
- **Directory bucket の PITR は「アカウント1件の復旧手段」として使えない** — bucket は同じ index に写像される全ユーザーの mapping を持つので、1人の退会取り消しが他の利用者の credential 状態まで巻き戻す

手順と監査は #38（第11.3節の PITR の項）へ送る。利用者へ「削除しました」と説明する際の正確さに直結するので、結論だけは設計側に置く。

### Consequences

- 良い点: 削除の完全性についての説明が事実と一致する。運用者が単独で復活させられる経路が手続きで塞がる
- トレードオフ: 30日以内の「誤って退会した」救済が承認手続きを要する。bucket 側の巻き添えを考えると、そもそも自動化してよい操作ではない

## ADR-064: DO プラットフォームエラーの翻訳層を DO 内と呼び出し側の2箇所に置く

### Status

Accepted

### Context

第4.7節の翻訳表4行を「DO アダプターが写す」と一括りにし、第8.3節 (d) が「第4.7節の翻訳表は DO 側で適用する — request 側に届く時点で既に共有エラー契約になっている」と断定していた。ところが4行のうち2行は **DO のコードが1行も走らない状況で発生する**。`.overloaded`（1オブジェクト 1,000 req/s の soft limit 超過）は超過分が DO へ配送されないので stub を叩いた側が受け取り、`ctx.abort()` / DO のリセットは DO が消滅した結果として RPC の promise が reject する形でしか観測できない（公式も output gate について「送出待ちのメッセージをすべて破棄し、クライアントにはエラーを返す」としている）。DO 側に catch 点が残らない。

### Decision

**第4.7節の表に「捕捉する側」列を足し、翻訳層を2箇所に置く。**

- **DO 内アダプター** — `SQLITE_FULL`、条件付き UPDATE の0行一致（OCC 不一致）
- **DO stub factory が返す facade ラッパー** — `.overloaded`、`ctx.abort()` / DO のリセット

第8.3節 (d) は「値エンベロープに載る `SerializedError` は DO 側で作る。ただし DO へ到達しなかった／DO が消滅した場合のプラットフォームエラーは stub 呼び出しを包む呼び出し側アダプターが翻訳する」へ差し替え、**エンベロープの `{ ok: false, error }` と「stub 呼び出し自体が throw する」が別経路であることを明記する**。ラッパーは request Worker 側だけでなく **state Worker 内の DO 間 RPC にも掛ける**（第3.2節で state Worker にも両 binding を置いたため）。

### Consequences

- 良い点: リトライ禁止の情報が呼び出し元まで届く。`kind: "unknown"` の 500 に落ちる経路が消える
- トレードオフ: 翻訳の実装が2箇所になる。第8.3節 (b) の DO stub factory が返す facade ラッパーの責務として1箇所にまとめられるので、分散は最小に留まる

## ADR-065: `alarm()` 先頭の再武装を `await ctx.storage.sync()` で確定させる

### Status

Accepted

### Context

第7.4節は「`alarm()` の先頭で `setAlarm` しておけば、黙ってリセットされても alarm は武装済みのまま残る」を再設定規則の中核に据えていた。しかしこの前提は公式仕様上そのままでは成立しない。公式は「Alarms are modified using the Storage API, and alarm operations follow the same rules as other storage operations」とし、そのストレージ書き込みは「in-memory write buffer へ書き、ディスクへは非同期にフラッシュされる」ものである。

本設計が自ら定義した支配的失敗モードは「例外ではなく **CPU 予算超過 → エビクションとリセット**」であり、そのモードでは isolate が同期実行の途中で殺されるので**バッファのフラッシュに必要なイベントループの一巡が起きない**。すなわち先頭の `setAlarm` はディスクに届いていない可能性がある。`finally` を棄却した論拠（isolate ごと殺されるので `finally` は走らない）が、そのまま先頭の `setAlarm` にも跳ね返る。防ごうとした帰結 —— dormant な User Data DO の `purge-trash` が恒久停止しゴミ箱の保持期限が無期限へ伸びる —— がそのまま残る。

`setAlarm` を `await` して代用することもできない。戻り値は公式ドキュメント内で食い違っており（alarms ページは `void`、storage API ページは `Promise`）、依拠できない。出力ゲートも救わない — output gate が保証するのは外向きネットワークメッセージを書き込み確定まで止めることであって、送信の無い CPU 専従の `alarm()` には効かない。

### Decision

**`alarm()` の先頭で `setAlarm` した直後に `await ctx.storage.sync()` を置き、永続化を確認してから仕事を始める。** `sync()` は公式に「Synchronizes any pending writes to disk. … 返された promise は pending write の完了時に解決する」と定義されており、`setAlarm` を await できない問題に対する公式の受け皿である。この `await` は `transactionSync` の外なので第8.2節の同期契約と衝突しない。

同じ規則を2箇所へ広げる。**チェックポイントごと**（カーソルを進めてコミットし次の Alarm を張り直した直後）と、**第9.4節の fail-closed 時の張り直し**である。fail-closed の DO は仕事をしないので実害は小さいが、規則を2系統に分岐させない。

第2.1節の事実表に4行（#28 write buffer / #29 alarm はストレージ操作と同じ規則 / #30 `setAlarm` 戻り値の公式内不整合 / #31 `ctx.storage.sync()`）を足して根拠を正本に置く。

### Consequences

- 良い点: 支配的失敗モードで再武装が失われる経路が閉じる。dormant DO の retention が止まらない
- トレードオフ: `alarm()` 起動ごとに1回の `await` が増える。pending write が無ければ既に解決済みの promise が返るので、コストは実質ゼロである

## ADR-066: `collectEvents` の後継として `enqueueJob` / `recordOperation` を UoW 契約に載せる

### Status

Accepted

### Context

第7.3節が `UnitOfWorkContext.collectEvents` を廃止した一方で、第8.2節の決定事項は「`UnitOfWorkContext` にはリポジトリしか載せない」と閉じていた。ところが設計の複数箇所が「ジョブ投入は本体更新と同一 `transactionSync` に入っていなければ意味がない」ことを要求している —— 第7.5節（`purge_after` の最小値から `purge-trash` を投入）、第7.6節（外部 I/O は必ずトランザクションでジョブ行を書く）、第6.2.2節 (b)（レート制限時もジョブ行を必ず書く）、第9.2節（migration ゲートの中でのジョブ投入）。

`jobs` / `operations` / `migration_progress` はドメイン集約ではないので、「リポジトリしか載せない」という肯定形の下では載せる場所が無い。`CLAUDE.md` が `collectEvents` を「the only path to enqueue domain events」と位置づけていた「トランザクション内の唯一の副作用登録点」というスロットが、後継を指名されないまま空いていた。放置すると #37 は (a) `jobRepository` をリポジトリとして載せる、(b) 専用メソッドを載せる、(c) usecase から `ctx.storage.sql` を直接触る（レイヤー違反）の3択を自分で決めることになる。

### Decision

**(b) を採る。`UnitOfWorkContext` に `enqueueJob(kind, operationKey, payload, nextRunAt)` と `recordOperation(operationId, kind, payloadDigest, phase)` を専用メソッドとして載せ、`collectEvents` が占めていたスロットをこれが引き継ぐ。** `migration_progress` のカーソル更新も同じ位置に置く。usecase から `ctx.storage.sql` を直接触る形は採らない —— UoW を通らない書き込み経路を作るためである。

あわせて **「リポジトリしか載せない」を禁止の形へ書き換える** —— 載せてはいけないのは**非同期ポート**（`MailSender` / `PasswordHasher` / DO stub factory / `fetch` を持つ任意のポート）である。肯定形は許可対象を過度に狭め、上の2メソッドを排除してしまう。第11.2節の新旧対比表の「イベント登録」行も「廃止」ではなく `ctx.enqueueJob(...) → jobs 行` を対向に置く。

### Consequences

- 良い点: 「トランザクション内の唯一の副作用登録点」という構造が保たれ、`CLAUDE.md` の Key concepts をそのまま書き換えられる。#37 が3択を自分で決める必要が消える
- トレードオフ: `UnitOfWorkContext` がリポジトリだけの均質な集合ではなくなる。ただし禁止の形（非同期ポートを載せない）が保証の実体なので、`await` を型で排除する仕掛けは無傷である

## ADR-067: チェックポイント予算を外側（ジョブ件数・経過時間）と内側（1チャンクの行数）の2階層にする

### Status

Accepted

### Context

第7.4節の予算「ジョブ25件 または 累積経過時間10秒のいずれか早い方」は**ジョブランナーのループ条件**として定義されていた。しかし設計が本当に守りたい対象 —— 第4.8節が「DO 内。ただし Alarm でチェックポイント分割する」と結論づけた FTS5 全件再インデックスと bulk migration、および第6.7節 手順2 の退会時一括削除 —— は、いずれも `jobs` テーブル上の**1レコード**である。「25件」はジョブ件数の上限なので1件の巨大ジョブには一度も発火せず、「累積10秒」はチャンクの反復間でしか評価できない。**1回のカーソル前進で何行処理するか**が未定義なので、「全行を1チャンクで書き換える」実装が規約に違反せずに書けてしまう。

さらに第9.2節が「`migrate-bulk` は `jobs` テーブルの1レコードとして同じジョブランナーが回すので、そこに閾値が2系統あると打ち切り条件が二重になる」として **migration 専用の閾値を明示的に禁止**していた。禁止の論拠は妥当だが、その結果 `migrate-bulk` に効く上限が「累積10秒」1本だけになり、実効的な保護が存在しない状態になっていた。

### Decision

**予算を2階層として明記し、階層が違うので二重にはならないことを書く。**

- **外側（ジョブランナー）** —— 現行どおり「ジョブ25件 または 累積経過時間10秒のいずれか早い方」。本設計で固定し、見直し契機は #38
- **内側（1ジョブの1回の起動で進めるカーソル）** —— **ジョブ種別ごとに「1チャンクで触ってよい行数の上限」を持ち、1チャンクを終えるたびに外側の累積経過時間を再評価する。** 対象は `reindex` / `migrate-bulk` / `finalize-withdrawal` の3種。値は #37 が spike で根拠値を出し #38 が運用値として確定する（出発点 1,000行）

第9.2節の「migration 専用の別閾値は置かない」は「**外側の**打ち切り条件を migration 専用に分岐させない」の意味に限定する。内側の行数上限はジョブ種別ごとに持つのが前提なので、`migrate-bulk` が自分の値を持つことはこの禁止に当たらない。

### Consequences

- 良い点: 「途中まで進んで黙ってリセットされる」失敗モードに対する保護が、1レコードの巨大ジョブにも効く
- トレードオフ: 予算の概念が2つになる。階層の違い（ジョブ件数 vs 行数）が明確なので、打ち切り条件の二重化にはならない

## ADR-068: `search_entries` の PK を `rowid INTEGER PRIMARY KEY` にする

### Status

Accepted

### Context

第7.1節の実装制約2は「`search_entries` に surrogate の INTEGER rowid 列（`AUTOINCREMENT` ではなく単調増加の採番でよい）を持たせ、`content_rowid` にそれを指定する」としていた。この形は UNIQUE 制約も索引も無い INTEGER 列として実装されうる。FTS5 は列値が必要になるたび content テーブルを `WHERE <content_rowid> = ?` で引く（公式: 「Whenever column values are required by FTS5, it queries the content table」）ので、その場合は列値取得が発生する経路（`fts5vocab`、整合性検査、将来の `snippet()` 導入）で毎回テーブル全走査になる。

加えて根拠の引用が空振りしていた。「第4.4節は全テーブルの PK を単一列 TEXT の `id` と決めているので」とあるが、第4.4節にその記述は無く、実際にあるのは第4.3節の述語 (b) である。しかも第4.2節が「`source_links` は複合 PK のまま」としているので「全テーブル」は事実と食い違う。

### Decision

**`search_entries` の PK を `rowid INTEGER PRIMARY KEY` にし、`id TEXT` を UNIQUE 制約付きの別列にする。** `INTEGER PRIMARY KEY` は真の rowid alias なので **VACUUM でも再採番されず**、「安定した INTEGER rowid」という要求を最も直接に満たす。この形なら `content_rowid` は既定の `rowid` のままでよい。

別列を surrogate にする形を採る場合は、**その列に UNIQUE 制約と索引を必須**とする。引用は第4.3節 (b) へ直し、`source_links` の複合 PK が例外であることを添える。

### Consequences

- 良い点: 列値取得が発生する経路で全走査にならない。`content_rowid` の指定そのものが要らなくなる
- トレードオフ: `id TEXT` の UNIQUE 索引が1本増える。DO 内の1ユーザー分に閉じるので容量への影響は小さい

## ADR-069: 予約 TTL の列名を `reservedUntil` に確定し、第4.1.1節を列の正本にする

### Status

Accepted

### Context

第4.1.1節は「#37 が実テーブルを判断する根拠はこの表である」と自ら正本を宣言し、`credential_mappings` について9列を明示列挙していた。ところが第6章が実際に読み書きする列のうち、識別に使う `kind` / `hmac` / `userId` / `generation`、saga のコーディネーター状態 `operationId` / `candidateUserId` / `sagaCommitted` / `locators[]` / `coordinatorLocator`、credential 変更の `pendingVerifier` が正本表に無かった。**とくに予約 TTL を保持する列はどこにも定義が無く**、第6.3節 phase 1 は「TTL 付き」、第6.4節の sweep 述語は「TTL 超過」と書くだけで列名も型も存在しなかった。#37 は `sweep-reservations` の述語 `WHERE status='reserved' AND ??? < now AND sagaCommitted IS NULL` の `???` を決められない。

同じ問題が `operations`（本文は6列、正本表は3列）にもあり、1パス目で新設・変更した列（`password_reset_tokens` の credential キー、`ai_client_connections.createdAtCredentialVersion`、`operations.targetLocator`）も正本表に反映されていなかった。

**第4.1.1節を「テーブルの全数」と「認証・saga・ジョブ系テーブルの列の全数」の両方の正本にする。** 集約テーブル（`memos` / `topics` / `documents` とその子）の列は `spec/database/index.md` が正本であり、第4.1.1節は所在だけを示す。**本表と第6〜9章の本文が食い違ったら本表を直す**（本文が列を導入した理由を持つので、本文の側が正しい）と衝突解決規則も明記する。

### Consequences

- 良い点: #37 が `sweep-reservations` を含む全ての述語を1つの表から組める。列の追加漏れが表の更新漏れとして検出できる
- トレードオフ: 第6〜9章で列を足すたびに第4.1.1節も直す必要がある。正本が1つあることの代価として受け入れる

## ADR-070: canonical の復号許可経路に「認証済み本人の自己参照」を4つ目として足す

### Status

Accepted

### Context

第6.2.1節 (c) は `encryptedCanonical` の復号が許される経路を3つ（メール送信ジョブ / 鍵ローテーションの再写像 / 暗号化鍵の再暗号化）に限っていた。ところがメールアドレスの原本は Directory bucket にしか無く（同 (a) が User Data DO への複製を明示的に禁じている）、`spec/testcases/identity/getCurrentUser.md` は `getCurrentUser` が `email` を返すことを期待している。設定画面が利用者に自分のアドレスを見せる経路が、許可された復号経路のどれにも当たらない。第11.1節の走査（手段4）でこの矛盾を検出した。

### Decision

**復号が許される経路を4つに広げ、4つ目を「認証済み本人の自己参照」とする。** RPC エントリは `read-own-canonical`（第5.1節のクラス (3)）で、ガードは3つ。

- 呼び出し元は **epoch ガードを通った User Data DO** に限る（request Worker からは直接呼ばせない）
- bucket は `credential_mappings.userId` が**呼び出し元 DO の `userId` と一致する行だけ**を復号する
- 返すのは復号結果1件だけで、**bulk 復号の口を開けない**

平文が Worker 境界を越える点は「メール送信ジョブ」と同じ性質だが、越える量が1件に限られるので、第5.2.3節が「全 PII の bulk 越境」を棄却した論拠には当たらない。第6.2.1節 (c) の「ログ・エラー・メトリクス・トレースに出さない」「永続化しない」は同じく守る。

### Consequences

- 良い点: 設定画面が自分のメールアドレスを表示できる。原本の所在を Directory bucket に一本化した判断が、既存の画面仕様と矛盾しなくなる
- トレードオフ: 復号経路が1つ増える。ガード3点で「1件・本人・認証済み」に閉じているので、攻撃面としては最小である

## ADR-071: 第11.1節の走査に4つ目の手段（新設・変更した振る舞いからの逆引き）を足す

### Status

Accepted

### Context

第11.1節は3つの走査手段（語彙走査 / ポート定義の目視 / マニュアルテストの環境前提の目視）で `spec/` 65ファイルに判定を付け、「判定なしのファイルは無い」「#35 は突き合わせ直さなくてよい」と書いていた。実測すると `spec/` の非レビュー md は **101ファイル**で、**36ファイルが未判定**のまま残っていた（除外対象のレビュー記録も「21ファイル」ではなく実測39ファイルだった）。

根本原因は走査語彙の性質にある。3手段はいずれも「**消す**もの」（Outbox / ベクトル / D1 / consumer / pruner）の語彙と手段に反応する走査であり、本設計が**足した**振る舞い —— 到達性検査、`credentialVersion`、ダミージョブ行、レート制限、export 上限、signup saga の phase 順、AI 接続の自動失効 —— を1件も捕まえない。実際、未判定36件のうち `spec/testcases/identity/requestPasswordReset.md` は第7.6節の結論の**反対**を assert しており、`spec/testcases/identity/loginWithPassword.md` は第5.3節が足した手順を1つも持っていなかった。

### Decision

**走査手段に4つ目「本設計が新設・変更した振る舞いからの逆引き」を足す。** 起点は8つ（login の到達性検査 / `credentialVersion` 照合 / `changeState: 'pending'` のダミー材料経路 / `failedAttempts`・`nextAttemptAllowedAt` のロックアウト / リセット依頼のダミージョブ行 / export の読み出し上限 / signup saga の phase 順とコーディネーター bucket / リセット完了時の AI 接続自動失効と必須導線）である。

**未判定36件の全数に判定を付けた** —— 改訂対象9件（`requestPasswordReset.md` / `loginWithPassword.md` / `getCurrentUser.md` / `listAiClientConnections.md` / `exportAllData.md` / `listTrash.md` / `scenario/account.md` / `manual-tests/account.md` / `inventory/frontend.md`）、影響なし27件。**カバレッジは「`spec/` の非レビュー md 101ファイルすべて。改訂対象72件 / 影響なし29件」に訂正する。** 再現手順（`comm -23` による差集合）も本文に載せ、#35 が同じ検算をできるようにする。

### Consequences

- 良い点: 本設計に正面から矛盾する spec を #35 が取りこぼす経路が閉じる。走査が「消すもの」と「足すもの」の両方を覆う
- トレードオフ: 手段4 は機械化できず目視に依存する。起点8つを明示することで再現性を確保している

## ADR-072: 鍵ローテーション中の2世代並存の規則を第6.1.1節に集約し、各手順から参照させる

### Status

Accepted

### Context

第6.8節のローテーションは 256 bucket をチェックポイント走査する保守作業なので、同じ credential が previous 世代と active 世代の両方に行を持つ窓が数時間〜数日オーダーで開く。ところがこの状態を一貫して扱っていたのは退会（第6.7節）だけで、unlink は1世代・1 bucket しか消さず、credential 変更 saga は locator の世代解決規則を持たず、signup 予約は移送対象になるかどうかが未定義だった。第6.1節 (c) の「previous 世代の行に対して起きる書き込みはローテーションによる削除だけである」という断定が、この状態を設計の視界から外していた（実際には credential 変更の phase 1 / 3、`failedAttempts`、`lastResetRequestedAt`、リセットトークン行の発行が previous 行に対して起きる）。

各節に個別のパッチを当てると同じ食い違いが再発する。

### Decision

**規則を第6.1.1節「ローテーション中の2世代並存の規則（正本）」に集約し、第6.3節・第6.4節・第6.5.1節・第6.6節・第6.7節・第6.8節はここを参照する。** 規則は7つ。

- (R1) 新規登録は必ず active 世代に取る。previous は読むだけ
- (R2) 既存行への更新は「行が実在する世代」へ向ける。active に無ければ previous が正本
- (R3) 削除は全世代・全 bucket を対象にし、「無ければ成功」の冪等操作にする
- (R4) ログイン手段の数え方は行数ではなく、`usableForLogin = true` かつ active な行の distinct な `(kind, hmac)` の個数
- (R5) locator 解決の出所は「未認証経路は canonical から」「認証済み経路は `credential_locators` から」「リセット完了はトークンから」の3つに限る。認証済み経路が canonical から導出することは無い
- (R6) 進行中の saga を跨いで行を移送しない（`changeState = 'pending'` と `status = 'reserved'` はスキップ）
- (R7) 移送は移送元・移送先の両側を CAS で守る

第6.1節 (c) の誤った根拠は「previous 世代の bucket に新しい canonical が登録されることは無い」へ差し替える（トゥームストーン不要という結論自体は成立する）。

### Consequences

- 良い点: 旧パスワードの復活・恒久ロックアウト・自己ロックアウト・解除済みクレデンシャルでのログインの4つが、1箇所の規則で同時に閉じる。新しい手順を足すときの検査項目が7つに固定される
- トレードオフ: ローテーションの所要時間が「予約 TTL と pending 解消時間より長い」ことが制約になる（(R6) のスキップ行を再走査で拾うため）

## ADR-073: `credential_locators` に `usableForLogin` を足し、「最後のログイン手段」検査を distinct な `(kind, hmac)` で行う

### Status

Accepted

### Context

unlink の「最後のログイン手段を外そうとしていないか」検査は `credential_locators` の**行数**が1かどうかで判定していた。この仮定は本設計自身の2つの決定で既に崩れていた。(a) SSO signup はメール canonical にも mapping を置く（第6.3節）ので SSO 専用ユーザーの行数は常に2だが、メール行は一意性の予約であってログイン手段ではない（`passwordVerifier` を持たない）。(b) ローテーション中は同じ credential の行が2世代並存する。どちらでも検査が発火せず、利用者が自分を恒久的に締め出せる。

`credential_locators` の既存列（`kind` / `hmac` / `generation` / `bucketIndex` / `credentialVersion` / `status`）だけでは「その行がログイン可能な手段か」を User Data DO 側で判定できないので、列か RPC の追加が必要だった。

### Decision

**`credential_locators` に `usableForLogin` 列を足す。** 値は「`kind = 'sso'` であるか、または `kind = 'email'` かつ Directory 側の mapping 行が `passwordVerifier` を持つ」で、**Directory 側が判定して `record-credential-locator` / `advance-credential-change` の引数で運ぶ**。SSO signup がメール一意性のためだけに置く行は偽になる。

**検査述語を「`usableForLogin = true` かつ active な行の distinct な `(kind, hmac)` を数え、対象 credential を除いた残りが0件なら拒否」に変える。** distinct を取ることでローテーション中の2世代行が畳まれる。第4.1.1節（列の全数の正本）と第6.3節 phase 4・第6.5.1節 phase 2・第6.6節 link 手順4 / unlink 手順1 を同時に更新する。

### Consequences

- 良い点: (a) と (b) の両方が1つの述語で閉じる。判定の権威が User Data DO 側に閉じたままになる（Directory への追加 RPC が要らない）
- トレードオフ: 列が1つ増え、Directory 側の状態（`passwordVerifier` の有無）が User Data 側へ複製される。複製が古くなる経路は credential 変更 saga の phase 2 だけなので、そこで同時に更新する

## ADR-074: DO 間 RPC のうち CAS も phase 条件も持たないエントリを `callerToken` で束縛する

### Status

Accepted

### Context

第5.1節は「クラス (3) のガードは呼び出し元が DO であることに一切依存していない。守っているのは `operationId` / `payloadDigest` の CAS と phase 条件である」と一括で正当化していた。ところが `read-own-canonical` / `delete-mapping` / `lookup-credential-by-locator` は CAS も phase 条件も持たず、守りは「呼び出し元 DO の `userId` と一致する行に限る」だけだった。**DO 間 RPC には呼び出し元の認証済み識別子が存在しない**ので、その `userId` は引数として渡るほか無く、bucket 側に検証する材料が無い。結果、`read-own-canonical` は「`userId` を1つ渡せばメール平文が1件返る」復号オラクル、`delete-mapping` は「`userId` を渡すだけで mapping が消える」ロックアウト原始関数になる。`userId` は秘密ではない。

第6.2.1節 (c) 4 のガード (i)「呼び出し元は epoch ガードを通った User Data DO に限る（request Worker からは直接呼ばせない）」は実装不能であり、同時に第5.1節の「(3) は request Worker からも binding 上は呼べる。それでよい」と正面から矛盾していた。

### Decision

**`callerToken` を導入する。** 128ビットの不透明値で、signup phase 0 に request Worker の `IdGenerator` が候補 `userId` と同時に採番する。保存先は User Data DO 側が `account.callerToken`、Directory 側が `credential_mappings.callerToken`。**CAS も phase 条件も持たない RPC エントリは引数に `callerToken` を必須で載せ、bucket は行の値と定数時間比較する。** 第5.2節 (c) の非露出対象に含める。移送は行ごと引き継ぎ、退会で消える。

**クラス (3) の正当化を3群に分ける。** (3-a) CAS と phase 条件が守る群、(3-b) `callerToken` が守る群（`read-own-canonical` / `delete-mapping` / `lookup-credential-by-locator`）、(3-c) 到達制御と監査だけが守る群（`check-previous-generation` / `purge-user-mappings`）。**`purge-user-mappings` は逆引き情報ごと失われた場合の最後の砦なので原理的にトークンを要求できないことを、残余リスクとして正直に書く。**

### Consequences

- 良い点: 本システムで最も価値の高い PII（メール平文）の復号経路が2層防御になる。実装不能なガード要求と、それと矛盾する断定の両方が消える
- トレードオフ: 列が2つ増える（`account` / `credential_mappings`）。`purge-user-mappings` だけは1層のままで、緩和は #38 の監査要件に依存する

## ADR-075: `rotate-remap` を Alarm ジョブから「maintenance 経路が1チャンクずつ駆動する同期 RPC」へ変える

### Status

Accepted

### Context

初版は `rotate-remap` を Directory bucket 所有の Alarm ジョブと定義していた。ところが3つの規則が同時に成立しない。(i) 再 HMAC は bucket の中で行う（平文を外へ出さない）、(ii) routing key は RPC 引数として一時注入し呼び出しのスコープを出たら破棄する、(iii) 大きな仕事は Alarm を跨ぐチェックポイントで分割する。(iii) を採ると次の Alarm 起動時に鍵が無く、(ii) を守って1回の RPC で全件処理すると CPU 予算超過（途中まで進んで黙って落ちる）に当たる。#37 が実装で辻褄を合わせる最も安易な解決は鍵を bucket の SQLite かインスタンスフィールドに置くことで、それは第3.2節が固定した「秘密の配布は非重複である」を壊す。しかもチェックポイントごとの `sync()` を守れば鍵は write buffer からディスクへ流れる。

### Decision

**`rotate-remap` の実行主体を決め直す。operator の maintenance 経路が「1チャンク = 1 RPC」で駆動する同期 RPC とし、Alarm ジョブにしない。** 鍵は毎チャンクの引数として注入され、チャンク境界で必ず破棄される。進捗は `rotation_checkpoints` と mapping 行の世代が既に持つので Alarm による自走は不要である。第7.4節の `kind` 表と第4.1.1節の Directory `jobs` 行から `rotate-remap` を外し、第5.1節のクラス (3) には「ローテーションの起動と鍵の一時注入」として残す。

**`rotate-encryption` は Alarm ジョブのままである。** `IDENTITY_MAIL_ENCRYPTION_KEY` は state Worker の常設バインディングなので Alarm 起動時にも鍵が存在する。この非対称を明記する。

### Consequences

- 良い点: 秘密の配布境界が壊れる実装へ倒れる経路が消える。チャンクの大きさを operator 側で制御できるので、CPU 予算の当て方も明示的になる
- トレードオフ: ローテーションが operator の駆動を必要とし、放っておいても進む性質を失う。走査は `previousCount = 0` が全 bucket で揃うまで繰り返す必要がある

## ADR-076: credential 変更 saga の locator 解決を起点ごとに定め、`lookup-credential-by-locator` を新設する

### Status

Accepted

### Context

第6.5.1節 phase 0 は「対象 credential の locator を導出する」とだけ書いていた。パスワード変更は認証済み操作なのでリクエストにメールアドレスが含まれず、canonical の原本は bucket の中で暗号化されている。`passwordVerifier` を返す唯一のエントリ `lookup-credential` の入力は canonical なので、**旧パスワード照合の材料を取得する経路が設計に存在しなかった**。`read-own-canonical` で復号平文を取ってくる形は「復号結果を持ち回らない」制約を破る。どの経路を採っても既存の制約のどれかを破る状態だった。

加えてローテーション中の世代解決も未定義で、まだ移送されていない利用者の変更が行の無い active 世代 bucket を叩く。

### Decision

**phase 0 の locator 解決を起点ごとに定める。** 起点 A（パスワード変更）は「セッション → User Data DO の `credential_locators`（+ `account.callerToken`）→ `lookup-credential-by-locator` → `PasswordHasher.verify`」の3段。起点 B（リセット完了）はトークン本体が運ぶ `{generation}.{bucketIndex}` と `consume-reset-token` の戻り値から組む。**どちらも canonical からは導出しない**（第6.1.1節 (R5)）。

**`lookup-credential-by-locator` を第5.1節のクラス (2) に新設する。** 引数は canonical ではなく `(kind, hmac, generation, bucketIndex)` + `callerToken`。返すのは `passwordVerifier` / `credentialVersion` / `changeState` だけで、`encryptedCanonical` も復号結果も返さない。

**`consume-reset-token` のガードに「同 bucket に対象 credential の mapping 行が存在すること」を足す。** 第6.1節 (d) の「移送後の旧世代トークンは無効になる」という断定は、このガードがあって初めて成立する。

### Consequences

- 良い点: 既存の制約（平文を持ち回らない / 認証済みリクエストは canonical を持たない）をどれも破らずに旧検証材料を取得できる。世代解決が (R2) に自動的に従う
- トレードオフ: RPC エントリが1本増え、パスワード変更のホットパスに往復が1本増える（頻度の低い操作なので許容する）

## ADR-077: signup の終端規則に「mapping の回収」を前置し、`cancel-reservation` / `abandon-account` を RPC エントリに足す

### Status

Accepted

### Context

第6.4節 3 の終端規則は「`resume-signup` は User Data DO の `account.status` を `deleting` へ倒し、退会と同じ経路で回収する」だった。ところが `finalize-withdrawal` は `credential_locators` を唯一の逆引き情報として mapping を消す設計で、`credential_locators` を書くのは phase 4 である。終端規則が発火するのは phase 3 の途中なので、この時点で `credential_locators` は空であり、回収対象が1件も見つからない。結果としてコーディネーター bucket に `active` な孤児 mapping が残り、そのメールアドレス / SSO 主体が恒久的に再登録不能になる。この孤児は `sweep-reservations` / `sweep-orphan-mapping` / `finalize-withdrawal` のいずれの対象でもない。SSO signup は常に2 bucket を跨ぐので、これは SSO 登録の標準経路である。

あわせて、第5.1節の「クラス (2)(3) の全数」を宣言する表から、signup saga の再開・補償に必要な3経路（コーディネーター bucket からの `reserve-credential` / `check-previous-generation`、敗者補償の削除、終端の `deleting` 化）が欠けていた。

### Decision

**終端規則を2段にする。** (3-i) コーディネーター予約行の `locators[]` を辿り、各 bucket へ `cancel-reservation` を発行して**自分の `operationId` を持つ行を `status` を問わず削除する**。(3-ii) その後で `abandon-account` により `account.status` を `deleting` へ倒す。

**第5.1節の表に不足していたエントリと呼び出し元を補う。** `reserve-credential` / `check-previous-generation` の呼び出し元欄にコーディネーター bucket を足し、`cancel-reservation` / `abandon-account` / `purge-user-mappings` / `exchange-authz-code` / `lookup-credential-by-locator` の5行を新設する。「この1本だけが (2) と (3) の両方から呼ばれる」という断定は撤回する。**表に「本文が RPC エントリを導入したら本表にも行を足す」という更新規則を添える。**

代替案（phase 4 を分割し phase 3 の各昇格の直後に `record-credential-locator` を発行する）は採らない。昇格前に locator を書くと「mapping が `reserved` なのに `credential_locators` に active 行がある」窓が開き、到達性検査の意味が緩むためである。

### Consequences

- 良い点: 「黙って到達不能アカウントを残さない」という第6.4節の宣言が、正本の表の側でも担保される。第5.1節の表が再び全数になる
- トレードオフ: `cancel-reservation` が `active` 行も消せるので、ガードは `operationId` 一致に依存する。`operationId` はサーバー採番でクライアントから受け取らない（第6.3節）ため、外部から任意の行を消す経路にはならない

## ADR-078: signup の重複エラーが公開の列挙オラクルであることを受容判断として記録する

### Status

Accepted

### Context

signup の phase 1a は `ConflictError("EMAIL_ALREADY_REGISTERED")` を返す。誰でも未認証で叩ける経路から「そのメールアドレスは登録済みである」を直接返すので、公開の列挙オラクルである。一方 login はダミー検証材料で応答を均一化し、リセット依頼はダミージョブ行で処理経路を完全一致させ、未認証経路のログには `userId` すら出さない。この非対称が一度も説明されていなかった。実装済みの `registerWithPassword.ts` も同じ挙動なので新規の後退ではないが、判断の記録が無いのは設計の欠落である。

### Decision

**受容する、と明記する。** 重複を秘匿する唯一の実装可能な形は「重複時もメールを送って結果を UI で区別しない」だが、本設計は signup にメールアドレスの所有確認を持たない（第5.2.1節 (a)）ためその経路そのものが存在しない。所有確認を持たないまま秘匿すると、利用者が「登録できたのかできなかったのか分からない」状態に置かれる。

緩和は既存の2つで足りる（未認証エンドポイントへの WAF / Rate Limiting Rules、canonical 単位の判定なので正確なアドレスの推測が必要）。**#35 への文言方針は「秘匿しない。画面に『このメールアドレスは既に登録されています』を出してよい」である。**

### Consequences

- 良い点: login / リセットに払っている均一化コストとの非対称が説明され、#35 が画面文言を判断できる
- トレードオフ: 登録済みメールアドレスの列挙が可能なままである。所有確認 phase の新設は #34 のスコープ外として引き継ぐ

## ADR-079: Alarm チェックポイント予算から経過時間を外し、3階層の件数上限だけで有界にする

### Status

Accepted

### Context

第7.4節の外側予算は「ジョブ25件 または 累積経過時間10秒のいずれか早い方」だった（先行案からの引き継ぎ）。ところが Workers の `Date.now()` は Spectre 緩和として意図的に凍結されており、公式が「最後の I/O の時刻を返し、コード実行中は進まない」と明記している（第2.1節 F-32）。`transactionSync` / `sql.exec()` は同期なので、ローカル SQL だけで完結するジョブを連続で回しても時計は動かない。つまり**時間側の打ち切りは、まさに保護が必要な CPU バウンドの列で発火しない**。「CPU ≤ 経過時間だから安全側」という論拠も、`Date.now()` の差分が実経過時間ではないので成立しない。支配的な失敗モードは CPU 予算超過によるエビクション（例外は上がらない）なので、保護が1本減ることの帰結は「黙って途中で止まる」である。

### Decision

**経過時間をチェックポイント予算の条件に一切使わない。3階層の件数上限で有界にする。**

1. **外側**（ジョブランナー）= 1回の Alarm 起動で処理するジョブ件数（25件）。
2. **中間**（1ジョブの1回の起動で回すチャンク数）= 同一ジョブについて連続で回してよい反復回数（出発点 20）。**新設。** 失われた時間側の保護をここが引き受ける。
3. **内側**（1チャンクで進めるカーソル）= 1チャンクで触る行数（出発点 1,000）。

**内側だけでは保護にならない** — 1チャンクの大きさを縛っても反復回数を縛らないので、「1,000 行ずつ 100 万回」が書けてしまう。**行数上限と反復回数上限は必ず対で置く。** (iii) の対象は内部カーソルを持つ4種（`reindex` / `migrate-bulk` / `finalize-withdrawal` / `purge-trash`）で、1回の起動で触る行数の上界は「25 × 中間 × 内側」として静的に決まる。第2.1節に F-32（`Date.now()` の凍結）と F-32b（`sql.exec()` が clock を進めるかは未確認）を足した。

### Consequences

- 良い点: 時計を読む実装が1箇所も無くなるので、凍結の影響を受けず、上界が静的に計算できる。テストも「N 件で打ち切る」を直接書ける
- トレードオフ: 1件あたりの実 CPU コストがジョブ種別で大きく違う場合、件数だけでは粒度が粗い。#38 の運用監視で初期値を見直す前提を残した

## ADR-080: `alarm()` 先頭の順序を確定し、due job がゼロなら `deleteAlarm()` する

### Status

Accepted

### Context

2つの穴があった。**(1)** 第7.4節は「`alarm()` の先頭で `setAlarm` して `sync()` してから仕事を始める」と定めたが、正常完了時の再設定規則は「DB の最早 `nextRunAt` へ張り直す」だけで、**最早 `nextRunAt` が存在しない場合が未定義**だった。素直に「無ければ呼ばない」と実装すると先頭で張った alarm が残り、再開間隔ごとに起きて先頭でまた張る**恒久ループ**になる。`setAlarm()` 1回は1行の書き込みとして課金され（第2.1節 F-24）、一度でもジョブを走らせた全ユーザー分が恒久的に発生する。文書中に `deleteAlarm` が1度も現れていなかった。**(2)** 第7.4節が「先頭で再武装」、第9.2節が「migration ゲートを `alarm()` の先頭に置く」と、両方が「先頭」を主張していて前後関係が決まっていなかった。

### Decision

- **`alarm()` の先頭の順序は (1) 再武装 + `await ctx.storage.sync()` → (2) migration ゲート → (3) 仕事 である。** ゲートを先にすると、ゲート内の DDL が CPU 予算を使い切った場合に第7.4節が塞いだはずの失敗モード（dormant DO の `purge-trash` が恒久停止）が再発する。再武装は `setAlarm` 1回と `sync()` 1回で DDL より桁違いに軽い。(1) の `await` はゲートに入る前に完了するので、第9.2節の「ゲート関数は `await` を1つも挟まない同期関数」という排他条件は破れない。
- **正常完了時、DB に `nextRunAt` を持つ行が1件も無ければ `deleteAlarm()` し、`sync()` で永続化を確認する。これは規則の一部であって最適化ではない。** `deleteAlarm()` の戻り値にも依拠しない（第2.1節 F-30 の公式内不整合は `getAlarm` / `deleteAlarm` にも及ぶ）。
- **例外は第9.4節の fail-closed 経路だけである。** そちらは意図的に alarm を残す（消すと正しいコードが戻っても dormant DO では誰も回復を検知しない）。両節に相互参照を置いた。

### Consequences

- 良い点: idle な DO が起き続けるコストが消え、第7.5節の「dormant な DO は Alarm でだけ起きる」が実際に成立する
- トレードオフ: 「先頭で張る → 末尾で消す」という非対称な組み合わせになるので、#37 は削除側を落とすと恒久ループになる。規則としてその帰結を明記した

## ADR-081: RPC 経路の `setAlarm` の実行主体を DO facade ラッパーに置き、`getAlarm()` を呼ばない

### Status

Accepted

### Context

`enqueueJob` は `UnitOfWorkContext` の同期メソッドでトランザクション内に閉じる一方、`setAlarm` はトランザクションの外である。**その `setAlarm` を誰がいつ呼ぶかが設計に書かれていなかった。** また「設定に失敗したら次の DO 入力で DB から最早時刻を再計算する」という回復策は、第7.4節自身が `finally` を棄却した論拠（dormant DO には次の入力が来ない）とまったく同じ理由で dormant な User Data DO に効かない。「利用者がメモをゴミ箱に入れて二度と戻ってこない」は典型ケースである。加えて既存 alarm との比較に `getAlarm()` を使うと `await` が入り、commit と `setAlarm` のフラッシュ単位が2つに割れうる。

### Decision

- **実行主体は DO facade のラッパーである**（UoW プロバイダではない）。`run()` の戻り後、**`await` を1つも挟まずに `setAlarm` を発行し、続けて `await ctx.storage.sync()` を1回入れる**。
- **`getAlarm()` を呼ばない。** DO インスタンスのフィールドに現在の alarm 時刻を保持して比較する（DO は1インスタンス = 1ユーザー / 1 bucket なので保持できる）。未初期化なら無条件に `setAlarm` する。
- **`sync()` が失敗したら RPC 自体を失敗させる。** 利用者にリトライさせるほうが、保持期限が黙って無期限へ伸びるより良い。

### Consequences

- 良い点: dormant DO の retention が黙って止まる経路が閉じる。フラッシュ単位が1つに保たれる
- トレードオフ: `setAlarm` の永続化失敗が利用者に見えるエラーになる。頻度は低く、代償（無言の停止）より軽い

## ADR-082: `operationKey` の収束を「`nextRunAt` を早める方向にのみ」に一本化し、`jobs` の prune をジョブランナーに置く

### Status

Accepted

### Context

**(1)** 「同じキーの再投入は既存行に収束する」は `kind` によって逆の更新を要求していた。`send-mail` では収束＝重複を捨てて既存行を保つこと、`purge-trash` では `trashRetentionDays` の短縮に伴って**既存行の `nextRunAt` を早める**ことである。しかも `payload` が変われば `payloadDigest` が変わり `ConflictError` になる。#37 はどちらかの意味論しか実装できず、`purge-trash` 側が落ちると retention 短縮が既存項目に効かず `spec/testcases/trash/listTrash.md` の遡及適用の期待が破れる。**(2)** 第7.4節は `done` / `poison` の prune を要求しているのに、`kind` の全数表にも第4.1.1節にも prune ジョブが無かった。

### Decision

- **再投入は `nextRunAt` を早める方向にのみ更新し、遅らせない。** `payloadDigest` の照合は `nextRunAt` を除いた payload に対して行う。`status = 'running'` の行の `nextRunAt` は書き換えない。これで `send-mail` の連打（同じ窓＝同じ `nextRunAt`）と `purge-trash` の前倒しが同じ1規則で説明できる。
- **`jobs` の prune に専用 `kind` を置かない。** ジョブランナーが1回の Alarm 起動の末尾で、保持期間を過ぎた `done` / `poison` を最大 N 行だけ削除する。`kind` に足すとその行自体が prune 対象になる入れ子ができるためである。**「表に現れない理由」を第7.4節が正本として持つ。** `send-mail` の空振り行には最も短い保持期間を割り当てる。

### Consequences

- 良い点: `kind` の全数表と第4.1.1節が変わらないまま、両方の欠落が閉じる
- トレードオフ: prune が「ジョブランナーの暗黙の責務」になるので、実装を読んだだけでは所在が分かりにくい。第7.4節に段落として明示した

## ADR-083: OCC の適用範囲を3テーブルに確定し、0行検出を `UPDATE ... RETURNING 1` で行う

### Status

Accepted

### Context

**(1)** 第4.1.1節は「テーブルの全数と列の全数の両方の正本」を宣言しているのに、**OCC の `version` 列が1つも無かった**。一方で第8.4節は「OCC は残す」と断定し、第8.2.1節は `Versioned` / `ExpectedVersion` を「そのまま残す」と決めている。#37 が第4.1.1節を正本として DDL を書くと identity 系から OCC が黙って消える。**(2)** 変更行数を `sql.exec("SELECT changes()")` で読む決定は workerd 上で未検証で、しかも #37 の spike 一覧にも無かった。実測があるのは棄却した側（`rowsWritten`）である。

### Decision

- **`version` を持つのは集約ルートの3つだけ** — `account` / `user_settings` / `ai_client_connections`。`User` 集約の分裂（第4.3節 行11 / 行7c）に伴い、設定側の OCC は `user_settings` と `account` が引き受ける。`recordUsage` による `lastUsedAt` の単独更新は `version` を進めない後勝ち更新にする（`spec/database/index.md` の現行規約の維持）。
- **`credential_mappings` は OCC を持たない、と断定する。** Directory 側の書き込みはすべて `operationId` / `changeState` / `status` / `sagaCommitted` を条件に含む CAS で直列化されており、同じ行に対する「読んで判断して書く」がリクエストを跨がない。汎用 OCC を重ねると CAS と `version` のどちらが権威かが二重になる。**分裂した `UserRepository` のうち Directory 側だけは `ExpectedVersion` を取らない。**
- **`credential_locators` / `password_reset_tokens` / `jobs` / `operations` / `migration_progress` / `rotation_checkpoints` / `_meta` も持たない**（集約ではなくアダプター内部のストア）。
- **0行検出の第一候補を `UPDATE ... WHERE id = ? AND version = ? RETURNING 1` にする。** 意味論がその文の中で閉じるからである。`SELECT changes()` は「`sql.exec()` をまたいでマッチ行数を返すか」が未確認なので**第二候補**とし、第11.4節の spike に足した。`rowsWritten` は課金単位なので不採用のまま。

### Consequences

- 良い点: 第4.1.1節と第8.4節の食い違いが閉じ、OCC の要否が全テーブルについて断定される。0行検出が未検証の関数に依存しなくなる
- トレードオフ: `RETURNING` は SQLite 3.35 以降の機能なので workerd の SQLite 版に依存する。先行ブランチが `INSERT ... RETURNING rowid` で使っている実績があるため受容する

## ADR-085: PITR 復旧後の必須ステップを「`sessionEpoch` の強制前進 + AI クライアント接続の全件失効」の2つに広げる

### Status

Accepted

### Context

第10.1節は「Directory mapping が到達性のゲート / User Data の `account.status` が状態の権威 / 片方だけの restore では復活しない」の3点で PITR に耐えると論じ、`sessionEpoch` の巻き戻しだけを独立した穴として特定して必須ステップを置いていた。ところがこの論証はすべて **login が必ず Directory を経由すること**に依存している。AI クライアントトークンは自己完結で、検証は request Worker が DB を触らずに行い、失効の権威は `ai_client_connections.status` と `account.status` の2つとも User Data DO の中にしか無い。したがって User Data DO を単独で restore すると `status` が `revoked` → `active` に戻り、`exp` までのあいだ失効させたはずのトークンが再び通る。

### Decision

**restore 直後の必須ステップを2つにする。** (i) `sessionEpoch` を現在時刻由来の十分大きな単調値へ強制的に進める（既存）。(ii) **その User Data DO の `ai_client_connections` を全件 `revoked` にし、利用者に再接続させる**（新設）。restore 前にどれが `revoked` だったかは復旧時点では読めない（restore で上書き済み）ので、**「復旧できないなら全部切る」を既定手順にする**。利用者向けの導線は第5.4節 (ii) がリセット完了画面に要求している「AI クライアント接続一覧 + すべて失効」を流用する。手順の実体は #38（第11.3節）。

### Consequences

- 良い点: 「片方の restore だけでは復活しない」の適用範囲（login 経路のみ）が明示され、AI トークン経路の穴が塞がる
- トレードオフ: 復旧のたびに全 AI 連携の再接続が要る。失効済み接続の復活より軽い

## ADR-088: 世代非依存の `credentialId` を導入し、credential の同一性を `hmac` から切り離す

### Status

Accepted

### Context

locator の全長 HMAC は `HMAC-SHA-256(DIRECTORY_ROUTING_SECRET[generation], canonical)` の出力なので、**同じ canonical でも世代が違えば値が違う**。ところが設計は `(kind, hmac)` を「世代をまたいで安定な credential の同一性」として使っており、鍵ローテーション中の2世代並存下で次が同時に破れていた — (i) unlink の「最後のログイン手段」検査が distinct `(kind, hmac)` を2件と数えて発火せず**自己ロックアウト**、(ii) unlink / 退会の削除対象を「同じ credential の別世代の行」として突き合わせるキーが存在しない、(iii) `record-credential-locator` の冪等キーが第6.6節（`(kind, hmac)`）と第6.8節（世代違いの2行が必須）で自己矛盾し、前者で実装すると**移送済み全利用者が到達性検査で締め出される**、(iv) `encryptedCanonical` の AAD が `hmac` を束縛しているため移送で**全行が復号不能**になる。同じ箇所が R2・R3・R4 の3ラウンド連続で別角度から再指摘されたため、個別パッチではなく構造で直す。

### Decision

**世代非依存の `credentialId` を1本立て、credential の突き合わせキーをすべてこれにする。** 値は `IdGenerator` が採番する128ビットの不透明値で、canonical からも鍵からも導出しない（`callerToken` とまったく同じ扱い）。採番点は request Worker — signup は phase 0 で credential ごとに、SSO link は `operationId` と同時に採番する。**鍵ローテーションの移送は行ごと引き継ぎ再採番しない**。置き場所は `credential_mappings` / `credential_locators` / `password_reset_tokens` の3テーブルで、`credential_locators` の一意性は `(credentialId, generation)` になる。`hmac` は落とさず「その世代における locator の材料」として役割を分ける。UI へは `credentialId` / `kind` / `label`（provider 名まで）の3つ組を出し、unlink は `credentialId` を指定して発行する。

### Consequences

- 良い点: 到達性検査・ログイン手段の数え上げ・削除対象の選択・`credentialVersion` の更新範囲・冪等キー・AAD の6つが**1つのキーに揃う**。「世代を照合条件に含めるか」という問い自体が消える。canonical 化規則の変更（版番号を持つ移行）にも耐える
- トレードオフ: 3テーブルに列が1つずつ増え、`credential_locators` に表示用の `label` も足した。`credentialId` は `userId` と同じく「不透明だが存在が登録済みを漏らす」値なので、未認証経路のログ非出力対象に加える必要がある

## ADR-089: `record-credential-locator` の冪等キーを `(credentialId, generation)` に統一し、`credentialVersion` を単調非減少の upsert にする

### Status

Accepted

### Context

同じ1本の RPC を signup phase 4 / SSO link 手順4 / 鍵ローテーション手順2 の (1)(4) が共有しているのに、冪等キーの定義が節ごとに違っていた。`(kind, hmac)` にするとローテーションの (1) が常に no-op になり、(4) が旧世代行を消した時点で `credential_locators` が空になる（移送済み全利用者が到達性検査で締め出される）。加えて `credential_locators` の `credentialVersion` / `usableForLogin` の**更新**に世代規則が無く（削除だけが全世代規則を持っていた）、ローテーション中の credential 変更が片側の世代の行だけを進めて**恒久ログイン不能**になる経路が開いていた。

### Decision

**冪等キーを `(credentialId, generation)` に統一し、既存行があれば no-op ではなく upsert にする。** あわせて第6.1.1節へ **(R8)** を足す — `credentialVersion` / `usableForLogin` / `label` は `credentialId` 単位で管理し、更新は常に全世代の行へ同時に行う。`credentialVersion` は `credentialId` 単位で**単調非減少**で、`record-credential-locator` は「引数の値とその `credentialId` の既存行の最大値のうち大きいほう」を全世代の行へ書く。第6.5.1節 phase 2 の「当該行」も「`credentialId` が一致する全世代の行」に直し、login step 5 (iii) は「一致する active 行**すべて**が引数の値と一致すること」にした。鍵ローテーションの巻き戻しでは (1) がその走査で新規に追加した locator 行も破棄する。

### Consequences

- 良い点: 世代スキューが原理的に発生しなくなり、step 5 (iii) を「すべて一致」と fail closed で書ける。ローテーションのチャンクが古いスナップショットで再実行されても単調性が値の後退を防ぐ
- トレードオフ: upsert は「同じ値の再書き込み」を1行分の rows written として計上する。ローテーション1周ぶんの増分なので第10.2節の見積りには影響しない

## ADR-090: 鍵ローテーションの移送を `credentialVersion` の新旧比較で正本へ収束させる

### Status

Accepted

### Context

移送規則が「移送先に行があれば書かずに削除だけ行う」だったため、**移送先が陳腐化する方向**が無防備だった。(2) の後・(3) の前で中断し、その窓で旧世代 bucket 宛の発行済みトークンによるリセットが完走すると、再実行は「行があるから書かない」を選んで移送元（新しい値）を消す。終状態は active bucket に旧 `passwordVerifier` で、login step 5 の (ii)(iii) はどちらも通る — **リセットで設定した新パスワードが黙って捨てられ、旧パスワードでログインできる**。着地先が移送元になるのは偶然ではなく、リセット完了ではトークンが発行時の世代を運ぶので構造的に必然である。

### Decision

第6.1.1節へ **(R9)** を足す — **2世代に行が並存する状態では `credentialVersion` が大きい側が正本であり、移送は必ず正本の側へ収束させる。** 第6.8節 手順2 の (2) を4分岐にした（行が無ければ書く / `userId` 違いは `poison` / 移送元のほうが大きければ移送先を行ごと上書き / 移送先のほうが大きければ触らず移送元を消すだけ / 等しければ何も書かない）。**(R8) と (R9) は対で入れる** — 片方だけでは失敗モードが「旧パスワード復活」と「恒久ロックアウト」で入れ替わるだけである。

### Consequences

- 良い点: 中断からの再実行が自動的に正本へ収束するので、(3) の CAS 失敗時の「移送先の行を破棄する」は最適化として扱える（クラッシュで実行主体が消えても正しさが壊れない）
- トレードオフ: (2) が読み取り1回ぶん重くなる。移送は保守作業なのでホットパスに影響しない

## ADR-091: `encryptedCanonical` の AAD から `hmac` を外し、移送では再暗号化しない

### Status

Accepted

### Context

AAD が `(kind, hmac, encryptionGeneration)` を束縛する一方、鍵ローテーションの移送はその `hmac` を作り替える。移送手順に再暗号化の規定が無いので、**移送された全行の canonical が復号不能**になる。復号失敗は `SystemError(DataIntegrityError)` で fail closed に止める規則なので、(i) リセットメールの宛先組み立て、(ii) 設定画面の自メールアドレス表示、(iii) 次回ローテーションの再 HMAC が恒久的に壊れる。(iii) が壊れるので1回目の完了時点で2回目が原理的に実行不能になり、しかも移送直後は誰も復号しないため最初のリセット依頼まで顕在化しない。取りうる形は「移送時に再暗号化する」か「AAD から `hmac` を外す」の2つである。

### Decision

**AAD を `(kind, credentialId, encryptionGeneration)` にする。`hmac` は含めない。移送では暗号文系の3列（`encryptedCanonical` / `encryptionGeneration` / `encryptionNonce`）をそのまま運び、再暗号化しない。** 付け替え防止は維持される — `credentialId` は credential ごとに一意なので別 credential への付け替えは検出でき、検出できないのは「同じ credential の2世代の行のあいだで入れ替える」場合だけだが、その2行の平文は同じ canonical なので入れ替えても何も起きない。再暗号化する案を採らないのは、**再暗号化を `rotate-encryption` ジョブだけの仕事として定義した規則と、2つのローテーションを独立に走らせてよいという断定の両方を崩す**からである。

### Consequences

- 良い点: 規則が1つ減る（移送手順が暗号処理を持たない）。2つのローテーションの独立性が保たれる
- トレードオフ: AAD が locator を束縛しなくなるので、「行を別の bucket へ丸ごと複製する」攻撃は AAD では検出できない。ただしそれは移送そのものと区別がつかない操作であり、検出責務は Directory 側の一意制約と `userId` 照合が負う

## ADR-092: saga を新規に開始する3エントリを `callerToken` で束縛し、脅威モデルを実態へ書き直す

### Status

Accepted

### Context

「クラス (3) は CAS と phase 条件が守る」という一括の正当化が、**`operations` 行を新規に作る側のエントリには成立しない**。該当は `begin-credential-change` / `advance-credential-change` / ローテーション経路の `record-credential-locator` の3本で、いずれも無束縛のまま残っていた。結果として「同じ locator に対する**読み**は `callerToken` で束縛されているのに、より強い**書き**が無束縛」という非対称が生じ、乗っ取り原始関数・恒久ロックアウト原始関数・任意アカウントへのクレデンシャル注入が成立する。あわせて `callerToken` の脅威モデル（「request Worker のコード実行を得た攻撃者に効く2層目」）が、同トークンを request Worker へ返す設計（phase 0 の A-1）と食い違っていた。

### Decision

**3本とも `callerToken` で束縛する。** 材料は新しく増えない — 起点 A は A-1 が `account.callerToken` を返し、残り2本は Directory 側の mapping 行が同じ値を持つ。**唯一の例外は `begin-credential-change` の起点 B（未認証のリセット完了）**で、`consume-reset-token` が消費したトークン行へ `consumedByOperationId` を記録し、その `operationId` と `credentialId` の一致を条件にする。**ローテーション経路の `record-credential-locator` に `operations` 行を要求しない、と決め切る**（移送は認証状態の変更ではない）。第5.1節の群分けを3群から4群へ広げ、(3-d)「saga を新規に開始できる群」を立てた。**脅威モデルは書き直す** — `callerToken` が守るのは「binding には到達できるが `SESSION_SECRET` を持たない呼び出し元」だけであり、request Worker のコード実行を得た攻撃者にはセッション偽造 → A-1 の1回の追加 RPC で越えられる。この残余リスクは #38 の監査要件へ送る。

### Consequences

- 良い点: 「読みだけ束縛されて書きが無束縛」という自己矛盾が消える。`operations` 行の有無で守れないエントリが明示的な群として台帳に載る
- トレードオフ: `password_reset_tokens` に `consumedByOperationId` 列が1つ増える。`callerToken` の防御範囲を正直に書いた結果、残余リスクの記述が1つ増える（機構は廃止しない）

## ADR-093: 周期・反復ジョブの再武装をジョブ自身の責務にし、収束規則の適用範囲を外部再投入に限定する

### Status

Accepted

### Context

`operationKey` の収束規則は「`nextRunAt` を早める方向にのみ更新し、遅らせない」だったが、`trashRetentionDays` を**延長**すると `min(purge_after)` は後ろへ動くので、「`purge_after` の最小値を `nextRunAt` へ写す」「retention 設定変更時に Alarm を張り直す」という別々の断定と同時には成立しない。より重いのは**完走後の再武装が誰の責務か決まっていない**ことで、`purge-trash` が期限到達分を消して `done` になると、残る `pending` 行が無ければ `deleteAlarm()` が走り、dormant な User Data DO は次の期限が来ても二度と起きない — **ゴミ箱の保持期限が誰にも気づかれずに無期限へ伸びる**。`finally` を棄却し先頭再武装を導入してまで塞いだ失敗モードが、retention の本体経路で開いたままだった。同じ穴が `sweep-reservations` / `sweep-reset-tokens` にもあり、第6.4節の TTL 掃除（3段ガードの1段目）が1回きりで止まる。

### Decision

第7.4節に「**周期・反復ジョブの再武装規則**」を足し、第4.1節・第7.5節の断定をそこへ帰着させた。(1) `purge-trash` / `sweep-*` は完了トランザクションの中で自分の駆動源（`min(purge_after)` / `min(reservedUntil)` / `min(expiresAt)`）を読み直し、**残件があれば自分の `nextRunAt` をその値へ設定して `pending` へ戻し、残件が無いときだけ `done` にする**。(2) 収束規則「早める方向にのみ」は**外部からの再投入（`enqueueJob`）にだけ適用し、ジョブ自身の再スケジュールには適用しない**。(3) `purge-trash` / `sweep-*` の `operationKey` は定数（DO ごとに1行）にする。あわせて `done` / `poison` の行への再投入は「同じ行を `pending` へ戻して `attempt` を0にする（別行は作らない。`terminalReason` は残す）」と決めた。

### Consequences

- 良い点: 「早める方向にのみ」と「最小値を写す」が両立し、retention の前倒しと後ろ倒しの両方が動く。往復は増えない（正常完了時の張り直しと同じ `transactionSync` に入る）
- トレードオフ: ジョブ実装が自分の駆動源を知る必要がある（種別ごとに読む列が違う）。ジョブ種別を足すときに再武装の有無を判断する項目が1つ増える

## ADR-094: チャンク反復上限で中断したジョブは `status` を `pending` へ戻し lease を解放する

### Status

Accepted

### Context

claim は `UPDATE jobs SET status='running', leaseUntil=?, ownerToken=? WHERE ...` なので実行中のジョブは必ず `running` である。ところが (iii-b)（1回の Alarm 起動で同一ジョブについて回してよいチャンク反復回数の上限）の記述は「そのジョブを `pending` のまま残して次の Alarm へ回す」で、claim 済みのジョブを `pending` へ戻すのか `running` のまま残すのかが決まらなかった。`running` のまま残すと再 claim 述語 `(status='pending' OR leaseUntil < ?)` がリース満了まで一致せず、**そのジョブだけがリース期間ぶん進捗を止める**。`migrate-bulk` は外側の25件上限が発火しないぶん (iii-b) が唯一の中断点なので、影響が migration の所要時間に直接出る。

### Decision

**(iii-b) で中断するときは、進捗カーソルのコミットと同じ `transactionSync` で `status` を `pending` へ戻し、`ownerToken` と `leaseUntil` を解放する。** これで lease の用途を「実行中に DO がリセットされた場合の回収手段」だけに限定できる。

### Consequences

- 良い点: 中断と再開の状態遷移が claim の CAS と一致する。lease の意味が1つに絞られる
- トレードオフ: 中断のたびに1行の更新が増える。チャンク境界では既にカーソルをコミットしているので同じトランザクションに畳める

## ADR-095: 第2.1節 F-4b の裏付けを「記載の不在」から公式 FAQ の当該文へ差し替える

### Status

Accepted

### Context

F-4b は「Alarm / RPC が CPU リセットの契機に当たるか」を**記載の不在による推論**と分類していた。ところが同じ limits ページの FAQ に「By default, the maximum CPU time per Durable Objects invocation (HTTP request, WebSocket message, or Alarm) is set to 30 seconds」という一文があり、**Alarm は30秒の CPU 予算を持つ invocation として名指しで列挙されている**（公式ページを実地に取得して確認した）。一方でリセットの契機として footnote 4 が挙げるのは「incoming HTTP request」と「WebSocket message」の2つだけで、Alarm は含まれていない。事実表は「本節が設計の依拠する事実の正本である」と宣言し種別を落とさないと決めているので、分類の誤りは正本の正確さの問題になる。

### Decision

**出典欄を「記載の不在」から「FAQ の当該文と footnote 4」へ差し替え、種別は「未確認」のまま残す。** 未確認である理由も書き換えた — 「記載が無い」からではなく「公式内の2文が別々のことを述べており、Alarm ごとに30秒が与えられるのか着信間で共有される枠を消費するだけなのかが決まらない」からである。**設計の結論は一切変わらない** — 残り CPU を読む API が無いことと `Date.now()` の凍結（F-32）だけで、3階層とも件数で有界にする判断は独立に成立する。変わるのは #37 が着手時に走らせる spike の出発点で、第11.4節の該当行にもこの一文を引いた。

### Consequences

- 良い点: 事実表の種別分類が公式の記述と一致する。#37 の spike が「肯定も否定も無い」からではなく「一段細かい問い」から始められる
- トレードオフ: 無い。結論は不変で、記述の正確さだけが上がる
