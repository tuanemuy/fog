# ADR — Issue #34: [設計] Cloudflare Workers + ユーザー単位 Durable Objects への集約を ADR 化し、DO の境界とルーティングを設計する

本 Issue の成果物そのものである永続 ADR 3件（ランタイム・データ配置 / 検索方式 / 非同期処理）は `.adr/002〜004` に置く。このファイルには、その3件には含めない**計画段階のメタな判断**だけを記録する。

## ADR-001: 先行ブランチの `.adr/` 8件を3件へ縮約し、残りを design.md に吸収する

### Status

Proposed

### Context

分割元 Issue #19 のブランチ `issue/19/cloudflare-do-fts` には、DO 実装一式とともに `.adr/001〜008` の8件が既に存在する（`git show issue/19/cloudflare-do-fts:.adr/00N-*.md` で全文が読める）。

| 先行 | 主題 |
|---|---|
| 001 | Cloudflare Workers + 利用者単位 DO への集約 |
| 002 | 検索は SQLite FTS5 のみ |
| 003 | ローカル更新は同期 commit、外部処理は Alarm job |
| 004 | Identity Directory の秘密鍵付き分割と DO 間 saga |
| 005 | DO class lifecycle は宣言的 exports で管理 |
| 006 | usecase は DO 内で実行し、Worker RPC は値だけを運ぶ |
| 007 | PITR は staging smoke、local は wrapper contract で検証 |
| 008 | Account Home を認証と session のオンライン権威にする |

一方、Issue #34 は「`.adr/` に置くのは3件だけ」「それ以外は `.thread/34/`」「採番は既存の `001-integration-tests-single-workers-pool.md` の続きから」と明示している。先行の 001〜003 は #34 の3件と主題が一致するが、採番が衝突する。先行の 004〜008 は #34 の3件に含まれない。

選択肢は3つあった。

1. 先行8件をそのまま採用する
2. 先行 001〜003 を 002〜004 に採番し直し、004〜008 は 005〜009 として `.adr/` に置く
3. 先行 001〜003 を 002〜004 に採番し直し、004〜008 の内容は `.thread/34/design.md` に吸収して `.adr/` には昇格させない

### Decision

**3 を採る。**

1 は `.adr/001` を上書きし ADR が8件になるため、Issue の受け入れ条件（`.adr/002` 以降に3件、それ以外が増えていない）を機械的に破る。

2 は採番の衝突こそ避けられるが、「`.adr/` はプロダクトの意思決定だけの薄い台帳」という Issue の明示的な指示に反する。先行 004〜008 は寿命テスト（本 Issue を見ていない人にも意味を持つか）は通るものの、Issue が挙げた判断例（「Identity Directory DO をハッシュ何分割にするか」は `.thread/34/` に留める）に照らせば、分割方式・saga・exports・RPC 形状・PITR の検証境界・認証権威の所在はいずれも「決定の実現手段」の側にある。Issue 自身が「迷ったら `.thread/34/` に書く — `.adr/` を薄く保つほうが、後続 Issue の担当者にとって価値が高い」と優先順位を示している。

3 では内容を捨てない。先行 004〜008 の言語化された論点は design.md の次の章へ吸収する。

| 先行 | 吸収先（design.md） |
|---|---|
| 004 Directory 分割と saga | 第6章（Identity Directory DO）全体 |
| 005 宣言的 exports | 第9.1節（DO class lifecycle と object 内 schema version の分離） |
| 006 値のみの Worker RPC | 第3.2節（Worker 分割）・第8.3節（ユースケースの実行位置と RPC） |
| 007 PITR の検証境界 | 第10.1節（運用上の論点。詳細は #38） |
| 008 Account Home 認証権威 | 第3.1節（クラス構成と責務分界）・第5.1節（認証済みリクエスト） |

将来これらを永続 ADR へ昇格させる必要が生じたら、そのときに `.adr/005` 以降として別途起こす。

### Consequences

- 良い点:
  - `.adr/` が薄いまま保たれ、architecture-audit / spec-sync など後続の読み手が「プロダクトの意思決定」だけを短時間で把握できる
  - 先行ブランチの検討成果を捨てずに済む
  - 採番が `001` の続きになり、既存 ADR を壊さない
- トレードオフ:
  - Account Home の導入や Directory の分割方式といった波及の大きい判断が `.adr/` に現れないため、`.thread/34/design.md` を読まないと全体像が掴めない。緩和として `.adr/002` の影響節から design.md へのポインタを1行置く

## ADR-002: design.md を先に書き、`.adr/` の3件を後から抽出する

### Status

Proposed

### Context

実装ステップの順序として、(a) `.adr/` の3件を先に書いて design.md で詳細化する、(b) design.md を先に書き切って決定部分だけを `.adr/` へ抽出する、の2案があった。

(a) は「決定 → 詳細」という文書の依存方向と一致し、直感的に見える。

### Decision

**(b) を採る。**

(a) の順序で書くと、ADR を書いている最中に「なぜそう決めたか」を説明するために実現手段（分割方式、saga の phase、migration 手順、スキーマ断片）を書き足したくなり、詳細が `.adr/` へ流れ込む。これは受け入れ条件「`.adr/` にはその詳細が流れ込んでいない」を直接破る失敗経路である。

design.md を先に書き切れば、`.adr/` へ抽出するときの操作が「決定文と代替案と影響だけを取り出し、詳細は design.md へのポインタに置き換える」という減算になる。減算のほうが混入を起こしにくい。

### Consequences

- 良い点: `.adr/` が薄いまま仕上がる。ADR の各節が design.md の裏付けを持つ
- トレードオフ: design.md を書いている間、`.adr/` に置く3件の決定文が確定しない。3件の主題は Issue が指定済みなので、実質的な手戻りリスクは低い

## ADR-003: supersede の正本は新 ADR 側に置き、旧側にはステータス行の1行ポインタだけを置く

### Status

Proposed

### Context

supersede される旧 ADR は2件あり、性質が異なる。

- `.thread/1/adr.md` の ADR-004 — Issue #1 当時の**作業ログ**。1662行の巨大ファイルの一部。Issue は「本文は書き換えない。追記するとしても1行ポインタまで」と明示
- `spec/adr/005-search-index-via-outbox.md` — 旧運用の ADR 置き場。`spec/index.md:42`・`spec/database/index.md:6`・`spec/domains/{search,memo,knowledge}.md`・`spec/usecases/search.md:3` の計6箇所から相対リンクで参照されている（実測）。Issue は「本文を保持したままステータス行に superseded ポインタを付ける」と指示

書き方として、(a) 旧側に「何が変わったか」を含む説明を書く、(b) 旧側は「→ `.adr/00N` に supersede された」の1行に留め、supersede の理由と範囲は新 ADR 側にだけ書く、の2案があった。

### Decision

**(b) を採る。** 旧側は1行ポインタのみ。「何を supersede したか」は新 `.adr/` のステータス節または影響節に書く。

理由は3つ。

1. Issue が「supersede の正本は新しい `.adr/` 側に書く」と明示している
2. 説明を両側に置くと、後から決定が変わったときに2箇所を同期する必要が生まれる。ポインタは1方向にしておけば正本が1つに保たれる
3. `.thread/1/adr.md` は過去の作業ログであり、改変量を最小化するほど「当時の記録」としての価値が保たれる。1行に限定すれば `git diff` の削除行がゼロであることを機械的に確認でき、誤って本文を壊していないことを検証できる

### Consequences

- 良い点: 正本が1箇所に定まる。旧ファイルの差分が最小になり、意図しない改変を検出しやすい
- トレードオフ: 旧 ADR だけを読んだ人は「supersede された」ことしか分からず、新 ADR へ辿らないと理由が分からない。ADR の読み方として妥当な非対称性と判断した

## ADR-004: `.thread/1/adr.md` の ADR-002 / ADR-015 には supersede ポインタを付けない

### Status

Proposed

### Context

Issue の「参照」節は旧 ADR として ADR-002 / ADR-004 / ADR-015 の3件を挙げている。一方「対応項目2」で supersede を明示的に指示しているのは ADR-004 と `spec/adr/005` の2件だけである。残る2件にポインタを付けるかを決める必要があった。

- **ADR-002（セッション管理方式 — HMAC 署名付きステートレス Cookie）** — セッションを DB を触らずに検証する決定。`SessionCodec` ポートとアダプター1本の交換で差し替え可能な構造になっており、ランタイム集約とは独立している。DO 構成でも `userId` をリクエスト先頭で確定できる点はむしろ好都合で、決定が覆るわけではない。ただし Account Home を認証の権威に据える設計（先行 ADR-008）を採ると、「サーバー側から失効できない」というトレードオフの前提が変わる可能性がある
- **ADR-015（AWS の `SESSION_SECRET` は Secrets Manager 参照で配る）** — AWS 固有のシークレット配布方法。AWS ランタイム自体が #36 で撤去済みなので、対象が既に存在しない

### Decision

**どちらにも supersede ポインタを付けない。**

ADR-015 は supersede ではなく**対象消滅**である。撤去は #36 で完了しており、本 Issue の3件が覆した決定ではない。ここにポインタを付けると「#34 が AWS の何かを決め直した」という誤読を招く。これは無条件の判断である。

ADR-002 についてはこの判断が **design.md 第3.1節の結論に条件付き**である。ここで確定形で「覆されていない」と書くと、まだ下していない設計判断を先取りすることになる。

- **design.md 第3.1節が Account Home を採用しない場合** — ADR-002 は覆されていない。セッション方式の決定は DO 構成でもそのまま生きるので、ポインタを付けない
- **Account Home を採用する場合** — session は「発行時 `sessionEpoch` を署名し、protected execution point ごとに Account Home と照合」になり、ADR-002 の「DB を触らずに検証する / サーバー側失効の手段が無い」というトレードオフが実質的に覆る。ただしそれを覆したのは `.adr/002〜004` の3件のいずれでもなく、セッション方式そのものを扱う別 ADR の仕事になる。したがって**本 Issue でもポインタは付けない**が、トレードオフが変わる事実を design.md 第5.1節に明記する

いずれの分岐でも「本 Issue では `.thread/1/adr.md` の ADR-002 に手を入れない」という結論は変わらない。変わるのは design.md 第5.1節に何を書くかである。

**「セッション方式そのものを扱う別 ADR を起こす必要があるか」の判断は、本 Issue が下す。** 実施タイミングは **design.md 第3.1節（Account Home の採否）の結論が出た時点**で、結論は design.md 第5.1節に書く。

初版はこれを「#37 の着手前に判断する」としていたが、それでは3つの穴が空く。(a) 判断の記録が `.adr/` に残らない、(b) 判断の実行主体と場所が誰にも割り当てられない、(c) AC-21 が「design.md の『未決事項』に Account Home が現れない」ことを要求している一方で、実質的な未決事項が `.thread/34/adr.md` 側に残る。第3.1節の結論が出れば判断材料は揃うので、先送りする理由が無い。

あわせて、この帰結が `.adr/` しか読まない読み手（architecture-audit / spec-sync）に見えるよう、`.adr/002` の影響節に1行だけポインタを置く — 「認証権威の所在によっては、`.thread/1/adr.md` ADR-002 のステートレスセッションのトレードオフが変わる。所在の決定と、別 ADR を要するかの判断は `.thread/34/design.md` 第3.1節 / 第5.1節」。仕組みを書かないので AC-6 は破らない。

### Consequences

- 良い点: supersede の関係が「本 Issue の3件が実際に覆した決定」だけに限定され、履歴が正確に読める。`.thread/1/adr.md` への変更が1行に収まる。分岐を明示したので、design.md 第3.1節の結論がどちらでも判断の再検討が不要。判断の実行主体・タイミング・記録先がすべて本 Issue 内に閉じる
- トレードオフ: Account Home を採用した場合、ADR-002 のトレードオフ変更が `.thread/1/adr.md` 側からは追えない。design.md 第5.1節が唯一の詳細記録で、`.adr/002` の1行がその入口になる

## ADR-005: Account Home DO の採否は本 Issue で決着させ、未決事項に落とさない

### Status

Proposed

### Context

計画初版は「リスクと注意点」で、Account Home の採否について「決めきれない場合は『未決事項』に落とし、#37 の着手前に決める期限を書く」という逃げ道を用意していた。設計 Issue で難所を先送りする選択肢を残すこと自体は一般には妥当な保険である。

しかし本 Issue の受け入れ条件9は「後続 Issue（#35 / #37）が本 Issue の成果物だけを見て着手できる」であり、Account Home の採否は次のすべてを決める最上流の分岐にあたる。

- DO クラス数（2クラスか3クラスか）
- アカウント作成 saga の phase 数と、部分失敗時に残る状態の種類
- session 検証が per-request の RPC になるかどうか（`.thread/1/adr.md` ADR-002 のトレードオフが覆るか）
- PITR の restore 対象境界（何を1単位として戻すか）

未決のままでは #37 は1行も書けない。つまりこの逃げ道は、受け入れ条件9 と直接衝突する。

### Decision

**逃げ道を削る。** design.md 第3.1節で理由付きで結論づけ、第11.4節「未決事項」には落とさない。計画側には AC-21 として「第3.1節に採否の断定があり、第11.4節に Account Home が現れない」を検証可能な基準で立てる。

判断材料は揃っている。先行ブランチが「Directory mapping だけでは signup 部分失敗・退会中・古い PITR mapping・credential 変更後の session を区別できない」という理由で3クラス構成を採っており（`.thread/19/adr.md`）、採る／採らないのどちらに倒すにせよ、この理由に対する態度を書けば結論になる。

### Consequences

- 良い点: #37 が設計の再検討なしに着手できる。受け入れ条件9 が実質的に満たされる
- トレードオフ: design.md 第3章の執筆コストが上がる。ただし先送りしても #37 の着手前に同じ判断が必要になるので、総量は増えない

## ADR-006: `spec/adr/005` の supersede 先を `.adr/003` と `.adr/004` の両方にする

### Status

Proposed

### Context

計画初版は `spec/adr/005-search-index-via-outbox.md` の supersede 先を `.adr/003`（検索方式）単独に固定していた。

`spec/adr/005` の決定は「検索インデックスの更新を Outbox 経由の consumer で非同期に行う」であり、その根拠は「埋め込み生成が外部 API を伴うから同期にできない」である。この決定を覆すには2つの判断が要る。

- **根拠を消す** — ベクトル検索をやめれば埋め込み生成が不要になり、非同期にする理由が消える（`.adr/003`）
- **更新方式そのものを置き換える** — ローカル更新は DO の同期 commit にし、Outbox を transport として使わない（`.adr/004`）

更新方式を実際に置き換えるのはむしろ後者である。`.adr/003` 単独に固定すると、履歴上「検索方式の変更だけで更新方式が変わった」という読みになり、非同期処理側の決定が supersede 関係から抜け落ちる。

### Decision

`spec/adr/005` のステータス行のポインタは **`.adr/003` と `.adr/004` の両方**を指す。新 ADR 側にも対応する記述を置く — `.adr/003` の影響節に「`.adr/004` と共同で supersede する（覆すのは根拠側）」、`.adr/004` の影響節に「`spec/adr/005` の更新方式部分を supersede する」。

AC-7 / AC-10 の検証欄も両方を指していることを見る形に直す。

### Consequences

- 良い点: supersede の関係が実態と一致する。`spec/adr/005` から辿った読み手が、検索方式と更新方式の両方の変更に到達できる
- トレードオフ: 旧側のステータス行が1行では収まらない可能性がある。本文には手を入れないという制約は守れるので、実害はない

## ADR-007: 検索方式の設計詳細は本 Issue の決着対象から外し、#35 への入力として位置づける

### Status

Proposed

### Context

計画初版の design.md 構成案は第7.2節「検索方式の設計詳細」に、正規化（NFKC）・トークナイザ（trigram）・短語フォールバック・topic filter・trash 除外・安定順位・snippet・ページングを並べ、すべてを AC-5（断定形で終える）の対象に含めていた。

Issue の対応項目4が検索について求めているのは「FTS5 を本体更新と同一 SQLite transaction で同期更新できるか。できる場合、Outbox consumer を介したインデックス維持は不要になる」の1点だけで、これは第7.1節が引き受ける。

一方、7.2 の項目は性質が2つに分かれる。

- **正規化・トークナイザ・短語フォールバック** — 「日本語で FTS5 のみで足りる」という `.adr/003` の決定を支える根拠。本 Issue に必要
- **topic filter / trash 除外 / 安定順位 / snippet / ページング** — 検索 API の仕様設計。`spec/domains/search.md` の改訂（#35）か実装（#37）の領分

計画自身が「`spec/domains/search.md` の 271行が総崩れになる」ことを #35 の作業量として認識しているので、後者をここで先取りすると #35 と設計が二重管理になる。

### Decision

第7.2節を「FTS5 のみで日本語全文検索が成立する根拠」に絞り、検索 API の仕様は第7.2.1節で **#35 へ委譲すると明記する**。第7.2.1節は AC-5 の対象外とする。

先行実装が既に決めている内容（snippet の `<mark>`、安定ページング等）は捨てず、第11.1節の #35 引き継ぎ表に「決めるべき論点」として送る。

### Consequences

- 良い点: 本 Issue と #35 のスコープ境界がきれいになる。二重管理と、先取りした設計が #35 で覆される手戻りを避けられる
- トレードオフ: design.md だけを読んだ #37 の担当者は検索 API の仕様を知れない。#35 の成果物が先に必要になるという依存が1本増えるが、これは元々の Issue の分割構成（#37 は #34 / #35 の両方に依存）どおりである

## ADR-008: プラットフォーム事実の確定を独立した先頭ステップに置く

### Status

Proposed

### Context

計画初版はプラットフォーム制約の確認を design.md 第2.1節（実装ステップ1の中の1節）として扱い、事実誤認は「リスクと注意点」に列挙するに留めていた。

しかし DO のストレージ上限・単一 Alarm・`transactionSync` の同期性・カーソルの `await` 跨ぎ・FTS5 とトークナイザの可用性・`blockConcurrencyWhile` の30秒・`overloaded` のリトライ禁止は、design.md の第4章から第9章までの結論の土台になる。誤認したまま書くと全成果物に波及し、`.adr/` に書かれた場合は後続 Issue まで汚染する。

「書きながら調べる」構造では、調査と執筆が混ざって誤認が紛れ込みやすい。

### Decision

**プラットフォーム事実と先行資料の確定を実装ステップ1として独立させ、design.md の執筆（ステップ2以降）はその上で行う。**

## ADR-009: 受け入れ基準は design.md の節番号ではなく節タイトル（論点名）で参照する

### Status

Proposed

### Context

計画初版の受け入れ基準は design.md の**節番号**に強く結合していた（AC-4「第4〜6章の全節」/ AC-5「第7.1 / 7.3 / 7.4 / 7.5 / 7.6 節・第8章・第9章」/ AC-13「第6.1節」/ AC-14「第5.2節」/ AC-21「第3.1節と第11.4節」/ AC-22「第4.3節」/ AC-23「第5.2節・第6章」）。

design.md はまだ1行も書かれていない。構成案は約50節あり、執筆中に節を足し引きする可能性は高い（実際、2周目のレビューで第5.2.5節・第5.4.1節を追加することになった）。節番号を1つずらすだけで、実装ステップ10 の機械的検証が全滅する。

選択肢は3つあった。

1. 節番号のまま維持し、構成を変えたら AC 表も追随して直す
2. 節番号を捨て、論点名だけで参照する
3. 論点名を主にし、節番号を括弧付きの参考として併記する

### Decision

**3 を採る。** AC の検証欄は「canonical 化の定義（正規化手順 / `Email.create` を唯一の出所にするか / SSO subject の扱い / 規則変更の位置づけ）が結論として書かれている」のような**論点名**で書き、節番号は `（参考: 第5.2.1節）` の形に落とす。

1 は二重管理になる。design.md を書きながら AC 表を直し続けることになり、レビュー中に不整合が生まれる。

2 は執筆者・レビュアーが該当箇所を探すコストが上がる。構成案が存在するのだから、初期対応としての節番号は残したほうが速い。

3 なら、検証の実体（「その論点に結論があるか」）と AC の記述が一致し、design.md の構成に自由度が戻る。

**AC 番号（AC-1〜AC-23）自体は動かさない。** レビューファイル（`.thread/34/plan-review/*`）と指摘台帳がこの番号を参照しているため、付け替えると過去のレビュー記録が読めなくなる。追加が必要なら AC-24 以降を末尾に足す。

### Consequences

- 良い点: design.md の章立てを変えても AC が壊れない。AC の意味（何を検証するのか）が読み手に明確になる
- トレードオフ: 検証欄の文字数が増える。節番号だけの短い記述より読むコストが上がるが、機械的検証が空振りするコストのほうが大きい

## ADR-010: design.md の各節に「Issue 要求 / 派生 / 参考」の3ラベルを付け、AC-5 の対象を前2つに絞る

### Status

Proposed

### Context

Issue の対応項目3・4 が求めている決着項目は12項目程度である。一方、計画の design.md 構成案は11章・約50節あり、Issue 本文に対応する要求が無い節がいくつも含まれる（プラットフォームエラー翻訳表 / 鍵の所有者と世代管理 / location hint と jurisdiction / `getContainer()` の去就 / `SerializedError` の RPC 越し維持 / 運用上の論点の章）。

- 執筆時: Issue 未要求の節を「AC-5 の断定形要求が掛かる節」と誤認し、根拠の薄い断定を書き込む

### Consequences

- 良い点: 執筆の優先順位が明確になる。レビューで「これは根拠が要る断定か」を判定できる。Issue のスコープを超えた分量が見える化される
- トレードオフ: ラベルの判定自体に裁量が入る。迷った節は `.thread/34/adr.md` に記録する（実装ステップ9）

## ADR-011: 「ユーザー境界に閉じない処理」の網羅性は `spec/inventory/adapter.md` の `ADP-*` 台帳走査で担保する

### Status

Proposed

### Context

AC-22 は「ユーザー境界に閉じない処理が**全数**棚卸しされ、各行に行き先が割り当てられている」を要求している。この表が design.md 第4.3節の入力になるので、漏れたものは誰の関心事にも割り当てられないまま #37 に落ちる。

ところがこの表は2周のレビューで2回拡大した。

- 計画初版: 7件
- 1周目のレビュー後: 6カテゴリ・16行
- 2周目のレビュー後: 8カテゴリ・25行

2周目で見つかった漏れは `PasswordResetTokenPort.verifyAndConsume`（グローバルなトークン空間から user を解決するポート）/ `UserRepository.findByEmail`・`findBySsoIdentity` / `SearchIndexPort.upsert*` / `AiClientConnectionRepository.insert`・`save` / 期限切れ列挙用インデックス3本 / indexer 専用 WorkerContainer など。**「全数」を名乗る表が2回連続で全数でなかった**ことになる。

原因は取り方にある。「思いついたものを列挙する」方式では、列挙者が意識していないカテゴリが構造的に落ちる（たとえば「ポートは挙げたがスキーマ側の実現手段は挙げていない」「読みは挙げたが書きは挙げていない」）。

### Decision

**手作りの列挙を捨て、`spec/inventory/adapter.md` の `ADP-*` 要素台帳の全件走査に切り替える。**

同ファイルは `spec/database/` と `spec/domains/`（ポート定義）から生成された台帳で、スキーマ14件 + ポート実装 identity 16 / memo 13 / knowledge 27 / search 9 / trash 4 / export 2 を `ADP-*` の ID 付きで持つ。ここに機械的な述語をかける。

- **(a) userId を第一引数に取らないポート**
- **(b) `user_id` 列を持たない・PK に含まないテーブル**

台帳の粒度では捕まらない次元（DI 構成・ジョブ・spec 上の未設計領域）だけを、末尾のカテゴリで手動補完する。

AC-22 の検証も2段にする。**主判定**は「表の25行すべてに行き先が入っている」、**網羅性の再検査**は「`ADP-*` を全件走査して漏れがゼロ」。カテゴリ数（8）は補助扱いにする — 括り方を変えても検証が壊れないようにするため。

design.md 執筆前（実装ステップ2）にもう一度台帳を走査し、出た漏れは表に足す。

### Consequences

- 良い点: 網羅性の根拠が「列挙者の記憶」から「台帳 + 述語」に変わり、再現可能になる。spec 側の追加は台帳の更新として現れるので、将来の乖離も検出できる。台帳が `spec/inventory/*` として既に存在していたのに本 Issue が使っていなかった（「#35 の改訂対象」としか扱っていなかった）のを是正できる
- トレードオフ: 台帳自体が古い可能性がある（`最終同期: 2026-07-25`）。走査時に `spec/domains/` と突き合わせる手間が残るが、ゼロから列挙するよりは軽い。台帳の更新自体は #35 のスコープ

### Status

Proposed

2周目のレビューで「AC 表を23件 → 19件へ統合する」提案があった。重複しているとされたのは3組。

## ADR-014: AC-22 の主判定を「行数」から「台帳走査」へ入れ替え、述語を明文化する

### Status

Proposed

### Context

ADR-011 で網羅性の担保方法を「列挙者の記憶」から「`spec/inventory/adapter.md` の `ADP-*` 台帳 + 述語」へ移した。方法自体は正しかったが、**3周目のレビューで表からさらに4件の漏れが出た** — `ADP-export-002`（`ArchiveWriter.write`）/ pruner 専用の拡張 `WorkerContainer`（`spec/usecases/trash.md:315`）/ `ai_client_connections` のスキーマ側の行 / `ADP-search-001`（`SearchIndexPort.query`）。「全数」を名乗る表が **3周連続で全数でなかった**ことになる。

原因は2つある。

1. **述語が判定として機能していなかった。** 述語 (b)「`user_id` 列を持たない・PK に含まないテーブル」は、設計上すべてのテーブルが単一列 TEXT の `id` を PK にしている以上、**全件が該当してしまう**。実際に適用されていたのは「`user_id` 列が無い、または当該の引き方（ユニーク索引 / 期限切れ索引 / PK 素引き）の経路に `user_id` が入っていない」だった。また述語 (a)「userId を第一引数に取らないポート」の適用も揺れていた — `SearchIndexPort.query(query: SearchQuery)` は除外されているのに、userId が引数オブジェクトの中にある点でまったく同じ `upsertMemo(entry)` / `upsertDocument(entry)` は表に入っていた
2. **AC-22 の主判定の置き方が構造的に漏れを見逃す。** 主判定が「25行すべてに行き先が入っている」である限り、**表そのものが不完全なケースは主判定では捕まらない**。網羅性は補助扱いの「再走査」に依存していた

### Decision

**AC-22 の主判定と再走査を入れ替える。**

- **主判定**: `ADP-*` 全85件を走査して述語を当て直し、**該当する全件が表にある**こと + 各行に行き先が入っていること
- **補助**: 行数（29）とカテゴリ数（8）。走査の結果として導かれる値であって、判定基準ではない

**あわせて述語を明文化し、表より先に置く。**

- (a) `userId` を第一引数に取らないポート。**引数オブジェクトの中に `userId` があるものも該当する** — 規約（`spec/domains/index.md:32`）が求めているのは第一引数による構造的保証であり、オブジェクトの中に埋まっていると型レベルで保証されないため
- (b) `user_id` 列を持たない、**または当該の引き方の経路に `user_id` が入っていない**テーブル。見るのは列の有無ではなく引き方の経路
- (c) 台帳の粒度では捕まらない次元（DI 構成・ジョブ・spec 上の未設計領域）

述語の定義は plan.md の調査結果と design.md 第4.3節の**両方**で、表より前に置く。

### Consequences

- 良い点: 「表が不完全」という失敗モードが主判定で捕まるようになる。述語が明文なので、走査を別の人がやっても同じ結果になる。`ADP-search-001` と `upsertMemo(entry)` のような同型のものが片方だけ落ちる事故が防げる
- トレードオフ: 主判定のコストが上がる（85件の走査が毎回必要）。ただし2周連続で行数判定が漏れを見逃した以上、このコストは払う価値がある。行数を補助に落としたので、台帳が更新されて数が動いても検証は壊れない

## ADR-015: AC-5 の断定形要求の対象を、節の列挙ではなくラベルで定義する

### Status

Proposed

### Context

ADR-010 で design.md の各節に `［Issue 要求］` / `［派生］` / `［参考］` の3ラベルを付け、AC-5 の対象を前2つに絞ることを決めた。ところが **AC-5 の本文はラベルによる定義と節の列挙を併記しており、その2つが食い違っていた。**

3周目のレビューで、列挙から漏れている節が2つ見つかった。

- **「FTS5 のみで日本語全文検索が成立する根拠」（第7.2節・ラベル［派生］）** — AC-5 が**明示的に除外**していた。除外理由は「`.adr/003` を支える根拠だから」。しかし正規化（NFKC）・トークナイザ（trigram）・短語フォールバックが結論に至らないと、`.adr/003`「FTS5 のみを採用する」の妥当性そのものが宙に浮く。しかも trigram の可用性は公式ドキュメントに記載が無く実測だけが根拠という、**最も結論の明記が要る部類**である。結果として `.adr/003` の根拠に結論を要求する AC が1つも無い状態になっていた
- **「分割方式」（第6.2節・ラベル［Issue 要求］）** — 列挙に含まれていなかった。AC-13 の検証欄は「『分割方式』にも節がある」「単一グローバル DO を無条件採用していない」なので、**「(b) が有力だが最終決定は #37」で書かれても通ってしまう**。Identity Directory の分割方式は #37 の前提であり、決着5論点のうちこれだけが断定形を要求する AC を持っていなかった

実装ステップ10 の自己検証は「ラベル前2つの節がすべて断定形」と広く書けているので実運用では拾えるが、**AC-5 本文の節リストと食い違っている**。

### Decision

**AC-5 の「対象」をラベルだけで定義する。** `［Issue 要求］` または `［派生］` が付いた節**すべて**が対象。節の列挙は「したがって次はいずれも対象に含まれる」という**例示**に格下げする。

対象外は次の2つだけにする。

- `［参考］` ラベルの節
- 「検索 API の仕様 → #35 へ委譲」（第7.2.1節）— 本文で明示的に委譲を宣言している節

## ADR-016: AC-8 は「追加はポインタ1行のみ（前後の空行を除く）」で判定し、挿入書式を固定する

### Status

Proposed

### Context

AC-8 は `.thread/1/adr.md` の ADR-004 への supersede ポインタ追記を「削除行が0・**追加行が1**」で判定していた。

実測すると該当箇所は `:160` 見出し / `:161` 空行 / `:162` `### Status` / `:163` 空行 / `:164` `Proposed` / `:165` 空行 / `:166` `### Context` である。ポインタ段落を通常どおり前後に空行を置いて挿入すると**追加行は2**（本文1 + 空行1）になり、AC-8 が落ちる。

空行を足さずに1行だけ挿すことは CommonMark 上は有効（見出しは段落を中断できる）なので**達成は可能**だが、それは**リポジトリの Markdown スタイル（ブロック要素の前後に空行）に反する書き方を実装フェーズに強いる**形になる。`markdown-style` の方針とも衝突する。

選択肢は2つあった。

1. 判定を「追加行が1〜2」に緩める
2. 判定を「削除行がゼロ、かつ追加が supersede ポインタ1行のみ（前後の空行を除く）」に書き換え、あわせて挿入書式を指定する

### Decision

**2 を採る。** 判定の意味を「追加された**内容**は1行だけ」に置き、空行は数から除外する。あわせてステップ8 に挿入書式を書き込む — **`Proposed`（`:164`）の直後に空行1行 + ポインタ1行**。したがって `git diff` 上の追加行は2になる。

1 は数値を緩めるだけで、「なぜ2なのか」が残らない。実装フェーズが「3行でもいいのか」と迷う余地を残す。2 なら判定の意図（本文を1行しか足していない）が読めるので、書式を守っている限り迷わない。

### Consequences

- 良い点: Markdown の規約と AC が両立する。挿入位置まで指定してあるので実装フェーズで判断が要らない。「削除行がゼロ」という本質的な保証（本文を壊していない）は変わらない
- トレードオフ: 判定が「行数を数える」から「差分の中身を見る」に少し重くなる。ただし差分は2行なので目視で済む

## ADR-017: AC-20 の既知 untracked は実測で作り、`.thread/36/` を含める

### Status

Proposed

### Context

2周目に AC-20 へ足した「`git status --porcelain` に既知の untracked 以外の未コミット変更がゼロ」という検査は、commit 漏れによる空振りを塞ぐためのものだった。ところがホワイトリストを**実データを見ずに書いた**ため、`.thread/36/` が漏れていた。

実測した `git status --porcelain` は次の6エントリを返す。

```
?? .artifacts/
?? .thread/34/
?? .thread/36/
?? apps/web/wrangler.request.production.toml
?? apps/web/wrangler.request.staging.toml
?? apps/web/wrangler.state.production.toml
?? apps/web/wrangler.state.staging.toml
```

`.thread/34/` は本 Issue の成果物として commit されるので残らないが、**`.thread/36/` は残る**。#36 はマージ済みだが、その作業ログ（`adr.md` / `plan.md` / `testing.md` / `manual-test/`）が commit されていない。

- 放置すれば AC-20 後半（未コミット変更ゼロ）が**誤検知**で落ちる
- commit すれば AC-20 前半（差分は `.adr/00{2,3,4}` / `.thread/34/**` / `spec/adr/005-*` / `.thread/1/adr.md` に限る）を破る

**ホワイトリスト方式を維持し、実測値で作り直す。** 既知の untracked は `.artifacts/` / **`.thread/36/`** / `apps/web/wrangler.{request,state}.{production,staging}.toml` の4本。

1. **否定形は commit 漏れを検出できない。** この検査の主目的は「成果物の commit し忘れ」を捕まえることで、成果物は `.adr/` と `.thread/34/` に置かれる。`.thread/34/` を否定形の対象に含めれば検出できるが、そうすると `.thread/36/` を含む `.thread/` 全体の扱いを結局ホワイトリストで書き分けることになり、同じ問題に戻る
2. **untracked の残骸が増えたら気づくべきである。** ホワイトリストは「作業ツリーに何が残っているか」を明示する副作用を持つ。実測で作り直す運用（下記）とセットなら、残骸の増加が検査の失敗として現れるのはむしろ望ましい

**`.thread/36/` 自体には本 Issue で触らない。** #36 は完了済みで、その作業ログの commit 要否は本 Issue の判断対象ではない。調査結果に「untracked のまま残っている / 本 Issue では触らない」と記録するだけに留める。

**ホワイトリストは着手時点で `git status --porcelain` を実際に実行して作り直す。** 計画に書いてある6エントリは計画時点のスナップショットである。

### Consequences

- 良い点: ステップ10 の検査が実データで通る。「検出装置を書くときに実データを見る」という規律が明文化される
- トレードオフ: 着手までの間に untracked が増減するとホワイトリストが再びずれる。「着手時点で実行して作り直す」を手順に入れて対処する。`.thread/36/` を本 Issue で commit しないので、#36 の作業ログはしばらく untracked のまま残る

## ADR-018: ステップ2 → ステップ3 の前方依存は「暫定判定 + ステップ3 で確定」で解消する

### Status

Proposed

### Context

実装ステップ2（design.md 第1〜6章）には、ステップ3（第7〜11章）の結論への**前方依存**がある。

- 第4.3節で「そもそも不要になる」に倒れる行は、**第7.1節（FTS5 同期更新の可否）と第7.3節（Outbox 廃止範囲）の結論が出るまで確定しない**
- 第5.4.1節 (b)（失効の到達手段）は本文自身が「Outbox 前提が 7.3 で消えるので決め直しが要る」と書いている

ステップ7（`spec/adr/005` の supersede）は同種の従属を「**前提**: 第7.1節が肯定的結論を出した場合に実施する」として扱えているのに、ステップ2 には同じ扱いが無い。単一ファイルを1人で書くので実務上は往復で吸収できるが、**順序の宣言としては逆流している**。

選択肢は2つあった。

1. ステップの順序を依存順に並べ直す（第7章を第4〜6章より先に書く）
2. 依存がある旨と解消手順をステップ2 に明記する

**2 を採る。** 具体的には3段階にする。

1. ステップ2 では従属する行・項目を「**7.1 / 7.3 の結論に従属。暫定判定: 〜の見込み**」と、暫定と分かる形で書く
2. ステップ3 で第7章を書き終えた**直後に**第4.3節 / 第5.4.1節 (b) / 第6.4節へ戻り、暫定を確定に置き換える
3. ステップ10 の自己検証で「暫定」「見込み」「〜次第」という語が第4〜6章に残っていないことを確認する

1（順序の入れ替え）を採らない理由は、第7章のほうが第4〜6章に依存する部分も相当あるためである — 第7.5節（trash retention）は第4.3節の帰属判断を前提にし、第7.4節（Alarm ジョブの所有者）は第3.1節のクラス構成と第6.4節の補償設計を前提にする。**依存は相互であって一方向ではない**ので、並べ替えでは解けない。解けるのは「どちらを先に書くか」ではなく「暫定をいつ確定に変えるか」を決めることである。

### Consequences

- 良い点: 依存が文書に現れるので、着手時に「なぜ第4.3節が埋まらないのか」で止まらない。ステップ7 の「前提」節と同じ扱いになり、計画内で表現が揃う。ステップ10 に機械的な検査（暫定を示す語が残っていない）が1つ増える
- トレードオフ: 第4〜6章に一度書いた箇所を書き直す往復が明示的なコストとして現れる。ただしこれは依存の実態であって、隠しても消えない

## ADR-019: プラットフォーム事実は「裏取り済み」でも主張の実在と裏付けの種別から点検する

### Status

Proposed

### Context

ADR-008 で「ステップ1 はゼロからの再調査ではなく差分確認」と決め、2周目のレビューで「プラットフォーム事実14項目は公式ドキュメントで全件一致が再確認された」と記録した。にもかかわらず、**3周目に3件の誤りが見つかった**。

1. **「`idFromName` に渡した名前は復元できない」は誤り。** 公式（`/durable-objects/api/id/`）は `name` を `DurableObjectId` の optional property と定義し、「especially useful inside **alarm handlers**, where there is no calling client to pass the name as an argument」と、本 Issue が設計する Alarm ジョブそのものを用例に挙げている
2. **「仮想テーブルは原則禁止だが FTS5 のみ例外」は出典が無い。** 該当ページを取得しても相当する記述が無く、仮想テーブルに言及するもう一箇所は課金の一文で、むしろ一般に使える前提の書き方になっている
3. **`bm25` / `snippet` / `highlight` は公式ドキュメントに一語も現れない**（workerd の allowlist ソースには存在するが、それは実装ソースであってドキュメントではない）のに、「公式にサポート明記」の側に書かれていた

3件に共通するのは「**値は合っているか**」ではなく「**その主張が出典ページに実在するか**」「**裏付けの種別（公式記載 / 実測 / 未確定）が正しいか**」の誤りだという点である。差分確認は前者しか見ない。

さらに悪いことに、計画が「この表は裏取り済み。ステップ1 は再取得ではなく差分確認」と宣言していること自体が、**再点検を止める作用**を持っていた。誤りは点検されずに design.md 第2.1節（#35 / #37 が読む正本）へ転記される経路にあった。

計画は「公式に記載が無い事項は『実測』または『未確定』と明示して区別する」という規律を自分で立てており、トークナイザにはそれを適用していたのに、**同じ行の他の主張には適用できていなかった**。

### Decision

**ステップ1 の差分確認に「主張の実在」と「裏付けの種別」の点検を含める。** 各行について次の3つを見る。

1. 値が変わっていないか（従来の差分確認）
2. **その主張が出典ページに実在するか**（原文を引ける表現になっているか）
3. **裏付けの種別が正しいか** — 公式記載 / 実測（`.thread/19/spike/fts5.integration.test.ts` 等）/ 未確定 のどれか

**裏取りできないものは「未確定」または「ステップ1 で実測して確定する」項目へ落とす。** 具体的には trigram トークナイザ・`bm25`・`snippet`・`highlight` の4つを実測項目に落とし、spike が触れていない関数があれば「未確定」のまま残して、第7.2節と `.adr/003` はその関数に依存しない書き方にする。

**事実の訂正が設計判断を再オープンするかは、判断ごとに切り分けて書く。** `ctx.id.name` の訂正では第6.2節 (c) の不採用理由と第6.8節の結論は再オープンしない — そこで効いているのは「namespace を実行時に列挙できない」という別の（確認済みで正しい）事実だからである。一方、第6.3 / 6.8 / 7.4節の「DO に自分の routing key を明示的に渡す」配線は不要になりうるので、そこは設計に反映する。**訂正のたびに「何が動いて何が動かないか」を1行添える。**

### Consequences

- 良い点: 誤認が design.md 第2.1節へ転記される経路を塞げる。「公式保証だと誤認する」という #35 / #37 側の失敗が防げる。訂正の波及範囲が明示されるので、事実が1つ直るたびに設計全体を疑い直さずに済む
- トレードオフ: ステップ1 のコストが「値の差分確認」より上がる。ただし18項目・各1行の確認であり、誤認が全成果物に波及するコストのほうが桁違いに大きい。3周のレビューで実際に3件出た以上、経験的にも正当化される

これは形式的な網羅性の話に留まらなかった。`PasswordHasher` の実行位置を問うた結果、**PBKDF2 210,000 回（`.thread/1/adr.md` の ADR-002）を single-threaded な DO の中で回してはいけない**という結論が出た。User Data DO で回せばそのユーザーの全リクエストが止まり、Directory bucket で回せば同じ bucket に写像される全ユーザーの認証が止まる。この結論は design.md 第4.8節・第8.3節 (a) に入り、第3.2節の秘密配布境界（照合を request Worker で行うので `passwordHasher` は request 側 DI に残る）とも噛み合った。

### Consequences

- 良い点: 台帳走査を主判定に置いた効果が実際に出た（AC-22 の設計意図どおり）。実行位置の結論が1つ増え、#37 が DO の中で CPU を焼く実装を書く経路が塞がれた
- トレードオフ: 述語が「純粋計算でも対象になりうる」まで広がったため、将来ポートが増えたときの判定にわずかな解釈の余地が残る。design.md 第4.3節の述語定義に判断根拠（実行位置の判断が要るか）を書いて補った

## ADR-024: ドメインイベントを業務表現としても残さず、`collectEvents` ごと廃止する

### Status

Accepted

### Context

Issue の対応項目4は「Outbox / relay / consumer / DLQ の廃止範囲」を求めているが、**ドメインイベントそのものを残すかどうか**は明示していない。plan.md の構成案は第7.3節の決着項目として「ドメインイベントを業務・監査の表現として残すか」を挙げていた。`spec/domains/*.md` にイベント定義が広範に存在するので、この判断は #35 の改訂量に直結する。

### Decision

**残さない。`UnitOfWorkContext.collectEvents` ごと廃止する。**

理由は3つ。(1) 唯一の購読者だった indexer consumer が消え、もう1つの購読者（トークン失効 consumer）も権威の直読みへ置き換わるので、発行された事実を消費する経路が1つも無くなる。(2) 監査ログが要件として存在しない（`spec/requirements.md` に監査要件が無い）。(3) 業務上の変更履歴は `memo_revisions` / `document_revisions` が既に持っており、業務表現としての役割が重複している。

「将来使うかもしれない」で仕組みだけ残すのは、`.adr/001-integration-tests-single-workers-pool.md` が空の Node プール設定について採った態度（理由が消えたら設定も消す）と一致しない。

### Consequences

- 良い点: `packages/core/src/application/ports/outboxRepository.ts` / `relayTrigger.ts` / `idempotencyStore.ts` の3本が丸ごと消え、`spec/domains/*.md` のイベント定義表も削除できる。設計の面積が大きく減る
- トレードオフ: #35 の改訂量が増える（イベント定義は memo / knowledge / identity の3ドメインに散らばっている）。将来監査要件が出た場合は、リビジョンからの再構築か新しい仕組みの導入になる

## ADR-025: プラットフォーム事実表の2点を、公式ドキュメントの再取得結果に合わせて書き換える

### Status

Accepted

### Context

`.thread/34/adr.md` の ADR-019 が定めた点検（値だけでなく「主張の実在」と「裏付けの種別」を見る）を、公式ドキュメント8ページの再取得で実行した。plan.md の表は3周目の修正を経ていたが、それでもなお2点が実態とずれていた。

### Decision

design.md 第2.1節では次のように書いた。

1. **「DO namespace を実行時に列挙する手段が無い」を「記載の不在による」と明示する。** 再取得の結果、この不在を明示的に述べた公式の一文は存在せず、namespace binding の API 一覧（`idFromName` / `idFromString` / `newUniqueId` / `get`）に列挙手段が載っていないことから導かれる事実だった。REST の List Objects が object ID と `hasStoredData` だけを返すことは公式に確認できる。**結論（第6.2節 (c) の不採用理由、第6.8節の retirement 証明）は変わらない**が、根拠の性質が「公式が明記した禁止」ではなく「提供されていないこと」である点は書き分ける。
2. **`bm25` と trigram を「実測で確認済み」へ、`snippet` / `highlight` を「未確認」へ振り分ける。** plan.md は4つをまとめて「ステップ1 で実測して確定させる」項目にしていた。先行ブランチを読んだ結果、trigram（`tokenize='trigram'`）と `bm25`（`bm25(search_fts, 3.0, 1.0)`）は実装と workerd 統合テストで実際に動いているのに対し、**SQL 関数の `snippet()` / `highlight()` は先行実装が使っていない** — インデックスは NFKC 正規化後のテキストを持つのに表示は原文でなければならないため、スニペットを TypeScript 側で原文から組み立てている。したがって `snippet()` の可用性には実測が存在しない。

`snippet()` / `highlight()` は「未確認」のまま第11.4節へ送り、**設計をこれに依存させない**（原文からスニペットを組む方式を採る）。`.adr/003-sqlite-fts5-only-search.md` の成否がこの未確認項目に懸からないようにした。

### Consequences

- 良い点: #35 / #37 が「公式保証」と誤認する経路が塞がれた。未確認項目が設計の critical path から外れているので、spike の結果がどちらでも `.adr/003-sqlite-fts5-only-search.md` は成立する
- トレードオフ: 事実表に「未確認」が3件残る（`snippet` / `highlight` の可用性、`transactionSync` のネスト可否、単一クエリの結果セットサイズ上限）。いずれも第11.4節で担当と時期を割り当てた

## ADR-026: bucket 数の変更を「世代の変更」として扱い、具体値は design.md にだけ書く

### Status

Accepted

### Context

design.md 第6.2節で Identity Directory の分割方式を「固定 bucket 数のハッシュ分割」に決めた。この案の最大の難点は「bucket 数を後から変えられない」ことで、3案比較の判断軸 (ii) がそこを突いていた。一方 `.adr/` には bucket 数の具体値を書けない（受け入れ基準が禁止している）。

### Decision

**bucket 数を locator 名に世代とともに埋め込み（`dir:g{generation}:b{index}`）、bucket 数の変更を鍵ローテーションとまったく同じ再写像機構で処理する。** これにより判断軸 (ii) は行き止まりではなくなる。具体値（初期256）と根拠は design.md 第6.2節にだけ書き、`.adr/` には一切書かない。

初期値を design.md で断定したのは、「実装時に決める」で終えると #37 が判断材料ごと持たされるためである。根拠（Directory を叩くのは未認証経路だけで認証済みトラフィックは通らない / 1 bucket あたりの負荷が soft limit から十分離れる / 全 bucket 走査が Alarm の CPU 予算で分割実行できる規模）も併記した。

### Consequences

- 良い点: (b) を採る最大の弱点が構造的に解消される。`.adr/003-sqlite-fts5-only-search.md` / `.adr/004-do-local-commit-and-alarm-jobs.md` と同様、`.adr/002-cloudflare-workers-and-user-data-durable-objects.md` にも数値が漏れない
- トレードオフ: 鍵ローテーション機構が bucket 数変更も担うため、その機構の正しさへの依存度が上がる。design.md 第6.8節で retirement 証明を bucket ごとの snapshot 置換に作り替えたのはこのためでもある

## ADR-027: 先行案の採否に「保留」を作らない

### Status

Accepted

### Context

plan.md は design.md 第1.3節の差分表を「採用 / 棄却 / 保留」の3値で書くことを想定していた。`.thread/19/adr.md` の10件 + #33 のレビュー指摘のうち、Account Home（先行 ADR-010）と検索 API 仕様（先行 ADR-002 の後半）は判断が重い。

### Decision

**全12行に採用 / 部分採用 / 棄却のいずれかを出し、保留をゼロにする。**

「保留」は #37 の着手時点で誰かが判断しなければならない項目を作る。受け入れ条件が「後続 Issue が本 Issue の成果物だけを見て着手できる」ことを求めている以上、保留は事実上その条件を破る。判断が重い2件はそれぞれ別の形で処理した — Account Home は棄却して理由を第3.1節に書き、検索 API 仕様は「棄却」ではなく **#35 への明示的な委譲**（第7.2.1節）として、委譲先と委譲する内容を第11.1節に列挙した。

「決めない」を選ぶ場合でも、**誰がいつ決めるかを割り当てて初めて成果物になる**。第11.4節の3件も同じ形にしてある。

### Consequences

- 良い点: #35 / #37 が「これは誰が決めるのか」を探す時間がゼロになる
- トレードオフ: 判断材料が薄いまま倒した行があれば、後で覆るコストを払う。#33 のレビュー指摘（B-IDDS6-001）のように、先行案のレビュー履歴まで読んで材料を厚くすることで緩和した
