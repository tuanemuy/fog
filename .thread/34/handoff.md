## 1. 何が起きていたか（経緯）

レビューを **10ラウンド（上限到達）+ 検証ラウンド4周（R11 / R12 / R13 / R14）** 回した。R10 までで設計の骨格は収束し、**R10 以降、設計の骨格に関わる指摘は1件も出ていない**。

ところが R11〜R13 で毎周 Blocker が出続けた。内訳を見ると原因は1箇所に集中していた。

| ラウンド | 設計 Blocker | 領域 |
|---|---|---|
| R11 | 1件 | **分類 (C) の終端規則**（起点 B の恒久締め出し） |
| R12 | 2件 | **分類 (C) の終端規則**（`callerToken` の材料寿命）/ 引き継ぎ表への伝播漏れ |
| R13 | 2件 | **分類 (C) の終端規則**（終端モードの印 / 3-i の除外単位）。**2件とも2層が独立検出** |

**R11 以降の設計 Blocker 5件のうち4件が「分類 (C) の cross-DO saga の異常系（終端規則）」だった。** 直すたびに「材料の寿命」「判定信号の永続性」「段どうしの順序」で新しい破れが見つかる状態で、**R13 の2件に至っては R12 の修正どうしが同じラウンドの中で互いを壊していた**（fix A が fix B の判定材料を別の段へ移し、fix B はその移動を知らずに書かれていた）。

**これは R8 で鍵ローテーションを #44 へ切り出したときとまったく同じパターンだった。** あのときも直近4ラウンドの Blocker がほぼすべてローテーション由来で、切り出した瞬間に静かになった（R9〜R14 でローテーション由来の指摘はゼロ）。

## 2. 決めたこと（反映済み）

**反映は `.thread/34/design.md` 第7.4節を正本として済んでいる**（第6.8節の #44 委譲と同じ4小見出しの構成にした）。判断の記録は **`.thread/34/adr.md` ADR-157 / ADR-158** にある。

## 3. 実施した作業（記録）

### ステップ1 — design.md への反映（完了）

**残したもの（#34 の成果。#45 の入力である）**

- 分類 (C) が `poison` に達しうること、`backoff と poison` の規則、`jobs` の12列（第7.4節・第4.1.1節）
- **発火条件**（「前進不能が確定した場合」＝ `ConflictError` またはバックオフ上限到達。`ConflictError` に限定してはならない）
- **各 saga が終端時に残しうる中間状態の列挙** — 第7.4節に**分類 (C) の全 `kind` を1つの表**にまとめ直した（従来は第6.4節 / 第6.5.1節 / 第6.6節 / 第6.7節 に散っていた）
- **第6.9節の締め出し経路22件の列挙。** 変えたのは塞ぎ方の欄4つだけである（#44 の7行と同じ扱い）
- **回収の材料が存在すること、およびその置き場** — `operations.targetLocators` / コーディネーター予約行の `locators[]` / `candidateUserId` / `callerToken` / `account.callerToken` / `credential_mappings.changeState` の3値
- **operator 経路の存在** — `purge-user-mappings` / `cancel-reservation`、および**`purge-user-mappings` では届かない残渣があること**
- **一様な終端の形** — `terminalReason` + `poison` + operator エスカレーション
- **`terminalReason` の制約** — 載せるのは終端の理由と `operationId`、載せないのは PII と再利用可能な秘密
- **「黙って中間状態を残す」は選ばない、という原則**

**#45 へ委譲したもの（塞ぎ方の具体）**

- signup の終端の段構成（段の順序と、コーディネーター行の除外単位）
- 終端モードの印の置き方（`jobs.terminalReason` を前倒しで書く形）
- 後始末そのものが失敗したときの規則と、再試行上限（`attempt` の2倍）
- (ii) の受け口の残渣種別ごとの割り当てと、`terminalReason` に載せる残渣の所在
- 起点別の (i)/(ii) の使い分け（`changeOrigin = 'reset'` の併用）
- link の終端の巻き戻し手順
- 上記を機械検証できる不変条件

**#37 が落としてはいけない前方互換点（第7.4節に4点として明記した）**

1. **`operations.targetLocators` を、#45 の自動回収が入るまで消さない**（一様な終端には消す契機が無い）
2. **コーディネーター予約行（`locators[]` / `candidateUserId` / `callerToken` を持つ行）を、#45 の自動回収が入るまで消さない**
3. **`account.callerToken` を退会完走時以外に消さない**
4. **`credential_mappings.changeState` を3値（`null` / `'pending'` / `'advanced'`）で実装する**

**委譲で根拠を失いかけた断定は justification を差し替えた**（詳細は ADR-157）。とくに **`changeState` の3値化**と **`'advanced'` を phase 2 の成功「後」に書く fail-safe の向き**は、旧版が「#45 側の (i)/(ii) 判定材料」「巻き戻しが発火しない」を唯一の根拠にしていたので、**#34 の側にある独立した根拠**（`promote-verifier` のガード / 後勝ち規則 / phase 3 が Directory 側だけを昇格させる破れ）へ載せ替えてある。

## 5. 機械検査で捕まらない残余リスク（引き継ぐ）

**#34 ではこの2つに機械検査を設計できなかった。** #45 の論点7 が同じ形式で設計することになっている。

1. **「正本だけを直して適用先の散文に届けない」形に検査が無い。** 第1.4節の不変条件が覆うのは**表どうしの整合**であって、正本の断定と適用先の散文の整合ではない。確認項目20 の固定 grep 13本も素通りする。R12 / R13 の指摘の大半がこの形だった
2. **同一ラウンド内で入れた複数の修正どうしの整合を、誰も検査していない。** R13 の Blocker 2件がこの形（R12 の fix A が fix B の前提を壊した）。**今回の反映でも1件発火した** — `abandon-account` の行に書いた「`rotate-remap` を全数表から外したのとは扱いが違う」という文が、**#44 の委譲を検査する確認項目19 手順3（RPC エントリ表に `rotate-remap` が現れないこと）を 0 → 1 に壊した**。今回は確認項目19 が拾ったが、**拾えたのは偶然その検査が存在したからである**

**帰結として、#35 / #37 は「本書の1つの節だけを読んで実装しない」ことを前提にする。** その節が名指しする適用先まで辿る必要がある。**#37 向けには第11.2節に「DO 側の新規実装になる6つ」の索引を置いてある**（同節の表は既存ファイルの一覧なので、新機構はどの行にも現れない）。
