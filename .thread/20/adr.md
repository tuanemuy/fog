# ADR — Issue #20: パスワードハッシュのコストパラメータを見直す

## ADR-001: 案 A / 案 B の選択を実測に基づく機械的な判定ゲートへ委ねる

### Status

Proposed

### Context

`DEFAULT_PBKDF2_ITERATIONS = 210_000` に付いた「OWASP の PBKDF2-HMAC-SHA256 推奨」というコメントは取り違えで、210,000 は OWASP Password Storage Cheat Sheet の **SHA-512 の行**の数字である（SHA-256 の推奨は 600,000）。したがって現状は SHA-256 の推奨に対してコストが約 1/3 で、「OWASP 推奨だから安全」という ADR-003 の前提がそこだけ崩れている。

選択肢は2つ。

- **案 A: PBKDF2-HMAC-SHA512 + 210,000。** 210,000 は OWASP Password Storage Cheat Sheet（2023 版）の PBKDF2-HMAC-SHA512 の行の数字である
- **案 B: PBKDF2-HMAC-SHA256 + 600,000。** 600,000 は同じ表の SHA-256 の行の数字。変更が定数1つに閉じ、`parse()` にもテストの大半にも手が入らない

**OWASP の表の読み方について、Issue 本文の説明を1点訂正しておく。** 表の2つの数字は「**各アルゴリズムで防御側の所要時間がおおむね揃うようにキャリブレートされた**」ものであり、SHA-512 は1反復あたりの CPU コストが SHA-256 より高いから回数が少ない。**「OWASP が GPU / ASIC 耐性を理由に SHA-512 の回数を低く設定した」という帰属は誤り**である。OWASP の表は防御側コストのキャリブレーションであって、意図の記述ではない。

そのうえで、**我々が案 A を検討する理由は別に成立する**: SHA-512 は 64bit 演算主体で、32bit 演算に最適化された GPU / ASIC での並列効率が SHA-256 より低いと一般に言われており、**同じサーバー負荷あたりの攻撃者コストが高い**。これは**我々の採用理由**であって OWASP の設定理由ではない。この2つを書き分けるのは体裁の問題ではない — 本 Issue は「OWASP の記述の取り違えがコードのコメントに定着した」ことを是正するものであり、訂正版の ADR に同種の誤引用を書き込めば、同じ失敗を形を変えて再生産することになる。

Issue 本文の参考実測（Node 24 / Apple Silicon）は `SHA-512 @ 210k = 54.2 ms` / `SHA-256 @ 600k = 66.5 ms` で案 A 有利だが、**この数字は Cloudflare の実サーバー（x86）に外挿できない**。SHA-256 は ARM / x86 とも SHA-NI / ARMv8 crypto extension でハードウェア加速されるのに対し、SHA-512 は一般にその加速対象外である。コスト比が反転しうるうえ、そもそも workerd の WebCrypto が `PBKDF2 + SHA-512` を実装しているかも未確認である（ADR-003 は SHA-256 について同じ懸念で一度実測を踏んでいる）。

**さらに、ローカルで測っても同じ理由でこの問いには答えられない。** 開発機は Apple Silicon（ARM）で、しかも M シリーズは ARMv8.2 の FEAT_SHA512 を実装しうるため、ローカル実測は **SHA-512 に系統的に有利な方向へ偏る**。「ローカル workerd で測ったから Apple Silicon の数字より一段近い」は、ISA の問いに関しては一段も近くない。

ここで問題になるのは「実測せずに決められない」ことそのものではなく、**実測値を見た実装者が主観で案を選べてしまうと、この Issue が是正しようとしている「根拠のない数字が定着する」という失敗が形を変えて再発する**ことである。

### Decision

**案の選択を、実測値に対する事前定義の判定ゲートへ委ねる。ただし実測は二段構えにし、比較は x86 でしか取らない。**

- **G-0（疎通）はローカル workerd で取る。** `PBKDF2 + SHA-512` が実装されているかは ISA に依存しないので、ローカルで足りる。**ここで落ちれば CI を待たずに案 B が確定する**という早期打ち切りの価値もある
- **`t_A` / `t_B`（比較）は CI で取る。** `.github/workflows/ci.yml` の `integration` ジョブは `runs-on: ubuntu-latest`（x86_64）で `pnpm test:integration:cf` を走らせるので、プローブ入りのコミットを main 宛の PR に載せるだけで x86 の workerd 実測が得られる。**ワークフロー定義には手を入れない**

**先行実測を取り込み、`G-0` は確定済みとして扱う。** 計画確定時に、steps.md ステップ1 と同じ形のプローブをローカル workerd（Apple Silicon / vitest-pool-workers）で設置・実行・撤去したところ、**`G-0` は通過**（`supported=true`）、`SHA-512 @ 210k` の中央値 45〜47 ms、`SHA-256 @ 600k` の中央値 47〜49 ms（**比 0.97〜0.99**）、`SHA-256 @ 210k` の中央値 16.4 ms（ADR-003 の 16ms と一致）が得られた。これにより (a) G-0 は済み、(b) R-2（workerd の時計が計算中に進まない）は否定され `G-0b` の発火見込みは低い、(c) `SHA-256 @ 210k` の連続性も裏が取れた。

**それでも案 A / 案 B の確定は CI（x86）実測による。** 比が 0.99 と**紙一重**だからである。SHA-NI の有無は SHA-256 側だけを加速するので、x86 では比が 1 を大きく超えうる。0.99 という値は「案 A 有利」を示すというより **`G-1` / `G-2` / G-0b の境界のどこにも十分な余裕が無い**ことを示しており、ここでローカル値を採ると本 ADR が最も避けたいと言っている「測定環境が案を決める」に戻る。先行実測が縮めたのは**疎通と計測可能性の不確実性**であって、**ISA の問い**ではない。

**計測値の回収は「故意に失敗するテスト」で行う。** Vitest 4 の**暗黙の**既定レポーターは通ったテストの `console.log` を出力せず（`--reporter=default` を明示したときとは挙動が違う）、CI ジョブは `run: pnpm test:integration:cf` 固定なのでレポーターフラグを足せない。`ci.yml` / `package.json` / vitest 設定の一時編集は、**恒久設定に一時的な穴を開けて戻し忘れるリスクを構造的に消す**という本計画の方針（プローブの配置をわざわざ `application/**` にしたのと同じ理由）に反するので採らない。代わりに**プローブは全計測の完了後に、測定値を JSON で埋め込んだ `Error` を故意に throw する**。テストの失敗メッセージはどのレポーターでも必ず出力されるので、これが**フラグ不要で、かつローカルと CI で分岐しない唯一の回収チャネル**になる。副作用として、プローブを含むコミットでは `integration` ジョブが赤くなる — **これは想定内であり、計測成功の印である**（Draft PR なのでマージには影響しない）。想定外の赤は `lint-typecheck-unit` のほうで、その切り分けを成立させるために push 前のローカルゲートを必須にしてある（steps.md ステップ1-4）。

ゲートの全文は steps.md ステップ2にあり、要点は次の4段である（行は上から評価し、最初に一致した行で確定する。表の外に追加条件は置かない）。

1. **G-0** — `deriveBits({ hash: "SHA-512", iterations: 210_000 })` が workerd で例外になれば**案 B**
2. **G-0b** — `BATCH` を上限まで上げても中央値が `0` のまま（＝計測不能）なら**案 B**。`0` は「速い」ではない
3. **G-1** — `t_A ≤ 2.0 × t_B` なら**案 A**
4. **G-2** — それ以外（＝ `t_A > 2.0 × t_B`）なら**案 B**

**判定に使うしきい値は `2.0×` の1本だけであり、絶対値の上限は置かない。** 当初は 2 / 3 に `t_A ≤ 100 ms` を併記していたが、これは3つの理由で外した。

- **判定に一度も寄与しない。** plan.md のスコープが「反復回数を OWASP 推奨より下げない」を既に固定しているので、絶対上限に触れたときに取れる行動は「案 B を選ぶ」しかない。ところが上限に触れるのは案 A が重い場合であり、その領域では相対比較（`2.0×`）が既に案 B を選んでいる。**上限が結論を変える入力の組み合わせが存在しない**
- **測定環境が案を決めてしまう。** `100 ms` は Issue の参考実測（Node 24 / Apple Silicon の 54〜67 ms）の 1.5 倍程度として引いた数字なのに、当てる先は `ubuntu-latest` の共有ランナーである。比 `t_A / t_B` については「CI は案 A にとって保守側」が成り立つが、**絶対値についてはそれが成り立たない** — ランナーの遅さは保守性ではなく測定環境のアーティファクトで、しかも本番（Cloudflare の実サーバー）は共有ランナーより速い側なので、方向としても保守的ですらない。本 ADR が最も避けたいと言っている「根拠のない数字が定着する」に形を変えて戻ってしまう
- **相対比較にはこの弱点が無い。** `2.0×` は同一ランの中で取った2つの中央値の比なので、ランナーの速さが約分されて消える

しきい値は実装者が動かしてよい数字ではなく、変えるなら本 ADR を書き直す。根拠は次のとおり。

- **`2.0×`** — **これは価値判断であり、実測から導かれる数字ではない。**「SHA-512 の GPU / ASIC 耐性を買うために、ログイン1回あたりのサーバー CPU コストを最大 2 倍まで許容する」。ゲートが備えているのは SHA-NI が SHA-256 だけを加速して比が反転するケースである（参考実測の比は 0.82 で案 A 有利）。**「同じ予算を SHA-256 の反復回数の上乗せに回すほうが有利になる」を根拠にはしない** — その選択肢は plan.md「含まれないもの」で明示的にスコープ外にしてあり、選べない対案を根拠にしたしきい値は、後から読んだときに理由が成立しない

**`100 ms` は観測項目へ格下げする。** どちらの案でも中央値がこれを超えたら数値を ADR-003 の実測節に記録し、完了報告にも載せる。**ただし案の選択は変えない。** 重さそのものが問題なら別 Issue として起票する。

**ゲートは全域である。** G-0 / G-0b が `t_A` / `t_B` の取れない世界を先に吸収し、そこを抜けた時点で両者は `expect(median).toBeGreaterThan(0)` により正の実数である。任意の正の実数は `t_A ≤ 2.0 × t_B` か否かのどちらか一方に必ず属するので、G-1 / G-2 は網羅かつ排他。除算を使わないので `t_B = 0` による未定義も生じない。**未定義になる入力も、ゲートの外で案を決める経路も無い。**

**反復回数を OWASP 推奨より下げる選択は取らない。** ADR-003 の Decision は代替案として「反復回数を 100,000 に下げる」を挙げていたが、それはセキュリティ上の後退であり、採るなら独立した ADR と Issue が要る。このスコープ固定こそが、上記1つ目の理由（絶対上限が判定に寄与しない）の前提である。

**ノイズが結論を決めていないことの確認もゲートに含める。** 中央値だけでは「線の位置が結論を決めた」のか「ノイズが決めた」のか区別できないので、min / median / max を出力し、**判定を反転させる唯一の線である `2.0×` の近傍**（比が 1.8〜2.2）に落ちた場合は CI を再実行して2回目の中央値で判定し直す。2回で判定が割れたら案 B を採る。**レンジの重なりは発火条件にしない** — 重なるのは `t_A ≈ t_B`（比 ≈ 1.0）のときで判定線から遠く、ノイズが結論を反転させえないためである（min / max は記録としては残す）。G-0 / G-0b で確定した場合は `t_A` / `t_B` が存在しないので、この確認は適用対象外。

`DERIVED_BITS = 256` はどちらの案でも据え置く。PBKDF2 のブロック数は `ceil(dkLen / hLen)` で、32 byte 出力は SHA-256（hLen 32）でも SHA-512（hLen 64）でも 1 ブロックだからである。

### Consequences

- 良い点:
  - 実測結果を見た実装者が、しきい値と数値の突き合わせだけで案を確定できる。「なぜその案なのか」が後から数値で再現できる
  - どちらに転んでも OWASP 推奨を下回らないことがゲートの構造として保証される
  - **ゲートに残る数字が `2.0×` の1本だけになり、それが比であるおかげで、どのランナーで測っても同じ結論が出る。** 実測は環境依存でも、判定は環境非依存である
  - **計測不能（中央値 0）も打ち切り経路もゲートの行になったので、「表がゲートの全文である」という宣言が実際に成り立つ。** 案が決まる経路は G-0 / G-0b / G-1 / G-2 の4つで尽きている
  - ADR-003 が一度踏んだ「workerd で実測してから確定する」手順の再演になっており、判断の作法がリポジトリ内で一貫する
  - **比較が x86 で取られるので、再測定の唯一の目的（SHA-NI で比が反転するか）に実際に答えられる。** `ubuntu-latest` は SHA-256 がハードウェア加速され、SHA-512 の x86 命令拡張（Zen 5 / Arrow Lake 以降）を持つ個体が標準ランナーに含まれる見込みは低い — つまり**案 A にとって保守側（不利側）の条件**であり、そこで案 A が勝つなら Cloudflare の実機でも成立する側に倒れる
- トレードオフ:
  - `2.0×` は連続量に引いた線であり、実測値がその近傍（例: 比が 1.9）に落ちたときに「線の位置が結論を決めた」形になる。それでも主観判断より再現可能性が高いという理由で受け入れる。近傍に落ちた場合の再実行ルールで、ノイズが決めた場合だけは切り分ける
  - **絶対的な重さがゲートから消えたので、「案 A も案 B も本番には重すぎる」という結論をこのゲートは出さない。** これは意図した縮小である（スコープ上その結論から取れる行動が無い）が、その分**重さの判断は観測項目として人間に残る** — 中央値を ADR-003 に記録し、必要なら別 Issue に切り出す、という手順で受け止める
  - 実測が Cloudflare の実サーバーそのものではない（GitHub Actions の共有ランナー上の Miniflare）。**ISA の条件は満たすが、実機の絶対値ではない**。ランナー個体は実行 URL から辿れるので、ADR-003 の実測節に URL を残して追跡可能にする。**判定を比だけにしたのは、この「絶対値は信用できない」という性質と整合させるためでもある**
  - 実測が1周増える（ローカル → PR → CI ログ）。PR はどのみち出すので追加コストは小さいが、**判定の前に必ず CI を1回通す**という手順上の制約が生まれる。加えて PR では `cancel-in-progress` が有効なので、**計測ランを回収し終える前に追加 push をしない**という運用上の制約も付く（steps.md ステップ1-4）
  - workerd は Spectre 緩和として計算中に時計を進めないため、計測そのものが失敗しうる（全値が 0 になる）。バッチ計測と I/O 挿入で回避し、`expect(median).toBeGreaterThan(0)` で自動的に赤くする。**0 を「速い」と読まない**という原則は G-0b としてゲートの行になった。先行実測でローカルの時計は進むことが確認できたので、**G-0b の入力は CI 実測に限る**（ローカルの 0 は環境固有のノイズであって案を確定させる入力ではない）
  - **回収を故意の失敗に載せた結果、「テストが赤い」の意味がジョブごとに分かれた。** `integration` の赤は想定内（計測成功）、`lint-typecheck-unit` の赤は想定外（ローカルゲートの飛ばし）。この切り分けは読み手が覚えておく必要のある約束事であり、**プローブが1コミットの寿命しか持たないことが受け入れの根拠**である。撤去後に `integration` が緑に戻ることを AC-3 の確認に含めて、約束事が残らないようにしてある

## ADR-002: 旧 `pbkdf2-sha256$` 分岐は読み取り専用の枝として残す（案 A の場合）

### Status

Proposed（案 A が確定した場合にのみ有効。案 B なら方式が変わらないので本 ADR は不適用）

### Context

案 A を採ると書き出す識別子が `pbkdf2-sha512` に変わる。既存の `pbkdf2-sha256$` を `parse()` が引き続き読めるようにするかどうかが判断点になる。

- **捨てる場合** — 本番データが存在しないので誰も締め出さない。`parse()` は単一アルゴリズム前提のまま、変更は識別子と `derive()` の `hash` 名だけで済む。**書き手の居ない枝という死にコードを抱え込まない**
- **残す場合** — ADR-003 が謳った「識別子付きエンコードによる無停止移行」の実証になる。開発用 D1 のデータも生き残る。一方、書き手が居ない以上その枝を実際に踏むのはテストだけで、退役させる機構（#18 の rehash-on-login）は本 Issue のスコープ外なので**枝は恒久的に残る**

ADR-003 は「将来 Argon2id へ移行する際は `verify` に分岐を1本足し、rehash-on-login するだけで無停止移行できる」と書いているが、その主張はこれまで一度も実行されていない。

### Decision

**残す。** `parse()` を「読める識別子は複数・書き出す識別子は1つ」という非対称な形にし、`pbkdf2-sha256` は読み取り専用の枝として置く。

- **その非対称は「読み取り経路は部分関数・書き出し経路は全域」としてコードに現れるのが正しい。** 読み取り側は全域関数 `hashFor(algorithm: string): "SHA-256" | "SHA-512" | null`、書き出し側は `ALGORITHM_ID`（保存形式に書く識別子）と `SHIPPED_HASH`（WebCrypto に渡す hash 名）を直に持つ
- **対応表（`Map` / 素の object）は導入しない。** 素の object を `obj[algorithm]` で引くと `constructor` などプロトタイプ由来のキーが truthy を返し、`constructor$1000$…$…` という保存値が未知アルゴリズムの拒否をすり抜ける。`Map` にすればそれは塞げるが、`.get()` の戻り値が `"SHA-256" | "SHA-512" | undefined` になり、**`hash()`（書き出し）がそれを引いた時点で書き出し経路まで部分関数になる** — 起こり得ない `undefined` に `!` / `??` / throw を書くことになり、本 ADR が型で表現したいと言っている非対称がまさにその型から消える（`CLAUDE.md`「Make illegal states unrepresentable at the type level before falling back to runtime checks」）。方式が2つしかない以上、表を持つ理由が無い
- **`ALGORITHM_ID` と `SHIPPED_HASH` のドリフトは無音ではない。** 2つが食い違えば `hash()` が書いた値を `verify()` が別のダイジェストで導出することになり、既存の往復テスト `it("verifies a password it hashed")` が必ず落ちる（本番挙動としても「全ログインが失敗する」という騒がしい壊れ方になる）。したがって検出は**型ピン（`ALGORITHM_ID: typeof DUMMY_PASSWORD_HASH_ALGORITHM_ID`）と往復テストの二層**で成立している。そのうえで意図を読み手に見せるため、対応をリテラルで固定するテストを1件置く（`expect(ALGORITHM_ID).toBe("pbkdf2-sha512")` / `expect(hashFor("pbkdf2-sha512")).toBe("SHA-512")`）。**この2つはテストが直接呼ぶので、`ALGORITHM_ID` と `hashFor` の両方をアダプターから `export` する。** 検査対象がアダプター内部の対応関係である以上、既存の `DEFAULT_PBKDF2_ITERATIONS` が同じ理由で export されている前例に従う。**`expect(hashFor(ALGORITHM_ID)).toBe(SHIPPED_HASH)` の形は採らない** — 両辺を検査対象の定数から組み立てているので2つがそろって別方式へずれた場合に通ってしまい、本計画が別の箇所（統合テストの正規表現）で自ら禁じている自己言及になる
- 旧形式のフィクスチャをハードコードしたリグレッションテストを1件置く。**書き手が居ない形式なので、このテストが旧枝の唯一の生存確認になる**。**フィクスチャは方式を差し替える前に採取する**（差し替え後は旧形式を書き出す経路がコード上から消えるため。steps.md ステップ3-2）
- プロトタイプ由来キーの拒否ケースは、実装上そもそも通らなくなった後も**テスト表に1件残す**。防御の証跡として安く、`parse()` が将来表引きに戻ったときの回帰網になる

「残す」を選ぶ決め手は開発用データの延命ではなく、**ADR-003 の移行戦略が机上の主張のままか、実際に一度通した経路かの差**である。Argon2id への移行は現実の選択肢として残っており、そのときに初めて 2 方式の `parse()` を書くより、本番データが無い今のうちに形を確定させておくほうが安い。

### Consequences

- 良い点:
  - ADR-003 の「識別子付きエンコードによる無停止移行」が主張から実装へ変わる
  - 開発用 D1 に既存データを持つ開発者がログインできなくなる事故が起きない
  - Argon2id 導入時に `parse()` の多方式化がすでに済んでいる
- トレードオフ:
  - **書き手の居ない枝が残る。** 退役の判断は本 Issue のスコープ外だが、**追加の調査を要しない形で退役条件を確定させておく**（下記）
  - `parse()` の分岐が1本増え、拒否ケースのテスト表も1件（プロトタイプ由来キー）増える
  - **旧 SHA-256 の行に対する誤パスワードは、新しいダミー（SHA-512）より計算量が安い。** ログインのタイミング等時化（ADR-026）に残差が生じる。ただしこれは既存 JSDoc が「旧コストで書かれた行では等時化が不完全」として既に自認している残差と**同じ向き**であり、新種のチャネルではない。JSDoc の記述を「コスト」から「コストまたはアルゴリズム」へ広げて明示する。**`.thread/1/adr.md:1221`（ADR-034）が「この限界は JSDoc と `progress.md` の2箇所に書いた」と明記しているので、`.thread/1/progress.md` の残存制約の記述も対で広げる**

**退役条件。** 本 Issue の前提（初回デプロイ前に閉じる。**着手時に確認する** — plan.md「前提」/ steps.md ステップ1「着手前の確認」）が正しいなら、**`pbkdf2-sha256$` 形式の行は本番に一度も存在しない**。したがってこの枝が守っているのは (a) 開発用 D1 のデータ、(b) 将来 Argon2id を足すときの `parse()` の形、の2つだけである。よって次のいずれか早い時点で**削除してよい**（削除に「全ユーザーが一度ログインしたか」の確認は要らない — 対象の行が本番に存在しないため）:

1. 開発用 D1 のデータの寿命が尽きた時点（誰も既存の開発用アカウントでログインしなくなった時点）
2. #18（rehash-on-login）が入った時点

削除そのものは本 Issue のスコープ外だが、条件をここに書いておけば将来の読み手が判断に追加の調査を要しない。**この条件が成立しなくなる唯一のケースは「本 Issue がデプロイ後に持ち越されること」**なので、その場合はここを読み直す。

## ADR-003: ダミーハッシュの識別子を型でピン留めし、salt と digest は流用する

### Status

Proposed

### Context

`loginWithPassword` は、パスワードアカウントが見つからない経路でもダミーハッシュを 1 回 `verify` して応答時間を等時化する（`spec/inventory/adapter.md:53` の ADP-identity-013 / ADR-026）。このダミーは `pbkdf2-sha256$210000$<salt>$<digest>` というアダプターの保存形式のリテラルである。

等時化が成立する条件は2つある。**(i) 出荷ハッシャーがダミーを読めること**（読めなければ `burnVerificationTime` が catch して等時化が無効化される）、**(ii) ダミーの計算量が本番と同じであること**。現在のコードはこのうち反復回数だけを型で強制している。**このピンを決めたのが `.thread/1/adr.md` の ADR-034（`:1192`「ダミーハッシュの反復回数をアダプター既定値と型で結び、握り潰しに警告を足す」）で、本 ADR はその語彙をアルゴリズム識別子へ拡張するもの**である。

```ts
export const DEFAULT_PBKDF2_ITERATIONS: typeof DUMMY_PASSWORD_HASH_ITERATIONS = 210_000;
```

**案 A はまさにこのピンをすり抜ける形の変更である。** 反復回数は 210,000 のまま動かず、アルゴリズムだけが動く。しかも ADR-002 で旧 `pbkdf2-sha256$` 枝を残す決定をしたため、ダミーを取り残しても `parse()` は成功し `verify` も成功する。つまり `burnVerificationTime` の catch も、一度きりの警告ログのラッチも、**どちらも発火しない**。型検査も通り、統合テストも（正規表現を直さなければ）通る。**タイミングオラクルが無音で復活する経路**が開いている。

加えて、アダプター側の JSDoc は「nothing else in the dummy needs regenerating, since `verify` derives at whatever cost the stored value declares」と書いているが、これは**コスト変更でのみ成立する主張**で、アルゴリズム変更では成立しない。

もう一点、ダミーの salt と digest を新方式で作り直すかどうかも決める必要がある。

### Decision

1. **アルゴリズム識別子にも、反復回数と同じ `typeof` ピンを掛ける。** application 層に `DUMMY_PASSWORD_HASH_ALGORITHM_ID = "pbkdf2-sha512"` を置き、アダプター側は `const ALGORITHM_ID: typeof DUMMY_PASSWORD_HASH_ALGORITHM_ID = "pbkdf2-sha512"` と宣言する。片方だけ動かすとコンパイルが通らない
2. **定数の所在は application 層のまま。** アダプターが application を型 import する現在の向きが内向きで正しい。逆向き（application が `ALGORITHM_ID` を adapters から import する）は依存方向違反になる
3. **salt と digest は既存のバイト列を流用する。** 長さは 16 / 32 byte で既に正しく、JSDoc が明言するとおり「誰も一致させるつもりのない任意のバイト列」なので、新方式で真正な導出をやり直しても何も買えない
4. 上記の JSDoc の主張を訂正する（「コストだけが現行であればよい」→「アルゴリズムとコストの2つが現行であればよい」）
5. **案 B の場合、本決定の 1 は不要とする。** 案 B ではアルゴリズムが動かないので、ピンを掛けるべき対象が存在しない。将来アルゴリズムを動かす Issue が来たときに同じ判断を再度行う

### Consequences

- 良い点:
  - 等時化を壊す2つの経路（反復回数の取り残し・アルゴリズムの取り残し）が**どちらも型検査で止まる**
  - 既存のピン（`.thread/1/adr.md` ADR-034）の語彙をそのまま拡張しただけで、読み手が新しい仕掛けを覚える必要がない
  - salt / digest を流用することで、ダミーの「任意のバイト列でよい」という性質が実物として維持される（真正な導出を埋めると、後の読み手が「これは意味のある値だ」と誤解する余地が生まれる）
- トレードオフ:
  - application 層の export が1つ増える。この定数はユースケースのロジックではなく**アダプターとの契約**なので、application に置く理由は依存方向の都合であって責務の帰属ではない。JSDoc でその旨を明記して補う。
    **この写し取り方式には寿命がある。** 今回のピンで application 層が抱えるアダプター実装知識は「保存形式の文字列」「反復回数」「アルゴリズム識別子」の3つになる。**4つ目が要るとき（例: Argon2id のメモリ・並列度パラメータ）にこの方式は破綻する**ので、そのときは `PasswordHasher` 側がダミー材料を供給する形（ポートに読み取り専用の材料を足す、あるいは DI 配線でアダプターからダミーを受け取る）への作り替えを検討する。**本 Issue ではやらない** — ドメインポートの契約変更になり、Issue のスコープを明確に超える
  - ピンは「2つの定数が同じ値であること」しか保証せず、「その値が正しいこと」は保証しない。正しさは単体テストと本 Issue の判定ゲートが担う
  - **案 B を採ると 1 が適用されず、アルゴリズムの取り残しに対する型の防護は無いまま残る。** 案 B ではアルゴリズムが動かないので今回は実害が無いが、次にアルゴリズムを動かすときに同じ落とし穴が待っている。スコープを絞るための意図的な先送りである
