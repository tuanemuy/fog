## 裁定メモ（メインが決めた事項）

1. **`SHIPPED_HASH` を型で結ぶためのリテラルキー表引きは採らない。** ADR-002 の結論（2方式に表は不要）は正しく、`SHIPPED_HASH` と `ALGORITHM_ID` のドリフトは往復テスト4件が必ず赤くすることが変異注入で実証されている。表を導入すれば「表を持たない」と決めた設計をこの PR で覆すことになり、ADR も書き直しになる。**コードは現状維持し、成立していない根拠の文言だけを直す。** 単位1（JSDoc）と単位4（ADR-002 Decision）で**同一文言**を使う:
   > リテラル型をキーにした表なら全域にできるが、方式が2つしかない現状では表を維持するコストが上回る。
2. **ファクトリ引数のピンの穴はテストで塞がない。** 塞ぐ案はいずれも本番強度の実導出を踏むテストを 2→3 件に増やして R-6 と衝突するか、既存のテスト様式から外れるモジュールモックを要する。ADR-003 の Consequences にトレードオフとして1行書いて閉じる。
3. **`.thread/1/adr.md` の当時の記録の扱いは、節の性格で規則を1本化する。** *Context / Decision*（当時の観測・当時の決定）を述べる行は**原文を残し括弧書きで現行値を添える**。*Consequences* など**今も有効な仕組み**を述べる行は本文修正のままにする。R-7 の自己規範（当時の記録を黙って書き換えない）と最も整合し、規則が説明可能な軸で1本になる。
4. **ADR-002 の `.adr/` 昇格はこの時点では行わない。** JSDoc に退役条件を1行書いて閉じる。昇格の判定は Phase 8 の ADR 昇格フェーズで、他のエントリとまとめて記録基準（寿命テスト・波及テスト）にかける。
5. **前提確認は「確認済み」として書いてよい。** 実装エージェントが着手前に `gh api repos/tuanemuy/fog/deployments`（空配列）と `.github/workflows/ci.yml`（デプロイジョブ無し）を確認している。ただし **Cloudflare アカウント側の実状態はこの環境から確認できない**という限界も併記する。実施していない確認を書かせない。
6. **#18 へのコメント投稿はメインが Phase 5 で行う。** リポジトリ外への副作用なので実装エージェントには委ねない。
