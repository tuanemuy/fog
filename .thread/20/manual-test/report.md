## 結論

PBKDF2-HMAC-SHA256 @ 210,000 から **PBKDF2-HMAC-SHA512 @ 210,000** への切り替えが、実機のブラウザ経路で end-to-end に成立していることを確認した。新形式での登録・ログイン、旧形式の読み取り、等時間化の維持、エラー契約のいずれも期待どおり。

## この Issue にとって決定的だった3点

1. **出荷される保存形式が確定した案どおりである**（TC-2）。単体テストは `createPbkdf2PasswordHasher()` の出力を見るだけだが、DI 配線（`serverCloudflare.ts`）を通って D1 に届くところまでは実機でしか通らない。実際の保存値は `pbkdf2-sha512$210000$…` で、salt 16 byte・derived 32 byte。不採用の案 B の値（`600000`）も旧識別子も出現しない。

2. **旧形式の読み取り枝が生きている**（TC-4 / TC-5）。`main` ブランチで作成した `pbkdf2-sha256$210000$…` の行と、単体テストが固定している低コストフィクスチャ `pbkdf2-sha256$1000$…` の**両方**が実装ブランチでログインできた。`hashFor()` の旧枝が実機経路で機能していることの唯一の確認であり、ADR-002 の「読み取り専用の枝として残す」という決定が実際に効いている。

3. **等時間化が無音で死んでいない**（TC-3）。`burnVerificationTime` は例外を握り潰す設計なので、ダミーハッシュが取り残されても UI には何も出ない。唯一の実機シグナルであるサーバーログの警告 `Login timing equalisation is inactive` を全ログ 148 行に対して grep し **0 件**を確認した。さらに「出ないこと」を確かめるテストの弱点を踏まえ、`lsof` でサーバープロセスの stdout/stderr がログファイルを指していることを確認して**ログ経路自体が生きている**ことも裏取りしている。

## スコープ確認

**rehash-on-login の混入なし**（TC-6）。旧形式の行はログイン成功の前後で `password_hash` がバイト単位で同一だった。これは本 Issue が「ハッシュ移行を一切発生させない」という前提で閉じられることの実機での裏付けであり、#18 との境界が守られていることを意味する。

## 既存機能への影響

セッション Cookie（`hmacSessionCodec`）・`/settings` の表示・`useActionState` の pending 表示はいずれも変更なく動作。`/settings` の DOM 全体（68KB）を grep してパスワードハッシュ・salt・derived・反復回数のいずれも露出していないことを確認した。`outbox_events` は登録4件に対して `identity.userRegistered` が4行で整合。`pnpm db:migrate` の再実行は「No migrations to apply!」で冪等（本 Issue がスキーマに触っていないことの確認でもある）。

## 実機で確認できなかったこと

- **本番の CPU 予算（Free 10ms / Paid 既定 30 秒）に対する余裕**。初回本番デプロイが未実施で、`pnpm start` / `pnpm preview` も #40 で起動しないため、ローカルでは測れない。CI（x86_64）実測を `.thread/1/adr.md` の実測節に残すところまでが本 Issue の範囲。
- **タイミング残差の実測**。testing.md「正直な限界」節が「この手順では測れない」と結論づけている。旧形式の行には約 97ms の残差があるが、受容の根拠は残差の小ささではなく「本番に `pbkdf2-sha256$` の行が1行も存在しない」という前提である。
- **確認項目7 の DevTools 計測**。agent-browser は DevTools を開けないため、時刻差とベースライン差分で代替した（差分は中央値 +53ms で、先行実測と同じ桁）。
- **連打による二重送信**。送信中のボタン無効化は確認したが、実際に連打する検証は行っていない。
