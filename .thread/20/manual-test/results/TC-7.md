# TC-7: ログインの体感速度が実用の範囲に収まっている

**結果**: PASS（桁は変わっていない）
**実行時間**: 約 60 秒

対応する受け入れ基準: steps.md ステップ2「観測項目（判定には使わない）」

## 手順の代替について（重要）

テストソースの手順は「DevTools の Network タブでフィルタを `_serverFn` にし、ログイン送信の POST の Time を控える」だが、**agent-browser 経由では DevTools の Network タブを開けない**。そのため担当指示のとおり、**操作前後の時刻差（`date +%s%3N`）による実測で代替**した。

計測区間は「送信ボタンのクリック発行 → `wait --load networkidle` の完了」で、**サーバー関数の往復に加えてクリック配送・クライアント遷移・描画・agent-browser CLI のプロセス起動オーバーヘッド（1計測につき2プロセス分）を含む**。したがって**絶対値はサーバー関数単体の Time より大きい**。

そこで、**パスワードハッシュを一切踏まない同形状の操作**（`/` → ナビの「設定」リンクをクリックして `/settings` へ遷移し networkidle まで待つ）を同じ計測方法でベースラインとして取り、**差分**でハッシュ由来のコストを見た。これが本項目の「桁が変わっていないか」の判断材料である。

## 確認ポイントの結果

- **これは絶対値の合否判定ではない** — 上記のとおり「桁が変わっていないか」だけを見た。差分 50〜70 ms は先行実測の 45〜47 ms と同じ桁であり、桁の変化はない
- **pending 表示が数秒間残るようなことがない** — TC-1 で捕捉した `登録中…` / `ログイン中…` は、上記の計測どおり 1 秒未満で解消している
- **ローカルで速いことは本番の CPU 予算内に収まる証明にはならない** — 本項目は本番デプロイ未実施のため実機確認できない。ADR-003 の実測節に CI 数値を残すところまでが範囲、という testing.md の記述のとおり
- **桁違いに遅い（1秒級）場合の疑い**（`derive()` の hash 名が固定されていない / 反復回数の取り違え）— 該当しない。TC-2 で保存値も `pbkdf2-sha512$210000$` を確認済み
