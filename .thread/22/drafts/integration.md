# ステップ 9〜16 の統合 — 下書き

8 つの並列ステップをまたぐ受け渡しと、担当外への変更要望のうちこの Issue の
スコープに入るものを処理した際の判断。番号は付けない（adr.md へ統合する担当が
付ける）。

## クラス名が CSS を生成しないことを、走査テストで落とす

### Context

ADR-018 は「値 0 は `p-[0]` のように任意値で書く」と決め、そのトレードオフとして
「値 0 を `p-0` と書いても落ちるテストは無い」を明記していた。実際に
`components/ui` の 6 か所ほかを含む 14 ファイルが `min-w-0` と書いていて、
`--spacing` を消した既定テーマ（ADR-001）では何も生成せず、flex の子の
`min-width: 0` が効かないまま残っていた（ステップ 11・13 が指摘）。Issue の
「値はトークンからだけ選ぶ」は、生の値を禁じる側だけがテストで守られていて、
「トークンに無い名前を書くと黙って消える」側が空いていた。

### Decision

- `lint/designTokens.test.ts` に「クラスリストの全トークンが CSS を生成する」
  検査を足す。クラスリストは走査の候補からではなくソースの文字列リテラルから
  読む（走査は散文の単語も候補にするため）: 空白区切りの全トークンが候補の形を
  していて、うち 1 つ以上が実際に CSS を生成する文字列を、クラスリストとみなす
- 生成の有無は Tailwind に聞く。`@layer utilities` に現れた候補は生成済みとし、
  現れなかったものだけ候補 1 つでコンパイルして、候補ゼロの出力と比べる
- 例外は Tailwind のマーカークラス（`group` / `peer`）だけ。宣言を持たないのが
  その役目である
- 見つかった `min-w-0` は全て `min-w-[0]` にする

### Consequences

- 良い点: ADR-018 が「落ちるテストは無い」と書いた穴が塞がる。`p-0`・`gap-0`・
  `m-0` など、既定スケールに頼って消えるユーティリティも同じ検査で捕まる
- トレードオフ: 検査が届かないのは、トークンが 1 つしかないクラス文字列
  （`className="p-0"` 単体）と、実行時に組み立てるクラス名（どちらにせよ
  Tailwind も見ない）。テンプレートリテラルは `${…}` で切れた両端のトークンを
  落とすので、補間に隣接する半端なトークンは検査されない

## `h1: "sheet"` のルートは、本体が無い間もフレームが見出しを持つ

### Context

ADR-023 は、シート内の固有名を `h1` にするルートで、ヘッダーの英語名を見出しで
ないラベルに落とすと決めた。ステップ 12・13 が、その結果として読み込み中・
見つからない・ルートエラーの間はページに `h1` が無くなることを指摘した
（ステップ 11 も同じ）。ADR-029 は認証シートについて同じ問題を
`components/ui/PageHeading` のコンテキスト（`"frame"` / `"screen"`）で解いて
いるが、アプリシェルは常に `"frame"` を配っていた。

### Decision

- `AppShell` は、ルートの宣言が `h1: "sheet"` のときシートの中を `"screen"` に
  する。画面の代わりに描かれる `RouteError` と `NotFound` は、既にこれを読んで
  一文を `h1` にする
- 読み込み中は `components/ui/LoadingRegion` が持つ。9 か所にコピーされていた
  `role="status"` ＋ `aria-busy` ＋ sr-only の「読み込み中」を 1 実装にまとめ、
  `asPageHeading` を渡されたときだけラベルを `h1` にする。渡すのは
  `h1: "sheet"` の 3 ルートのスケルトン（トピック詳細・ドキュメント閲覧・
  ドキュメント履歴）
- 画面自身の「見つからない」（`KnowledgeNotFound`）は props で受ける。これは
  ストリームされる RSC の木で描かれ、クライアント側のコンテキストが届かない

### Consequences

- 良い点: `h1: "sheet"` の 3 ルートは、どの状態でも `h1` を 1 つ持つ。読み込み中の
  見出しは「読み込み中」で、届いていない固有名を仮に名乗らない
- トレードオフ: スケルトンが `h1` を持つかどうかは、ルートの宣言と手で揃える
  必要がある（型では結べない）。認証シートのスケルトンは、その上に
  `AuthSheetTitle` が既に `h1` を描いているので渡さない

## `components/ui` に足すのは、複数の担当が近似で組んだ形だけにする

### Context

各ステップが `components/ui` への追加を要望した。素の `href` を受けるボタン形の
リンク（ステップ 9 の SSO・ステップ 16 の SSO 連携）、子要素を置けるダイアログ
（ステップ 15 の復元先選択）、線と間隔を持つセクション（ステップ 11。ステップ 9
も同じ文字列を持つ）、バッジ（ステップ 14）、スピナー行（ステップ 14）、行全体の
トグル（ステップ 13）、作成導線の行（ステップ 11）、遷移しない行（ステップ 11）。

### Decision

追加の基準は「2 つ以上の担当が同じ形を別々に組んだか」とする。

- `ButtonAnchor` — 素の `href` にボタンの段を当てる。`ButtonLink` の中に隠れて
  いた無名のコンポーネントを出し、`SsoButtons`（`buttonClassName` の直接利用）と
  設定の「連携を追加」（GET フォーム＋`Button` の近似）を差し替える。`ButtonLink`
  はこれを `createLink` で包んだものになる
- `Dialog` — `<dialog>`・カード・見出し・一文と、ダイアログ固有の 2 つのボタン
  （`DialogDangerButton` / `DialogCancelButton`）と `DialogActions`。
  `ConfirmDialog` はこれに質問を載せたものになり、`RestoreDestinationDialog` は
  同じ枠の中に自分のフォームを置く。取消の見た目も 1 つになる
- `SheetSection` と `SHEET_SECTION_CLASS` — `mt-section border-t
  border-neutral-100 pt-lg` が 6 か所に写されていた。ラベル付きの区画は
  `SheetSection`（`components/knowledge/KnowledgeSection` を移設）、自分で要素を
  組む区画（設定・認証シート・履歴・ドキュメント）は定数を読む
- `LoadingRegion` — 上記のとおり

足さないもの（1 つの持ち場でしか使わないか、統一がデザインの判断になるもの）:

- **バッジ** — 検索チップの「完了」・トピックの「完了済み」・ゴミ箱の種別ピル・
  履歴の「比較元 / 比較先」は、地・文字色・語（「完了」と「完了済み」）が画面ごとに
  違う。1 つの形に寄せるのはモックの決め直しであって、機械的な統合ではない
- **スピナー行** — 同上。search.html は timeline.html と同形と書いているが、
  ゴミ箱・エクスポートの進行中表示は行の中にあり、形が違う
- **行全体のトグル（`RowToggle`）** — 使うのは履歴の版の行だけ
- **作成導線の行（`AddRow`）** — 使うのはトピック一覧とトピック詳細だけで、
  どちらも `components/topics` にある
- **遷移しない行** — `knowledge/OriginRow` の削除済み行と
  `documents/SourceMemoLine` が同じ形を別々に持つ。中身（時刻＋2 行の本文）まで
  含めて 1 つにするかは、出典の行の設計の判断なので followups に送る
- **テキストリンク（`FormLink`）** — 認証の 2 画面だけが使うので
  `components/auth` に残す

`components/auth/AuthSheetDescription` は `components/layout/AuthSheet` へ移す。
枠の部品であり、ルート（リセット完了）からも使われている。

### Consequences

- 良い点: 同じ役割の見た目が 1 か所から来る。近似で組まれた枠（復元先ダイアログ）
  と、プリミティブのクラス関数の直接利用（SSO ボタン）が無くなる
- トレードオフ: 足さなかった 5 つは、画面ごとの定義のまま残る。どれも
  followups.md に理由つきで置いた

## 画面をまたいで共有する文言と書式は、モックに合わせて 1 つにする

### Context

ステップ 9 と 16 が、`presentation/errorDisplay.ts` の 3 つの文言と
`presentation/time.ts` の日付書式をモックとの差として挙げ、共有物なので
画面側では直さなかった。ステップ 11・15 は、再試行の文言が「リトライ」と
「再試行」に割れることを挙げ、持ち場で分けるか片方に寄せるかを統合に委ねた。
ステップ 16 は、設定画面用の `Intl.DateTimeFormat` を 2 つ画面の中に置いていた。

### Decision

- `errorDisplay.ts`: 弱いパスワードを「8文字以上で入力してください」、メール形式を
  「有効なメールアドレスを入力してください」、試行制限を「試行が制限されています。
  しばらくしてからお試しください」にする（いずれもモックの語）
- `time.ts`: `formatDateTime` を `2026/07/20 12:42` から `2026年7月20日 12:42` に
  改め、曜日を持たない `formatDate`（`2026年7月20日`）を足す。設定画面が持って
  いた 2 つの書式はこれに置き換わる。`formatDay`（曜日つき）はタイムラインの
  日付見出し専用のまま残す。年を落とす書式（モックの「7月20日 12:30」）は足さない:
  どの年かを省けるかは描画時の現在時刻に依る判断で、SSR とハイドレーションで
  食い違う
- 再試行の文言は持ち場で決める。行（`RowError`）は「リトライ」、面（フォームの
  先頭・コンポーザー・`InlineAlert`・ルートエラー）は「再試行」。規則は
  `RowError` の props の JSDoc に書き、外れていた 1 か所（タイムラインの削除失敗）を
  直した
- `ConfirmDialog` の保留中の文言は、既定の `${confirmLabel}中…` のほかに
  `pendingLabel` を受ける。「戻す中…」「空にする中…」になる 2 か所が渡す

### Consequences

- 良い点: 同じ失敗が画面によって違う文で出ることが無くなる。日付の書式が 1 か所で
  決まる
- トレードオフ: 「リトライ」と「再試行」は同じ画面に並びうる（ゴミ箱・設定）。
  これはモックがそう描き分けている形で、持ち場の違いとして保つ
