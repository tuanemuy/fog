# ADR — Issue #22: Web 実装がデザイン（トークン・基準形・ロゴ）を反映していない

## ADR-001: トークンの消費経路を Tailwind v4 のユーティリティに一本化する

### Context
`theme.css` は全トークンを Tailwind の `@theme` に写しているが、ユーティリティを使うのは 3 ファイルだけで、残りの約 490 箇所はグローバルな `fog-*` クラスである。候補は (a) ユーティリティに一本化する、(b) トークンを `var()` で参照する素の CSS クラスに一本化する、(c) 両方を残す、(d) CSS Modules の 4 つだった。当初は、モックの兄弟セレクタを 1:1 に写せて値の検査が CSS の走査 1 本で済む (b) を採ったが、ユーザー判断で (a) に改めた。(b) には、グローバルなセレクタから画面がプリミティブを上書きできる穴が残る。(d) はその穴を閉じるが、消費経路が 3 つ目になる。

### Decision
(a) を採る。
- スタイルは、プリミティブ・シェル・画面コンポーネントの TSX にユーティリティで書く。`fog-*` クラスと、`app.css` および画面ごとの CSS は、全画面の載せ替えが済んだ時点で撤去する
- `styles/` に残すのは `tokens.css`（tokens.md の写し、ADR-003）、`theme.css`（投影）、`index.css`（入口・base 層・ADR-012 の定義）の 3 つ
- `theme.css` は既定のテーマを `--*: initial` で丸ごと消し、`tokens.css` のトークンを Tailwind の名前空間へ `var()` で写す。トークンの値は持たず、直接書くのは tokens.md の表にあるブレークポイントと ADR-012 の `@keyframes` だけにする。トークンに無い既定スケール（`p-4`・`bg-red-500`・`rounded-xl` など）は生成されない
- 主経路はトークン名のユーティリティ（`p-md`・`text-sm`・`rounded-lg`）とする。`(--token)` の参照は、名前空間に載らないトークン（複合値の `--pad-btn`・`--border-input` など）に限る
- 値を持たない構造のユーティリティ（`flex`・`sr-only` など）はそのまま使う

### Consequences
- 良い点: 見た目がそのコンポーネントの TSX に閉じ、グローバルなセレクタから別の要素を上書きする経路が無くなる。CLAUDE.md の Frontend 節（Tailwind v4）と実態が一致する
- トレードオフ: 値の検査が CSS だけでは済まず、className にも要る（ADR-002）。リセット後の既定スケールの名前はエラーにならず、何も生成しない（見た目の欠落はブラウザ確認で見つける）。モックの素の CSS は、ユーティリティへの写し替えになる

## ADR-002: 「値はトークンからだけ選ぶ」をリポジトリ走査のユニットテストで担保する

### Context
候補は Biome の GritQL プラグインと、リポジトリを走査するユニットテストの 2 つだった。守りたい性質には、ファイルをまたぐ関係（tokens.md と `tokens.css` の一致、参照したトークンが定義済みか）が含まれる。ADR-001 でユーティリティに一本化したので、生の値は手書きの CSS だけでなく、className の任意値（`p-[13px]`・`text-[#fff]`）と、テーマを通らない裸の数値（`border-3`・`duration-300`）からも入る。

### Decision
`lint/banList.test.ts` と同じ走査テスト（node）を `lint/` に置き、次を検査する。
- `tokens.css` の名前と値が tokens.md と一致する。`var()` のフォールバックが無く、参照したトークン（`theme.css` の投影を含む）がすべて定義されている
- 手書きの CSS と、Tailwind がアプリのソースから生成したユーティリティの CSS を、同じ検査にかける。`tokens.css` の外に、生の色も、許容リスト外の生の値（長さ・書体・文字サイズ・ウェイト・行間・字間・角丸・影・トランジション）も無い。任意値と裸の数値は、生成された CSS の段で捕まる。Tailwind のリセット（preflight）の出力は対象外
- `(--token)` の参照が、名前空間に写したトークンを指していない（ADR-001 の主経路）
- 許容リストは、tokens.md 自身が生の値を認めているものに限る。`0`、ヘアラインの `1px`、フォーカスリングの `±2px`、ブレークポイント、相対単位（`%`・ビューポート単位・`fr`）、「余白の向き」の例外にある `em` の余白、`@keyframes`
- プリミティブを上書きする経路の検査（ADR-004）も同じテストが持つ

### Consequences
- 良い点: 手書きと生成の両経路を、1 つの検査と 1 つの許容リストで守れる。失敗メッセージにトークン名を出せる。Tailwind が拾えない動的な className はそもそも CSS にならないので、検査の見落としが画面に届く値の見落としにならない
- トレードオフ: エディタ上の即時の指摘は無い。モック HTML と TSX の `style` 属性は対象外で、この限界は docs/test.md に一文で書く

## ADR-003: `tokens.css` は tokens.md の写しに限り、モックの生の値は 1 つずつ選別する

### Context
`tokens.css` には tokens.md に無いトークンがある（`--gradient-page`・`--duration-*`・`--sheet-w*`・`--nav-sheet-inset`・`--pad-input`・`--size-*`・`--skeleton-*`・`--space-safe-*` など）。モックも、トークンに無い生の寸法を使う。その多くは実測の中間値で（timeline.html だけで `gap` の 2 / 6 / 10 / 18px、`border-radius: 3px` など）、SVG のアイコン寸法も 18 / 15 / 14 / 10px と tokens.md の 4 段の外にある。design/index.md は、生の値を (a) 既存トークンへ寄せるべき思いつきと、(b) トークン化すべき新しい役割に分けることを求めている。

### Decision
tokens.md を唯一の出所とし、`tokens.css` はそのコードブロックの写しに限る（ADR-002 の一致検査で固定する）。
- モックの生の値と `tokens.css` だけにあるトークンは、1 つずつ (a) 既存トークンへ寄せる / (b) 新しい役割として役割名のトークンを tokens.md に足す、に選別する。どちらでもないトークンは消す
- 段数が閉じたスケール（アイコン 4 段・影 3 段・トランジション 2 種）には段を足さず、(a) だけにする
- 選別の結果（どの値をどのトークンに寄せたか、なぜ新しい役割か）は tokens.md 側の判断として残す
- 追加はトークン層のステップ 1 回にまとめ、画面ステップはトークンを消費するだけにする
- 「モックと同形」は構造（要素の並び・役割・余白の段）の一致で、px の一致ではない

### Consequences
- 良い点: tokens.md の規則がそのまま実装の規則になり、閉じたスケールが崩れない
- トレードオフ: 寄せた箇所は、モックと px 単位では一致しない。モック HTML は書き換えないので、モックと tokens.md の乖離が残る（起票は Phase 5 で判断する）

## ADR-004: プリミティブは基準形の 1 役割 1 コンポーネントとし、見た目の変種は閉じた union で受ける

### Context
候補は、汎用コンポーネントに `className` を渡して画面が見た目を足す形、`as` による多相、役割ごとに分けたコンポーネントの 3 つだった。ユーティリティに一本化すると（ADR-001）、`className` を受けるだけで画面がどの値でも上書きできる。

### Decision
- 基準形の 1 役割を 1 コンポーネントとし、`components/ui/<Name>/` に置く
- 段・トーンは文字列リテラルの union の props で受け、`className` と `style` は受けない。配置は画面側のラッパー要素が持つ
- ボタンとリンクは別のコンポーネントに分ける。リンク版は TanStack Router の `Link` の型付き props をそのまま受ける
- `IconButton` はアクセシブルネームを必須の props にし、`Icon` のアイコン名は閉じた集合にする
- 型が届かない経路は、走査テスト（ADR-002）で塞ぐ。`components/ui` の外で、ほかの要素を狙うバリアント（`*:`・`**:`・子孫や子を狙う任意バリアント）を使うと落ちる。兄弟を狙うバリアントは、ADR-012 の上余白だけを通す。`styles/` の CSS にクラスセレクタの規則があると落ちる
- プリミティブは、継承するプロパティ（色・書体・文字サイズ・行間）を自分で指定する
- `components/ui` を Biome の lint 対象に戻す

### Consequences
- 良い点: `className` / `style` による再定義は型で、ラッパーのバリアントと CSS のセレクタによる再定義は走査テストで塞がる。ラベルの無いアイコンボタンは書けない
- トレードオフ: 継承するプロパティの指定漏れは検出できず、ラッパーの色や文字サイズがプリミティブに漏れ込みうる。この限界は docs/test.md に一文で書く。基準形に無い見た目が要るときは、プリミティブに段を足す改修になる（意図どおり）

## ADR-005: スケルトンは実 DOM に被せる `Sk` で組み、アニメーションを持たない

### Context
現状は汎用の `Skeleton` バー（`animate-pulse`）を並べて形を真似ている。モックは実 DOM の要素の中で文字を透明にして同じ行高を保つ形（`.sk`）で、読み込み後はそのまま置き換わる。

### Decision
- 各画面のスケルトンは、実画面と同じプリミティブ・同じ DOM 構造で組み、文字だけを `Sk` で包む
- 領域全体に `aria-busy` と読み込み中のラベルを 1 つ付け、中の操作要素は操作不能な形で描く
- 汎用の `Skeleton` バーとアニメーションは撤去する。ルートの pending も `Sk` で組む

### Consequences
- 良い点: 行高と余白が実画面と同じ定義から来るので、差し替えでずれない
- トレードオフ: プリミティブの DOM を変えると、スケルトンの形も一緒に変わる（同じ定義を使うので、ずれではなく追従になる）

## ADR-006: ヘッダーはルートの宣言から AppShell が描き、データに依存する操作はスロットへ差し込む

### Context
現状はパス名からタイトルを引く表を AppShell が持つ。ヘッダーの操作には、画面のデータや状態に依存するものがある。ドキュメントの削除（topicId が要る）、編集画面の保存（フォームの状態）、タイムラインの絞り込み・日付移動（ボードの状態）である。ローダーは RSC の promise しか返さないので、ルートの段では値が無い。候補は 2 つあった。(a) 画面がヘッダーとシートを丸ごと描く、(b) シェルが描き、操作だけを画面が差し込む。

### Decision
(b) を採る。
- ヘッダーの種類は、ルートの `staticData` に型付きで宣言する。上位はタイトル（sr-only の `h1`）、戻る付きは対象の英語名と戻り先の既定値を持つ。`AppShell` は一番深いマッチの宣言から `PageHeader` を描く
- データや状態に依存する操作は、それを持つ島がヘッダーの操作スロットへポータルで差し込む。ポータルはマウント後に張る
- 戻るボタンは、アプリ内の履歴があれば戻り、無ければ宣言された既定の戻り先へ遷移する

### Consequences
- 良い点: ヘッダーはフォールバック・エラー・404 の間も同じ DOM のまま即座に出る。スクロールコンテナとナビシートの持ち主も 1 つで済む
- トレードオフ: 差し込む操作は SSR の HTML に含まれず、ハイドレーション後に出る。直リンクで開いたドキュメントの戻り先はトピック一覧になる（トピック id を静的に持てないため）

## ADR-007: モバイルのナビシートは、ネイティブの `<dialog>` をボトムシートとして描く

### Context
モックは、オーバーレイの `button` と固定配置の `nav` を JS で出し入れする静的なデモである。Issue は `<dialog>` であることを乖離として挙げているが、合意 1・2 が求めるのは見た目と開き方（メニューから開く、ハンドル付きの白いカード）である。

### Decision
要素は `<dialog>` の `showModal()` のまま保ち、モックのボトムシートの形で描く。
- ハンドル・`--color-bg-card`・`--shadow-lg`・上辺の `--radius-lg`・シートと同じ横フレーム
- オーバーレイは `::backdrop`（`--color-overlay`）で描き、押すと閉じる
- 開閉のトランジションは、トークンの 2 種だけを使う

### Consequences
- 良い点: フォーカスの閉じ込め・Esc・背景の不活性化・最上位レイヤーを、ブラウザの実装に任せられる
- トレードオフ: 開閉のトランジションは、`<dialog>` の表示切り替えに追従する CSS に頼る。非対応のブラウザではトランジションなしで開閉する

## ADR-008: 認証シート系は pathless レイアウト `_sheet` に集め、認証済みの 2 画面は入れ子のガードに置く

### Context
AI クライアント認可とパスワードリセット完了は、どちらもセッションを要する。そのため今は `_app`（ガード＋AppShell）の下にある。デザインでは、どちらもナビの無い単体の認証シートである。ログイン・登録・パスワードリセットは、各フォームが自前の枠で描いている。

### Decision
- フレームはレイアウトルートが決める、を規則にする。`_app`（AppShell）の隣に `_sheet`（AuthSheet）を置き、認証シートの 5 画面をその下に移す
- 認証済みの 2 画面は、`_sheet` の中の入れ子の pathless ガードの下に置く
- ガードの本体は presentation のヘルパーに出し、`_app` と共有する。`readAuthStateFn` を通すので、`no-store` が付く性質もそのまま保たれる
- URL は変えない

### Consequences
- 良い点: 画面がどの枠に出るかがルートツリーだけで読める。ガードもレイアウト単位のまま保てる
- トレードオフ: 5 ルートのファイル移動で、ルート ID と `routeTree.gen.ts` が変わる

---

## ADR-009: ルートエラーと 404 は既定コンポーネントに一本化し、レイアウトルートには枠つきの境界を明示する

### Context
`_app` 配下の 12 ルートが、同じ「読み込めませんでした」ブロックをそれぞれインラインで持っている。`__root` のエラーと 404 は英語の素の見出しである。合意 3 で、基準形を「空状態の一文＋操作 1 つ」の組み合わせとして定義した。既定のエラーコンポーネントを置くと、`errorComponent` を持たないレイアウトルートにも境界ができる。`_app` の `beforeLoad`（`readAuthStateFn`）が失敗すると、エラーは `_app` の境界で捕まり、AppShell も AuthSheet も無い `__root` の Outlet に直接描かれる。

### Decision
- ルーターの `defaultErrorComponent` / `defaultNotFoundComponent` に基準形のエラー表示と 404 を置き、ルートごとの `errorComponent` を消す
- 子ルートのエラーは親のレイアウトの Outlet の中に出るので、表示はそのフレーム（アプリシートか認証シート）に収まる。これは子ルートに限る
- `__root` 直下のレイアウトルート（`_app`・`_sheet`）には、AuthSheet で包んだ `errorComponent` を明示する。ガードや描画が失敗しても、自分のフレームを描けないまま裸で出ることが無い。`__root` 自身のエラーと未知の URL も AuthSheet の枠で出す
- 入れ子のガードは `_sheet` の Outlet の中で失敗するので、既定のままで認証シートに収まる
- 再試行は、ローダーの読み直しとエラー境界のリセットを行う。画面内の「見つからない」も同じ基準形を使う

### Consequences
- 良い点: エラー表示が 1 実装になり、ルートを足しても付け忘れが起きない。どの段で失敗しても、フレームの無い表示にならない
- トレードオフ: ログイン済みでも `_app` 自身が失敗すると、ナビの無い認証シートの枠で出る。ルート固有のエラー文言は持てない（要るなら、そのルートだけ `errorComponent` を足す）

## ADR-010: 操作の成功と一度きりの通知はフレームがホストするトーストで出し、トーストは操作を持たない

### Context
成功は、各画面のローカル状態によるインライン表示で出ている（`fog-notice`、ゴミ箱の `notice` など）。design/index.md は、成功を消えるトースト、エラーを項目に帰属するインライン表示とする。既存の通知には、成功と部分失敗が混ざるもの（AI 接続の一括失効の、失効した件数と競合で失効できなかった件数）、操作を含むもの（ゴミ箱の復元成功の「タイムラインで見る」）、成功ではない知らせがある。成功ではない知らせは 2 種類ある。画面にいる間ずっと成り立ち、読み返して行動するもの（リセットメール送信後の案内）と、遷移の結果を一度だけ知らせるもの（指定メモが見つからない旨。P-04 は通知して通常のタイムラインへフォールバックする）である。後者は対象のメモが存在しないので付け先の項目が無く、画面に残すと閉じる操作が要る。数秒で消える表示に操作を置くと WCAG 2.2.1 に反する。`spec/pages/index.md` の P-13 は成功を項目ごとに表示するとしている。トーストは、出した要素がアンマウントされた後も残る必要がある。

### Decision
- ホスト（`role="status"` の領域と自動消去）は `AppShell` と `AuthSheet` が持ち、画面はフックで文言を渡すだけにする
- トーストは文言だけを持ち、操作を持たない
- 既存の通知は 5 つに分けて扱う。成功ではない知らせを分ける軸は、持続する状態か一度きりの知らせかである
  - 成功だけのもの → トーストにする
  - 成功と部分失敗の混在 → 分割する。成功の部分はトースト、失敗の部分（件数と再試行の案内）は項目に帰属するインラインに残す
  - 操作を含む成功 → 操作を撤去してトーストにする。ゴミ箱の「タイムラインで見る」は撤去する（ユーザー判断）
  - 付け先の項目が無い一度きりの通知（例: 指定メモ不在）→ 操作を持たないトーストにする。画面は通常の表示にフォールバックしているので、読み逃しても失う情報は無い
  - 画面に持続する状態の説明（その画面にいる間ずっと成り立つもの。例: リセットメール送信後の案内）→ `InlineAlert` のまま残す
- P-13 の「各フォームの保存中・エラー・成功を項目ごとに表示」を、成功はトースト、保存中とエラーは項目ごと、に改める

### Consequences
- 良い点: 出した側の寿命に依存せず、失敗の情報は数秒で消えない。トーストの位置と形が 1 つに決まる
- トレードオフ: 復元したメモへの近道が無くなる（メモは元の位置に戻るので、タイムラインから辿れる）。DOM テストでトーストを確かめるには、ホストを含めて描く必要がある

## ADR-011: コンポーザーは、改行で伸びる複数行の入力をピルの見た目のまま持つ

### Context
モックのコンポーザーは `<input type="text">` の 1 行ピルである。一方で、メモは Markdown のリストを含む複数行を投稿でき、DOM テストもそれを押さえている。ユーザー判断で、改行でスムーズに複数行へ伸び、複数行のときも美しく、ピルの見た目を保つ形にする。

### Decision
- 入力要素は複数行のまま保ち、高さを内容に合わせて自動で伸ばす。改行ごとに段差なく伸び、最大高さを超えたら中でスクロールする
- 1 行のときは、モックのアイコン付きピルと同形にする（左端に「メモを追加」のアイコンの送信ボタン）
- 複数行のときも、角丸は 1 行時の半径のまま保ち（縦に伸びても角が楕円に歪まない）、アイコンは入力の下端に揃える。最大高さ・角丸・アイコン位置の最終形は、デザインゲートで複数行の状態のモックを描いて確定する
- モックにある「音声で入力」は、spec に機能が無いので置かない

### Consequences
- 良い点: 投稿できる内容を変えずに基準形へ載せられ、長い入力でも形が崩れない
- トレードオフ: 複数行の見た目にはモックが無く、デザインゲートでの作図が要る。CSS だけで高さを内容に合わせられないブラウザでは、入力ごとの高さ合わせに頼る

## ADR-012: ユーティリティで書けない指定は、名前付きのバリアントと組み込みのバリアントで書き、クラスの規則は書かない

### Context
モックと tokens.md は、素の CSS でしか書けないように見える指定を使う。ラベルの次の要素に上余白を付ける兄弟セレクタ（tokens.md「余白の向き」の `.ラベル + *`）、`:has()`、`@media (hover: hover)`、`<dialog>` の `::backdrop` と開閉、Markdown 本文の要素ごとの組版（`em` の余白を含む）、スピナーの `@keyframes`、`body` の地と `prefers-reduced-motion` である。書き方の候補は、任意バリアント・`@utility`・`@custom-variant`・`@layer components` だった。

### Decision
CSS にクラスセレクタの規則は書かない（`@layer components` も使わない）。それぞれ次で書く。
- 「余白の向き」の兄弟セレクタ: `index.css` の `@custom-variant` で名前を付けた「次の兄弟」バリアントを、ラベル側に上余白のユーティリティと組で書く。`[&+*]:` の直書きはしない
- `:has()`・ホバー・`::backdrop`・`<dialog>` の開閉: Tailwind 組み込みのバリアント（`has-[]`・`hover`（v4 はホバーできる端末に限る）・`backdrop`・`open`・`starting`）
- Markdown 本文: 描画の要素対応表で、各要素にユーティリティを付ける。子孫セレクタは使わない。メモとドキュメントの組版の差は、プリミティブの段で持つ
- `@keyframes` とアニメーション: `theme.css` の `@theme` の中に置く
- `html` / `body` の地と `prefers-reduced-motion`: `index.css` の `@layer base` に、要素セレクタだけで書く

### Consequences
- 良い点: `styles/` の CSS からクラスセレクタが無くなり、「CSS からプリミティブを上書きしない」を走査テストで守れる（ADR-004）
- トレードオフ: ラベルの次の要素の上余白は、ラベルの側に書くので、次の要素の定義からは見えない（tokens.md の記法と同じ向き）

## ADR-013: 旧 CSS は、生の長さなどの検査だけを明示の対象外リストで外し、ステップ 17 で外す

### Context
ADR-002 の走査テストをステップ 2・3 で入れると、`fog-*` の旧 CSS（`app.css` と画面ごとの 5 ファイル）が抱える生の長さ（約 150 行）で落ちる。steps.md は、手書き CSS の生の値の検査をステップ 17 に置いている。候補は (a) 旧 CSS の生の値を今トークンに置き換える、(b) 旧 CSS のファイルを明示の対象外リストに入れ、ステップ 17 で外す、の 2 つだった。旧 CSS はステップ 17 でファイルごと消える。

### Decision
(b) を採る。
- 対象外にするのは、生の長さ・時間・ウェイト・行間・書体などの検査だけにする。生の色・`var()` のフォールバック・未定義の参照・存在しない ADR の引用は、旧 CSS にも今から効かせる（ステップ 2 でゼロにした）
- リストはテストの定数に置き、Issue #22 のステップ 17 を参照する。各項目は、ファイルが存在し、`index.css` から読み込まれ、まだ生の値を持つ間だけ有効で、どれかが崩れるとテストが落ちる
- リストが空でない間は、`it.todo` がテストの実行ごとに対象外のファイル名を出す

### Consequences
- 良い点: 消えるファイルを書き換えない。旧 CSS に新しい色や未定義の参照が入る経路は、今から塞がる。消し忘れた項目は残れない
- トレードオフ: ステップ 17 までは、旧 CSS に生の長さを足してもテストは落ちない（画面ステップは `styles/` を触らないので、足す経路は無い）

## ADR-014: 許容リストの読み方と、トランジションのトークンの成分化

### Context
ADR-002 の許容リストは、tokens.md が認めるものに限る。モックと実装には、リストの語だけでは扱いが決まらない値がある。行数で数える高さ（`1lh`・`6lh`。コンポーザーの伸びる高さ、アイコンを文字の 1 行目に揃える箱）、スケルトンの透明な文字の `transparent`、`sr-only` の `margin: -1px`、角度（`rotate(90deg)`）、`calc` の係数や `z-index` などの単位の無い数である。また、tokens.md のトランジションは shorthand（`0.15s ease`）だけで、Tailwind の `transition-*` と `duration-*` は持続時間とイージングを別々に読む。`theme.css` は値を持てない（ADR-001）ので、成分のトークンが要る。

### Decision
- `lh` は相対単位として認める。1 行の高さは行間トークンから決まり、px を持たない
- `transparent`・`currentColor`・`none`・CSS 全体キーワードは、値を選ばないので生の値としない
- ヘアラインは `±1px`、フォーカスリングの `±2px` は `outline` と `outline-offset` だけに認める。`em` は `margin` だけ
- ADR-002 の区分（色・長さ・書体・文字サイズ・ウェイト・行間・字間・角丸・影・トランジション）に入らない角度と単位の無い倍率は、検査しない
- トランジションは、tokens.md に成分（`--duration-fast` / `--duration-default` / `--ease-default`）を置き、shorthand をその合成にする。種類は 2 つのまま（ADR-003 の閉じたスケールに段を足さない）

### Consequences
- 良い点: 許容リストの各項目が tokens.md の文と 1 対 1 になり、検査の判定と文書が食い違わない
- トレードオフ: `lh` と `%` による寸法は、トークンを通らずに書ける（どちらも px を持たないので、スケールの外の中間値にはならない）

## ADR-015: ガードは Tailwind のコンパイラで生成物を作って読み、上書きの経路は className の文法で判定する

### Context
ADR-002 は、Tailwind がアプリのソースから生成したユーティリティを検査する。生成物を得る方法は、ビルド成果物を読む、テストの中でコンパイルする、の 2 つがある。前者はビルドを先に走らせる必要がある。また、Tailwind のスキャナは散文やコメントの単語も候補にするので、`container` のように、どこかに現れた単語が既定の値を持つユーティリティを生む（`container` はブレークポイントを幅として出す）。ADR-004 の上書きの経路は、生成されたセレクタの形からも className の文法からも判定できるが、セレクタの形は `group-*`・`has-*` の入れ子と見分けにくい。

### Decision
- テストの中で `@tailwindcss/node` の `compile` と `@tailwindcss/oxide` の `Scanner` を使い、`@tailwindcss/vite` と同じ入力（`index.css` と Vite のルート `apps/web`）から生成物を作る。どちらもルートの devDependencies に置く
- 検査するのは生成物の `@layer utilities` だけで、preflight・`@property`・`@layer properties` のフォールバックは Tailwind 自身の出力として外す
- `(--token)` の検査は、裸の `[var(--token)]` も同じ参照として扱う。トークンを含む式（`calc(100% + var(--space-xs))`）は対象にしない
- 上書きの経路は className の文法で判定する。`*`・`**`・`marker`・`selection` のバリアント、`&` の後ろに結合子がある任意バリアント、子を狙う `space-*`・`divide-*` を、`components/ui` の外で落とす。兄弟を狙う任意バリアントは `components/ui` の中でも落とし、`next-sibling:` には `mt-*` だけを載せる
- `container` は `index.css` の `@source not inline("container")` で生成を止める。横フレームの幅は `--sheet-*` が持つ

### Consequences
- 良い点: ビルドを待たずにユニットテストで完結し、失敗メッセージに className と書いたファイルを出せる。スキャナの誤検出で既定の値が CSS に混ざる経路も、同じ検査が捕まえる
- トレードオフ: 散文の単語が値を持つユーティリティを生んだら、テストが落ちる（言い換えるか `@source not inline` で止める）。文法の判定は、ここに挙げていない組み込みバリアントが他の要素を狙うようになったら追従が要る

## ADR-016: ボタンの段は文字サイズを 1 つにし、段ごとの箱はモックの多数派に寄せる

### Context
モックのボタンは同じ段でも画面ごとに寸法が違う。塗り大は、認証系の `.btn` が `--text-base`、空状態・エラーの `.action-btn` が `--text-sm` である。アウトラインは、認証系が `--pad-btn`・`--text-base`、設定とトピック詳細の `.outline-btn` が `--pad-btn-sm`・`--text-sm` である。テキストの段は、キャンセルとログアウトが中立色（`--color-neutral-600`）、タイムラインの `.empty-clear` が `--color-primary-dark` である。危険テキストの箱は、設定が `8px 12px`、ゴミ箱が `6px 8px` である。ADR-004 は段を閉じた union で受けるので、1 つの段に 1 つの形を決める必要がある。

### Decision
- 文字はすべての段で `--text-sm`・`--weight-medium` にする。段の差は箱と色だけで付ける
- 塗り大は `--pad-btn`、塗り小・アウトライン・テキストは `--pad-btn-sm` とし、この 4 段は `--radius-full` のピルにする
- テキストの段は中立色にする（キャンセル・ログアウト。ホバーで `--color-neutral-50` の面）。`.empty-clear` はこの段に寄せる
- 危険テキストは設定の箱（`--space-sm` × `--space-md`、`--radius-sm`）にし、フォーカスリングは `--color-focus-danger` にする
- 全幅は段に持たせない。縦並びの flex のラッパーが子を引き伸ばす

### Consequences
- 良い点: 認証シートの主ボタンと SSO のボタンが同じ文字サイズで並ぶ。段を選べば見た目が決まる
- トレードオフ: 認証系のボタンは、モックより文字と箱が一回り小さい（「同形」は構造の一致で、px の一致ではない。ADR-003）

## ADR-017: 行の区切り線はリストが持ち、行全体のリンクは末尾のジャンプ矢印まで含めて 1 つの形にする

### Context
モックの区切り線は兄弟セレクタ（`.doc-row + .doc-row::before`、`.trash-group + .trash-group`）で、`RowLink` のホバー面の張り出しに追従しない位置に引かれている。画面は行を `<ul>` / `<ol>` の `<li>` に並べている。兄弟を狙うバリアントは `next-sibling:mt-*` しか使えず（ADR-012・015）、画面から `<li>` に線を引くと画面ごとの再定義に戻る。行の下のエラーは、行の下余白を詰め、次の要素との間に `--pad-row` を空ける（`trash.html` の `:has(+ .row-error)`）。

### Decision
- `RowList`（`<ul>`、`ordered` で `<ol>`）を置き、`*:not-first:border-t` で項目の間にだけ線を引く。線は `<li>` の幅、つまり本文のカラム幅に乗り、`RowLink` の張り出しには追従しない
- `RowLink` は `createLink` で作り、行全体を 1 つのリンクとホバー面にして、末尾を `--color-primary` のジャンプ矢印に固定する
- `Row` は本文・`actions`・`error` の枠を持つ。`error` があれば行の下余白を詰めてエラーを行の下に全幅で置く。トピックに従属する行の段は `level="nested"` で持つ
- アイコンだけの操作は `IconButton` とリンク版の `IconButtonLink` にする。見た目は `placement`（ヘッダー / 行）× `tone`（中立 / 紫 / 危険）で決め、アクセシブルネームは `label` から付けて、渡された `aria-label` より優先する

### Consequences
- 良い点: 区切り線・ホバー面・エラーの位置が行の定義から決まり、画面は `<li>` を並べるだけになる
- トレードオフ: 行を `RowList` の外に並べると線が引かれない。行全体のボタン（履歴の版の行）と、新規作成の導線の行はこの 2 種に入らない（要るならステップ 11・13 で段を足す）

## ADR-018: 値 0 は任意値で書き、Markdown の組版は要素ごとのクラスとツリーの前処理で持つ

### Context
既定テーマの消去（ADR-001）で `--spacing` も消えるので、`p-0`・`mt-0`・`left-0` は何も生成しない。Markdown の組版は、モックでは `.doc-body p + p` などの子孫・兄弟セレクタで書かれ、ADR-012 はこれを要素ごとのユーティリティにすると決めている。ただし `components` の要素は親を見られないので、箇条書きの項目か番号付きの項目かを `li` の側で区別できない。コードブロックの `<code>` も、行内コードと同じ `code` の対応表を通る。

### Decision
- 値 0 は `lg:p-[0]` のように任意値で書く（許容リストの `0`）。0 を置かずに済むときは、先頭以外にだけ付ける形（`not-first:mt-*`）を選ぶ
- Markdown は `components/ui/Markdown` に置き、`variant`（`memo` / `document`）で要素からクラスへの対応表を選ぶ。各ブロックは自分の上余白を `not-first:` で持ち、値はモックの `em` を保つ（許容リストの `em` の余白）。ドキュメントの見出しの下余白だけは、tokens.md「余白の向き」の例外として残す
- 箇条書きのダッシュは、描画の前に rehype の段で `ul` 直下の `li` に印を付け、印のある `li` だけに付ける。タスクリストの項目には付けない
- コードブロックは `pre` の対応でツリーから文字を取り出して描き、行内コードの背景を通さない
- 継承するプロパティ（書体・文字サイズ・行間・色・折り返し）はルートの要素に置く

### Consequences
- 良い点: 子孫セレクタを使わずにモックの組版を写せ、番号付きの項目にダッシュが混ざらない
- トレードオフ: ステップ 17 で旧 CSS が消えるまでは、レイヤーの外にある旧 CSS（`.fog-memo p`・`a`・`:focus-visible`・`button:disabled` など）がユーティリティより優先され、タイムラインの本文とプリミティブのフォーカスリング・無効時の見た目は最終形にならない。値 0 を `p-0` と書いても落ちるテストは無く、見た目の欠落はブラウザ確認で見つける

## ADR-019: フォームの項目は FormGroup が id と配線を持ち、テキスト入力は 1 行と複数行の 2 つに畳む

### Context
入力欄の定義は 9 通りあり、ラベル・補足・項目のエラーと入力の結び付け（`aria-describedby` / `aria-invalid`）は画面ごとに id を手で組んでいる。モックの入力の箱は、フォームの `.form-input`（`--pad-input`、フォーカスリングは外側 2px）と、インライン編集の `.edit-field` / `.memo-edit`（`--space-sm` × `--space-md`、行間 `--leading-normal`、リングは内側 -2px）の 2 種類ある。補足（`.form-label-helper`）も、signup.html / password-reset.html はラベルの下の `--text-sm`・neutral-600、settings.html はラベルの横の `--text-xs`・neutral-400 と揺れている。数値・日付・タイトル・本文・コンポーザー・検索欄は、それぞれ別の箱を持つ。

### Decision
- `FormGroup` が id を作り、ラベル・補足・項目のエラーを描く。入力要素は render prop の `children` で受け、`id`・`aria-describedby`（エラー、補足の順）・`aria-invalid` を渡す。画面は文字列を渡すだけで、id を組まない
- 項目のエラーは `FormGroup` の `error` が入力の下に描く。`FormGroup` の縦並びに載らない入力（設定行の数値、ドキュメントのタイトル）のために、同じ見た目の `FieldError` を独立に出し、`id` を必須にする。どちらも `role="alert"` で、送信後に出たことを読み上げる
- テキスト入力は `TextField`（1 行、`--pad-input`、`--leading-tight`）と `TextAreaField`（複数行、`--space-sm` × `--space-md`、`--leading-normal`、2 行から内容に合わせて伸びる）の 2 つにする。`type` は文字入力の型に閉じ、`className`・`style`・`id`・`aria-describedby` は受けない
- フォーカスリングは両方とも外側 2px に揃える。補足は signup.html の形（ラベルの下、`--text-sm`・neutral-600）に寄せる
- ラベルを見せない項目（プレースホルダで意味が通るインラインのフォーム）は `hideLabel` で sr-only のラベルにする
- 数値・日付・タイトル・本文・コンポーザー・検索欄の箱は、それぞれの画面ステップが持つ（`FormGroup` の中に置けるものは置く）

### Consequences
- 良い点: ラベル・補足・エラーと入力の結び付けが、書き忘れられない形になる。9 通りの定義のうちフォームとインライン編集の分が 2 つの実装に畳まれる
- トレードオフ: settings.html の補足と、`.edit-field` の単一行（トピック名）は、モックと形が変わる（「同形」は構造の一致、ADR-003）。`aria-describedby` に画面が別の説明を足す経路は無い（要るなら `FormGroup` を直に使う）

---

## ADR-020: エラーは持ち場ごとに別のプリミティブにし、再試行の文言は呼び出し側が渡す

### Context
`fog-error` 1 クラスが、フォーム・項目・行・コンポーザーの失敗をすべて兼ねている。モックでは持ち場ごとに形が違う。フォームの先頭の `.error-message`（枠線つきの角丸の箱）、項目の下の `.field-error`（文字だけ）、行の下の `.row-error`（ピル、下線の「リトライ」）、コンポーザーの直上の `.composer-error`（影で浮くピル、白いピルの「再試行」）、画面に持続する `.inline-alert`（警告とエラー、エラーは白いピルの「再試行」）である。再試行の文言は、モックの中でも「リトライ」と「再試行」に揺れている。ADR-010 は、画面に持続する状態の説明（リセットメール送信後の案内）も `InlineAlert` に残すとしたが、モックの `.inline-alert` には警告とエラーしかなく、info の線画も無い。

### Decision
- `FormError`（フォームの先頭）・`FieldError`（項目の下、ADR-019）・`RowError`（行の下。`Row` の `error` に入れる）・`ComposerError`（コンポーザーの直上）・`InlineAlert`（画面に持続する知らせ）を別のコンポーネントにする。`ComposerError` は浮く唯一のエラーなので影を持ち、ラッパーの `pointer-events: none` から操作を取り戻す
- 再試行は `{ label, onRetry }` で受け、文言を呼び出し側が決める（モックの揺れは画面ステップの文言合わせで決める）。`InlineAlert` の再試行は `tone: "error"` のときだけ書ける union にする
- `InlineAlert` に `info` トーンを足す。`--color-info-bg` の地に `--color-primary-darker` の文字で、`role="status"` にする。グリフは持たない（Icon の閉じた集合に info を足すのはモックの作図が要る）。警告とエラーは `role="alert"`
- `InlineAlert` は次の要素との間隔を持たない（モックでも `--space-sm` と `--space-lg` に揺れている）。配置はラッパーが持つ

### Consequences
- 良い点: 失敗の出る場所が、選ぶコンポーネントで決まる。成功をインラインに書く受け皿が無いので、成功はトーストに寄る
- トレードオフ: info のインライン表示にはモックが無い。見た目の最終形はステップ 9（リセットメール送信後）で確かめる

## ADR-021: トーストはフレームのプロバイダが持ち、領域は常にマウントし、同じ文は置き換える

### Context
ADR-010 で、トーストはフレーム（`AppShell` / `AuthSheet`）がホストし、画面はフックで文言を渡すと決めた。出した要素がアンマウントされた後も残る必要がある。ホストの配置（コンポーザーの直上、無い画面では同じ下端）はステップ 6・7 が決める。同じ操作を続けて行うと（ゴミ箱の復元を 3 件）、同じ文のトーストが重なる。

### Decision
- `ToastProvider`（一覧とタイマー）・`ToastRegion`（表示の領域）・`useToast`（文言を渡すフック）・`Toast`（1 枚のピル）に分ける。一覧はプロバイダが持つので、出した画面がアンマウントされても消えない
- 領域は空でも常にマウントし、`role="status"`・`aria-live="polite"`・`aria-atomic="false"` で足されたトーストだけを読み上げる。トーストは操作を持たないので、領域ごと `pointer-events: none` にする
- 表示は 4 秒。同じ文が表示中に来たら、古い方を消して新しく足す（新しいノードなので読み上げ直され、時間も数え直す）。同時に出すのは 3 枚までで、古い方から消す
- プロバイダの外で `useToast` / `ToastRegion` を使うと throw する。フレームの外で描かれる画面は無い前提で、付け忘れを黙って失わない

### Consequences
- 良い点: 画面は `useToast()` を呼ぶだけで、位置と寿命はフレームが決める。連続する同じ操作でトーストが積み上がらない
- トレードオフ: `useToast` を使う画面の DOM テストは、プロバイダ（トーストを確かめるなら領域も）を含めて描く必要がある（ADR-010）。ホバーで消去を止める仕組みは無い（トーストが失う情報は無い、ADR-010）

## ADR-022: ポップオーバーメニューは項目を子要素で受けてフォーカスを管理し、確認ダイアログの 2 つのボタンはダイアログが持つ

### Context
メモ・トピック・トピック詳細の「…」メニューは、画面ごとに開閉とクリック外の検出を書いている。フォーカスは項目へ移らず、矢印キーでも動かない。項目にはボタン（編集・削除）とリンク（履歴）がある。トピック行のメニューは右クリックと長押しでも開く。確認ダイアログは `fog-*` のボタンを使い、モック（trash.html）の形と違う。モックのダイアログのボタンは、非破壊の確定が塗り（`fill-sm` と同じ）、破壊の確定がカード地に赤字と `--border-input` の枠、取消が中立色に枠である。後の 2 つは ADR-016 のボタンの段に無い。

### Decision
- `PopoverMenu` は、トリガー（`IconButton` の `more`・`sm`・`row`）と、トリガーの下端に `--space-xs` を空けて右端を揃えたカードを描く。項目は `PopoverMenuItem`（ボタン、`tone` は中立 / 危険）と `PopoverMenuLink`（`createLink` のリンク）の子要素で受ける
- 開くと先頭の項目へフォーカスを移し、矢印・Home・End で項目を巡回する。Escape は閉じてトリガーへ戻し、外側を押すか Tab で閉じる。項目を選ぶと、閉じてトリガーへフォーカスを戻してから `onSelect` を呼ぶ（確認ダイアログが閉じたときに戻る先が残る）
- 開閉は内部で持ち、`open` / `onOpenChange` を渡せば外から制御できる（右クリック・長押しで開く行）
- 危険の項目は赤字にするが、フォーカスリングは紫のままにする（`--color-focus-danger` は実行ボタン専用で、削除の項目は確認を開くだけ）
- `ConfirmDialog` は、破壊の確定と取消のボタンをダイアログ固有の見た目として自分の中に持ち、`Button` の段に足さない。非破壊の確定は `Button` の `fill-sm` を使う。箱の幅は横フレーム（`w-sheet`）を `--narrow-max` で頭打ちにする

### Consequences
- 良い点: メニューの開閉・フォーカス・クリック外の検出が 1 つの実装になる。ボタンの段は ADR-016 の 6 段のまま保てる
- トレードオフ: 項目は文言とグリフだけで、ほかの中身を持てない。ダイアログの 2 つのボタンは、`Button` の段が変わっても追従しない（ダイアログの見た目としてここで直す）

## ADR-023: ヘッダーの宣言は h1 の置き場所を持ち、戻るボタンは既定の戻り先へのリンクとして描く

### Context
ADR-006 は、ヘッダーをルートの `staticData` の宣言から描くと決めた。モックでは、戻る付きのページの `h1` が 2 通りある。メモ履歴はヘッダーの英語タイトルが `h1` で、ドキュメント閲覧・トピック詳細・ドキュメント履歴はシートの中の固有名（`doc-title` / `topic-title`）が `h1` になり、ヘッダーの英語タイトルは見出しではない。今の画面は固有名を `h2` で描いていて、`h1` へ上げるのは画面の載せ替え（ステップ 11〜13）である。この 3 ステップは並列に進み、ヘッダーのコンポーネントを共有する。戻るボタンは、アプリ内の履歴があれば戻り、無ければ既定の戻り先へ遷移する（ADR-006）。候補は、`onClick` だけを持つ `<button>` と、既定の戻り先を `href` に持つリンクの 2 つだった。

### Decision
- 戻る付きの宣言は `entity`・`back`（既定の戻り先。`routeTree.gen` の `to` の union で型付け）・`h1`（`"header"` / `"sheet"`）を持つ。`"sheet"` のとき英語タイトルは見出しでないラベルになる。このステップでは、どの画面もまだ `h1` を描かないので、全ルートを `"header"` で宣言する。画面が固有名を `h1` に上げるステップは、自分のルートの宣言を `"sheet"` に変える
- 既定の戻り先は、トピック詳細 → `/topics`、メモ履歴 → `/`、ドキュメント閲覧 → `/topics`、編集・履歴 → `/documents/$documentId`、新規 → `/topics/$topicId`。`$segments` は今のルートのパラメータで埋まる（ルーターの既定の動作）
- 戻るボタンは `IconButtonLink` で既定の戻り先へのリンクとして描き、修飾キーの無い左クリックで、アプリ内の履歴がある（`router.history.canGoBack()`）ときだけ遷移を止めて履歴を戻る
- 宣言の無いルートは、上位の形で `h1` を「fog」にする（`titleFor` の既定を引き継ぐ）。本番の `_app` 配下は全ルートが宣言し、DOM テストがそれを確かめる。ステップ 7 で `_sheet` へ移る 2 ルート（AI クライアント認可・リセット完了）も、移るまではアプリシェルの中に出るので上位の形で宣言する

### Consequences
- 良い点: ヘッダーを共有する並列のステップが、ヘッダーのコンポーネントに触れずに自分のルートの宣言だけで `h1` の置き場所を変えられる。戻るボタンはハイドレーション前と新しいタブでも既定の戻り先へ進む
- トレードオフ: ステップ 11〜13 が済むまで、戻る付きのページの `h1` は英語の対象名で、固有名は `h2` のまま。ステップ 7 で移る 2 ルートの宣言は、移動と同時に不要になる

## ADR-024: トーストの領域はシートの列の下端に浮かせ、コンポーザーは同じドックへポータルで差し込む

### Context
ADR-021 は、トーストの領域の配置をステップ 6・7 に委ねた。timeline.html の状態例では、トーストはコンポーザーの直上に同じ中央軸で出て、コンポーザーの無い画面では同じ下端に出る。投稿失敗（`ComposerError`）と重なるときは、失敗がコンポーザーの直上に残り、トーストはその上に積む。コンポーザーを持つのは画面（ステップ 10）で、領域を持つのはフレームである。

### Decision
- `AppShell` は、ヘッダーとシートの列（サイドバーの右）の下端に、`--space-safe-b-xl` の高さで浮くドックを置く。ドックは縦並びの flex で、上から `ToastRegion`、画面が差し込む枠の順に並び、ドック自体は `pointer-events: none` にする
- 画面は `BottomDock` で、自分の浮く要素（コンポーザーと投稿失敗）をこの枠へポータルで差し込む。差し込んだ要素が操作を取り戻す（ADR-020）
- ヘッダーの操作スロットへの `HeaderActions` と同じく、ポータルはマウント後に張り、シェルの外で使うと throw する。シェルの外で描かれる画面は無い前提で、差し込み忘れを黙って失わない
- ドックは列の中の絶対配置なので、中央軸は列の中央、つまりシートの中央になる

### Consequences
- 良い点: トーストの位置が、コンポーザーの有無と高さに追従する。画面はトーストの位置を知らない
- トレードオフ: コンポーザーはハイドレーション後に出る（SSR の HTML に含まれない）。`BottomDock` を使う画面の DOM テストは `AppShell` を含めて描く必要がある。ステップ 10 が差し込むまでは、タイムラインのコンポーザーは旧 CSS の固定配置のままで、トーストの領域と重なりうる（トーストを出す画面はまだ無い）

## ADR-025: スクロールの基準はシートの要素にし、画面へは ref のコンテキストで渡す

### Context
シートをスクロールコンテナにしたので、ウィンドウは動かない。スクロールに関わる既存の実装は 3 つある。ルーターのスクロール復元と画面遷移時の先頭へのリセット、タイムラインの無限スクロール（`IntersectionObserver`、`rootMargin: 200px`）、指定メモ位置と日付移動の `scrollIntoView` である。`IntersectionObserver` の既定の root はビューポートで、`rootMargin` はビューポートにしか効かない。シートの中の番兵は、シートのスクロールポートで切り取られてから判定されるので、先読みの 200px が失われる。

### Decision
- シートの `<main>` に `data-scroll-restoration-id="app-sheet"` を置き、ルーターの `scrollToTopSelectors` も同じ値から組む（`components/layout/sheet.ts`）。ルーターはこの属性の付いた要素のスクロール位置を記録・復元する
- `AppShell` はシートの ref をコンテキストで配り、画面は `useSheetScrollContainer()` で受ける。シェルの外では `current` が `null` で、`IntersectionObserver` はビューポートを root に読む
- タイムラインの番兵は、シートを root にして観察する
- `scrollIntoView` は最も近いスクロールコンテナを動かすので、変えない

### Consequences
- 良い点: 復元・リセット・先読み・位置指定のすべてが、同じ 1 つの要素を基準に動く（ブラウザで確認した）
- トレードオフ: ウィンドウがスクロールしないので、モバイルブラウザのアドレスバーはスクロールで畳まれない（モックの構造どおり）。スクロール位置を扱う実装を足すときは、ウィンドウではなくこのコンテキストを使う

## ADR-026: シートの内側余白は、上・左右と本文幅をシェルが持ち、下だけを画面が持つ

### Context
モックの `.inner` は、上 `--space-2xl`・左右 `--space-lg`（sm 以上で `--space-2xl`）・`max-width: var(--content-max)` がどの画面でも同じで、下だけが画面で違う（通常 80px、コンポーザーを持つタイムラインは 150px。tokens.md の `--space-sheet-end` / `--space-sheet-end-composer`）。実装では、各画面が旧 CSS の `fog-content`（ルートのラッパーや、設定・ゴミ箱の画面の根）と `fog-timeline` で内側余白を丸ごと自前で持っていた。候補は (a) シェルが全部持ち、下の段をルートの `staticData` で宣言する、(b) シェルが上・左右と本文幅を持ち、下は画面が持つ、の 2 つだった。

### Decision
(b) を採る。
- `AppShell` はシートの中に本文のカラム（`mx-auto max-w-content px-lg pt-2xl sm:px-2xl`）を置き、画面をその中に描く。カラムは下の余白を持たない
- 下の余白は、画面がルートのコンポーネントの根で持つ。`_app` 配下の各ルートは `pb-sheet-end`、タイムラインは `pb-sheet-end-composer` のラッパーでスケルトンと本体を包む
- 画面が自前で持っていた同じ余白（`fog-content`・`fog-timeline` のクラスの付与）は外す。旧 CSS の規則そのものはステップ 17 まで残る。汎用の `RoutePendingFallback` も、フレームと二重になる `p-md`・`max-w-content` を外す
- 認証シート（`AuthSheet`）はスクロールしないので、この分担に入らない。上下対称の余白をカードが 4 辺とも持つ（design/index.md「余白と区切り」）

### Consequences
- 良い点: 上・左右と本文幅が 1 箇所で決まり、ヘッダーの横フレームと同じ定義から来る。コンポーザーを避ける分は、コンポーザーを持つ画面の側で読める
- トレードオフ: 画面が下の余白を付け忘れても検出されない（最終行がシートの下端に張り付き、ブラウザ確認で見つける）。この限界は docs/test.md に書く。エラー表示（ルートの `errorComponent`）は下の余白を持たない（ステップ 8 で基準形に置き換える）

## ADR-027: 認証シートの枠とロックアップはフレームが描き、画面の見出しは `AuthSheetTitle` で描く

### Context
ADR-008 で認証シートの 5 画面を `_sheet` に集めた。ログイン・登録・パスワードリセット・AI クライアント認可のフォームは、`<main class="fog-auth">` と `fog-auth-sheet` のカードとロックアップを自前で描いていて、見出しの見た目は旧 CSS の `.fog-auth-sheet h1` にぶら下がっていた。リセット完了は、アプリシェルのヘッダーが描く sr-only の `h1` しか持っていなかった。ガードの共有（ADR-008）は、ルートの `beforeLoad` が同じ関数を指すかどうかで確かめられる。

### Decision
- `AuthSheet` がカード（`<main>`）・縦横中央の配置・ロックアップ・トーストのホストを持つ。4 つのフォームは自前の `main`・カード・ロックアップを外し、中身（`aria-labelledby` の `section` から下）だけを描く。中身の載せ替えはステップ 9 に残す
- モックの 4 画面に共通する `.page-title` を `AuthSheetTitle`（`components/layout/AuthSheet`）にし、フォームの `h1` とリセット完了の見出しはこれで描く。リセット完了はヘッダーを失うので、同じ文言「パスワードを再設定しました」を見える `h1` にする（文言をモックに合わせるのはステップ 9）
- ガードは `presentation/authGuard.ts` の `requireSessionBeforeLoad` を `_app` と `_sheet/_authenticated` の `beforeLoad` にそのまま渡す（包んだ関数にしない）。DOM テストが本番のルートツリーで、認証済みの 2 画面と `_app` 配下の全画面の祖先にこの関数があること、ほかの 3 画面の祖先に無いこと、これを持つレイアウトが 2 つだけであることを確かめる。ガードが `noStoreMiddleware` 付きの `readAuthStateFn` を通ることは、ユニットテストが確かめる
- 入れ子のガードの名前は `_authenticated` にする

### Consequences
- 良い点: 認証シートの枠とロックアップが 1 実装になり、画面がどの枠に出るかがルートツリーだけで決まる。ガードを包んだりコピーしたりすると、DOM テストが落ちる
- トレードオフ: ステップ 9 までは、説明文（`fog-auth-description`、旧 CSS の `margin: 0`）が見出しの直下に詰まって出る（ステップ 9 で説明文ごと撤去する）。レスポンスの `Cache-Control` そのものはテストせず、ブラウザ確認に頼る

## ADR-028: 404 はどのルートも `notFoundComponent` を持たずに既定へ任せ、未知の URL はルートのコンポーネントが認証シートで包む

### Context
ADR-009 は、`_app` 配下の子ルートの not found をアプリシェル内に、未知の URL を認証シートの枠に出すと決めた。ルーターは、ローダーが投げた `notFound()` を、投げたルートから上へたどって最初に `notFoundComponent` を持つルートで描く（`router-core` の `getNotFoundBoundaryIndex`）。上に 1 つも無ければ、投げたルート自身が既定の 404 を描く。そのため `__root` に認証シートで包んだ `notFoundComponent` を置くと、子ルートの 404 まで `__root` へ吸い上げられ、アプリシェルの外に出る。また既定の `notFoundMode: "fuzzy"` では、未知の URL（`/topics/x/nowhere`）でも接頭辞が合ったレイアウト（`_app`）が not found を受け、アプリシェルの中に出る。

### Decision
- どのルートも `notFoundComponent` を宣言しない。ルーターの `defaultNotFoundComponent` に `NotFound` を置き、子ルートの `notFound()` はそのルート自身が親のフレームの中で描く
- ルーターを `notFoundMode: "root"` にし、未知の URL は常に `__root` で受ける
- `__root` のコンポーネントは、ルートのマッチが global not found のときだけ `<Outlet />` を `AuthSheet` で包む。`Outlet` はそこで既定の `NotFound` を描く
- `__root` は `shellComponent` に `<html>` の枠を持ち、`errorComponent` は `_app`・`_sheet` と同じ `AuthSheetRouteError` にする
- DOM テストが、`notFoundComponent` を宣言するルートが無いこと、`errorComponent` を宣言するのが `__root`・`_app`・`_sheet` の 3 つだけで、どれも `AuthSheetRouteError` であることを本番のルートツリーで確かめる

### Consequences
- 良い点: 子ルートの 404 はそのフレームに、未知の URL は接頭辞に関係なく認証シートに出る。ルートを足しても 404 の付け忘れも取り違えも起きない
- トレードオフ: 未知の URL の枠は `notFoundComponent` ではなくルートのコンポーネントの分岐で決まる。ルート固有の 404 が要るルートは、自分に `notFoundComponent` を足すと、その下の子ルートの 404 もそこへ吸い上げる

---

## ADR-029: 認証シートの枠のエラーと 404 は、見た目を変えずに一文を `h1` にする

### Context
steps.md ステップ 8 の申し送りで、認証シートの枠に出るエラーと 404 には見出しが無いと指摘された。アプリシェルはヘッダーが常に `h1` を描く（ADR-006）が、認証シートの枠は見出しを描かず、画面の `AuthSheetTitle` が `h1` になる（ADR-027）。エラーと 404 は画面の代わりに描かれるので、認証シートでは `h1` が無いページになる。認証シートに出るのは、`__root`・`_app`・`_sheet` 自身の失敗（`AuthSheetRouteError`）、未知の URL（ADR-028）に加えて、`_sheet` の子ルートの失敗（既定の `RouteError` が `_sheet` の `Outlet` に出る）である。最後のものは既定のコンポーネントなので、props で見出しの有無を渡せない。

### Decision
- 一文を `h1` にする。見た目は変えない（`EmptyState` の `asPageHeading` は、段落と同じクラスを `h1` に付ける。preflight が見出しの文字サイズとウェイトを継承にしている）
- `h1` を描くのが枠か画面かを、`components/ui/PageHeading` のコンテキスト（`"frame"` / `"screen"`、既定は `"frame"`）で配る。`AuthSheet` がカードの中を `"screen"` にし、`RouteError` と `NotFound` はこれを読んで一文を `h1` にする
- アプリシェルでは `"frame"` のままで、一文は段落のまま（ヘッダーの `h1` と二重にしない）

### Consequences
- 良い点: 認証シートに出るエラーと 404 は、どの経路で出ても `h1` を 1 つ持つ。見た目はモックの状態例のまま
- トレードオフ: 一文の要素が、置かれたフレームで変わる。`EmptyState` を直に使う画面の空状態は、コンテキストを読まないので段落のまま

## ADR-030: 再試行の押下中の状態は `useTransition` ではなく素の state で持ち、旧 CSS の `a` の色は base 層へ移す

### Context
`RouteError` の再試行は `router.invalidate()` を待つ間ボタンを無効にする。`useTransition` で包むと、ブラウザ（`vite dev` と本番ビルドの両方）で、再試行がまた失敗したとき、読み込みが終わった後も保留の状態が下りず、ボタンが無効のまま残った（jsdom では再現しない）。また、`NotFound` はリンク版のボタン（`ButtonLink`）を画面に出す最初の場所で、レイヤーの外にある旧 CSS の `a { color: var(--color-primary-dark) }` がユーティリティの `text-text-inverse` に勝ち、塗りのボタンの文字が地と同じ色で見えなかった（ADR-018 が挙げた、旧 CSS がユーティリティに勝つ経路の 1 つ）。旧 CSS はステップ 17 まで残り、ステップ 9〜16 の画面も `ButtonLink`・`RowLink` を使う。

### Decision
- 再試行の押下中は `useState` で持ち、`router.invalidate()` の後に `finally` で下ろす。理由はコードのコメントに書く
- `app.css` の `a` の規則だけを `@layer base` に入れる。クラスの無いリンクと `fog-*` の規則（レイヤーの外）は今の色のまま、色のユーティリティを持つリンク（`ButtonLink`・サイドバーのリンクなど）はユーティリティが勝つ。旧 CSS のほかの規則には触らない

### Consequences
- 良い点: 再試行が続けて失敗しても、もう一度押せる。リンク版のボタンの文字が見え、サイドバーのリンクも宣言どおりの中立色になる
- トレードオフ: 押下中の表示は遷移に乗らない。保留が下りない原因は特定していない（DOM テストは jsdom で押さえ、ブラウザでの保留は docs/test.md に限界として書いた）。旧 CSS の `button` の `font: inherit` や `:focus-visible` は残り、再試行のボタンの文字サイズとフォーカスリングはステップ 17 まで最終形にならない（ADR-018）
