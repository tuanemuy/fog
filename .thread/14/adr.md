# 設計判断 — Issue #14

## ADR-001: 一覧に並ぶ行は窓の届く範囲で窓が決め、保存結果は行を足さない

### Context

`TimelineBoard` は、ローダーの窓（`initial.items`）とスクロールで読み込んだページ（`loaded`）を `mergeTimeline` で合わせて一覧にしている。編集の保存結果（`onSaved`）も `loaded` に足していたので、絞り込み中に一致しなくなったメモが、再取得した窓に無くても `loaded` から一覧に残った。

`onSaved` が担っていた役目は、`router.invalidate()` が終わってから窓の RSC が届くまでの間、編集した行に保存した本文を出すこと（`Deferred` は届くまで古い中身を出し、`MemoEntry` の `useOptimistic` は action が終わると外れる）。

契約の読みで、窓とスクロールで読み込んだページの両方にある行（窓が下にずれた後に生じる）を一致から外すと、窓から消えても `loaded` から残ることが分かった。

### Decision

- 保存結果は `saved`（id → `MemoView`）に分けて持ち、`applySaved` で一覧が持つ行に重ねるだけにする。版の大きいほうが勝ち、同じ版なら行が勝つ。行を足さない
- 一覧の行は `timelineRows(initial, loaded)` で決める。`windowCovers` が窓の届く範囲（先頭の行から末尾の行まで、両端を含む。カーソルを持たない端の向こう側を含む）を判定し、その範囲では窓に無い `loaded` の行を落とす。窓とページの両方にある行は `mergeTimeline` の版の規則のまま
- 窓が届かない範囲の `loaded` の行は、再取得されないので残す（#14 に残し、コメントで追う）

退けた案:

- `onSaved` を「`loaded` にある行だけ書き換える」にする: 窓の行は再取得が届くまで古い本文に戻る（AC-5 が落ちる）
- 保存結果は `loaded` に足したまま、`windowCovers` の範囲の規則だけで落とす: 編集した行が窓の新しい側の端（`/?date=&q=` の着地点など）で、再取得した窓の先頭がそれより古くなると、行は窓の範囲から外れて `loaded` から残る
- クライアントでキーワードの一致を判定する: 一致の規則はアダプター（`memoRepository.ts` の `LIKE … ESCAPE`）が持ち、1 つの規則が 2 か所に分かれる
- 再取得のたびに `loaded` を捨てる: スクロールで読み込んだページを再取得でも保つ設計（`docs/frontend_implementation_example.md`）に反する

### Consequences

- 窓が届かない範囲の行を絞り込み中に編集して一致しなくなっても、行は残る。直すにはスクロールで読み込んだページを読み直す手段が要る（起票の下書きの 1.・2.）
- `saved` は保存のたびに増え、island が残る間（同じ URL の間）は消えない。1 件あたり 1 つの `MemoView` で、版が窓に追いつくと効かなくなるだけで害はない

## ADR-002: 窓を受け取るたびに `loaded` を刈り込み、保存結果は `loaded` に足すままにする

### Context

差分の読み 1 の反例で、ADR-001 の 2 点が崩れた。

- 描画のたびに今の窓で `loaded` を絞る形（`timelineRows`）では、落とした行が `loaded` に残る。後の窓が届く範囲を狭めると（別のクライアントが一致を投稿し、窓の古い側の端が新しい側へ動くなど）、落とした行が一致しない本文のまま一覧に戻る
- ADR-001 が「保存結果を `loaded` に足したまま範囲の規則だけで落とす」案を退けた理由（編集した行が窓の新しい側の端で、再取得した窓の範囲から外れる）は、リポジトリが返す窓では起きない。着地点が窓の新しい側の端になるのは `newerCursor` が null のときだけで（`memoRepository.ts` の `findTimelineAround`）、そのとき外れた後の窓も `newerCursor` が null で、範囲は新しい側へ開いている。編集した行は窓の中にあったので、外れた後の窓も必ずその位置に届く

### Decision

- 変える前の案: 保存結果を `saved` に分けて `applySaved` で重ね、描画のたびに `timelineRows` で今の窓に絞る
- 変えた後の案: `onSaved` は変更前のまま `loaded` に足す。ローダーが窓を渡すたびに 1 回、`pruneToWindow(initial, loaded)` で `loaded` から、窓が届く範囲にあって窓に無い行を取り除く。前に刈り込んだ窓を状態に持ち、違えば描画中に `setLoaded` する（props の変化で状態を直す React の形）
- 変えた理由: 落とした行を状態から消すので、後の窓が範囲を狭めても戻らない。保存結果の置き場が `loaded` 1 つに戻り、版の規則は `mergeTimeline` の 1 か所だけになる（`applySaved` が同じ規則を 2 か所目に持っていた）

### Consequences

- 刈り込みは窓の受け取りごとに 1 回で、窓を受け取った後に読み込んだページの行は次の窓まで刈り込まれない。ページは窓の端のカーソルから外へ読むので、受け取った窓の範囲には入らない
- 窓が届かない範囲の行は残る（ADR-001 の Consequences のまま）

## ADR-003: 保存結果は行を足さない置き場に戻し、窓の受け取りごとの刈り込みと組み合わせる

### Context

差分の読み 2 の反例 N1: 窓の古い側の端（古い側のカーソルあり）にある行 B を一致しない本文に編集するのと重なって、別のクライアントが一致を投稿すると、再取得した窓は B の手前で終わり、B の位置に届かない。ADR-002 の形では `onSaved` が B を `loaded` に入れているので、刈り込みが B に届かず、B が一覧に残る。ADR-002 の Context の「編集した行は窓の中にあったので、外れた後の窓も必ずその位置に届く」は、この手順で成り立たない（反例 N2）。

### Decision

- 変える前の案（ADR-002）: `onSaved` は保存結果を `loaded` に足し、窓の受け取りごとに `loaded` を刈り込む
- 変えた後の案: 保存結果は `saved` に持ち、`overlaySaved` で一覧が持つ行に `mergeTimeline` の規則で重ねる。行は足さない。窓の受け取りごとの刈り込み（`pruneToWindow`）は ADR-002 のまま残す
- 変えた理由: 窓にだけあった行は `loaded` に入らないので、外れた後は窓が運ばなくなった時点で消える（N1）。スクロールで読み込んだ行は刈り込みが `loaded` から取り除くので、後の窓が範囲を狭めても戻らない（差分の読み 1 の反例 1）。重ねる規則は `mergeTimeline` を呼ぶので、版の規則は 1 か所のまま（差分の読み 1 の反例 8）
- この判断は保存結果を足さない → 足す → 足さないと 2 度覆した。ユーザーに聞く場面で、代行して進めた（`plan.md` の「ユーザーの答え」）

### Consequences

- `saved` は保存のたびに積まれ、同じ URL の間は消えない。行に重なるのは版が行より大きいときだけで、窓が追いつけば効かない
- 窓が届かない範囲の行は残る（ADR-001 の Consequences のまま）

## ADR-004: 保存結果は変更前のまま `loaded` に足す（ADR-002 に戻す）

### Context

差分の読み 3 の反例 1・2: ADR-003 の形（保存結果は行を足さない）では、窓の端の行を編集するのと重なって別のクライアントが投稿すると、再取得した窓はその行の手前で終わり、行は窓にも `loaded` にも無くなる。一致したままの編集（絞り込み中）でも、絞り込みなしの編集でも、編集した行が一覧から消える。変更前のツリーでは `onSaved` が行を `loaded` に入れていたので残った。

差分の読み 2 の反例 N1（ADR-002 の形で、窓の古い側の端の行を一致しない本文に編集するのと重なって投稿があると、行が残る）と、この反例は同じ状態の裏表である。どちらも、再取得した窓が編集した行の位置まで届かない。そのとき窓は、その行が一致するかどうかを答えていない。クライアントは一致を判定できない（規則はアダプターが持つ）ので、窓が届かない行を消すか残すかを、編集後の本文から決められない。

### Decision

- 変える前の案（ADR-003）: 保存結果は `saved` に持ち、一覧が持つ行にだけ重ねる
- 変えた後の案（ADR-002 に戻す）: `onSaved` は変更前のまま保存結果を `loaded` に足す。窓の受け取りごとの刈り込み（`pruneToWindow`）はそのまま
- 変えた理由: 再取得した窓が届かない位置の行は、窓の答えが無い行で、スクロールで読み込んだページだけにある行（R-1b）と同じ扱いにする。残すのは変更前と同じ振る舞いで、一致したまま・絞り込みなしの編集を壊さない。一致しなくなった場合に残るのは R-1b の範囲で、#14 に残して追う
- ADR-002 の Context の「編集した行は窓の中にあったので、外れた後の窓も必ずその位置に届く」は、編集と重なる別のクライアントの投稿があると成り立たない（差分の読み 2 の反例 N2）。そのときの行は窓が届かない範囲に入り、上のとおり R-1b として扱う
- この判断は 3 度覆した。ユーザーに聞く場面で、代行して進めた（`plan.md` の「ユーザーの答え」）

### Consequences

- 窓が届かない範囲の行は、スクロールで読み込んだページの行でも、窓がずれて届かなくなった編集した行でも、一致しなくなっても残る（R-1b。#14 へのコメントの下書き）
- 版の規則は `mergeTimeline` の 1 か所
- 窓が届かなくなるのは窓の末尾の行に限らない。編集と重なった投稿が k 件なら、窓の古い側の k 件が範囲から外れる。その行はどのページにも無く、編集の保存結果として `loaded` に残り、続きのページの読み込みでは刈り込まれない（刈り込みは窓の受け取りのときだけ）。これも R-1b に入る（差分の読み 4）
- R-1b の直し方は、ADR-001 の Consequences の「スクロールで読み込んだページを読み直す手段」では足りない。窓の範囲から外れた行はどのページにも無いので、窓の末尾から持っている行の末尾までをサーバーに答えさせる手段（読み直しか、1 件の一致を問うサーバー関数）が要る（起票の下書き 1.）
